# Часть XVI. Manifest V3 как платформа

# Глава 50. Manifest V3 Design Principles

В предыдущей главе мы рассмотрели Manifest V3 как платформу, а не просто как формат `manifest.json` и набор API.

Теперь необходимо перейти от **механизмов** к **принципам проектирования**.

API отвечают на вопрос:

> **Что может делать extension?**

Архитектурные принципы отвечают на другой вопрос:

> **Как extension должно быть спроектировано, чтобы эффективно и безопасно работать внутри браузера?**

Это принципиально важно.

Можно знать `chrome.runtime`, `chrome.storage`, `chrome.tabs`, `chrome.scripting` и при этом построить плохое extension.

И наоборот: разработчик, который понимает runtime model Manifest V3, способен построить простое, надёжное и эффективное расширение даже без большого количества API.

В этой главе мы сформулируем семь фундаментальных принципов:

```text
Least Privilege
Event-Driven Execution
Declarative Execution
Ephemeral Background Runtime
Isolated Execution
Browser-Managed Lifecycle
Platform-First Architecture
```

Их можно рассматривать как своеобразный **Manifest V3 architectural manifesto**.

---

# 50.1. Least Privilege

Первый принцип:

> **Extension должно получать только те права, которые действительно необходимы для его работы.**

Это классический принцип информационной безопасности:

> Principle of Least Privilege.

Он особенно важен для browser extensions, потому что extension потенциально получает доступ к пользовательскому браузеру, страницам, данным и действиям пользователя.

---

## 50.1.1. Permission — это capability

Permission следует рассматривать не как формальность в `manifest.json`, а как **capability**.

Например:

```json
{
    "permissions": [
        "storage"
    ]
}
```

означает:

```text
Extension
    ↓
Storage capability
```

А:

```json
{
    "permissions": [
        "tabs"
    ]
}
```

предоставляет другой класс возможностей.

Host permissions:

```json
{
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

определяют область доступа к web origins.

Таким образом:

```text
Permission
    ↓
Capability
    ↓
Potential impact
```

---

# 50.1.2. Чем меньше permissions, тем меньше attack surface

Представим два расширения.

### Extension A

```json
{
    "permissions": [
        "storage"
    ],
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

### Extension B

```json
{
    "permissions": [
        "tabs",
        "scripting",
        "cookies",
        "storage"
    ],
    "host_permissions": [
        "<all_urls>"
    ]
}
```

Даже если оба расширения реализуют одну и ту же функцию, архитектурно они сильно отличаются.

Extension B имеет гораздо большую поверхность доступа.

---

# 50.1.3. Не запрашивайте permission «на всякий случай»

Плохой подход:

```json
{
    "permissions": [
        "tabs",
        "scripting",
        "storage",
        "cookies",
        "history",
        "bookmarks"
    ]
}
```

если реально используется только:

```text
storage
```

Правильный подход:

```text
Начать с минимального набора
        ↓
Реализовать функциональность
        ↓
Обнаружить реальную необходимость
        ↓
Добавить permission
```

---

# 50.1.4. Permission как часть архитектуры

Permissions следует проектировать одновременно с архитектурой.

Например:

```text
Feature
   ↓
Required capability
   ↓
Required permission
   ↓
Required context
```

Если функция требует:

```text
read current page
```

необходимо определить:

* нужен ли Content Script;
* нужен ли host permission;
* можно ли ограничить конкретным доменом;
* нужен ли `activeTab`;
* требуется ли `scripting`.

То есть permission model нельзя проектировать после завершения приложения.

---

# 50.1.5. Минимальный доступ к страницам

Вместо:

```json
{
    "host_permissions": [
        "<all_urls>"
    ]
}
```

предпочтительнее:

```json
{
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

если функциональность действительно относится только к одному сайту.

Ещё лучше — если задача позволяет, использовать механизм временного доступа вроде `activeTab`, а не постоянный host access.

---

# 50.1.6. Least Privilege распространяется не только на Manifest

Принцип минимальных прав применяется ко всей архитектуре.

Например:

```text
Content Script
```

не должен получать больше ответственности, чем необходимо.

Плохая архитектура:

```text
Content Script
    ↓
all business logic
    ↓
all privileged operations
```

Лучше:

```text
Content Script
    ↓
DOM integration
    ↓
Message
    ↓
Service Worker
    ↓
Privileged operation
```

Каждый context получает только необходимые обязанности.

---

# 50.1.7. Главный вопрос

При проектировании каждого permission нужно спросить:

> **Что произойдёт, если этот capability будет скомпрометирован?**

Если ответ:

> «Почти ничего».

это хороший признак.

Если:

> «Расширение сможет читать и изменять все сайты пользователя».

permission model следует пересмотреть.

---

# 50.2. Event-Driven Execution

Второй фундаментальный принцип:

> **Extension должно реагировать на события, а не постоянно выполнять background code.**

Это особенно важно для Manifest V3 Service Worker.

---

## 50.2.1. Старое представление

Разработчик может интуитивно представить background runtime так:

```text
start
  ↓
background.js
  ↓
while running
  ↓
wait for events
  ↓
process
  ↓
continue forever
```

Это неправильная модель для Manifest V3.

---

## 50.2.2. Manifest V3 model

Правильнее:

```text
             Browser
                │
              Event
                │
                ▼
         Service Worker
                │
             Handler
                │
             Execute
                │
                ▼
             Finish
                │
                ▼
        Runtime may stop
```

Service Worker является **event-driven runtime**.

---

# 50.2.3. Events становятся точками входа

Например:

```javascript
chrome.runtime.onMessage.addListener(
    handleMessage
);
```

или:

```javascript
chrome.tabs.onUpdated.addListener(
    handleTabUpdate
);
```

или:

```javascript
chrome.commands.onCommand.addListener(
    handleCommand
);
```

Каждый handler является entry point.

---

# 50.2.4. Архитектура вокруг событий

Вместо:

```text
Background Application
```

мы проектируем:

```text
Event
 ↓
Handler
 ↓
Command
 ↓
State change
 ↓
Side effect
```

Например:

```text
User presses shortcut
        ↓
commands.onCommand
        ↓
Command handler
        ↓
Query active tab
        ↓
Send message
        ↓
Content Script
```

---

# 50.2.5. Event-driven не означает «всё делать в callback»

Это важное уточнение.

Плохой код:

```javascript
chrome.tabs.onUpdated.addListener(() => {
    // 1000 lines
});
```

Event-driven architecture не означает:

> «Пишем огромные callbacks».

Лучше разделять:

```javascript
chrome.tabs.onUpdated.addListener(
    eventRouter.handleTabUpdated
);
```

а затем:

```text
Event
 ↓
Router
 ↓
Application service
 ↓
Domain logic
 ↓
Infrastructure
```

---

# 50.2.6. Event-driven architecture уменьшает runtime cost

Если extension не выполняет работу, runtime не должен постоянно работать.

Например:

```text
99.9% времени
    ↓
ничего не происходит
```

Тогда постоянный background runtime не нужен.

Вместо:

```text
CPU → background → idle → CPU → background
```

получаем:

```text
Browser
   ↓
sleep
   ↓
event
   ↓
extension
   ↓
work
   ↓
sleep
```

Это соответствует природе browser extension.

---

# 50.3. Declarative Execution

Третий принцип:

> **Если браузер способен выполнить логику декларативно, не следует без необходимости переносить эту работу в JavaScript runtime.**

Это один из наиболее важных концептуальных сдвигов Manifest V3.

---

# 50.3.1. Imperative подход

Imperative code описывает:

> **как** выполнить действие.

Например:

```javascript
if (request.url.includes("/ads/")) {
    blockRequest();
}
```

Extension должен:

```text
receive event
    ↓
start/execute JavaScript
    ↓
evaluate condition
    ↓
perform action
```

---

# 50.3.2. Declarative подход

Declarative model описывает:

> **что должно произойти при определённом условии.**

Например:

```text
IF URL matches /ads/
THEN BLOCK
```

Browser engine может выполнить это самостоятельно.

```text
Network request
      ↓
Browser engine
      ↓
Rule matching
      ↓
BLOCK
```

Extension JavaScript не требуется для каждого запроса.

---

# 50.3.3. Почему браузер может сделать это лучше

Browser engine уже контролирует:

* network stack;
* tab management;
* navigation;
* security;
* rendering;
* request processing.

Поэтому для некоторых операций естественнее:

```text
Extension
   ↓
declare intent
   ↓
Browser
   ↓
execute
```

чем:

```text
Browser
   ↓
start extension
   ↓
run JavaScript
   ↓
ask browser
   ↓
execute
```

---

# 50.3.4. Declarative execution как оптимизация

Это можно представить как:

```text
Imperative:

Event
 ↓
JS runtime
 ↓
Decision
 ↓
Action
```

против:

```text
Declarative:

Rule
 ↓
Browser engine
 ↓
Decision + Action
```

Второй вариант потенциально:

* быстрее;
* дешевле;
* безопаснее;
* менее зависим от lifecycle;
* проще масштабируется.

---

# 50.3.5. DNR как пример

`declarativeNetRequest` особенно хорошо демонстрирует этот принцип.

Вместо:

```javascript
onRequest(request => {
    if (matches(request)) {
        block();
    }
});
```

можно определить rule.

```text
Request
    ↓
Rule engine
    ↓
Match
    ↓
Block
```

Browser engine выполняет rule независимо от постоянного JavaScript background runtime.

---

# 50.3.6. Declarative APIs как новый уровень runtime

Это позволяет представить Manifest V3 следующим образом:

```text
Application JavaScript
        │
        ├── complex logic
        │
        └── UI
       
Declarative rules
        │
        └── browser-executable logic
```

То есть часть приложения фактически выполняется не extension runtime, а browser runtime.

---

# 50.3.7. Архитектурный вопрос

Для каждой функции стоит спрашивать:

> **Должна ли эта логика выполняться JavaScript-кодом extension или её можно выразить декларативным правилом?**

Это один из важнейших вопросов при проектировании современного extension.

---

# 50.4. Ephemeral Background Runtime

Четвёртый принцип:

> **Background runtime должен рассматриваться как временный, а не постоянно существующий процесс.**

Это фундаментальная особенность Service Worker в Manifest V3.

---

# 50.4.1. Нельзя рассчитывать на global state

Например:

```javascript
let currentUser = null;
let cache = {};
let activeJob = null;
```

Такой state существует только пока существует конкретный экземпляр Service Worker.

После остановки:

```text
Service Worker
     ↓
terminated
     ↓
memory lost
```

---

# 50.4.2. Persistent state

Данные, которые должны переживать restart:

```text
Settings
User preferences
Application state
Cached metadata
Queues
Identifiers
```

должны сохраняться в соответствующем storage.

Например:

```javascript
await chrome.storage.local.set({
    settings
});
```

---

# 50.4.3. Правильная модель

```text
Service Worker
│
├── ephemeral state
│       ↓
│     memory
│
└── persistent state
        ↓
      storage
```

---

# 50.4.4. Service Worker как orchestrator

Это приводит к интересной архитектуре.

Service Worker не должен быть:

```text
"вечным backend сервером"
```

Он скорее является:

```text
event orchestrator
```

То есть:

```text
Event
 ↓
Wake up
 ↓
Read state
 ↓
Perform operation
 ↓
Persist state
 ↓
Send result
 ↓
Finish
```

---

# 50.4.5. Идемпотентность

Ephemeral runtime повышает значение идемпотентности.

Например, если операция:

```text
PROCESS_ITEM
```

может быть запущена повторно, она должна безопасно переживать повторный вызов.

Вместо:

```javascript
counter++;
```

может понадобиться:

```javascript
if (!await isProcessed(id)) {
    await process(id);
    await markProcessed(id);
}
```

Это особенно важно для:

* asynchronous operations;
* retries;
* alarms;
* network operations;
* state synchronization.

---

# 50.4.6. Не проектируйте Service Worker как сервер

Обычный сервер:

```text
start
 ↓
run continuously
 ↓
accept requests
 ↓
run continuously
```

Service Worker:

```text
event
 ↓
wake
 ↓
execute
 ↓
sleep/terminate
```

Это совершенно разные runtime models.

---

# 50.5. Isolated Execution

Пятый принцип:

> **Различные execution contexts должны рассматриваться как изолированные среды.**

Это относится как к security, так и к архитектуре.

---

# 50.5.1. Content Script не является page script

Content Script работает рядом со страницей, но не является обычным JavaScript страницы.

Упрощённо:

```text
Web Page
│
├── Page JavaScript world
│
└── Content Script world
```

DOM при этом может быть общим объектом взаимодействия.

Но JavaScript environments различаются.

---

# 50.5.2. Почему isolation важна

Предположим, страница содержит:

```javascript
window.appState = {
    authenticated: true
};
```

Content Script не должен автоматически рассматриваться как часть доверенного page JavaScript.

Аналогично:

```javascript
window.someLibrary
```

страницы не должна автоматически определять внутреннюю архитектуру extension.

---

# 50.5.3. Isolation уменьшает конфликты

Страница может использовать:

```javascript
const $ = ...
```

или:

```javascript
window.app = ...
```

Extension может иметь:

```javascript
const app = ...
```

Изоляция JavaScript environments предотвращает множество конфликтов.

---

# 50.5.4. Но DOM остаётся границей взаимодействия

Именно поэтому ситуация сложнее:

```text
JavaScript environments
    ≠
DOM
```

DOM может быть общим пространством взаимодействия.

Например:

```javascript
document.querySelector(...)
```

может работать с элементами страницы.

Но JavaScript state страницы и extension state не становятся автоматически общими.

---

# 50.5.5. MAIN world

Иногда extension необходимо выполнять JavaScript в `MAIN` world.

Это должно рассматриваться как специальный случай, а не стандартный режим.

Причина проста:

```text
MAIN world
    ↓
более тесная интеграция со страницей
    ↓
меньше isolation
    ↓
больше security risks
```

Поэтому переход в MAIN world должен быть обоснован конкретной задачей.

---

# 50.5.6. Isolation как архитектурный boundary

Каждый context следует рассматривать как отдельный компонент:

```text
Popup
  ↕
Message
  ↕
Service Worker
  ↕
Message
  ↕
Content Script
  ↕
Page
```

Нельзя предполагать:

```text
global variable
```

между этими компонентами.

Нужно явно использовать:

```text
message
storage
port
DOM bridge
```

---

# 50.6. Browser-Managed Lifecycle

Шестой принцип:

> **Lifecycle extension контролируется браузером, а не самим extension.**

Это фундаментальное отличие browser extension от standalone application.

---

# 50.6.1. Extension не владеет процессом

В desktop application разработчик может контролировать:

```text
process start
process lifetime
threads
memory
shutdown
```

В extension:

```text
Browser
   ↓
controls runtime
```

Браузер решает, когда определённый context:

* создаётся;
* активируется;
* становится неактивным;
* закрывается;
* уничтожается;
* создаётся снова.

---

# 50.6.2. Lifecycle каждого context различается

Например:

### Popup

```text
open
 ↓
active
 ↓
close
```

### Content Script

```text
page
 ↓
injection
 ↓
execution
 ↓
navigation
 ↓
destroy
```

### Service Worker

```text
dormant
 ↓
event
 ↓
startup
 ↓
execute
 ↓
idle
 ↓
termination
```

### Side Panel

```text
open
 ↓
active
 ↓
background
 ↓
close
```

Поэтому невозможно использовать одну lifecycle strategy для всего extension.

---

# 50.6.3. Lifecycle-aware architecture

Хорошее приложение должно знать:

```text
What survives?
What disappears?
What can restart?
What must be persisted?
What must be reconstructed?
```

Например:

```text
Service Worker memory
       ↓
temporary

chrome.storage
       ↓
persistent
```

---

# 50.6.4. Restartability

Каждый background component должен быть способен начать работу практически с нуля.

Идеальная модель:

```text
Start
 ↓
Load required state
 ↓
Initialize services
 ↓
Handle event
```

а не:

```text
Start
 ↓
Assume previous memory still exists
```

---

# 50.6.5. Browser-controlled lifecycle как преимущество

На первый взгляд это ограничение.

Но оно даёт преимущества:

```text
Lower resource usage
Better browser control
Better isolation
Automatic suspension
Predictable event model
```

Браузер может оптимизировать ресурсы одновременно для десятков и сотен extensions.

---

# 50.7. Platform-First Architecture

Седьмой принцип объединяет все предыдущие:

> **Сначала проектируйте решение относительно возможностей Web Platform и Manifest V3, а затем добавляйте собственный runtime.**

Это особенно важно для разработчиков, привыкших к традиционным frontend frameworks.

---

# 50.7.1. Не начинайте с framework

Типичный подход:

```text
React
 ↓
Application
 ↓
Extension wrapper
```

или:

```text
Angular
 ↓
Application
 ↓
Extension wrapper
```

Это может работать, но заставляет browser extension подстраиваться под модель framework.

Platform-first подход предлагает обратное:

```text
Browser
 ↓
Web Platform
 ↓
Manifest V3
 ↓
Extension architecture
 ↓
Optional framework
```

---

# 50.7.2. Сначала Web Platform

Для каждой задачи нужно сначала спросить:

```text
Можно ли решить её через DOM?
```

```text
Можно ли использовать Fetch?
```

```text
Можно ли использовать IndexedDB?
```

```text
Можно ли использовать Web Components?
```

```text
Можно ли использовать ESM?
```

И только затем:

```text
Нужен ли extension API?
```

---

# 50.7.3. Затем Extension Platform

Если Web Platform недостаточно:

```text
Need browser tabs?
        ↓
chrome.tabs

Need extension messaging?
        ↓
chrome.runtime

Need persistent extension state?
        ↓
chrome.storage

Need injection?
        ↓
chrome.scripting
```

---

# 50.7.4. Затем Declarative APIs

После этого:

```text
Can this logic be declarative?
```

Например:

```text
Network filtering
     ↓
DNR

Page activation
     ↓
Declarative mechanism
```

---

# 50.7.5. И только потом собственный runtime

Если возможностей платформы недостаточно:

```text
Web Platform
      ↓
Extension APIs
      ↓
Declarative APIs
      ↓
Custom runtime
```

Это помогает избежать создания ненужной инфраструктуры.

---

# 50.7.6. Platform-first против framework-first

### Framework-first

```text
Framework
   ↓
Application
   ↓
Extension APIs
   ↓
Browser
```

### Platform-first

```text
Browser
   ↓
Web Platform
   ↓
Manifest V3
   ↓

   ↓

   ↓

```

Второй вариант лучше соответствует природе browser extension.

# 50.10. Seven principles как checklist

Перед публикацией extension полезно пройти следующий checklist.

### 1. Least Privilege

```text
Все ли permissions необходимы?
```

### 2. Event-Driven

```text
Есть ли постоянно работающий код,
который можно заменить event-driven execution?
```

### 3. Declarative

```text
Можно ли часть логики перенести
в declarative API?
```

### 4. Ephemeral Background

```text
Может ли Service Worker
начать работу с чистой памяти?
```

### 5. Isolated Execution

```text
Чётко ли определены boundaries
между contexts?
```

### 6. Browser-Managed Lifecycle

```text
Что произойдёт при restart,
suspension или destruction context?
```

### 7. Platform-First

```text
Используем ли мы возможности браузера
до добавления собственной инфраструктуры?
```

# 50.12. Что изменилось в мышлении разработчика

До изучения Manifest V3 разработчик может мыслить так:

```text
I have a JavaScript application.
How do I put it into a browser extension?
```

После изучения платформы мышление должно измениться:

```text
I have a browser capability to implement.
Which platform mechanism should own it?
```

Например:

```text

    ↓
Content Script

Browser event
    ↓
Service Worker

Persistent configuration
    ↓
Storage

Long-lived UI
    ↓
Side Panel

Keyboard command
    ↓
Commands

Network filtering
    ↓
Declarative Net Request

Page integration
    ↓
Content Script / Bridge

Privileged operation
    ↓
Service Worker
```

Это и есть переход от **API-oriented development** к **architecture-oriented development**.

# 50.13. Главный принцип: не бороться с платформой

Самая важная идея всей главы:

> **Хорошее Manifest V3 extension не пытается превратить браузер в собственную операционную систему. Оно использует браузер как runtime.**

Плохая архитектура:

```text
Browser
   ↓
Extension
   ↓
Own Runtime
   ↓
Own State
   ↓
Own Scheduler
   ↓
Own Event System
```

Хорошая архитектура:

```text
Browser
   ↓
Web Platform
   ↓
Manifest V3
   ↓
Extension Application
```

Собственный runtime должен появляться только там, где платформы действительно недостаточно.

# 50.14. Manifest V3 Design Manifesto

В итоге семь принципов можно сформулировать как короткий манифест.

### I. Least Privilege

**Запрашивай минимальные capabilities.**

### II. Event-Driven Execution

**Работай тогда, когда происходит событие.**

### III. Declarative Execution

**Передавай браузеру ту логику, которую браузер способен выполнить самостоятельно.**

### IV. Ephemeral Background Runtime

**Не рассчитывай на постоянное существование Service Worker.**

### V. Isolated Execution

**Рассматривай каждый execution context как отдельную среду.**

### VI. Browser-Managed Lifecycle

**Проектируй приложение так, чтобы браузер мог остановить и снова запустить его runtime.**

### VII. Platform-First Architecture

**Сначала используй Web Platform и Manifest V3, затем создавай собственную инфраструктуру.**

# 50.15. Итог главы

Manifest V3 — это не просто новая версия `manifest.json`.

Это изменение архитектурной модели browser extensions.

Старая интуиция:

```text
Extension
   =
Background JavaScript
+
Content Script
+
Popup
```

недостаточна.

Современная модель:

```text
                 Extension
                     │
              Manifest V3
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   Permissions     Contexts    Declarative
       │             │             │
       └─────────────┼─────────────┘
                     ▼
                 Events
                     │
                     ▼
                Messaging
                     │
                     ▼
                  Storage
                     │
                     ▼
                Lifecycle
                     │
                     ▼
                  Browser
```

А семь принципов задают правила проектирования:

```text
                    Manifest V3
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
 Least Privilege   Event-Driven     Declarative
        │                │                │
        ▼                ▼                ▼
   Isolation       Ephemeral SW    Browser Engine
        │                │                │
        └────────────────┼────────────────┘
                         ▼
               Browser-Managed Lifecycle
                         │
                         ▼
                Platform-First Design
```

**Именно эти принципы должны стать фундаментом архитектуры любого серьёзного Manifest V3 extension.**

Следующий шаг — научиться применять их не по отдельности, а **совместно при проектировании реальных приложений**: от определения requirements и permission model до выбора contexts, message protocol, state architecture и declarative runtime.
