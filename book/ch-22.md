# Глава 22. Tabs и Windows

После изучения Commands необходимо перейти к одному из центральных механизмов браузерных расширений — управлению вкладками и окнами.

Для обычного веб-приложения браузер в основном является средой выполнения:

```text
Browser
   ↓
Web application
```

Для extension браузер одновременно становится **объектом управления**:

```text
Extension
   ↓
Browser
   ├── Windows
   │     ├── Tabs
   │     └── Tabs
   │
   └── Windows
         ├── Tabs
         └── Tabs
```

Именно APIs `chrome.tabs` и `chrome.windows` позволяют extension понимать:

* какие окна существуют;
* какие вкладки открыты;
* какая вкладка активна;
* какой URL открыт;
* когда вкладка создана;
* когда она обновилась;
* когда пользователь переключился на другую вкладку;
* когда вкладка закрылась;
* как координировать работу нескольких вкладок.

Для сложного extension это уже не просто API.

Это **browser orchestration layer**.

---

# 22.1. Tabs API

`chrome.tabs` представляет API для работы с вкладками браузера.

Базовая модель:

```text
chrome.tabs
      │
      ├── query()
      ├── get()
      ├── create()
      ├── update()
      ├── remove()
      ├── move()
      ├── duplicate()
      │
      └── events
```

Основные задачи:

```text
Read tab
Create tab
Update tab
Close tab
Move tab
Find tabs
React to tab events
```

---

## Tab как объект

Вкладка представляется объектом `Tab`.

Упрощённо:

```javascript
{
    id: 123,
    windowId: 10,
    index: 2,
    active: true,
    pinned: false,
    url: "https://example.com/",
    title: "Example",
    status: "complete"
}
```

Не все поля всегда доступны.

Особенно важно помнить, что URL и другие чувствительные данные зависят от permissions и контекста.

Поэтому нельзя проектировать приложение так, будто `Tab` всегда содержит полный набор информации.

---

## `tab.id`

Один из важнейших идентификаторов:

```javascript
tab.id
```

Например:

```javascript
const tabId = tab.id;
```

Он используется во множестве других API:

```text
Tab
 │
 └── tab.id
       │
       ├── tabs.sendMessage()
       ├── scripting.executeScript()
       ├── tabs.update()
       └── tabs.remove()
```

То есть `tab.id` становится своеобразным **address** вкладки внутри extension runtime.

---

## `windowId`

У каждой вкладки есть:

```javascript
tab.windowId
```

Например:

```text
Window 10
 ├── Tab 101
 ├── Tab 102
 └── Tab 103
```

Тогда:

```text
tab.windowId = 10
```

Это позволяет связывать Tabs и Windows.

---

# `chrome.tabs.query()`

Один из наиболее часто используемых методов:

```javascript
const tabs =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });
```

Результат:

```javascript
[
    {
        id: 123,
        windowId: 10,
        active: true
    }
]
```

---

# Получение active tab

Типичный паттерн:

```javascript
async function getActiveTab() {

    const [tab] =
        await chrome.tabs.query({
            active: true,
            currentWindow: true
        });

    return tab;
}
```

Использование:

```javascript
const tab =
    await getActiveTab();

console.log(tab.id);
```

Это один из фундаментальных паттернов MV3.

---

# Почему `query()` возвращает массив

Даже если вы запрашиваете:

```javascript
active: true
```

результат — массив.

Поэтому:

```javascript
const [tab] =
    await chrome.tabs.query(...);
```

является обычным способом получения первого результата.

---

# Query как механизм поиска

`tabs.query()` позволяет не только получить active tab.

Например:

```javascript
const tabs =
    await chrome.tabs.query({
        pinned: true
    });
```

Получим pinned tabs.

Можно искать вкладки по различным критериям.

Например:

```javascript
const tabs =
    await chrome.tabs.query({
        windowId: 10
    });
```

Все вкладки конкретного окна.

---

# Поиск всех вкладок

```javascript
const tabs =
    await chrome.tabs.query({});
```

Это позволяет получить доступные extension вкладки.

Но использовать такой запрос без необходимости не стоит.

В production extension лучше получать только необходимые данные:

```text
query narrowly
```

вместо:

```text
query everything
```

---

# 22.2. Windows API

Если `tabs` работает на уровне вкладок, `chrome.windows` работает на уровне окон браузера.

Модель:

```text
chrome.windows
       │
       ├── get()
       ├── getCurrent()
       ├── getLastFocused()
       ├── getAll()
       ├── create()
       ├── update()
       ├── remove()
       │
       └── events
```

---

# Window как контейнер

Можно представить:

```text
Window
   │
   ├── Tab
   ├── Tab
   ├── Tab
   └── Tab
```

Поэтому:

```text
Window
   ↓
Tabs
```

---

# `window.id`

Например:

```javascript
const windowId =
    window.id;
```

Этот ID используется для управления конкретным окном.

---

# `chrome.windows.getCurrent()`

Можно получить текущее окно extension context:

```javascript
const window =
    await chrome.windows.getCurrent();
```

Например:

```javascript
console.log(
    window.id
);
```

---

# `getLastFocused()`

Можно получить последнее сфокусированное окно:

```javascript
const window =
    await chrome.windows.getLastFocused();
```

Это особенно полезно в background/service-worker сценариях.

---

# Получение всех окон

```javascript
const windows =
    await chrome.windows.getAll();
```

Это позволяет построить представление:

```text
Browser
│
├── Window 1
│   ├── Tab 1
│   ├── Tab 2
│   └── Tab 3
│
├── Window 2
│   ├── Tab 4
│   └── Tab 5
│
└── Window 3
    └── Tab 6
```

---

# Когда использовать Tabs, а когда Windows

Простое правило:

```text
Работа с конкретной страницей
        ↓
      Tabs
```

```text
Работа с browser window
        ↓
     Windows
```

Например:

### Tabs

```text
Read URL
Send message
Inject script
Navigate page
Close tab
```

### Windows

```text
Create window
Focus window
Resize window
Move window
Close window
```

# 22.3. Active tab

Понятие **active tab** является центральным для огромного количества extensions.

Пользователь смотрит на:

```text
┌─────────────────────────────┐
│ Tab 1 │ Tab 2 │ Tab 3       │
├─────────────────────────────┤
│                             │
│        Current page         │
│                             │
└─────────────────────────────┘
```

В каждый момент времени одна вкладка является активной в конкретном окне.

---

# Получение active tab

```javascript
const [tab] =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });
```

Это означает:

```text
current window
       ↓
active tab
```

---

# `currentWindow` и `windowId`

Есть два распространённых сценария.

### Текущее окно

```javascript
{
    active: true,
    currentWindow: true
}
```

### Конкретное окно

```javascript
{
    active: true,
    windowId: 123
}
```

Второй вариант используется, когда приложение уже знает, каким окном управляет.

---

# Active tab ≠ focused tab

Необходимо различать:

```text
active tab
```

и:

```text
focused window
```

Архитектурно:

```text
Browser
│
├── Window A
│   ├── Tab A1
│   └── Tab A2 ← active
│
└── Window B ← focused
    ├── Tab B1 ← active
    └── Tab B2
```

В каждом окне может существовать active tab, но только одно окно в данный момент обычно является сфокусированным.

Поэтому при проектировании browser-aware extension необходимо чётко понимать, что именно означает ваш термин **current**.

---

# Active tab как context

Для многих extension команд схема выглядит так:

```text
Command
   ↓
Active Window
   ↓
Active Tab
   ↓
Content Script
   ↓
Page
```

Например:

```text
Ctrl+Shift+A
      ↓
Analyze current page
```

---

# Почему нельзя хранить active tab в global variable

Плохой подход:

```javascript
let activeTabId;
```

и затем:

```javascript
activeTabId = 123;
```

Проблема в том, что Service Worker может быть остановлен.

Кроме того, active tab может измениться в любой момент.

Поэтому актуальное состояние браузера следует получать через API:

```javascript
const [tab] =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });
```

---

# 22.4. Tab lifecycle

Вкладка имеет собственный lifecycle.

Упрощённо:

```text
create
  ↓
loading
  ↓
complete
  ↓
update
  ↓
navigate
  ↓
loading
  ↓
complete
  ↓
close
```

Но реальная последовательность событий сложнее.

Главная идея:

> Вкладка — динамический объект.

Она может:

* появиться;
* изменить URL;
* изменить title;
* изменить статус загрузки;
* стать активной;
* перестать быть активной;
* переместиться;
* сменить окно;
* быть закрыта.

---

# `tabs.onCreated`

Когда создаётся вкладка:

```javascript
chrome.tabs.onCreated.addListener(
    (tab) => {

        console.log(
            "Created:",
            tab.id
        );
    }
);
```

---

# `tabs.onRemoved`

Когда вкладка закрывается:

```javascript
chrome.tabs.onRemoved.addListener(
    (tabId, removeInfo) => {

        console.log(
            "Removed:",
            tabId
        );
    }
);
```

Это особенно важно для очистки state.

---

# `tabs.onActivated`

Когда пользователь переключается на другую вкладку:

```javascript
chrome.tabs.onActivated.addListener(
    (activeInfo) => {

        console.log(
            "Active tab:",
            activeInfo.tabId
        );
    }
);
```

Объект обычно содержит:

```javascript
{
    tabId,
    windowId
}
```

---

# Activation event

Архитектура:

```text
User clicks Tab 2
       ↓
tabs.onActivated
       ↓
Service Worker
       ↓
Application
       ↓
Update state/UI
```

Например:

```text
Active tab changed
       ↓
Side Panel
       ↓
Load state for new tab
```

---

# 22.5. Navigation events

Одно из наиболее важных понятий — **navigation**.

Пользователь может:

```text
https://example.com
       ↓
https://example.com/page
```

или:

```text
https://example.com
       ↓
https://github.com
```

При этом `tab.id` может остаться тем же.

Это важный момент.

---

# Tab identity ≠ Page identity

Вкладка:

```text
tab.id = 123
```

может сначала показывать:

```text
example.com
```

а затем:

```text
github.com
```

Поэтому:

```text
Tab ID
```

не является идентификатором конкретного документа.

---

# `tabs.onUpdated`

Одно из основных событий:

```javascript
chrome.tabs.onUpdated.addListener(
    (tabId, changeInfo, tab) => {

        console.log(
            tabId,
            changeInfo,
            tab
        );
    }
);
```

Оно вызывается при изменениях вкладки.

---

# `changeInfo`

Например:

```javascript
{
    status: "loading"
}
```

или:

```javascript
{
    status: "complete"
}
```

или:

```javascript
{
    url: "https://example.com/new"
}
```

Поэтому нельзя воспринимать `onUpdated` как:

> «страница полностью загрузилась».

Это более общий механизм уведомления об изменениях tab state.

---

# Проверка URL

Например:

```javascript
chrome.tabs.onUpdated.addListener(
    (tabId, changeInfo) => {

        if (changeInfo.url) {

            console.log(
                "Navigation:",
                changeInfo.url
            );
        }
    }
);
```

Это позволяет реагировать на navigation.

---

# Проверка завершения загрузки

```javascript
chrome.tabs.onUpdated.addListener(
    (tabId, changeInfo) => {

        if (
            changeInfo.status ===
            "complete"
        ) {

            console.log(
                "Page completed:",
                tabId
            );
        }
    }
);
```

Но это всё ещё не означает, что:

> всё содержимое страницы гарантированно доступно в том состоянии, которое ожидает ваше приложение.

Современные сайты используют SPA routing, динамический DOM и асинхронные загрузки.

---

# SPA и navigation

Представим:

```text
GitHub
   ↓
React application
```

Пользователь переходит:

```text
/github
   ↓
/github/repository
```

без полной перезагрузки документа.

Поэтому extension, ориентированный на современные web applications, должен понимать разницу между:

```text
browser navigation
```

и:

```text
application-level navigation
```

---

# Content Script и navigation

Иногда правильная архитектура:

```text
tabs.onUpdated
      ↓
Service Worker
      ↓
Content Script
      ↓
observe page state
```

Content Script может наблюдать DOM и реагировать на изменения страницы.

---

# Tab state

Для сложного extension удобно иметь state:

```text
Application State
│
├── tab 101
│   ├── analyzed
│   └── result
│
├── tab 102
│   ├── analyzed
│   └── result
│
└── tab 103
    └── not analyzed
```

Но такой state нельзя просто держать в памяти Service Worker.

Нужно учитывать его ephemeral lifecycle.

---

# 22.6. Работа с несколькими вкладками

Теперь перейдём от одной вкладки к нескольким.

Это место, где browser extension превращается из простой page utility в **browser application**.

Например:

```text
Window
│
├── Tab A
├── Tab B
├── Tab C
└── Tab D
```

Extension может анализировать:

```text
Tab A
Tab B
Tab C
```

одновременно или последовательно.

---

# Получение всех вкладок окна

```javascript
const tabs =
    await chrome.tabs.query({
        windowId: windowId
    });
```

Затем:

```javascript
for (const tab of tabs) {

    console.log(
        tab.id,
        tab.url
    );
}
```

---

# Фильтрация вкладок

Например:

```javascript
const tabs =
    await chrome.tabs.query({
        windowId,
        pinned: false
    });
```

Можно строить собственную модель:

```text
All tabs
   ↓
Filter
   ↓
Relevant tabs
```

---

# Parallel processing

Если операции независимы:

```javascript
await Promise.all(
    tabs.map(
        tab => processTab(tab)
    )
);
```

Это позволяет обрабатывать несколько вкладок параллельно.

Но здесь нужно быть осторожным.

---

# Почему нельзя бездумно запускать сотни операций

Представим:

```text
100 tabs
   ↓
100 injections
   ↓
100 network requests
```

Можно получить:

* высокую нагрузку;
* rate limits;
* большое потребление памяти;
* множество сообщений;
* race conditions.

Поэтому production extension должен контролировать concurrency.

---

# Sequential processing

Иногда безопаснее:

```javascript
for (const tab of tabs) {

    await processTab(tab);
}
```

Это медленнее, но проще контролировать.

---

# Limited concurrency

Для больших extension часто нужен worker pool:

```text
100 tabs
   ↓
Queue
   ↓
┌────────┬────────┬────────┐
│ Worker │ Worker │ Worker │
└────────┴────────┴────────┘
```

Например, одновременно обрабатывать только несколько вкладок.

---

# Tab orchestration

Теперь мы подходим к главному понятию главы.

**Tab orchestration** — это координация операций над несколькими вкладками и окнами.

Например:

```text
User command
      ↓
Service Worker
      ↓
Find relevant tabs
      ↓
Process tabs
      ↓
Collect results
      ↓
Store results
      ↓
Update UI
```

---

# Пример: research extension

Пусть пользователь открывает:

```text
Tab A → article
Tab B → documentation
Tab C → GitHub
```

и нажимает:

```text
Ctrl+Shift+A
```

Extension:

```text
Command
   ↓
Get all relevant tabs
   ↓
┌─────────┬─────────────┬─────────┐
│ Article │ Documentation│ GitHub │
└─────────┴─────────────┴─────────┘
   ↓
Analyze
   ↓
Results
```

---

# Tab orchestration layer

Вместо того чтобы помещать всё в Service Worker:

```javascript
chrome.commands.onCommand.addListener(
    async command => {
        // 500 lines
    }
);
```

лучше выделить отдельный слой:

```text
Service Worker
      ↓
Tab Orchestrator
      ↓
Tab Operations
```

Например:

```javascript
class TabOrchestrator {

    async getActiveTab() {
        const [tab] =
            await chrome.tabs.query({
                active: true,
                currentWindow: true
            });

        return tab;
    }

    async getWindowTabs(windowId) {
        return chrome.tabs.query({
            windowId
        });
    }

    async processTab(tab) {
        // ...
    }
}
```

---

# Orchestrator как application service

Архитектура:

```text
Command
   ↓
Application Service
   ↓
Tab Orchestrator
   ↓
Chrome Tabs API
```

Это гораздо лучше масштабируется.

---

# Tab lifecycle manager

Для сложного приложения можно иметь отдельный менеджер:

```text
TabManager
│
├── track()
├── untrack()
├── activate()
├── navigate()
├── close()
├── process()
└── cleanup()
```

Но важно не превращать его в копию самого Browser Tabs API.

Его задача — **application-specific orchestration**, а не повторение API браузера.

---

# Таблица как состояние

Иногда полезно представить:

```text
Tab Registry

┌────────┬─────────────┬───────────┐
│ Tab ID │ URL         │ State     │
├────────┼─────────────┼───────────┤
│ 101    │ example.com │ ready     │
│ 102    │ github.com  │ analyzing │
│ 103    │ docs.com    │ complete  │
└────────┴─────────────┴───────────┘
```

Но registry должен быть либо:

* восстанавливаемым;
* persistent;
* либо вычисляться заново.

Нельзя предполагать, что память Service Worker будет жить бесконечно.

---

# Tab ID как ключ

Для временного runtime state удобно:

```javascript
const state =
    new Map();
```

например:

```javascript
state.set(
    tabId,
    {
        status: "analyzing"
    }
);
```

Но после termination Service Worker:

```text
Map
 ↓
lost
```

Поэтому важное состояние следует сохранять:

```text
Tab ID
   ↓
chrome.storage
```

---

# Но не сохраняйте всё подряд

Не нужно делать:

```text
every tab
every event
every DOM state
every temporary value
       ↓
storage
```

Нужно разделять:

```text
Ephemeral state
```

и:

```text
Persistent application state
```

---

# Navigation и state invalidation

Предположим:

```text
tab 123
URL = example.com/page1
```

Extension сохраняет:

```text
analysis = result A
```

Пользователь переходит:

```text
example.com/page2
```

Теперь результат A может быть недействительным.

Поэтому:

```text
Navigation
    ↓
Invalidate tab state
```

Это один из важнейших паттернов browser-aware applications.

---

# Например

```javascript
chrome.tabs.onUpdated.addListener(
    async (tabId, changeInfo) => {

        if (!changeInfo.url) {
            return;
        }

        await invalidateTabState(
            tabId
        );
    }
);
```

---

# Tab lifecycle как state machine

Можно представить:

```text
             create
               ↓
            loading
               ↓
            ready
               ↓
          ┌────┴────┐
          │         │
      navigate    close
          │         │
          ▼         ▼
       loading    removed
          │
          ▼
        ready
```

Для сложных extensions такая модель намного понятнее, чем набор разрозненных callbacks.

---

# Race conditions

Работа с несколькими вкладками создаёт race conditions.

Например:

```text
Tab A
   ↓
start analysis

Tab A
   ↓
navigate

Old analysis
   ↓
returns result
```

Теперь результат относится уже к старой странице.

---

# Решение: generation/version

Можно использовать navigation token:

```text
Tab A
generation = 17
```

После navigation:

```text
generation = 18
```

Если старый operation возвращает:

```text
generation = 17
```

он больше не актуален.

---

# Почему это важно

Без такой защиты:

```text
Old request
      ↓
New page
      ↓
Old result
      ↓
Wrong UI
```

С защитой:

```text
Old request
      ↓
generation 17
      ↓
page changed
      ↓
generation 18
      ↓
old result rejected
```

# Что должен делать Tab Orchestrator

Хороший orchestrator отвечает на вопросы:


# Browser Adapter

Можно создать:

```javascript
class TabsAdapter {

    async getActiveTab() {

        const [tab] =
            await chrome.tabs.query({
                active: true,
                currentWindow: true
            });

        return tab;
    }

    async getTabs(windowId) {

        return chrome.tabs.query({
            windowId
        });
    }
}
```

А application layer работает уже с:

```javascript
tabsAdapter.getActiveTab()
```

а не непосредственно с каждым вызовом Chrome API.

# Главные принципы главы

### 1. Tabs и Windows — разные уровни

```text
Window
  ↓
Tabs
```

---

### 2. `tab.id` — адрес вкладки внутри extension

Он используется для связи с другими APIs.

---

### 3. Active tab нужно получать динамически

Не полагайтесь на вечную глобальную переменную.

---

### 4. Tab lifecycle динамический

Вкладка может:

```text
create
update
activate
navigate
move
close
```

---

### 5. Navigation не означает смену `tab.id`

Одна вкладка может последовательно показывать множество документов.

```text
tab 123
   ├── page A
   ├── page B
   └── page C
```

---

### 6. `tabs.onUpdated` — это не просто "page loaded"

Это событие изменения состояния вкладки.

---

### 7. Состояние вкладки должно учитывать navigation

```text
Navigation
   ↓
invalidate state
```

---

### 8. Несколько вкладок требуют orchestration

```text
Tabs
 ↓
Queue
 ↓
Workers
 ↓
Results
```

---

### 9. Не храните критически важное состояние только в Service Worker

Worker ephemeral.

Persistent state должен иметь соответствующее хранилище.

---

### 10. Tab Orchestrator — application layer

Он должен координировать browser APIs, а не просто дублировать их.

# Заключение

`chrome.tabs` и `chrome.windows` являются фундаментом для превращения extension из инструмента, работающего с одной страницей, в **browser-aware application**.

Простейшее расширение может работать так:

```text
Action
 ↓
Active Tab
 ↓
Content Script
```

Но production-grade extension постепенно приходит к гораздо более сложной модели:

```text
                         Browser
                            │
                    ┌───────┴───────┐
                    │               │
                 Windows           Tabs
                    │               │
                    └───────┬───────┘
                            │
                     Service Worker
                            │
                     Tab Orchestrator
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
     Content Script     Application State   Side Panel
          │                 │                 │
          ▼                 ▼                 ▼
         DOM              Storage              UI
```

Именно здесь появляется важная концепция **browser orchestration**: extension уже не просто реагирует на события отдельной страницы, а управляет состоянием и взаимодействием между множеством браузерных объектов — окнами, вкладками, страницами и собственными extension contexts.

В следующей главе логично перейти к **Alarms и Scheduling**: если Tabs дают extension возможность управлять *где* выполняется работа, то Alarms позволяют определить *когда* эта работа должна выполняться.
