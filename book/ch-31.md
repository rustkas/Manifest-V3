# Часть XII. Продвинутая инъекция и интеграция со страницей

# Глава 31. Programmatic Injection

Content Scripts — один из центральных механизмов Manifest V3. В предыдущих главах мы рассмотрели автоматическую инъекцию через `content_scripts` в `manifest.json`.

Однако у расширения часто возникает другая задача:

> **не запускать Content Script автоматически на каждой подходящей странице, а внедрять код именно тогда, когда это необходимо.**

Для этого Manifest V3 предоставляет API:

```javascript
chrome.scripting
```

Главный метод:

```javascript
chrome.scripting.executeScript()
```

С его помощью Service Worker или другой extension context может программно внедрить JavaScript в конкретную вкладку и, при необходимости, в определённые frames.

Архитектурно это выглядит так:

```text
User action / Event
        ↓
Service Worker
        ↓
chrome.scripting
        ↓
Target Tab
        ↓
Content Script
        ↓
Page DOM
```

Programmatic Injection особенно важен для расширений, которые работают **on demand**.

Например:

```text
пользователь нажал кнопку
        ↓
расширение определило активную вкладку
        ↓
внедрило код
        ↓
код проанализировал страницу
        ↓
вернул результат
```

В отличие от статической декларации `content_scripts`, здесь решение об инъекции принимается **во время выполнения**.

---

# 31.1. `chrome.scripting`

`chrome.scripting` — Extension API Manifest V3, предназначенный для программного управления JavaScript и CSS, внедряемыми в страницы.

Для выполнения скрипта используется:

```javascript
chrome.scripting.executeScript()
```

Например:

```javascript
const [tab] =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });

await chrome.scripting.executeScript({
    target: {
        tabId: tab.id
    },
    func: () => {
        document.body.style.outline =
            "3px solid red";
    }
});
```

Архитектура:

```text
Service Worker
      │
      │ executeScript()
      ▼
Browser
      │
      ▼
Target Tab
      │
      ▼
Content Script execution
```

---

## Почему появился `chrome.scripting`

В Manifest V2 многие задачи решались через старые механизмы:

```text
tabs.executeScript()
```

В Manifest V3 используется:

```text
chrome.scripting.executeScript()
```

Это соответствует общей архитектурной модели MV3, в которой browser APIs становятся более явно разделёнными и capability-oriented.

---

## Permissions

Для использования `chrome.scripting` расширению обычно требуется permission:

```json
{
    "permissions": [
        "scripting"
    ]
}
```

Но этого недостаточно для доступа к произвольным страницам.

Необходимо также иметь соответствующее право на target page — например через:

```text
host_permissions
```

или другой механизм предоставления доступа, включая пользовательское разрешение для активной вкладки в подходящем сценарии.

Таким образом:

```text
scripting
   +
page access
   ↓
programmatic injection
```

---

# 31.2. `executeScript()`

Основной метод:

```javascript
chrome.scripting.executeScript(
    injection
);
```

Он принимает объект, описывающий:

```text
что внедрить
куда внедрить
в каком execution world
```

Минимальный вариант:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId: tab.id
    },
    func: () => {
        console.log(
            "Hello from extension"
        );
    }
});
```

---

## Что происходит при вызове

Допустим, Service Worker выполняет:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId: 123
    },
    func: () => {
        document.title =
            "Modified by extension";
    }
});
```

Браузер:

```text
Service Worker
      │
      │ executeScript()
      ▼
Chrome extension subsystem
      │
      ▼
Tab 123
      │
      ▼
Page execution environment
      │
      ▼
func()
```

Функция выполняется в контексте target page, а не внутри самого Service Worker.

---

# Функция не выполняется в Service Worker

Это принципиальный момент.

Рассмотрим:

```javascript
const value = 42;

await chrome.scripting.executeScript({
    target: {
        tabId: tab.id
    },
    func: () => {
        console.log(value);
    }
});
```

Такой код нельзя рассматривать как обычный вызов функции:

```text
Service Worker
      │
      └── function()
```

Функция переносится для выполнения в другой context.

Поэтому её окружение не является обычным closure Service Worker.

---

## Не рассчитывайте на closure

Неправильная концептуальная модель:

```javascript
const user = {
    name: "Alice"
};

chrome.scripting.executeScript({
    target: { tabId },
    func: () => {
        console.log(user.name);
    }
});
```

Нужно явно передавать данные через предусмотренный механизм.

Например:

```javascript
const user = {
    name: "Alice"
};

await chrome.scripting.executeScript({
    target: {
        tabId
    },
    func: user => {
        console.log(user.name);
    },
    args: [user]
});
```

Здесь:

```text
Service Worker
    │
    │ args
    ▼
Injected function
```

получает данные явно.

---

# Возвращаемые значения

`executeScript()` возвращает результаты выполнения.

Например:

```javascript
const results =
    await chrome.scripting.executeScript({
        target: {
            tabId
        },
        func: () => {
            return document.title;
        }
    });

console.log(results);
```

Результат содержит данные, возвращённые функцией.

Концептуально:

```text
Service Worker
      │
      │ executeScript()
      ▼
Page
      │
      │ return document.title
      ▼
Browser
      │
      ▼
Service Worker
```

Это удобно для небольших операций:

```text
read title
read selection
detect element
calculate value
inspect DOM
```

---

# 31.3. Injecting Files

Вместо передачи функции можно внедрить JavaScript-файл.

Например:

```text
extension/
├── manifest.json
├── background.js
└── scripts/
    └── analyzer.js
```

Service Worker:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    files: [
        "scripts/analyzer.js"
    ]
});
```

---

## Почему файлы удобнее для больших scripts

Если код небольшой:

```javascript
func: () => {
    // ...
}
```

может быть достаточно.

Но большой код лучше хранить в отдельном модуле:

```text
scripts/
    analyzer.js
```

а затем:

```javascript
files: [
    "scripts/analyzer.js"
]
```

---

## Архитектура

```text
Service Worker
      │
      │ executeScript()
      │
      └──── files ────→ analyzer.js
                              │
                              ▼
                           Page
```

---

# Несколько файлов

Можно внедрить несколько файлов:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    files: [
        "scripts/utils.js",
        "scripts/analyzer.js"
    ]
});
```

Но при проектировании нужно учитывать зависимости между ними и порядок выполнения.

Если:

```text
utils.js
```

создаёт необходимые функции, а:

```text
analyzer.js
```

их использует, порядок имеет значение.

---

# File injection и ESM

Здесь важно не смешивать несколько механизмов.

Статические ES Modules:

```html
<script type="module">
```

и программная инъекция через:

```javascript
chrome.scripting.executeScript()
```

не являются полностью одинаковыми моделями загрузки.

Если extension имеет сложную модульную архитектуру, нужно заранее определить:

```text
что является extension module
        ↓
что является injected script
        ↓
как передаются зависимости
```

Не следует превращать Programmatic Injection в способ случайно загружать весь application runtime на страницу.

---

# 31.4. Injecting Functions

Вместо файла можно передать функцию:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    func: () => {
        const selection =
            window.getSelection()
                ?.toString();

        return selection;
    }
});
```

Это особенно удобно для небольших операций.

---

# Аргументы функции

Функция может получать аргументы через `args`.

Например:

```javascript
const color = "red";

await chrome.scripting.executeScript({
    target: {
        tabId
    },
    func: color => {
        document.body.style.outline =
            `3px solid ${color}`;
    },
    args: [color]
});
```

Получается:

```text
Service Worker
    │
    │ color = "red"
    ▼
executeScript()
    │
    ▼
Injected function
    │
    ▼
DOM
```

---

# Structured data

В `args` можно передавать структурированные данные, если они поддерживаются механизмом сериализации API.

Например:

```javascript
const config = {
    selector: ".product",
    limit: 20
};

await chrome.scripting.executeScript({
    target: {
        tabId
    },
    func: config => {
        const elements =
            document.querySelectorAll(
                config.selector
            );

        console.log(
            elements.length,
            config.limit
        );
    },
    args: [config]
});
```

Это лучше, чем пытаться строить JavaScript-код динамической строкой.

---

# Не создавайте код через string concatenation

Плохой подход:

```javascript
const code =
    `document.body.innerHTML =
     "${userInput}"`;
```

Затем пытаться выполнить этот код.

Это приводит к:

```text
code generation
   ↓
injection risk
   ↓
security problems
```

Вместо этого используйте:

```javascript
func: data => {
    // ...
},
args: [data]
```

Так данные остаются данными, а код — кодом.

---

# 31.5. Target Tabs

Каждая программная инъекция должна иметь target.

Минимальный вариант:

```javascript
target: {
    tabId
}
```

Например:

```javascript
const [tab] =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });

await chrome.scripting.executeScript({
    target: {
        tabId: tab.id
    },
    func: () => {
        console.log("Injected");
    }
});
```

---

# Active Tab

Один из распространённых сценариев:

```text
User clicks Action
        ↓
Service Worker
        ↓
find active tab
        ↓
executeScript()
        ↓
current page
```

Например:

```javascript
chrome.action.onClicked.addListener(
    async tab => {

        await chrome.scripting.executeScript({
            target: {
                tabId: tab.id
            },
            func: () => {
                document.body.style
                    .backgroundColor =
                    "lightyellow";
            }
        });
    }
);
```

Это хороший пример **on-demand extension**.

---

# Target должен быть валидным

Не каждая вкладка является подходящей target page.

Например, расширение не должно исходить из предположения:

```text
tabId → injection always works
```

Возможны страницы:

```text
chrome://...
edge://...
about:...
browser internal pages
extension pages
Web Store
```

и другие специальные contexts, где выполнение может быть ограничено.

Поэтому production extension должен обрабатывать ошибки.

Например:

```javascript
try {

    await chrome.scripting.executeScript({
        target: {
            tabId: tab.id
        },
        func: run
    });

} catch (error) {

    console.error(
        "Injection failed",
        error
    );
}
```

---

# 31.6. Frames

Современные страницы часто состоят не из одного document.

Например:

```text
Top Frame
│
├── iframe A
│
├── iframe B
│    └── iframe C
│
└── iframe D
```

По умолчанию операция может быть направлена на основной frame target.

Но `chrome.scripting` позволяет управлять target frames.

---

# `allFrames`

Например:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId,
        allFrames: true
    },
    func: () => {
        console.log(
            "Executed in frame"
        );
    }
});
```

Теперь script будет выполнен во всех подходящих frames target tab.

Архитектура:

```text
Tab
│
├── Main Frame      ← execute
├── iframe A        ← execute
├── iframe B        ← execute
└── iframe C        ← execute
```

---

# `frameIds`

Можно вместо всех frames указать конкретные frame IDs:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId,
        frameIds: [2, 5]
    },
    func: () => {
        // ...
    }
});
```

Это позволяет выполнять более точную адресацию.

---

# Почему frames важны

Представим страницу:

```text
example.com
    │
    └── iframe
          │
          └── payment.example
```

Элемент, который вам нужен, может находиться не в top-level document.

Тогда:

```javascript
document.querySelector(...)
```

в основном frame его не найдёт.

Необходимо определить:

```text
какой frame содержит элемент?
```

и затем направить injection туда.

---

# Frame-aware architecture

Для сложных extension полезно мыслить так:

```text
Tab
 │
 ├── Frame 0
 │
 ├── Frame 1
 │
 ├── Frame 2
 │
 └── Frame 3
```

а не:

```text
Tab = one document
```

Это особенно важно для:

```text
embedded applications
payment widgets
video players
ads
third-party integrations
micro-frontends
```

# 31.7. Dynamic Injection

Programmatic Injection позволяет сделать extension динамическим.

Вместо:

```text
manifest
  ↓
always inject
```

можно использовать:

```text
event
  ↓
decision
  ↓
inject
```

Например:

```text
User opens extension
       ↓
Service Worker
       ↓
Check URL
       ↓
Check permissions
       ↓
Check page
       ↓
Inject script
```

---

# Статическая vs динамическая инъекция

### Static

```json
{
    "content_scripts": [
        {
            "matches": [
                "https://example.com/*"
            ],
            "js": [
                "content.js"
            ]
        }
    ]
}
```

Браузер сам решает:

```text
match?
   ↓
inject
```

---

### Programmatic

```javascript
if (shouldInject(tab)) {

    await chrome.scripting.executeScript({
        target: {
            tabId: tab.id
        },
        files: [
            "content.js"
        ]
    });
}
```

Теперь решение принадлежит application logic.

---

# Когда dynamic injection лучше

Programmatic Injection особенно полезна, когда:

### 1. Код нужен только по запросу

```text
User clicks Action
       ↓
inject
```

---

### 2. Код нужен только для определённого состояния страницы

```text
Page
 ↓
detect application
 ↓
inject
```

---

### 3. Не хочется постоянно загружать Content Script

Например:

```text
1000 page visits
       ↓
only 10 relevant pages
```

Вместо:

```text
1000 injections
```

можно сделать:

```text
1000 checks
       ↓
10 injections
```

---

### 4. Extension имеет несколько режимов

Например:

```text
Normal
Analysis
Debug
Extraction
Automation
```

И каждый режим загружает собственный код:

```text
mode
 ↓
dynamic injection
 ↓
specific module
```

---

# Dynamic injection как архитектурный инструмент

В больших системах можно разделить:

```text
Core
 │
 ├── detection
 ├── permissions
 ├── routing
 └── orchestration
          │
          ▼
     Dynamic Injection
          │
     ┌────┼────┐
     ▼    ▼    ▼
 Extract Analyze Automate
```

Это позволяет не держать весь функционал внутри постоянно активного Content Script.

---

# Но dynamic injection не бесплатна

Есть несколько важных вопросов:

```text
Когда inject?
Куда inject?
В какой frame?
В какой world?
Есть ли permission?
Не был ли script уже injected?
Что произойдёт при navigation?
```

Поэтому Programmatic Injection требует lifecycle architecture.

---

# Повторная инъекция

Если пользователь несколько раз запускает команду:

```text
click
 ↓
inject
click
 ↓
inject
click
 ↓
inject
```

можно случайно создать несколько экземпляров одного приложения:

```text
Page
 ├── Extension instance #1
 ├── Extension instance #2
 └── Extension instance #3
```

Поэтому injected code часто должен быть idempotent.

Например:

```javascript
if (window.__MY_EXTENSION_ACTIVE__) {
    return;
}

window.__MY_EXTENSION_ACTIVE__ = true;
```

Но здесь нужно помнить о различиях execution worlds и contexts. Глобальное состояние страницы не является универсальным способом синхронизации extension.

---

# 31.8. Permissions

Programmatic Injection тесно связана с permission model Manifest V3.

Для использования:

```javascript
chrome.scripting.executeScript()
```

нужен соответствующий доступ к API:

```json
{
    "permissions": [
        "scripting"
    ]
}
```

Но расширению также нужен доступ к target page.

---

# `host_permissions`

Например:

```json
{
    "permissions": [
        "scripting"
    ],
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

Теперь архитектура выглядит:

```text
scripting permission
       +
host permission
       ↓
programmatic injection
       ↓
example.com
```

---

# `activeTab`

Для некоторых сценариев можно использовать:

```json
{
    "permissions": [
        "scripting",
        "activeTab"
    ]
}
```

Это особенно интересно для расширений типа:

```text
Click Action
      ↓
operate on current page
```

Вместо постоянного доступа:

```text
<all_urls>
```

можно получить временный доступ к активной вкладке в рамках подходящего пользовательского взаимодействия.

---

# Least Privilege

С точки зрения безопасности:

```text
<all_urls>
```

не следует использовать автоматически.

Если extension работает только с:

```text
example.com
```

лучше рассмотреть:

```json
"host_permissions": [
    "https://example.com/*"
]
```

Если функциональность нужна только для текущей вкладки по пользовательскому действию, может быть уместнее:

```text
activeTab
```

при условии, что сценарий соответствует требованиям этого permission.

---

# Permission architecture

Получается:

```text
Need injection
      │
      ▼
Need scripting?
      │
      ├── yes
      │
      ▼
Need access to page?
      │
      ├── specific hosts
      │       ↓
      │   host_permissions
      │
      └── current user-selected tab
              ↓
          activeTab
```

Это значительно лучше, чем:

```text
Need injection
      ↓
<all_urls>
```

---

# Programmatic Injection и безопасность

Injected code работает непосредственно рядом с содержимым страницы.

Поэтому нельзя доверять всему, что приходит из page.

Например:

```javascript
const value =
    document.querySelector(
        ".user-data"
    )?.textContent;
```

`value` нужно рассматривать как:

```text
untrusted input
```

Если затем передать его в HTML:

```javascript
container.innerHTML =
    value;
```

можно создать XSS.

Безопаснее:

```javascript
container.textContent =
    value;
```

или использовать безопасную DOM-конструкцию.

---

# Injection ≠ Page Script

Programmatic Injection не означает:

```text
Extension
   ↓
becomes page JavaScript
```

Нужно продолжать различать:

```text
Extension context
Content Script
Page context
MAIN world
```

Особенно важно понимать `world`.

Для обычной инъекции используется соответствующая extension-controlled execution model, а при необходимости взаимодействия непосредственно с JavaScript environment страницы существует отдельная возможность выбора `world`.

Это будет подробно рассмотрено в следующей главе.

# Programmatic Injection и messaging

Часто injection — только первый шаг.

Например:

```text
Service Worker
      │
      │ executeScript()
      ▼
Content Script
      │
      │ runtime.sendMessage()
      ▼
Service Worker
```

То есть injection может использоваться для запуска агента на странице, после чего основное взаимодействие выполняется через Message Passing.

---

# Типичная архитектура

```text
                    Service Worker
                          │
              ┌───────────┴───────────┐
              │                       │
          permission               target
              │                       │
              └───────────┬───────────┘
                          ▼
                 executeScript()
                          │
                          ▼
                    Content Script
                          │
              ┌───────────┴───────────┐
              │                       │
             DOM                  Page data
              │                       │
              └───────────┬───────────┘
                          ▼
                   sendMessage()
                          │
                          ▼
                    Service Worker
```

# Static + Programmatic Injection

В реальном extension не обязательно выбирать только один механизм.

Можно использовать оба.

Например:

```text
Static Content Script
        ↓
small bootstrap
        ↓
detect environment
        ↓
Dynamic Injection
        ↓
heavy feature
```

Это очень интересный архитектурный паттерн.

---

# Bootstrap architecture

Например:

```text
content-bootstrap.js
        │
        ├── detect page
        ├── detect feature
        └── request activation
                  │
                  ▼
             Service Worker
                  │
                  ▼
          executeScript()
                  │
                  ▼
            feature.js
```

Преимущество:

```text
small always-loaded code
        +
large on-demand code
```

# Compile-time generated injection

Для сложных extension можно пойти ещё дальше.

Например, build system знает:

```text
feature A → script A
feature B → script B
feature C → script C
```

и генерирует manifest/application metadata.

Получается:

```text
Source
  ↓
Build
  ↓
Injection manifest
  ↓
Runtime decision
  ↓
chrome.scripting
  ↓
Feature
```

Это особенно хорошо соответствует архитектуре:

> **Compile More, Execute Less.**

То есть runtime не должен каждый раз загружать и анализировать весь application code.

# Пример: on-demand page analyzer

Рассмотрим практическое расширение.

Пользователь открывает страницу:

```text
https://example.com/article/123
```

Нажимает Action:

```text
Analyze page
```

Service Worker получает событие:

```javascript
chrome.action.onClicked.addListener(
    async tab => {

        await chrome.scripting.executeScript({
            target: {
                tabId: tab.id
            },
            files: [
                "content/analyzer.js"
            ]
        });

    }
);
```

Analyzer:

```javascript
const title =
    document.querySelector("h1")
        ?.textContent;

const text =
    document.body.innerText;

console.log({
    title,
    text
});
```

Архитектура:

```text
User
 ↓
Action
 ↓
Service Worker
 ↓
executeScript()
 ↓
analyzer.js
 ↓
DOM
```

# Более зрелая версия

В production extension лучше разделить ответственность:

```text
Service Worker
 ├── permissions
 ├── target selection
 ├── injection
 └── message routing

Injected Content Script
 ├── DOM
 ├── extraction
 └── page interaction

Storage
 └── persistent state
```

То есть Service Worker не должен сам заниматься DOM.

# Injection Manager

В большом расширении полезно создать отдельный слой:

```text
InjectionManager
```

Например:

```javascript
async function injectAnalyzer(
    tabId
) {
    return chrome.scripting.executeScript({
        target: {
            tabId
        },
        files: [
            "content/analyzer.js"
        ]
    });
}
```

Теперь application logic может использовать:

```javascript
await injectAnalyzer(
    tab.id
);
```

вместо прямого вызова API в десятках мест.

---

# Injection Registry

Для ещё более сложной системы:

```javascript
const injections = {
    analyzer: {
        files: [
            "content/analyzer.js"
        ]
    },

    extractor: {
        files: [
            "content/extractor.js"
        ]
    },

    automation: {
        files: [
            "content/automation.js"
        ]
    }
};
```

Тогда:

```javascript
await inject(
    "analyzer",
    tab.id
);
```

становится единым механизмом.

# Идемпотентность

Очень важное свойство injected modules:

> повторный запуск не должен разрушать состояние страницы.

Например:

```javascript
if (
    document.querySelector(
        "[data-my-extension-root]"
    )
) {
    return;
}
```

После чего:

```javascript
const root =
    document.createElement("div");

root.dataset.myExtensionRoot = "";

document.body.append(root);
```

Теперь:

```text
first injection
      ↓
create UI

second injection
      ↓
detect existing UI
      ↓
do nothing
```

# Lifecycle после Navigation

Programmatic Injection не означает, что script будет существовать вечно.

Если пользователь делает:

```text
Page A
  ↓
navigation
  ↓
Page B
```

старый document уничтожается.

Поэтому:

```text
Injected Script
      ↓
document lifecycle
      ↓
navigation
      ↓
destroyed
```

Если функциональность нужна на новой странице, её необходимо запустить снова.

Это особенно важно для SPA и обычной navigation.

---

# Programmatic Injection в SPA

В SPA ситуация сложнее:

```text
URL A
 ↓
history.pushState()
 ↓
URL B
```

document может не уничтожаться.

Поэтому extension должен различать:

```text
full navigation
```

и:

```text
client-side navigation
```

В некоторых приложениях нужно отслеживать:

```text
history
location
DOM mutations
application state
```

а не только сам факт первоначальной загрузки.

---

# Главное различие

Статическая инъекция:

```text
Browser decides
      ↓
match pattern
      ↓
inject
```

Programmatic Injection:

```text
Extension decides
      ↓
target
      ↓
permission
      ↓
executeScript()
      ↓
inject
```

Это фундаментальное различие.

---

# Когда использовать `executeScript()`

Programmatic Injection особенно хорошо подходит для:

* действий пользователя;
* инструментов анализа страницы;
* page extraction;
* automation;
* debugging;
* временных UI;
* on-demand features;
* context-aware functionality;
* работы только с определёнными tabs;
* снижения постоянной нагрузки Content Scripts.

---

# Когда лучше использовать `content_scripts`

Статическая инъекция лучше подходит, когда:

* script должен запускаться автоматически;
* набор страниц заранее известен;
* функциональность является постоянной;
* важна автоматическая обработка navigation;
* не требуется дополнительная runtime decision.

---

# Static vs Programmatic

| Характеристика   | Static          | Programmatic       |
| ---------------- | --------------- | ------------------ |
| Где определяется | `manifest.json` | JavaScript         |
| Кто решает       | Browser         | Extension          |
| Когда inject     | автоматически   | по событию/условию |
| Runtime control  | ниже            | выше               |
| Архитектура      | проще           | гибче              |
| On-demand        | ограниченно     | отлично            |
| Dynamic features | ограниченно     | отлично            |
| Target selection | match patterns  | runtime            |
| Frames           | декларативно    | программно         |
| Сложность        | ниже            | выше               |

# Типичная ошибка №1 — использовать `<all_urls>` без необходимости

Плохая архитектура:

```text
Need one-click analyzer
        ↓
<all_urls>
        ↓
Content Script everywhere
```

Лучше:

```text
User clicks
    ↓
activeTab / appropriate host access
    ↓
executeScript()
```

если функциональность действительно on-demand.

---

# Типичная ошибка №2 — передавать код строками

Плохая идея:

```javascript
const code =
    "document.body.innerHTML = ...";
```

Лучше:

```javascript
func: value => {
    document.body.textContent =
        value;
},
args: [value]
```

Так значительно легче контролировать границу:

```text
code
≠
data
```

---

# Типичная ошибка №3 — не учитывать frames

Разработчик проверяет:

```javascript
document.querySelector(...)
```

но элемент находится внутри iframe.

Результат:

```text
element not found
```

Поэтому для сложных страниц необходимо понимать frame topology.

---

# Типичная ошибка №4 — считать injected script постоянным

После:

```text
navigation
```

его document может быть уничтожен.

Нужно проектировать:

```text
injection
+
lifecycle
+
reinjection
```

как единую систему.

---

# Типичная ошибка №5 — смешивать orchestration и DOM logic

Не стоит превращать Service Worker в:

```text
Service Worker
 ├── DOM logic
 ├── UI
 ├── parsing
 ├── network
 └── injection
```

Лучше:

```text
Service Worker
 └── orchestration
       ↓
Content Script
 └── page interaction
```

# Архитектурная модель Programmatic Injection

В зрелом Manifest V3 extension можно выделить отдельный pipeline:

```text
                 User / Event
                       │
                       ▼
                Decision Layer
                       │
             ┌─────────┴─────────┐
             │                   │
        Permission          Target Selection
             │                   │
             └─────────┬─────────┘
                       ▼
                Injection Manager
                       │
                       ▼
              chrome.scripting
                       │
                       ▼
                 Target Frame
                       │
                       ▼
                Injected Module
                       │
                 ┌─────┴─────┐
                 │           │
                DOM        Page API
                 │           │
                 └─────┬─────┘
                       ▼
                 Message Layer
                       │
                       ▼
                 Service Worker
```

Это уже не просто вызов API.

Это отдельная **архитектурная подсистема extension**.

# Итог

`chrome.scripting.executeScript()` превращает Content Script из статически объявленного ресурса в **динамический capability**.

Вместо:

```text
Manifest
   ↓
always inject
```

можно построить:

```text
Event
 ↓
Decision
 ↓
Permission
 ↓
Target
 ↓
Injection
 ↓
Execution
 ↓
Result
```

Главные идеи главы:

1. `chrome.scripting` предоставляет программную инъекцию.
2. `executeScript()` позволяет выполнять функцию или внедрять файл.
3. `target` определяет вкладку и frames.
4. `func` удобен для небольших операций.
5. `files` лучше подходит для самостоятельных модулей.
6. `args` позволяют безопасно передавать данные в injected function.
7. Injection требует соответствующих permissions и доступа к target page.
8. `activeTab` может быть полезнее широких host permissions для on-demand сценариев.
9. Frames необходимо рассматривать как отдельные execution targets.
10. Injected code имеет собственный lifecycle и не должен считаться постоянным.
11. Dynamic Injection особенно полезна для on-demand функциональности.
12. Injection следует проектировать вместе с messaging, permissions и lifecycle.

Главный принцип:

> **Не внедряйте код на страницу просто потому, что это возможно. Внедряйте его тогда, когда архитектуре действительно требуется page-level capability.**

В хорошо спроектированном MV3 extension `chrome.scripting` становится не механизмом «запустить JavaScript на странице», а **контролируемым мостом между extension runtime и конкретным page context**.
