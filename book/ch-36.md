# Глава 36. Extension как распределённое приложение

До этого момента мы рассматривали отдельные элементы архитектуры Manifest V3: contexts, Service Worker, messaging, storage, permissions, content scripts, Side Panel и browser APIs.

Теперь необходимо сделать следующий архитектурный шаг.

На первый взгляд browser extension кажется обычным небольшим JavaScript-приложением:

```text
Extension
   └── JavaScript
```

Но такая модель быстро перестаёт работать, когда extension становится сложным.

Реальное Manifest V3 extension больше похоже на **маленькую распределённую систему**:

```text
                    Extension
                        │
        ┌───────────────┼────────────────┐
        │               │                │
        ▼               ▼                ▼
      Popup        Service Worker   Content Script
        │               │                │
        ▼               ▼                ▼
    UI State       Application       Page State
                        │
                        ▼
                    Storage
```

Каждый context:

* имеет собственную память;
* запускается независимо;
* может быть уничтожен независимо;
* имеет собственный lifecycle;
* не разделяет обычные JavaScript variables с другими contexts;
* взаимодействует с остальными через сообщения, события и persistence.

Именно поэтому архитектурные идеи distributed systems неожиданно хорошо применимы к browser extensions.

---

# 36.1. Почему extension похож на distributed system

Классическая distributed system состоит из нескольких независимых компонентов:

```text
Node A
   │
   │ network
   ▼
Node B
   │
   │ network
   ▼
Node C
```

У каждого node есть:

```text
memory
lifecycle
state
failure
communication
```

В Manifest V3 происходит нечто похожее:

```text
Popup
   │
   │ message
   ▼
Service Worker
   │
   │ message
   ▼
Content Script
```

Каждый context имеет собственный JavaScript environment.

Поэтому:

```javascript
// Popup
let counter = 10;
```

не создаёт:

```javascript
// Service Worker
counter === 10
```

и:

```javascript
// Content Script
counter === 10
```

Каждый context имеет собственное состояние.

---

# Shared memory отсутствует

В обычном приложении можно представить:

```text
Application
     │
     ▼
Shared memory
```

Например:

```javascript
const state = {
    user: null,
    settings: {},
    currentTab: null
};
```

Все компоненты приложения могут работать с одним объектом.

В extension:

```text
Popup memory
Service Worker memory
Content Script memory
Side Panel memory
Options memory
```

раздельны.

Получается:

```text
        ┌─────────────┐
        │ Popup       │
        │ Memory      │
        └─────────────┘

        ┌─────────────┐
        │ Worker      │
        │ Memory      │
        └─────────────┘

        ┌─────────────┐
        │ Content     │
        │ Memory      │
        └─────────────┘
```

Следовательно, communication становится фундаментальной частью architecture.

---

# Extension как collection of nodes

Удобно рассматривать contexts как nodes:

```text
Node:
  Popup

Node:
  Side Panel

Node:
  Options

Node:
  Service Worker

Node:
  Content Script
```

А communication channels:

```text
Popup
   │
   ├── message ──► Service Worker
   │
   └── state ────► Storage

Service Worker
   │
   ├── message ──► Content Script
   ├── message ──► Side Panel
   └── event ────► Application Core
```

Это уже очень напоминает distributed architecture.

---

# Почему это не просто аналогия

Важно понимать: extension не является distributed system в полном смысле классической распределённой системы.

Contexts обычно работают внутри одного браузера и одной extension origin.

Но архитектурные свойства похожи:

| Distributed system  | Extension                    |
| ------------------- | ---------------------------- |
| Node                | Execution context            |
| Network message     | Runtime message              |
| Process restart     | Context restart              |
| Local memory        | Context globals              |
| Persistent database | `chrome.storage` / IndexedDB |
| Event bus           | Extension events             |
| Failure boundary    | Context failure              |
| Distributed state   | Shared extension state       |
| UI node             | Popup / Side Panel           |
| Client              | Content Script / UI          |

Поэтому полезно применять **принципы**, но не переносить механически всю сложность распределённых систем.

---

# 36.2. Независимые execution contexts

Основной элемент extension architecture — execution context.

Например:

```text
Service Worker
```

может выполнять:

```text
background orchestration
storage
network
alarms
commands
message routing
```

Content Script:

```text
DOM
page interaction
events
page integration
```

Popup:

```text
short-lived UI
```

Side Panel:

```text
persistent UI
```

Options:

```text
configuration UI
```

---

# Каждый context — отдельный runtime

Можно представить:

```text
Popup Runtime
    │
    ├── JavaScript heap
    ├── DOM
    ├── event loop
    └── lifecycle

Service Worker Runtime
    │
    ├── JavaScript heap
    ├── event loop
    └── lifecycle

Content Script Runtime
    │
    ├── JavaScript heap
    ├── DOM access
    ├── event loop
    └── lifecycle
```

Поэтому архитектура должна учитывать не только **что делает модуль**, но и:

> **в каком context он выполняется.**

---

# Context placement

При проектировании feature нужно задавать вопрос:

> Где должна выполняться эта операция?

Например:

### Чтение DOM страницы

```text
Content Script
```

### Длительное состояние extension

```text
Storage + Application Core
```

### Global event handling

```text
Service Worker
```

### Пользовательские настройки

```text
Options
```

### Постоянный рабочий интерфейс

```text
Side Panel
```

### Короткое действие

```text
Popup
```

Это называется **context placement**.

---

# Context boundaries

Граница context — это одновременно:

```text
execution boundary
memory boundary
lifecycle boundary
failure boundary
security boundary
```

Например:

```text
Popup
   │
   │
   ▼
Service Worker
```

Popup может закрыться.

Service Worker может быть остановлен.

Content Script может исчезнуть вместе со страницей.

Поэтому нельзя строить архитектуру, предполагая:

```text
"все компоненты всегда существуют".
```

---

# 36.3. Message passing

Если contexts не разделяют memory, им необходим communication mechanism.

Основной механизм:

```text
runtime.sendMessage()
```

Например:

```javascript
await chrome.runtime.sendMessage({
    type: "GET_SETTINGS"
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    async (message) => {
        if (message.type === "GET_SETTINGS") {
            return getSettings();
        }
    }
);
```

Концептуально:

```text
Client Context
      │
      │ message
      ▼
Service Context
```

---

# Messages как API

Очень важно не рассматривать messages как случайные JavaScript objects.

Лучше считать их **API между contexts**.

Например:

```text
GET_SETTINGS
SAVE_SETTINGS
ANALYZE_PAGE
GET_PAGE_STATE
START_TASK
STOP_TASK
```

Это уже protocol.

---

# Message protocol

Например:

```javascript
{
    type: "ANALYZE_PAGE",
    version: 1,
    requestId: "req-123",
    payload: {
        tabId: 42
    }
}
```

Ответ:

```javascript
{
    requestId: "req-123",
    ok: true,
    result: {
        title: "Example"
    }
}
```

Ошибка:

```javascript
{
    requestId: "req-123",
    ok: false,
    error: {
        code: "PERMISSION_DENIED",
        message: "Host permission required"
    }
}
```

---

# Message passing вместо direct calls

В обычном приложении:

```javascript
const result = service.analyze(page);
```

В extension:

```text
Popup
   │
   │ ANALYZE_PAGE
   ▼
Service Worker
   │
   │ EXECUTE
   ▼
Content Script
```

То есть функция превращается в protocol operation.

---

# Почему это важно

Message protocol позволяет:

* отделить contexts;
* контролировать доступ;
* валидировать данные;
* логировать communication;
* обрабатывать ошибки;
* версионировать API;
* тестировать взаимодействие.

---

# 36.4. Eventual state synchronization

Если разные contexts имеют локальное состояние, возникает вопрос:

> Как они узнают об изменениях?

Например:

```text
Options
   │
   │ changes settings
   ▼
Storage
```

Side Panel уже был открыт:

```text
Side Panel
   │
   └── old settings
```

Content Script тоже имеет:

```text
old state
```

Теперь необходимо синхронизировать их.

---

# Shared state model

Можно использовать:

```text
                 Storage
                    │
             source of truth
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Popup      Side Panel   Worker
        │           │           │
        ▼           ▼           ▼
      local       local       local
      state       state       state
```

Каждый context имеет локальную копию.

Storage выступает persistent source of truth.

---

# Eventual consistency

Представим:

```text
t0:
enabled = false
```

Options изменяет:

```text
t1:
enabled = true
```

Side Panel ещё некоторое время знает:

```text
enabled = false
```

После события:

```text
STATE_CHANGED
```

получает:

```text
enabled = true
```

Таким образом:

```text
old state
   ↓
update
   ↓
propagation
   ↓
new state
```

Система становится согласованной не обязательно мгновенно, а после распространения изменения.

Это и есть идея **eventual consistency**.

---

# Почему это нормально

Для многих extension не требуется абсолютная синхронность.

Например:

```text
Theme changed
```

может обновиться через несколько миллисекунд.

Необходимо лишь гарантировать:

```text
eventually:
all relevant contexts → new state
```

---

# State update protocol

Хороший протокол:

```text
1. Context changes state
2. State is persisted
3. Change event is emitted
4. Other contexts receive event
5. Context reloads/updates local state
6. UI rerenders
```

Например:

```text
Options
   │
   ▼
StateManager
   │
   ▼
Storage
   │
   ▼
storage.onChanged
   │
   ├──► Popup
   ├──► Side Panel
   └──► Service Worker
```

---

# Не отправлять состояние только UI

Плохая архитектура:

```text
Options
   ↓
sendMessage()
   ↓
Side Panel
```

Почему?

Потому что Side Panel может быть закрыт.

Правильнее:

```text
Options
   ↓
Persistent State
   ↓
Storage
   ↓
State synchronization
```

Теперь Side Panel может открыться позже и получить актуальное состояние.

---

# State synchronization после restart

Предположим:

```text
Service Worker
```

был остановлен.

После запуска:

```text
Service Worker starts
      ↓
load state
      ↓
initialize
```

Он не должен ожидать:

```text
"кто-нибудь пришлёт мне состояние".
```

Он должен уметь восстановить его самостоятельно.

---

# 36.5. Ephemeral processes

Service Worker — главный пример ephemeral process.

Его можно представить:

```text
                    Browser
                       │
                       ▼
                Service Worker
                       │
                 event arrives
                       │
                       ▼
                    starts
                       │
                       ▼
                  handles event
                       │
                       ▼
                    becomes
                      idle
                       │
                       ▼
                   terminates
```

Следующий event:

```text
event
  ↓
new worker instance
```

---

# Почему это похоже на process restart

В классической distributed system процесс может упасть:

```text
Node A
   ↓
crash
   ↓
restart
```

В Manifest V3:

```text
Service Worker
   ↓
suspended
   ↓
restarted
```

Следовательно, архитектура должна быть restart-safe.

---

# Global variables не являются persistent state

Например:

```javascript
let cache = {};
```

может существовать некоторое время.

Но нельзя считать его durable storage.

Правильнее:

```text
Global memory
    ↓
performance cache
```

а:

```text
Storage
    ↓
persistent state
```

---

# Cache versus state

Это важное различие.

### State

```text
must survive restart
```

### Cache

```text
can be recreated
```

Например:

```text
User settings
→ state

Downloaded metadata
→ possibly cache

Current computation
→ ephemeral state

DOM reference
→ ephemeral state
```

---

# Restart-safe architecture

Хорошая архитектура:

```text
Start
  ↓
Load state
  ↓
Rebuild cache
  ↓
Initialize services
  ↓
Subscribe to events
```

А не:

```text
Start
  ↓
Assume globals still exist
```

---

# 36.6. Failure boundaries

В distributed systems отказ одного node не должен автоматически уничтожать всю систему.

То же самое желательно для extension.

Например:

```text
Content Script failed
```

не должен означать:

```text
Extension completely broken
```

---

# Context isolation as failure isolation

Можно представить:

```text
              Extension
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
      Popup     Worker    Content
        X          ✓         ✓
```

Popup сломался.

Но:

```text
Worker → работает
Content → работает
Storage → работает
```

Это и есть **failure containment**.

---

# Failure matrix

Для сложного extension полезно заранее определить:

| Failure                  | Result                |
| ------------------------ | --------------------- |
| Popup closed             | normal                |
| Service Worker restarted | recover               |
| Content Script destroyed | re-inject when needed |
| Network unavailable      | retry/degrade         |
| Permission denied        | feature disabled      |
| Storage error            | fail safely           |
| Port disconnected        | reconnect             |
| Page navigation          | recreate page state   |

Такое проектирование значительно повышает устойчивость.

---

# Failure recovery

Каждый failure должен иметь стратегию:

```text
Failure
  │
  ├── Retry
  ├── Reconnect
  ├── Reinitialize
  ├── Reload state
  ├── Degrade
  └── Fail permanently
```

---

# 36.7. Idempotency

Одно из важнейших понятий distributed systems — **idempotency**.

Операция является idempotent, если повторное выполнение не приводит к нежелательному дополнительному эффекту.

Например:

```text
SET enabled = true
```

можно выполнить:

```text
1 раз
2 раза
10 раз
```

результат будет:

```text
enabled = true
```

---

# Non-idempotent operation

Например:

```text
INCREMENT counter
```

Если выполнить дважды:

```text
counter = 1
```

становится:

```text
counter = 3
```

если начальное значение было 1.

Поэтому повторная доставка message может создать проблему.

---

# Почему idempotency важна в extension

Messages могут быть повторены из-за:

* retry;
* reconnect;
* повторного initialization;
* race conditions;
* восстановления после failure;
* пользовательских повторных действий.

Поэтому важные operations лучше делать idempotent.

---

# Request ID

Один из способов:

```text
requestId
```

Например:

```javascript
{
    type: "SAVE_RESULT",
    requestId: "abc123",
    payload: {...}
}
```

Service Worker может помнить обработанные IDs:

```text
abc123 → processed
```

Если сообщение пришло повторно:

```text
abc123
```

операция не выполняется повторно.

---

# Idempotency keys

Для критических операций:

```text
Operation
   +
Idempotency Key
```

Например:

```text
SAVE_PAYMENT_STATE
operationId = "op-981"
```

Повтор:

```text
SAVE_PAYMENT_STATE
operationId = "op-981"
```

может безопасно вернуть уже известный результат.

---

# Idempotent UI

Idempotency относится не только к network или messages.

Например, Content Script может получить:

```text
INITIALIZE
```

несколько раз.

Плохая реализация:

```javascript
document.body.appendChild(toolbar);
```

Каждый вызов создаёт новую toolbar.

После трёх вызовов:

```text
toolbar
toolbar
toolbar
```

Лучше:

```javascript
if (!document.querySelector("#my-extension-toolbar")) {
    createToolbar();
}
```

Теперь:

```text
initialize()
initialize()
initialize()
```

безопасны.

---

# Idempotent event handling

То же относится к listeners.

Плохой вариант:

```text
initialize()
 → add listener

initialize()
 → add listener

initialize()
 → add listener
```

Хороший:

```text
initialize()
 → ensure listener exists
```

или:

```text
dispose()
 → remove listener
initialize()
 → add listener
```

---

# 36.8. Race conditions

Когда несколько contexts работают одновременно, появляется ещё одна проблема:

> **Race condition.**

Например:

```text
Popup              Service Worker
  │                      │
  │ GET_STATE            │
  │─────────────────────►│
  │                      │
  │ SAVE_STATE           │
  │─────────────────────►│
```

А другой context:

```text
Options
  │
  │ SAVE_STATE
  └─────────────────────►
```

Теперь два изменения могут конкурировать.

---

# Lost update

Например:

Начальное состояние:

```text
count = 0
```

Popup читает:

```text
0
```

Options тоже читает:

```text
0
```

Popup записывает:

```text
1
```

Options записывает:

```text
2
```

В результате изменение Popup потеряно.

---

# Последовательная обработка

Для некоторых операций нужен coordinator:

```text
             State Coordinator
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        Popup     Options   Worker
```

Все изменения проходят через него.

Например:

```text
UPDATE_STATE
     ↓
State Manager
     ↓
serialize updates
     ↓
persist
```

---

# Version numbers

Можно использовать version:

```javascript
{
    version: 12,
    settings: {...}
}
```

Изменение:

```text
v12
 ↓
v13
```

Если приходит update на основе старой версии:

```text
client version = 11
server version = 13
```

runtime может:

* отклонить изменение;
* повторно загрузить state;
* объединить изменения.

---

# Optimistic concurrency

Другой подход:

```text
Read version 12
      ↓
Modify
      ↓
Write only if version still 12
```

Если уже:

```text
version = 13
```

операция конфликтует.

Это особенно полезно для сложных shared-state моделей.

---

# Race conditions в Content Scripts

Они возникают и при работе со страницей.

Например:

```text
Content Script
   ↓
query DOM
```

но SPA framework в этот момент:

```text
replaces DOM
```

Получается:

```text
read
  ↓
DOM changed
  ↓
modify old element
```

Поэтому DOM integration тоже должна быть рассчитана на concurrency-like изменения.

---

# Race conditions с navigation

Например:

```text
Tab A
  ↓
URL A
  ↓
start analysis
```

Пользователь быстро переходит:

```text
URL B
```

а старый анализ ещё продолжается.

Теперь его результат может прийти уже после navigation.

Нужно проверить:

```text
Is result still relevant?
```

---

# Cancellation

Для таких случаев полезна cancellation model:

```text
Task A
   ↓
navigation
   ↓
cancel Task A
```

или:

```text
Task A
   ↓
completed
   ↓
check generation
   ↓
ignore stale result
```

---

# Generation number

Например:

```text
tab generation = 5
```

После navigation:

```text
generation = 6
```

Старый task:

```text
generation = 5
```

возвращает результат.

Runtime видит:

```text
5 != 6
```

и игнорирует его.

Это простой и эффективный способ защиты от stale results.

---

# 36.9. Distributed UI

Последний и особенно интересный аспект — UI.

В обычном веб-приложении UI обычно находится в одном DOM:

```text
Application
    ↓
DOM
    ↓
UI
```

Extension может иметь несколько UI surfaces:

```text
              Application
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
     Popup     Side Panel    Options
       │           │           │
       ▼           ▼           ▼
      DOM         DOM         DOM
```

И все они должны представлять одно приложение.

Это можно назвать:

> **Distributed UI.**

---

# Один application state — несколько UI

Например:

```text
State:

{
    enabled: true,
    theme: "dark",
    currentTab: 42
}
```

Этот state отображается в:

```text
Popup
Side Panel
Options
```

Но каждый UI имеет собственный DOM и собственный runtime.

---

# UI не должен быть source of truth

Плохая модель:

```text
Popup
   ↓
state

Side Panel
   ↓
different state

Options
   ↓
another state
```

В результате:

```text
Popup: enabled = true
Side Panel: enabled = false
Options: enabled = true
```

Это классическая проблема distributed state.

---

# Центральное состояние

Лучше:

```text
                 Application State
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
        Popup       Side Panel      Options
```

UI получает state:

```text
state → render
```

и отправляет intentions:

```text
user action → command
```

---

# UI as projection

Очень полезная модель:

> **UI — это projection of application state.**

То есть:

```text
Application State
       ↓
     render
       ↓
       UI
```

А не:

```text
UI
 ↓
owns application state
```

---

# Unidirectional flow

Можно использовать:

```text
User Action
     ↓
Command
     ↓
Application Core
     ↓
State Change
     ↓
Persistence
     ↓
State Event
     ↓
UI Render
```

Например:

```text
User clicks "Enable"
       ↓
ENABLE_FEATURE
       ↓
Service Worker
       ↓
State = enabled
       ↓
Storage
       ↓
STATE_CHANGED
       ↓
Popup / Side Panel
       ↓
render()
```

---

# Popup и Side Panel

Особенно хорошо это видно при сравнении Popup и Side Panel.

Popup:

```text
short-lived
```

Side Panel:

```text
longer-lived
```

Но оба должны получать:

```text
same application state
```

Поэтому architecture не должна зависеть от конкретного UI.

---

# Distributed UI synchronization

Предположим, пользователь открыл Side Panel:

```text
Side Panel
enabled = false
```

Затем в Options:

```text
enabled = true
```

Правильный flow:

```text
Options
   ↓
State update
   ↓
Storage
   ↓
STATE_CHANGED
   ↓
Side Panel
   ↓
render
```

В результате:

```text
Options:    true
Side Panel: true
Popup:      true
```

---

# UI lifecycle и synchronization

Popup может закрыться:

```text
Popup
  ↓
closed
```

Затем пользователь снова открывает его:

```text
open
 ↓
load current state
 ↓
render
```

Не нужно пытаться восстановить старый DOM.

Нужно:

> **reconstruct UI from current state.**

Это очень мощный принцип.

---

# UI reconstruction

Правильная модель:

```text
Open UI
   ↓
Load state
   ↓
Create view
   ↓
Subscribe
   ↓
Render
```

Закрытие:

```text
Close UI
   ↓
Dispose subscriptions
   ↓
Destroy runtime
```

Следующее открытие:

```text
Open
   ↓
Load current state
   ↓
Render again
```

---

# Distributed UI и stale state

UI может временно содержать устаревшее состояние:

```text
State v10

Popup → v10
Side Panel → v10
```

после изменения:

```text
State v11
```

может быть:

```text
Popup → v11
Side Panel → v10
```

на короткое время.

Это допустимо, если synchronization protocol eventually приводит систему к:

```text
Popup → v11
Side Panel → v11
```

---

# UI commands вместо direct mutation

Вместо:

```javascript
button.onclick = () => {
    state.enabled = !state.enabled;
};
```

лучше:

```javascript
button.onclick = () => {
    dispatch({
        type: "TOGGLE_FEATURE"
    });
};
```

Application Core решает:

```text
what state should change
```

UI отвечает только за:

```text
what user requested
```

---

# Distributed UI architecture

В итоге:

```text
                    Application State
                           │
                           ▼
                     State Manager
                           │
                 ┌─────────┼─────────┐
                 │         │         │
                 ▼         ▼         ▼
              Popup    Side Panel  Options
                 │         │         │
                 └─────────┼─────────┘
                           │
                       Commands
                           │
                           ▼
                    Application Core
```

UI является не отдельными приложениями, а разными **проекциями одной application model**.

# Полная distributed model Extension

Теперь можно объединить все идеи главы:

```text
                         EXTENSION
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
      Popup              Side Panel            Options
        │                    │                    │
        └────────────────────┼────────────────────┘
                             │
                       Message Transport
                             │
                             ▼
                      Service Worker
                             │
                 ┌───────────┼───────────┐
                 ▼           ▼           ▼
               Events      State       Commands
                 │           │           │
                 │           ▼           │
                 │        Storage        │
                 │                       │
                 └───────────┬───────────┘
                             ▼
                       Content Scripts
                             │
                             ▼
                          Web Page
```

Каждый компонент имеет:

```text
local memory
local lifecycle
local failure boundary
local responsibilities
```

а система объединяется через:

```text
messages
events
persistent state
protocols
```

---

# Основные принципы Extension Distributed Architecture

Из всей главы можно вывести несколько фундаментальных правил.

### Правило 1. Context — это отдельный runtime

Нельзя считать Popup, Service Worker и Content Script одной JavaScript-программой.

---

### Правило 2. Не полагаться на shared memory

```text
global variable
```

не является механизмом communication между contexts.

Используйте:

```text
messages
storage
events
```

---

### Правило 3. Persistent state должен переживать contexts

```text
Context
   ↓
may disappear

State
   ↓
must survive
```

---

### Правило 4. Messages — это protocol

Не передавайте произвольные объекты.

Определяйте:

```text
type
version
requestId
payload
error
```

---

### Правило 5. Проектируйте на повторную доставку

Операции должны по возможности быть:

```text
idempotent
```

---

### Правило 6. Проектируйте на restart

Service Worker должен иметь возможность:

```text
start
load state
reconstruct
continue
```

---

### Правило 7. Учитывайте stale state

Любой context может временно иметь старую копию состояния.

Поэтому необходим механизм synchronization.

---

### Правило 8. Учитывайте races

Особенно:

```text
navigation
multiple tabs
multiple UI contexts
concurrent messages
async operations
```

---

### Правило 9. UI — это projection

Popup, Side Panel и Options не должны быть независимыми источниками истины.

Они представляют application state.

---

### Правило 10. Failure одного context не должен разрушать всю систему

Архитектура должна поддерживать:

```text
restart
reconnect
retry
reinitialize
degrade
recover
```

---

# Extension Runtime как miniature distributed system

В результате Manifest V3 extension можно концептуально представить так:

```text
              ┌──────────────────────────────┐
              │       Browser Platform       │
              └──────────────┬───────────────┘
                             │
                    Extension Runtime
                             │
      ┌──────────────┬───────┼───────┬──────────────┐
      │              │       │       │              │
      ▼              ▼       ▼       ▼              ▼
    Popup          Panel   Options  Worker      Content
      │              │       │       │              │
      └──────────────┴───────┼───────┴──────────────┘
                             │
                       Message Protocol
                             │
                             ▼
                       State Manager
                             │
                             ▼
                          Storage
```

Именно поэтому сложное extension уже нельзя эффективно проектировать только как набор файлов:

```text
manifest.json
popup.js
background.js
content.js
```

Нужно проектировать **систему взаимодействующих runtime components**.

---

# Главный архитектурный вывод

Manifest V3 заставляет разработчика отказаться от модели:

```text
"У меня есть одно JavaScript-приложение."
```

и перейти к модели:

```text
"У меня есть несколько независимых runtime contexts,
которые совместно реализуют одно приложение."
```

Это принципиально другой способ мышления.

Можно сформулировать его так:

> **Extension — это distributed application running inside the browser.**

А значит, такие понятия, как:

```text
state synchronization
message protocols
event routing
idempotency
failure recovery
lifecycle management
race conditions
distributed UI
```

становятся не академическими концепциями, а практическими инструментами проектирования.

Именно этот переход — от **API-level thinking** к **runtime-level thinking** — является одной из ключевых границ между простым browser extension и профессиональной Extension Platform Architecture.
