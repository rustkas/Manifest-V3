# Глава 9. Content Scripts

Content Scripts — один из центральных механизмов Manifest V3.

Если Extension Page позволяет расширению работать **внутри собственного UI**, а Service Worker — выполнять **background logic**, то Content Script решает совершенно другую задачу:

> **Content Script позволяет расширению взаимодействовать с содержимым веб-страницы.**

Например, расширение может:

* прочитать заголовок статьи;
* найти элементы DOM;
* изменить страницу;
* добавить собственный интерфейс;
* отслеживать действия пользователя;
* извлечь структурированные данные;
* реагировать на изменения страницы;
* передать данные Service Worker.

Упрощённая архитектура:

```text
                  Browser Tab
                       │
                       ▼
                ┌─────────────┐
                │ Web Page    │
                │             │
                │ HTML / DOM  │
                └──────┬──────┘
                       │
                       ▼
                Content Script
                       │
                       │ messaging
                       ▼
                Service Worker
```

Content Script является одним из главных мостов между:

```text
Extension
```

и:

```text
Web Page
```

---

# 9.1. Назначение Content Scripts

Content Script — JavaScript-код расширения, который браузер выполняет в контексте конкретной веб-страницы.

Например:

```text
https://example.com/article
```

может получить:

```text
content.js
```

После инъекции:

```text
Web Page
│
├── HTML
├── CSS
├── Page JavaScript
│
└── Content Script
```

Content Script получает возможность работать с DOM страницы.

Например:

```javascript
const title = document.querySelector("h1");

console.log(title?.textContent);
```

---

# Основные задачи Content Script

Content Script особенно хорошо подходит для задач типа:

```text
Read page
     ↓
Analyze DOM
     ↓
Extract data
     ↓
Modify DOM
     ↓
Add UI
     ↓
Send result to extension
```

Например, extension для чтения статей может:

```text
Article
   │
   ▼
Content Script
   │
   ├── find <article>
   ├── extract paragraphs
   ├── detect language
   └── collect metadata
           │
           ▼
      Service Worker
```

---

# Content Script не является Web Page Script

Это очень важное различие.

На странице могут существовать:

```text
Page JavaScript
```

и:

```text
Content Script
```

Они не являются одним и тем же JavaScript runtime.

Упрощённо:

```text
                Web Page
                    │
        ┌───────────┴───────────┐
        │                       │
   Page JavaScript        Content Script
        │                       │
   Page World              Isolated World
```

По умолчанию Content Script работает в **isolated world**.

Это означает, что extension получает собственную JavaScript environment, изолированную от page scripts.

При этом Content Script может работать с DOM страницы.

---

# Один DOM — разные JavaScript environments

Это кажется парадоксальным, но является фундаментальным свойством browser extensions.

Можно представить:

```text
               Same Document
                     │
             ┌───────┴───────┐
             │               │
        Page World       Isolated World
             │               │
       Page JS             Content Script
             │               │
             └────── DOM ────┘
```

Поэтому:

```javascript
document.querySelector("h1")
```

может работать в Content Script, хотя сам Content Script не является обычным page script.

---

# Что Content Script может делать?

Типичный Content Script:

```javascript
const title =
    document.querySelector("h1");

if (title) {
    title.style.outline = "2px solid red";
}
```

Он изменяет DOM текущей страницы.

Можно также слушать события:

```javascript
document.addEventListener("click", event => {
    console.log(event.target);
});
```

И наблюдать изменения:

```javascript
const observer =
    new MutationObserver(() => {
        console.log("DOM changed");
    });

observer.observe(document.body, {
    childList: true,
    subtree: true
});
```

---

# Content Script как page adapter

Очень полезно рассматривать Content Script как **adapter между extension и конкретным сайтом**.

Например:

```text
Generic Extension
        │
        ▼
Content Script
        │
        ▼
Specific Website
```

Content Script знает:

* где находится нужный элемент;
* как устроен DOM;
* какие данные нужно извлечь;
* какие элементы нужно изменить.

А Service Worker может оставаться независимым от конкретной страницы.

---

# 9.2. `content_scripts` в manifest

Самый традиционный способ автоматической инъекции Content Script — объявить его в `manifest.json`.

Например:

```json
{
  "manifest_version": 3,
  "name": "Page Analyzer",
  "version": "1.0.0",

  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Теперь браузер знает:

> Когда открывается URL, соответствующий этому pattern, нужно загрузить `content.js`.

---

# Минимальная структура

```text
extension/
│
├── manifest.json
└── content.js
```

`manifest.json`:

```json
{
  "manifest_version": 3,
  "name": "Demo",
  "version": "1.0.0",

  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

`content.js`:

```javascript
console.log("Content Script loaded");

console.log(document.title);
```

---

# Что происходит после загрузки страницы?

Упрощённо:

```text
User opens:

https://example.com/article

        ↓

Browser checks manifest

        ↓

matches:
https://example.com/*

        ↓

MATCH

        ↓

Load content.js

        ↓

Execute Content Script
```

---

# Content Script declaration

Поле:

```json
"content_scripts": []
```

содержит набор деклараций.

Например:

```json
{
  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "js": [
        "content.js"
      ],
      "run_at": "document_idle"
    }
  ]
}
```

Это декларативная модель:

```text
Manifest
   ↓
Browser
   ↓
Matching
   ↓
Injection
```

Разработчику не нужно вручную вызывать injection при каждой загрузке страницы.

---

# 9.3. `matches`

`matches` определяет, на каких URL Content Script должен автоматически запускаться.

Например:

```json
"matches": [
  "https://example.com/*"
]
```

означает:

```text
https://example.com/
https://example.com/about
https://example.com/article/123
https://example.com/products/item
```

---

# Match pattern

Match pattern состоит из нескольких частей:

```text
scheme://host/path
```

Например:

```text
https://example.com/*
```

Здесь:

```text
scheme = https
host   = example.com
path   = /*
```

---

# Несколько сайтов

Можно указать массив:

```json
"matches": [
  "https://example.com/*",
  "https://example.org/*"
]
```

Теперь:

```text
example.com
     +
example.org
```

оба подходят.

---

# Все страницы домена

Например:

```json
"matches": [
  "https://example.com/*"
]
```

означает все подходящие HTTP(S) URL на этом host.

---

# Поддомены

Здесь необходимо внимательно проектировать match pattern.

Например, pattern:

```text
https://*.example.com/*
```

предназначен для соответствующего host hierarchy.

Это может охватывать:

```text
https://www.example.com/
https://shop.example.com/
https://news.example.com/
```

При работе с permissions и content scripts всегда следует проверять точную семантику match patterns, а не предполагать её.

---

# `http` и `https` — разные схемы

Например:

```json
"matches": [
  "https://example.com/*"
]
```

не следует автоматически воспринимать как:

```text
http://example.com/*
```

Если расширение должно работать с обоими протоколами, это нужно выразить соответствующими patterns.

---

# Несколько patterns

Например:

```json
"matches": [
  "https://example.com/*",
  "https://*.example.org/*",
  "http://localhost/*"
]
```

Это позволяет достаточно точно определить область действия Content Script.

---

# 9.4. `exclude_matches`

Иногда нельзя просто перечислить разрешённые страницы.

Нужно сказать:

> Работать почти везде в этой области, кроме определённых URL.

Для этого используется:

```json
"exclude_matches"
```

Например:

```json
{
  "matches": [
    "https://example.com/*"
  ],
  "exclude_matches": [
    "https://example.com/private/*"
  ],
  "js": [
    "content.js"
  ]
}
```

Теперь:

```text
https://example.com/article
        ↓
Content Script запускается

https://example.com/private/account
        ↓
Content Script не запускается
```

---

# `matches` + `exclude_matches`

Архитектурно:

```text
Candidate URLs
      │
      ▼
   matches
      │
      ▼
Possible injection
      │
      ▼
exclude_matches
      │
      ▼
Final URLs
```

Это удобный механизм для построения точной области действия.

---

# Зачем исключать страницы?

Например, extension работает на:

```text
https://example.com/*
```

но не должен работать на:

```text
https://example.com/editor/*
```

потому что Content Script:

* может конфликтовать с редактором;
* не нужен на служебных страницах;
* может ухудшать производительность;
* может нарушить UI.

Тогда:

```json
"exclude_matches": [
  "https://example.com/editor/*"
]
```

---

# 9.5. `include_globs`

`include_globs` позволяет дополнительно фильтровать URL с помощью glob patterns.

Например:

```json
{
  "matches": [
    "https://example.com/*"
  ],
  "include_globs": [
    "*article*"
  ],
  "js": [
    "content.js"
  ]
}
```

Теперь URL должен соответствовать общей области `matches` и дополнительному glob.

---

# Почему существуют и `matches`, и `include_globs`?

Потому что они решают немного разные задачи.

`matches`:

```text
scheme + host + path
```

представляет основную security-oriented область.

`include_globs`:

```text
additional URL filtering
```

позволяет дополнительно сузить выбор.

---

# Комбинация фильтров

Упрощённо можно мыслить так:

```text
URL
 │
 ▼
matches
 │
 ▼
include_globs
 │
 ▼
exclude_matches
 │
 ▼
exclude_globs
 │
 ▼
Inject
```

На практике важно знать точную семантику комбинации этих полей и тестировать patterns на реальных URL.

---

# Пример

```json
{
  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],

      "include_globs": [
        "*article*"
      ],

      "exclude_globs": [
        "*draft*"
      ],

      "js": [
        "content.js"
      ]
    }
  ]
}
```

Концептуально:

```text
https://example.com/article/123
        ↓
MATCH

https://example.com/article/draft/123
        ↓
EXCLUDED
```

---

# Когда использовать glob filtering?

Обычно:

```text
matches
```

должен быть основным механизмом.

`include_globs` и `exclude_globs` полезны, когда требуется дополнительная фильтрация URL.

Не стоит строить чрезмерно сложную систему patterns без необходимости.

Чем сложнее patterns, тем сложнее поддерживать manifest.

---

# 9.6. `exclude_globs`

`exclude_globs` — дополнительный способ исключить URL на основании glob pattern.

Например:

```json
"exclude_globs": [
  "*admin*"
]
```

Вместе с:

```json
"matches": [
  "https://example.com/*"
]
```

можно исключить URL, соответствующие этому дополнительному шаблону.

---

# Пример архитектуры

```json
{
  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "exclude_matches": [
        "https://example.com/private/*"
      ],
      "include_globs": [
        "*article*"
      ],
      "exclude_globs": [
        "*draft*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Это уже достаточно сложное правило.

Поэтому хорошее правило проектирования:

> **Сначала сделайте простейший корректный `matches`, а дополнительные фильтры добавляйте только при реальной необходимости.**

---

# 9.7. `run_at`

`run_at` определяет, когда Content Script должен быть выполнен относительно загрузки документа.

Основные варианты:

```text
document_start
document_end
document_idle
```

---

# `document_start`

```json
"run_at": "document_start"
```

Content Script запускается очень рано в процессе загрузки документа.

Концептуально:

```text
Navigation
   ↓
Document created
   ↓
Content Script
   ↓
Page continues loading
```

Это полезно, когда extension должен вмешаться максимально рано.

---

# Когда нужен `document_start`?

Например:

* ранняя инициализация;
* установка page hooks;
* раннее наблюдение за DOM;
* предотвращение определённых page behaviours, если архитектура это допускает.

Но ранняя инъекция означает, что DOM может быть ещё практически пустым.

Поэтому:

```javascript
document.querySelector("main")
```

может вернуть:

```text
null
```

---

# `document_end`

```json
"run_at": "document_end"
```

Content Script запускается после формирования DOM.

Упрощённо:

```text
HTML parsing
      ↓
DOM available
      ↓
Content Script
```

Это удобнее, если основная задача — работать с уже созданным DOM.

---

# `document_idle`

```json
"run_at": "document_idle"
```

Это стандартный и часто наиболее удобный вариант.

Браузер выбирает подходящий момент после того, как документ и ресурсы достигли достаточно поздней стадии загрузки.

Для большинства обычных DOM-oriented Content Scripts можно начинать именно с:

```json
"run_at": "document_idle"
```

---

# Сравнение

| `run_at`         | Когда                | Типичные задачи             |
| ---------------- | -------------------- | --------------------------- |
| `document_start` | Очень рано           | раннее вмешательство        |
| `document_end`   | После построения DOM | DOM processing              |
| `document_idle`  | Позже, в idle phase  | большинство обычных scripts |

---

# Не путайте `run_at` и lifecycle

`run_at` отвечает на вопрос:

> **Когда начать выполнение Content Script при загрузке документа?**

Он не отвечает на вопрос:

> **Как долго Content Script должен работать?**

Это разные концепции.

---

# SPA и `run_at`

Современные сайты часто являются Single Page Applications.

Например:

```text
https://example.com/app
```

переходит:

```text
/app
   ↓
/app/products
   ↓
/app/product/123
```

без полной перезагрузки документа.

Content Script не обязательно будет автоматически перезапущен при каждой такой client-side navigation.

Поэтому для SPA часто требуется дополнительная логика:

```text
MutationObserver
+
history/navigation detection
+
DOM state management
```

---

# 9.8. `all_frames`

По умолчанию Content Script обычно внедряется только в основной frame страницы.

Но веб-страница может содержать:

```html
<iframe src="https://example.com/widget"></iframe>
```

Получаем:

```text
Top Frame
│
└── iframe
```

Если нужно выполнять Content Script также во frames, используется:

```json
"all_frames": true
```

---

# Без `all_frames`

```json
{
  "matches": [
    "https://example.com/*"
  ],
  "js": [
    "content.js"
  ]
}
```

Концептуально:

```text
Top Frame
   ↓
Content Script

iframe
   ↓
No Content Script
```

---

# С `all_frames`

```json
{
  "matches": [
    "https://example.com/*"
  ],
  "all_frames": true,
  "js": [
    "content.js"
  ]
}
```

Теперь браузер может внедрять Content Script в подходящие frames.

```text
Top Frame
   ↓
Content Script

iframe
   ↓
Content Script
```

Но важно:

> `all_frames: true` не означает "внедрить абсолютно в любой iframe".

Каждый frame всё равно должен соответствовать условиям инъекции и ограничениям browser security model.

---

# Почему frames важны?

Некоторые сайты строятся так:

```text
Page
├── Header
├── Main
└── iframe
      └── Application
```

Если нужный UI находится внутри iframe, Content Script, работающий только в top frame, может его не видеть.

---

# Frame-specific architecture

Можно представить:

```text
Tab
│
├── Frame 0
│    └── content.js
│
├── Frame 1
│    └── content.js
│
└── Frame 2
     └── content.js
```

Каждый injected Content Script работает в своём frame context.

---

# 9.9. `match_about_blank`

Особый случай — страницы и frames с URL:

```text
about:blank
```

или некоторыми другими специальными origins.

Например:

```text
https://example.com
       │
       └── iframe
             │
             └── about:blank
```

У iframe URL:

```text
about:blank
```

но его содержимое может быть создано страницей, которая соответствует вашему match pattern.

Для таких сценариев существует:

```json
"match_about_blank": true
```

---

# Зачем это нужно?

Рассмотрим:

```text
Parent Page
https://example.com

        │
        ▼

iframe
about:blank
```

Если extension должен работать и внутри такого frame, `match_about_blank` может быть необходим.

---

# Важное ограничение

`about:blank` сам по себе не означает:

> "Content Script можно запускать везде."

Browser должен установить соответствующую relationship с родительским документом и применить остальные правила injection.

Поэтому этот параметр следует рассматривать как специальное дополнение к нормальным match conditions.

---

# Пример

```json
{
  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "all_frames": true,
      "match_about_blank": true,
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Теперь extension ориентирован не только на top-level page, но и на подходящие frames, включая соответствующие `about:blank` scenarios.

---

# 9.10. Автоматическая инъекция

Автоматическая инъекция — наиболее простой способ использования Content Scripts.

Вы объявляете:

```json
"content_scripts": [
    {
        "matches": [
            "https://example.com/*"
        ],
        "js": [
            "content.js"
        ]
    }
]
```

После этого браузер сам решает:

```text
URL
 ↓
Does it match?
 ↓
Yes
 ↓
Inject content.js
```

---

# Почему это удобно?

Разработчику не нужно отслеживать каждую navigation event.

Browser сам занимается:

* match patterns;
* document lifecycle;
* injection;
* frame selection;
* execution timing.

---

# Автоматическая инъекция как declarative model

Это хороший пример принципа Manifest V3:

```text
Developer
    │
    ▼
Declarative Manifest
    │
    ▼
Browser
    │
    ├── match URL
    ├── check conditions
    ├── inject
    └── execute
```

Вместо:

```text
Developer manually controls everything
```

часть логики передаётся браузеру.

---

# Автоматическая инъекция — не всегда лучший вариант

Она хороша, когда:

```text
Every matching page
        ↓
Needs the script
```

Но если Content Script нужен только после действия пользователя:

```text
User clicks "Analyze"
        ↓
Inject script
```

может быть лучше programmatic injection.

---

# 9.11. Dynamic content scripts

Manifest V3 также позволяет регистрировать Content Scripts динамически.

Это особенно полезно, когда список scripts или их параметры должны изменяться во время работы extension.

Для этого используются APIs `chrome.scripting`.

---

# Static vs Dynamic

## Static

```text
manifest.json
     ↓
content_scripts
     ↓
Browser
     ↓
Automatic injection
```

## Dynamic

```text
Service Worker
     ↓
chrome.scripting
     ↓
Register script
     ↓
Browser
     ↓
Injection
```

---

# Почему dynamic registration полезна?

Представим extension, где пользователь выбирает:

```text
Enabled sites:

[x] example.com
[x] example.org
[ ] example.net
```

Вместо того чтобы жёстко зашить всю конфигурацию в manifest, extension может динамически управлять зарегистрированными scripts.

---

# Концептуальный пример

```javascript
await chrome.scripting.registerContentScripts([
    {
        id: "page-analyzer",
        matches: [
            "https://example.com/*"
        ],
        js: [
            "content.js"
        ]
    }
]);
```

После регистрации браузер может автоматически inject этот script на соответствующие страницы.

---

# Dynamic registration — persistent configuration

Здесь важно понимать, что dynamic registration отличается от обычного:

```text
executeScript()
```

Dynamic registration создаёт зарегистрированный Content Script, который браузер затем может применять согласно его configuration.

То есть:

```text
Register
   ↓
Browser remembers registration
   ↓
Matching pages
   ↓
Injection
```

Это особенно полезно для управляемых пользовательских конфигураций.

---

# Удаление dynamic script

Если script больше не нужен, его можно удалить через соответствующий API.

Концептуально:

```javascript
await chrome.scripting.unregisterContentScripts({
    ids: ["page-analyzer"]
});
```

Получаем:

```text
Registered
    ↓
Unregister
    ↓
No longer registered
```

---

# Почему нужно давать script `id`?

Например:

```javascript
{
    id: "page-analyzer",
    matches: ["https://example.com/*"],
    js: ["content.js"]
}
```

ID позволяет затем однозначно управлять registration.

---

# Dynamic Content Scripts и permissions

Очень важный момент:

> Dynamic registration не отменяет permission model.

Если extension не имеет необходимых прав для соответствующей страницы, нельзя считать, что `chrome.scripting` магически обходит security boundaries.

Permissions, host permissions и runtime grants остаются частью общей архитектуры.

---

# 9.12. Programmatic injection

Programmatic injection — это когда extension явно говорит браузеру:

> Выполни этот Content Script на этой странице сейчас.

Вместо:

```text
Manifest
   ↓
Automatic injection
```

получаем:

```text
User action / event
       ↓
Service Worker
       ↓
chrome.scripting.executeScript()
       ↓
Target tab/frame
```

---

# Пример

Service Worker:

```javascript
chrome.action.onClicked.addListener(
    async (tab) => {

        await chrome.scripting.executeScript({
            target: {
                tabId: tab.id
            },
            files: [
                "content.js"
            ]
        });
    }
);
```

Теперь script запускается после клика пользователя на Extension Action.

---

# Почему это полезно?

Представим extension:

> Analyze current page.

Нет смысла запускать:

```text
content.js
```

на каждой странице пользователя.

Гораздо эффективнее:

```text
User opens page
        ↓
Nothing happens

User clicks Analyze
        ↓
Inject content.js
        ↓
Analyze page
```

Это:

* уменьшает overhead;
* уменьшает количество background work;
* уменьшает поверхность воздействия;
* делает permission model понятнее.

---

# Static injection

```text
Every matching page
       ↓
Inject
```

# Programmatic injection

```text
Only when needed
       ↓
Inject
```

---

# `executeScript()`

Основной API:

```javascript
chrome.scripting.executeScript(...)
```

Например:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId: tab.id
    },
    files: [
        "content.js"
    ]
});
```

---

# Injection function

Можно также инжектировать функцию.

Например:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId: tab.id
    },
    func: () => {
        return document.title;
    }
});
```

Результат может быть возвращён в calling context через механизм API.

Это очень удобно для небольших операций.

---

# Но не превращайте `executeScript()` в RPC framework

Плохая архитектура:

```text
Service Worker
      │
      ├── executeScript(function A)
      ├── executeScript(function B)
      ├── executeScript(function C)
      ├── executeScript(function D)
      └── executeScript(function E)
```

Если логика становится сложной, лучше создать полноценный Content Script:

```text
Service Worker
      │
      ▼
Content Script
      │
      ├── DOM
      ├── UI
      ├── observers
      └── page logic
```

# 9.13. `chrome.scripting`

`chrome.scripting` — основной namespace Manifest V3 для программного управления scripts.

Он используется для:

* programmatic injection;
* dynamic content script registration;
* управления registered scripts;
* выполнения JavaScript в target contexts.

---

# `executeScript()`

Базовый сценарий:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    files: ["content.js"]
});
```

---

# Target

Target определяет, куда должен быть инжектирован script.

Минимально:

```javascript
{
    tabId: 123
}
```

Можно также указывать frame:

```javascript
{
    tabId: 123,
    frameIds: [0]
}
```

Это особенно важно для страниц с iframe.

---

# `allFrames`

В зависимости от API и сценария можно указать target, охватывающий frames.

Концептуально:

```text
Tab
│
├── Frame 0
├── Frame 1
└── Frame 2
```

и injection:

```text
Target
   ↓
Selected frames
```

Это позволяет точно контролировать область выполнения.

---

# File injection

Наиболее простой production-friendly вариант:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    files: [
        "content.js"
    ]
});
```

---

# Function injection

Для маленькой операции:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    func: () => {
        document.body.dataset.analyzed = "true";
    }
});
```

---

# Arguments

Для function injection также можно передавать сериализуемые аргументы.

Концептуально:

```javascript
await chrome.scripting.executeScript({
    target: {
        tabId
    },
    func: (value) => {
        document.body.dataset.value = value;
    },
    args: ["example"]
});
```

---

# `chrome.scripting` и permissions

Programmatic injection требует соответствующих extension permissions.

В частности, архитектура обычно связана с:

```json
"permissions": [
  "scripting"
]
```

и соответствующими host permissions или другим допустимым основанием для injection.

Например:

```json
{
  "permissions": [
    "scripting"
  ],

  "host_permissions": [
    "https://example.com/*"
  ]
}
```

---

# Важный security principle

`chrome.scripting` — мощный API.

Он позволяет extension запускать код в web page contexts.

Поэтому:

```text
scripting
+
host permissions
```

нужно рассматривать как значительную capability.

Не следует запрашивать:

```text
<all_urls>
```

только потому, что:

```text
"chrome.scripting"
```

кажется удобным.

# 9.14. Content Script lifecycle

Content Script имеет собственный lifecycle, связанный прежде всего с документом/frame, в который он был инжектирован.

Упрощённо:

```text
Page Navigation
      │
      ▼
Document created
      │
      ▼
Injection
      │
      ▼
Content Script starts
      │
      ▼
Content Script runs
      │
      ▼
Page remains
      │
      ▼
Navigation / Frame destroyed
      │
      ▼
Content Script context destroyed
```

---

# Начало lifecycle

Для static content script:

```text
Manifest
    ↓
URL matches
    ↓
run_at
    ↓
Content Script starts
```

Для programmatic injection:

```text
Event
   ↓
executeScript()
   ↓
Injection
   ↓
Execution
```

---

# Content Script не является permanent process

Очень важно не думать:

```text
Content Script
   =
background process
```

Нет.

Content Script существует в рамках соответствующего page/frame context.

Когда document исчезает:

```text
Document destroyed
        ↓
Content Script destroyed
```

---

# Navigation

Например:

```text
https://example.com/page1
```

Content Script:

```text
content.js
```

Пользователь переходит:

```text
https://example.com/page2
```

При новой navigation создаётся новый document.

Если `page2` соответствует `matches`, Content Script может быть инжектирован снова.

Получаем:

```text
page1
  ↓
content.js instance #1
  ↓
navigation
  ↓
page2
  ↓
content.js instance #2
```

---

# Это особенно важно для SPA

В SPA может произойти:

```text
page1
  ↓
history.pushState()
  ↓
page2
```

без полного document navigation.

Поэтому:

```text
Browser navigation lifecycle
```

и:

```text
Application routing lifecycle
```

могут быть разными.

---

# Content Script state

Предположим:

```javascript
let state = {
    initialized: true
};
```

Этот state существует только внутри конкретного Content Script context.

При уничтожении документа:

```text
state
   ↓
destroyed
```

Если состояние должно сохраняться:

```text
Content Script
      ↓
Messaging
      ↓
Service Worker
      ↓
Storage
```

---

# Инициализация должна быть idempotent

Очень полезный принцип для Content Scripts:

> **Повторный запуск не должен ломать страницу.**

Например, плохой код:

```javascript
const button =
    document.createElement("button");

document.body.append(button);
```

Если script запустится дважды:

```text
button
button
```

---

# Лучше использовать marker

Например:

```javascript
if (document.documentElement.dataset
    .myExtensionInitialized) {
    return;
}

document.documentElement.dataset
    .myExtensionInitialized = "true";
```

Теперь:

```text
First execution
    ↓
initialize

Second execution
    ↓
detect marker
    ↓
skip
```

Это особенно полезно в сложных SPA environments.

---

# MutationObserver и lifecycle

Если сайт динамически изменяет DOM:

```text
Initial DOM
   ↓
JavaScript
   ↓
DOM changes
   ↓
new elements
```

Content Script может использовать:

```javascript
const observer =
    new MutationObserver(
        mutations => {
            // process changes
        }
    );

observer.observe(
    document.body,
    {
        childList: true,
        subtree: true
    }
);
```

Но observer тоже является частью lifecycle.

При уничтожении document он исчезает вместе с context.

---

# Cleanup

Если Content Script создаёт:

* event listeners;
* MutationObservers;
* timers;
* DOM elements;
* subscriptions;

следует учитывать их lifecycle.

Например:

```javascript
const observer =
    new MutationObserver(...);

observer.observe(...);
```

Если script имеет собственный long-running lifecycle внутри текущего document, нужно предусмотреть отключение observer, когда это необходимо.

# Content Script и Service Worker

Очень распространённая архитектура:

```text
             Web Page
                 │
                 ▼
          Content Script
                 │
             message
                 │
                 ▼
          Service Worker
                 │
       ┌─────────┼─────────┐
       │         │         │
    Storage    Network    APIs
```

Например, Content Script извлекает:

```javascript
const article = {
    title: document.querySelector("h1")?.textContent,
    url: location.href
};
```

и отправляет:

```javascript
chrome.runtime.sendMessage({
    type: "ARTICLE_FOUND",
    article
});
```

Service Worker принимает:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender) => {

        if (message.type === "ARTICLE_FOUND") {
            processArticle(message.article);
        }
    }
);
```

---

# Почему не выполнять всё в Content Script?

Потому что Content Script предназначен прежде всего для page integration.

Например:

```text
Content Script
    ↓
DOM extraction
    ↓
Send data
```

а:

```text
Service Worker
    ↓
Network
    ↓
Storage
    ↓
Browser APIs
```

Это разделение ответственности.

---

# Content Script как thin layer

Очень хорошая архитектурная модель:

```text
                    Service Worker
                         │
                    Application
                       Logic
                         │
                      Message
                         │
                         ▼
                  Content Script
                         │
                  Page Adapter
                         │
                         ▼
                      DOM
```

То есть Content Script может быть относительно тонким слоем, который адаптирует конкретную веб-страницу к общей логике extension.

---

# Пример: универсальный Article Extractor

Допустим, мы создаём extension:

> Extract article data.

Content Script:

```text
DOM
 │
 ├── find title
 ├── find author
 ├── find date
 └── find article body
       │
       ▼
    structured data
       │
       ▼
    messaging
       │
       ▼
Service Worker
       │
       ├── storage
       ├── API
       └── processing
```

Это гораздо лучше, чем пытаться реализовать всю систему в Content Script.

# Static vs Dynamic vs Programmatic

Теперь можно сравнить три основных способа.

| Подход                   | Когда используется                                      |
| ------------------------ | ------------------------------------------------------- |
| Static `content_scripts` | Script нужен автоматически на matching pages            |
| Dynamic registration     | Нужна динамическая конфигурация persistent registration |
| `executeScript()`        | Script нужен прямо сейчас по событию                    |

---

# Static injection

```text
manifest.json
      ↓
Browser
      ↓
matching URL
      ↓
content.js
```

Пример:

```json
{
  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

---

# Dynamic registration

```text
Service Worker
      ↓
registerContentScripts()
      ↓
Browser registration
      ↓
matching page
      ↓
content.js
```

Подходит для:

* пользовательских настроек;
* динамической конфигурации;
* включения/выключения functionality.

---

# Programmatic injection

```text
User action
     ↓
Service Worker
     ↓
executeScript()
     ↓
Content Script
```

Подходит для:

* "Analyze current page";
* "Extract data now";
* одноразовых операций;
* функций, которые не нужны на каждой странице.

---

# Как выбрать подход?

Задайте вопрос:

### Script нужен на каждой подходящей странице?

```text
Да
 ↓
Static content_scripts
```

### Script должен автоматически работать, но правила меняются?

```text
Да
 ↓
Dynamic registration
```

### Script нужен только после конкретного действия?

```text
Да
 ↓
Programmatic injection
```

# Production-like пример

Рассмотрим extension:

> **Web Data Extractor**

Пользователь открывает:

```text
https://shop.example.com/product/123
```

Extension должен извлечь:

```json
{
  "name": "...",
  "price": "...",
  "sku": "..."
}
```

Но анализировать все страницы постоянно не нужно.

Тогда архитектура:

```text
User
 │
 │ clicks "Extract"
 ▼
Popup
 │
 │ request
 ▼
Service Worker
 │
 │ executeScript()
 ▼
Content Script
 │
 ├── DOM
 ├── extract product
 └── validate data
 │
 ▼
Service Worker
 │
 ├── storage
 └── processing
```

Это эффективная архитектура.

# Безопасность Content Scripts

Content Script работает с **недоверенным web content**.

Поэтому нельзя предполагать:

```text
DOM
=
trusted data
```

Например:

```javascript
const title =
    document.querySelector("h1")
        ?.textContent;
```

`title` — данные страницы.

Их нельзя автоматически считать безопасными.

---

# Особенно опасен `innerHTML`

Плохой вариант:

```javascript
output.innerHTML = pageTitle;
```

Если `pageTitle` контролируется страницей, это может создать XSS risk.

Безопаснее:

```javascript
output.textContent = pageTitle;
```

---

# Content Script и security boundary

Правильная модель:

```text
Web Page
   │
   │ untrusted input
   ▼
Content Script
   │
   │ validate / sanitize
   ▼
Extension
```

Content Script должен рассматриваться как boundary adapter.

---

# Message validation

Если Content Script отправляет:

```javascript
chrome.runtime.sendMessage({
    type: "SAVE",
    data: pageData
});
```

Service Worker не должен безусловно доверять:

```text
message.data
```

Нужно проверять:

```text
message.type
data structure
data types
allowed values
size
```

Например:

```javascript
if (
    message?.type !== "SAVE" ||
    typeof message.data !== "object"
) {
    return;
}
```

Для production систем нужна более строгая schema validation.

---

# Content Script и MAIN world

По умолчанию:

```text
Content Script
      ↓
Isolated World
```

Если же требуется page-level JavaScript integration:

```text
Content Script
      ↓
MAIN world
```

Но MAIN world следует рассматривать как недоверенную среду.

Архитектура:

```text
Service Worker
      │
      ▼
Content Script
      │
      ▼
MAIN world
      │
      ▼
Page API
```

Privileged operations должны оставаться за extension-controlled contexts.

```text
   ↓
Content Script
   ↓
Document destroyed
   ↓
Content Script destroyed
```

---

### 12. Content Script не должен хранить критическое persistent state

Для этого лучше использовать:

```text
Content Script
      ↓
Messaging
      ↓
Service Worker
      ↓
Storage
```

---

### 13. Content Script лучше проектировать как page adapter

Идеальная архитектурная роль:

```text
Web Page
    ↓
Content Script
    ↓
Structured Data
    ↓
Service Worker
    ↓
Application Logic
```

---

## Ключевая архитектурная формула главы

Content Script — это не "JavaScript, который magically запускается на сайте".

Это отдельный execution context, управляемый browser security model:

```text
                 URL matching
                      │
                      ▼
               Injection Policy
                      │
                      ▼
               Content Script
                      │
             ┌────────┴────────┐
             │                 │
       Isolated World      MAIN world
             │                 │
             └────────┬────────┘
                      │
                      ▼
                   Page DOM
                      │
                      ▼
                Page Integration
                      │
                      ▼
                  Messaging
                      │
                      ▼
               Service Worker
```

Именно поэтому профессиональная работа с Content Scripts требует одновременно понимать **match patterns, permissions, frames, lifecycle, isolated worlds, `chrome.scripting` и messaging**. Content Script — это место, где Web Platform непосредственно соприкасается с Extension Platform.
