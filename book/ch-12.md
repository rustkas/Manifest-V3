# Глава 12. Service Worker Lifecycle

В предыдущей главе мы рассмотрели основную идею background Service Worker в Manifest V3: это **event-driven runtime**, а не постоянно работающий процесс.

Теперь необходимо разобраться в его жизненном цикле подробнее.

Для обычного JavaScript-приложения разработчик часто мыслит так:

```text
start application
      ↓
initialize state
      ↓
application runs
      ↓
state remains in memory
      ↓
application stops
```

Для Manifest V3 Service Worker правильнее использовать другую модель:

```text
                    EVENT
                      │
                      ▼
                 COLD START
                      │
                      ▼
              INITIALIZATION
                      │
                      ▼
               EVENT HANDLER
                      │
                      ▼
               ASYNC WORK
                      │
                      ▼
                PERSIST STATE
                      │
                      ▼
                WORK FINISHES
                      │
                      ▼
             WORKER MAY STOP
                      │
                      │
                  new event
                      │
                      └──────────► COLD START
```

Это означает, что Service Worker необходимо проектировать с учётом **непредсказуемого прекращения runtime**.

Главная идея главы:

> **Service Worker должен быть готов исчезнуть после выполнения работы и восстановить необходимое состояние при следующем запуске.**

---

# 12.1. Worker как ephemeral runtime

Слово **ephemeral** означает:

> существующий ограниченное время; временный.

Именно так следует воспринимать Service Worker Manifest V3.

Он существует:

```text
пока браузеру нужен его runtime
```

а не:

```text
пока пользователь не закроет браузер
```

---

## Постоянный процесс

Традиционная модель:

```text
┌───────────────────────────────────────┐
│          Background Process            │
│                                       │
│  start ─────────────────────── stop   │
│             постоянно                 │
│             работает                  │
└───────────────────────────────────────┘
```

Service Worker:

```text
Event
  │
  ▼
┌──────────────┐
│    Worker    │
│    starts    │
└──────┬───────┘
       │
       ▼
    execute
       │
       ▼
    finish
       │
       ▼
┌──────────────┐
│    Worker    │
│    becomes   │
│   inactive   │
└──────────────┘
```

---

## Почему это важно?

Предположим, вы написали:

```javascript
let user = null;
let cache = new Map();
let counter = 0;
```

Разработчик может подсознательно предполагать:

```text
user
cache
counter
```

существуют всё время.

Но это не гарантируется.

После нового запуска:

```text
user    → null
cache   → empty
counter → 0
```

Это новый JavaScript runtime.

---

## RAM — временное состояние

Поэтому полезно разделять:

```text
Runtime state
      │
      ▼
JavaScript memory
```

и:

```text
Persistent state
      │
      ▼
chrome.storage / IndexedDB
```

Первое предназначено для текущего выполнения.

Второе — для состояния, которое должно пережить lifecycle worker.

---

## Правильная ментальная модель

Service Worker:

```text
             ┌─────────────┐
             │   Storage   │
             └──────┬──────┘
                    │
                 restore
                    │
                    ▼
             ┌─────────────┐
             │   Worker    │
             └──────┬──────┘
                    │
                  event
                    │
                    ▼
                 process
                    │
                    ▼
                 persist
                    │
                    ▼
             Worker stops
```

---

# 12.2. Event listeners

Service Worker в первую очередь существует для обработки событий.

Поэтому одна из его главных задач при загрузке:

> зарегистрировать event listeners.

Например:

```javascript
chrome.runtime.onInstalled.addListener(() => {
    console.log("Extension installed");
});
```

Или:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {
        console.log(message);
    }
);
```

Или:

```javascript
chrome.commands.onCommand.addListener(
    command => {
        console.log(command);
    }
);
```

---

## Listener registration

Можно представить worker следующим образом:

```text
service-worker.js
       │
       ├── register onInstalled
       ├── register onMessage
       ├── register onCommand
       ├── register onAlarm
       └── register onClicked
```

После регистрации:

```text
Worker
  │
  ▼
wait for event
```

---

## Почему listeners должны регистрироваться быстро?

Представьте:

```javascript
initializeHugeApplication();

chrome.runtime.onMessage.addListener(
    handleMessage
);
```

Если initialization выполняется долго, архитектура становится сложной и хрупкой.

Гораздо лучше:

```javascript
chrome.runtime.onMessage.addListener(
    handleMessage
);

chrome.commands.onCommand.addListener(
    handleCommand
);
```

А дополнительную работу выполнять непосредственно при необходимости.

---

## Хороший entry point

Например:

```javascript
chrome.runtime.onInstalled.addListener(
    handleInstalled
);

chrome.runtime.onMessage.addListener(
    handleMessage
);

chrome.commands.onCommand.addListener(
    handleCommand
);

chrome.alarms.onAlarm.addListener(
    handleAlarm
);
```

Такой файл является своего рода **event registry**.

---

# Event listener ≠ постоянно работающий код

Это принципиально.

Когда вы пишете:

```javascript
chrome.runtime.onMessage.addListener(
    handleMessage
);
```

вы не говорите:

> "запусти `handleMessage()` сейчас и держи его работающим".

Вы говорите:

> "когда произойдёт это событие, вызови данный обработчик".

То есть:

```text
REGISTER
   ↓
WAIT
   ↓
EVENT
   ↓
HANDLER
```

---

# Event-driven architecture

Именно поэтому Service Worker можно представить как:

```text
                 ┌──────────────┐
                 │ Event source │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │   Listener   │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │    Handler   │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │    Result    │
                 └──────────────┘
```

---

# 12.3. Cold start

**Cold start** — это запуск нового экземпляра Service Worker.

Для пользователя это может быть незаметно.

Но архитектурно происходит примерно следующее:

```text
Worker does not exist
        │
        ▼
Browser needs worker
        │
        ▼
Load service-worker.js
        │
        ▼
Create JavaScript runtime
        │
        ▼
Execute top-level code
        │
        ▼
Register listeners
        │
        ▼
Handle event
```

---

## Cold start ≠ extension installation

Это очень важное различие.

Extension может быть установлен:

```text
Day 1
```

а Service Worker запускаться:

```text
Day 1
Day 1
Day 2
Day 5
Day 5
Day 12
...
```

Каждый такой запуск потенциально создаёт новый runtime.

---

# Что происходит при cold start?

Допустим:

```javascript
console.log("Service Worker started");

chrome.runtime.onMessage.addListener(
    handleMessage
);
```

При запуске:

```text
1. Load JS
2. Execute top-level code
3. Register listeners
4. Process event
```

---

## Top-level code

Поэтому необходимо внимательно относиться к коду:

```javascript
const cache = loadHugeDataset();
```

или:

```javascript
initializeEverything();
```

или:

```javascript
connectToServer();
```

на верхнем уровне модуля.

Этот код может выполняться при каждом новом запуске worker.

---

# Cold start и стоимость initialization

Предположим:

```javascript
import "./huge-library.js";
import "./analytics.js";
import "./database.js";
import "./everything.js";
```

Если для каждого небольшого события необходимо загружать огромную систему, background runtime становится тяжелее.

Поэтому для MV3 полезна идея:

> **Load what you need when you need it.**

---

## Lazy initialization

Вместо:

```javascript
const database = initializeDatabase();
```

можно архитектурно использовать:

```javascript
async function getDatabase() {
    // initialize when required
}
```

Тогда:

```text
event
  ↓
handler
  ↓
database required?
  ↓
yes
  ↓
initialize
```

---

# Cold start должен быть нормальным сценарием

Нельзя проектировать extension так, будто:

```text
Worker started once
       ↓
everything initialized forever
```

Правильнее:

```text
Worker may start
       ↓
load required state
       ↓
process event
       ↓
finish
       ↓
Worker may disappear
```

---

# 12.4. State persistence

Теперь главный вопрос:

> Где хранить состояние?

Ответ зависит от типа состояния.

---

## Временное состояние

Можно хранить в памяти:

```javascript
const cache = new Map();
```

Например:

```text
cache
temporary calculation
current operation
local optimization
```

Если worker исчезнет — это нормально.

---

## Постоянное состояние

Если данные должны переживать restart:

```text
settings
user preferences
extension configuration
processed IDs
application state
```

их необходимо сохранять в persistent storage.

Например:

```javascript
await chrome.storage.local.set({
    enabled: true
});
```

---

# Source of truth

Очень полезная архитектурная концепция:

```text
               Persistent State
                      │
                      ▼
                Source of Truth
                      │
                      ▼
                Service Worker
                      │
                      ▼
                   RAM cache
```

Не наоборот.

То есть:

```text
RAM
```

может ускорять работу.

Но:

```text
RAM ≠ permanent state
```

---

# Пример

Допустим extension хранит настройки:

```javascript
{
    enabled: true,
    theme: "dark",
    interval: 30
}
```

Плохая архитектура:

```javascript
let settings = {
    enabled: true,
    theme: "dark",
    interval: 30
};
```

Если worker перезапустится, это состояние будет потеряно.

---

# Лучше

```javascript
await chrome.storage.local.set({
    settings: {
        enabled: true,
        theme: "dark",
        interval: 30
    }
});
```

И при необходимости:

```javascript
const {
    settings
} = await chrome.storage.local.get("settings");
```

---

# 12.5. `chrome.storage` вместо global state

Global variables не являются хорошей заменой persistent storage.

Рассмотрим:

```javascript
let settings = {};
```

Это:

```text
global runtime state
```

а:

```javascript
chrome.storage.local
```

это:

```text
persistent extension state
```

---

## Почему global state опасен?

Потому что lifecycle:

```text
Worker starts
   ↓
settings loaded
   ↓
settings modified
   ↓
Worker terminates
   ↓
settings variable disappears
```

При следующем запуске:

```text
Worker starts
   ↓
settings = {}
```

---

# Правильный паттерн

Можно использовать:

```text
Storage
   │
   ▼
load state
   │
   ▼
RAM
   │
   ▼
modify
   │
   ▼
save
```

Например:

```javascript
async function getSettings() {
    const result =
        await chrome.storage.local.get("settings");

    return result.settings ?? {
        enabled: true
    };
}
```

---

# Обновление состояния

Например:

```javascript
async function setEnabled(enabled) {
    await chrome.storage.local.set({
        enabled
    });
}
```

И получение:

```javascript
async function isEnabled() {
    const result =
        await chrome.storage.local.get("enabled");

    return result.enabled ?? true;
}
```

---

# Storage abstraction

В production-like extension полезно не разбрасывать:

```javascript
chrome.storage.local.get(...)
```

по всему проекту.

Можно сделать отдельный модуль:

```text
storage/
    settings.js
    state.js
    cache.js
```

Например:

```javascript
export async function getSettings() {
    const result =
        await chrome.storage.local.get("settings");

    return result.settings;
}
```

Теперь бизнес-логика работает с:

```javascript
const settings = await getSettings();
```

а не знает деталей storage API.

---

# Persistent state и cache

Можно использовать двухуровневую модель:

```text
             Persistent Storage
                    │
                    ▼
                Load once
                    │
                    ▼
                RAM cache
                    │
              ┌─────┴─────┐
              │           │
            read        update
              │           │
              └─────┬─────┘
                    ▼
              persist update
```

Но нужно помнить:

> cache является производной от persistent state.

Если cache исчез:

```text
cache = empty
```

его можно восстановить.

---

# 12.6. Timers и lifecycle

Одна из распространённых ошибок при переходе к MV3 — перенос модели обычного JavaScript-приложения:

```javascript
setInterval(...)
setTimeout(...)
```

в background Service Worker без учёта lifecycle.

---

# Почему timers нельзя считать permanent scheduler?

Например:

```javascript
setInterval(() => {
    sync();
}, 60 * 1000);
```

В обычной странице разработчик может воспринимать это как:

```text
каждую минуту
каждую минуту
каждую минуту
```

Но Service Worker может прекратить выполнение.

Поэтому такой timer не следует воспринимать как надёжный persistent scheduler.

---

# Для периодической работы

В extension background architecture следует рассматривать специализированные extension APIs, в частности:

```text
chrome.alarms
```

Например:

```javascript
chrome.alarms.create("sync", {
    periodInMinutes: 30
});
```

И:

```javascript
chrome.alarms.onAlarm.addListener(
    alarm => {
        if (alarm.name === "sync") {
            sync();
        }
    }
);
```

Получается:

```text
Alarm
  ↓
event
  ↓
Service Worker
  ↓
sync()
```

---

# Timer vs Alarm

Упрощённо:

| Механизм        | Подходит для                                                |
| --------------- | ----------------------------------------------------------- |
| `setTimeout()`  | кратковременной работы текущего runtime                     |
| `setInterval()` | кратковременных повторных операций внутри активного runtime |
| `chrome.alarms` | extension-level scheduled events                            |

Главное:

> Не используйте обычный JavaScript timer как замену persistent background scheduler.

---

# Timeout внутри операции

При этом `setTimeout()` может быть совершенно нормальным:

```javascript
await new Promise(resolve => {
    setTimeout(resolve, 1000);
});
```

если он является частью **текущей операции**.

Проблема начинается тогда, когда вы строите на нём постоянную background architecture.

---

# 12.7. Async operations

Большинство реальной background logic является асинхронной:

```text
Storage
Network
Tabs
Messages
Alarms
Extension APIs
```

Поэтому Service Worker должен быть спроектирован с учётом asynchronous execution.

---

# Promise-based architecture

Современный JavaScript-код обычно выглядит так:

```javascript
async function loadSettings() {
    const result =
        await chrome.storage.local.get("settings");

    return result.settings;
}
```

Затем:

```javascript
chrome.runtime.onMessage.addListener(
    async message => {
        const settings =
            await loadSettings();

        // ...
    }
);
```

Однако при messaging есть важный нюанс: способ обработки ответа должен соответствовать конкретному API и используемой модели callback/Promise. Нельзя автоматически предполагать, что любой `async` listener будет корректным способом отправки ответа.

---

# Async boundaries

Хорошо разделять:

```text
Event
 ↓
Handler
 ↓
Async operation
 ↓
Persistence
 ↓
Response
```

Например:

```javascript
async function handleMessage(message) {
    const settings = await getSettings();

    const result = await performOperation(
        message,
        settings
    );

    await saveResult(result);

    return result;
}
```

---

# Не блокируйте event handler

Плохая архитектура:

```javascript
while (true) {
    // expensive synchronous work
}
```

Service Worker должен выполнять конечную работу.

Если задача тяжёлая:

```text
event
 ↓
validate
 ↓
execute bounded work
 ↓
persist result
 ↓
finish
```

---

# Promise и lifecycle

Важный момент:

> Нельзя проектировать долгую асинхронную операцию так, будто worker гарантированно останется живым неограниченное время.

Поэтому background operations должны быть:

* конечными;
* хорошо обрабатывающими ошибки;
* сохраняющими критическое состояние;
* не зависящими от долгого существования global variables.

---

# Состояние операции

Если операция сложная:

```text
START
 ↓
DOWNLOAD
 ↓
PROCESS
 ↓
SAVE
```

не следует полагаться исключительно на:

```javascript
let currentStep = "DOWNLOAD";
```

Если lifecycle может прерваться, критический progress лучше моделировать явно.

Например:

```javascript
await chrome.storage.local.set({
    job: {
        id,
        status: "downloading"
    }
});
```

---

# Recoverable operations

Тогда после restart:

```text
Worker starts
   ↓
read job state
   ↓
status = downloading
   ↓
determine whether recovery is required
   ↓
continue / retry / mark failed
```

Это уже архитектура устойчивого background runtime.

---

# 12.8. Promise-based APIs

Manifest V3 и современные Chrome extension APIs широко используют Promise-based подход там, где он поддерживается соответствующим API.

Например:

```javascript
const tabs =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });
```

или:

```javascript
const result =
    await chrome.storage.local.get(
        "settings"
    );
```

---

# `async/await`

Для сложного background runtime обычно гораздо удобнее:

```javascript
async function handleEvent() {
    const settings = await getSettings();

    const data = await fetchData(settings);

    await saveData(data);
}
```

чем глубокая цепочка callbacks:

```javascript
getSettings(settings => {
    fetchData(settings, data => {
        saveData(data, () => {
            // ...
        });
    });
});
```

---

# Но `async/await` не отменяет lifecycle

Очень важное правило:

```text
Promise
≠
guaranteed permanent runtime
```

То есть:

```javascript
await longOperation();
```

не означает:

> "Service Worker теперь гарантированно существует сколько угодно долго".

Архитектура должна учитывать ограничения lifecycle и конкретного API.

---

# Error propagation

Асинхронные операции должны иметь обработку ошибок:

```javascript
try {
    const data = await fetchData();

    await saveData(data);
} catch (error) {
    console.error(
        "Operation failed:",
        error
    );
}
```

---

# Почему ошибки особенно важны в Service Worker?

Потому что worker — background runtime.

Пользователь может не видеть:

```text
console
```

и не понимать, что произошло.

Поэтому production-like extension должен иметь:

```text
error handling
logging
retry strategy
persistent operation state
```

где это необходимо.

---

# 12.9. Ошибки и восстановление

Устойчивый background runtime должен предполагать:

```text
network failure
API failure
invalid input
permission failure
storage failure
unexpected exception
worker restart
```

---

# Неудачная модель

```text
event
 ↓
operation
 ↓
error
 ↓
everything stops
```

Лучше:

```text
event
 ↓
validate
 ↓
operation
 ↓
 ┌───────────────┐
 │ success       │
 │ failure       │
 └───────────────┘
       │
       ▼
persist outcome
       │
       ▼
recover / retry / report
```

---

# Retry

Например, network operation:

```text
Attempt 1
   ↓
failure
   ↓
Attempt 2
   ↓
failure
   ↓
Attempt 3
   ↓
success
```

Но retry должен быть ограниченным.

Плохая идея:

```text
retry forever
```

Лучше:

```text
retry N times
```

и затем:

```text
mark failed
```

---

# Persistent failure state

Например:

```javascript
await chrome.storage.local.set({
    sync: {
        status: "failed",
        attempts: 3,
        lastError: "Network error"
    }
});
```

После следующего worker startup можно определить:

```text
sync.status === "failed"
```

и решить:

```text
retry
ignore
notify user
```

---

# Idempotency

Особенно важна для background operations.

Представим:

```text
Event
 ↓
Create record
 ↓
Worker terminates
```

Если событие будет обработано повторно:

```text
Create record
 ↓
Create same record again
```

может появиться duplicate.

---

## Решение

Использовать уникальный operation ID:

```text
operationId = abc123
```

и сохранять результат:

```text
abc123 → completed
```

При повторной обработке:

```text
abc123 already completed
        ↓
skip
```

---

# Transactional thinking

Очень полезно мыслить операциями как:

```text
READ
 ↓
COMPUTE
 ↓
WRITE
```

и определить, что произойдёт при сбое между этапами.

Например:

```text
READ
 ↓
COMPUTE
 ↓
FAIL
 ↓
nothing persisted
```

или:

```text
READ
 ↓
WRITE
 ↓
success
```

---

# Recovery strategy

Для каждой важной операции нужно определить:

```text
What if it fails?

What if it is repeated?

What if worker disappears?

What if browser restarts?

What if network disappears?

What if storage contains partial state?
```

Это уже не просто JavaScript programming.

Это **runtime architecture**.

---

# 12.10. Архитектура устойчивого background runtime

Теперь объединим всё вместе.

Хорошая архитектура Service Worker должна иметь несколько уровней.

```text
                    EVENT
                      │
                      ▼
              ┌──────────────┐
              │ Event Handler│
              └──────┬───────┘
                     │
                     ▼
              ┌──────────────┐
              │  Validation  │
              └──────┬───────┘
                     │
                     ▼
              ┌──────────────┐
              │ Business     │
              │ Logic        │
              └──────┬───────┘
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
       Storage              Extension APIs
          │                     │
          └──────────┬──────────┘
                     │
                     ▼
              ┌──────────────┐
              │ Persist      │
              │ Result       │
              └──────┬───────┘
                     │
                     ▼
                   DONE
```

---

# Слой 1. Event layer

Он принимает:

```text
onInstalled
onMessage
onCommand
onAlarm
onClicked
...
```

Например:

```javascript
chrome.commands.onCommand.addListener(
    handleCommand
);
```

---

# Слой 2. Validation

Нельзя автоматически доверять данным, поступившим от:

* Content Script;
* popup;
* веб-страницы;
* других extension contexts.

Например:

```javascript
function validateMessage(message) {
    return (
        message &&
        typeof message.type === "string"
    );
}
```

Подробнее эту тему мы уже рассматривали в главе о безопасности.

---

# Слой 3. Business Logic

Не стоит помещать всю application logic непосредственно в listener:

```javascript
chrome.runtime.onMessage.addListener(
    async message => {

        // 500 lines of business logic

    }
);
```

Лучше:

```javascript
chrome.runtime.onMessage.addListener(
    handleMessage
);
```

и:

```javascript
async function handleMessage(message) {
    return processCommand(message);
}
```

---

# Слой 4. Persistence

Business logic должна иметь понятный способ работы с состоянием:

```text
Storage
   │
   ▼
Repository / State layer
   │
   ▼
Business logic
```

Например:

```text
storage/
    settings.js
    jobs.js
    cache.js
```

---

# Слой 5. External APIs

Network и extension APIs лучше также изолировать:

```text
services/
    tabs.js
    network.js
    storage.js
    permissions.js
```

Тогда Service Worker становится координатором, а не огромным монолитным файлом.

---

# Production-like architecture

Например:

```text
extension/
│
├── manifest.json
│
├── background/
│   ├── service-worker.js
│   │
│   ├── events/
│   │   ├── messages.js
│   │   ├── commands.js
│   │   ├── alarms.js
│   │   └── installation.js
│   │
│   ├── services/
│   │   ├── tabs.js
│   │   ├── network.js
│   │   └── permissions.js
│   │
│   ├── storage/
│   │   ├── settings.js
│   │   └── state.js
│   │
│   └── domain/
│       └── application.js
│
├── content/
├── popup/
└── options/
```

---

# `service-worker.js` как composition root

В такой архитектуре:

```javascript
import {
    registerMessageHandlers
} from "./events/messages.js";

import {
    registerCommandHandlers
} from "./events/commands.js";

import {
    registerAlarmHandlers
} from "./events/alarms.js";

registerMessageHandlers();
registerCommandHandlers();
registerAlarmHandlers();
```

Service Worker становится:

> точкой сборки background runtime.

Это значительно лучше масштабируется.

---

# Stateless Service Worker

Идеальная концепция:

```text
Service Worker
      │
      ├── receives event
      │
      ├── loads state
      │
      ├── performs computation
      │
      ├── persists result
      │
      └── finishes
```

То есть:

```text
Worker memory
```

не является источником истины.

---

# Durable state

Можно использовать термин:

**durable state**

для состояния, которое должно переживать:

```text
worker restart
browser restart
extension restart
```

В зависимости от требований это может быть:

```text
chrome.storage.local
chrome.storage.sync
IndexedDB
```

Выбор зависит от размера данных, необходимости синхронизации и характера приложения.

---

# Ephemeral state

И наоборот:

**ephemeral state**:

```text
temporary
runtime-only
reconstructable
```

Например:

```javascript
const cache = new Map();
```

Если cache исчез:

```text
load again
```

и система продолжает работать.

---

# Идеальная характеристика cache

Очень хороший архитектурный критерий:

> Если удаление RAM cache ломает extension — вероятно, cache используется неправильно.

Cache должен быть:

```text
rebuildable
```

---

# Архитектура восстановления

Хорошая система:

```text
                Worker starts
                     │
                     ▼
               Load durable state
                     │
                     ▼
               Validate state
                     │
                     ▼
              Register handlers
                     │
                     ▼
                  WAIT
                     │
                   EVENT
                     │
                     ▼
                Execute task
                     │
             ┌───────┴───────┐
             │               │
           success         failure
             │               │
             ▼               ▼
          persist          persist
          result           failure
             │               │
             └───────┬───────┘
                     ▼
                    DONE
                     │
                     ▼
               Worker may stop
```

---

# Архитектурный принцип №1

> **Never assume the worker will be alive later.**

Если важное состояние уже получено и должно сохраниться:

```text
persist it
```

не рассчитывайте:

```javascript
let state = ...
```

---

# Архитектурный принцип №2

> **Make every event handler independently executable.**

То есть обработчик должен уметь:

```text
receive event
     ↓
load required state
     ↓
perform work
     ↓
persist result
```

а не:

```text
receive event
     ↓
hope some global variable
was initialized yesterday
```

---

# Архитектурный принцип №3

> **Make operations recoverable.**

Если worker исчез:

```text
operation interrupted
```

система должна иметь понятную стратегию:

```text
retry
resume
rollback
ignore
mark failed
```

---

# Архитектурный принцип №4

> **Prefer deterministic state transitions.**

Например:

```text
pending
   ↓
running
   ↓
completed
```

или:

```text
pending
   ↓
running
   ↓
failed
```

Состояние можно хранить:

```javascript
{
    status: "running",
    operationId: "abc123"
}
```

---

# Архитектурный принцип №5

> **Separate runtime state from durable state.**

```text
                 State
                   │
           ┌───────┴────────┐
           │                │
           ▼                ▼
       Ephemeral          Durable
           │                │
           ▼                ▼
          RAM             Storage
```

---

# Полный lifecycle

Теперь можно сформулировать полный жизненный цикл:

```text
                    ┌──────────────┐
                    │   REGISTERED │
                    └──────┬───────┘
                           │
                        event
                           │
                           ▼
                    ┌──────────────┐
                    │  COLD START  │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ INITIALIZE   │
                    │ + LISTENERS  │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ HANDLE EVENT │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ ASYNC WORK   │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ PERSIST      │
                    │ RESULT       │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   INACTIVE   │
                    └──────┬───────┘
                           │
                       lifecycle
                           │
                           ▼
                    ┌──────────────┐
                    │ TERMINATED   │
                    └──────┬───────┘
                           │
                       new event
                           │
                           └──────────► COLD START
```

# Практический пример

Предположим, extension должен периодически синхронизировать данные.

Наивная архитектура:

```javascript
setInterval(() => {
    sync();
}, 30 * 60 * 1000);
```

Это плохая модель background runtime.

---

## Event-driven вариант

```text
chrome.alarms
      │
      ▼
onAlarm
      │
      ▼
load settings
      │
      ▼
check whether sync required
      │
      ▼
fetch data
      │
      ▼
save data
      │
      ▼
record sync status
      │
      ▼
finish
```

---

# Если worker исчез во время lifecycle

Следующий запуск может сделать:

```text
load sync state
      │
      ▼
determine last successful sync
      │
      ▼
continue
```

То есть система не зависит от существования конкретного экземпляра worker.

---

# Service Worker как disposable process

Очень полезная ментальная модель:

> **Service Worker — disposable process.**

Его можно представить как объект:

```text
create
  ↓
use
  ↓
discard
```

а не:

```text
create
  ↓
keep forever
```

---

# Почему эта модель важна для будущих глав

Понимание lifecycle понадобится практически во всех последующих темах:

```text
Messaging
     ↓
Worker may disappear

Storage
     ↓
Worker memory is not persistent

Alarms
     ↓
Events replace permanent timers

Content Scripts
     ↓
Communication must tolerate lifecycle

Network
     ↓
Async operations need error handling

Permissions
     ↓
Permission state must be queried when needed
```

---

# Типичные ошибки

### 1. Global state как database

```javascript
let users = [];
```

❌ Нельзя использовать как persistent storage.

---

### 2. `setInterval()` как permanent scheduler

```javascript
setInterval(sync, 60000);
```

❌ Не следует строить на этом долгоживущую background architecture.

---

### 3. Огромный startup

```javascript
initializeEverything();
```

❌ Увеличивает стоимость cold start.

---

### 4. Бесконечный lifecycle

```javascript
while (true) {
    await doSomething();
}
```

❌ Противоречит event-driven модели.

---

### 5. Отсутствие recovery

```text
operation failed
      ↓
nothing
```

❌ Нельзя считать background environment надёжным.

---

### 6. Непредсказуемая бизнес-логика

Если одна и та же операция дважды выполняется:

```text
event
event
```

она не должна неконтролируемо ломать состояние.

---

# Чек-лист устойчивого Service Worker

Перед публикацией extension полезно проверить:

### Lifecycle

* [ ] Worker может быть запущен заново.
* [ ] Worker не зависит от постоянного существования.
* [ ] Cold start корректно работает.
* [ ] Global variables используются только для временного состояния.

### Events

* [ ] Event listeners регистрируются при startup.
* [ ] Каждый handler выполняет ограниченную задачу.
* [ ] Нет бесконечных loops.

### State

* [ ] Persistent state находится в storage.
* [ ] Cache можно восстановить.
* [ ] Worker restart не уничтожает критическое состояние.

### Async

* [ ] Promise/async операции корректно обрабатываются.
* [ ] Ошибки не теряются.
* [ ] Длительные операции имеют понятную стратегию завершения.

### Recovery

* [ ] Есть retry strategy.
* [ ] Есть failure state для важных операций.
* [ ] Повторное выполнение не приводит к неконтролируемым duplicate effects.

# Итог главы

Service Worker Manifest V3 следует воспринимать как:

```text
EPHEMERAL
+
EVENT-DRIVEN
+
RESTARTABLE
+
STATE-PERSISTENT
```

То есть:

```text
                 Event
                   │
                   ▼
             Cold Start
                   │
                   ▼
             Register Events
                   │
                   ▼
              Load State
                   │
                   ▼
             Handle Event
                   │
                   ▼
            Async Operation
                   │
                   ▼
             Persist State
                   │
                   ▼
                Finish
                   │
                   ▼
           Worker disappears
                   │
                   │
              new event
                   │
                   ▼
             Cold Start
```

Именно поэтому основное архитектурное правило MV3 можно сформулировать так:

> **Не проектируйте extension вокруг жизни Service Worker. Проектируйте Service Worker вокруг событий и состояния extension.**

Service Worker может исчезнуть — **extension не должен исчезнуть вместе с ним**.

А значит, в следующей части изучения особенно важными становятся механизмы, которые позволяют различным execution contexts взаимодействовать независимо от lifecycle конкретного runtime: **Messaging между Popup, Content Script, Service Worker и другими extension contexts**.
