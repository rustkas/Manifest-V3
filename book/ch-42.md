# Глава 42. Project 2 — Page Modifier

В предыдущей главе мы создали минимальное Manifest V3 extension, состоящее из `manifest.json`, `action` и Popup.

Теперь сделаем следующий шаг.

Наш extension должен начать работать **не только внутри собственного Popup, но и непосредственно внутри веб-страницы**.

Для этого мы используем:

* Content Script;
* `content_scripts`;
* host permissions;
* DOM API;
* `matches`;
* `run_at`;
* обработку DOM;
* безопасную интеграцию со страницей.

Наш проект будет называться:

```text
Page Modifier
```

Его задача очень проста:

> при открытии подходящей веб-страницы extension изменяет её внешний вид.

Например:

```text
Обычная страница
       ↓
Content Script
       ↓
DOM manipulation
       ↓
Изменённая страница
```

---

# 42.1. Что мы создаём

Сделаем extension, который при загрузке страницы:

1. добавляет небольшой информационный блок;
2. изменяет цвет фона страницы;
3. добавляет кнопку `Restore`;
4. позволяет вернуть исходное состояние.

Например:

```text
┌─────────────────────────────────────────────┐
│ Page Modifier                               │
│                                             │
│ This page is controlled by an extension.    │
│ [ Restore ]                                 │
├─────────────────────────────────────────────┤
│                                             │
│             Web page content                │
│                                             │
└─────────────────────────────────────────────┘
```

Архитектура:

```text
Browser
   │
   ▼
Web Page
   │
   ▼
Content Script
   │
   ▼
DOM
```

Это принципиально отличается от предыдущего проекта:

```text
Project 1

Browser
   │
   ▼
Extension
   │
   ▼
Popup
```

Теперь:

```text
Project 2

Browser
   │
   ├── Extension
   │
   └── Web Page
          │
          ▼
     Content Script
          │
          ▼
         DOM
```

---

# 42.2. Почему Content Script нужен отдельно

Extension page и web page являются разными execution contexts.

Наш Popup находится внутри extension:

```text
chrome-extension://...
```

А целевая страница:

```text
https://example.com
```

Popup не должен напрямую выполнять JavaScript внутри страницы.

Вместо этого браузер предоставляет специальный механизм:

```text
Extension
     │
     │ injection
     ▼
Content Script
     │
     ▼
Web Page DOM
```

Content Script становится связующим слоем между extension и содержимым страницы.

# 42.5. `content_scripts`

Главная часть Manifest:

```json
{
    "content_scripts": [
        {
            "matches": [
                "https://example.com/*"
            ],
            "css": [
                "content.css"
            ],
            "js": [
                "content.js"
            ],
            "run_at": "document_idle"
        }
    ]
}
```

Здесь мы говорим браузеру:

> Когда пользователь открывает страницу, соответствующую этому pattern, загрузить CSS и JavaScript extension.

---

# 42.6. `matches`

В нашем случае:

```json
"matches": [
    "https://example.com/*"
]
```

означает:

```text
https://example.com/
https://example.com/about
https://example.com/products/1
https://example.com/foo/bar
```

Все эти URL соответствуют pattern.

Но:

```text
http://example.com/
```

не соответствует, потому что мы указали:

```text
https://
```

---

# 42.7. Почему не использовать `<all_urls>`

Можно было бы написать:

```json
"matches": [
    "<all_urls>"
]
```

Но для учебного проекта это плохая привычка.

`<all_urls>` означает очень широкую область действия.

Лучше начинать с:

```text
минимального scope
```

Например:

```json
"matches": [
    "https://example.com/*"
]
```

Это соответствует Principle of Least Privilege.

---

# 42.8. Content Script автоматически инжектируется браузером

Нам не нужно писать:

```javascript
chrome.scripting.executeScript(...)
```

Браузер сам выполняет injection на основании:

```json
"content_scripts"
```

То есть:

```text
Page navigation
       ↓
Browser checks matches
       ↓
URL matches
       ↓
Browser creates content-script context
       ↓
content.js executes
```

Это называется **declarative content script injection**.

# 42.10. Важный момент: Console Content Script

Здесь легко ошибиться.

Content Script работает в специальном execution context.

Поэтому DevTools может показывать сообщения, связанные с разными contexts.

Это соответствует архитектуре, которую мы рассматривали в главе об Isolated World:

```text
Web Page
   │
   ├── Page JavaScript
   │
   └── Content Script
```

Они работают на одной странице, но их JavaScript environments различаются.

# 42.11. Первый DOM manipulation

Теперь изменим заголовок страницы.

```javascript
const heading = document.querySelector("h1");

if (heading) {
    heading.textContent =
        "Modified by Page Modifier";
}
```

На:

```text
https://example.com/
```

если существует:

```html
<h1>Example Domain</h1>
```

получим:

```html
<h1>Modified by Page Modifier</h1>
```

---

# 42.12. Почему используется проверка `if`

Нельзя предполагать, что элемент существует.

Плохой вариант:

```javascript
document.querySelector("h1").textContent =
    "Modified";
```

Если `h1` отсутствует:

```text
Cannot set properties of null
```

Лучше:

```javascript
const heading = document.querySelector("h1");

if (heading) {
    heading.textContent =
        "Modified by Page Modifier";
}
```

Это особенно важно для extension development.

Web pages находятся **вне нашего контроля**.

---

# 42.13. Страница является недоверенной средой

Extension должен относиться к DOM страницы как к внешней системе.

Мы не знаем:

* существует ли элемент;
* когда он появится;
* будет ли он удалён;
* изменится ли его структура;
* использует ли сайт SPA;
* добавит ли сайт новый DOM;
* изменит ли сайт наш элемент.

Поэтому Content Script должен быть устойчивым.

# 42.15. Почему лучше использовать `textContent`

При работе с недоверенными данными предпочтительнее:

```javascript
element.textContent = value;
```

а не:

```javascript
element.innerHTML = value;
```

Например:

```javascript
const message =
    "<img src=x onerror=alert(1)>";
```

При:

```javascript
element.innerHTML = message;
```

мы передаём браузеру HTML.

При:

```javascript
element.textContent = message;
```

это просто текст.

Получаем важный принцип:

```text
Untrusted data
      ↓
textContent
      ↓
Text
```

вместо:

```text
Untrusted data
      ↓
innerHTML
      ↓
HTML parsing
```

# 42.21. Изменение background

Добавим:

```javascript
document.documentElement
    .classList
    .add("page-modifier-active");
```

И в CSS:

```css
html.page-modifier-active {
    background: #f5f5f5;
```

Однако это может не изменить вид страницы, если сайт имеет собственный background на `body` или других элементах.

```javascript
document.body.style.backgroundColor =
```

Но для production extension прямое изменение inline styles не всегда лучший вариант.

Предпочтительнее добавлять class:

```javascript
document.body.classList.add(
    "page-modifier-active"
);
```

и:

```css
body.page-modifier-active {
    background-color: #f5f5f5;
}
```

# 42.22. Полный `content.js`

Теперь соберём всё вместе:

```javascript
console.log("Page Modifier loaded");

const body = document.body;

if (!body) {
    console.warn(
        "Page Modifier: document.body is not available"
    );
} else {

    body.classList.add(
        "page-modifier-active"
    );

    const panel =
        document.createElement("div");

    panel.className =
        "page-modifier-panel";

    const message =
        document.createElement("div");

    message.textContent =
        "This page is controlled by Page Modifier.";

    const button =
        document.createElement("button");

    button.textContent =
        "Restore";

    button.addEventListener(
        "click",
        () => {

            body.classList.remove(
                "page-modifier-active"
            );

            panel.remove();
        }
    );

    panel.appendChild(message);
    panel.appendChild(button);

    body.prepend(panel);
}
```

# 42.28. `run_at`

Мы указали:

```json
"run_at": "document_idle"
```

Это означает, что браузер старается выполнить Content Script после того, как документ достаточно загружен для нормальной работы.

Другие варианты:

```text
document_start
document_end
document_idle
```

---

# 42.29. `document_start`

При:

```json
"run_at": "document_start"
```

script запускается очень рано.

Это полезно, например, когда extension должен вмешаться в раннюю фазу загрузки.

Но DOM в этот момент может быть ещё далеко не полностью построен.

Поэтому:

```javascript
document.querySelector(...)
```

может вернуть `null`.

---

# 42.30. `document_end`

При:

```json
"run_at": "document_end"
```

DOM документа уже построен, но дополнительные ресурсы страницы могут ещё загружаться.

Это может быть полезно, когда extension должен работать с ранним DOM.

---

# 42.31. `document_idle`

Наш выбор:

```json
"run_at": "document_idle"
```

часто удобен для обычной DOM manipulation.

Для простых page modifiers это хороший default.

Но это не означает:

> Страница полностью закончила работу.

Особенно на современных SPA.

---

# 42.32. Проблема современных сайтов

Сегодняшняя web page часто выглядит не так:

```text
HTML
  ↓
DOM
  ↓
Done
```

а так:

```text
HTML
  ↓
JavaScript application
  ↓
API requests
  ↓
DOM
  ↓
More JavaScript
  ↓
More DOM
  ↓
User interaction
  ↓
More DOM
```

Например:

```text
React
Vue
Angular
Svelte
Next.js
```

могут создавать и удалять DOM после первоначальной загрузки.

Поэтому:

```javascript
document.querySelector(...)
```

однократно может быть недостаточно.

# 42.33. Dynamic DOM

Представим:

```text
Content Script
      ↓
querySelector("#app")
      ↓
null
```

а через 500 ms сайт создаёт:

```html
<div id="app">
```

Наш extension уже не найдёт его.

Для динамических сайтов понадобится:

```text
MutationObserver
```

---

# 42.34. MutationObserver

Простейший пример:

```javascript
const observer =
    new MutationObserver(() => {

        const target =
            document.querySelector("#app");

        if (target) {
            console.log(
                "#app found"
            );
        }
    });

observer.observe(
    document.documentElement,
    {
        childList: true,
        subtree: true
    }
);
```

Теперь extension наблюдает за изменениями DOM.

---

# 42.35. Но MutationObserver нельзя использовать бездумно

Если наблюдать весь документ:

```javascript
observer.observe(
    document.documentElement,
    {
        childList: true,
        subtree: true
    }
);
```

на очень динамичном сайте можно получать огромное количество событий.

Например:

```text
DOM mutation
DOM mutation
DOM mutation
DOM mutation
...
```

Поэтому production extension должен:

* ограничивать область наблюдения;
* быстро фильтровать события;
* не выполнять тяжёлую работу на каждую mutation;
* отключать observer, когда он больше не нужен.

# 42.36. Идемпотентность Content Script

Есть ещё одна важная проблема.

Представим, что функция выполняется дважды:

```javascript
addPanel();
addPanel();
```

Мы получим:

```text
┌─────────────────────┐
│ Page Modifier       │
└─────────────────────┘

┌─────────────────────┐
│ Page Modifier       │
└─────────────────────┘
```

Это плохо.

Лучше сделать операцию идемпотентной.

Например:

```javascript
if (
    document.querySelector(
        ".page-modifier-panel"
    )
) {
    return;
}
```

Теперь повторный запуск не создаёт второй panel.

---

# 42.37. Идемпотентная реализация

Можно написать:

```javascript
function createPanel() {

    const existing =
        document.querySelector(
            ".page-modifier-panel"
        );

    if (existing) {
        return existing;
    }

    const panel =
        document.createElement("div");

    panel.className =
        "page-modifier-panel";

    panel.textContent =
        "Page Modifier";

    document.body.prepend(panel);

    return panel;
}
```

Теперь:

```javascript
createPanel();
createPanel();
createPanel();
```

не создаёт три панели.

Это очень важная техника для реальных extensions.

# 42.38. Content Script и CSS isolation

CSS Content Script может влиять на страницу, а CSS страницы может потенциально влиять на DOM extension UI в зависимости от конкретной архитектуры и контекста.

Поэтому сложные extension UI должны быть защищены от конфликтов.

Возможные подходы:

```text
namespace CSS
Shadow DOM
CSS isolation strategies
```

Например:

```text
.page-modifier-*
```

намного безопаснее, чем:

```text
.button
.container
.panel
```

# 42.39. Shadow DOM

Для сложного UI можно создать:

```javascript
const host =
    document.createElement("div");

const shadow =
    host.attachShadow({
        mode: "open"
    });
```

После этого:

```text
Page
 │
 ├── обычный DOM
 │
 └── Extension Host
       │
       └── Shadow Root
             │
             ├── HTML
             └── CSS
```

Это значительно уменьшает вероятность CSS conflicts.

Shadow DOM мы подробно рассмотрим в следующих главах.

# 42.40. Content Script не является Page Script

Это один из наиболее важных моментов всей главы.

На странице существуют концептуально два JavaScript мира:

```text
Web Page
│
├── Page JavaScript
│
└── Content Script
```

Content Script имеет:

* доступ к DOM;
* специальный extension environment;
* доступ к разрешённым extension APIs.

Но он не является обычным:

```html
<script>
```

который загрузил сам сайт.

Это и есть **Isolated World**.

---

# 42.41. Почему это важно

Предположим, сайт объявил:

```javascript
const appState = {
    loggedIn: true
};
```

Content Script не должен автоматически считать, что это его глобальная переменная.

И наоборот.

Page JavaScript и Content Script имеют разные JavaScript environments.

При этом:

```text
DOM
```

является общей точкой взаимодействия.

Упрощённо:

```text
Page JS
    │
    │
    ▼
   DOM
    ▲
    │
    │
Content Script
```

---

# 42.42. Что Content Script может делать

Content Script может:

* читать DOM;
* изменять DOM;
* создавать элементы;
* устанавливать event listeners;
* использовать `MutationObserver`;
* работать с некоторыми extension APIs;
* отправлять messages другим extension contexts.

Например:

```javascript
document.querySelector("button");
```

или:

```javascript
document.body.appendChild(element);
```

---

# 42.43. Что Content Script не должен делать

Content Script не должен предполагать, что он является главным владельцем страницы.

Например, опасно:

```javascript
document.body.innerHTML = "...";
```

потому что это может уничтожить:

* DOM сайта;
* event listeners;
* состояние frontend application;
* пользовательский интерфейс.

Правильнее изменять только конкретные элементы:

```javascript
const element =
    document.querySelector(".target");

if (element) {
    element.textContent =
        "Modified";
}
```

---

# 42.44. Безопасность DOM manipulation

Основное правило:

> Любые данные, полученные со страницы, следует считать недоверенными.

Например:

```javascript
const title =
    document.title;
```

не следует автоматически вставлять как HTML.

Плохо:

```javascript
element.innerHTML =
    title;
```

Лучше:

```javascript
element.textContent =
    title;
```

Ещё лучше — явно разделять:

```text
data
  ↓
validation
  ↓
DOM representation
```

# 42.45. Host permissions и Content Scripts

В нашем примере мы используем:

```json
"matches": [
    "https://example.com/*"
]
```

Это определяет страницы, на которых браузер должен запускать Content Script.

Это не то же самое, что:

```json
"host_permissions": [...]
```

Хотя concepts связаны, их не следует механически смешивать.

Для declarative `content_scripts` область injection задаётся непосредственно через `matches`.

---

# 42.46. Почему это важно архитектурно

Нужно различать:

```text
Where may code run?
```

и:

```text
Where may extension perform privileged operations?
```

Это разные вопросы.

В extension architecture:

```text
Injection scope
        +
Permission scope
        +
API capability
```

образуют security model.

---

# 42.47. Более универсальный пример

Для учебного проекта мы ограничили extension:

```json
"matches": [
    "https://example.com/*"
]
```

Для собственного тестового сайта можно использовать:

```json
"matches": [
    "https://my-test-site.example/*"
]
```

А для extension, которое действительно предназначено для большого количества сайтов, scope должен быть обоснован функциональностью.

Не следует начинать с:

```json
"matches": [
    "<all_urls>"
]
```

только потому, что это проще.

---

# 42.48. Типичный Content Script architecture

Production extension обычно не должен выглядеть так:

```javascript
// 1000 lines
// everything here
```

Лучше разделять:

```text
Content Script
│
├── DOM adapter
├── UI
├── page observer
├── state
├── event handling
└── communication
```

Например:

```text
content/
├── index.js
├── dom.js
├── ui.js
├── observer.js
└── styles.css
```

`index.js` становится entry point.

---

# 42.49. Entry point

Например:

```javascript
import {
    createPanel
} from "./ui.js";

import {
    observePage
} from "./observer.js";

createPanel();

observePage();
```

А архитектура:

```text
content.js
    │
    ├── ui.js
    │
    ├── dom.js
    │
    └── observer.js
```

становится намного проще для сопровождения.

# 42.52. Новая архитектура

После второго проекта наше понимание extension выглядит так:

```text
                    Browser
                       │
            ┌──────────┴──────────┐
            │                     │
       Extension                Web Page
            │                     │
            │                     │
            ▼                     │
      Extension Page              │
                                  │
                                  ▼
                           Content Script
                                  │
                                  ▼
                                 DOM
```

Но пока отсутствует важнейший элемент:

```text
Service Worker
```

# 42.53. Следующая проблема

Представим, что пользователь хочет:

```text
изменить страницу
+
сохранить настройки
+
получить данные с сервера
+
управлять несколькими вкладками
```

Content Script уже не является идеальным местом для всей этой логики.

Появляется необходимость:

```text
Content Script
      │
      ▼
Service Worker
      │
      ├── Storage
      ├── Network
      ├── Tabs
      └── Extension state
```

То есть следующий архитектурный уровень:

```text
Page
  │
  ▼
Content Script
  │
  │ message
  ▼
Service Worker
```

---

# 42.54. Главный архитектурный урок

Content Script следует воспринимать не как «JavaScript, который магически попал на сайт», а как **специализированный runtime-компонент extension**.

Его задача:

```text
Page Integration
```

То есть:

```text
DOM
Events
Page Observation
UI Injection
Page Interaction
```

А задачи вроде:

```text
Persistent State
Network
Scheduling
Cross-tab coordination
Business logic
```

обычно лучше размещать в других extension contexts.

Таким образом, хорошая архитектура постепенно приобретает вид:

```text
                 Extension
                     │
          ┌──────────┴──────────┐
          │                     │
   Service Worker         Content Script
          │                     │
          │                     ▼
          │                    DOM
          │                     │
          └──── messages ───────┘
```

# Итог главы

В проекте **Page Modifier** мы впервые создали extension, который работает непосредственно с веб-страницей.

Мы научились:

* объявлять `content_scripts`;
* использовать `matches`;
* автоматически инжектировать JavaScript;
* использовать `run_at`;
* работать с DOM страницы;
* создавать и удалять DOM elements;
* использовать `textContent`;
* добавлять CSS;
* избегать CSS naming conflicts;
* учитывать динамический DOM;
* использовать `MutationObserver`;
* проектировать идемпотентную DOM manipulation;
* понимать отличие Content Script от Page Script;
* ограничивать scope extension;
* рассматривать веб-страницу как внешнюю и недоверенную среду.

Главное изменение по сравнению с первым проектом:

```text
Project 1

Extension
   │
   └── Popup
```

превратилось в:

```text
Project 2

Extension
   │
   └── Content Script
           │
           ▼
       Web Page
           │
           ▼
          DOM
```

Именно здесь начинается настоящая интеграция extension с Web Platform.

Следующий логичный шаг — добавить **Service Worker и communication layer**, чтобы Content Script перестал быть изолированным скриптом страницы и стал частью полноценного распределённого extension runtime.
