# Глава 5. Host Permissions

В предыдущей главе мы рассмотрели общую permission model Manifest V3 и увидели важное различие:

```text
permissions
    ↓
доступ к Extension APIs

host_permissions
    ↓
доступ к определённым web origins
```

Теперь разберём вторую часть подробно.

`host_permissions` — одна из наиболее важных и одновременно наиболее часто неправильно понимаемых возможностей Manifest V3.

Если обычный permission отвечает примерно на вопрос:

> **"Какую возможность браузера хочет использовать extension?"**

то host permission отвечает на другой вопрос:

> **"С какими веб-ресурсами extension разрешено взаимодействовать?"**

Например:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

означает, что extension запрашивает host access для URL, соответствующих этому шаблону.

Это особенно важно для extensions, которые:

* внедряют Content Scripts;
* анализируют веб-страницы;
* модифицируют DOM;
* работают с несколькими сайтами;
* выполняют cross-origin network requests;
* взаимодействуют с определёнными web origins.

---

# 5.1. Что такое host permission

Начнём с простого примера.

Представим extension:

> **Page Translator**

Он должен работать на страницах:

```text
https://example.com/*
```

и:

```text
https://news.example.org/*
```

Тогда manifest может содержать:

```json
{
  "manifest_version": 3,

  "name": "Page Translator",
  "version": "1.0.0",

  "host_permissions": [
    "https://example.com/*",
    "https://news.example.org/*"
  ]
}
```

Здесь extension говорит браузеру:

> Мне требуется host access к этим URL patterns.

---

## Host permission — не "доступ к Интернету"

Это важное различие.

Если написать:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

это **не означает**:

> extension получает полный доступ ко всему Интернету.

Он получает соответствующий доступ только к указанному host pattern.

Например:

```text
https://example.com/page
https://example.com/news
https://example.com/products/123
```

соответствуют:

```text
https://example.com/*
```

Но:

```text
https://google.com/
https://example.org/
https://another.com/
```

не соответствуют.

---

## Host permission как security boundary

Можно представить:

```text
                    Extension
                        │
                  Host Permission
                        │
              ┌─────────┴─────────┐
              │                   │
          Allowed              Not allowed
              │                   │
      example.com            other-site.com
```

Таким образом, host permissions являются частью security boundary extension.

---

# 5.2. Match patterns

Host permissions используют специальный синтаксис — **match patterns**.

Базовая форма выглядит примерно так:

```text
scheme://host/path
```

Например:

```text
https://example.com/*
```

Здесь есть три компонента:

```text
https://example.com/*
│      │             │
│      │             └── path
│      └──────────────── host
└─────────────────────── scheme
```

---

## Scheme

Основные схемы:

```text
http
https
```

Например:

```text
http://example.com/*
```

и:

```text
https://example.com/*
```

— это разные patterns.

---

## Host

Host может быть конкретным:

```text
example.com
```

или использовать wildcard для поддоменов:

```text
*.example.com
```

Например:

```text
https://*.example.com/*
```

может охватывать соответствующие поддомены:

```text
https://www.example.com/
https://app.example.com/
https://api.example.com/
```

---

## Path

В host permissions path обычно задаётся через wildcard:

```text
https://example.com/*
```

Это означает соответствующие URL на этом host.

---

# 5.3. `http://*/*`

Рассмотрим:

```text
http://*/*
```

Разберём его:

```text
http://*/*
│     │ │
│     │ └── любой путь
│     └──── любой host
└────────── HTTP
```

То есть pattern охватывает HTTP URLs.

Например:

```text
http://example.com/
http://example.org/
http://localhost/
http://test.local/page
```

могут соответствовать этому pattern.

Но HTTPS:

```text
https://example.com/
```

— уже другой scheme.

---

## Почему HTTP и HTTPS разделены?

Потому что:

```text
http
```

и:

```text
https
```

— разные schemes и разные security properties.

Поэтому:

```text
http://*/*
```

не следует автоматически воспринимать как:

```text
http + https
```

---

## Нужно ли использовать HTTP?

Для современного Web чаще всего предпочтительнее HTTPS.

Поэтому extension, которому необходим только защищённый веб, обычно не должен автоматически запрашивать:

```text
http://*/*
```

если HTTP ему не нужен.

---

# 5.4. `https://*/*`

Аналогично:

```text
https://*/*
```

означает соответствующий доступ к HTTPS URLs независимо от host.

Например:

```text
https://example.com/
https://google.com/
https://github.com/
https://news.example.org/
```

могут соответствовать этому pattern.

Но:

```text
http://example.com/
```

не соответствует.

---

## Сравнение

```text
http://*/*
```

→ HTTP hosts.

```text
https://*/*
```

→ HTTPS hosts.

```text
https://example.com/*
```

→ только `example.com` по HTTPS.

```text
https://*.example.com/*
```

→ соответствующие поддомены `example.com` по HTTPS.

---

# 5.5. Ограничение доменами

На практике лучше всего давать extension максимально конкретный host access.

Допустим, мы создаём extension для внутренней CRM:

```text
https://crm.mycompany.com/
```

Тогда вместо:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

разумнее использовать:

```json
{
  "host_permissions": [
    "https://crm.mycompany.com/*"
  ]
}
```

Это значительно более узкая permission boundary.

---

## Несколько доменов

Extension может работать с несколькими hosts:

```json
{
  "host_permissions": [
    "https://crm.mycompany.com/*",
    "https://app.mycompany.com/*",
    "https://api.mycompany.com/*"
  ]
}
```

Теперь permission model явно показывает архитектуру приложения:

```text
Extension
   │
   ├── CRM
   ├── Application
   └── API
```

---

## Поддомены

Если extension должен работать с несколькими поддоменами:

```json
{
  "host_permissions": [
    "https://*.example.com/*"
  ]
}
```

Например:

```text
https://www.example.com/
https://app.example.com/
https://admin.example.com/
```

Это удобнее, чем перечислять каждый поддомен отдельно.

Но wildcard расширяет scope.

Поэтому его следует использовать только тогда, когда это действительно требуется.

---

## Два разных архитектурных подхода

### Подход A — широкий wildcard

```json
{
  "host_permissions": [
    "https://*.example.com/*"
  ]
}
```

### Подход B — конкретные hosts

```json
{
  "host_permissions": [
    "https://app.example.com/*",
    "https://www.example.com/*"
  ]
}
```

Если extension работает только с двумя конкретными hosts, второй вариант точнее.

---

# 5.6. `<all_urls>`

Особое значение имеет:

```text
<all_urls>
```

Например:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

Это очень широкая host permission.

Она охватывает соответствующие HTTP/HTTPS URLs и ряд других поддерживаемых URL schemes в соответствии с правилами browser extension platform.

Главная идея:

> Extension заявляет потребность работать практически с любыми обычными веб-страницами.

---

## Когда `<all_urls>` оправдан

Например:

### Ad blocker

Он должен анализировать страницы различных сайтов.

```text
Google
Wikipedia
News
Social networks
Shopping
...
```

### Universal page analyzer

Extension предназначен именно для анализа любых веб-страниц.

### Accessibility extension

Например, инструмент, который должен улучшать доступность произвольных сайтов.

В таких случаях широкий host access может быть частью самой функции продукта.

---

## Когда `<all_urls>` не оправдан

Представим extension:

> GitHub Issue Helper

который работает только на:

```text
https://github.com/*
```

Тогда:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

будет неоправданно широким.

Лучше:

```json
{
  "host_permissions": [
    "https://github.com/*"
  ]
}
```

---

## Широкое разрешение — это не обязательно плохое разрешение

Важно избежать неправильного вывода:

> `<all_urls>` всегда плохо.

Это неверно.

Правильнее:

> `<all_urls>` должен соответствовать функциональности extension.

Если приложение действительно является universal web extension, широкое разрешение может быть оправдано.

Проблема возникает тогда, когда scope permissions намного шире scope продукта.

---

# 5.7. Host permissions и Content Scripts

Это одна из самых важных связей в Manifest V3.

Рассмотрим:

```json
{
  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Здесь мы видим `matches`.

Content Script будет автоматически инжектироваться на страницы, соответствующие этому pattern.

Например:

```text
https://example.com/
https://example.com/news
https://example.com/products/1
```

---

## `matches` и `host_permissions` — не одно и то же

Это очень важное различие.

`content_scripts.matches` отвечает на вопрос:

> **На каких страницах должен инжектироваться этот Content Script?**

`host_permissions` отвечает на вопрос:

> **Какие host access capabilities запрашивает extension?**

Например:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ],

  "content_scripts": [
    {
      "matches": [
        "https://example.com/*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Здесь две декларации связаны, но выполняют разные функции.

---

## Почему это важно?

Потому что extension architecture может быть сложнее.

Например:

```text
Host Permission
      │
      ├── API access
      │
      └── Network access

Content Script matches
      │
      └── Automatic script injection
```

Поэтому нельзя воспринимать:

```text
matches
```

как просто ещё одно имя для:

```text
host_permissions
```

---

## Example

Допустим:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ],

  "content_scripts": [
    {
      "matches": [
        "https://example.com/news/*"
      ],
      "js": [
        "news.js"
      ]
    }
  ]
}
```

Теперь:

```text
Host access:
example.com/*
```

но автоматическая инъекция:

```text
example.com/news/*
```

То есть host permission может быть шире, чем область конкретного Content Script.

Это нормальная архитектура.

---

# 5.8. Host permissions и network requests

Host permissions также важны при работе extension с сетью.

Представим:

```text
Extension
    │
    │ fetch()
    ▼
https://api.example.com
```

Extension может выполнять cross-origin network requests в сценариях, предусмотренных extension platform, при наличии соответствующих permissions.

Например:

```json
{
  "host_permissions": [
    "https://api.example.com/*"
  ]
}
```

Теперь host access к API явно отражён в manifest.

---

## Почему это отличается от обычного сайта?

Обычная страница:

```text
https://my-site.com
```

подчиняется обычной Web security model, включая CORS.

Extension имеет дополнительные возможности, но они также регулируются extension permission model.

Поэтому важно не думать:

> Extension — это JavaScript без CORS.

Правильнее:

> Extension имеет отдельную security model, в которой host permissions являются одной из ключевых частей.

---

## Network architecture

Например:

```text
Popup
  │
  ▼
Service Worker
  │
  │ fetch()
  ▼
API Server
```

Manifest может содержать:

```json
{
  "host_permissions": [
    "https://api.example.com/*"
  ]
}
```

Теперь permission model явно описывает:

```text
Extension
    ↓
API
```

---

## Host permission не заменяет authentication

Очень важно.

Если extension имеет:

```json
{
  "host_permissions": [
    "https://api.example.com/*"
  ]
}
```

это не означает:

> extension автоматически авторизован на API.

Host permission отвечает за capability взаимодействия с origin.

А authentication может по-прежнему требовать:

* cookies;
* tokens;
* OAuth;
* API keys;
* session;
* другие механизмы.

То есть:

```text
Host Permission
       +
Authentication
       ↓
Authorized application operation
```

— это разные уровни.

---

# 5.9. Безопасность host permissions

Host permissions — потенциально очень мощная capability.

Поэтому здесь особенно важен принцип:

> **The broader the host permission, the larger the security boundary.**

Представим два extension.

### Extension A

```json
{
  "host_permissions": [
    "https://crm.example.com/*"
  ]
}
```

### Extension B

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

Если оба имеют одинаковый JavaScript bug, потенциальный scope воздействия у второго значительно шире.

---

## Чем опасен чрезмерный host access?

Extension, имеющее широкие host permissions, потенциально работает с большим количеством веб-контента.

Это увеличивает последствия ошибок в:

* Content Scripts;
* message handlers;
* DOM manipulation;
* data extraction;
* network code;
* authentication;
* storage;
* page bridges.

Поэтому permission scope необходимо рассматривать вместе с кодом.

---

## Content Script + `<all_urls>`

Особенно важная комбинация:

```text
<all_urls>
     +
Content Script
     +
DOM access
```

означает:

> Extension потенциально может работать с DOM большого количества веб-сайтов.

Это может быть полностью оправдано для универсального инструмента.

Но архитектура должна быть очень аккуратной.

---

## Нельзя доверять странице

Представим:

```text
Web Page
    │
    ▼
Content Script
    │
    ▼
Service Worker
```

Page content нельзя автоматически считать trusted data.

Страница может содержать:

* пользовательский ввод;
* HTML;
* произвольный JavaScript;
* malicious content;
* данные, созданные сторонним сайтом.

Поэтому:

```text
Page Data
    ↓
Validate
    ↓
Normalize
    ↓
Process
```

а не:

```text
Page Data
    ↓
Trust
    ↓
Execute
```

---

## Host permissions и data minimization

Если extension работает только на:

```text
https://example.com/*
```

нет причин давать:

```text
<all_urls>
```

Это не просто хороший UX.

Это **снижение потенциального security impact**.

---

# 5.10. Dynamic permission requests

Manifest V3 позволяет строить более динамическую permission model.

Вместо:

```text
Install
   ↓
Request access to everything
```

можно сделать:

```text
Install
   ↓
Basic functionality
   ↓
User selects advanced feature
   ↓
Request additional host access
   ↓
Grant
   ↓
Enable feature
```

Для этого используются optional host permissions.

Например:

```json
{
  "optional_host_permissions": [
    "https://*.example.com/*"
  ]
}
```

---

## Пример

Представим extension:

> Universal Web Exporter

При установке ему не обязательно иметь доступ ко всем сайтам.

Основной интерфейс:

```text
┌───────────────────────────────┐
│ Web Exporter                  │
│                               │
│ Export current page           │
│                               │
│ [Export]                      │
└───────────────────────────────┘
```

Пользователь нажимает:

```text
Export
```

Extension понимает, что ему нужен дополнительный host access.

Тогда архитектура:

```text
User Action
     ↓
Check Permission
     ↓
Permission missing?
     │
     ├── No ──→ Continue
     │
     └── Yes
           ↓
      Request permission
           ↓
       User decision
         /       \
    Granted     Denied
       │           │
       ▼           ▼
     Export     Explain why
```

Это называется **just-in-time permission request**.

---

## Проверка permission

Перед выполнением функциональности можно проверить, есть ли permission:

```javascript
const granted = await chrome.permissions.contains({
  origins: ["https://*.example.com/*"]
});

if (granted) {
  // Continue
}
```

Если permission отсутствует, приложение может предложить пользователю его предоставить.

---

## Удаление permission

Permissions не обязательно должны существовать навсегда.

В соответствующих сценариях extension может отказаться от ранее предоставленной capability:

```javascript
await chrome.permissions.remove({
  origins: ["https://*.example.com/*"]
});
```

Это позволяет строить более динамическую permission model.

Например:

```text
Feature enabled
      ↓
Permission granted
      ↓
Feature no longer needed
      ↓
Permission removed
```

---

# Host Permissions как часть архитектуры

Теперь можно построить полную картину:

```text
                         Extension
                             │
                   ┌─────────┴─────────┐
                   │                   │
              API Permissions     Host Permissions
                   │                   │
             storage/tabs/etc.     Web origins
                                       │
                         ┌─────────────┴─────────────┐
                         │                           │
                    Content Scripts             Network
                         │                           │
                         ▼                           ▼
                      Web Page                   API Server
```

При этом Content Script имеет ещё одну важную характеристику:

```text
Host Permission
       ≠
Content Script Match
```

То есть:

```text
permissions
    ↓
capabilities

host_permissions
    ↓
host access

content_scripts.matches
    ↓
automatic injection targets
```

Это три связанные, но разные концепции.

---

# Практический пример: Web Research Extension

Предположим, мы создаём extension:

> **Research Assistant**

Он должен:

1. работать на страницах Wikipedia;
2. извлекать заголовки;
3. сохранять результаты;
4. обращаться к собственному API;
5. не иметь доступа ко всему Интернету.

Можно начать с:

```json
{
  "manifest_version": 3,

  "name": "Research Assistant",
  "version": "1.0.0",

  "permissions": [
    "storage"
  ],

  "host_permissions": [
    "https://*.wikipedia.org/*",
    "https://api.example.com/*"
  ],

  "content_scripts": [
    {
      "matches": [
        "https://*.wikipedia.org/*"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Обратите внимание на архитектуру:

```text
                    Research Assistant
                            │
              ┌─────────────┴─────────────┐
              │                           │
        wikipedia.org               api.example.com
              │                           │
        Content Script                  fetch()
              │                           │
              └─────────────┬─────────────┘
                            │
                         Extension
                            │
                         Storage
```

Здесь permissions соответствуют реальным функциям приложения.

# Практический пример: Universal Page Analyzer

Теперь другой продукт:

> Extension должен анализировать любую веб-страницу.

Тогда широкое разрешение может быть оправдано:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

и:

```json
{
  "content_scripts": [
    {
      "matches": [
        "<all_urls>"
      ],
      "js": [
        "content.js"
      ]
    }
  ]
}
```

Архитектура:

```text
                    Browser
                       │
                 Any Web Page
                       │
                       ▼
                 Content Script
                       │
                       ▼
                 Extension Runtime
                       │
             ┌─────────┴─────────┐
             │                   │
          Storage              API
```

В этом случае широкий host access является частью самого продукта.

Но безопасность должна быть соответственно более строгой.

---

# Host Permission Decision Tree

При проектировании нового extension полезно пройти следующий алгоритм:

```text
                    Does extension need
                    web page access?
                           │
                    ┌──────┴──────┐
                    │             │
                   No            Yes
                    │             │
                    ▼             ▼
              No host access   Which hosts?
                                  │
                    ┌─────────────┼─────────────┐
                    │             │             │
                 One host     Several hosts   Any site
                    │             │             │
                    ▼             ▼             ▼
              exact host      exact list    <all_urls>
                    │             │             │
                    └─────────────┴─────────────┘
                                  │
                                  ▼
                       Can access be optional?
                              │
                         ┌────┴────┐
                        Yes        No
                         │          │
                         ▼          ▼
                     optional    required
                       host        host
                    permission   permission
```

Это очень простой, но полезный алгоритм.

# Главные выводы главы

### 1. Host permission — это не просто URL configuration

Это security capability:

```text
host permission
       ↓
host access
```

---

### 2. Match pattern имеет структуру

```text
scheme://host/path
```

Например:

```text
https://*.example.com/*
```

---

### 3. `http://*/*` и `https://*/*` различаются

```text
http://*/*
```

— HTTP.

```text
https://*/*
```

— HTTPS.

---

### 4. Лучше ограничивать hosts

Вместо:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

если возможно, использовать:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

---

### 5. `<all_urls>` не является автоматически плохим

Если extension действительно предназначен для работы с любыми веб-страницами, широкая permission может быть необходимой.

Важно соответствие:

```text
Product scope
      ↕
Permission scope
```

---

### 6. `host_permissions` и `content_scripts.matches` — разные вещи

```text
host_permissions
       ↓
host access

content_scripts.matches
       ↓
automatic Content Script injection
```

---

### 7. Host permissions могут участвовать в network architecture

Например:

```text
Extension
    ↓
fetch()
    ↓
API origin
```

при соответствующем host access.

---

### 8. Host access должен проектироваться с точки зрения безопасности

Особенно опасна без необходимости комбинация:

```text
<all_urls>
+
Content Scripts
+
широкий DOM access
```

---

### 9. Optional host permissions позволяют делать permission model динамической

```text
Basic installation
       ↓
User activates feature
       ↓
Request host access
       ↓
Grant
       ↓
Feature enabled
```

---

# Практическое задание

Создайте extension **Site Analyzer**, который должен:

1. работать только на `example.com`;
2. автоматически запускать Content Script на страницах `/articles/`;
3. получать данные с `api.example.com`;
4. сохранять результаты локально;
5. иметь дополнительную функцию анализа другого сайта, permission для которого должен быть optional.

Попробуйте самостоятельно определить:

```text
1. Какие entries должны находиться в permissions?
2. Какие entries должны находиться в host_permissions?
3. Что должно находиться в content_scripts.matches?
4. Нужен ли <all_urls>?
5. Что можно сделать через optional_host_permissions?
6. В какой момент следует запрашивать дополнительный host access?
```

После выполнения упражнения у вас должна появиться следующая архитектурная модель:

```text
                 Site Analyzer
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     Storage       example.com    api.example.com
        │              │              │
        │        Content Script      fetch()
        │              │              │
        └──────────────┼──────────────┘
                       │
                 Extension Runtime
                       │
                 Optional Access
                       │
                       ▼
                Additional Site
```

Следующая глава логично продолжает эту тему с точки зрения безопасности: **как устроена security model Manifest V3, какие trust boundaries существуют между веб-страницей и extension и почему Content Script нельзя считать обычным JavaScript страницы.**
