# Глава 35. Designing an Extension Runtime

В предыдущей главе мы рассматривали архитектурные паттерны Manifest V3 и пришли к важному выводу:

> **Современное browser extension — это не одна JavaScript-программа, а распределённый runtime, состоящий из нескольких execution contexts.**

Popup, Side Panel, Content Script, Service Worker и Options Page имеют разные lifecycle и разные возможности.

Поэтому при создании серьёзного расширения недостаточно просто правильно разместить файлы:

```text
popup/
background/
content/
options/
```

Необходимо спроектировать **runtime** — систему, которая определяет:

* как запускаются contexts;
* как маршрутизируются события;
* где хранится состояние;
* как передаются сообщения;
* как предоставляется доступ к Storage;
* как контролируются permissions;
* как extension взаимодействует с Browser APIs;
* как обрабатываются ошибки;
* как освобождаются ресурсы;
* как наблюдать за работой системы.

Можно представить runtime следующим образом:

```text
                    Browser
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
      Popup       Service Worker   Content Script
        │              │              │
        ▼              ▼              ▼
       Runtime Coordination Layer
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
     State          Transport        Events
       │               │               │
       └───────────────┼───────────────┘
                       ▼
                Application Core
```

В этой главе мы построим такую модель шаг за шагом.

---

# 35.1. Context lifecycle

Первый фундаментальный принцип Extension Runtime:

> **Каждый context имеет собственный lifecycle.**

Это принципиально отличает extension от обычного веб-приложения.

В обычном SPA мы часто имеем:

```text
Page
  ↓
JavaScript application
  ↓
long-running runtime
```

В Manifest V3 такого предположения делать нельзя.

---

## Service Worker lifecycle

Service Worker может пройти через:

```text
Created
   ↓
Started
   ↓
Event handling
   ↓
Idle
   ↓
Suspended / terminated
   ↓
Restarted
```

Следовательно, нельзя считать Service Worker постоянным процессом.

Плохая модель:

```javascript
let currentUser = null;
let cache = {};
let currentJob = null;
```

и предположение:

```text
"Эти данные будут доступны всегда."
```

Это неверно.

---

## Popup lifecycle

Popup ещё более ephemeral:

```text
Closed
   ↓
Opened
   ↓
Interactive
   ↓
Closed
```

После закрытия Popup его runtime исчезает.

Поэтому:

```text
Popup state
```

не должен быть единственным источником истины.

---

## Content Script lifecycle

Content Script связан с жизненным циклом страницы или frame:

```text
Page loaded
   ↓
Content Script injected
   ↓
Running
   ↓
Navigation / reload
   ↓
Destroyed
```

При SPA-сайтах ситуация сложнее.

URL может измениться без полной перезагрузки документа:

```text
/page/a
   ↓
/page/b
   ↓
/page/c
```

а JavaScript context страницы останется существовать.

Поэтому Content Script должен учитывать не только:

```text
document load
```

но и:

```text
SPA navigation
DOM replacement
dynamic content
```

---

## Side Panel lifecycle

Side Panel находится между Popup и обычной постоянно открытой страницей.

Он имеет собственный lifecycle:

```text
Closed
   ↓
Opened
   ↓
Active
   ↓
Hidden / Closed
```

Следовательно, Side Panel также не должен быть единственным владельцем глобального состояния.

---

## Lifecycle как часть архитектуры

Полезно описывать каждый context через четыре характеристики:

```text
Context
  │
  ├── Creation
  ├── Lifetime
  ├── Destruction
  └── Recovery
```

Например:

| Context        | Создание          | Lifetime           | Что происходит с состоянием |
| -------------- | ----------------- | ------------------ | --------------------------- |
| Popup          | открытие UI       | короткий           | runtime исчезает            |
| Service Worker | событие           | ephemeral          | globals ненадёжны           |
| Content Script | injection         | lifecycle страницы | может исчезнуть             |
| Side Panel     | открытие          | длительный UI      | может закрыться             |
| Options        | открытие страницы | длительный         | может быть закрыта          |

---

# Lifecycle-independent design

Из этого следует главный архитектурный принцип:

> **Критически важное состояние должно существовать независимо от lifecycle конкретного context.**

Например:

```text
Popup
   │
   ▼
Application State
   │
   ▼
Storage
```

а не:

```text
Popup
   │
   ▼
global variable
```

То же самое относится к Service Worker.

---

# Runtime должен уметь восстанавливаться

Правильная модель:

```text
Runtime starts
     ↓
Load persistent state
     ↓
Initialize services
     ↓
Subscribe to events
     ↓
Handle event
     ↓
Runtime becomes idle
```

После нового запуска:

```text
Runtime starts again
     ↓
Load state again
     ↓
Continue operation
```

Таким образом:

> **Restart — это нормальное состояние системы, а не исключение.**

---

# 35.2. Event routing

Вторая задача runtime — маршрутизация событий.

Browser API генерирует множество событий:

```text
tabs
windows
commands
alarms
runtime
storage
permissions
webNavigation
```

Если каждый модуль напрямую подписывается на десятки Chrome APIs, архитектура быстро становится запутанной.

Плохой вариант:

```text
Service Worker
 ├── tabs listener
 ├── tabs listener
 ├── storage listener
 ├── command listener
 ├── alarm listener
 ├── message listener
 ├── permission listener
 └── ...
```

и внутри каждого обработчика находится бизнес-логика.

---

# Event Router

Лучше создать отдельный слой маршрутизации:

```text
Chrome Events
      │
      ▼
 Event Router
      │
      ├── TAB_UPDATED
      ├── TAB_ACTIVATED
      ├── COMMAND
      ├── ALARM
      ├── MESSAGE
      └── STORAGE_CHANGED
             │
             ▼
      Application Handlers
```

Например:

```javascript
chrome.tabs.onActivated.addListener(
    ({ tabId }) => {
        dispatch({
            type: "TAB_ACTIVATED",
            tabId
        });
    }
);
```

Теперь Chrome API превращается во внутреннее событие приложения.

---

# Browser events и application events

Это важное разделение.

Browser event:

```text
chrome.tabs.onActivated
```

Application event:

```text
TAB_ACTIVATED
```

Browser API относится к инфраструктуре.

Application event относится к бизнес-логике.

Получается:

```text
Browser API
     ↓
Adapter
     ↓
Application Event
     ↓
Handler
```

---

# Почему это важно

Без такого слоя application code начинает зависеть от конкретного браузерного API.

Например:

```javascript
chrome.tabs.onUpdated.addListener(...)
chrome.tabs.query(...)
chrome.storage.local.get(...)
```

оказываются распределены по всему проекту.

С Event Router:

```text
Browser
  ↓
Adapters
  ↓
Runtime
  ↓
Application
```

граница становится значительно чище.

---

# Event routing table

Можно даже формализовать маршрутизацию:

| Event           | Source       | Handler               |
| --------------- | ------------ | --------------------- |
| `TAB_ACTIVATED` | Tabs API     | TabCoordinator        |
| `TAB_UPDATED`   | Tabs API     | NavigationCoordinator |
| `COMMAND`       | Commands API | CommandDispatcher     |
| `ALARM`         | Alarms API   | Scheduler             |
| `MESSAGE`       | Runtime API  | MessageRouter         |
| `STATE_CHANGED` | Storage      | StateManager          |

Такой подход особенно полезен в больших extensions.

---

# Event normalization

Разные Browser APIs могут генерировать события разной структуры.

Runtime может нормализовать их:

```text
Chrome event
     ↓
normalize()
     ↓
Internal event
```

Например:

```javascript
{
    type: "TAB_ACTIVATED",
    payload: {
        tabId: 123,
        windowId: 7
    }
}
```

Теперь application code не обязан знать точную структуру Chrome callback.

---

# 35.3. State management

Runtime должен определить:

> **Где находится состояние системы?**

Это один из самых важных архитектурных вопросов.

Полезно разделять state на четыре категории:

```text
State
 │
 ├── Persistent
 ├── Shared
 ├── Ephemeral
 └── Derived
```

---

# Persistent state

Состояние, которое должно пережить:

* закрытие Popup;
* остановку Service Worker;
* перезапуск браузера;
* navigation;
* создание нового context.

Например:

```text
settings
user preferences
feature flags
subscription state
cached configuration
```

Для такого состояния подходит Storage.

---

# Ephemeral state

Временное состояние:

```text
isPopupOpen
currentRequest
loading
temporarySelection
currentUIState
```

Его необязательно сохранять.

---

# Shared state

Состояние, доступное нескольким contexts:

```text
currentUser
selectedTab
extensionMode
featureState
```

Оно должно иметь определённый source of truth.

---

# Derived state

Состояние, которое можно вычислить:

```text
isAuthenticated
```

из:

```text
authToken
```

или:

```text
isCurrentPageSupported
```

из:

```text
currentTab.url
```

Derived state обычно не нужно отдельно сохранять.

---

# Source of truth

Хорошая архитектура явно определяет владельца:

```text
Settings
   ↓
Storage

Current application state
   ↓
State Manager

Page DOM
   ↓
Content Script

UI state
   ↓
UI context
```

Главное правило:

> **Не должно существовать двух независимых источников истины для одного и того же состояния.**

---

# State flow

Например:

```text
User action
    ↓
Command
    ↓
Application Core
    ↓
State update
    ↓
Storage
    ↓
State event
    ↓
UI contexts
```

Это гораздо надёжнее, чем:

```text
Popup changes itself
Side Panel changes itself
Content Script changes itself
```

---

# State manager

В большом extension полезно создать:

```text
StateManager
```

который отвечает за:

* загрузку состояния;
* изменение состояния;
* persistence;
* subscriptions;
* synchronization.

Например:

```javascript
const state = await stateManager.get();

await stateManager.update({
    enabled: true
});
```

Теперь UI не должен напрямую знать детали Storage API.

---

# Reactive state

Можно построить поток:

```text
State
  ↓
Change
  ↓
Event
  ↓
Subscribers
  ↓
UI
```

Например:

```text
Storage changed
      ↓
StateManager
      ↓
STATE_CHANGED
      ↓
Popup
      ↓
render()
```

Это особенно полезно для Side Panel.

---

# 35.4. Message transport

Contexts должны взаимодействовать через transport layer.

Основные механизмы:

```text
runtime.sendMessage()
runtime.connect()
Port
window.postMessage()
chrome.storage events
```

Но application architecture не должна зависеть от конкретного способа передачи сообщений.

---

# Transport abstraction

Вместо:

```javascript
chrome.runtime.sendMessage({
    type: "ANALYZE"
});
```

по всему проекту можно использовать:

```javascript
transport.send({
    type: "ANALYZE"
});
```

А внутри:

```text
Transport
   ↓
chrome.runtime.sendMessage()
```

---

# Request/response

Для RPC-подобных операций:

```text
Client
  │
  │ request
  ▼
Service Worker
  │
  │ response
  ▼
Client
```

Например:

```text
GET_SETTINGS
```

ответ:

```text
{
    theme: "dark",
    enabled: true
}
```

---

# Events

Для однонаправленных уведомлений:

```text
Service Worker
      │
      │ event
      ▼
Side Panel
```

Например:

```text
STATE_CHANGED
```

---

# Long-lived communication

Для streaming или длительного взаимодействия:

```text
runtime.connect()
      ↓
Port
      ↓
multiple messages
```

Архитектурно:

```text
Connection
    │
    ├── open
    ├── message
    ├── error
    └── close
```

---

# Typed protocol

Для production-системы сообщения лучше описывать как protocol.

Например:

```typescript
type Message =
    | {
        type: "GET_SETTINGS";
      }
    | {
        type: "ANALYZE_PAGE";
        tabId: number;
      }
    | {
        type: "SAVE_RESULT";
        result: AnalysisResult;
      };
```

Теперь transport становится типизированным.

---

# Message envelope

Полезно использовать envelope:

```javascript
{
    id: "req-123",
    type: "ANALYZE_PAGE",
    version: 1,
    payload: {
        tabId: 42
    }
}
```

Это позволяет добавить:

* request ID;
* protocol version;
* payload;
* tracing;
* error information.

---

# 35.5. Storage abstraction

Storage API не должен распространяться по всему приложению.

Плохая архитектура:

```text
Popup
 └── chrome.storage.local.get()

Side Panel
 └── chrome.storage.local.get()

Options
 └── chrome.storage.local.set()

Service Worker
 └── chrome.storage.local.get()
```

В результате каждый context реализует собственную логику persistence.

---

# Storage abstraction

Лучше:

```text
                 Application
                     │
                     ▼
               StorageService
                     │
           ┌─────────┼─────────┐
           ▼         ▼         ▼
        local       sync     session
```

Application code работает с абстракцией:

```javascript
await storage.get("settings");
await storage.set("settings", settings);
```

а не обязательно напрямую с:

```javascript
chrome.storage.local
```

---

# Storage adapter

Например:

```text
StorageService
      │
      ▼
StorageAdapter
      │
      ▼
chrome.storage
```

Это позволяет централизовать:

* serialization;
* validation;
* migrations;
* defaults;
* quotas;
* error handling.

---

# Defaults

Storage может не содержать значение.

Поэтому runtime должен иметь defaults:

```javascript
const defaults = {
    enabled: true,
    theme: "system",
    language: "en"
};
```

И загрузка:

```text
Storage
   ↓
merge defaults
   ↓
Application State
```

---

# Schema versioning

Состояние тоже может эволюционировать.

Например:

```text
v1
{
    enabled: true
}
```

позже:

```text
v2
{
    enabled: true,
    mode: "auto"
}
```

Runtime должен уметь мигрировать:

```text
Stored State v1
       ↓
Migration
       ↓
Stored State v2
```

---

# Storage как persistence layer

Важно разделять:

```text
State
```

и:

```text
Persistence
```

State:

```text
что приложение знает сейчас
```

Persistence:

```text
как это состояние переживает lifecycle
```

Это не одно и то же.

---

# 35.6. Permission abstraction

Permissions — ещё один infrastructure concern.

Плохая архитектура:

```javascript
if (chrome.permissions) {
    ...
}
```

разбросанная по всему приложению.

Лучше:

```text
PermissionService
       │
       ├── has()
       ├── request()
       ├── remove()
       └── getAll()
```

---

# Permission service

Например:

```javascript
const canAnalyze =
    await permissions.has({
        origins: ["https://example.com/*"]
    });
```

Внутри:

```text
PermissionService
       ↓
chrome.permissions
```

---

# Почему это важно

Application Core должен задавать вопрос:

> «У меня есть возможность выполнить эту операцию?»

а не:

> «Как именно Chrome реализует permissions API?»

Получается:

```text
Application
     ↓
PermissionService
     ↓
Browser Permission API
```

---

# Capability-oriented architecture

Permissions можно рассматривать как capabilities.

Например:

```text
Capability
 ├── ReadTabs
 ├── ModifyPage
 ├── AccessHost
 ├── NetworkAccess
 └── Notifications
```

Application operation требует capability:

```text
Analyze page
    ↓
ModifyPage / AccessHost
    ↓
permission check
```

Это делает security model частью architecture.

---

# Graceful degradation

Если permission отсутствует:

```text
Permission denied
      ↓
Feature unavailable
```

а не:

```text
Unhandled exception
```

Например:

```text
[ Analyze page ]

Permission required
[ Grant access ]
```

Это значительно лучше с точки зрения UX.

---

# 35.7. Browser API abstraction

Extension Runtime постоянно взаимодействует с браузером:

```text
tabs
windows
storage
alarms
permissions
scripting
runtime
commands
sidePanel
notifications
```

Если эти APIs вызываются непосредственно из application logic, возникает сильная зависимость от браузера.

---

# Browser adapter layer

Можно создать:

```text
                 Application Core
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
    TabService     StorageService   PermissionService
        │               │               │
        ▼               ▼               ▼
    Chrome API      Chrome API       Chrome API
```

---

# Почему abstraction полезна

Например, вместо:

```javascript
chrome.tabs.query({
    active: true,
    currentWindow: true
});
```

application code использует:

```javascript
tabs.getActive();
```

Преимущества:

* меньше coupling;
* проще тестирование;
* единое место обработки ошибок;
* легче менять implementation;
* проще mocking.

---

# Не следует абстрагировать всё

Однако abstraction сама по себе не является целью.

Плохой вариант:

```text
ChromeAPIWrapper
ChromeAPIManager
ChromeAPIProvider
ChromeAPIService
ChromeAPIAdapter
```

для одной простой функции.

Абстракция оправдана, если она решает проблему:

```text
coupling
testing
security
consistency
complexity
```

---

# Browser API как infrastructure

Полезная архитектурная граница:

```text
┌───────────────────────────────┐
│        Application Core       │
├───────────────────────────────┤
│ State                         │
│ Business Logic               │
│ Commands                     │
│ Rules                        │
├───────────────────────────────┤
│ Browser Adapters             │
├───────────────────────────────┤
│ Chrome Extension APIs        │
└───────────────────────────────┘
```

Это позволяет отделить:

```text
что приложение делает
```

от:

```text
как браузер предоставляет эту возможность
```

---

# 35.8. Error boundaries

В распределённой системе ошибки неизбежны.

Ошибка может произойти в:

```text
Popup
Service Worker
Content Script
Network
Storage
Permission
Browser API
Message transport
```

Поэтому runtime должен иметь error boundaries.

---

# Local error boundary

Каждый context должен иметь собственную защиту:

```text
Context
   │
   └── Error Boundary
          │
          ├── log
          ├── recover
          └── notify
```

---

# Global error boundary

Service Worker может иметь общий механизм:

```text
Event
  ↓
Router
  ↓
Handler
  ↓
try/catch
  ↓
Error Manager
```

Например:

```javascript
async function execute(handler, event) {
    try {
        return await handler(event);
    } catch (error) {
        reportError(error, {
            event
        });

        throw error;
    }
}
```

---

# Не скрывать ошибки

Плохая архитектура:

```javascript
try {
    ...
} catch {
    // ignore
}
```

Это приводит к:

```text
failure
   ↓
silent
   ↓
user sees wrong state
```

Лучше:

```text
failure
   ↓
classify
   ↓
recover or propagate
   ↓
observe
```

---

# Error classification

Полезно разделять:

```text
Error
 │
 ├── ValidationError
 ├── PermissionError
 ├── NetworkError
 ├── StorageError
 ├── TransportError
 ├── BrowserAPIError
 └── UnexpectedError
```

Это позволяет выбирать правильную стратегию восстановления.

---

# Retry

Не каждая ошибка требует retry.

Например:

```text
NetworkError
    → retry
```

но:

```text
PermissionError
    → request permission
```

а:

```text
ValidationError
    → reject
```

---

# Error propagation

Например:

```text
Content Script
      │
      │ error
      ▼
Service Worker
      │
      ▼
Error Manager
      │
      ├── log
      ├── state update
      └── UI notification
```

Это лучше, чем оставлять ошибку только в DevTools конкретного context.

---

# 35.9. Cleanup

В distributed runtime создание ресурсов должно сопровождаться их освобождением.

Это касается:

* event listeners;
* Ports;
* timers;
* observers;
* DOM listeners;
* subscriptions;
* connections;
* temporary state.

---

# Resource lifecycle

Полезно мыслить:

```text
Acquire
   ↓
Use
   ↓
Cleanup
```

Например:

```javascript
const observer =
    new MutationObserver(handler);

observer.observe(
    document.body,
    options
);

// later
observer.disconnect();
```

---

# Listener cleanup

Если context создаёт listener динамически:

```javascript
const handler = event => {
    ...
};

element.addEventListener(
    "click",
    handler
);
```

необходимо иметь возможность:

```javascript
element.removeEventListener(
    "click",
    handler
);
```

---

# Subscription manager

В сложном runtime полезно централизовать cleanup:

```text
RuntimeScope
   │
   ├── listeners
   ├── observers
   ├── ports
   ├── timers
   └── subscriptions
```

При завершении scope:

```text
dispose()
   ↓
cleanup everything
```

---

# Disposable pattern

Например:

```javascript
const scope = new RuntimeScope();

scope.add(
    subscribe(...)
);

scope.add(
    observer
);

scope.dispose();
```

Это особенно полезно для Content Scripts и UI contexts.

---

# Почему cleanup важен для SPA

В SPA можно повторно инициализировать компоненты:

```text
Route A
  ↓
initialize()
  ↓
Route B
  ↓
initialize()
```

Если предыдущие listeners не удалены:

```text
handler
handler
handler
handler
```

одно событие начинает обрабатываться несколько раз.

Поэтому:

```text
initialize()
```

должен иметь соответствующий:

```text
dispose()
```

---

# Idempotent initialization

Хороший runtime должен по возможности поддерживать:

```text
initialize()
initialize()
initialize()
```

без создания трёх одинаковых subscriptions.

Например:

```text
if already initialized
    return
```

или:

```text
dispose previous
initialize new
```

---

# Cleanup Service Worker

У Service Worker lifecycle контролируется браузером.

Поэтому не нужно пытаться самостоятельно имитировать его termination.

Но нужно правильно закрывать собственные ресурсы:

```text
Port
network operation
temporary subscription
state transaction
```

и не создавать долгоживущие ресурсы без необходимости.

# 35.10. Runtime observability

Последний элемент runtime — observability.

Большое extension невозможно нормально поддерживать, если разработчик не знает:

```text
что произошло?
где произошло?
когда произошло?
какой context это сделал?
какое сообщение было отправлено?
какое состояние изменилось?
```

---

# Logging

Минимальный runtime logger:

```javascript
logger.info("TAB_ACTIVATED", {
    tabId
});
```

Ошибки:

```javascript
logger.error(
    "ANALYZE_FAILED",
    {
        tabId,
        error
    }
);
```

---

# Context-aware logging

Очень полезно добавлять context:

```text
[service-worker]
[content-script]
[popup]
[side-panel]
[options]
```

Например:

```text
[content-script] PAGE_READY
[service-worker] ANALYZE_REQUEST
[service-worker] STORAGE_UPDATED
[side-panel] STATE_CHANGED
```

Это значительно облегчает debugging.

# Correlation ID

В распределённом runtime одна операция может пройти через несколько contexts:

```text
Popup
 ↓
Service Worker
 ↓
Content Script
 ↓
Service Worker
 ↓
Side Panel
```

Если каждому запросу дать ID:

```text
requestId = "req-8f32"
```

можно проследить весь workflow:

```text
[popup]       req-8f32 ANALYZE
[worker]      req-8f32 received
[content]     req-8f32 started
[content]     req-8f32 completed
[worker]      req-8f32 result
[side-panel]  req-8f32 rendered
```

Это один из наиболее полезных методов observability.

# Runtime как собственная платформа

На этом этапе возникает интересная идея.

Если один extension имеет такой runtime:

```text

├── lifecycle
├── event bus
├── state
├── messaging
├── storage
├── permissions
├── browser APIs
├── error handling

то следующий extension уже может использовать тот же архитектурный фундамент.

                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   Extension A     Extension B     Extension C
```

И это уже фактически **framework-level architecture**.

# Runtime Design Principles

Всю главу можно свести к нескольким принципам.

### 1. Contexts disposable

```text
Any context can disappear.
```

### 2. State persistent

```text
Important state must survive context lifecycle.
```

### 3. Events explicit

```text
Browser event
    ↓
Application event
```

### 4. Messages typed

```text
Context
   ↓
Protocol
   ↓
Context
```

### 5. Browser APIs isolated

```text
Application
    ↓
Adapter
    ↓
Browser
```

### 6. Permissions explicit

```text
Feature
   ↓
Capability
   ↓
Permission
```

### 7. Errors observable

```text
Error
  ↓
Classify
  ↓
Recover / propagate
  ↓
Observe
```

### 8. Resources disposable

```text
Acquire
   ↓
Use
   ↓
Dispose
```

### 9. Runtime observable

```text
Event
Message
State
Error
Lifecycle
```

должны быть доступны для диагностики.

# Финальная модель

Хорошо спроектированный Manifest V3 extension можно представить как:

```text
                           EXTENSION
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
        ▼                      ▼                      ▼
      UI                      PAGE                 SYSTEM
        │                      │                      │
   ┌────┼────┐                 │                 ┌────┼────┐
   ▼    ▼    ▼                 ▼                 ▼    ▼    ▼
Popup Panel Options       Content Script       Tabs Alarms Perms
   │    │    │                 │
   └────┼────┘                 │
        │                      │
        └──────────┬───────────┘
                   ▼
            MESSAGE TRANSPORT
                   │
                   ▼
             EVENT ROUTER
                   │
                   ▼
            APPLICATION CORE
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      STATE      SERVICES   COMMANDS
        │          │          │
        ▼          ▼          ▼
     STORAGE    BROWSER API  HANDLERS
                   │
                   ▼
             ERROR MANAGER
                   │
                   ▼
             OBSERVABILITY
```

Такой runtime решает главную проблему Manifest V3:

> **как превратить множество независимых, ephemeral и ограниченных execution contexts в одну согласованную application system.**

Именно здесь заканчивается простое изучение отдельных Chrome APIs и начинается **архитектура extension platform**.

Следующая логическая ступень — уже не просто знать `chrome.runtime`, `chrome.storage`, `chrome.tabs` или `chrome.scripting`, а научиться строить поверх них **собственный runtime protocol и application model**.
