# Глава 32. Работа с DOM страницы

Content Script становится по-настоящему полезным тогда, когда расширение начинает взаимодействовать с содержимым страницы.

Оно может:

* читать DOM;
* изменять DOM;
* создавать собственный интерфейс;
* отслеживать изменения;
* реагировать на действия пользователя;
* взаимодействовать с динамическими приложениями;
* работать со Shadow DOM;
* обнаруживать client-side navigation;
* интегрироваться с SPA.

На первый взгляд задача кажется простой:

```javascript
document.querySelector(...)
```

Но современная Web Platform устроена значительно сложнее.

Страница может:

```text
загрузиться
    ↓
изменить DOM
    ↓
запустить JavaScript framework
    ↓
создать новые элементы
    ↓
изменить URL без reload
    ↓
перерисовать интерфейс
    ↓
создать Shadow DOM
    ↓
удалить ранее найденный элемент
    ↓
создать его снова
```

Поэтому современный extension должен рассматривать DOM не как статический документ, а как **динамическую среду выполнения**.

Базовая архитектура:

```text
                 Web Page
                    │
          ┌─────────┴─────────┐
          │                   │
        DOM              JavaScript
          │                   │
          └─────────┬─────────┘
                    │
              Content Script
                    │
          ┌─────────┴─────────┐
          │                   │
       Observe             Modify
          │                   │
          └─────────┬─────────┘
                    ▼
              Extension logic
```

Главная идея этой главы:

> **Надёжная интеграция с DOM — это не поиск элементов, а управление жизненным циклом взаимодействия со страницей.**

---

# 32.1. Reading DOM

Самая простая задача Content Script — прочитать DOM страницы.

Например:

```javascript
const title =
    document.querySelector("h1");

console.log(title?.textContent);
```

Здесь расширение:

```text
document
   ↓
querySelector()
   ↓
element
   ↓
textContent
```

получает данные из страницы.

---

## Основные DOM API

Content Script может использовать стандартные Web Platform API:

```javascript
document.querySelector()
document.querySelectorAll()

document.getElementById()

element.querySelector()

element.textContent
element.innerHTML

element.getAttribute()
element.hasAttribute()

element.matches()
element.closest()
```

Например:

```javascript
const products =
    document.querySelectorAll(
        ".product"
    );

for (const product of products) {
    console.log(
        product.textContent
    );
}
```

---

# `querySelector()`

Наиболее универсальный механизм:

```javascript
const element =
    document.querySelector(
        ".article-title"
    );
```

Если элемент не существует:

```javascript
null
```

Поэтому безопасный код:

```javascript
const element =
    document.querySelector(
        ".article-title"
    );

if (element) {
    console.log(
        element.textContent
    );
}
```

Не следует предполагать, что элемент обязательно существует.

---

# `querySelectorAll()`

Для нескольких элементов:

```javascript
const elements =
    document.querySelectorAll(
        ".product"
    );
```

Например:

```javascript
for (const element of elements) {
    console.log(
        element.textContent
    );
}
```

---

# DOM — это не данные приложения

Очень важно понимать разницу между:

```text
DOM
```

и:

```text
Application state
```

Например:

```html
<div class="counter">10</div>
```

может показывать:

```text
10
```

но реальное состояние приложения может находиться внутри:

```text
React state
Vue state
Redux store
server cache
application memory
```

Поэтому:

```javascript
element.textContent
```

не обязательно показывает полное состояние приложения.

DOM — это **представление**, а не универсальный источник истины.

---

# `textContent` и `innerHTML`

Для чтения обычного текста:

```javascript
const text =
    element.textContent;
```

Для чтения HTML:

```javascript
const html =
    element.innerHTML;
```

Но `innerHTML` требует особой осторожности.

Если данные страницы недоверенные:

```javascript
container.innerHTML =
    untrustedData;
```

может привести к XSS.

Для обычного текста предпочтительнее:

```javascript
container.textContent =
    untrustedData;
```

---

# Чтение атрибутов

Например:

```html
<a
    class="product"
    href="/products/123"
    data-id="123"
>
    Product
</a>
```

Можно получить:

```javascript
const link =
    document.querySelector(
        ".product"
    );

const href =
    link?.getAttribute("href");

const id =
    link?.dataset.id;
```

---

# `dataset`

Современные сайты часто используют:

```html
<div
    data-product-id="123"
    data-category="books"
>
```

Content Script может получить:

```javascript
const element =
    document.querySelector(
        "[data-product-id]"
    );

console.log(
    element?.dataset.productId
);
```

Это часто лучше, чем зависеть от визуальных CSS-классов.

---

# Не полагайтесь на случайные CSS-классы

Плохой selector:

```javascript
".css-1a2b3c"
```

Если класс генерируется framework, он может измениться завтра.

Лучше искать:

```text
data-* attributes
semantic elements
ARIA attributes
stable IDs
structural relationships
```

Например:

```javascript
document.querySelector(
    "[data-product-id]"
);
```

обычно устойчивее, чем:

```javascript
document.querySelector(
    ".css-1a2b3c"
);
```

---

# DOM Traversal

Иногда элемент проще найти через отношения:

```javascript
element.closest()
element.parentElement
element.children
element.nextElementSibling
element.previousElementSibling
```

Например:

```javascript
const button =
    document.querySelector(
        "button"
    );

const card =
    button?.closest(
        "[data-product-id]"
    );
```

Это особенно полезно при сложной структуре UI.

---

# 32.2. Modifying DOM

Content Script может изменять DOM страницы.

Например:

```javascript
const banner =
    document.createElement("div");

banner.textContent =
    "Hello from extension";

document.body.append(
    banner
);
```

Получаем:

```text
Page DOM
   │
   ├── existing content
   │
   └── extension element
```

---

# Создание элементов

Базовый способ:

```javascript
const button =
    document.createElement(
        "button"
    );

button.textContent =
    "Analyze";

document.body.append(button);
```

---

# Добавление CSS

Можно использовать:

```javascript
button.style.position =
    "fixed";

button.style.top =
    "20px";
```

Но для больших интерфейсов inline styles неудобны.

Лучше создать stylesheet или использовать Shadow DOM для изоляции UI.

Например:

```javascript
const style =
    document.createElement("style");

style.textContent = `
    .my-extension-button {
        position: fixed;
        top: 20px;
        right: 20px;
    }
`;

document.head.append(style);
```

---

# Изменение существующего элемента

Например:

```javascript
const button =
    document.querySelector(
        ".submit"
    );

if (button) {
    button.textContent =
        "Processed";
}
```

Можно изменять:

```javascript
element.textContent
element.classList
element.attributes
element.style
element.hidden
```

---

# `classList`

Например:

```javascript
element.classList.add(
    "extension-active"
);
```

Удаление:

```javascript
element.classList.remove(
    "extension-active"
);
```

Переключение:

```javascript
element.classList.toggle(
    "extension-active"
);
```

---

# Не разрушайте DOM без необходимости

Опасный подход:

```javascript
document.body.innerHTML =
    newHtml;
```

Он может:

* уничтожить существующие элементы;
* удалить event listeners;
* нарушить состояние framework;
* сломать application runtime;
* вызвать неожиданные side effects.

Лучше изменять минимально необходимую часть DOM:

```javascript
const target =
    document.querySelector(
        ".target"
    );

target?.append(newElement);
```

---

# Extension UI должен иметь собственную границу

Если расширение добавляет интерфейс:

```text
Page
 ├── website DOM
 │
 └── extension UI
```

желательно иметь явный root:

```html
<div
    data-my-extension-root
></div>
```

Тогда extension легко найти:

```javascript
const root =
    document.querySelector(
        "[data-my-extension-root]"
    );
```

и удалить:

```javascript
root?.remove();
```

---

# 32.3. Observing DOM Mutations

Современные сайты редко имеют полностью готовый DOM после:

```javascript
DOMContentLoaded
```

Например:

```text
HTML
 ↓
JavaScript
 ↓
API request
 ↓
render
 ↓
new elements
 ↓
render again
```

Поэтому расширению нужен механизм наблюдения.

Для этого используется:

```javascript
MutationObserver
```

---

# Базовый MutationObserver

```javascript
const observer =
    new MutationObserver(
        mutations => {

            console.log(
                "DOM changed",
                mutations
            );

        }
    );

observer.observe(
    document.body,
    {
        childList: true,
        subtree: true
    }
);
```

Теперь observer получает уведомления об изменениях DOM.

---

# `childList`

Отслеживает добавление или удаление дочерних nodes:

```javascript
{
    childList: true
}
```

---

# `subtree`

Если нужно наблюдать не только непосредственных детей:

```javascript
{
    childList: true,
    subtree: true
}
```

Это означает:

```text
body
 ├── div
 │    ├── section
 │    │    └── article ← observe
 │    └── ...
 └── ...
```

---

# `attributes`

Можно наблюдать изменение атрибутов:

```javascript
observer.observe(
    document.body,
    {
        attributes: true,
        subtree: true
    }
);
```

Например:

```html
<div class="loading">
```

изменяется на:

```html
<div class="loaded">
```

---

# `characterData`

Можно наблюдать изменения текстовых nodes:

```javascript
{
    characterData: true,
    subtree: true
}
```

Однако это часто приводит к большому количеству событий.

Поэтому не следует включать всё подряд.

---

# MutationObserver не должен быть глобальным сканером

Плохая архитектура:

```javascript
observer.observe(
    document,
    {
        childList: true,
        subtree: true,
        attributes: true,
        characterData: true
    }
);
```

а затем на каждое изменение:

```javascript
document.querySelectorAll(
    "..."
);
```

Это может быть очень дорого на больших страницах.

Лучше:

```text
mutation
   ↓
determine affected nodes
   ↓
process only relevant nodes
```

---

# Проверка добавленных nodes

Например:

```javascript
const observer =
    new MutationObserver(
        mutations => {

            for (const mutation of mutations) {

                for (
                    const node
                    of mutation.addedNodes
                ) {

                    if (
                        node.nodeType !==
                        Node.ELEMENT_NODE
                    ) {
                        continue;
                    }

                    if (
                        node.matches(
                            ".product"
                        )
                    ) {
                        processProduct(node);
                    }

                    for (
                        const product
                        of node.querySelectorAll(
                            ".product"
                        )
                    ) {
                        processProduct(product);
                    }
                }
            }
        }
    );
```

Так расширение обрабатывает только появившиеся элементы.

---

# Disconnect

Observer можно остановить:

```javascript
observer.disconnect();
```

Это важно для lifecycle management.

Например:

```text
extension disabled
      ↓
disconnect observer
      ↓
remove UI
      ↓
cleanup listeners
```

---

# 32.4. Event interception

Content Script может подписываться на DOM events:

```javascript
document.addEventListener(
    "click",
    event => {
        console.log(
            "click",
            event.target
        );
    }
);
```

Можно использовать:

```text
click
input
change
submit
keydown
keyup
pointerdown
pointerup
focus
blur
```

и другие стандартные DOM events.

---

# Event delegation

В динамическом DOM не следует обязательно создавать listener для каждого элемента.

Вместо:

```javascript
for (const button of buttons) {
    button.addEventListener(
        "click",
        handler
    );
}
```

можно использовать delegation:

```javascript
document.addEventListener(
    "click",
    event => {

        const button =
            event.target.closest(
                "[data-action]"
            );

        if (!button) {
            return;
        }

        handleAction(button);
    }
);
```

Это особенно полезно для SPA.

---

# Почему delegation подходит для dynamic DOM

Представим:

```text
Page
 ↓
new button
 ↓
new button
 ↓
new button
```

При delegation:

```text
document
   ↓
one listener
   ↓
all matching buttons
```

Не нужно повторно регистрировать обработчик для каждого нового элемента.

---

# `preventDefault()`

Расширение может отменить стандартное действие:

```javascript
document.addEventListener(
    "click",
    event => {

        if (
            event.target.closest(
                "[data-block]"
            )
        ) {
            event.preventDefault();
        }
    }
);
```

Но использовать это следует осторожно.

Content Script вмешивается в поведение страницы.

---

# `stopPropagation()`

Можно остановить распространение события:

```javascript
event.stopPropagation();
```

Но это особенно опасно в third-party application.

Например:

```text
Website
 └── React event system

Extension
 └── stopPropagation()
```

может нарушить логику сайта.

Поэтому event interception должен быть максимально локальным.

---

# Capture phase

Event listener можно установить в capture phase:

```javascript
document.addEventListener(
    "click",
    handler,
    true
);
```

Тогда:

```text
capture
   ↓
target
   ↓
bubble
```

Extension может увидеть событие раньше некоторых обработчиков страницы.

Но это не означает, что Content Script получает абсолютный контроль над event system.

---

# Не перехватывайте всё

Плохая архитектура:

```javascript
document.addEventListener(
    "click",
    globalHandler,
    true
);
```

для всего сайта без строгой фильтрации.

Лучше:

```javascript
if (
    target.closest(
        "[data-extension-target]"
    )
) {
    // handle
}
```

Принцип:

> **Interception should be selective.**

---

# 32.5. Shadow DOM

Shadow DOM создаёт отдельное дерево DOM внутри host element.

Например:

```javascript
const host =
    document.createElement(
        "div"
    );

const shadow =
    host.attachShadow({
        mode: "open"
    });
```

Получаем:

```text
Document
   │
   └── Host
        │
        └── Shadow Root
             ├── button
             ├── style
             └── content
```

---

# Почему Shadow DOM важен для extensions

Если расширение добавляет собственный UI:

```text
Extension
   ↓
Page
   ↓
Website CSS
```

CSS сайта может неожиданно повлиять на UI extension.

Например:

```css
button {
    font-size: 30px;
}
```

может изменить внешний вид вашей кнопки.

Shadow DOM позволяет создать более сильную границу:

```text
Page DOM
   │
   └── Extension Host
          │
          └── Shadow Root
                │
                ├── CSS
                ├── UI
                └── logic
```

---

# `open` Shadow Root

```javascript
const host =
    document.createElement(
        "div"
    );

const shadow =
    host.attachShadow({
        mode: "open"
    });
```

Теперь:

```javascript
shadow.innerHTML = `
    <style>
        button {
            font-size: 14px;
        }
    </style>

    <button>
        Analyze
    </button>
`;
```

---

# Shadow DOM не является полной security boundary

Очень важно:

> Shadow DOM — это прежде всего encapsulation mechanism, а не security boundary.

`open` Shadow Root можно получить:

```javascript
host.shadowRoot
```

А `closed` Shadow Root:

```javascript
attachShadow({
    mode: "closed"
});
```

не делает содержимое абсолютной секретной зоной.

Не следует проектировать security architecture на предположении, что:

```text
closed Shadow DOM
=
private secure storage
```

---

# Shadow DOM и MutationObserver

MutationObserver, установленный на:

```javascript
document
```

не означает автоматически, что он будет наблюдать внутреннее содержимое каждого Shadow Root.

Shadow DOM создаёт отдельную DOM boundary.

Для сложных приложений необходимо отдельно учитывать:

```text
Document
 ├── normal DOM
 │
 └── Shadow Root
       ├── element
       └── element
```

---

# Nested Shadow DOM

Современные приложения могут содержать:

```text
Shadow Root
   ↓
Component
   ↓
Shadow Root
   ↓
Component
```

Поэтому поиск:

```javascript
document.querySelector(
    ".target"
);
```

может не найти нужный элемент.

---

# 32.6. SPA navigation

Современные веб-приложения часто не выполняют полный reload при изменении URL.

Например:

```text
/products
   ↓
click
   ↓
/products/123
```

HTML document остаётся тем же.

Framework меняет:

```text
history
URL
DOM
application state
```

---

# Почему это важно для extension

Если extension работает только при:

```text
initial page load
```

он может пропустить:

```text
SPA route transition
```

Например:

```text
Extension starts
       ↓
find product page
       ↓
nothing

User navigates SPA
       ↓
product UI appears
       ↓
extension does nothing
```

---

# `pushState`

SPA часто использует:

```javascript
history.pushState()
```

Для наблюдения можно перехватывать navigation-related mechanisms, но делать это нужно осторожно.

Например:

```javascript
const originalPushState =
    history.pushState;

history.pushState =
    function (...args) {

        const result =
            originalPushState.apply(
                this,
                args
            );

        window.dispatchEvent(
            new Event(
                "extension:locationchange"
            )
        );

        return result;
    };
```

Затем:

```javascript
window.addEventListener(
    "extension:locationchange",
    () => {
        handleNavigation();
    }
);
```

Но это уже page-level instrumentation, и такой подход нужно применять осознанно.

---

# `popstate`

Для browser navigation:

```javascript
window.addEventListener(
    "popstate",
    () => {
        handleNavigation();
    }
);
```

Например:

```text
Back
Forward
history navigation
```

может вызвать `popstate`.

---

# URL ≠ DOM lifecycle

Очень важно:

```text
URL changed
```

не означает автоматически:

```text
DOM completely replaced
```

И наоборот:

```text
DOM changed
```

не обязательно означает:

```text
URL changed
```

Поэтому зрелый extension отслеживает несколько сигналов:

```text
URL
DOM
application state
navigation events
```

---

# Mutation + navigation

Надёжная архитектура SPA integration может выглядеть так:

```text
                Page
                 │
       ┌─────────┴─────────┐
       │                   │
   Navigation          DOM changes
       │                   │
       └─────────┬─────────┘
                 ▼
          Integration layer
                 │
                 ▼
          detect page state
                 │
                 ▼
          Extension feature
```

---

# 32.7. Dynamic websites

Современный сайт нельзя считать:

```text
HTML file
```

Правильнее:

```text
HTML
 ↓
JavaScript runtime
 ↓
API
 ↓
state
 ↓
render
 ↓
DOM
 ↓
more JavaScript
 ↓
more DOM
```

Поэтому extension должен работать с **eventual DOM**.

---

# Eventual DOM

Элемент может появиться:

```text
0 ms
    element absent

100 ms
    element absent

500 ms
    API response

700 ms
    element created

900 ms
    framework updated element
```

Поэтому:

```javascript
document.querySelector(
    ".target"
);
```

может вернуть `null` не потому, что элемент не существует вообще, а потому что **он ещё не появился**.

---

# Плохое решение — бесконечный polling

Например:

```javascript
setInterval(() => {

    const element =
        document.querySelector(
            ".target"
        );

    if (element) {
        process(element);
    }

}, 100);
```

Это может работать, но создаёт:

```text
CPU overhead
unnecessary queries
duplicate processing
lifecycle problems
```

MutationObserver обычно лучше подходит для ожидания DOM mutations.

---

# Хорошая модель

```text
initial scan
      ↓
MutationObserver
      ↓
new elements
      ↓
process only relevant elements
```

Например:

```javascript
function processPage() {
    const elements =
        document.querySelectorAll(
            "[data-product]"
        );

    for (const element of elements) {
        process(element);
    }
}

processPage();

const observer =
    new MutationObserver(
        mutations => {
            // process changes
        }
    );

observer.observe(
    document.body,
    {
        childList: true,
        subtree: true
    }
);
```

---

# Debouncing

Некоторые frameworks генерируют множество изменений подряд.

Например:

```text
mutation
mutation
mutation
mutation
mutation
mutation
```

Необязательно запускать тяжёлый анализ пять раз.

Можно использовать batching:

```javascript
let scheduled = false;

function scheduleScan() {

    if (scheduled) {
        return;
    }

    scheduled = true;

    queueMicrotask(() => {
        scheduled = false;
        scan();
    });
}
```

Теперь серия событий может быть обработана более эффективно.

Для более тяжёлых операций можно использовать другие scheduling strategies.

---

# Не обрабатывайте один элемент дважды

Dynamic DOM может привести к:

```text
element added
   ↓
processed

framework updates element
   ↓
processed again

another mutation
   ↓
processed again
```

Можно использовать marker:

```javascript
if (
    element.dataset.extensionProcessed
) {
    return;
}

element.dataset.extensionProcessed =
    "true";

process(element);
```

Но лучше использовать более явное состояние, если оно сложное.

---

# WeakSet

Для runtime tracking удобно использовать:

```javascript
const processed =
    new WeakSet();

function process(element) {

    if (processed.has(element)) {
        return;
    }

    processed.add(element);

    // process
}
```

Преимущество `WeakSet`:

```text
element removed
      ↓
no need to manually remove
```

что хорошо подходит для DOM lifecycle.

---

# Dynamic content + delegation

Для событий часто можно избежать tracking вообще:

```javascript
document.addEventListener(
    "click",
    event => {

        const target =
            event.target.closest(
                "[data-product]"
            );

        if (!target) {
            return;
        }

        handleProduct(target);
    }
);
```

Это одна из наиболее устойчивых моделей для динамического DOM.

# 32.8. Robust DOM integration

Теперь можно сформулировать архитектуру надёжной DOM integration.

Не:

```text
find element
modify element
done
```

а:

```text
Detect
  ↓
Validate
  ↓
Observe
  ↓
Process
  ↓
Track
  ↓
React
  ↓
Cleanup
```

---

# 1. Detect

Сначала определить:

```text
подходящая ли страница?
```

Например:

```javascript
function isSupportedPage() {
    return location.hostname ===
        "example.com";
}
```

---

# 2. Validate

Затем проверить наличие необходимых элементов:

```javascript
const root =
    document.querySelector(
        "[data-app-root]"
    );

if (!root) {
    return;
}
```

Не следует предполагать, что DOM всегда соответствует ожиданиям.

---

# 3. Observe

Если нужные элементы могут появиться позже:

```javascript
const observer =
    new MutationObserver(
        handleMutations
    );
```

---

# 4. Process

Обрабатывайте только необходимые nodes:

```javascript
function processProduct(
    element
) {
    // ...
}
```

Не выполняйте полный scan всего document после каждой mutation.

---

# 5. Track

Нужно понимать:

```text
какие элементы уже обработаны?
какие listeners установлены?
создан ли extension UI?
активен ли observer?
```

Например:

```javascript
const processed =
    new WeakSet();
```

---

# 6. React

Страница может измениться.

Поэтому extension должен реагировать:

```text
new element
       ↓
process

element removed
       ↓
cleanup

route changed
       ↓
re-evaluate

component recreated
       ↓
process again
```

---

# 7. Cleanup

Особенно важно для SPA.

Например:

```javascript
function destroy() {
    observer.disconnect();

    root?.remove();

    document.removeEventListener(
        "click",
        clickHandler
    );
}
```

Это предотвращает накопление:

```text
listeners
observers
DOM nodes
state
```

---

# Lifecycle Manager

Для сложного extension можно создать:

```text
PageIntegration
```

с состояниями:

```text
idle
 ↓
detecting
 ↓
active
 ↓
observing
 ↓
destroying
 ↓
destroyed
```

Например:

```javascript
class PageIntegration {

    start() {
        // detect
        // inject UI
        // observe
        // bind events
    }

    stop() {
        // disconnect
        // cleanup
        // remove UI
    }
}
```

# DOM Adapter

Если extension работает с несколькими версиями сайта, полезно отделить DOM selectors от бизнес-логики.

Например:

```text
Page Integration
      │
      ▼
DOM Adapter
      │
      ├── findProducts()
      ├── getTitle()
      ├── getPrice()
      └── observeProducts()
```

А application logic получает:

```javascript
const products =
    adapter.findProducts();
```

а не:

```javascript
document.querySelectorAll(
    ".some-random-class"
);
```

---

# Почему это важно

Допустим, сайт изменил:

```html
<div class="product-card">
```

на:

```html
<article data-product>
```

Если selectors разбросаны по всему проекту:

```text
100 files
   ↓
100 modifications
```

Если есть DOM Adapter:

```text
DOM Adapter
    ↓
few selectors
```

архитектура значительно устойчивее.

# DOM как внешняя система

Для extension полезно мыслить о чужом сайте как о внешней системе:

```text
Extension
    │
    │ integration boundary
    ▼
Third-party DOM
```

А внешний DOM:

* может измениться;
* может быть неполным;
* может быть динамическим;
* может быть несовместимым;
* может содержать недоверенные данные;
* может использовать framework;
* может содержать Shadow DOM.

Следовательно:

> **DOM страницы следует рассматривать примерно так же, как внешний API.**

# Не доверяйте DOM

Например:

```javascript
const price =
    document.querySelector(
        ".price"
    )?.textContent;
```

Не следует сразу делать:

```javascript
const numericPrice =
    Number(price);
```

Нужно учитывать:

```text
element missing
unexpected format
localized number
hidden content
malicious content
different page version
```

DOM integration должна иметь validation layer.

# Пример устойчивого extractor

```javascript
function extractProduct(
    element
) {
    const title =
        element.querySelector(
            "[data-title]"
        )?.textContent?.trim();

    const priceText =
        element.querySelector(
            "[data-price]"
        )?.textContent?.trim();

    if (!title || !priceText) {
        return null;
    }

    return {
        title,
        priceText
    };
}
```

Здесь extractor:

```text
DOM
 ↓
validate
 ↓
normalize
 ↓
structured data
```

Это намного лучше, чем передавать DOM nodes по всему приложению.

# DOM → Structured Data

Это один из наиболее важных архитектурных принципов.

Вместо:

```text
Service Worker
       ↓
DOM Element
```

лучше:

```text
Content Script
       ↓
DOM
       ↓
extract
       ↓
structured data
       ↓
message
       ↓
Service Worker
```

Например:

```javascript
{
    title: "Product",
    price: 199,
    currency: "USD"
}
```

Content Script отвечает за DOM.

Service Worker получает уже нормализованные данные.

# Основные архитектурные правила

При работе с DOM страницы полезно придерживаться следующих правил.

### Правило 1

**DOM динамический.**

Не предполагайте, что нужный элемент существует сразу.

---

### Правило 2

**Не сканируйте весь document после каждого изменения.**

Используйте MutationObserver и обрабатывайте только необходимые nodes.

---

### Правило 3

**Используйте устойчивые selectors.**

Предпочитайте:

```text
data-*
ARIA
semantic structure
stable IDs
```

случайным CSS-классам.

---

### Правило 4

**Не смешивайте DOM и application logic.**

Создайте отдельный integration/adapter layer.

---

### Правило 5

**DOM — недоверенный источник данных.**

Валидируйте всё, что извлекается из страницы.

---

### Правило 6

**Не используйте `innerHTML` без необходимости.**

Особенно для данных, полученных со страницы.

---

### Правило 7

**Учитывайте Shadow DOM.**

`document.querySelector()` не видит автоматически содержимое каждого Shadow Root.

---

### Правило 8

**Учитывайте SPA navigation.**

URL может измениться без полной загрузки документа.

---

### Правило 9

**Делайте injection и initialization idempotent.**

Повторный запуск не должен создавать несколько экземпляров extension UI.

---

### Правило 10

**Всегда проектируйте cleanup.**

Observer, event listeners, timers и DOM nodes должны иметь lifecycle.

# Заключение

Работа с DOM — одна из наиболее специфичных частей разработки браузерных расширений.

На простом сайте можно написать:

```javascript
const button =
    document.querySelector(
        ".button"
    );

button?.click();
```

и считать задачу решённой.

Но современный production extension должен учитывать гораздо больше:

```text
DOM
│
├── dynamic rendering
├── SPA navigation
├── asynchronous loading
├── MutationObserver
├── events
├── Shadow DOM
├── framework lifecycle
├── changing selectors
└── untrusted content
```

Поэтому зрелая архитектура строится вокруг нескольких уровней:

```text
             Page
              │
              ▼
         DOM Integration
              │
      ┌───────┼────────┐
      │       │        │
    Read    Observe   Events
      │       │        │
      └───────┼────────┘
              ▼
         DOM Adapter
              │
              ▼
       Structured Data
              │
              ▼
       Extension Core
              │
              ▼
        Message Layer
              │
              ▼
        Service Worker
```

Главный принцип этой главы:

> **Не программируйте против конкретного DOM. Проектируйте слой интеграции с динамической внешней системой.**

Именно это различает простой Content Script от production-grade browser extension.
