# Часть X. Storage и состояние

# Глава 27. Extension Storage

Состояние — одна из наиболее важных частей архитектуры Manifest V3.

В предыдущих главах мы уже увидели, почему нельзя проектировать extension так, будто Service Worker является постоянно работающим процессом:

```text
Service Worker
    ↓
startup
    ↓
work
    ↓
suspend
    ↓
termination
```

Следовательно, состояние приложения нельзя надёжно хранить только в JavaScript-переменных.

Например:

```javascript
let currentUser = null;
let settings = {};
let cache = {};
```

Такие переменные существуют только пока существует конкретный runtime context.

После остановки Service Worker:

```text
Service Worker
      ↓
terminated
      ↓
global variables
      ↓
lost
```

Поэтому Manifest V3 предоставляет специальную систему persistent storage:

```text
chrome.storage
```

Она позволяет отделить **application state** от **runtime lifetime**.

Главная идея этой главы:

> **Runtime может исчезнуть. State — нет.**

---

# 27.1. `chrome.storage`

`chrome.storage` — это API для хранения данных расширения.

Базовая модель выглядит так:

```javascript
await chrome.storage.local.set({
    theme: "dark"
});
```

Получение:

```javascript
const result = await chrome.storage.local.get("theme");

console.log(result.theme);
```

Удаление:

```javascript
await chrome.storage.local.remove("theme");
```

Очистка:

```javascript
await chrome.storage.local.clear();
```

---

# Storage как отдельный слой архитектуры

Не следует рассматривать `chrome.storage` просто как замену:

```javascript
localStorage
```

Для extension это архитектурный компонент.

Хорошая модель:

```text
Extension
    │
    ├── UI
    │
    ├── Service Worker
    │
    ├── Content Scripts
    │
    └── Storage Layer
             │
             ├── local
             ├── sync
             ├── session
             └── managed
```

---

# Почему не обычный `localStorage`

Extension contexts имеют разные lifecycle.

Например:

```text
Popup
   ↓
opened
   ↓
closed
```

или:

```text
Service Worker
   ↓
started
   ↓
suspended
```

Поэтому `localStorage` конкретной страницы не является универсальным state layer extension.

`chrome.storage` предназначен именно для extension architecture.

---

# Storage API

Основные операции:

```javascript
chrome.storage.local.get()
chrome.storage.local.set()
chrome.storage.local.remove()
chrome.storage.local.clear()
```

Также существуют:

```javascript
chrome.storage.sync
chrome.storage.session
chrome.storage.managed
```

Каждый backend имеет собственную семантику.

---

# Storage ≠ database

Важно не переоценивать `chrome.storage`.

Это не полноценная реляционная база данных.

Не следует проектировать:

```text
chrome.storage
    ↓
complex relational database
```

с десятками связанных сущностей.

Для типичного extension storage лучше использовать для:

```text
settings
preferences
small application state
user configuration
cached metadata
session state
```

---

# Key-value model

Основная модель:

```text
key → value
```

Например:

```javascript
await chrome.storage.local.set({
    language: "en",
    theme: "dark",
    enabled: true
});
```

Получаем:

```text
language → "en"
theme    → "dark"
enabled  → true
```

---

# Namespace

Каждый storage area имеет собственный namespace.

Например:

```javascript
chrome.storage.local
```

и:

```javascript
chrome.storage.sync
```

не являются одним и тем же хранилищем.

---

# 27.2. `storage.local`

`storage.local` предназначен для локального хранения данных extension.

```javascript
await chrome.storage.local.set({
    settings: {
        theme: "dark"
    }
});
```

Данные остаются на данном browser profile и не предназначены для автоматической синхронизации между устройствами.

---

# Когда использовать `local`

Типичные случаи:

```text
local
├── application cache
├── large-ish local state
├── user preferences
├── locally generated data
└── extension state
```

Например:

```javascript
await chrome.storage.local.set({
    lastProcessedTab: 123,
    enabled: true
});
```

---

# Local state

Представим extension, которое анализирует страницы.

Можно хранить:

```text
settings
lastRun
statistics
cache
user preferences
```

в:

```text
storage.local
```

---

# Пример

```javascript
async function saveSettings(settings) {
    await chrome.storage.local.set({
        settings
    });
}
```

Получение:

```javascript
async function loadSettings() {
    const { settings } =
        await chrome.storage.local.get("settings");

    return settings;
}
```

---

# Storage abstraction

Лучше не разбрасывать вызовы API по всему приложению:

```javascript
chrome.storage.local.get(...)
chrome.storage.local.set(...)
chrome.storage.local.get(...)
```

Вместо этого создайте storage layer:

```javascript
const storage = {
    async getSettings() {
        const { settings } =
            await chrome.storage.local.get("settings");

        return settings;
    },

    async saveSettings(settings) {
        await chrome.storage.local.set({
            settings
        });
    }
};
```

Теперь остальная система не зависит непосредственно от деталей storage API.

---

# 27.3. `storage.sync`

`storage.sync` предназначен для синхронизации данных через browser account/sync infrastructure.

Идея:

```text
Device A
    │
    ▼
storage.sync
    │
    ▼
Browser Sync
    │
    ▼
Device B
```

Это особенно удобно для пользовательских настроек.

Например:

```text
theme
language
enabled features
keyboard preferences
UI settings
```

---

# Пример

```javascript
await chrome.storage.sync.set({
    theme: "dark",
    language: "en"
});
```

На другом устройстве extension может получить:

```javascript
const settings =
    await chrome.storage.sync.get([
        "theme",
        "language"
    ]);
```

---

# Что синхронизировать

Хороший кандидат:

```text
User Preferences
```

Плохой кандидат:

```text
Huge cache
temporary state
large datasets
rapidly changing counters
```

---

# Почему нельзя синхронизировать всё

Sync storage имеет ограничения по размеру и частоте операций.

Кроме того, синхронизация сама по себе имеет смысл только для данных, которые пользователь действительно хочет видеть на нескольких устройствах.

Например:

```text
Theme
```

логично синхронизировать.

А:

```text
Downloaded cache of 50 MB
```

— нет.

---

# Local + Sync

Очень часто архитектура использует оба storage area.

Например:

```text
storage.sync
    ↓
User preferences

storage.local
    ↓
Cache
Application data
Local state
```

Можно представить:

```text
                 Extension State
                       │
            ┌──────────┴──────────┐
            ▼                     ▼
        Portable                Local
        settings                data
            │                     │
            ▼                     ▼
       storage.sync         storage.local
```

---

# 27.4. `storage.session`

`storage.session` предназначен для данных, которые должны существовать в течение текущей browser/extension session, но не должны сохраняться постоянно.

Это особенно полезно для MV3.

---

# Почему он важен

У нас есть три принципиально разных типа state:

```text
Persistent state
Temporary state
Runtime state
```

Например:

```text
Persistent:
user settings

Temporary:
current session state

Runtime:
in-memory variables
```

`storage.session` занимает место между обычной памятью runtime и persistent storage.

---

# Сравнение

Упрощённо:

```text
global variable
    ↓
самая короткая lifetime

storage.session
    ↓
session lifetime

storage.local
    ↓
persistent local lifetime

storage.sync
    ↓
persistent + sync
```

---

# Когда использовать session

Например:

```text
temporary authorization state
current workflow
ephemeral cache
runtime coordination state
```

---

# Пример

```javascript
await chrome.storage.session.set({
    activeWorkflow: {
        step: 2
    }
});
```

Затем:

```javascript
const { activeWorkflow } =
    await chrome.storage.session.get("activeWorkflow");
```

---

# Почему это лучше глобальной переменной

Плохой вариант:

```javascript
let activeWorkflow = null;
```

Если Service Worker будет перезапущен:

```text
worker terminated
       ↓
activeWorkflow lost
```

С session storage состояние может пережить runtime restart в пределах соответствующей session semantics.

---

# Но session не равно persistent

Не следует путать:

```text
storage.session
```

с:

```text
storage.local
```

Session state не предназначен для долговременного хранения.

Если данные должны переживать browser/session lifecycle, используйте persistent storage.

---

# 27.5. `storage.managed`

`storage.managed` предназначен для данных, которыми управляет administrator через enterprise policy.

Это другой класс storage.

Архитектурно:

```text
Administrator
      ↓
Enterprise Policy
      ↓
storage.managed
      ↓
Extension
```

---

# Главная особенность

Extension не должен рассматривать managed storage как обычное пользовательское хранилище.

Например:

```text
User settings
```

и:

```text
Organization policy
```

— разные источники истины.

---

# Пример

Представим корпоративное extension.

Пользователь хочет:

```text
featureEnabled = true
```

Но организация установила:

```text
featureEnabled = false
```

Тогда application должна учитывать policy.

Можно представить:

```text
User configuration
        +
Enterprise policy
        ↓
Effective configuration
```

---

# Read-only configuration

Managed settings обычно воспринимаются как policy-controlled configuration.

Архитектура:

```text
storage.managed
       │
       ▼
Organization Policy
       │
       ▼
Application Configuration
```

---

# Очень важный принцип

Не смешивайте:

```text
user preference
```

и:

```text
administrator policy
```

Например:

```text
theme = dark
```

может быть пользовательской настройкой.

А:

```text
allowExternalSites = false
```

может быть корпоративной policy.

---

# Effective configuration

Хорошая архитектура может вычислять:

```text
effectiveConfig =
    merge(
        defaults,
        userConfig,
        managedConfig
    )
```

При этом правила приоритета должны быть явно определены.

Например:

```text
defaults
    ↓
user
    ↓
managed policy
```

где policy имеет более высокий приоритет.

---

# 27.6. Quotas

Storage API имеет ограничения.

Это важная часть архитектуры.

Нельзя проектировать extension так:

```text
store everything
store constantly
store forever
```

---

# Почему существуют quotas

Ограничения защищают browser environment от:

```text
excessive storage
excessive writes
abuse
performance degradation
```

---

# Размер

Разные storage areas имеют разные ограничения.

Поэтому при проектировании нужно учитывать:

```text
storage.local
storage.sync
storage.session
```

не как идентичные backend'ы, а как разные ресурсы.

---

# Sync особенно ограничен

`storage.sync` предназначен не для произвольного data warehouse.

Это механизм синхронизации небольшого пользовательского state.

Поэтому:

```text
settings → sync
```

обычно хорошо.

А:

```text
logs → sync
analytics → sync
cache → sync
```

обычно плохая идея.

---

# Write frequency

Важно учитывать не только размер, но и частоту записи.

Плохая архитектура:

```javascript
window.addEventListener("mousemove", async () => {
    await chrome.storage.local.set({
        x: event.clientX
    });
});
```

Это может создавать огромное количество storage operations.

---

# Debouncing

Если состояние изменяется часто:

```text
event
event
event
event
event
```

не обязательно записывать каждое изменение.

Можно:

```text
events
  ↓
debounce
  ↓
storage write
```

---

# Например

```javascript
let saveTimer;

function scheduleSave(state) {
    clearTimeout(saveTimer);

    saveTimer = setTimeout(() => {
        chrome.storage.local.set({ state });
    }, 300);
}
```

Идея здесь важнее конкретного значения timeout:

> **Сначала собрать изменения, затем сохранить агрегированное состояние.**

---

# Storage as boundary

Storage также является boundary между:

```text
fast-changing runtime state
```

и:

```text
persistent state
```

Например:

```text
Runtime
  │
  │ many updates
  ▼
In-memory state
  │
  │ debounced persistence
  ▼
chrome.storage
```

---

# Quota-aware architecture

Хорошая система должна учитывать:

```text
How much?
How often?
Which storage?
Why persist?
```

---

# 27.7. Serialization

Storage хранит значения в сериализуемой форме.

Поэтому нельзя рассматривать его как место, куда можно положить произвольный JavaScript object graph.

---

# Хорошие значения

Например:

```javascript
{
    enabled: true,
    count: 10,
    name: "Extension",
    tags: ["a", "b"],
    settings: {
        theme: "dark"
    }
}
```

---

# Плохая модель

Не следует рассчитывать на сохранение:

```text
DOM nodes
Functions
Class instances with behavior
Open sockets
Browser objects
Complex runtime resources
```

---

# Data ≠ behavior

Это фундаментальный принцип:

```text
Storage
   ↓
Data
```

а не:

```text
Storage
   ↓
Executable behavior
```

---

# Например

Вместо:

```javascript
{
    handler: someFunction
}
```

сохраняйте:

```javascript
{
    action: "block"
}
```

А затем приложение интерпретирует:

```text
action
 ↓
known behavior
```

---

# Serialization boundary

Storage можно рассматривать как serialization boundary:

```text
Runtime object
      ↓
   serialize
      ↓
   storage
      ↓
 deserialize
      ↓
Runtime object
```

Поэтому storage schema должна быть определена явно.

---

# Versioned schema

Хорошая практика — хранить версию schema:

```javascript
{
    version: 2,
    settings: {
        theme: "dark"
    }
}
```

Тогда при обновлении extension можно выполнить migration:

```text
v1
 ↓
migration
 ↓
v2
```

---

# Migration

Например:

```text
v1:
{
    darkMode: true
}
```

новая версия:

```text
v2:
{
    theme: "dark"
}
```

Migration layer:

```text
storage v1
    ↓
migration
    ↓
storage v2
```

---

# Это особенно важно для production extensions

Extension может жить:

```text
months
years
```

Пользователь не переустанавливает его каждый раз после обновления.

Следовательно, storage schema должна эволюционировать.

---

# 27.8. Storage events

Storage — это не только:

```text
get()
set()
```

Он также предоставляет механизм наблюдения за изменениями.

Основной механизм:

```javascript
chrome.storage.onChanged
```

---

# Пример

```javascript
chrome.storage.onChanged.addListener(
    (changes, areaName) => {

        console.log(areaName);
        console.log(changes);

    }
);
```

Когда состояние меняется, contexts могут реагировать на изменение.

---

# Почему это важно

Представим:

```text
Options Page
      │
      ▼
storage.sync
      │
      ▼
Content / UI / Service Worker
```

Options Page изменяет:

```text
theme = dark
```

Другие части extension могут узнать об изменении через storage event.

---

# Reactive architecture

Это позволяет строить реактивную модель:

```text
State
 ↓
Storage
 ↓
change event
 ↓
Consumers
```

---

# Например

```javascript
chrome.storage.onChanged.addListener(
    async (changes, area) => {

        if (area !== "sync") {
            return;
        }

        if (changes.theme) {
            applyTheme(changes.theme.newValue);
        }
    }
);
```

---

# Storage как event source

В определённых архитектурах storage можно рассматривать как:

```text
state
+
change notification
```

Но не следует превращать его в полноценную event bus.

Это разные вещи.

---

# Storage Event ≠ Message

Message:

```text
A → B
```

обычно означает:

> "Сделай что-то / обработай это событие."

Storage change:

```text
State changed
```

означает:

> "Состояние теперь другое."

Это принципиально разные семантики.

---

# 27.9. State synchronization

Теперь соберём всё вместе.

В extension одновременно могут существовать:

```text
Popup
Side Panel
Options
Service Worker
Content Scripts
```

Все они могут работать с одним application state.

---

# Проблема

Например:

```text
Options Page
    ↓
theme = dark
```

Но:

```text
Side Panel
```

всё ещё показывает:

```text
theme = light
```

Если каждый context хранит собственную копию state, появляется рассинхронизация.

---

# Single source of truth

Лучше определить единый источник истины.

Например:

```text
                Application State
                       │
                       ▼
                 chrome.storage
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Popup       Side Panel       Options
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                 Service Worker
```

---

# Но storage не всегда должен быть единственным source of truth

Для высокочастотного runtime state это может быть неэффективно.

Например:

```text
mouse position
scroll position
temporary UI state
```

не следует записывать в persistent storage при каждом изменении.

Поэтому полезно разделять:

```text
Persistent State
Session State
Runtime State
```

---

# Трёхуровневая модель

Можно построить:

```text
                STATE
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
 Persistent    Session    Runtime
       │          │          │
       ▼          ▼          ▼
    local/sync  session    memory
```

---

# Persistent State

Содержит:

```text
settings
preferences
user configuration
important application data
```

---

# Session State

Содержит:

```text
current workflow
temporary application state
session-specific data
```

---

# Runtime State

Содержит:

```text
current UI state
cached computations
temporary objects
active connections
```

---

# State hydration

После запуска context должен восстановить необходимое состояние.

Например:

```text
Service Worker starts
        ↓
load persistent state
        ↓
hydrate runtime state
        ↓
handle event
```

---

# Не наоборот

Не следует рассчитывать:

```text
Service Worker starts
       ↓
global state magically exists
```

Потому что после termination:

```text
global state = gone
```

---

# State machine

Для сложного extension удобно представить состояние как state machine:

```text
          ┌────────────┐
          │   Initial  │
          └─────┬──────┘
                │
                ▼
          ┌────────────┐
          │ Hydrating  │
          └─────┬──────┘
                │
                ▼
          ┌────────────┐
          │   Ready    │
          └─────┬──────┘
                │
          state changes
                │
                ▼
          ┌────────────┐
          │ Persisting │
          └────────────┘
```

---

# State synchronization pattern

Один из полезных вариантов:

```text
              User Action
                   │
                   ▼
              Context A
                   │
                   ▼
                Storage
                   │
            onChanged event
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       Context B Context C Context D
```

Это позволяет contexts не обращаться друг к другу напрямую для каждого state update.

---

# Но есть важное ограничение

Storage не следует использовать как high-frequency message bus.

Плохая архитектура:

```text
Context A
   ↓
storage.set()
   ↓
Context B
   ↓
storage.set()
   ↓
Context C
```

при сотнях или тысячах изменений в секунду.

Для такого взаимодействия подходят:

```text
runtime.sendMessage()
Port
```

или локальный runtime state.

---

# Storage и messaging

Хорошая архитектура разделяет:

### Message

Используется для:

```text
commands
requests
events
RPC
coordination
```

### Storage

Используется для:

```text
state
configuration
persistence
synchronization
```

---

# Очень важное различие

Можно сформулировать:

> **Messages transport events. Storage represents state.**

Например:

```text
Message:
"Enable dark mode"
```

Storage:

```text
theme = dark
```

После перезапуска Service Worker сообщение уже исчезло.

Но:

```text
theme = dark
```

остаётся.

# Storage architecture

Для production extension удобно иметь отдельный модуль:

```text
src/
  storage/
      schema.js
      local.js
      sync.js
      session.js
      migrations.js
      index.js
```

# Storage repository

Например:

```javascript
export const settingsRepository = {

    async get() {
        const { settings } =
            await chrome.storage.sync.get("settings");

        return settings;
    },

    async save(settings) {
        await chrome.storage.sync.set({
            settings
        });
    }
};
```

Теперь UI не знает:

```text
sync
local
serialization
schema
```

Он работает с:

```text
settingsRepository
```

# Typed storage

В TypeScript это особенно удобно.

Например:

```typescript
interface Settings {
    theme: "light" | "dark";
    language: string;
    enabled: boolean;
}
```

И repository:

```typescript
interface SettingsRepository {
    get(): Promise<Settings>;
    save(settings: Settings): Promise<void>;
}
```

# Schema validation

Для production-приложения полезно проверять данные после чтения.

Почему?

Storage может содержать данные старой версии:

```text
old extension version
```

или некорректные значения:

```text
unexpected state
```

Поэтому:

```text
Storage
   ↓
Read
   ↓
Validate
   ↓
Migrate
   ↓
Application State
```

# Storage и Service Worker

Для MV3 особенно важна следующая архитектура:

```text
             Service Worker
                    │
          ┌─────────┴─────────┐
          │                   │
      Runtime state       Persistent state
          │                   │
          ▼                   ▼
       Memory           chrome.storage
          │                   │
          │                   │
      ephemeral          persistent
```

---

# Не храните всё в storage

Это тоже важный принцип.

Не нужно превращать storage в замену RAM:

```text
Every variable
    ↓
storage
```

Правильнее:

```text
Frequently used
    ↓
memory

Need persistence
    ↓
storage
```

---

# Не храните всё в memory

Обратная ошибка ещё опаснее:

```text
Everything
   ↓
global variables
```

После worker termination состояние исчезнет.

# Storage decision matrix

Условно можно использовать такую модель:

| Тип данных                    | Storage       |
| ----------------------------- | ------------- |
| User settings                 | `sync`        |
| Local cache                   | `local`       |
| Large local application state | `local`       |
| Temporary session state       | `session`     |
| Enterprise policy             | `managed`     |
| High-frequency runtime state  | Memory        |
| Messages/events               | Messaging API |

---

# Storage как persistence boundary

В конечном итоге storage выполняет очень конкретную роль:

```text
                Runtime
                   │
                   │
             transient state
                   │
                   ▼
             Persistence
                   │
                   ▼
             chrome.storage
```

Он защищает application state от ephemeral nature MV3 runtime.

# Production principles

Для production extension полезно придерживаться следующих правил.

### Правило 1

Не храните критическое состояние только в Service Worker globals.

### Правило 2

Разделяйте:

```text
runtime
session
persistent
```

### Правило 3

Используйте `sync` только для действительно синхронизируемых пользовательских данных.

### Правило 4

Не используйте storage как message bus.

### Правило 5

Не пишите слишком часто.

### Правило 6

Версионируйте storage schema.

### Правило 7

Делайте migrations.

### Правило 8

Изолируйте storage API за repository/service layer.

### Правило 9

Валидируйте данные после чтения.

### Правило 10

Определяйте один явный source of truth.

# Итоговая модель главы

После этой главы storage architecture можно представить так:

```text
                         APPLICATION
                              │
                    ┌─────────┴─────────┐
                    │                   │
              Runtime State       Persistent State
                    │                   │
                    ▼                   ▼
                 Memory        chrome.storage
                                      │
                    ┌─────────────────┼─────────────────┐
                    │                 │                 │
                    ▼                 ▼                 ▼
                  local             sync             session
                    │                 │                 │
                    │                 │                 │
                    ▼                 ▼                 ▼
                Local data      User settings      Session state
                                     
                                     
                       Enterprise
                           │
                           ▼
                    storage.managed
                           │
                           ▼
                    Admin policy
```

А взаимодействие между contexts:

```text
                    STATE
                      │
                      ▼
               chrome.storage
                      │
              onChanged event
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    Popup        Side Panel       Options
       │              │              │
       └──────────────┼──────────────┘
                      │
                      ▼
               Service Worker
```

Главная архитектурная идея:

> **`chrome.storage` — это не просто API для сохранения настроек. Это persistence layer, который отделяет состояние extension от lifecycle его execution contexts.**

Именно поэтому для Manifest V3 правильная модель выглядит не так:

```text
Service Worker
     ↓
global variables
     ↓
application state
```

а так:

```text
                  Application
                      │
              ┌───────┴───────┐
              ▼               ▼
        Runtime State     Persistent State
              │               │
              ▼               ▼
           Memory       chrome.storage
              │               │
              └───────┬───────┘
                      ▼
                 MV3 Runtime
```

**Runtime может остановиться, перезапуститься или исчезнуть. Persistent state должен продолжать существовать независимо от этого lifecycle.**

Это одна из фундаментальных идей, на которой строится надёжная архитектура Manifest V3.
