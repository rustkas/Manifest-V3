# Глава 24. Declarative Content

В предыдущей главе мы рассмотрели фундаментальную идею **Declarative APIs**: расширение не всегда должно реагировать на события с помощью JavaScript. Во многих случаях достаточно описать **условие и действие**, а браузер самостоятельно выполнит соответствующую операцию.

`declarativeContent` — один из классических примеров такого подхода.

Его основная идея проста:

> **Показывать или активировать определённое поведение extension только тогда, когда текущая страница соответствует заданным условиям.**

Вместо того чтобы постоянно запускать Content Script или Service Worker и проверять:

```text
На какой странице находится пользователь?
Подходит ли эта страница?
Можно ли здесь показать кнопку?
```

extension может зарегистрировать декларативное правило:

```text
IF page matches condition
THEN perform action
```

Это превращает браузер в механизм определения контекста.

---

# 24.1. `declarativeContent`

`declarativeContent` — это permission/API Manifest V3, позволяющий создавать правила, зависящие от состояния или содержимого страницы.

Исторически API называется:

```text
chrome.declarativeContent
```

Его основная концепция:

```text
Page
 ↓
Condition
 ↓
Action
```

Например:

```text
IF
    URL matches example.com

THEN
    show extension action
```

---

## Imperative вариант

Без declarative API разработчик мог бы реализовать похожую логику через события вкладок:

```javascript
chrome.tabs.onUpdated.addListener(
    async (tabId, changeInfo, tab) => {

        if (!tab.url) {
            return;
        }

        if (tab.url.includes("example.com")) {
            // показать / изменить состояние action
        }
    }
);
```

Получается:

```text
Navigation
    ↓
Service Worker
    ↓
JavaScript
    ↓
Inspect URL
    ↓
Condition
    ↓
Action
```

---

## Declarative вариант

С `declarativeContent` идея становится:

```text
Rule:
    condition = page matches X
    action    = show page action
```

То есть:

```text
Navigation
    ↓
Browser
    ↓
Condition matching
    ↓
Action
```

JavaScript extension не обязан обрабатывать каждую навигацию.

---

# Permission

Для использования API требуется соответствующее permission:

```json
{
  "permissions": [
    "declarativeContent"
  ]
}
```

В Manifest V3 permission указывается в обычном массиве:

```json
{
  "manifest_version": 3,

  "name": "Context Extension",
  "version": "1.0.0",

  "permissions": [
    "declarativeContent"
  ]
}
```

После этого Service Worker может работать с:

```javascript
chrome.declarativeContent
```

---

# Важная архитектурная деталь

Declarative Content не означает:

> "Extension больше не использует JavaScript."

На практике JavaScript всё равно нужен для:

* регистрации правил;
* изменения правил;
* обработки пользовательских действий;
* сложной бизнес-логики;
* взаимодействия с другими contexts.

Но **само условие активации** может быть передано браузеру.

---

# Регистрация правил

Концептуально extension создаёт правило:

```javascript
chrome.declarativeContent.onPageChanged.removeRules(
    undefined,
    () => {

        chrome.declarativeContent.onPageChanged.addRules([
            {
                conditions: [
                    // condition
                ],
                actions: [
                    // action
                ]
            }
        ]);

    }
);
```

Структура выглядит примерно так:

```text
Rule
├── conditions
└── actions
```

То есть:

```text
conditions → WHEN
actions    → THEN
```

---

# Упрощённая модель

Можно представить правило так:

```javascript
{
    conditions: [
        condition
    ],

    actions: [
        action
    ]
}
```

Это очень похоже на обычное правило бизнес-логики:

```text
IF condition
THEN action
```

---

# Почему правила обычно регистрируют при установке

Declarative rules часто регистрируются при установке или обновлении extension.

Например:

```javascript
chrome.runtime.onInstalled.addListener(() => {

    chrome.declarativeContent.onPageChanged.addRules([
        // rules
    ]);

});
```

Получается:

```text
Install extension
       ↓
Service Worker starts
       ↓
Register rules
       ↓
Browser stores rules
       ↓
Future pages
       ↓
Browser evaluates conditions
```

Это важный архитектурный паттерн.

Service Worker выполняет **configuration work**, а браузер затем выполняет **runtime evaluation**.

---

# 24.2. Conditions

Главная часть declarativeContent — `conditions`.

Условие отвечает на вопрос:

> **Когда правило должно сработать?**

Общая структура:

```text
Rule
 │
 ├── conditions
 │       │
 │       └── PageStateMatcher
 │
 └── actions
```

Основным механизмом проверки страницы является `PageStateMatcher`.

---

# PageStateMatcher

Упрощённо:

```javascript
new chrome.declarativeContent.PageStateMatcher({
    pageUrl: {
        hostEquals: "example.com"
    }
});
```

Это означает:

```text
IF
    current page host == example.com
```

---

# URL condition

Один из наиболее очевидных вариантов — проверять URL.

Например:

```javascript
{
    pageUrl: {
        hostEquals: "example.com"
    }
}
```

Теперь:

```text
https://example.com/page
```

может соответствовать условию.

А:

```text
https://google.com/
```

не соответствует.

---

# Host

Можно использовать условия, связанные с host.

Например:

```javascript
{
    pageUrl: {
        hostEquals: "example.com"
    }
}
```

Получается:

```text
example.com       → match
www.example.com   → зависит от условия
other.com         → no match
```

Поэтому условия необходимо проектировать точно.

---

# Host prefix

В некоторых сценариях полезно проверять префикс host.

Например концептуально:

```javascript
{
    pageUrl: {
        hostPrefix: "shop"
    }
}
```

Это позволяет создавать правила для определённых групп hostnames.

---

# Path

Можно ограничить условие частью URL.

Например:

```text
https://example.com/products/...
```

Концептуально:

```javascript
{
    pageUrl: {
        pathPrefix: "/products/"
    }
}
```

Тогда:

```text
/products/123
/products/456
```

соответствуют условию.

---

# URL pattern

Можно использовать URL patterns для более сложных условий.

Например:

```javascript
{
    pageUrl: {
        urlMatches: "example\\.com/products/.*"
    }
}
```

Здесь важно понимать, что `urlMatches` использует регулярное выражение.

Поэтому:

```text
.
*
?
```

и другие специальные символы имеют значение регулярного выражения.

---

# CSS selectors

Это особенно интересная возможность.

Condition может зависеть не только от URL, но и от наличия определённого элемента на странице.

Например:

```javascript
{
    css: ".product-page"
}
```

Идея:

```text
IF page contains:

<div class="product-page">
```

тогда правило считается подходящим.

Это делает `declarativeContent` намного интереснее обычной проверки URL.

---

# URL + CSS

Можно комбинировать условия.

Например:

```text
IF

    host == example.com

AND

    page contains .product

THEN

    activate extension
```

Концептуально:

```javascript
{
    conditions: [
        new chrome.declarativeContent.PageStateMatcher({
            pageUrl: {
                hostEquals: "example.com"
            },
            css: [
                ".product"
            ]
        })
    ]
}
```

Теперь activation зависит сразу от двух факторов.

---

# Почему CSS condition важен

Представим extension для интернет-магазинов.

Необходимо активировать extension только на страницах товаров.

Проверять только URL:

```text
/shop/123
```

может быть недостаточно.

Сайт может иметь:

```text
/shop/123
/shop/category
/shop/search
```

Но только product page содержит:

```html
<div class="product-details">
```

Тогда declarative condition может использовать DOM structure страницы как часть условия.

---

# AND semantics

Если в одном matcher указано несколько условий, они концептуально работают как:

```text
Condition A
    AND
Condition B
```

Например:

```text
host == example.com
AND
CSS ".product"
```

Только если оба условия выполняются:

```text
match
```

---

# Несколько rules

Можно зарегистрировать несколько правил:

```text
Rule 1
    example.com
        ↓
    Action A

Rule 2
    github.com
        ↓
    Action B

Rule 3
    docs.example.com
        ↓
    Action C
```

Получается:

```text
                    Browser
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Rule 1       Rule 2       Rule 3
          │            │            │
          ▼            ▼            ▼
       Action A     Action B     Action C
```

---

# 24.3. Actions

Если `conditions` отвечают на вопрос:

> Когда?

то `actions` отвечают:

> Что делать?

В declarativeContent actions представляют ограниченный набор заранее определённых browser operations.

---

# `ShowAction`

Наиболее известный вариант:

```javascript
new chrome.declarativeContent.ShowAction()
```

Идея:

```text
Page matches
      ↓
Show extension action
```

То есть extension action становится доступным/активным в соответствующем контексте страницы.

---

# Почему это полезно

Допустим, extension работает только на:

```text
github.com
```

Нет смысла показывать пользователю активный action на:

```text
google.com
youtube.com
example.org
```

Можно сделать:

```text
GitHub page
     ↓
ShowAction
```

и:

```text
Other page
     ↓
No action
```

---

# `RequestContentScript`

Другой интересный механизм — запрос на запуск Content Script.

Концептуально:

```text
Condition
    ↓
RequestContentScript
    ↓
Content Script
```

Это позволяет использовать declarative condition как своего рода gate:

```text
Page qualifies
      ↓
Content Script becomes relevant
```

---

# Архитектурная модель

Получается:

```text
                Page
                 │
                 ▼
          PageStateMatcher
                 │
             condition
                 │
          ┌──────┴──────┐
          │             │
          ▼             ▼
      ShowAction   RequestContentScript
          │             │
          ▼             ▼
       Action       Content Script
```

---

# DeclarativeContent не является универсальным rule engine

Это принципиально важно.

Нельзя ожидать, что можно написать:

```text
IF arbitrary JavaScript expression
THEN execute arbitrary JavaScript
```

Такой подход противоречил бы самой философии Declarative APIs.

Вместо этого API предоставляет ограниченный набор:

```text
Conditions
+
Actions
```

которые понимает браузер.

---

# 24.4. Page-based activation

Одно из главных применений `declarativeContent` — **page-based activation**.

То есть:

> состояние extension зависит от текущей страницы.

---

# Без page-based activation

Extension action может быть постоянно доступен:

```text
Google       → active
GitHub       → active
YouTube      → active
Random site  → active
```

Пользователь не понимает:

> Где extension действительно работает?

---

# С page-based activation

```text
Google       → inactive
GitHub       → active
YouTube      → inactive
Random site  → inactive
```

Теперь UI отражает capabilities extension.

---

# Это часть UX

Declarative Content — это не только технический API.

Он позволяет сделать интерфейс extension контекстным.

Например:

```text
Current page
      ↓
Does extension support this page?
      │
   ┌──┴──┐
  yes    no
   │      │
   ▼      ▼
Active   Disabled/hidden
```

Пользователь сразу понимает:

> extension работает здесь.

---

# Контекстная активация

Можно представить extension как функцию:

```text
ExtensionCapability(page)
```

Она возвращает:

```text
enabled
```

или:

```text
disabled
```

Но вместо постоянного JavaScript:

```javascript
if (pageIsSupported()) {
    ...
}
```

часть этой логики передаётся браузеру.

---

# Пример: GitHub extension

Представим extension:

> GitHub Issue Assistant

Оно работает только на страницах issues.

URL:

```text
https://github.com/*/*/issues/*
```

Можно добавить дополнительные условия:

```text
host == github.com
AND
CSS element related to issue exists
```

Результат:

```text
GitHub repository page
        ↓
condition
        ↓
match
        ↓
activate extension
```

---

# Пример: Shopping Assistant

Extension работает только на product pages.

```text
example-shop.com
       +
.product-details
```

Тогда:

```text
Category page
    ↓
No match

Product page
    ↓
Match
    ↓
Show extension action
```

---

# Пример: Documentation Assistant

Extension предназначено для документации.

```text
docs.example.com
```

На обычном сайте:

```text
example.com
```

оно не должно активироваться.

На документации:

```text
docs.example.com/api
```

оно становится доступным.

---

# Page state

Важная идея `declarativeContent`:

> activation зависит не только от URL, но и от состояния страницы.

Например:

```text
URL
+
DOM
```

может определять:

```text
Extension capability
```

---

# Почему это лучше, чем постоянно анализировать страницу

Imperative:

```text
Page changes
 ↓
Content Script
 ↓
Inspect DOM
 ↓
Send message
 ↓
Service Worker
 ↓
Update action
```

Declarative:

```text
Page
 ↓
Browser evaluates condition
 ↓
Action state
```

В простых сценариях это значительно проще архитектурно.

---

# 24.5. Когда declarativeContent полезен

`declarativeContent` особенно полезен в ситуациях, когда:

### 1. Extension работает только на определённых сайтах

Например:

```text
github.com
stackoverflow.com
docs.example.com
```

---

### 2. Extension работает только на определённых страницах

Например:

```text
/products/*
/issues/*
/articles/*
```

---

### 3. Extension должен активироваться при наличии DOM element

Например:

```text
.product-page
.editor
.video-player
.issue-header
```

---

### 4. Нужно сделать action context-aware

То есть:

```text
Supported page
    ↓
Action available

Unsupported page
    ↓
Action inactive
```

---

### 5. Не хочется запускать JavaScript для каждой страницы

Это особенно важно в MV3.

Вместо:

```text
Every navigation
    ↓
Service Worker
    ↓
JavaScript
```

можно использовать:

```text
Navigation
    ↓
Browser
    ↓
Condition
```

---

# 6. Extension имеет много страниц

Если extension работает только на:

```text
https://example.com/editor/*
```

нет необходимости активировать его на:

```text
https://example.com/
https://example.com/about
https://example.com/pricing
```

Declarative activation позволяет выразить это как policy.

---

# 7. Нужно минимизировать runtime work

Чем меньше:

```text
Service Worker
 ↓
JavaScript
```

тем меньше работы runtime.

DeclarativeContent может выступать первым уровнем фильтрации:

```text
All pages
   ↓
Declarative condition
   ↓
Relevant pages
   ↓
Extension logic
```

---

# 24.6. Ограничения

Теперь самая важная часть.

`declarativeContent` очень полезен, но его нельзя воспринимать как замену Content Scripts или Service Worker.

---

# Ограничение №1. Ограниченный набор conditions

Вы не можете произвольно написать:

```javascript
function isPageSupported(page) {

    return (
        page.user.isPremium &&
        page.data.score > 42 &&
        complexAlgorithm(page)
    );
}
```

Declarative API работает только с теми conditions, которые поддерживает browser API.

---

# Ограничение №2. Ограниченный набор actions

Аналогично нельзя сказать:

```text
THEN:
    execute arbitrary JavaScript
```

Action должен быть одним из поддерживаемых API механизмов.

---

# Ограничение №3. Сложная логика остаётся imperative

Если нужно:

```text
Fetch API
 ↓
Parse JSON
 ↓
Run algorithm
 ↓
Update storage
 ↓
Send message
```

это уже задача JavaScript runtime.

То есть:

```text
Declarative
    ↓
simple browser policy

Imperative
    ↓
application logic
```

---

# Ограничение №4. CSS condition не заменяет Content Script

Это очень важный момент.

Если вы указали:

```text
css = ".product"
```

это не означает:

> extension получил DOM element и может работать с ним.

Condition только отвечает:

```text
Does the page match?
```

Content Script отвечает:

```text
What should extension do with the page?
```

Это две разные задачи.

---

# Ограничение №5. Страница может быть динамической

Современные сайты часто используют:

```text
SPA
React
Vue
Angular
Svelte
```

DOM может изменяться после первоначальной загрузки.

Например:

```text
Page loaded
    ↓
No .product
    ↓
JavaScript application runs
    ↓
.product appears
```

Поэтому нельзя автоматически предполагать, что проверка состояния страницы будет вести себя как постоянный `MutationObserver`.

---

# Ограничение №6. Не весь DOM является доступным одинаково

Страница может содержать:

```text
iframe
shadow DOM
cross-origin iframe
```

и другие сложные структуры.

Declarative matching не превращает extension в универсальный механизм анализа всего DOM.

---

# Ограничение №7. Dynamic permissions остаются отдельной проблемой

Даже если условие совпало:

```text
condition = true
```

это не означает автоматически:

```text
extension has every required capability
```

Permissions и host permissions продолжают определять границы extension.

---

# Ограничение №8. DeclarativeContent не заменяет архитектуру

Нельзя строить extension по принципу:

```text
Everything → declarativeContent
```

Правильнее:

```text
DeclarativeContent
       ↓
Context detection
       ↓
Imperative runtime
       ↓
Business logic
```

---

# Declarative Content как Gate

Очень полезно воспринимать `declarativeContent` как **gate**.

```text
                    All pages
                       │
                       ▼
              Declarative Content
                       │
             ┌─────────┴─────────┐
             │                   │
          No match             Match
             │                   │
             ▼                   ▼
           Ignore          Activate capability
                                 │
                                 ▼
                           Content Script
                                 │
                                 ▼
                           Service Worker
                                 │
                                 ▼
                           Business Logic
```

Это одна из наиболее практичных моделей.

---

# DeclarativeContent и Content Script

Не нужно выбирать:

```text
DeclarativeContent
OR
Content Script
```

Часто правильный ответ:

```text
DeclarativeContent
+
Content Script
```

Первый отвечает:

> Нужно ли extension работать здесь?

Второй:

> Что extension должен делать со страницей?

---

# DeclarativeContent и Service Worker

Аналогично:

```text
DeclarativeContent
        ↓
Context detection

Service Worker
        ↓
Application orchestration
```

Service Worker не обязан самостоятельно анализировать каждую страницу.

---

# DeclarativeContent и Action

Один из наиболее естественных паттернов:

```text
Page
 ↓
PageStateMatcher
 ↓
ShowAction
```

Это позволяет сделать:

```text
Context-aware Action
```

---

# Полная архитектура

Например, extension анализирует товары:

```text
                      Browser
                         │
                    Current Page
                         │
                         ▼
                PageStateMatcher
                         │
                    conditions
                         │
                  ┌──────┴──────┐
                  │             │
                false          true
                  │             │
                  ▼             ▼
                Ignore      ShowAction
                                │
                             click
                                │
                                ▼
                             Popup
                                │
                                ▼
                         Service Worker
                                │
                                ▼
                         Content Script
                                │
                                ▼
                              DOM
```

Это уже полноценная MV3 architecture.

# DeclarativeContent как часть Progressive Enhancement

Интересно рассмотреть этот API через принцип progressive enhancement.

Базовый браузер:

```text
Page
```

Extension добавляет capability:

```text
Page
 ↓
Condition
 ↓
Enhanced capability
```

То есть enhancement включается только там, где он имеет смысл.

---

# Правильный способ проектирования

При разработке extension полезно пройти следующий pipeline:

```text
1. Определить capability
        ↓
2. Определить supported pages
        ↓
3. Формализовать condition
        ↓
4. Выбрать declarative action
        ↓
5. Только затем писать imperative logic
```

Например:

```text
Capability:
    Analyze product

Supported page:
    Product page

Condition:
    host == shop.example
    AND
    .product-details exists

Action:
    Show extension action

Imperative logic:
    Analyze product
```

# Declarative Content как boundary

Это позволяет создать чёткую границу:

```text
Browser
──────────────────────────────
Page detection
Rule matching
Activation
──────────────────────────────
Extension
Business logic
State
Network
UI
```

Чем больше простой контекстной логики находится выше границы, тем меньше работы приходится выполнять application runtime.

---

# Главный архитектурный паттерн главы

Запомните:

```text
              PAGE
                │
                ▼
        ┌────────────────┐
        │ Declarative    │
        │ Content        │
        │                │
        │ "Is this page  │
        │  relevant?"    │
        └───────┬────────┘
                │
              YES
                │
                ▼
        ┌────────────────┐
        │ Extension      │
        │ Runtime        │
        │                │
        │ "What should   │
        │  we do?"       │
        └────────────────┘
```

То есть:

> **Declarative Content отвечает за контекст. Imperative runtime отвечает за поведение.**

# Итог

`declarativeContent` показывает фундаментальный принцип Manifest V3 на небольшом и понятном примере.

Вместо:

```text
Every page
   ↓
JavaScript
   ↓
Check page
   ↓
Maybe activate
```

мы можем использовать:

```text
Page
   ↓
Declarative condition
   ↓
Browser
   ↓
Action
```

Основные компоненты:

| Компонент              | Назначение                      |
| ---------------------- | ------------------------------- |
| `declarativeContent`   | Declarative page-based behavior |
| `PageStateMatcher`     | Описание условий страницы       |
| `pageUrl`              | Условия по URL                  |
| `css`                  | Условия по DOM                  |
| `ShowAction`           | Контекстная активация action    |
| `RequestContentScript` | Запрос на запуск Content Script |
| `conditions`           | Когда правило применяется       |
| `actions`              | Что происходит после match      |

Главная идея:

```text
        Condition
            ↓
        Browser
            ↓
          Action
```

А не:

```text
        Event
          ↓
    Service Worker
          ↓
      JavaScript
          ↓
       Condition
          ↓
        Action
```

Именно поэтому `declarativeContent` хорошо вписывается в общую архитектуру MV3:

```text
                       Manifest V3
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
     Extension UI    Service Worker   Declarative APIs
                           │                │
                           │         declarativeContent
                           │                │
                           └───────┬────────┘
                                   ▼
                              Web Platform
```

**Declarative Content не является заменой Service Worker или Content Scripts. Он является механизмом контекстной фильтрации и активации, который позволяет передать браузеру простую логику определения того, когда extension должен быть активен.**

В следующей главе логично перейти к гораздо более мощному и практически важному declarative API — **`declarativeNetRequest`**, где декларативная модель применяется уже не к активации UI, а к **сетевым запросам: блокировке, перенаправлению и модификации HTTP request/response поведения**.
