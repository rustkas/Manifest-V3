# Глава 17. Extension Action

`action` — один из основных механизмов пользовательского интерфейса расширения Manifest V3.

Именно через `action` расширение получает точку присутствия в браузере:

```text
Browser Toolbar
       │
       ▼
 Extension Action
       │
 ┌─────┼─────────────┐
 ▼     ▼             ▼
Icon  Badge         Popup
```

Для пользователя `action` обычно выглядит как кнопка расширения на панели браузера.

Для разработчика это не просто кнопка. `action` объединяет несколько возможностей:

* toolbar icon;
* tooltip;
* badge;
* popup;
* обработку клика;
* динамическое изменение состояния;
* взаимодействие с текущей вкладкой.

В Manifest V3 `action` является современным механизмом, пришедшим на смену нескольким старым API, прежде всего `browser_action` и `page_action`.

---

# 17.1. Что такое `action`

В `manifest.json` `action` описывает пользовательскую точку входа в расширение.

Минимальный вариант:

```json
{
    "manifest_version": 3,
    "name": "My Extension",
    "version": "1.0.0",
    "action": {}
}
```

После установки браузер получает возможность отображать extension action в интерфейсе.

Наиболее важная идея:

> `action` связывает расширение с toolbar UI браузера.

---

# Action как UI entry point

Пользователь может:

```text
Click
  │
  ▼
Action
  │
  ├── Popup
  │
  └── Click event
```

Например:

```text
User
 │
 │ click
 ▼
Extension Action
 │
 ├── открыть Popup
 │
 └── либо передать событие Service Worker
```

Какой именно сценарий используется, зависит от конфигурации `action`.

---

# `action` в Manifest V3

Пример:

```json
{
    "action": {
        "default_title": "My Extension",
        "default_popup": "popup.html"
    }
}
```

Здесь мы говорим браузеру:

```text
Toolbar button
      │
      ├── title = My Extension
      │
      └── click → popup.html
```

---

# Основные свойства `action`

В практической работе наиболее важны:

```text
action
├── default_title
├── default_popup
├── default_icon
└── icons
```

Кроме manifest-конфигурации существуют runtime API:

```text
chrome.action
├── setBadgeText()
├── setBadgeBackgroundColor()
├── setTitle()
├── setIcon()
├── enable()
├── disable()
└── onClicked
```

Таким образом, `action` имеет две стороны:

```text
Manifest
   │
   ▼
Initial configuration

Runtime API
   │
   ▼
Dynamic state
```

---

# 17.2. Toolbar button

Основное визуальное представление `action` — кнопка расширения в toolbar браузера.

Условно:

```text
┌──────────────────────────────────────────────┐
│ ←  →  ⟳   Address bar        [Extension]    │
└──────────────────────────────────────────────┘
                                      ▲
                                      │
                                   action
```

Однако важно понимать:

> Extension не может произвольно разместить кнопку в любом месте toolbar.

Браузер управляет интерфейсом toolbar.

Пользователь может:

* установить расширение;
* закрепить его;
* убрать его из toolbar;
* изменить порядок кнопок.

Поэтому приложение не должно предполагать конкретное положение `action`.

---

# Action — часть browser UI

Это фундаментальное отличие от обычной HTML-кнопки.

Мы не создаём:

```html
<button>
    My Extension
</button>
```

в собственной странице.

Вместо этого:

```text
Browser UI
    │
    ▼
chrome.action
```

Браузер сам отображает кнопку и управляет её жизненным циклом.

---

# Click event

Если `action` не связан с popup, можно обрабатывать клик:

```javascript
chrome.action.onClicked.addListener((tab) => {
    console.log("Action clicked");
});
```

Обычно этот код находится в Service Worker:

```javascript
// service-worker.js

chrome.action.onClicked.addListener((tab) => {
    console.log("Clicked:", tab.id);
});
```

---

# Popup и `onClicked`

Здесь есть важный архитектурный момент.

Если у `action` определён:

```json
{
    "action": {
        "default_popup": "popup.html"
    }
}
```

то обычный click открывает popup.

В таком сценарии не следует проектировать систему так, будто:

```text
click
  ↓
onClicked
  ↓
popup
```

Popup открывается браузером непосредственно как UI.

То есть это два разных сценария:

### Action без popup

```text
Click
  ↓
chrome.action.onClicked
```

### Action с popup

```text
Click
  ↓
Popup
```

---

# 17.3. Icon

Icon — визуальное представление расширения.

Можно указать icon в `action`:

```json
{
    "action": {
        "default_icon": {
            "16": "icons/icon16.png",
            "32": "icons/icon32.png",
            "48": "icons/icon48.png",
            "128": "icons/icon128.png"
        }
    }
}
```

Конкретный набор размеров может зависеть от требований браузера и от того, где используется изображение.

---

# Почему несколько размеров?

Потому что браузер отображает icon в различных UI contexts.

Условно:

```text
16 × 16
32 × 32
48 × 48
128 × 128
```

могут использоваться в различных местах.

Не следует просто масштабировать маленькую иконку до любого размера.

Лучше подготовить подходящие ресурсы.

---

# `icons` и `action.default_icon`

Не следует путать:

```json
{
    "icons": {
        "16": "icons/icon16.png",
        "48": "icons/icon48.png",
        "128": "icons/icon128.png"
    }
}
```

и:

```json
{
    "action": {
        "default_icon": {
            "16": "icons/icon16.png",
            "32": "icons/icon32.png"
        }
    }
}
```

`icons` — общие icon resources расширения.

`action.default_icon` — icon, используемый именно для Action.

В некоторых случаях можно использовать одинаковые файлы:

```text
extension icon
      │
      ├── manifest icon
      └── action icon
```

Но концептуально это разные назначения.

---

# Dynamic icon

Icon можно менять во время работы:

```javascript
await chrome.action.setIcon({
    path: {
        16: "icons/active16.png",
        32: "icons/active32.png"
    }
});
```

Например:

```text
Extension inactive
      ↓
gray icon

Extension active
      ↓
colored icon
```

Это позволяет визуально сообщать пользователю состояние extension.

---

# Но icon не должен быть единственным indicator

Например, не стоит делать:

```text
gray  = stopped
blue  = running
red   = error
green = completed
```

без дополнительного объяснения.

Пользователь может не понимать значение цвета.

Поэтому состояние можно дополнительно отображать через:

```text
Icon
+
Badge
+
Title
+
Popup
```

---

# 17.4. Badge

Badge — небольшая текстовая область поверх Action icon.

Например:

```text
       ┌─────┐
       │  12 │
       │  ◉  │
       └─────┘
```

Badge особенно полезен для:

* количества элементов;
* состояния;
* уведомлений;
* прогресса;
* небольших числовых значений.

---

# Установка текста

```javascript
await chrome.action.setBadgeText({
    text: "12"
});
```

---

# Background color

Можно установить цвет фона badge:

```javascript
await chrome.action.setBadgeBackgroundColor({
    color: "#FF0000"
});
```

Однако конкретное визуальное оформление зависит от браузера и его UI.

---

# Очистка badge

```javascript
await chrome.action.setBadgeText({
    text: ""
});
```

---

# Badge как state indicator

Например:

```text
Extension
    │
    ├── 0 → ""
    ├── 5 → "5"
    └── 99 → "99"
```

Это удобно для notification-like сценариев.

---

# Ограниченность badge

Badge не является полноценным UI.

Нельзя рассчитывать на него для отображения:

```text
Long descriptive text
Complex state
Multiple controls
Detailed error
```

Для этого нужен Popup или другой UI.

Badge предназначен для **короткого визуального сигнала**.

---

# Badge и текущая вкладка

Особенно интересный сценарий:

```text
Tab A → 3 items
Tab B → 10 items
Tab C → 0 items
```

Action может показывать состояние, связанное с текущей вкладкой.

Например:

```text
Tab A       Tab B       Tab C
  │           │           │
 "3"         "10"         ""
```

Для этого необходимо учитывать `tabId`.

Например:

```javascript
await chrome.action.setBadgeText({
    tabId: tab.id,
    text: "3"
});
```

Таким образом badge может быть контекстным.

---

# 17.5. Title

`title` — это текстовая подсказка, связанная с Action.

В manifest:

```json
{
    "action": {
        "default_title": "Open My Extension"
    }
}
```

Можно изменить его динамически:

```javascript
await chrome.action.setTitle({
    title: "Extension is active"
});
```

---

# Зачем нужен title?

Title позволяет дать пользователю краткое объяснение:

```text
Icon
  +
Tooltip
```

Например:

```text
"Start scanner"
"Scanner is running"
"3 items found"
```

---

# Dynamic title

Состояние:

```text
inactive
```

может отображаться:

```text
Scanner inactive
```

А после запуска:

```text
Scanner is running
```

Пример:

```javascript
await chrome.action.setTitle({
    title: "Scanner is running"
});
```

---

# Title не заменяет UI

Нельзя превращать title в основной механизм информирования пользователя.

Он должен быть:

* коротким;
* понятным;
* контекстным.

Если нужно показать подробности, используйте Popup или Side Panel.

---

# 17.6. Popup

Popup — HTML-интерфейс, который открывается при взаимодействии с Action.

Manifest:

```json
{
    "action": {
        "default_popup": "popup.html"
    }
}
```

Структура:

```text
extension/
│
├── manifest.json
├── service-worker.js
│
├── popup.html
├── popup.css
└── popup.js
```

---

# Popup — обычная extension page

Очень важно понимать:

> Popup не является особым JavaScript environment в том же смысле, что Content Script.

Это extension page.

Поэтому он имеет:

* свой DOM;
* свой JavaScript;
* свой CSS;
* extension origin;
* доступ к разрешённым extension APIs.

Например:

```html
<!doctype html>
<html>
<head>
    <meta charset="utf-8">
</head>
<body>

    <button id="start">
        Start
    </button>

    <script type="module" src="popup.js"></script>
</body>
</html>
```

---

# Popup → Service Worker

Popup может отправить команду:

```javascript
document.querySelector("#start")
    .addEventListener("click", async () => {

        await chrome.runtime.sendMessage({
            type: "START"
        });

    });
```

Получаем:

```text
Popup
 │
 │ START
 ▼
Service Worker
```

---

# Popup lifecycle

У Popup очень короткая жизнь.

Условно:

```text
open
  ↓
user interaction
  ↓
close
  ↓
destroy
```

Поэтому нельзя считать Popup persistent runtime.

Например:

```javascript
let state = {};
```

будет существовать только пока конкретный экземпляр Popup существует.

После закрытия:

```text
Popup destroyed
```

состояние исчезает.

---

# Где хранить состояние?

Не:

```javascript
// popup.js

let currentState = {};
```

если состояние должно пережить закрытие Popup.

Лучше:

```text
Popup
   │
   ▼
Service Worker
   │
   ▼
chrome.storage
```

или, если логика простая, Popup может напрямую работать с:

```text
chrome.storage
```

---

# Popup как command UI

Очень хорошая модель:

```text
Popup
 ├── render state
 ├── collect user input
 └── send commands
```

А не:

```text
Popup
 ├── global state
 ├── network
 ├── scheduling
 ├── tabs management
 ├── business logic
 └── everything else
```

---

# 17.7. Dynamic action state

Одна из самых сильных возможностей `chrome.action` — изменение состояния Action во время работы расширения.

Состояние может включать:

```text
Icon
Badge
Title
Enabled/disabled
Popup
```

---

# `setBadgeText()`

```javascript
chrome.action.setBadgeText({
    text: "5"
});
```

---

# `setBadgeBackgroundColor()`

```javascript
chrome.action.setBadgeBackgroundColor({
    color: "#000000"
});
```

---

# `setTitle()`

```javascript
chrome.action.setTitle({
    title: "5 items found"
});
```

---

# `setIcon()`

```javascript
chrome.action.setIcon({
    path: {
        16: "icons/active16.png",
        32: "icons/active32.png"
    }
});
```

---

# `enable()` и `disable()`

Action можно включать и отключать:

```javascript
chrome.action.disable(tab.id);
```

и:

```javascript
chrome.action.enable(tab.id);
```

Это особенно интересно для tab-specific functionality.

---

# Например

Расширение работает только на:

```text
https://example.com/*
```

На других сайтах Action может быть отключён:

```text
example.com
   ↓
enabled

google.com
   ↓
disabled
```

Но важно понимать:

> Отключение Action — это UI/interaction control, а не замена permission model.

Нельзя считать:

```text
action.disable()
```

механизмом безопасности.

Безопасность должна определяться permissions, host permissions, validation и архитектурой доступа.

---

# Dynamic Popup

Для Action также существуют runtime-возможности настройки popup.

Например, архитектура может учитывать состояние текущей вкладки.

Но здесь важно не превращать Action в слишком сложную систему.

Лучше:

```text
Action
   ↓
Popup
   ↓
Context-specific UI
```

чем создавать множество динамических вариантов без необходимости.

---

# State machine

Для сложного extension удобно представить Action как state machine:

```text
                 ┌───────────┐
                 │   IDLE    │
                 └─────┬─────┘
                       │
                    START
                       │
                       ▼
                 ┌───────────┐
                 │  RUNNING  │
                 └─────┬─────┘
                       │
                    COMPLETE
                       │
                       ▼
                 ┌───────────┐
                 │ COMPLETED │
                 └───────────┘
```

Каждому состоянию можно соответствовать:

```text
IDLE
 ├── icon
 ├── title
 └── badge

RUNNING
 ├── icon
 ├── title
 └── badge

COMPLETED
 ├── icon
 ├── title
 └── badge
```

---

# Не хранить Action state только в Action

Это важный архитектурный принцип.

Плохой вариант:

```text
Action = state
```

Лучше:

```text
Application State
       │
       ▼
Action Presentation
```

То есть Action является **представлением состояния**, а не самим источником истины.

Например:

```text
chrome.storage
      │
      ▼
Application state
      │
      ▼
Service Worker
      │
      ├── setIcon()
      ├── setBadgeText()
      └── setTitle()
```

---

# 17.8. Контекст вкладки

Action тесно связан с текущей browser tab.

При клике:

```javascript
chrome.action.onClicked.addListener((tab) => {
    console.log(tab.id);
});
```

объект `tab` позволяет понять контекст взаимодействия.

Например:

```javascript
chrome.action.onClicked.addListener((tab) => {

    if (!tab.id) {
        return;
    }

    chrome.tabs.sendMessage(tab.id, {
        type: "START"
    });

});
```

Архитектура:

```text
User
 │
 ▼
Action
 │
 ▼
Current Tab
 │
 ▼
Content Script
```

---

# Почему `tabId` важен?

Потому что расширение может работать одновременно с множеством вкладок:

```text
Tab 1
Tab 2
Tab 3
Tab 4
```

У каждой вкладки может быть собственное состояние:

```text
Tab 1 → idle
Tab 2 → scanning
Tab 3 → completed
Tab 4 → unsupported
```

Поэтому часто необходимо мыслить состоянием:

```text
state[tabId]
```

а не просто:

```text
state
```

---

# Tab-specific Action state

Action API позволяет использовать `tabId` для некоторых операций.

Например:

```javascript
await chrome.action.setBadgeText({
    tabId: tab.id,
    text: "3"
});
```

Это означает:

> Показать badge `3` для данного tab context.

Таким образом Action может представлять состояние конкретной страницы.

---

# Пример

Пусть extension анализирует страницу.

На первой вкладке:

```text
example.com
5 elements
```

На второй:

```text
another.com
12 elements
```

Action может отображать:

```text
Tab 1 → [5]
Tab 2 → [12]
```

---

# Но не следует путать tab state и global state

Например:

```text
Global:
extensionEnabled = true
```

и:

```text
Per-tab:
tab[123].scanStatus = "running"
```

Это разные уровни состояния.

Хорошая архитектура явно разделяет:

```text
Global State
      │
      └── Extension configuration

Tab State
      │
      ├── page capability
      ├── scan state
      └── result
```

---

# 17.9. Action events

Основное событие Action:

```javascript
chrome.action.onClicked
```

Например:

```javascript
chrome.action.onClicked.addListener((tab) => {
    console.log("Action clicked", tab.id);
});
```

Это event-driven модель.

---

# Event-driven architecture

Action не требует постоянного polling:

```text
❌

while (true) {
    checkIfUserClicked();
}
```

Вместо этого:

```text
Browser
   │
   │ click
   ▼
Action event
   │
   ▼
Service Worker
```

---

# `onClicked` как вход в application

Для расширения без popup:

```text
User
  │
  ▼
Action click
  │
  ▼
onClicked
  │
  ▼
Application command
```

Например:

```javascript
chrome.action.onClicked.addListener(async (tab) => {

    if (!tab.id) {
        return;
    }

    await chrome.tabs.sendMessage(
        tab.id,
        {
            type: "TOGGLE"
        }
    );

});
```

---

# Action event и message protocol

Не стоит смешивать browser event и application logic.

Плохая модель:

```javascript
chrome.action.onClicked.addListener(async (tab) => {

    // 300 строк business logic

});
```

Лучше:

```javascript
chrome.action.onClicked.addListener(async (tab) => {

    await handleCommand({
        type: "TOGGLE",
        tabId: tab.id
    });

});
```

Теперь:

```text
Browser Event
     │
     ▼
Application Command
     │
     ▼
Business Logic
```

---

# Action и Service Worker

Очень естественная архитектура Manifest V3:

```text
              Browser
                 │
              Action
                 │
             onClicked
                 │
                 ▼
          Service Worker
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Storage     Tabs     Content
```

Action не должен становиться самостоятельным application runtime.

---

# Action и Popup: две разные модели

Нужно чётко различать.

## Модель A — Action как command

```text
Click
  ↓
onClicked
  ↓
Service Worker
```

Подходит для:

* toggle;
* start/stop;
* command;
* immediate operation.

---

## Модель B — Action как UI launcher

```text
Click
  ↓
Popup
```

Подходит для:

* настроек текущей операции;
* нескольких кнопок;
* отображения информации;
* небольшого интерфейса.

---

# Можно ли совместить?

Popup сам может после открытия отправить команду:

```text
Click
 ↓
Popup
 ↓
sendMessage()
 ↓
Service Worker
```

Таким образом:

```text
Action
   │
   ▼
Popup
   │
   ▼
Service Worker
```

# Action как presentation layer

На архитектурном уровне Action можно представить так:

```text
                    Application State
                           │
                           ▼
                  ┌─────────────────┐
                  │ Action Presenter│
                  └────────┬────────┘
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
           Icon          Badge          Title
                           │
                           ▼
                         Popup
```

Это очень полезная модель для больших расширений.

# Пример production-like архитектуры

Представим extension, которое анализирует веб-страницу.

Состояние:

```javascript
{
    enabled: true,
    tabs: {
        "123": {
            status: "running",
            count: 7
        }
    }
}
```

Service Worker получает изменение:

```text
Content Script
      │
      │ SCAN_PROGRESS
      ▼
Service Worker
      │
      ▼
Application State
      │
      ▼
Action Presenter
```

После этого:

```text
Action
 ├── badge = "7"
 ├── title = "7 items found"
 └── icon = active
```

# Такой подход масштабируется

Позже можно добавить:

```text
Popup
Side Panel
Options
Notifications
```

И все они получают информацию из одного application state.

```text
                   Application State
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
        Action          Popup        Side Panel
```

Это значительно лучше, чем хранить отдельную версию состояния в каждом UI context.

# Что нужно запомнить

`action` — это не просто иконка.

Это **browser-managed entry point** в extension.

Он объединяет:

```text
Action
├── Toolbar button
├── Icon
├── Badge
├── Title
├── Popup
├── Click event
└── Dynamic state
```

---

## Архитектурные правила

### 1. Action — UI layer

```text
Action ≠ Business Logic
```

---

### 2. Popup — ephemeral UI

```text
Popup
  ↓
open
  ↓
use
  ↓
destroy
```

Не храните в нём критическое persistent state.

---

### 3. Service Worker — coordinator

```text
Action
   ↓
Service Worker
   ↓
Application
```

---

### 4. Action state — представление application state

```text
Application State
       ↓
Action
```

а не:

```text
Action
   ↓
Application State
```

---

### 5. Badge предназначен для коротких сигналов

```text
5
!
NEW
```

а не для полноценного интерфейса.

---

### 6. Title — краткая подсказка

Используйте его для:

```text
context
status
short explanation
```

---

### 7. Учитывайте `tabId`

Если поведение зависит от страницы:

```text
global state
+
per-tab state
```

должны быть разделены.

---

### 8. `onClicked` — event, а не business logic

Правильная цепочка:

```text
Browser event
     ↓
Command
     ↓
Service Worker
     ↓
Application logic
```

# Итоговая модель Action

В полном Manifest V3 extension `action` занимает примерно такое место:

```text
                         USER
                           │
                         click
                           │
                           ▼
                    ┌─────────────┐
                    │   ACTION    │
                    └──────┬──────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
          Popup                    onClicked
             │                           │
             │                           ▼
             │                    Service Worker
             │                           │
             └──────────────┬────────────┘
                            ▼
                     Application Logic
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           Storage         Tabs        Content
              │
              ▼
        Application State
              │
              ▼
       Action Presentation
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
     Icon   Badge   Title
```

Именно поэтому `action` следует рассматривать не как «кнопку расширения», а как **границу между browser UI и application runtime**.

Браузер управляет визуальным присутствием Action, пользователь инициирует взаимодействие, а само расширение через Service Worker превращает это взаимодействие в команды, изменяет application state и при необходимости отражает новое состояние обратно через icon, badge, title или Popup.
