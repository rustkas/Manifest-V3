# Часть III. Extension Contexts

# Глава 7. Контексты выполнения

В предыдущей главе мы рассмотрели безопасность Manifest V3 и пришли к одному из главных выводов:

> **Browser extension — это не один JavaScript runtime.**

Extension состоит из нескольких контекстов выполнения.

Каждый контекст:

* имеет собственный жизненный цикл;
* имеет свой набор API;
* работает в определённой security environment;
* имеет собственное состояние JavaScript;
* по-разному взаимодействует с веб-страницей;
* может существовать независимо от других контекстов.

Упрощённо архитектуру можно представить так:

```text
                           Browser
                              │
               ┌──────────────┴──────────────┐
               │                             │
          Web Platform                  Extension
               │                             │
        ┌──────┴──────┐              ┌───────┴────────┐
        │             │              │                │
     Web Page    Content Script   Extension UI   Service Worker
                                   │
                            ┌──────┼──────┐
                            │      │      │
                          Popup  Options Side Panel
```

А при разработке более сложного extension появляется ещё один контекст:

```text
DevTools
```

Поэтому одна из первых архитектурных задач разработчика Manifest V3 — понять:

> **В каком context должен выполняться конкретный код?**

---

# 7.1. Что такое execution context

**Execution context** — это среда, в которой выполняется JavaScript.

В обычном веб-приложении разработчик часто мыслит очень просто:

```text
HTML
  ↓
JavaScript
  ↓
DOM
```

В extension модель значительно сложнее.

Например:

```text
                   Extension
                       │
       ┌───────────────┼────────────────┐
       │               │                │
     Popup         Content Script   Service Worker
       │               │                │
    DOM/UI          Page DOM         No DOM
```

У каждого из этих contexts свой JavaScript environment.

---

## Почему это важно?

Рассмотрим:

```javascript
const counter = 10;
```

Если этот код выполняется в Popup:

```text
Popup → counter
```

и такой же код выполняется в Service Worker:

```text
Service Worker → counter
```

это **не одна и та же переменная**.

У каждого context собственное JavaScript state.

Упрощённо:

```text
Popup
┌─────────────────┐
│ counter = 10    │
└─────────────────┘

Service Worker
┌─────────────────┐
│ counter = 20    │
└─────────────────┘
```

Изменение одной переменной не изменяет другую.

---

## Context имеет собственный global object

Например:

```javascript
globalThis
```

существует в каждом context.

Но это разные объекты в разных execution environments.

Поэтому нельзя рассчитывать на:

```javascript
// Popup
globalThis.someData = ...
```

и затем:

```javascript
// Service Worker
console.log(globalThis.someData);
```

Так это не работает.

---

# Контекст как отдельный runtime

Полезно мыслить не так:

```text
Extension
└── JavaScript
```

а так:

```text
Extension
├── Popup runtime
├── Options runtime
├── Side Panel runtime
├── Content Script runtime
├── Service Worker runtime
└── DevTools runtime
```

Это одно из фундаментальных архитектурных понятий Manifest V3.

---

# 7.2. Extension page

**Extension page** — HTML-страница, принадлежащая самому extension.

Например:

```text
popup.html
options.html
sidepanel.html
```

Такие страницы работают внутри extension origin:

```text
chrome-extension://<extension-id>/
```

---

## Пример

Пусть extension содержит:

```text
extension/
├── manifest.json
├── popup.html
├── popup.js
├── options.html
└── options.js
```

Когда открывается:

```text
popup.html
```

создаётся отдельный extension page context.

```text
chrome-extension://ID/popup.html
```

---

## Extension page имеет DOM

В отличие от Service Worker:

```javascript
document
window
document.querySelector(...)
```

обычно доступны extension pages.

Например:

```javascript
const button = document.querySelector("#save");

button.addEventListener("click", () => {
    console.log("Save");
});
```

Это обычная DOM-oriented environment.

---

## Но extension page — не web page

Это важное различие.

```text
https://example.com
```

и:

```text
chrome-extension://ID/popup.html
```

— разные origins.

Extension page принадлежит extension.

---

## Extension pages могут использовать extension APIs

Например:

```javascript
chrome.storage.local
```

или:

```javascript
chrome.runtime.sendMessage(...)
```

в зависимости от конкретного API и контекста.

Таким образом:

```text
Extension Page
      │
      ├── DOM
      ├── JavaScript
      └── Extension APIs
```

---

# 7.3. Service Worker

Service Worker — центральный background execution context Manifest V3.

В Manifest V2 использовалась более постоянная background page.

Manifest V3 изменила эту модель.

Вместо:

```text
Always running background page
```

используется:

```text
Event-driven Service Worker
```

---

## Архитектура

```text
                   Extension
                       │
                       ▼
                 Service Worker
                       │
          ┌────────────┼────────────┐
          │            │            │
       messages      events       APIs
```

Service Worker реагирует на события.

Например:

```javascript
chrome.runtime.onMessage.addListener(...);
```

или:

```javascript
chrome.commands.onCommand.addListener(...);
```

или:

```javascript
chrome.action.onClicked.addListener(...);
```

---

## У Service Worker нет DOM

Это принципиальное отличие.

В Service Worker нельзя рассчитывать на:

```javascript
document
window
```

как в обычной extension page.

Поэтому:

```javascript
document.querySelector(...)
```

в background Service Worker — неправильная архитектура.

---

## Service Worker должен быть event-driven

Не следует проектировать его как:

```text
Start
 ↓
Run forever
 ↓
Keep all state in memory
```

Вместо этого:

```text
Event
 ↓
Wake Service Worker
 ↓
Process event
 ↓
Save persistent state if needed
 ↓
Finish
```

---

## Жизненный цикл

Очень упрощённо:

```text
          Browser event
               │
               ▼
        ┌─────────────┐
        │ Wake worker │
        └──────┬──────┘
               │
               ▼
           Execute
               │
               ▼
        No more work
               │
               ▼
          Worker stops
```

Поэтому глобальная переменная:

```javascript
let cache = {};
```

не должна рассматриваться как долговременное хранилище.

Для persistent state следует использовать соответствующие механизмы, например:

```javascript
chrome.storage.local
```

---

# 7.4. Content Script

Content Script — специальный JavaScript context, предназначенный для взаимодействия с веб-страницей.

Например:

```text
https://example.com/article
```

и:

```text
content.js
```

---

## Основная роль

Content Script обычно используется для:

* чтения DOM;
* изменения DOM;
* обработки пользовательских действий на странице;
* извлечения данных;
* добавления UI;
* взаимодействия между web page и extension.

Архитектура:

```text
Web Page
   │
   ├── DOM
   │
   └── Content Script
           │
           ▼
      Extension Runtime
```

---

## Content Script видит DOM страницы

Например:

```javascript
const title = document.querySelector("h1");

console.log(title?.textContent);
```

Это одна из главных причин существования Content Scripts.

---

## Но Content Script — не Service Worker

У них совершенно разные задачи.

| Context        | DOM | Extension APIs     | Основная роль       |
| -------------- | --- | ------------------ | ------------------- |
| Content Script | Да  | Ограниченный набор | Работа со страницей |
| Service Worker | Нет | Широкий набор      | Background logic    |
| Popup          | Да  | Extension APIs     | UI                  |
| Options        | Да  | Extension APIs     | Settings            |
| Side Panel     | Да  | Extension APIs     | Persistent UI       |

---

# 7.5. Popup

Popup — UI, который открывается при взаимодействии пользователя с Extension Action.

Например:

```text
┌─────────────────────────┐
│  My Extension           │
│                         │
│  Current page           │
│                         │
│  [Analyze]              │
│                         │
└─────────────────────────┘
```

---

## Popup — это extension page

То есть:

```text
Popup
  ↓
Extension Page
  ↓
DOM + Extension APIs
```

Popup имеет:

```text
document
window
DOM
```

---

## Popup живёт недолго

Это очень важная особенность.

Когда пользователь открывает popup:

```text
Open
 ↓
Popup context created
 ↓
User interacts
 ↓
Popup closes
 ↓
Context destroyed
```

Поэтому нельзя использовать popup как постоянный background runtime.

---

## Плохая архитектура

```text
Popup
  ↓
Start timer
  ↓
Wait 30 minutes
```

Пользователь закроет popup, и context исчезнет.

Если задача должна продолжаться независимо от UI, её следует передать Service Worker.

---

## Правильная архитектура

```text
Popup
  │
  │ user clicks
  ▼
Service Worker
  │
  ▼
Background operation
```

---

# 7.6. Options Page

Options Page — интерфейс настроек extension.

Например:

```text
┌──────────────────────────────────┐
│ Extension Settings               │
│                                  │
│ Theme:        [Dark       ▼]     │
│ Language:     [English    ▼]     │
│ Auto analyze: [✓]                │
│                                  │
│              [Save]              │
└──────────────────────────────────┘
```

---

## Options Page — extension page

Поэтому:

```text
Options Page
      ↓
Extension origin
      ↓
DOM
      +
Extension APIs
```

---

## Главная задача

Options Page должна отвечать за:

> **конфигурацию extension.**

Например:

```javascript
await chrome.storage.local.set({
    language: "en",
    autoAnalyze: true
});
```

Service Worker затем может читать эти настройки.

---

## Но contexts всё равно разные

Например:

```text
Options Page
    │
    └── language = "en"

Service Worker
    │
    └── language = ?
```

Это не одна переменная.

Для обмена используется persistent storage или messaging:

```text
Options Page
      │
      ▼
chrome.storage
      │
      ▼
Service Worker
```

---

# 7.7. Side Panel

Side Panel — UI, который может оставаться открытым рядом с содержимым браузера.

Упрощённо:

```text
┌───────────────────────────────┬──────────────┐
│                               │              │
│       Web Page                │  Extension   │
│                               │  Side Panel  │
│                               │              │
│                               │              │
└───────────────────────────────┴──────────────┘
```

Это особенно интересно для extensions, где UI должен существовать дольше, чем popup.

Например:

> Research Assistant.

Пользователь читает страницу:

```text
Article
```

и одновременно держит:

```text
Research Assistant
```

открытым в Side Panel.

---

## Side Panel — extension page

Как и popup:

```text
Side Panel
    ↓
Extension page
    ↓
DOM
+
Extension APIs
```

Но жизненный цикл другой.

Side Panel может оставаться открытым существенно дольше.

---

## Архитектурное преимущество

Popup:

```text
click
 ↓
open
 ↓
interaction
 ↓
close
```

Side Panel:

```text
open
 ↓
longer session
 ↓
interact with multiple pages
 ↓
close later
```

Поэтому Side Panel хорошо подходит для:

* research tools;
* productivity tools;
* note taking;
* AI assistants;
* page analyzers;
* navigation tools.

---

# 7.8. DevTools context

Extensions могут интегрироваться с DevTools.

Например:

```text
┌──────────────────────────────────────┐
│ Web Page                             │
├──────────────────────────────────────┤
│ DevTools                             │
│                                      │
│ Elements | Console | Network | ...  │
│                                      │
│       Extension panel                │
└──────────────────────────────────────┘
```

DevTools integration создаёт отдельный execution context.

---

## Почему это отдельный context?

Потому что DevTools работает с:

* inspected page;
* debugging information;
* network;
* DOM;
* developer tooling.

Это другая среда, чем:

```text
Popup
Service Worker
Content Script
```

---

## DevTools Page

Extension может иметь специальную DevTools page:

```text
devtools.html
```

которая создаётся для конкретной вкладки DevTools.

Например:

```text
Developer opens DevTools
          ↓
Extension DevTools context
          ↓
Extension panel
```

---

## DevTools context не является Content Script

Это важно.

```text
Content Script
    ↓
Web page interaction
```

а:

```text
DevTools context
    ↓
Developer tools integration
```

— разные задачи.

---

# 7.9. Изолированный мир

Теперь мы подошли к одной из наиболее важных концепций Content Scripts.

В Chromium-based extension architecture Content Scripts обычно работают в **isolated world**.

Упрощённо:

```text
Web Page JavaScript
        │
        │
   ─────┼───── isolation boundary
        │
        ▼
Content Script
```

Хотя Content Script работает с DOM страницы, его JavaScript environment изолирован от JavaScript environment самой страницы.

---

## Почему это необходимо?

Представим страницу:

```javascript
window.foo = "page value";
```

Content Script не должен автоматически находиться в том же JavaScript environment, что и код страницы.

Это защищает extension от непосредственного вмешательства page scripts в его JavaScript environment.

---

## Один DOM — разные JavaScript worlds

Это можно представить так:

```text
                Same Page
                    │
          ┌─────────┴─────────┐
          │                   │
      Page World         Isolated World
          │                   │
    Page JavaScript      Content Script
          │                   │
          └────── DOM ────────┘
```

Они могут видеть один DOM, но JavaScript execution environment отличается.

Это очень важное понятие.

---

## Пример концепции

Page script:

```javascript
window.myValue = 123;
```

Content Script не следует рассматривать как код, который просто продолжает выполнение в том же JavaScript global environment.

Именно поэтому взаимодействие между page JavaScript и extension часто требует специального механизма обмена данными.

---

# 7.10. MAIN world

Manifest V3 также предоставляет возможность выполнить Content Script в **MAIN world**.

Это означает, что код выполняется в JavaScript environment самой страницы.

Упрощённо:

```text
             Page
              │
      ┌───────┴────────┐
      │                │
Isolated World      MAIN world
      │                │
Content Script     Page JS context
```

---

## Почему MAIN world вообще нужен?

Иногда extension должен взаимодействовать с JavaScript environment страницы.

Например, страница может предоставлять:

```javascript
window.someApplicationAPI
```

или использовать определённые page-level JavaScript objects.

В isolated world доступ к таким JavaScript globals может отличаться.

MAIN world позволяет работать непосредственно в page JavaScript environment.

---

## Но это снижает изоляцию

Если выполнить extension code в MAIN world:

```text
Extension Code
      ↓
MAIN world
      ↓
Page JavaScript environment
```

extension code оказывается в окружении, которое контролируется страницей.

Поэтому MAIN world следует использовать очень осторожно.

---

## Ключевой принцип

```text
Isolated World
    ↓
Default / safer boundary

MAIN World
    ↓
Use only when page-level JS access is required
```

---

## MAIN world не превращает страницу в trusted environment

Это очень важно.

Если extension запускает код в MAIN world:

```text
MAIN world
    =
Page JavaScript environment
```

а page JavaScript нельзя считать trusted.

Поэтому нельзя переносить туда privileged logic.

---

## Правильная архитектура

Если нужен MAIN world:

```text
                Extension
                    │
              Service Worker
                    │
             validated message
                    │
                    ▼
              Content Script
                    │
                    ▼
               MAIN world
                    │
               page API
```

То есть MAIN world лучше рассматривать как **тонкий bridge**, а не как место хранения privileged extension logic.

---

Теперь соберём contexts в одну таблицу.

| Context        |                  DOM |                                    Extension APIs |                    Page JS | Основное назначение    |

| Service Worker |                    ❌ |                                 Да, широкий набор |                          ❌ | Background logic       |

# 7.12. Что между contexts нельзя передавать напрямую

Это место особенно важно для понимания архитектуры.

Начинающий разработчик часто думает:

```text
Popup
 ↓
global variable
 ↓
Service Worker
```

или:

```text
Content Script
 ↓
global variable
 ↓
Popup
```

Так делать нельзя.

Каждый context имеет собственную память.

---

# Нельзя передавать JavaScript variables напрямую

Например:

```javascript
// popup.js

const user = {
    name: "John"
};
```

Service Worker не может сделать:

```javascript
console.log(user);
```

потому что переменной `user` в его context нет.

---

## Нельзя использовать общий `window`

Например:

```javascript
// popup.js

window.extensionState = {
    loggedIn: true
};
```

Service Worker не увидит:

```javascript
window.extensionState
```

Это разные environments.

---

# Нельзя использовать DOM одного context из другого

Popup:

```javascript
const button = document.querySelector("#save");
```

Service Worker не может сделать:

```javascript
button.click();
```

У Service Worker вообще нет DOM Popup.

---

## Даже два extension pages не имеют общего DOM

Например:

```text
Popup
    │
    └── document

Options
    │
    └── document
```

Это два разных DOM.

---

# Как contexts взаимодействуют?

Для этого используются специальные механизмы.

Основные:

```text
Messaging
Storage
Runtime APIs
Tabs APIs
Ports
Browser APIs
```

---

# Messaging

Например:

```text
Popup
   │
   │ sendMessage()
   ▼
Service Worker
```

Popup:

```javascript
chrome.runtime.sendMessage({
    type: "GET_STATUS"
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        if (message.type === "GET_STATUS") {
            sendResponse({
                status: "ready"
            });
        }
    }
);
```

Это нормальный способ взаимодействия.

---

# Content Script ↔ Service Worker

```text
Content Script
      │
      │ message
      ▼
Service Worker
```

Например:

```javascript
chrome.runtime.sendMessage({
    type: "PAGE_DATA",
    title: document.title
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message) => {

        if (message.type === "PAGE_DATA") {
            console.log(message.title);
        }
    }
);
```

---

# Popup ↔ Content Script

Архитектура может выглядеть так:

```text
Popup
  │
  │ tabs.sendMessage()
  ▼
Content Script
  │
  │ DOM operation
  ▼
Web Page
```

Например:

```javascript
chrome.tabs.sendMessage(tabId, {
    type: "HIGHLIGHT"
});
```

Content Script:

```javascript
chrome.runtime.onMessage.addListener(
    (message) => {

        if (message.type === "HIGHLIGHT") {
            highlightPage();
        }
    }
);
```

# Storage как shared persistent state

Другой способ:

```text
Options
   │
   ▼
chrome.storage
   │
   ├──────────────┐
   │              │
   ▼              ▼
Popup       Service Worker
```

Например:

```javascript
await chrome.storage.local.set({
    theme: "dark"
});
```

Другой context:

```javascript
const { theme } =
    await chrome.storage.local.get("theme");
```

Это не shared memory.

Это **persistent shared data store**.

# Message passing architecture

В результате extension можно представить как распределённую систему:

```text
                 ┌─────────────┐
                 │    Popup    │
                 └──────┬──────┘
                        │
                     Message
                        │
                        ▼
┌─────────────┐   ┌───────────────┐
│   Content   │◄─►│Service Worker │
│   Script    │   └───────┬───────┘
└──────┬──────┘           │
       │                   │
       ▼                   ▼
   Web Page            Storage/API
```

Это уже очень похоже на distributed application.

# Почему это важная архитектурная идея?

Потому что extension нельзя проектировать как:

```text
One Application
One Process
One DOM
One State
```

Правильнее:

```text
Multiple Contexts
      +
Multiple Lifecycles
      +
Explicit Communication
      +
Persistent State
```

# Главное правило выбора context

При проектировании функции задайте четыре вопроса.

### Вопрос 1

Нужно работать с DOM веб-страницы?

```text
Да → Content Script
```

---

### Вопрос 2

Нужно выполнять background logic независимо от UI?

```text
Да → Service Worker
```

---

### Вопрос 3

Нужен UI extension?

```text
Да → Popup / Options / Side Panel
```

---

### Вопрос 4

Нужно взаимодействовать непосредственно с JavaScript page world?

```text
Да → рассмотреть MAIN world
```

Но только если isolated world недостаточен.

# Главные выводы главы

### 1. Extension — это набор execution contexts

Не:

```text
Extension = JavaScript
```

а:

```text
Extension =
    Popup
    +
Options
    +
Side Panel
    +
Content Scripts
    +
Service Worker
    +
DevTools
```

---

### 2. Каждый context имеет собственное состояние

Нельзя рассчитывать на:

```text
global variables
window
DOM
```

как на shared state между contexts.

---

### 3. Service Worker — background runtime

Он:

```text
не имеет DOM
```

и должен проектироваться как event-driven context.

---

### 4. Popup — временный UI

Не следует использовать Popup как background process.

```text
Popup
  ≠
Background Worker
```

---

### 5. Content Script — мост между extension и Web Page

Он работает с DOM страницы, но обычно выполняется в isolated world.

---

### 6. Isolated World — важная security boundary

Условно:

```text
Page JS
   ║
   ║ isolation
   ║
Content Script
```

Они могут работать с одним DOM, но находятся в разных JavaScript environments.

---

### 7. MAIN world следует использовать осторожно

Он нужен для page-level JavaScript integration, но снижает изоляцию.

Главное правило:

> **Privileged extension logic не должна зависеть от доверия к MAIN world.**

---

### 8. Contexts взаимодействуют через API, а не через общую память

Основные механизмы:

```text
Messaging
Storage
Ports
Browser APIs
```

---

### 9. Lifecycle каждого context различается

Особенно важно помнить:

```text
Popup        → short-lived
Content      → page lifecycle
ServiceWorker → event-driven
Side Panel   → longer-lived UI
Options      → settings UI
```

---

### 10. Extension лучше проектировать как распределённую систему

Итоговая модель:

```text
                UI Contexts
                    │
                    │ messaging
                    ▼
              Service Worker
                    │
          ┌─────────┼─────────┐
          │         │         │
       Storage    Network   Browser APIs
                    ▲
                    │
                 messages
                    │
                    ▼
              Content Script
                    │
                    ▼
                 Web Page
```

Именно понимание **execution contexts + lifecycle + trust boundaries + messaging** превращает разработку Manifest V3 из набора API в полноценное архитектурное проектирование.
