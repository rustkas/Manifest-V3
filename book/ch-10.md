# Глава 10. Isolated World

Одно из фундаментальных понятий Chrome Extension Manifest V3 — **Isolated World**.

На первый взгляд Content Script выглядит как обычный JavaScript:

```javascript
document.querySelector("h1");
```

Он работает внутри веб-страницы, видит её DOM и может изменять элементы.

Возникает естественный вопрос:

> Если Content Script находится внутри страницы, почему JavaScript страницы не может просто обратиться к переменным Content Script?

Ответ связан с механизмом **JavaScript worlds**.

В браузере одна и та же веб-страница может одновременно обслуживаться несколькими независимыми JavaScript environments.

Для Chrome Extension это особенно важно:

```text
                    Web Page
                       │
             ┌─────────┴─────────┐
             │                   │
        Page World          Isolated World
             │                   │
      Page JavaScript       Content Script
```

При этом обе среды могут работать с одним DOM:

```text
                 Document
                    │
          ┌─────────┴─────────┐
          │                   │
     Page JavaScript     Content Script
          │                   │
          └─────── DOM ───────┘
```

Это и есть основа модели безопасности Content Scripts.

---

# 10.1. Что такое isolated world

**Isolated World** — это отдельная JavaScript environment, в которой браузер выполняет Content Script.

Она изолирована от JavaScript environment самой веб-страницы.

Упрощённая модель:

```text
                    Browser
                       │
                 Web Document
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
     Page World               Isolated World
          │                         │
          ▼                         ▼
   Page JavaScript            Content Script
```

Главная идея:

> **DOM является общим объектом страницы, но JavaScript globals между worlds изолированы.**

---

# Простой пример

Допустим, веб-страница содержит:

```html
<script>
    window.pageValue = 42;
</script>
```

Page JavaScript может сделать:

```javascript
console.log(window.pageValue);
```

и получить:

```text
42
```

Но Content Script не следует рассматривать как обычный page script, который автоматически находится в той же JavaScript environment.

Например:

```javascript
console.log(window.pageValue);
```

не является способом надёжно взаимодействовать с внутренними JavaScript variables страницы.

Именно это и обеспечивает isolation.

---

# Почему браузеру нужна такая модель?

Представим страницу:

```text
https://example.com
```

На ней работает потенциально недоверенный JavaScript.

Одновременно extension имеет дополнительные возможности:

```text
chrome.storage
chrome.runtime
chrome.tabs
chrome.scripting
```

Если бы Content Script выполнялся непосредственно в той же JavaScript environment, что и сайт, страница могла бы получить гораздо больше возможностей extension.

Это было бы серьёзной проблемой безопасности.

Поэтому браузер создаёт отдельный JavaScript world:

```text
             Page
               │
       untrusted JavaScript
               │
          ╔════╧════╗
          ║ boundary ║
          ╚════╤════╝
               │
        Extension world
               │
          privileged APIs
```

---

# Isolated World как security boundary

Это можно представить следующим образом:

```text
Web Page
   │
   │ untrusted code
   ▼
┌─────────────────────┐
│     Page World      │
└─────────────────────┘

        ║
        ║ isolation
        ║
        ▼

┌─────────────────────┐
│   Isolated World    │
│                     │
│   Content Script    │
└─────────────────────┘
```

Изоляция не означает, что Content Script не может работать со страницей.

Она означает:

> Content Script взаимодействует со страницей через контролируемые browser primitives, а не просто становится частью JavaScript-кода сайта.

---

# 10.2. DOM общий, JavaScript environment различается

Это наиболее важная идея всей главы.

Можно представить две JavaScript среды:

```text
Page World

window
document
global variables
functions
prototypes
```

и:

```text
Isolated World

window
document
global variables
functions
prototypes
```

Но при этом:

```text
document
   ↓
same underlying page document
```

То есть:

```text
             Same DOM
                │
       ┌────────┴────────┐
       │                 │
 Page World        Isolated World
       │                 │
 window             window
 variables          variables
 functions          functions
 prototypes         prototypes
```

---

# Почему это необычно?

В обычном веб-программировании мы привыкли считать:

```javascript
window
```

глобальным объектом страницы.

В модели extension это представление недостаточно точно.

Условно можно думать:

```text
Page World window
        ≠
Content Script window
```

но:

```text
Page World document
        ↔
Content Script document
```

работают с одним документом.

---

# Пример

Page Script:

```javascript
window.foo = "page";
```

Content Script:

```javascript
window.foo = "extension";
```

Можно концептуально получить:

```text
Page World:

window.foo
    ↓
"page"
```

и:

```text
Isolated World:

window.foo
    ↓
"extension"
```

То есть одинаковое имя глобальной переменной не означает, что оба скрипта используют одну переменную.

---

# Но DOM общий

Предположим Content Script выполняет:

```javascript
document.body.dataset.extension = "active";
```

Page JavaScript может увидеть изменение DOM:

```javascript
console.log(
    document.body.dataset.extension
);
```

Получается:

```text
Content Script
      │
      ▼
     DOM
      │
      ▼
Page JavaScript
```

Поэтому isolation **не означает DOM isolation**.

Это очень важное различие.

---

# DOM как shared surface

Можно представить архитектуру:

```text
Page World
     │
     │
     ▼
┌───────────────┐
│     DOM       │
└───────────────┘
     ▲
     │
     │
Isolated World
```

DOM становится своего рода общей поверхностью взаимодействия.

Но JavaScript environments остаются разделёнными.

---

# Что именно изолируется?

Главным образом изолируется JavaScript environment:

* глобальные переменные;
* JavaScript objects;
* функции;
* многие prototype modifications;
* JavaScript execution state.

Но DOM API остаётся доступным Content Script.

---

# Пример с глобальной переменной

Page:

```javascript
window.extensionTest = "page";
```

Content Script:

```javascript
window.extensionTest = "content";
```

Это не должно восприниматься как запись в одну и ту же JavaScript variable storage.

Получается концептуально:

```text
Page World
window.extensionTest
        │
        ▼
     "page"


Isolated World
window.extensionTest
        │
        ▼
    "content"
```

---

# Почему это важно для разработки?

Потому что Content Script нельзя проектировать так:

```text
"I'll just access the website's JavaScript variables."
```

Например, если сайт создаёт:

```javascript
window.appState = {
    user: ...
};
```

нельзя автоматически считать, что Content Script может просто использовать:

```javascript
window.appState
```

как часть своего собственного JavaScript environment.

Если extension действительно должен взаимодействовать с page-level JavaScript, архитектура становится другой.

---

# 10.3. Доступ к странице

Content Script имеет широкие возможности работы с содержимым страницы.

В первую очередь это:

```text
DOM
CSS
Events
URL
Document state
```

---

# Работа с DOM

Например:

```javascript
const title =
    document.querySelector("h1");

console.log(title?.textContent);
```

Content Script может:

* искать элементы;
* читать текст;
* читать attributes;
* изменять attributes;
* создавать элементы;
* удалять элементы;
* менять DOM structure.

---

# Создание UI

Например:

```javascript
const panel =
    document.createElement("div");

panel.textContent =
    "Hello from extension";

document.body.append(panel);
```

На странице появится:

```text
┌──────────────────────────────┐
│ Web Page                     │
│                              │
│ Content                     │
│                              │
│ ┌──────────────────────────┐ │
│ │ Hello from extension     │ │
│ └──────────────────────────┘ │
└──────────────────────────────┘
```

При этом созданный элемент становится частью DOM страницы.

---

# Стили

Content Script может создавать:

```javascript
const style =
    document.createElement("style");

style.textContent = `
    .my-extension-panel {
        position: fixed;
        top: 20px;
        right: 20px;
    }
`;

document.head.append(style);
```

Но необходимо учитывать CSS isolation и возможные конфликты со стилями сайта.

---

# Events

Content Script может работать с DOM events:

```javascript
document.addEventListener(
    "click",
    event => {
        console.log(event.target);
    }
);
```

Например:

```text
User click
    ↓
DOM event
    ↓
Content Script
```

---

# URL

Content Script может использовать page URL:

```javascript
console.log(location.href);
```

Например:

```text
https://example.com/products/123
```

Это особенно важно для extension, работающих с конкретными сайтами.

---

# Но доступ к странице не означает полный доступ к page runtime

Вот принципиальная граница:

```text
Content Script
      │
      ├── DOM             ✓
      ├── events          ✓
      ├── document        ✓
      ├── location        ✓
      │
      └── page's private
          JS state        ✗
```

То есть:

> **Content Script работает с Web Page, но не становится частью её JavaScript runtime.**

---

# 10.4. Доступ к extension APIs

Теперь возникает другая сторона вопроса.

Content Script является extension-controlled context.

Поэтому он может использовать определённые extension APIs, которые недоступны обычному page script.

Например:

```javascript
chrome.runtime.sendMessage({
    type: "HELLO"
});
```

Обычный page script не получает такой extension API просто потому, что находится на той же странице.

---

# Content Script и Service Worker

Очень распространённая схема:

```text
Web Page
    │
    ▼
Content Script
    │
    │ chrome.runtime
    ▼
Service Worker
    │
    ├── Storage
    ├── Network
    └── Extension APIs
```

Content Script выступает посредником.

---

# Почему это безопаснее?

Допустим страница содержит:

```javascript
fetch("https://attacker.example");
```

Этот код работает в Page World.

Он не должен автоматически получить:

```javascript
chrome.runtime
chrome.storage
chrome.tabs
```

которые доступны extension context.

Изоляция предотвращает смешение этих двух моделей.

---

# Extension API ≠ Web API

Это полезно разделять.

Web Page имеет:

```text
document
window
fetch
WebSocket
localStorage
IndexedDB
```

Content Script может также использовать многие Web Platform APIs.

Но extension получает дополнительные возможности:

```text
chrome.runtime
chrome.storage
chrome.i18n
chrome.scripting
...
```

Конкретный набор зависит от context и API permissions.

---

# Content Script как privileged-but-limited context

Можно использовать такую модель:

```text
Page Script
    │
    │ least privilege
    ▼
Web capabilities


Content Script
    │
    │ extension capabilities
    ▼
Extension APIs


Service Worker
    │
    │ broader extension capabilities
    ▼
Extension backend
```

Но Content Script всё равно не обладает всеми возможностями Service Worker.

---

# 10.5. Почему Content Script не равен обычному page script

Рассмотрим два скрипта.

Page Script:

```html
<script src="page.js"></script>
```

Content Script:

```json
{
  "content_scripts": [
    {
      "matches": ["https://example.com/*"],
      "js": ["content.js"]
    }
  ]
}
```

Внешне оба выполняют JavaScript.

Но архитектурно это совершенно разные вещи.

---

# Page Script

```text
Web Page
    │
    ▼
Page World
    │
    ▼
Page JavaScript
```

Page Script:

* принадлежит сайту;
* работает в page world;
* имеет доступ к page JavaScript state;
* не получает extension APIs только из-за нахождения на странице.

---

# Content Script

```text
Extension
    │
    ▼
Content Script
    │
    ▼
Isolated World
    │
    ▼
Page DOM
```

Content Script:

* принадлежит extension;
* запускается browser injection mechanism;
* имеет isolated JavaScript environment;
* может работать с DOM;
* может использовать определённые extension APIs;
* может взаимодействовать с Service Worker.

---

# Сравнение

| Возможность                    | Page Script |           Content Script |
| ------------------------------ | ----------: | -----------------------: |
| DOM                            |           ✓ |                        ✓ |
| Page JavaScript globals        |           ✓ |              Изолированы |
| Extension APIs                 |           ✗ | ✓, в разрешённых случаях |
| Isolated World                 |           ✗ |                        ✓ |
| Service Worker messaging       |           ✗ |                        ✓ |
| Extension-controlled injection |           ✗ |                        ✓ |

---

# Пример конфликта

Предположим сайт содержит:

```javascript
Array.prototype.customMethod =
    function () {
        // page implementation
    };
```

Content Script находится в отдельном JavaScript world.

Поэтому modifications JavaScript prototypes страницы не должны автоматически превращаться в modifications environment Content Script.

Это одно из важных преимуществ isolated world.

---

# 10.6. Конфликты с JavaScript страницы

Несмотря на isolation, Content Script всё равно работает **на реальной странице**.

Поэтому конфликты возможны на уровне shared DOM и browser events.

---

# DOM collision

Допустим extension создаёт:

```html
<div id="panel"></div>
```

Но сайт тоже использует:

```html
<div id="panel"></div>
```

Возникает collision.

Поэтому extension должен использовать уникальные идентификаторы.

Например:

```text
my-extension-panel
```

вместо:

```text
panel
```

---

# CSS collision

Extension добавляет:

```css
button {
    background: red;
}
```

Это потенциально опасно.

Потому что selector:

```text
button
```

слишком общий.

Он может повлиять на UI сайта.

Лучше:

```css
.my-extension-root button {
    ...
}
```

---

# Еще лучше — namespace

Например:

```html
<div class="my-extension-root">
    ...
</div>
```

и:

```css
.my-extension-root .button {
    ...
}
```

Получаем:

```text
Web Page
│
├── Site UI
│
└── .my-extension-root
      └── Extension UI
```

---

# Event collisions

Content Script может слушать:

```javascript
document.addEventListener(
    "click",
    handler
);
```

Но страница тоже может слушать click events.

Поэтому extension должен понимать DOM event propagation:

```text
capture
   ↓
target
   ↓
bubble
```

Не следует без необходимости использовать:

```javascript
event.stopPropagation();
```

потому что это может ломать behaviour сайта.

---

# Global names

Хотя JavaScript globals изолированы, не следует использовать бессмысленные глобальные имена.

Плохой подход:

```javascript
window.app = ...
```

Лучше минимизировать global state вообще.

В Content Script предпочтительно использовать:

```javascript
const state = {};
```

внутри module scope или application scope.

---

# Page functions

Предположим сайт создаёт:

```javascript
window.showModal = ...
```

Content Script не должен автоматически ожидать:

```javascript
showModal();
```

как будто это его собственная функция.

Если нужно вызвать page-level function, требуется специальный механизм взаимодействия между worlds.

---

# Почему это важно?

Потому что isolation защищает extension от:

```text
page variables
page functions
page prototypes
```

Но иногда extension **намеренно** должен взаимодействовать с ними.

Например:

* React application internals;
* page-level framework;
* custom page API;
* JavaScript SDK сайта;
* application state.

Тогда появляется необходимость в MAIN world.

---

# 10.7. MAIN world

**MAIN world** — это JavaScript environment самой веб-страницы.

То есть:

```text
Page JavaScript
        ↓
     MAIN world
```

В отличие от:

```text
Content Script
        ↓
  Isolated world
```

---

# Два мира

Можно представить:

```text
                Web Page
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
      MAIN world       Isolated world
          │                 │
      Page JS          Content Script
```

MAIN world позволяет extension code выполняться в той же JavaScript environment, что и page scripts.

---

# Почему это может быть необходимо?

Допустим сайт предоставляет:

```javascript
window.somePageAPI
```

Content Script в isolated world не должен рассматриваться как обычный page script с прямым доступом к page JavaScript state.

Если extension должен взаимодействовать с page runtime, MAIN world может быть подходящим инструментом.

---

# MAIN world и `world`

В современных Chrome extension APIs можно указывать world для программной инъекции.

Концептуально:

```javascript
chrome.scripting.executeScript({
    target: {
        tabId
    },
    world: "MAIN",
    func: () => {
        // page world
    }
});
```

В manifest-based сценариях также существует возможность определить соответствующий world для Content Script.

---

# MAIN world — это не "более мощный Content Script"

Это очень важное правило.

MAIN world:

```text
ближе к странице
```

но:

```text
дальше от extension isolation
```

То есть это **не повышение привилегий**.

Наоборот, с точки зрения безопасности MAIN world обычно менее надёжен.

---

# Почему MAIN world опаснее?

Потому что page JavaScript находится в той же environment.

Если сайт полностью контролирует JavaScript runtime, extension code должен учитывать возможность взаимодействия с:

* page functions;
* page globals;
* monkey patches;
* modified prototypes;
* malicious page code.

Поэтому MAIN world следует использовать только тогда, когда это действительно необходимо.

---

# Extension code в MAIN world

Нужно мыслить так:

```text
MAIN world
=
page-controlled JavaScript environment
```

а не:

```text
MAIN world
=
trusted extension environment
```

---

# Privileged logic нельзя переносить в MAIN world

Представим extension имеет:

```text
Secret
API token
Sensitive state
```

Нельзя проектировать:

```text
Service Worker
      ↓
MAIN world
      ↓
secret
```

Это плохая архитектура.

Лучше:

```text
MAIN world
      │
      │ page interaction
      ▼
Isolated Content Script
      │
      │ validated message
      ▼
Service Worker
      │
      ▼
Sensitive operation
```

---

# Безопасная архитектура с MAIN world

Например:

```text
                 Web Page
                    │
              MAIN world
                    │
             page interaction
                    │
                    ▼
             Isolated World
                    │
             validate data
                    │
                    ▼
             Service Worker
                    │
             privileged logic
```

Здесь каждый context имеет собственную ответственность.

---

# MAIN world для page hooks

Один из возможных сценариев:

```text
Page API
   ↓
MAIN world hook
   ↓
Intercept/observe
   ↓
Isolated Content Script
   ↓
Service Worker
```

Например, extension должен наблюдать за вызовом page-level API.

Это уже задача, для которой MAIN world может быть оправдан.

---

# MAIN world для framework integration

Иногда extension должен интегрироваться с приложением:

```text
React
Vue
Angular
custom runtime
```

и получить доступ к page-level JavaScript objects.

В таких случаях isolated world может быть недостаточен.

MAIN world позволяет работать непосредственно в той же JavaScript environment.

Но это должно быть исключением, а не стандартом.

---

# 10.8. Когда использовать MAIN world

Главное правило:

> **Используйте Isolated World по умолчанию. Используйте MAIN world только тогда, когда вам действительно нужен доступ к page JavaScript environment.**

---

# Сценарий 1. Работа с DOM

Нужно:

```text
read HTML
modify DOM
add UI
listen DOM events
```

Используйте:

```text
Isolated World
```

Не нужен MAIN world.

---

# Сценарий 2. Извлечение данных

Например:

```text
title
price
article
product data
```

Используйте:

```text
Isolated World
```

потому что данные можно получить через DOM.

---

# Сценарий 3. Добавление UI

Например:

```text
overlay
toolbar
button
sidebar
```

Используйте:

```text
Isolated World
```

---

# Сценарий 4. MutationObserver

```javascript
const observer =
    new MutationObserver(...);
```

Это обычная задача Content Script.

Используйте:

```text
Isolated World
```

---

# Сценарий 5. Работа с page JavaScript API

Например:

```javascript
window.someApplicationAPI
```

если extension действительно должен взаимодействовать именно с page runtime.

Тогда может потребоваться:

```text
MAIN world
```

---

# Сценарий 6. Перехват page-level JavaScript behaviour

Например, extension должен интегрироваться с:

```text
page API
custom SDK
framework runtime
```

и для этого требуется monkey-patching или hook в page environment.

Тогда:

```text
MAIN world
```

может быть оправдан.

---

# Сценарий 7. Работа с секретами

Например:

```text
API credentials
private extension state
sensitive configuration
```

**Не используйте MAIN world.**

Используйте:

```text
Service Worker
```

или другой подходящий extension-controlled context.

---

# Сценарий 8. Работа с Extension APIs

Если основная задача:

```text
chrome.storage
chrome.runtime
chrome.tabs
extension messaging
```

то MAIN world не является правильным местом.

Используйте:

```text
Isolated World
```

или:

```text
Service Worker
```

в зависимости от API и архитектуры.

# Главный принцип: Privilege Separation

Хорошая Manifest V3 архитектура выглядит так:

```text
                    WEB PAGE
                       │
                       ▼
                  MAIN WORLD
                       │
             page-specific logic
                       │
                       ▼
              ISOLATED CONTENT
                    SCRIPT
                       │
                validation
                       │
                       ▼
                SERVICE WORKER
                       │
              privileged logic
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
          Storage    Network    APIs
```

Не нужно пытаться заставить один context делать всё.

---

# Почему нельзя просто всегда использовать MAIN world?

Потому что тогда extension теряет важное преимущество isolated execution.

Если всё делать в MAIN world:

```text
Extension code
      +
Page code
      +
Page modifications
      +
Page prototypes
      +
Page globals
```

становятся частью одной JavaScript environment.

Это увеличивает сложность и потенциальную поверхность атаки.

---

# Правило "Isolated First"

Для production extension полезно принять правило:

```text
                Need page JS runtime?
                       │
              ┌────────┴────────┐
              │                 │
             No                Yes
              │                 │
              ▼                 ▼
        Isolated World      MAIN world
```

То есть MAIN world должен быть **explicit architectural decision**.

Не default.

---

# Isolated World и DOM — важное исключение

Изоляция JavaScript не означает, что DOM становится безопасным хранилищем данных.

Помните:

```text
Content Script
     │
     ▼
Shared DOM
     ▲
     │
Page JavaScript
```

Страница может изменить DOM после того, как Content Script его прочитал.

Поэтому:

```javascript
const value =
    element.textContent;
```

нужно рассматривать как чтение данных из недоверенного источника.

---

# DOM не является trusted channel

Например:

```text
Page
  ↓
DOM attribute
  ↓
Content Script
```

Это не означает:

```text
trusted data
```

Это означает:

```text
untrusted input
```

Поэтому:

```text
Read
 ↓
Validate
 ↓
Normalize
 ↓
Use
```

---

# Communication between worlds

Если Content Script должен взаимодействовать с MAIN world, архитектура обычно требует явного communication channel.

Один из классических механизмов — DOM events / `window.postMessage()` и другие page-visible communication primitives.

Концептуально:

```text
MAIN world
    │
    │ message
    ▼
Isolated world
    │
    │ chrome.runtime
    ▼
Service Worker
```

Но любой такой канал должен рассматриваться как **untrusted input boundary**.

---

# `window.postMessage()`

Например, page-side code может отправить сообщение:

```javascript
window.postMessage({
    source: "my-page-integration",
    type: "DATA",
    value: ...
}, "*");
```

Content Script может слушать:

```javascript
window.addEventListener(
    "message",
    event => {
        // validate event.data
    }
);
```

Но нельзя делать:

```javascript
if (event.data.type === "DATA") {
    trustedOperation(event.data.value);
}
```

без дополнительной валидации.

---

# Почему?

Потому что любое page JavaScript может попытаться отправить похожее сообщение.

Поэтому необходимо проверять:

```text
origin
source
message type
schema
data types
allowed values
```

и только после этого выполнять privileged action.

---

# Типичная ошибка

Плохая архитектура:

```text
MAIN world
    ↓
message
    ↓
Service Worker
    ↓
"trusted"
```

Правильнее:

```text
MAIN world
    ↓
untrusted message
    ↓
Isolated Content Script
    ↓
validation
    ↓
Service Worker
    ↓
validated command
```

# Главные выводы главы

### 1. Isolated World — отдельная JavaScript environment

Content Script не выполняется просто как ещё один `<script>` страницы.

---

### 2. DOM общий

```text
Page World
     ↕
    DOM
     ↕
Isolated World
```

Поэтому Content Script может изменять страницу, несмотря на JavaScript isolation.

---

### 3. JavaScript globals изолированы

Условно:

```text
Page window
    ≠
Content Script window
```

Поэтому page variables и extension variables не следует смешивать.

---

### 4. Content Script имеет доступ к определённым Extension APIs

Именно поэтому он является частью extension architecture, а не обычным page script.

---

### 5. MAIN world — это Page JavaScript environment

```text
MAIN world
    =
Page JavaScript environment
```

Он нужен только для специфических задач, требующих доступа к page runtime.

---

### 6. MAIN world не является "более привилегированным" режимом

Наоборот:

> **MAIN world ближе к недоверенному page code.**

Поэтому sensitive extension logic там размещать не следует.

---

### 7. Используйте Isolated World по умолчанию

```text
DOM
UI
events
extraction
observers
```

обычно должны выполняться в Isolated World.

---

### 8. Используйте MAIN world только для page-runtime integration

Например:

```text
page globals
page functions
page APIs
framework internals
page-level hooks
```

если без этого действительно нельзя решить задачу.

---

### 9. Разделяйте ответственность

Хорошая архитектура:

```text
MAIN world
    ↓
Page integration

Isolated Content Script
    ↓
DOM + validation + bridge

Service Worker
    ↓
Business logic + privileged APIs
```

---

## Архитектурное правило главы

> **Isolated World — стандартная среда для Content Script. MAIN world — специальный механизм интеграции с JavaScript runtime страницы.**

Именно это различие позволяет Manifest V3 одновременно решить две, на первый взгляд противоречивые задачи:

```text
             Extension
                 │
        ┌────────┴────────┐
        │                 │
   Security          Page Integration
        │                 │
        ▼                 ▼
 Isolated World       MAIN World
        │                 │
        └────────┬────────┘
                 ▼
                DOM
```

**Расширение может работать с веб-страницей, не превращая свой код в обычный JavaScript-код этой страницы.** Это один из фундаментальных принципов архитектуры browser extensions.
