# Глава 33. Page ↔ Extension Bridge

В предыдущих главах мы рассмотрели Content Scripts, Isolated World, `MAIN` world и работу с DOM страницы.

Теперь возникает более сложная задача.

Иногда расширению необходимо взаимодействовать не просто с **DOM страницы**, а непосредственно с JavaScript-кодом, который выполняется самой страницей.

Например, расширение хочет:

* получить данные из JavaScript-приложения страницы;
* вызвать функцию page runtime;
* перехватить событие, которое существует только в page JavaScript;
* интегрироваться с библиотекой, загруженной сайтом;
* получить доступ к application state;
* перехватить API, который недоступен непосредственно Content Script;
* установить собственный API для страницы.

Здесь появляется архитектурная граница:

```text
                 Web Page
                    │
              Page JavaScript
                    │
          ┌─────────┴─────────┐
          │   Security        │
          │   Boundary        │
          └─────────┬─────────┘
                    │
              Content Script
                    │
                    ▼
             Extension APIs
                    │
                    ▼
             Service Worker
```

Главная проблема заключается в том, что:

> **Page JavaScript и Content Script могут видеть один DOM, но не имеют одного JavaScript execution environment.**

Для связи между ними используется специальный **bridge**.

---

# 33.1. Почему page и extension изолированы

Браузер специально разделяет:

```text
Page JavaScript
```

и:

```text
Extension JavaScript
```

Это фундаментальный механизм безопасности браузерных расширений.

Например, обычный page script может выполнять:

```javascript
console.log(window);
```

А Content Script также имеет:

```javascript
window
document
location
```

Но это не означает, что:

```text
page.window === contentScript.window
```

в смысле JavaScript execution environment.

Можно представить архитектуру так:

```text
                 Browser
                    │
       ┌────────────┴────────────┐
       │                         │
   Page World              Isolated World
       │                         │
       │                         │
 Page JavaScript           Content Script
       │                         │
       └────────── DOM ──────────┘
```

DOM является общей точкой взаимодействия, но JavaScript globals и объекты runtime разделены.

---

# Почему это сделано

Предположим, страница содержит:

```javascript
window.app = {
    secret: "..."
};
```

Если бы Content Script автоматически получал тот же JavaScript environment, страница могла бы потенциально воздействовать на extension runtime.

И наоборот, page JavaScript получил бы гораздо больше возможностей вмешиваться в extension code.

Изоляция уменьшает эту поверхность атаки.

---

# Что Content Script видит

Content Script может работать с:

```javascript
document
window
location
Element
MutationObserver
fetch
Web APIs
```

и другими объектами Web Platform.

Но page script и Content Script не должны рассматриваться как один JavaScript runtime.

Например, если страница делает:

```javascript
window.pageAPI = {
    getData() {
        return "secret";
    }
};
```

не следует проектировать extension так, будто Content Script может просто сделать:

```javascript
window.pageAPI.getData();
```

и получить page runtime API.

Для такого взаимодействия нужен bridge.

---

# DOM как общая граница

Хотя JavaScript environments разделены, DOM является важной точкой взаимодействия.

Например:

```text
Page JavaScript
      │
      ▼
     DOM
      ▲
      │
Content Script
```

Page может изменить:

```javascript
document.body.dataset.status =
    "ready";
```

Content Script может прочитать:

```javascript
const status =
    document.body.dataset.status;
```

Это один из самых простых видов communication.

---

# 33.2. DOM-based communication

Самый простой bridge может использовать DOM.

Например, page script:

```javascript
document.documentElement.dataset
    .extensionState = "ready";
```

Content Script:

```javascript
const state =
    document.documentElement.dataset
        .extensionState;

console.log(state);
```

Получаем:

```text
Page
 │
 │ write
 ▼
DOM
 │
 │ read
 ▼
Content Script
```

---

# Custom Events

Более гибкий вариант — DOM events.

Page:

```javascript
document.dispatchEvent(
    new CustomEvent(
        "my-extension-event",
        {
            detail: {
                type: "ready"
            }
        }
    )
);
```

Content Script:

```javascript
document.addEventListener(
    "my-extension-event",
    event => {
        console.log(
            event.detail
        );
    }
);
```

Это уже напоминает message bus.

---

# В обратную сторону

Content Script также может отправлять событие:

```javascript
document.dispatchEvent(
    new CustomEvent(
        "my-extension-command",
        {
            detail: {
                action: "start"
            }
        }
    )
);
```

Page:

```javascript
document.addEventListener(
    "my-extension-command",
    event => {

        const {
            action
        } = event.detail;

        if (action === "start") {
            startApplication();
        }
    }
);
```

Получается:

```text
Page
 ▲
 │ CustomEvent
 │
Content Script
```

---

# Проблема DOM-based communication

Такой bridge прост, но имеет ограничения.

Например:

```javascript
document.dispatchEvent(
    new CustomEvent(
        "my-extension-event",
        {
            detail: {
                userId: 123,
                data: {...}
            }
        }
    )
);
```

Любой page JavaScript потенциально может наблюдать такие события.

Следовательно:

> **DOM-based bridge не является приватным каналом между page и extension.**

Это принципиально важно.

---

# Не передавайте секреты

Не следует передавать через DOM:

```text
API keys
access tokens
passwords
private credentials
internal extension secrets
```

Например, плохой дизайн:

```javascript
document.dispatchEvent(
    new CustomEvent(
        "extension-token",
        {
            detail: {
                token: SECRET_TOKEN
            }
        }
    )
);
```

Page JavaScript может попытаться перехватить такую информацию.

---

# DOM communication как public protocol

Лучше мыслить так:

```text
DOM Bridge
     =
Public communication surface
```

То есть всё, что передаётся через него, должно считаться потенциально наблюдаемым.

---

# 33.3. `window.postMessage()`

Более стандартный механизм для коммуникации между window contexts:

```javascript
window.postMessage(
    message,
    targetOrigin
);
```

Например:

```javascript
window.postMessage(
    {
        source: "my-extension",
        type: "PING"
    },
    window.location.origin
);
```

Получатель:

```javascript
window.addEventListener(
    "message",
    event => {

        console.log(
            event.data
        );

    }
);
```

---

# Структура MessageEvent

При обработке сообщения доступны:

```javascript
event.source
event.origin
event.data
```

Например:

```javascript
window.addEventListener(
    "message",
    event => {

        console.log(
            event.origin
        );

        console.log(
            event.data
        );
    }
);
```

---

# `event.origin`

Одна из наиболее важных проверок:

```javascript
if (
    event.origin !==
    window.location.origin
) {
    return;
}
```

Она ограничивает сообщения ожидаемым origin.

Но важно понимать:

> Проверка `origin` сама по себе не доказывает, что сообщение отправил именно ваш extension.

На странице может существовать другой JavaScript-код с тем же origin.

Поэтому нужен дополнительный protocol-level validation.

---

# Почему `*` опасен как привычка

Можно написать:

```javascript
window.postMessage(
    message,
    "*"
);
```

Это допустимо в некоторых сценариях, но не должно становиться архитектурной привычкой.

Если сообщение содержит чувствительные данные, использование:

```javascript
"*"
```

может создать ненужную поверхность раскрытия данных.

Лучше использовать конкретный target origin там, где это возможно.

---

# Message validation

Никогда не следует доверять:

```javascript
event.data
```

автоматически.

Плохой код:

```javascript
window.addEventListener(
    "message",
    event => {

        if (
            event.data.action ===
            "delete"
        ) {
            deleteEverything();
        }
    }
);
```

Почему?

Потому что любой код страницы потенциально может отправить:

```javascript
window.postMessage(
    {
        action: "delete"
    },
    "*"
);
```

---

# Envelope protocol

Лучше использовать формальный message envelope:

```javascript
{
    source: "my-extension",
    version: 1,
    type: "GET_PRODUCT",
    requestId: "abc123",
    payload: {
        productId: "123"
    }
}
```

Получатель проверяет:

```text
source
version
type
requestId
payload
```

---

# Пример validation

```javascript
function isValidMessage(
    data
) {
    return (
        data &&
        data.source ===
            "my-extension" &&
        data.version === 1 &&
        typeof data.type ===
            "string"
    );
}
```

Использование:

```javascript
window.addEventListener(
    "message",
    event => {

        if (
            event.origin !==
            window.location.origin
        ) {
            return;
        }

        if (
            !isValidMessage(
                event.data
            )
        ) {
            return;
        }

        handleMessage(
            event.data
        );
    }
);
```

---

# 33.4. MAIN world

Manifest V3 позволяет выполнять код в `MAIN` world.

Концептуально:

```text
ISOLATED world
       │
       │
       │ bridge
       │
       ▼
MAIN world
       │
       ▼
Page JavaScript
```

В `MAIN` world код выполняется в том же JavaScript environment, что и page code.

Это даёт возможность взаимодействовать с:

```javascript
window
```

и объектами, созданными page JavaScript.

---

# Почему MAIN world отличается

В Isolated World:

```javascript
window.pageLibrary
```

может быть недоступен так, как ожидается.

В MAIN world:

```javascript
window.pageLibrary
```

может быть доступен, потому что код работает в page's JavaScript world.

Это полезно для:

```text
API instrumentation
page library integration
global hooks
page-level event handling
```

---

# Но MAIN world имеет серьёзную цену

Главный принцип:

> **MAIN world находится под влиянием страницы.**

То есть extension code, работающий там, не следует считать защищённым от page JavaScript.

Если страница делает:

```javascript
window.someFunction = maliciousFunction;
```

или изменяет глобальные объекты, MAIN-world code может столкнуться с этими изменениями.

---

# MAIN world не получает магически все extension APIs

Это важное различие.

Нельзя мыслить:

```text
MAIN world
=
Content Script
+
page globals
+
all chrome APIs
```

Это неверно.

MAIN world предназначен прежде всего для взаимодействия с page JavaScript environment.

Поэтому часто архитектура выглядит так:

```text
MAIN World
    │
    │ postMessage
    ▼
Content Script
    │
    │ chrome.runtime.sendMessage()
    ▼
Service Worker
```

---

# Почему нельзя выполнять всё в MAIN world

Потому что это расширяет trust boundary.

Если выполнить:

```javascript
// MAIN world
```

слишком много extension logic, значительная часть логики окажется в environment, контролируемом страницей.

Лучше:

```text
MAIN world
    │
    │ minimal bridge
    ▼
Content Script
    │
    ▼
Extension logic
```

---

# 33.5. Injection bridge

Иногда extension должен установить небольшой JavaScript bridge непосредственно в page world.

Концептуально:

```text
Extension
   │
   ▼
Content Script
   │
   │ inject
   ▼
MAIN world bridge
   │
   ▼
Page runtime
```

Например, page bridge может устанавливать:

```javascript
window.__MY_EXTENSION_BRIDGE__ = {
    version: 1
};
```

Однако такой глобальный объект должен использоваться очень осторожно.

---

# Почему глобальный объект опасен

Page JavaScript может:

```javascript
window.__MY_EXTENSION_BRIDGE__.send = ...
```

изменить его.

Или:

```javascript
delete window.__MY_EXTENSION_BRIDGE__;
```

Поэтому нельзя считать объект в `window` доверенным.

---

# Bridge должен быть минимальным

Хорошая архитектура:

```text
MAIN world bridge
        │
        ├── receive command
        ├── validate
        ├── execute narrow operation
        └── return result
```

Плохая архитектура:

```text
MAIN world
    │
    └── entire extension application
```

---

# Пример bridge

Page-world code:

```javascript
window.addEventListener(
    "message",
    event => {

        if (
            event.source !== window
        ) {
            return;
        }

        const message =
            event.data;

        if (
            !message ||
            message.source !==
                "my-extension"
        ) {
            return;
        }

        if (
            message.type ===
            "GET_TITLE"
        ) {

            window.postMessage(
                {
                    source:
                        "my-extension",
                    type:
                        "GET_TITLE_RESULT",
                    requestId:
                        message.requestId,
                    payload: {
                        title:
                            document.title
                    }
                },
                window.location.origin
            );
        }
    }
);
```

Content Script может отправить:

```javascript
window.postMessage(
    {
        source: "my-extension",
        version: 1,
        type: "GET_TITLE",
        requestId: crypto.randomUUID()
    },
    window.location.origin
);
```

---

# Bridge не должен доверять request

Даже если сообщение выглядит так:

```javascript
{
    source: "my-extension",
    type: "GET_TITLE"
}
```

это ещё не означает, что оно действительно пришло от extension.

Любой page script может попытаться создать аналогичный объект.

Поэтому bridge должен быть спроектирован так, чтобы поддельное сообщение не приводило к опасной операции.

---

# Capability-based design

Особенно полезен принцип:

> **Bridge должен предоставлять минимальный набор capabilities.**

Например:

```text
GET_PAGE_TITLE
GET_PRODUCT_DATA
REQUEST_ANALYSIS
```

а не:

```text
EXECUTE_ARBITRARY_CODE
```

или:

```text
CALL_ANY_FUNCTION
```

---

# Плохой bridge

Например:

```javascript
window.postMessage({
    type: "execute",
    code: "..."
});
```

А bridge делает:

```javascript
eval(message.code);
```

Это полностью разрушает security model.

---

# Хороший bridge

Вместо этого:

```javascript
switch (
    message.type
) {

    case "GET_TITLE":
        return getTitle();

    case "GET_PRODUCT":
        return getProduct();

    default:
        return error();
}
```

Это **explicit capability model**.

---

# Request/Response protocol

Хороший bridge может поддерживать request ID:

```javascript
{
    source: "my-extension",
    version: 1,
    type: "GET_PRODUCT",
    requestId: "9d8...",
    payload: {
        id: "123"
    }
}
```

Ответ:

```javascript
{
    source: "my-extension",
    version: 1,
    type: "GET_PRODUCT_RESULT",
    requestId: "9d8...",
    payload: {
        id: "123",
        title: "Book"
    }
}
```

`requestId` позволяет сопоставить:

```text
request
   │
   ▼
response
```

---

# Error protocol

Не следует возвращать ошибки в произвольном формате.

Например:

```javascript
{
    source: "my-extension",
    version: 1,
    type: "ERROR",
    requestId: "9d8...",
    error: {
        code: "PRODUCT_NOT_FOUND",
        message: "Product was not found"
    }
}
```

Лучше использовать стабильные error codes:

```text
INVALID_MESSAGE
UNSUPPORTED_VERSION
UNKNOWN_COMMAND
INVALID_PAYLOAD
NOT_FOUND
INTERNAL_ERROR
```

---

# 33.6. Безопасный bridge protocol

Теперь можно сформулировать полноценную архитектуру.

```text
                PAGE
                  │
          window.postMessage()
                  │
                  ▼
          MAIN WORLD BRIDGE
                  │
          validate message
                  │
                  ▼
          CONTENT SCRIPT
                  │
      validate / normalize
                  │
                  ▼
          runtime.sendMessage()
                  │
                  ▼
          SERVICE WORKER
```

Каждый слой имеет собственную responsibility.

---

# Layer 1 — Page

Page может быть:

```text
untrusted
```

Поэтому данные от неё нельзя автоматически считать доверенными.

---

# Layer 2 — MAIN bridge

Bridge:

```text
receive
 ↓
validate
 ↓
normalize
 ↓
allow/deny
```

---

# Layer 3 — Content Script

Content Script находится в extension-controlled isolated environment.

Он может:

```text
validate again
translate protocol
call chrome APIs
communicate with Service Worker
```

---

# Layer 4 — Service Worker

Service Worker выполняет privileged operations:

```text
storage
network
tabs
alarms
extension state
other extension APIs
```

---

# Двойная validation

Иногда возникает вопрос:

> Если MAIN bridge уже проверяет сообщение, зачем проверять его ещё раз в Content Script?

Потому что trust boundaries независимы.

Правильная модель:

```text
Page
 ↓
validate
 ↓
MAIN
 ↓
validate
 ↓
Content Script
 ↓
validate
 ↓
Service Worker
```

Каждый boundary должен защищать сам себя.

---

# Никогда не передавайте произвольные функции

Плохая идея:

```javascript
{
    type: "CALL",
    functionName: "...",
    args: [...]
}
```

если затем bridge динамически разрешает:

```javascript
window[functionName](...args);
```

Это превращает bridge в произвольный RPC механизм.

Лучше иметь whitelist:

```javascript
const handlers = {
    GET_TITLE: getTitle,
    GET_PRODUCT: getProduct,
    GET_SELECTION: getSelection
};
```

---

# Versioning

Bridge — это API.

Поэтому ему нужен versioning.

Например:

```javascript
{
    source: "my-extension",
    version: 1,
    type: "GET_PRODUCT"
}
```

В будущем:

```javascript
{
    source: "my-extension",
    version: 2,
    type: "GET_PRODUCT"
}
```

Это позволяет менять protocol без мгновенной поломки всех участников.

---

# Schema validation

Для сложного bridge полезно использовать schema validation.

Например, концептуально:

```text
Message
 ├── source: string
 ├── version: number
 ├── type: enum
 ├── requestId: string
 └── payload: object
```

Можно реализовать собственный validator или использовать TypeScript + runtime schema validation library.

Важно понимать:

> TypeScript types исчезают после компиляции.

Поэтому TypeScript:

```typescript
interface Message {
    type: string;
}
```

не защищает runtime от произвольного `postMessage()`.

Runtime validation всё равно необходима.

---

# Origin validation

При обработке `message` желательно проверять:

```javascript
if (
    event.source !== window
) {
    return;
}
```

и:

```javascript
if (
    event.origin !==
    window.location.origin
) {
    return;
}
```

Но эти проверки не заменяют schema validation.

---

# Не путайте origin и extension ID

Это разные понятия.

Например:

```text
Page origin:
https://example.com
```

и:

```text
Extension origin:
chrome-extension://<extension-id>
```

Bridge между page и extension не должен предполагать, что page может быть trusted просто потому, что она имеет ожидаемый origin.

---

# Nonce

Для некоторых bridge architectures можно использовать session nonce.

Например:

```javascript
const nonce =
    crypto.randomUUID();
```

Bridge получает:

```text
session nonce
```

и требует его в каждом сообщении:

```javascript
{
    source: "my-extension",
    version: 1,
    nonce: "...",
    type: "GET_PRODUCT"
}
```

Это не делает DOM communication секретной, но позволяет усложнить простую подделку сообщений и связывать сообщения с конкретной bridge session.

При этом nonce не должен рассматриваться как универсальная authentication mechanism против полностью контролируемого page environment.

---

# 33.7. Типичные ошибки

Теперь рассмотрим наиболее распространённые ошибки.

---

## Ошибка 1. Считать `window` общим объектом

Неверная модель:

```text
Page window
=
Content Script window
```

Правильная:

```text
Page JavaScript environment
        │
        │ shared DOM
        │
Content Script isolated world
```

---

## Ошибка 2. Передавать секреты через `postMessage`

Например:

```javascript
window.postMessage({
    token: SECRET
}, "*");
```

Так делать нельзя.

---

## Ошибка 3. Использовать `*` без необходимости

Плохо:

```javascript
window.postMessage(
    message,
    "*"
);
```

Лучше указывать ожидаемый origin там, где это возможно.

---

## Ошибка 4. Не проверять `event.origin`

Плохо:

```javascript
window.addEventListener(
    "message",
    handleMessage
);
```

Лучше:

```javascript
window.addEventListener(
    "message",
    event => {

        if (
            event.origin !==
            window.location.origin
        ) {
            return;
        }

        handleMessage(
            event.data
        );
    }
);
```

---

## Ошибка 5. Доверять `event.data`

Нельзя считать:

```javascript
event.data
```

валидным только потому, что он имеет:

```javascript
source: "my-extension"
```

Любой page script может попытаться создать такой объект.

---

## Ошибка 6. Делать bridge универсальным RPC

Опасная модель:

```text
Page
 ↓
CALL(function, args)
 ↓
Extension
 ↓
execute arbitrary function
```

Bridge должен предоставлять ограниченный API.

---

## Ошибка 7. Помещать всю extension logic в MAIN world

MAIN world должен содержать только минимально необходимый page-facing code.

Основная логика должна оставаться в:

```text
Content Script
Service Worker
Extension Pages
```

где это возможно.

---

## Ошибка 8. Использовать DOM как secret channel

Например:

```javascript
element.dataset.secret =
    token;
```

DOM не является приватным каналом.

---

## Ошибка 9. Использовать `innerHTML` для bridge data

Плохо:

```javascript
container.innerHTML =
    message.payload.html;
```

Если данные контролируются page, это может привести к XSS.

---

## Ошибка 10. Не учитывать page tampering

В MAIN world страница может изменять глобальные объекты:

```javascript
window.fetch = ...
window.postMessage = ...
```

и другие API.

Поэтому MAIN-world integration должна быть минимальной и осторожной.

---

# Рекомендуемая архитектура

Для production extension хороший общий шаблон выглядит следующим образом:

```text
                       WEB PAGE
                           │
                  Page JavaScript
                           │
                           │
                  ┌────────▼────────┐
                  │  MAIN Bridge    │
                  │                 │
                  │ validate        │
                  │ normalize       │
                  │ narrow API      │
                  └────────┬────────┘
                           │
                     postMessage
                           │
                           ▼
                  CONTENT SCRIPT
                           │
                  ┌────────┴────────┐
                  │                 │
              DOM work          Validation
                  │                 │
                  └────────┬────────┘
                           │
                  runtime.sendMessage()
                           │
                           ▼
                    SERVICE WORKER
                           │
              ┌────────────┼────────────┐
              │            │            │
           Storage        Tabs       Network
```

Здесь каждый уровень выполняет свою задачу.

# Когда bridge действительно нужен

Не следует создавать bridge только потому, что это технически возможно.

Во многих случаях Content Script уже может решить задачу:

```text
DOM
MutationObserver
events
dataset
attributes
text
forms
```

Если этого достаточно:

> **Bridge не нужен.**

Bridge нужен тогда, когда требуется взаимодействие именно с page JavaScript environment.

Например:

```text
Page global API
        ↓
JavaScript object
        ↓
library runtime
        ↓
application-level event
        ↓
interception of page API
```

---

# Простая матрица выбора

| Задача                            | Подход                             |
| --------------------------------- | ---------------------------------- |
| Прочитать DOM                     | Content Script                     |
| Изменить DOM                      | Content Script                     |
| Наблюдать DOM                     | MutationObserver                   |
| Обработать click                  | Content Script                     |
| Получить данные через `data-*`    | Content Script                     |
| Взаимодействовать с page JS       | Bridge                             |
| Передать событие page ↔ extension | `postMessage` / CustomEvent        |
| Вызвать page-level API            | MAIN world                         |
| Использовать `chrome.*` APIs      | Content Script / Extension context |
| Privileged operation              | Service Worker                     |
| Передать секрет page              | **Не делать**                      |

# Итоговая модель доверия

Самая важная идея главы:

```text
             TRUST BOUNDARY

        PAGE = UNTRUSTED
                │
                ▼
        MAIN WORLD BRIDGE
                │
         validate data
                │
                ▼
        CONTENT SCRIPT
                │
         validate again
                │
                ▼
        EXTENSION CORE
                │
                ▼
        SERVICE WORKER
```

Page должна рассматриваться как внешняя среда.

Даже если:

```text
это известный сайт
```

и даже если:

```text
мы сами установили bridge
```

это не означает, что page JavaScript становится trusted extension code.

# Главные принципы Page ↔ Extension Bridge

Можно свести всю главу к десяти правилам.

### 1. Изоляция — фундамент

Page JavaScript и Content Script находятся в разных JavaScript worlds.

### 2. DOM — общая поверхность

DOM является удобной точкой интеграции, но не приватным каналом.

### 3. `postMessage()` — коммуникационный механизм

Он позволяет организовать явный page ↔ extension protocol.

### 4. `MAIN world` — специальный инструмент

Используйте его только тогда, когда действительно необходимо взаимодействовать с page JavaScript.

### 5. Page — недоверенная сторона

Никогда автоматически не доверяйте сообщениям от страницы.

### 6. Protocol должен быть explicit

Используйте:

```text
source
version
type
requestId
payload
```

### 7. Валидируйте сообщения

Проверяйте:

```text
origin
source
schema
command
payload
```

### 8. Используйте capability-based design

Предоставляйте конкретные операции:

```text
GET_TITLE
GET_PRODUCT
GET_SELECTION
```

а не:

```text
EXECUTE_CODE
CALL_ANY_FUNCTION
```

### 9. MAIN world должен быть минимальным

Чем меньше extension logic находится в page world, тем лучше.

### 10. Bridge — это API

У него должны быть:

```text
protocol
version
validation
errors
request IDs
lifecycle
security boundaries
```

# Заключение

Page ↔ Extension Bridge — это не просто способ «передать сообщение между двумя JavaScript-файлами».

Это **архитектурная граница между двумя различными trust domains**:

```text
┌─────────────────────────────┐
│         Web Page            │
│                             │
│   Page JavaScript           │
│   Application Runtime       │
│   Third-party libraries     │
└──────────────┬──────────────┘
               │
          Bridge Protocol
               │
┌──────────────▼──────────────┐
│        Extension            │
│                             │
│   Content Script            │
│        ↓                    │
│   Extension Core            │
│        ↓                    │
│   Service Worker            │
└─────────────────────────────┘
```

Поэтому хороший bridge должен быть:

**маленьким, явным, типизированным, валидируемым и capability-oriented.**

А основная архитектурная идея выглядит так:

```text
Page
 ↓
Minimal MAIN-world bridge
 ↓
Content Script
 ↓
Typed protocol
 ↓
Service Worker
 ↓
Extension capabilities
```

Такой подход позволяет получить мощную интеграцию с JavaScript-приложениями страниц, не разрушая при этом security model Manifest V3.
