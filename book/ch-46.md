# Глава 46. Project 6 — Keyboard-driven Extension

В предыдущих проектах мы постепенно построили несколько разных моделей расширений:

```text
Project 1
Hello Extension
        ↓
минимальный extension

Project 2
Page Modifier
        ↓
Content Script + DOM

Project 3
Background Extension
        ↓
Service Worker + Messaging

Project 4
Productivity Extension
        ↓
Popup + Content Script + Storage

Project 5
Side Panel Application
        ↓
Side Panel + Tabs + Messaging + State
```

Теперь мы построим extension другого типа:

> **Keyboard-driven Extension**

Главным интерфейсом пользователя здесь будет не Popup и не Side Panel, а **клавиатура**.

Пользователь нажимает:

```text
Ctrl + Shift + F
```

и расширение выполняет действие на текущей странице.

Например:

```text
Ctrl + Shift + F
        ↓
Service Worker
        ↓
Content Script
        ↓
Page
        ↓
Focus Mode
```

Это очень важная архитектурная модель.

Она показывает, что extension может вообще не иметь постоянного визуального интерфейса.

---

# 46.1. Цель проекта

Создадим расширение:

> **Keyboard Toolkit**

Оно будет выполнять несколько команд:

```text
Ctrl + Shift + F
    → Toggle Focus Mode

Ctrl + Shift + H
    → Highlight headings

Ctrl + Shift + R
    → Read page information

Ctrl + Shift + C
    → Clear modifications
```

Архитектура:

```text
Keyboard
    ↓
Commands API
    ↓
Service Worker
    ↓
Content Script
    ↓
DOM
```

Главный принцип:

> **Keyboard command является событием, а Service Worker — маршрутизатором этого события.**

---

# 46.2. Почему keyboard-driven extension

Большинство extensions проектируются вокруг:

```text
Toolbar
   ↓
Popup
   ↓
Button
```

Но для некоторых задач это лишний шаг.

Сравним.

### Mouse-driven

```text
User
 ↓
Move mouse
 ↓
Find toolbar icon
 ↓
Click icon
 ↓
Open popup
 ↓
Click button
 ↓
Action
```

### Keyboard-driven

```text
User
 ↓
Ctrl + Shift + F
 ↓
Action
```

Разница особенно заметна для пользователей, которые часто выполняют одну и ту же операцию.

```text
→ переключить режим чтения

Ctrl + Shift + H
→ показать headings

Ctrl + Shift + S

```

# 46.7. Command name

Название:

```text
toggle-focus
```

не является самим keyboard shortcut.

Это **идентификатор команды**.

То есть:

```text
toggle-focus
```

— внутреннее имя.

А:

```text
Ctrl+Shift+F
```

— пользовательское назначение клавиш.

Это важно разделять.

---

# 46.8. Suggested key

Например:

```json
"suggested_key": {
    "default": "Ctrl+Shift+F"
}
```

означает:

> Мы предлагаем браузеру использовать эту комбинацию.

Это не следует понимать как абсолютную гарантию.

На клавиатурные сочетания могут влиять:

* browser shortcuts;
* operating system;
* раскладка клавиатуры;
* другие extensions;
* пользовательские настройки.

---

# 46.10. Команды не являются DOM events

Это важный момент.

Команда:

```text
Ctrl + Shift + F
```

не проходит через:

```javascript
document.addEventListener(
    "keydown",
    ...
);
```

в Content Script.

Мы **не реализуем shortcuts через `keydown`**.

Вместо этого используется:

```javascript
chrome.commands
```

То есть браузер сам распознаёт command.

Архитектура:

```text
Keyboard
   ↓
Browser
   ↓
Commands API
   ↓
Service Worker
```

---

# 46.11. Почему это лучше, чем `keydown`

Можно было бы написать:

```javascript
document.addEventListener(
    "keydown",
    event => {

        if (
            event.ctrlKey &&
            event.shiftKey &&
            event.key === "F"
        ) {
            ...
        }
    }
);
```

Но это плохая архитектура для глобального extension shortcut.

Почему?

Потому что Content Script:

* должен быть загружен;
* должен существовать на странице;
* зависит от `matches`;
* работает только в доступных контекстах;
* должен самостоятельно обрабатывать keyboard events.

Commands API позволяет браузеру самому маршрутизировать shortcut.

# 46.30. Улучшение архитектуры

Видно, что код начинает повторяться:

```javascript
const tab =
    await getActiveTab();

if (...) {
    return;
}

await chrome.tabs.sendMessage(
    tab.id,
    ...
);
```

Это хороший момент для выделения abstraction.

Создадим:

```javascript
async function sendToActiveTab(
    message
) {

    const tab =
        await getActiveTab();

    if (
        !tab ||
        typeof tab.id !== "number"
    ) {
        return false;
    }

    try {

        await chrome.tabs.sendMessage(
            tab.id,
            message
        );

        return true;

    } catch (error) {

        console.warn(
            "Unable to send message",
            error
        );

        return false;
    }
}
```

# 46.34. Commands как события

Очень важно понять философию.

Мы не говорим:

```text
"клавиша F должна вызвать функцию X"
```

Мы говорим:

```text
"произошло событие toggle-focus"
```

То есть keyboard shortcut является только способом породить событие.

```text
Keyboard
   ↓
Command Event
   ↓
Application
```

В будущем это же событие можно запускать другим способом:

```text
Keyboard
   ↓
toggle-focus

Popup
   ↓
toggle-focus

Side Panel
   ↓
toggle-focus

Context Menu
   ↓
toggle-focus
```

А обработчик остаётся одним.

---

# 46.35. Это важный architectural pattern

Например:

```javascript
async function executeCommand(
    command
) {
    ...
}
```

не должен знать:

```text
клавиатура
Popup
Side Panel
Context Menu
```

Он знает только:

```text
command
```

Это separation of concerns.

---

# 46.36. Command как application protocol

Можно представить:

```text
"toggle-focus"
```

как application-level command.

Например:

```javascript
{
    type: "COMMAND",
    command: "toggle-focus"
}
```

Тогда:

```text
Input
  ↓
Command
  ↓
Handler
  ↓
Effect
```

Это приближает extension architecture к архитектуре обычного приложения.

---

# 46.37. Browser shortcuts

В реальном browser environment пользователь может обнаружить конфликт:

```text
Ctrl + Shift + F
```

уже используется браузером или другой системой.

Поэтому нельзя считать shortcut гарантированно доступным.

Пользователь может изменить shortcut через интерфейс управления расширениями браузера.

Следовательно:

> **Shortcut — это пользовательская конфигурация, а не жёстко зашитая часть application logic.**

---

# 46.38. Почему не стоит делать слишком много shortcuts

Можно зарегистрировать:

```text
Ctrl+Shift+A
Ctrl+Shift+B
Ctrl+Shift+C
Ctrl+Shift+D
...
```

Но это создаёт UX problem.

Пользователь не запомнит:

```text
20 shortcuts
```

Лучше иметь небольшой набор:

```text
5–8 core commands
```

а сложные действия вынести в:

* Popup;
* Side Panel;
* Command palette;
* Options.

---

# 46.39. Command naming

Хорошие имена:

```text
toggle-focus
highlight-headings
save-page
open-workspace
extract-content
```

Плохие:

```text
cmd1
action2
doSomething
foo
```

Имя должно описывать **операцию**, а не способ её запуска.

---

# 46.40. Keyboard-first UX

Keyboard-driven extension следует проектировать вокруг вопроса:

> Что пользователь хочет сделать?

а не:

> Какую кнопку мы ему покажем?

Например:

```text
User sees paragraph
        ↓
wants to focus
        ↓
Ctrl + Shift + F
```

Это гораздо ближе к command-oriented UX.

---

# 46.41. Command palette

Следующий уровень такого extension — command palette:

```text
┌──────────────────────────────┐
│ Search commands...           │
├──────────────────────────────┤
│ Toggle Focus            ⌘ F  │
│ Highlight headings      ⌘ H  │
│ Page information        ⌘ R  │
│ Clear page              ⌘ C  │
└──────────────────────────────┘
```

В таком случае:

```text
Keyboard
   ↓
Command Palette
   ↓
Command
   ↓
Service Worker
```

Commands API становится частью более общей command architecture.

# 46.42. Command-driven architecture

Можно построить:

```text
                    Inputs
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Keyboard      Popup     Side Panel
          │           │           │
          └───────────┼───────────┘
                      ▼
                Command Layer
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Navigation    Page       Storage
                      │
                      ▼
                 Content Script
```

Это уже масштабируемая архитектура.

---

# 46.43. Content Script не должен знать о клавиатуре

Очень важное правило:

`content.js` не должен знать:

```text
Ctrl
Shift
F
commands
shortcut
```

Он должен знать только:

```text
TOGGLE_FOCUS
HIGHLIGHT_HEADINGS
PAGE_INFO
CLEAR_PAGE
```

То есть:

```text
Keyboard
   ↓
Service Worker
   ↓
Semantic command
   ↓
Content Script
```

Это делает Content Script reusable.

---

# 46.44. Почему это полезно

Позже можно добавить:

```text
Popup button
```

и сделать:

```javascript
chrome.runtime.sendMessage({
    type: "EXECUTE_COMMAND",
    command: "toggle-focus"
});
```

Popup не должен напрямую знать:

```text
как менять DOM
```

Он только запускает command.

То же самое может делать Side Panel.

Например:

```text
Input
│
├── Keyboard
├── Popup
├── Side Panel
└── Context Menu
        │
        ▼
   Command Router
        │

        ├── highlight-headings
        ├── page-info
        └── clear-page
                 │
                 ▼
          Content Script
```

Теперь у нас появляется единый command bus.

# 46.46. Runtime state

В текущей реализации:

```javascript
let focusEnabled = false;
```

это state Content Script.

Но Content Script может быть уничтожен при navigation.

Поэтому:

```text
focusEnabled
```

не является надёжным persistent state.

Если мы хотим сохранять Focus Mode:

```text
tab 123 → ON
```

между lifecycle Content Script, нужно использовать:

```text
chrome.storage
```

или другой источник persistent state.

# 46.47. Keyboard extension с persistent state

Можно изменить архитектуру:

```text
Keyboard
   ↓
Command
   ↓
Service Worker
   ↓
Storage
   ↓
Content Script
```

Например:

```javascript
{
    focusTabs: {
        "123": true,
        "456": false
    }
}
```

Теперь состояние принадлежит application runtime, а не конкретному Content Script.

# 46.50. Ошибки выполнения команды

Что произойдёт, если пользователь нажмёт shortcut на:

```text
chrome://extensions
```

Content Script там может отсутствовать.

Поэтому:

```javascript
try {

    await chrome.tabs.sendMessage(
        tab.id,
        message
    );

} catch (error) {

    console.warn(
        "Command could not be executed:",
        error
    );
}
```

Нельзя считать отсутствие Content Script неожиданным исключением.

Это нормальный browser state.

---

# 46.51. Idempotency

Некоторые commands должны быть idempotent.

Например:

```text
clear-page
```

можно вызвать дважды:

```text
clear
clear
```

и результат должен оставаться одинаковым.

А вот:

```text
toggle-focus
```

не является idempotent:

```text
toggle
    → ON

toggle
    → OFF
```

Это важно учитывать при проектировании commands.

---

# 46.52. Лучше использовать `set`, чем `toggle`, когда возможно

Например:

```text
SET_FOCUS
enabled: true
```

лучше с точки зрения distributed architecture, чем:

```text
TOGGLE_FOCUS
```

Почему?

Потому что `TOGGLE` зависит от текущего состояния.

```text
state = ON
toggle → OFF
```

Если команда повторится:

```text
toggle → ON
```

Результат изменится.

А:

```javascript
{
    type: "SET_FOCUS",
    enabled: true
}
```

можно повторить несколько раз.

Результат останется:

```text
ON
```

Это важный принцип для надёжных event-driven систем.

---

# 46.53. Улучшенная команда

Вместо:

```javascript
{
    type:
        "TOGGLE_FOCUS"
}
```

можно использовать:

```javascript
{
    type:
        "SET_FOCUS",

    enabled:
        true
}
```

Но тогда Service Worker должен знать текущее состояние или получить его от Content Script.

---

# 46.54. Command result

В production application команда может возвращать:

```javascript
{
    success: true,
    command: "toggle-focus"
}
```

или:

```javascript
{
    success: false,
    error: "CONTENT_SCRIPT_UNAVAILABLE"
}
```

Это значительно лучше, чем просто игнорировать результат.

---

# 46.55. Типизированный command protocol

В TypeScript:

```typescript
type Command =
    | {
        type: "SET_FOCUS";
        enabled: boolean;
    }
    | {
        type: "HIGHLIGHT_HEADINGS";
    }
    | {
        type: "PAGE_INFO";
    }
    | {
        type: "CLEAR_PAGE";
    };
```

Теперь команда является частью formal protocol.

---

# 46.56. Event vs Command

Важно различать:

### Event

Что-то произошло:

```text
ACTIVE_TAB_CHANGED
```

### Command

Приложение должно что-то сделать:

```text
SET_FOCUS
```

То есть:

```text
Event
    ↓
describes what happened

Command
    ↓
describes what should happen
```

Это очень полезное разделение для больших extensions.

---

# 46.57. Наша архитектура после этого разделения

```text
Browser
   │
   ├── Command
   │      ↓
   │   Service Worker
   │      ↓
   │   Content Script
   │
   └── Event
          ↓
      Service Worker
          ↓
      Side Panel
```

Например:

```text

    ↓
COMMAND: toggle-focus
```

а:

```text
User switches tab
    ↓
EVENT: ACTIVE_TAB_CHANGED
```

# 46.60. Debugging

Если shortcut не работает, проверяем последовательно:

```text
1. Command существует?
        ↓
2. Shortcut назначен?
        ↓
3. Service Worker запущен?
        ↓
4. onCommand получил command?
        ↓
5. Active tab существует?
        ↓
6. Content Script загружен?
        ↓
7. Message отправлен?
        ↓
8. Content Script получил message?
        ↓
9. DOM изменился?
```

Это гораздо эффективнее, чем просто смотреть на страницу и думать:

> «Почему Ctrl+Shift+F ничего не делает?»

```text
                    User

               Ctrl+Shift+F
                     │

              ┌─────────────┐
              │   Browser   │

             │               │
```

---

# 46.62. Что делает каждый context

| Context        | Ответственность                |
| -------------- | ------------------------------ |
| Browser        | распознаёт shortcut            |
| Commands API   | создаёт command event          |
| Service Worker | маршрутизирует command         |
| Content Script | выполняет действие на странице |
| Page           | предоставляет DOM              |

Обратите внимание:

> **Ни один context не делает работу другого context.**

Это один из ключевых принципов MV3 architecture.

---

# 46.63. Почему Service Worker является правильным местом

Можно было бы отправлять keyboard events непосредственно в Content Script.

Но тогда:

```text
Content Script
```

становится одновременно:

```text
keyboard listener
DOM controller
command router
application logic
```

Это быстро превращается в монолит.

В нашей архитектуре:

```text
Service Worker
    ↓
command orchestration

Content Script
    ↓
page integration
```

Разделение намного чище.

---

# 46.64. Главный архитектурный принцип проекта

Keyboard-driven extension показывает следующую модель:

```text
Input
  ↓
Command
  ↓
Orchestrator
  ↓
Context-specific action
```

И это значительно более универсальная модель, чем:

```text
button
  ↓
callback
```

Потому что один command может иметь несколько источников.

# 46.66. Главный вывод

До этой главы мы в основном строили extensions вокруг UI:

```text
Popup
Side Panel
```

Теперь мы видим другую возможность:

```text
                Extension
                    │
             ┌──────┴──────┐
             │             │
           UI            Commands
             │             │
             ▼             ▼
          Runtime       Runtime
             │             │
             └──────┬──────┘
                    ▼
              Content Script
                    │
                    ▼
                   DOM
```

То есть extension вовсе не обязан начинаться с интерфейса.

Он может начинаться с **команд и событий**.

Именно поэтому keyboard-driven architecture особенно хорошо подходит для power-user extensions:

```text
Keyboard
   ↓
Commands
   ↓
Service Worker
   ↓
Content Scripts
   ↓
Web Platform
```

А если добавить к этой архитектуре Storage, Tabs, Side Panel и declarative APIs, то мы уже получаем фундамент для действительно сложного **browser-native application runtime**.
