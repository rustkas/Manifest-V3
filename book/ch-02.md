# Глава 2. Manifest V3

Manifest V3 — это современная модель описания браузерного расширения. Если обычное веб-приложение начинает свою жизнь с HTML-документа, то browser extension начинается с **`manifest.json`**.

Manifest определяет не только имя и версию расширения. Он описывает его **архитектуру, разрешения, точки входа, фоновые процессы, пользовательский интерфейс, скрипты и доступ к веб-страницам**.

Поэтому `manifest.json` следует воспринимать не как простой конфигурационный файл, а как **декларативное описание приложения для браузера**.

В этой главе мы разберём структуру Manifest V3 и постепенно построим минимальное расширение.

---

## 2.1. Что такое `manifest.json`

`manifest.json` — это специальный JSON-файл, расположенный в корне браузерного расширения.

Минимальный пример:

```json
{
  "manifest_version": 3,
  "name": "My First Extension",
  "version": "1.0.0"
}
```

Этого уже достаточно, чтобы браузер распознал каталог как extension.

Однако само по себе такое расширение практически ничего не делает. Чтобы добавить поведение, необходимо декларативно описать его возможности:

```json
{
  "manifest_version": 3,
  "name": "My First Extension",
  "version": "1.0.0",

  "permissions": [
    "storage"
  ],

  "action": {
    "default_popup": "popup.html"
  },

  "background": {
    "service_worker": "background.js"
  }
}
```

Здесь manifest сообщает браузеру:

* это Manifest V3 extension;
* расширение называется `My First Extension`;
* его версия — `1.0.0`;
* ему нужен доступ к Storage API;
* у него есть toolbar action;
* при нажатии action открывается `popup.html`;
* у расширения есть background service worker.

Таким образом, браузер получает представление об архитектуре приложения **до выполнения его JavaScript-кода**.

Это принципиальное отличие extension от обычного веб-приложения.

---

## 2.2. Структура Manifest V3

Manifest представляет собой JSON-объект.

В нём используются различные поля верхнего уровня:

```json
{
  "manifest_version": 3,

  "name": "...",
  "version": "...",
  "description": "...",

  "icons": {},

  "action": {},

  "background": {},

  "permissions": [],
  "host_permissions": [],

  "content_scripts": [],

  "options_page": "...",
  "options_ui": {},

  "side_panel": {},

  "commands": {},

  "web_accessible_resources": [],

  "content_security_policy": {}
}
```

Не все эти поля обязательны.

Фактически manifest состоит из нескольких концептуальных уровней.

### Identity

Определяет, **что это за extension**:

```text
name
version
description
icons
```

### Runtime

Определяет, **какой код браузер должен запускать**:

```text
background
content_scripts
action
side_panel
options_page
```

### Capabilities

Определяет, **что extension имеет право делать**:

```text
permissions
host_permissions
```

### Interaction

Определяет, **как пользователь взаимодействует с extension**:

```text
action
commands
side_panel
```

### Security

Определяет ограничения выполнения:

```text
content_security_policy
web_accessible_resources
```

Это полезная концептуальная модель:

```text
                    manifest.json
                         │
        ┌────────────────┼────────────────┐
        │                │                │
     Identity         Runtime        Capabilities
        │                │                │
 name/version       service worker    permissions
 description        content scripts   host permissions
 icons               popup
                     options
                     side panel
        │                │                │
        └────────────────┼────────────────┘
                         │
                      Browser
```

Manifest, таким образом, является своеобразным **контрактом между extension и браузером**.

---

# 2.3. Обязательные поля

Для Manifest V3 базово необходимы три поля:

```json
{
  "manifest_version": 3,
  "name": "My Extension",
  "version": "1.0.0"
}
```

### `manifest_version`

Определяет версию формата manifest.

Для современного extension:

```json
"manifest_version": 3
```

### `name`

Название расширения:

```json
"name": "Page Tools"
```

### `version`

Версия расширения:

```json
"version": "1.0.0"
```

Эти три поля образуют минимальную идентичность extension.

При этом **обязательность поля не означает наличие функциональности**.

Расширение с таким manifest будет корректным, но практически бесполезным:

```json
{
  "manifest_version": 3,
  "name": "Empty Extension",
  "version": "1.0"
}
```

В нём нет ни пользовательского интерфейса, ни background logic, ни content scripts.

---

# 2.4. Metadata расширения

Metadata — это информация, описывающая extension.

Основные поля:

```json
{
  "name": "Page Tools",
  "version": "1.0.0",
  "description": "Tools for working with web pages",
  "icons": {
    "16": "icons/16.png",
    "48": "icons/48.png",
    "128": "icons/128.png"
  }
}
```

Эти данные используются браузером и магазином расширений.

Важно понимать разницу между:

```text
manifest
```

и

```text
application configuration
```

Manifest не предназначен для хранения произвольных настроек приложения.

Например, не следует превращать его в:

```json
{
  "api_url": "...",
  "theme": "dark",
  "refresh_interval": 5000
}
```

Такие данные обычно должны находиться в runtime configuration или `chrome.storage`.

Manifest описывает **структуру и capabilities extension**, а не его изменяемое состояние.

---

# 2.5. `manifest_version`

Поле:

```json
"manifest_version": 3
```

говорит браузеру, какую модель extension API необходимо использовать.

Это не версия вашего приложения.

Например:

```json
{
  "manifest_version": 3,
  "name": "My Extension",
  "version": "4.7.2"
}
```

Здесь:

```text
manifest_version = 3
```

— версия формата manifest.

А:

```text
version = 4.7.2
```

— версия самого extension.

Это две совершенно разные вещи.

---

## Почему появилась Manifest V3?

Manifest V3 представляет собой переход от более старой архитектуры Manifest V2 к более ограниченной и управляемой модели.

Особенно важными стали:

* Service Worker вместо постоянного background page;
* более строгая модель permissions;
* переход к declarative APIs;
* ограничения на выполнение удалённого кода;
* более чёткое разделение execution contexts;
* более контролируемая модель сетевых запросов.

Главная архитектурная идея MV3:

> Браузер должен лучше контролировать то, когда, где и каким образом работает код расширения.

Поэтому Manifest V3 следует изучать не просто как новый набор полей JSON.

Это **изменение runtime-модели browser extensions**.

---

# 2.6. `name`, `version`, `description`

## `name`

Название расширения:

```json
"name": "Page Inspector"
```

Это имя отображается пользователю.

---

## `version`

Версия:

```json
"version": "1.0.0"
```

Обычно используется схема:

```text
MAJOR.MINOR.PATCH
```

Например:

```text
1.0.0
1.1.0
1.1.1
2.0.0
```

Однако версия extension имеет требования и ограничения, поэтому нельзя автоматически считать её полностью идентичной любой системе Semantic Versioning.

---

## `description`

Описание:

```json
"description": "Inspect and modify web pages"
```

Оно используется для представления extension пользователю и в интерфейсах распространения.

Хорошее описание отвечает на простой вопрос:

> Зачем пользователю устанавливать это расширение?

Например:

```json
"description": "Quickly extract structured data from web pages"
```

лучше, чем:

```json
"description": "A browser extension"
```

---

# 2.7. `icons`

Extension может иметь несколько иконок:

```json
"icons": {
  "16": "icons/icon16.png",
  "32": "icons/icon32.png",
  "48": "icons/icon48.png",
  "128": "icons/icon128.png"
}
```

Размер указывается в пикселях.

Например:

```text
16 → 16×16
32 → 32×32
48 → 48×48
128 → 128×128
```

Структура проекта:

```text
my-extension/
│
├── manifest.json
│
├── icons/
│   ├── icon16.png
│   ├── icon32.png
│   ├── icon48.png
│   └── icon128.png
│
└── ...
```

Иконки используются в разных интерфейсах браузера и магазина.

Важно не путать:

```json
"icons"
```

с иконкой конкретного toolbar action.

Action также может иметь собственную конфигурацию.

---

# 2.8. `action`

`action` определяет основную пользовательскую точку входа extension через интерфейс браузера.

Простейший вариант:

```json
"action": {}
```

Можно определить popup:

```json
"action": {
  "default_popup": "popup.html"
}
```

Теперь структура:

```text
extension/
├── manifest.json
└── popup.html
```

При нажатии на кнопку extension браузер откроет:

```text
popup.html
```

Можно также определить tooltip:

```json
"action": {
  "default_title": "Page Tools",
  "default_popup": "popup.html"
}
```

Здесь:

```text
default_title
```

— текст, который браузер может показывать пользователю как название/подсказку action.

Action может также использовать badge:

```text
┌─────────────────────┐
│       Browser       │
│                     │
│             [EXT]   │
└─────────────────────┘
```

Badge позволяет показывать небольшое текстовое состояние на иконке extension.

Например:

```text
3
```

может означать количество найденных элементов.

Важно понимать архитектурную границу:

```text
Action
  │
  ├── toolbar button
  ├── popup
  └── badge
```

Action — это **точка пользовательского входа**, а не background runtime.

---

# 2.9. `background`

В Manifest V3 background logic реализуется через Service Worker.

Пример:

```json
"background": {
  "service_worker": "background.js"
}
```

Структура:

```text
extension/
├── manifest.json
├── background.js
└── popup.html
```

`background.js` не является постоянно работающим процессом.

Это принципиально важно.

В старых моделях extension background code мог существовать как постоянно работающая страница.

В MV3 background Service Worker запускается браузером в ответ на события и может быть остановлен, когда больше не нужен.

Поэтому архитектура должна быть:

```text
Event
  ↓
Service Worker starts
  ↓
Handle event
  ↓
Persist necessary state
  ↓
Worker may stop
```

А не:

```text
Start application
        ↓
Infinite background process
        ↓
Keep state in memory forever
```

Это одно из наиболее важных изменений Manifest V3.

---

# 2.10. `permissions`

`permissions` определяет дополнительные API и возможности, которыми extension хочет пользоваться.

Например:

```json
"permissions": [
  "storage"
]
```

Теперь extension может использовать Storage API.

Другой пример:

```json
"permissions": [
  "storage",
  "tabs",
  "alarms"
]
```

Каждое permission должно быть обосновано.

Не следует автоматически запрашивать всё:

```json
"permissions": [
  "tabs",
  "storage",
  "history",
  "bookmarks",
  "downloads",
  "cookies"
]
```

если приложению это не требуется.

Чем больше permissions, тем:

* больше возможностей extension;
* больше потенциальная поверхность атаки;
* больше доверия требуется от пользователя;
* сложнее пройти review в магазине.

Поэтому важнейший принцип:

> Request only the capabilities your extension actually needs.

Этот принцип будет постоянно повторяться при изучении Manifest V3.

---

# 2.11. `host_permissions`

`permissions` и `host_permissions` решают разные задачи.

Например:

```json
"permissions": [
  "storage"
]
```

означает:

> Extension хочет использовать Storage API.

А:

```json
"host_permissions": [
  "https://example.com/*"
]
```

означает:

> Extension запрашивает доступ к страницам данного host pattern.

Например:

```json
"host_permissions": [
  "https://*.example.com/*"
]
```

даёт соответствующий host access для страниц, подходящих под этот pattern.

Можно указать несколько:

```json
"host_permissions": [
  "https://example.com/*",
  "https://*.example.org/*"
]
```

Очень важно различать:

```text
API permission
        ↓
что extension может делать

Host permission
        ↓
с какими web origins extension может взаимодействовать
```

Это две разные оси security model.

---

# 2.12. `content_scripts`

Content scripts позволяют выполнять JavaScript и CSS непосредственно в контексте веб-страниц.

Например:

```json
"content_scripts": [
  {
    "matches": [
      "https://example.com/*"
    ],
    "js": [
      "content.js"
    ]
  }
]
```

Теперь браузер автоматически загрузит:

```text
content.js
```

на страницы, соответствующие:

```text
https://example.com/*
```

Можно добавить CSS:

```json
"content_scripts": [
  {
    "matches": [
      "https://example.com/*"
    ],
    "js": [
      "content.js"
    ],
    "css": [
      "content.css"
    ]
  }
]
```

Также можно управлять моментом инъекции:

```json
"run_at": "document_idle"
```

Например:

```json
"content_scripts": [
  {
    "matches": [
      "https://example.com/*"
    ],
    "js": [
      "content.js"
    ],
    "run_at": "document_idle"
  }
]
```

Content Script — одна из важнейших концепций extensions.

Он работает **не как обычный script веб-страницы**.

У него есть собственный execution environment — isolated world.

Поэтому архитектура выглядит примерно так:

```text
Web Page
   │
   │ DOM
   │
Content Script
   │
   │ messages
   ▼
Service Worker
```

Позже мы подробно разберём эту модель.

---

# 2.13. `options_page` и `options_ui`

Extension может иметь страницу настроек.

Самый простой вариант:

```json
"options_page": "options.html"
```

Например:

```text
extension/
├── manifest.json
├── options.html
└── options.js
```

Пользователь может открыть страницу настроек extension через интерфейс браузера.

Современный вариант:

```json
"options_ui": {
  "page": "options.html",
  "open_in_tab": true
}
```

`open_in_tab` определяет, должна ли страница настроек открываться как отдельная вкладка.

Options page обычно отвечает за:

```text
User Settings
      ↓
Storage
      ↓
Service Worker / Content Scripts / UI
```

Например:

```text
options.html
    │
    ▼
chrome.storage
    │
    ├── Service Worker
    ├── Popup
    └── Content Script
```

Это хороший пример того, почему extension нельзя рассматривать как одну HTML-страницу.

У него может существовать несколько независимых UI contexts, работающих с общим persistent state.

---

# 2.14. `side_panel`

Side Panel позволяет extension создавать интерфейс в боковой панели браузера.

Пример:

```json
"side_panel": {
  "default_path": "sidepanel.html"
}
```

Структура:

```text
extension/
├── manifest.json
├── sidepanel.html
└── sidepanel.js
```

Side Panel особенно интересен для приложений, которым требуется **длительно существующий UI**.

Например:

```text
┌──────────────────────────────┬───────────────┐
│                              │               │
│          Web Page            │  Extension    │
│                              │  Side Panel   │
│                              │               │
│                              │               │
│                              │               │
└──────────────────────────────┴───────────────┘
```

В отличие от popup, который обычно закрывается после потери фокуса, Side Panel может оставаться доступным во время работы пользователя с веб-страницей.

Это делает его особенно интересным для:

* productivity tools;
* research assistants;
* developer tools;
* data extraction;
* AI assistants;
* CRM extensions;
* document tools.

---

# 2.15. `commands`

`commands` позволяет определить keyboard shortcuts.

Например:

```json
"commands": {
  "open-panel": {
    "suggested_key": {
      "default": "Ctrl+Shift+Y"
    },
    "description": "Open extension panel"
  }
}
```

Теперь у extension появляется команда:

```text
Ctrl + Shift + Y
```

Её обработка выполняется в extension runtime.

Например, Service Worker может слушать:

```javascript
chrome.commands.onCommand.addListener((command) => {
  if (command === "open-panel") {
    // ...
  }
});
```

Commands особенно полезны для extensions, которые должны позволять пользователю быстро выполнять действия без мыши.

---

# 2.16. `web_accessible_resources`

По умолчанию ресурсы extension не являются свободно доступными веб-страницам.

Если необходимо разрешить странице загружать определённые ресурсы extension, используется:

```json
"web_accessible_resources": [
  {
    "resources": [
      "images/logo.png"
    ],
    "matches": [
      "https://example.com/*"
    ]
  }
]
```

Здесь:

```text
resources
```

определяет, какие файлы разрешено сделать доступными.

А:

```text
matches
```

определяет, с каких страниц они могут быть доступны.

Это важная security boundary.

Не следует делать все файлы extension доступными всем сайтам без необходимости.

Например, плохая идея:

```text
все ресурсы
    ↓
все сайты
```

Лучше:

```text
конкретный ресурс
       ↓
конкретные origins
```

Это снова реализация принципа Least Privilege.

---

# 2.17. `content_security_policy`

Manifest V3 также позволяет определить Content Security Policy для extension.

Например:

```json
"content_security_policy": {
  "extension_pages": "script-src 'self'; object-src 'self'"
}
```

CSP ограничивает способы выполнения и загрузки кода.

Одна из важнейших идей MV3 заключается в том, что extension не должен произвольно загружать и исполнять удалённый JavaScript.

Например, архитектура вида:

```javascript
fetch("https://example.com/code.js")
```

а затем выполнение полученного кода как extension code — именно тот тип архитектуры, который MV3 стремится ограничить.

Вместо этого код extension должен входить в контролируемый build/deployment pipeline.

Условно:

```text
Source Code
    ↓
Build
    ↓
Extension Package
    ↓
Browser
```

а не:

```text
Extension
    ↓
Download arbitrary code
    ↓
Execute downloaded code
```

Это имеет большое значение для безопасности.

# 2.18. Полный минимальный Manifest V3

Теперь объединим основные элементы.

Рассмотрим небольшое extension:

```text
my-extension/
│
├── manifest.json
│
├── background.js
│
├── content.js
│
├── popup.html
│
├── popup.js
│
├── options.html
│
├── options.js
│
├── sidepanel.html
│
├── sidepanel.js
│
└── icons/
    ├── icon16.png
    ├── icon48.png
    └── icon128.png
```

Manifest:

```json
{
  "manifest_version": 3,

  "name": "Page Tools",
  "version": "1.0.0",
  "description": "A modern Manifest V3 browser extension.",

  "icons": {
    "16": "icons/icon16.png",
    "48": "icons/icon48.png",
```

Это уже довольно богатая архитектура.

Её можно представить следующим образом:

```text
                         Browser
                            │
                     manifest.json
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
      UI                  Runtime          Permissions
        │                   │                   │
   ┌────┼────┐              │              ┌────┴────┐
   │    │    │              │              │         │
Popup Options Side Panel  Service       API       Hosts
                           Worker      permissions permissions
                              │
                              │
                         Content Script
                              │
                              ▼
                          Web Page
```

Именно здесь становится видна главная архитектурная особенность Manifest V3:

**extension — это не один JavaScript application runtime.**

Это набор различных execution contexts, которыми браузер управляет независимо:

```text
                    Extension
                        │
        ┌───────────────┼───────────────┐
        │               │               │
      Popup          Side Panel       Options
        │               │               │
        └───────────────┼───────────────┘
                        │
                  Message Passing
                        │
                        ▼
                 Service Worker
                        │
                        │
                 Message Passing
                        │
                        ▼
                 Content Script
                        │
                        ▼
                    Web Page
```

Именно поэтому при изучении Manifest V3 недостаточно запоминать поля `manifest.json`.

Нужно понимать **архитектурные отношения между ними**.

# Итог главы

После этой главы следует уже уметь читать Manifest V3 как архитектурную схему.

Например:

```json
{
  "manifest_version": 3,
  "name": "Example",
  "version": "1.0.0",

  "permissions": [
    "storage"
  ],

  "host_permissions": [
    "https://example.com/*"
  ],

  "background": {
    "service_worker": "background.js"
  },

  "content_scripts": [
    {
      "matches": ["https://example.com/*"],
      "js": ["content.js"]
    }
  ],

  "action": {
    "default_popup": "popup.html"
  }
}
```

должен читаться не как набор JSON-полей, а примерно так:

> **У extension есть toolbar UI, background Service Worker, Content Script, доступ к Storage и разрешение работать с определённым web origin.**

Это гораздо более важный уровень понимания.

В дальнейшем мы будем постоянно возвращаться к этой модели:

```text
                MANIFEST V3
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   Capabilities    Contexts      UI
        │            │            │
 permissions    Service Worker   Action
 host access    Content Script   Popup
                Extension Pages  Side Panel
                                 Options
                     │
                     ▼
                Communication
                     │
                     ▼
                   State
                     │
                     ▼
                  Storage
```

Именно эта схема станет фундаментом для следующих глав — прежде всего для изучения **permissions, execution contexts, Content Scripts, Service Worker и message passing**.
