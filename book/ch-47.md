# Глава 47. Project 7 — Network Extension

В предыдущем проекте мы построили **keyboard-driven extension**, где основной механизм управления был событийным:

```text
Keyboard
    ↓
Commands
    ↓
Service Worker
    ↓
Content Script
    ↓
DOM
```

В этой главе мы переходим к другой фундаментальной возможности Manifest V3:

> **управлению сетевыми запросами через Declarative Net Request (DNR).**

Здесь архитектура будет принципиально другой.

Вместо:

```text
JavaScript
    ↓
перехват request
    ↓
решение
    ↓
action
```

мы будем использовать:

```text
Rules
    ↓
Browser engine
    ↓
Request matching
    ↓
Action
```

Это один из самых важных архитектурных переходов Manifest V3.

---

# 47.1. Цель проекта

Создадим небольшое расширение:

> **Network Guard**

Его задача — демонстрировать обработку сетевых запросов через `declarativeNetRequest`.

Расширение будет:

1. блокировать определённые URL;
2. перенаправлять определённые запросы;
3. изменять HTTP headers;
4. использовать static ruleset;
5. использовать dynamic rules;
6. включать и выключать ruleset;
7. показывать архитектуру DNR;
8. использовать минимальное количество JavaScript.

Итоговая архитектура:

```text
                    Browser
                       │
                 Network Request
                       │
                       ▼
              ┌─────────────────┐
              │      DNR        │
              │                 │
              │ Rules Engine    │
              └────────┬────────┘
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
          Block     Redirect   Headers
```

---

# 47.2. Почему это отдельный тип extension

Обычное extension может работать так:

```text
Page
 ↓
Content Script
 ↓
Service Worker
 ↓
API
```

Network extension работает иначе:

```text
Network
    ↓
Browser
    ↓
DNR
    ↓
Rules
```

JavaScript Service Worker может вообще не участвовать в обработке каждого запроса.

Это фундаментальная идея:

> **Browser engine выполняет декларативные правила вместо JavaScript-кода extension.**

---

# 47.3. Пример задачи

Предположим, мы хотим блокировать:

```text
https://example.com/tracker.js
```

Императивная модель выглядела бы концептуально так:

```text
Request
   ↓
JavaScript
   ↓
if URL matches
   ↓
block
```

DNR позволяет описать:

```text
если URL соответствует условию
→ применить action block
```

То есть мы описываем **что должно произойти**, а не пишем алгоритм обработки каждого request.

# 47.5. Manifest

Начнём с:

```json
{
    "manifest_version": 3,

    "name": "Network Guard",

    "version": "1.0.0",

    "description":
        "A declarative network filtering extension.",

    "permissions": [
        "declarativeNetRequest"
    ],

    "host_permissions": [
        "<all_urls>"
    ],

    "declarative_net_request": {
        "rule_resources": [
            {
                "id": "main_rules",
                "enabled": true,
                "path": "rules/rules.json"
            }
        ]
    }
}
```

Обратите внимание:

```json
"declarative_net_request"
```

описывает rulesets extension.

---

# 47.6. Что такое ruleset

Ruleset — это набор правил:

```text
Ruleset
    │
    ├── Rule 1
    ├── Rule 2
    ├── Rule 3
    ├── Rule 4
    └── ...
```

В нашем проекте:

```text
rules/rules.json
```

будет содержать эти правила.

---

# 47.7. Первое правило

Создадим:

```json
[
    {
        "id": 1,

        "priority": 1,

        "action": {
            "type": "block"
        },

        "condition": {
            "urlFilter": "tracker.example.com",
            "resourceTypes": [
                "script"
            ]
        }
    }
]
```

Теперь разберём его.

---

# 47.8. `id`

```json
"id": 1
```

Каждое правило должно иметь уникальный идентификатор в пределах ruleset.

Например:

```text
1
2
3
4
...
```

Нельзя создавать два правила:

```json
{
    "id": 1
}
```

и:

```json
{
    "id": 1
}
```

в одном ruleset.

---

# 47.9. `priority`

```json
"priority": 1
```

Priority определяет относительный приоритет правил.

Например:

```text
Rule A
priority = 1

Rule B
priority = 10
```

Правило с большей priority имеет более высокий приоритет при обработке конфликтующих действий.

Это становится особенно важно, когда одновременно существуют:

```text
block
redirect
allow
modifyHeaders
```

---

# 47.10. `action`

В нашем случае:

```json
"action": {
    "type": "block"
}
```

означает:

> если условие правила совпало, заблокировать request.

Основные категории actions включают:

```text
block
redirect
allow
allowAllRequests
upgradeScheme
modifyHeaders
```

Конкретные допустимые варианты зависят от API и контекста правила.

---

# 47.11. `condition`

Условие:

```json
"condition": {
    "urlFilter":
        "tracker.example.com"
}
```

определяет, какие requests должны соответствовать правилу.

Мы можем дополнительно ограничить resource type:

```json
"resourceTypes": [
    "script"
]
```

Теперь правило применяется только к JavaScript requests.

---

# 47.12. Resource types

Сетевой запрос может быть связан с различными ресурсами:

```text
main_frame
sub_frame
script
stylesheet
image
font
object
xmlhttprequest
ping
media
websocket
other
```

Поэтому правило может быть очень конкретным.

Например:

```json
"resourceTypes": [
    "script"
]
```

означает:

> рассматриваем только requests типа script.

---

# 47.13. Первое практическое правило

Полный файл:

```json
[
    {
        "id": 1,
        "priority": 1,

        "action": {
            "type": "block"
        },

        "condition": {
            "urlFilter":
                "tracker.example.com",

            "resourceTypes": [
                "script"
            ]
        }
    }
]
```

Это уже полноценный declarative network rule.

---

# 47.14. Как происходит обработка

Предположим, страница содержит:

```html
<script src="https://tracker.example.com/script.js">
</script>
```

Browser выполняет:

```text
Request
   │
   ▼
DNR Rule Engine
   │
   ▼
urlFilter matches
   │
   ▼
resourceTypes = script
   │
   ▼
action = block
   │
   ▼
Request blocked
```

Extension JavaScript при этом не должен запускаться на каждый такой request.

---

# 47.15. Это и есть declarative architecture

Мы не написали:

```javascript
if (
    request.url.includes(
        "tracker.example.com"
    )
) {
    block();
}
```

Мы написали:

```json
{
    "condition": {
        "urlFilter":
            "tracker.example.com"
    },

    "action": {
        "type": "block"
    }
}
```

Это принципиально разные модели.

# 47.16. Добавляем несколько правил

Теперь:

```json
[
    {
        "id": 1,
        "priority": 1,

        "action": {
            "type": "block"
        },

        "condition": {
            "urlFilter":
                "tracker.example.com",

            "resourceTypes": [
                "script"
            ]
        }
    },

    {
        "id": 2,
        "priority": 1,

        "action": {
            "type": "block"
        },

        "condition": {
            "urlFilter":
                "ads.example.com",

            "resourceTypes": [
                "script",
                "image"
            ]
        }
    }
]
```

Теперь ruleset содержит две политики.

---

# 47.17. Ruleset как data

Обратите внимание на архитектуру.

`rules.json` — это не программа.

Это **данные, описывающие network policy**.

То есть:

```text
JavaScript
    ↓
program

rules.json
    ↓
policy
```

Это очень важное различие.

---

# 47.18. URL filtering

`urlFilter` позволяет задавать шаблон для сопоставления URL.

Например:

```json
"urlFilter":
    "analytics"
```

может соответствовать URL, содержащим этот фрагмент.

Но в production extension нельзя бездумно использовать слишком общие фильтры.

Например:

```json
"urlFilter":
    "ads"
```

может оказаться слишком широким.

---

# 47.19. Ограничение доменом

Лучше использовать дополнительные условия.

Например:

```json
"requestDomains": [
    "tracker.example.com"
]
```

В зависимости от задачи можно также ограничивать:

```text
initiatorDomains
requestDomains
excludedRequestDomains
excludedInitiatorDomains
```

Это позволяет сделать правила намного точнее.

---

# 47.20. Почему точность важна

Плохое правило:

```text
block everything containing "api"
```

может сломать:

```text
API calls
images
scripts
analytics
application functionality
```

Хорошее правило:

```text
specific domain
+
specific resource type
+
specific condition
```

обычно безопаснее.

---

Можно создать:

```json
{
    "id": 10,

    "priority": 1,

    "action": {
        "type": "block"
    },

    "condition": {
        "urlFilter":
            "ads.example.com",

        "resourceTypes": [

        ]
    }
}
```

Теперь блокируются изображения с указанного источника.

# 47.22. Redirect

DNR умеет не только блокировать.

Можно сделать redirect.

Например:

```json
{
    "id": 20,

    "priority": 1,

    "action": {
        "type": "redirect",
        "redirect": {
            "url":
                "https://example.com/"
        }
    },

    "condition": {
        "urlFilter":
            "old.example.com",

        "resourceTypes": [
            "main_frame"
        ]
    }
}
```

Теперь navigation может быть перенаправлена.

---

# 47.23. Redirect architecture

```text
Request
   ↓
Match
   ↓
redirect
   ↓
New URL
```

Это уже другой тип network transformation.

---

# 47.24. Upgrade Scheme

Ещё один полезный action:

```text
upgradeScheme
```

Он позволяет переводить HTTP requests на HTTPS там, где это применимо.

Концептуально:

```text
http://example.com
        ↓
https://example.com
```

Это пример декларативной security policy.

---

# 47.25. Modify Headers

DNR может работать и с HTTP headers.

Например:

```json
{
    "id": 30,

    "priority": 1,

    "action": {
        "type": "modifyHeaders",

        "requestHeaders": [
            {
                "header":
                    "X-Extension",

                "operation":
                    "set",

                "value":
                    "NetworkGuard"
            }
        ]
    },

    "condition": {
        "urlFilter":
            "api.example.com",

        "resourceTypes": [
            "xmlhttprequest"
        ]
    }
}
```

Теперь для соответствующих запросов можно модифицировать request headers с учётом ограничений DNR.

---

# 47.26. Почему `modifyHeaders` сложнее

Изменение headers потенциально влияет на:

* authentication;
* caching;
* CORS;
* application logic;
* security;
* server behavior.

Поэтому такие правила нужно проектировать особенно осторожно.

---

# 47.27. Static rules

Наш:

```text
rules/rules.json
```

— пример static ruleset.

Он поставляется вместе с extension.

Архитектура:

```text
Extension package
      │
      ├── manifest.json
      │
      └── rules.json
             │
             ▼
        Browser loads
             │
             ▼
         DNR engine
```

Это хорошо подходит для заранее известных политик.

Например:

```text
ad blocker
privacy filter
security policy
tracking protection
```

---

# 47.28. Dynamic rules

Иногда правила должны изменяться во время работы extension.

Для этого существуют dynamic rules.

Например:

```text
User blocks domain
       ↓
Extension
       ↓
Add DNR rule
```

В таком случае JavaScript используется не для обработки каждого network request, а для **изменения набора правил**.

Это важное различие.

---

# 47.29. Dynamic rule architecture

```text
User
 ↓
Extension UI
 ↓
Service Worker
 ↓
updateDynamicRules()
 ↓
Browser DNR engine
 ↓
Future requests
```

То есть JavaScript участвует в **configuration**, но не обязательно в **execution**.

---

# 47.30. Получение dynamic rules

Например:

```javascript
const rules =
    await chrome.declarativeNetRequest
        .getDynamicRules();

console.log(rules);
```

Это позволяет узнать текущее состояние dynamic rules.

---

# 47.31. Добавление dynamic rule

Концептуально:

```javascript
await chrome.declarativeNetRequest
    .updateDynamicRules({

        addRules: [
            {
                id: 1000,

                priority: 1,

                action: {
                    type: "block"
                },

                condition: {
                    urlFilter:
                        "tracker.example.com",

                    resourceTypes: [
                        "script"
                    ]
                }
            }
        ]
    });
```

Теперь правило хранится как dynamic rule.

---

# 47.32. Удаление dynamic rule

Например:

```javascript
await chrome.declarativeNetRequest
    .updateDynamicRules({

        removeRuleIds: [
            1000
        ]
    });
```

Важно:

```text
addRules
```

добавляет правила, а:

```text
removeRuleIds
```

удаляет правила по идентификаторам.

---

# 47.33. Почему нужны уникальные IDs

Допустим:

```text
1000 → user rule
1001 → user rule
1002 → user rule
```

Тогда extension может адресно управлять ими:

```text
remove 1001
```

не затрагивая остальные.

Поэтому в production architecture полезно резервировать диапазоны IDs.

Например:

```text
1–999
    static rules

1000–999999
    user dynamic rules
```

Конкретные диапазоны должны учитывать реальные ограничения платформы.

---

# 47.34. Static vs Dynamic

Сравним.

| Static                                      | Dynamic                                |
| ------------------------------------------- | -------------------------------------- |
| поставляется с extension                    | изменяется во время работы             |
| подходит для фиксированной политики         | подходит для пользовательских настроек |
| описан в manifest                           | управляется API                        |
| хорош для больших заранее известных наборов | хорош для персональных правил          |

Например:

```text
Static:
privacy filter

Dynamic:
user blocked domains
```

---

# 47.35. Session rules

Существуют также session-scoped rules.

Идея:

```text
Browser session
      ↓
temporary rules
      ↓
session ends
      ↓
rules disappear
```

Это полезно, когда правило не должно становиться постоянной настройкой.

Например:

```text
"Block this domain for this session."
```

---

# 47.36. Архитектура трёх уровней

В итоге можем получить:

```text
              DNR
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
   Static   Dynamic   Session
   Rules     Rules     Rules
```

Каждый уровень решает свою задачу.

---

# 47.37. Service Worker не является request loop

Это одно из главных различий между DNR и старой императивной моделью.

Не следует проектировать:

```text
Request
   ↓
Service Worker
   ↓
inspect
   ↓
decision
   ↓
action
```

для каждого сетевого запроса.

В declarative model:

```text
Rules
   ↓
DNR engine
   ↓
Request
   ↓
Match
   ↓
Action
```

Это и есть смысл переноса логики в browser engine.

---

# 47.38. Что делает Service Worker

В нашем проекте Service Worker может заниматься:

```text
settings
rule management
user commands
dynamic rules
telemetry
storage
```

Но не обязан быть посредником каждого request.

Например:

```text
User
 ↓
"Block this domain"
 ↓
Service Worker
 ↓
add dynamic rule
```

После этого:

```text
Requests
 ↓
DNR
```

работают без постоянного участия Service Worker.

---

# 47.39. Минимальный Service Worker

Если extension использует только static rules, Service Worker может вообще не понадобиться.

Это особенно интересно.

Минимальная архитектура:

```text
manifest.json
      +
rules.json
```

То есть:

```text
Extension
   ↓
DNR
   ↓
Browser
```

---

# 47.40. Это действительно "browser-native" architecture

В обычном application runtime:

```text
Application
   ↓
JavaScript
   ↓
Browser APIs
```

В declarative extension:

```text
Policy
   ↓
Browser engine
```

Часть application logic фактически становится частью browser-controlled execution.

# 47.43. Проверка ruleset

После загрузки extension необходимо убедиться, что manifest принят браузером.

Если ruleset содержит ошибку:

```text
invalid rule
invalid condition
invalid action
duplicate id
invalid resource type
```

браузер сообщит об ошибке extension.

Поэтому DNR rules должны проходить валидацию ещё до production deployment.

# 47.44. Как тестировать блокировку

Нужен тестовый URL, который соответствует нашему rule.

Например:

```text
https://tracker.example.com/script.js
```

Если такой request возникает на странице:

```text
Page
 ↓
Request
 ↓
DNR
 ↓
Rule 1
 ↓
BLOCK
```

---

# 47.45. Почему лучше использовать собственный тестовый server

Для реального обучения лучше создать controlled environment:

```text
test-page/
│
├── index.html
└── tracker.js
```

Например:

```html
<!doctype html>

<html>

<head>

    <title>
        DNR Test
    </title>

    <script src="/tracker.js">
    </script>

</head>

<body>

    <h1>DNR Test Page</h1>

</body>

</html>
```

А затем создать правила, соответствующие тестовым URL.

Так мы можем воспроизводимо проверять поведение extension.

---

# 47.46. Testing matrix

Нужно тестировать не только успешный блок.

Например:

| Request             | Expected        |
| ------------------- | --------------- |
| matching script     | BLOCK           |
| non-matching script | ALLOW           |
| matching image      | ALLOW           |
| matching XHR        | зависит от rule |
| unrelated domain    | ALLOW           |

Это превращает ruleset в тестируемую policy.

---

# 47.47. Rule debugging

Для network extension необходимо проверять:

```text
1. Rule loaded?
2. Rule valid?
3. URL matches?
4. Resource type matches?
5. Domain condition matches?
6. Priority correct?
7. Another rule overrides it?
8. Request is actually visible to DNR?
```

Последний пункт особенно важен.

Не каждый URL, который кажется "сетевым запросом" с точки зрения страницы, обязательно означает одинаковый тип DNR request.

# 47.49. Почему DNR хорошо подходит для ad blockers

Ad blocker имеет огромное количество правил:

```text

initiator
```

Если каждый request обрабатывать через JavaScript:

```text

 ↓
JS
 ↓
matching algorithm
 ↓
decision
```

это может быть дорого.

DNR позволяет браузеру выполнять matching внутри специализированного engine.

Архитектура:

```text
              Filter Lists
                   │
                   ▼
            Rule Generation
                   │
                   ▼
              DNR Rules
                   │
                   ▼
              Browser Engine
                   │
             ┌─────┴─────┐
             ▼           ▼
```

# 47.50. Rules как Intermediate Representation

Очень важная архитектурная идея:

```text
High-level policy
       ↓
Rule compiler
       ↓
DNR rules
       ↓
Browser engine
```

Например:

```text
"Block trackers from Domain X"
```

может быть представлено в application-level DSL:

```json
{
    "domain":
        "tracker.example.com",

    "types": [
        "script",
        "image"
    ],

    "action":
        "block"
}
```

А затем преобразовано в DNR rule:

```json
{
    "id": 100,
    "priority": 1,
    "action": {
        "type": "block"
    },
    "condition": {
        "requestDomains": [
            "tracker.example.com"
        ],
        "resourceTypes": [
            "script",
            "image"
        ]
    }
}
```

Это уже напоминает compiler pipeline.

# 47.53. Security advantage

Чем меньше extension может делать программно, тем меньше поверхность атаки.

# 47.54. Ограничения DNR

DNR не является универсальной заменой JavaScript.

Он не предназначен для:


DNR работает только в рамках поддерживаемой декларативной модели.

Если задача требует:

```text

        ↓

        ↓

```

скорее всего понадобится комбинация:

```text

+

```

# 47.63. От JavaScript runtime к Browser runtime

Сравним две модели.

### Imperative

```text
Request
   ↓
Service Worker
   ↓
JavaScript
   ↓
Decision
   ↓
Action
```

### Declarative

```text
Rules
   ↓
DNR Engine
   ↓
Request matching
   ↓
Action
```

Вторая модель потенциально позволяет:

* уменьшить количество background JavaScript;
* уменьшить runtime overhead;
* сделать execution более предсказуемым;
* ограничить возможности extension;
* перенести работу в оптимизированный browser engine.
