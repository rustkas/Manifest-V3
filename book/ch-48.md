# Глава 48. Project 8 — Full Multi-context Application

В предыдущих проектах мы постепенно собирали отдельные части Manifest V3:

* Action и Popup;
* Content Script;
* Service Worker;
* Messaging;
* Storage;
* Commands;
* Side Panel;
* Declarative Net Request.

Теперь впервые объединим их в **одно полноценное multi-context extension**.

Главная цель проекта — не создать сложный продукт, а научиться проектировать расширение, в котором несколько независимых execution contexts работают как единое приложение.

---

# 48.1. Цель проекта

Создадим расширение **Page Workspace**.

Идея проста:

> расширение позволяет сохранять рабочее состояние для текущей страницы, отображать его в Side Panel и изменять настройки через Options Page.

Пользователь сможет:

1. открыть Popup;
2. увидеть информацию о текущей вкладке;
3. добавить заметку к странице;
4. открыть Side Panel;
5. редактировать данные страницы через Side Panel;
6. изменить глобальные настройки через Options;
7. Content Script будет интегрироваться со страницей;
8. Service Worker будет координировать contexts;
9. Storage будет хранить состояние;
10. Messaging будет связывать все части приложения.

Архитектура:

```text
                         Browser
                            │
       ┌────────────────────┼────────────────────┐
       │                    │                    │
       ▼                    ▼                    ▼
     Popup              Side Panel           Options
       │                    │                    │
       └──────────────┬─────┴──────────────┬─────┘
                      │                    │
                      ▼                    ▼
                 Service Worker       Storage
                      │
                      │
                      ▼
                Content Script
                      │
                      ▼
                    Page
```

Это уже полноценное extension application.

---

# 48.2. Почему этот проект важнее предыдущих

До этого мы изучали contexts преимущественно отдельно.

Например:

```text
Popup → Service Worker
```

или:

```text
Content Script → Service Worker
```

Теперь появляется система:

```text
Popup
   ↕
Service Worker
   ↕
Side Panel
   ↕
Content Script
   ↕
Page

Options
   ↕
Storage
```

И возникает новая проблема:

> **Как сделать так, чтобы несколько независимых contexts представляли одно логическое приложение?**

Это уже не вопрос API.

Это вопрос архитектуры.

---

# 48.3. Multi-context application

Наше приложение состоит из нескольких runtime environments.

```text
Extension
│
├── Popup
├── Side Panel
├── Options Page
├── Service Worker
└── Content Script
```

У каждого context:

* свой lifecycle;
* своё JavaScript environment;
* свои глобальные переменные;
* свои DOM;
* свои ограничения.

Поэтому нельзя сделать:

```javascript
// popup.js

appState.user.name
```

и ожидать, что:

```javascript
// side-panel.js

appState.user.name
```

автоматически увидит тот же объект.

Такого общего JavaScript state нет.

---

# 48.4. Поэтому нужен application state

Мы должны определить:

```text
Canonical State
```

Например:

```json
{
    "settings": {
        "enabled": true,
        "theme": "system"
    },

    "pages": {
        "https://example.com/": {
            "note": "Important page",
            "favorite": true
        }
    }
}
```

Но этот state не должен находиться внутри Popup.

И не должен находиться внутри Side Panel.

Лучше использовать:

```text
chrome.storage
```

как persistent state layer.

---

# 48.5. Архитектура состояния

Получаем:

```text
                 Application State
                        │
                        ▼
                  chrome.storage
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
        Popup       Side Panel      Options
          │             │             │
          └─────────────┼─────────────┘
                        │
                        ▼
                 Service Worker
```

Storage становится общей точкой сохранённого состояния.

Но это ещё не решает проблему **моментального обновления UI**.

Для этого нужен messaging.

---

# 48.6. Два механизма взаимодействия

В приложении будут использоваться два разных механизма:

```text
Storage
    =
persistent state

Messaging
    =
runtime communication
```

Например:

```text
Side Panel
    │
    │ UPDATE_NOTE
    ▼
Service Worker
    │
    ▼
Storage
    │
    ▼
storage.onChanged
```

После этого другие contexts могут обновить свой UI.

# 48.11. Service Worker

Начнём с центрального координатора:

```javascript
console.log(
    "Page Workspace service worker started"
);

chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        console.log(
            "Message:",
            message,
            "from:",
            sender.contextType
        );

        handleMessage(
            message,
            sender
        )
        .then(sendResponse)
        .catch(error => {

            sendResponse({
                ok: false,
                error: error.message
            });

        });

        return true;
    }
);
```

Обратите внимание:

```text
Service Worker
```

не является "главным приложением" в традиционном смысле.

Он является:

```text
orchestrator
```

---

# 48.12. Почему Service Worker — orchestrator

Он отвечает за:

```text
routing
state access
browser APIs
validation
coordination
```

Но UI не должен находиться внутри него.

Поэтому:

```text
Popup
```

отвечает за Popup UI.

```text
Side Panel
```

отвечает за Side Panel UI.

```text
Options
```

отвечает за настройки.

# 48.13. Message protocol

Теперь определим единый протокол сообщений.

Файл:

```text
shared/messages.js
```

Например:

```javascript
export const MESSAGE_TYPES = {

    GET_ACTIVE_TAB:
        "GET_ACTIVE_TAB",

    GET_PAGE_STATE:
        "GET_PAGE_STATE",

    UPDATE_PAGE_STATE:
        "UPDATE_PAGE_STATE",

    GET_SETTINGS:
        "GET_SETTINGS",

    UPDATE_SETTINGS:
        "UPDATE_SETTINGS"
};
```

Теперь contexts не используют произвольные строки:

```javascript
sendMessage({
    type: "something"
});
```

а используют общий protocol:

```javascript
sendMessage({
    type:
        MESSAGE_TYPES.GET_PAGE_STATE
});
```

---

# 48.14. Message schema

Сообщение:

```javascript
{
    type: "UPDATE_PAGE_STATE",

    payload: {
        url:
            "https://example.com",

        changes: {
            note:
                "Important"
        }
    }
}
```

можно представить как:

```text
Message
│
├── type
│
└── payload
      │
      ├── url
      └── changes
```

Это становится application protocol.

---

# 48.15. Почему protocol важен

Без протокола быстро появляется:

```text
"getState"
"GET_STATE"
"get_page_state"
"pageState"
"loadPage"
```

разные contexts начинают говорить на разных языках.

Централизованный protocol предотвращает эту проблему.

# 48.16. Storage layer

Создадим abstraction:

```javascript
export async function getSettings() {

    const result =
        await chrome.storage.local.get(
            "settings"
        );

    return result.settings ?? {
        enabled: true,
        theme: "system"
    };
}
```

И:

```javascript
export async function saveSettings(
    settings
) {

    await chrome.storage.local.set({
        settings
    });
}
```

Теперь UI не обязан знать детали storage API.

---

# 48.17. Page state

Для данных страниц:

```javascript
export async function getPageState(
    url
) {

    const result =
        await chrome.storage.local.get(
            "pages"
        );

    const pages =
        result.pages ?? {};

    return pages[url] ?? {
        note: "",
        favorite: false
    };
}
```

---

# 48.18. Обновление page state

Например:

```javascript
export async function updatePageState(
    url,
    changes
) {

    const result =
        await chrome.storage.local.get(
            "pages"
        );

    const pages =
        result.pages ?? {};

    pages[url] = {
        ...(pages[url] ?? {}),
        ...changes
    };

    await chrome.storage.local.set({
        pages
    });
}
```

Теперь storage становится нашей persistence layer.

# 48.21. Message dispatcher

Теперь:

```javascript
async function handleMessage(
    message,
    sender
) {

    switch (message.type) {

        case "GET_ACTIVE_TAB":

            return {
                ok: true,
                tab:
                    await getActiveTab()
            };

        case "GET_PAGE_STATE":

            return {
                ok: true,

                state:
                    await getPageState(
                        message.payload.url
                    )
            };

        default:

            return {
                ok: false,
                error:
                    "Unknown message type"
            };
    }
}
```

Это уже маленький application protocol server.

# 48.40. Почему Content Script не должен хранить application state

Content Script может знать:

```text
DOM state
page-specific runtime information
```

Но canonical application state лучше держать в:

```text
chrome.storage
```

или управляемом через Service Worker state layer.

Иначе возникает:

```text
Popup state
Side Panel state
Content Script state
```

и они начинают расходиться.

# 48.43. Полный data flow

Теперь изменение заметки выглядит так:


# 48.44. Single source of truth

Главный принцип:

> **Для каждого вида данных должен существовать один canonical source of truth.**

Например:

```text
Settings
   ↓
chrome.storage.local
```

```text
Page metadata
   ↓
chrome.storage.local
```

А не:

```text
Popup → own copy
Side Panel → own copy
Content Script → own copy
```

# 48.45. Почему копии всё равно существуют

На практике UI всё равно имеет локальное представление:

```javascript

```

Но это:

```text
UI cache
```

а не canonical state.

Например:

```text
Storage
   │
   ▼
Side Panel state
```

Если state изменился:

```text
Storage
   │
   ▼
Side Panel update
```

# 48.46. Eventual consistency

Contexts могут обновляться не одновременно.

Например:

```text
t0:
Side Panel = A
Popup = A

t1:
Side Panel changes → B

t2:
Storage = B

t3:
Content Script receives B

t4:
other UI receives B
```

Это нормально.

Multi-context extension фактически имеет свойства distributed application.

---

# 48.47. Idempotent updates

Предпочтительно проектировать команды так, чтобы повторное выполнение было безопасным.

Например:

```text
SET_FAVORITE = true
```

обычно безопаснее, чем:

```text
TOGGLE_FAVORITE
```

Почему?

Если сообщение:

```text
TOGGLE_FAVORITE
```

будет доставлено дважды:

```text
false
 ↓
true
 ↓
false
```

получим неправильный результат.

А:

```text
SET_FAVORITE(true)
```

при повторении остаётся:

```text
true
true
```

# 48.69. Почему это distributed system

На первый взгляд это обычное приложение.

Но технически:

```text
Popup
Side Panel
Options
Service Worker
Content Script
```

— отдельные execution contexts.

Они:

* запускаются независимо;
* завершаются независимо;
* имеют отдельное состояние;
* общаются сообщениями;
* могут временно отсутствовать.

Поэтому extension имеет свойства distributed system.

---

# 48.70. Но это не классическая distributed system

Здесь нет:


```text

lifecycle
failure boundaries
race conditions
eventual consistency
idempotency
```

Поэтому архитектурные идеи распределённых систем здесь неожиданно полезны.
