# Глава 8. Extension Pages

В предыдущей главе мы рассмотрели execution contexts и увидели, что browser extension состоит не из одного JavaScript runtime, а из нескольких независимых сред.

Теперь рассмотрим **Extension Pages** — HTML-страницы, принадлежащие самому extension.

К ним относятся, в частности:

* Popup;
* Options Page;
* Side Panel;
* DevTools pages;
* другие HTML-документы, которые extension использует как собственный UI или внутреннюю страницу.

Упрощённо:

```text
Extension
│
├── manifest.json
│
├── popup.html
├── options.html
├── sidepanel.html
├── devtools.html
│
├── css/
│
├── js/
│
└── assets/
```

Главная идея этой главы:

> **Extension Page — это обычная HTML-страница Web Platform, но работающая внутри специального extension origin и имеющая доступ к extension capabilities, разрешённым для данного контекста.**

Это сочетание двух миров:

```text
Web Platform
    +
Extension Platform
```

---

# 8.1. Extension origin

Каждый extension получает собственный origin.

В Chromium-based browsers он имеет вид:

```text
chrome-extension://<extension-id>/
```

Например:

```text
chrome-extension://abcdefghijklmnop/
```

Если extension содержит:

```text
popup.html
```

его URL концептуально выглядит так:

```text
chrome-extension://abcdefghijklmnop/popup.html
```

---

## Extension origin — не обычный HTTP origin

Он отличается от:

```text
https://example.com/
```

и:

```text
http://example.com/
```

Extension имеет собственную origin boundary.

Можно представить:

```text
                 Browser
                    │
       ┌────────────┴────────────┐
       │                         │
 https://example.com     chrome-extension://ID
       │                         │
    Web Page                Extension Pages
```

Это одна из основ безопасности extensions.

---

## Почему origin имеет значение?

Origin участвует в определении:

* security boundaries;
* доступа к storage;
* относительных URL;
* загрузки ресурсов;
* поведения DOM APIs;
* взаимодействия с другими origins;
* политики безопасности.

Поэтому нельзя относиться к:

```text
chrome-extension://...
```

как просто к "ещё одному URL".

Это отдельная среда браузера.

---

# Extension ID

В URL extension используется его ID:

```text
chrome-extension://EXTENSION_ID/
```

Например:

```text
chrome-extension://abcdefghijklmnop/
```

ID идентифицирует установленное extension.

Это позволяет браузеру отличать ресурсы:

```text
chrome-extension://AAAA/popup.html
```

от:

```text
chrome-extension://BBBB/popup.html
```

---

# Extension root

Условно можно считать:

```text
chrome-extension://ID/
```

корнем extension.

Например:

```text
chrome-extension://ID/
├── popup.html
├── options.html
├── css/style.css
├── js/popup.js
└── images/icon.png
```

---

# Относительные URL

Внутри HTML можно использовать обычные относительные URL:

```html
<link rel="stylesheet" href="./css/popup.css">
```

и:

```html
<script type="module" src="./js/popup.js"></script>
```

Браузер разрешит их относительно текущего extension document.

---

# Абсолютный extension URL

Можно сформировать URL:

```text
chrome-extension://ID/options.html
```

но в коде обычно лучше использовать API браузера для получения URL ресурса.

Например:

```javascript
const url = chrome.runtime.getURL("options.html");
```

Результат будет примерно:

```text
chrome-extension://abcdefghijklmnop/options.html
```

Это особенно удобно, когда URL нужно передать другому API.

---

# 8.2. HTML внутри extension

Extension Page — это прежде всего HTML.

Например:

```html
<!doctype html>
<html lang="en">
<head>
    <meta charset="UTF-8">

    <meta
        name="viewport"
        content="width=device-width, initial-scale=1.0"
    >

    <title>My Extension</title>

    <link
        rel="stylesheet"
        href="./css/style.css"
    >
</head>

<body>

    <main>
        <h1>My Extension</h1>

        <button id="run">
            Run
        </button>
    </main>

    <script
        type="module"
        src="./js/main.js"
    ></script>

</body>
</html>
```

С точки зрения Web Platform это совершенно нормальный HTML-документ.

---

# HTML First

Это особенно хорошо соответствует архитектуре Manifest V3.

Не нужно превращать extension UI в обязательный JavaScript-generated application.

Можно начать с:

```text
HTML
 +
CSS
 +
Web APIs
```

и только затем добавить:

```text
Extension APIs
```

Например:

```html
<button id="save">
    Save
</button>
```

а JavaScript:

```javascript
const button = document.querySelector("#save");

button.addEventListener("click", () => {
    console.log("Saved");
});
```

Это обычная Web Platform.

---

# Extension Page и DOM

Поскольку Extension Page является HTML-документом, в нём доступны стандартные DOM APIs:

```javascript
document.querySelector(...)
document.createElement(...)
element.append(...)
element.remove(...)
```

Например:

```javascript
const title = document.createElement("h1");

title.textContent = "Hello Extension";

document.body.append(title);
```

---

# Не путайте Extension Page и Content Script

Оба могут работать с DOM, но DOM относится к разным документам.

Extension Page:

```text
chrome-extension://ID/popup.html
        │
        └── Extension DOM
```

Content Script:

```text
https://example.com
        │
        └── Web Page DOM
```

То есть:

```text
Popup DOM
    ≠
Web Page DOM
```

Content Script может работать с DOM веб-страницы.

Popup работает со своим DOM.

---

# 8.3. CSS

В Extension Pages используется обычный CSS.

Например:

```css
body {
    margin: 0;
    padding: 16px;
    font-family: system-ui, sans-serif;
}

button {
    padding: 8px 12px;
}
```

Подключение:

```html
<link
    rel="stylesheet"
    href="./css/style.css"
>
```

---

## Можно использовать современный CSS

Extension Pages работают на базе браузерного движка, поэтому доступны современные возможности CSS, поддерживаемые конкретным браузером.

Например:

```css
.container {
    display: grid;
    grid-template-columns: 1fr 1fr;
    gap: 12px;
}
```

или:

```css
.panel {
    display: flex;
    align-items: center;
    justify-content: space-between;
}
```

---

# CSS Custom Properties

Очень удобно использовать CSS variables:

```css
:root {
    --background: white;
    --foreground: #222;
    --border: #ddd;
}

body {
    background: var(--background);
    color: var(--foreground);
}
```

Затем JavaScript может изменить:

```javascript
document.documentElement.style
    .setProperty("--background", "#222");
```

---

# CSS не является Extension API

Важно разделять:

```text
CSS
```

и:

```text
Chrome Extension APIs
```

CSS отвечает за:

```text
layout
style
animation
appearance
```

Extension APIs отвечают за:

```text
tabs
storage
runtime
permissions
commands
sidePanel
```

Архитектурно это разные уровни.

---

# CSS isolation

CSS Extension Page применяется к её собственному DOM.

Например:

```text
popup.html
    │
    └── Popup DOM
          │
          └── popup.css
```

CSS страницы:

```text
https://example.com
```

не должен рассматриваться как CSS Popup.

И наоборот.

Это ещё одно следствие разных document contexts и origins.

---

# 8.4. JavaScript modules

Современное Manifest V3 extension следует строить на обычных JavaScript modules.

Например:

```text
js/
├── main.js
├── storage.js
├── ui.js
└── api.js
```

`main.js`:

```javascript
import { loadSettings } from "./storage.js";
import { renderSettings } from "./ui.js";

const settings = await loadSettings();

renderSettings(settings);
```

---

# Почему модули особенно важны?

Extension быстро становится многокомпонентным приложением.

Без модулей появляется:

```text
popup.js
    2000 lines
```

и затем:

```text
options.js
    2500 lines
```

и большое количество глобальных переменных.

Модули позволяют разделить систему:

```text
UI
│
├── ui.js
│
├── storage.js
│
├── messaging.js
│
└── validation.js
```

---

# ES Modules

HTML:

```html
<script
    type="module"
    src="./js/main.js"
></script>
```

Теперь:

```javascript
import ...
export ...
```

работают как стандартные ES Modules.

Например:

```javascript
// math.js

export function add(a, b) {
    return a + b;
}
```

и:

```javascript
// main.js

import { add } from "./math.js";

console.log(add(2, 3));
```

Результат:

```text
5
```

---

# 8.5. ESM

Manifest V3 хорошо сочетается с современной модульной архитектурой JavaScript.

Для Extension Pages:

```html
<script
    type="module"
    src="./main.js"
></script>
```

Это стандартный ESM механизм браузера.

---

# Module graph

Важно понимать, что `main.js` может импортировать другие модули.

```text
main.js
   │
   ├── ui.js
   │
   ├── storage.js
   │
   └── messaging.js
```

А `storage.js` может импортировать:

```text
storage.js
   │
   └── validation.js
```

Получается module graph:

```text
                main.js
              /    |    \
             /     |     \
           ui    storage messaging
                   │
                   ▼
              validation
```

Это естественная архитектура для современного extension.

---

# Static imports

Например:

```javascript
import { saveSettings }
    from "./storage.js";
```

Такие зависимости известны заранее.

Это хорошо соответствует принципу:

```text
Static code
    ↓
Bundled / packaged extension
```

---

# Dynamic import

В Extension Pages также можно использовать стандартный:

```javascript
const module = await import("./feature.js");
```

Например:

```javascript
button.addEventListener("click", async () => {
    const { analyze } =
        await import("./analyzer.js");

    await analyze();
});
```

Это позволяет загружать функциональность по требованию.

Однако нужно учитывать ограничения CSP и общую security model extension.

---

# Не смешивайте ESM и background architecture

Очень важный момент:

```text
Extension Page
```

и:

```text
Service Worker
```

оба используют JavaScript, но имеют разные lifecycle и особенности.

Поэтому архитектура:

```text
Popup
   ↓
ES modules
```

и:

```text
Service Worker
   ↓
event-driven background
```

должна рассматриваться отдельно.

---

# 8.6. DOM API

Extension Pages имеют доступ к стандартному DOM API.

Например:

```javascript
const button =
    document.querySelector("#run");
```

Создание элементов:

```javascript
const message =
    document.createElement("p");

message.textContent =
    "Analysis complete.";

document.body.append(message);
```

---

# Event handling

Обычная модель:

```javascript
button.addEventListener(
    "click",
    handleClick
);
```

Например:

```javascript
async function handleClick() {

    const result =
        await analyzeCurrentPage();

    document.querySelector("#result")
        .textContent = result;
}
```

---

# DOM и extension APIs работают вместе

Например:

```javascript
const button =
    document.querySelector("#analyze");

button.addEventListener("click", async () => {

    const [tab] =
        await chrome.tabs.query({
            active: true,
            currentWindow: true
        });

    console.log(tab.url);
});
```

Здесь мы соединяем два слоя:

```text
DOM API
   +
Extension API
```

---

# Web Platform First

Очень полезный принцип:

> Используйте Web Platform там, где её возможностей достаточно, и Extension APIs там, где нужны возможности браузерного extension runtime.

Например, для UI:

```text
document.querySelector()
addEventListener()
fetch()
URL()
URLSearchParams()
AbortController()
```

не требуют extension-specific API.

А для:

```text
tabs
storage
runtime messaging
permissions
commands
```

используются Extension APIs.

---

# 8.7. Web APIs внутри extension

Extension Pages не перестают быть web documents.

Поэтому многие стандартные Web APIs доступны.

Например:

```text
Fetch API
URL API
Web Storage
DOM
Events
Promises
Web Crypto
Web Workers
Streams
AbortController
```

— в зависимости от конкретного API и browser context.

---

# Fetch

Например:

```javascript
const response =
    await fetch("https://api.example.com/data");

const data =
    await response.json();
```

Но здесь появляется важное различие между:

```text
Web Platform capability
```

и:

```text
Extension permission model
```

Наличие `fetch()` само по себе не означает отсутствие ограничений.

---

# CORS и Extension Pages

Обычная веб-страница ограничена browser security model, включая CORS.

Extension contexts имеют дополнительные возможности и правила, зависящие от permissions и типа context.

Поэтому нельзя делать универсальный вывод:

> "Если fetch работает на сайте, он точно будет работать в extension."

И наоборот.

Network architecture extension нужно проектировать отдельно.

---

# URL API

Обычные Web APIs доступны:

```javascript
const url = new URL(
    "https://example.com/search?q=extension"
);

console.log(url.hostname);
console.log(url.searchParams.get("q"));
```

---

# AbortController

Например:

```javascript
const controller =
    new AbortController();

const response = await fetch(
    url,
    {
        signal: controller.signal
    }
);
```

Можно отменить:

```javascript
controller.abort();
```

Это особенно полезно для UI extension, где пользователь может быстро изменить запрос.

---

# Web Crypto

Современные Web APIs также позволяют использовать криптографические примитивы, предоставляемые браузером.

Например:

```javascript
const bytes =
    crypto.getRandomValues(
        new Uint8Array(16)
    );
```

Но следует различать:

```text
Cryptographic API
```

и:

```text
Secure secret storage
```

Наличие `crypto` не означает, что extension становится защищённым хранилищем секретов.

---

# 8.8. Storage

В Extension Pages есть несколько вариантов хранения данных.

Наиболее важный extension-specific механизм:

```text
chrome.storage
```

Например:

```javascript
await chrome.storage.local.set({
    theme: "dark"
});
```

Чтение:

```javascript
const data =
    await chrome.storage.local.get("theme");

console.log(data.theme);
```

---

# `chrome.storage` как shared extension storage

Это особенно важно для архитектуры contexts.

Например:

```text
                  chrome.storage
                  /      |      \
                 /       |       \
            Popup    Options    Service Worker
                              \
                               Content Script
```

Разные contexts могут получать доступ к соответствующим storage areas.

Это позволяет хранить состояние независимо от lifetime конкретного context.

---

# Почему не `let state = {}`?

Предположим:

```javascript
let state = {
    theme: "dark"
};
```

В Popup это состояние исчезнет вместе с Popup context.

Поэтому:

```text
JavaScript memory
    ≠
Persistent extension state
```

Если данные должны переживать закрытие страницы, их нужно сохранять в подходящее persistent storage.

---

# `chrome.storage.local`

Основное локальное хранилище extension:

```javascript
await chrome.storage.local.set({
    language: "en"
});
```

И:

```javascript
const {
    language
} = await chrome.storage.local.get(
    "language"
);
```

---

# Storage и архитектура

Например:

```text
Options Page
     │
     ▼
storage.local
     │
     ▼
Service Worker
```

Options Page меняет:

```text
language = "pl"
```

Service Worker может прочитать:

```text
language = "pl"
```

не потому, что они используют общую память, а потому что используют общий persistent data store.

---

# `session` storage

Extension APIs также предоставляют storage areas с разными semantics, включая session-oriented storage.

Это полезно, когда данные не должны переживать определённые lifecycle boundaries.

Главный принцип:

> Выбирайте storage исходя из lifetime данных, а не из удобства конкретного context.

---

# 8.9. Navigation

Extension Pages могут навигироваться, как HTML-документы, но navigation имеет особое значение для extension security model.

Например:

```text
chrome-extension://ID/popup.html
```

может содержать ссылки:

```html
<a href="./options.html">
    Settings
</a>
```

или JavaScript navigation:

```javascript
location.href = "./options.html";
```

---

# Extension navigation

Можно использовать:

```javascript
location.href =
    chrome.runtime.getURL("options.html");
```

Например:

```javascript
button.addEventListener("click", () => {
    location.href =
        chrome.runtime.getURL("options.html");
});
```

---

# `chrome.runtime.getURL()`

Это один из наиболее полезных методов при работе с extension resources:

```javascript
const url =
    chrome.runtime.getURL(
        "images/icon.png"
    );
```

или:

```javascript
const url =
    chrome.runtime.getURL(
        "options.html"
    );
```

Результат:

```text
chrome-extension://ID/options.html
```

---

# Navigation между Extension Pages

Например:

```text
Popup
  │
  ▼
Options Page
```

можно реализовать через:

```javascript
location.href =
    chrome.runtime.getURL("options.html");
```

Но часто лучше использовать специализированные extension mechanisms, когда они предоставляются API.

---

# Opening an extension page

Для открытия отдельной extension page в новой вкладке можно использовать соответствующий browser API.

Например:

```javascript
chrome.tabs.create({
    url: chrome.runtime.getURL("options.html")
});
```

Архитектура:

```text
Popup
  │
  │ chrome.tabs.create()
  ▼
Browser Tab
  │
  ▼
options.html
```

---

# Navigation и lifecycle

Помните, что navigation может уничтожить текущий document.

Например:

```javascript
location.href = "./options.html";
```

после этого текущая Popup/Extension Page context прекращает существовать, а создаётся новый document.

Поэтому нельзя рассчитывать, что состояние JavaScript:

```javascript
let state = {...};
```

переживёт navigation.

Если оно нужно после navigation:

```text
state
 ↓
storage
 ↓
new context
 ↓
restore
```

# 8.10. Extension URLs

В Manifest V3 разработчику постоянно приходится работать с URL ресурсов extension.

Основной формат:

```text
chrome-extension://<extension-id>/<path>
```

Например:

```text
chrome-extension://abcdefghijklmnop/popup.html
```

---

# `chrome.runtime.getURL()`

Предпочтительный способ построения URL ресурса:

```javascript
const resourceUrl =
    chrome.runtime.getURL(
        "assets/logo.svg"
    );
```

Это лучше, чем вручную конструировать:

```text
chrome-extension://...
```

потому что extension ID не следует хардкодить.

---

# Почему нельзя хардкодить Extension ID?

Плохо:

```javascript
const url =
    "chrome-extension://abcdefghijklmnop/options.html";
```

ID может отличаться между environments.

Например:

```text
Development
Production
Different installation
Different browser
```

Лучше:

```javascript
const url =
    chrome.runtime.getURL("options.html");
```

---

# Extension URL и resources

Например:

```text
extension/
├── images/
│   └── logo.svg
├── styles/
│   └── main.css
├── scripts/
│   └── main.js
└── options.html
```

Можно получить:

```javascript
chrome.runtime.getURL(
    "images/logo.svg"
);
```

или:

```javascript
chrome.runtime.getURL(
    "styles/main.css"
);
```

---

# Extension URL и Web Page

Здесь появляется важная security distinction.

Ресурс extension:

```text
chrome-extension://ID/resource
```

не является автоматически публичным ресурсом для любого сайта.

Если веб-странице необходимо получить доступ к определённому extension resource, используются механизмы вроде:

```text
web_accessible_resources
```

которые мы рассматривали в Manifest.

---

# Почему это важно?

Представим:

```text
Extension
│
└── secret-data.json
```

Не следует предполагать:

> "Если файл лежит внутри extension package, любой сайт может его прочитать."

И наоборот:

> "Любой файл extension автоматически доступен web page."

Доступ контролируется extension security model.

# URL как архитектурный интерфейс

Extension URL — это не просто строка.

Например:

```text
chrome-extension://ID/options.html
```

сообщает сразу несколько вещей:

```text
scheme       = chrome-extension
origin       = extension
resource     = options.html
```

Поэтому URL API особенно полезны при построении extension architecture.

# Extension Page как Web Platform application

Очень важно не переусложнять Extension Pages.

Это всё ещё:

```text
HTML
CSS
JavaScript
DOM
Web APIs
```

То есть extension development не требует отказаться от Web Platform.

Наоборот, хорошая архитектура строится поверх неё.

---

# Platform First

Можно использовать следующий принцип:

```text
Need
 │
 ├── UI?
 │      ↓
 │     HTML/CSS/DOM
 │
 ├── Browser capability?
 │      ↓
 │     Extension API
 │
 ├── Persistent data?
 │      ↓
 │     chrome.storage
 │
 ├── Page interaction?
 │      ↓
 │     Content Script
 │
 └── Background operation?
        ↓
       Service Worker
```

Это позволяет не использовать Extension API там, где стандартного Web API достаточно.

# Практический пример

Создадим небольшую Extension Page.

Структура:

```text
my-extension/
│
├── manifest.json
│
├── popup.html
│
├── css/
│   └── popup.css
│
└── js/
    ├── popup.js
    └── storage.js
```

---

## `popup.html`

```html
<!doctype html>

<html lang="en">

<head>
    <meta charset="UTF-8">

    <meta
        name="viewport"
        content="width=device-width,
                 initial-scale=1.0"
    >

    <title>My Extension</title>

    <link
        rel="stylesheet"
        href="./css/popup.css"
    >
</head>

<body>

    <main>
        <h1>My Extension</h1>

        <button id="save">
            Save
        </button>

        <output id="status"></output>
    </main>

    <script
        type="module"
        src="./js/popup.js"
    ></script>

</body>

</html>
```

---

## `storage.js`

```javascript
export async function saveSettings(settings) {

    await chrome.storage.local.set({
        settings
    });
}
```

---

## `popup.js`

```javascript
import {
    saveSettings
} from "./storage.js";

const button =
    document.querySelector("#save");

const status =
    document.querySelector("#status");

button.addEventListener(
    "click",
    async () => {

        await saveSettings({
            theme: "dark"
        });

        status.textContent =
            "Settings saved";
    }
);
```

Получаем:

```text
HTML
  ↓
DOM
  ↓
ES Module
  ↓
Extension API
  ↓
chrome.storage
```

Это и есть типичный современный Extension Page.

# Extension Pages и архитектура приложения

Можно разделить ответственность:

```text
                  Extension
                      │
       ┌──────────────┼───────────────┐
       │              │               │
       ▼              ▼               ▼
     Popup         Side Panel       Options
       │              │               │
       └──────────────┼───────────────┘
                      │
                   Messaging
                      │
                      ▼
               Service Worker
                      │
             ┌────────┼────────┐
             │        │        │
          Storage   Network   Browser
                      APIs
```

Каждая Extension Page занимается UI.

Service Worker занимается background logic.

Content Script занимается web page integration.

Это разделение делает систему значительно проще.

# Главные выводы главы

### 1. Extension Page — это полноценный HTML-документ

Она использует:

```text
HTML
CSS
JavaScript
DOM
Web APIs
```

---

### 2. Extension Pages работают внутри специального origin

```text
chrome-extension://<extension-id>/
```

---

### 3. Popup, Options и Side Panel — разновидности Extension Pages

У них разные lifecycle и назначения, но фундаментально они используют web document model.

---

### 4. Современный Manifest V3 extension естественно использовать с ESM

```html
<script
    type="module"
    src="./main.js"
></script>
```

и:

```javascript
import ...
export ...
```

---

### 5. Web Platform остаётся основой

Не нужно использовать Extension API для всего.

Хорошая архитектура:

```text
Web Platform
     +
Extension APIs
```

---

### 6. DOM Extension Page и DOM Web Page — разные документы

```text
Popup DOM
    ≠
Web Page DOM
```

---

### 7. JavaScript memory не является shared state

Contexts не имеют общей памяти.

Для взаимодействия используются:

```text
Messaging
Storage
Ports
Browser APIs
```

---

### 8. Для persistent state используйте подходящий storage

Например:

```javascript
chrome.storage.local
```

а не глобальные переменные Popup.

---

### 9. Для extension resources используйте `chrome.runtime.getURL()`

Вместо:

```text
chrome-extension://ID/...
```

вручную используйте:

```javascript
chrome.runtime.getURL("options.html");
```

---

### 10. Extension Page — это Web Platform внутри Extension Platform

Именно эту идею следует запомнить:

```text
                 Manifest V3
                     │
        ┌────────────┴────────────┐
        │                         │
 Web Platform              Extension Platform
        │                         │
 HTML CSS JS DOM             APIs / Permissions
 Web APIs                    Messaging
 ESM                         Storage
 Events                      Tabs
        │                         │
        └────────────┬────────────┘
                     │
               Extension Page
```

Таким образом, **Extension Page не является каким-то отдельным "магическим UI-фреймворком"**. Это обычный web document, помещённый в extension architecture и дополненный возможностями браузерного extension runtime.

Именно поэтому разработчику Manifest V3 особенно важно хорошо знать саму **Web Platform**: HTML, CSS, DOM, Events, ESM, Fetch, URL, Storage и другие Web APIs. Extension API должен добавляться поверх этой основы только там, где возможностей самой платформы недостаточно.
