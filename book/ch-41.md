# Часть XV. Практические проекты

# Глава 41. Project 1 — Hello Extension

В этой главе мы создадим первое полностью рабочее расширение для браузера на Manifest V3.

Цель проекта — не создать полезный коммерческий продукт, а собрать **минимальный extension runtime**, через который можно увидеть весь базовый цикл:

```text
Source files
    ↓
manifest.json
    ↓
Browser
    ↓
Extension installation
    ↓
Action
    ↓
Popup
    ↓
JavaScript
```

После выполнения проекта у нас будет расширение, которое:

1. устанавливается в браузер;
2. появляется среди extensions;
3. имеет собственную иконку;
4. отображается на toolbar;
5. открывает Popup;
6. выполняет JavaScript;
7. взаимодействует с DOM собственного extension page.

Это будет фундамент для следующих практических проектов.

# 41.10. Почему используется `type="module"`

Мы подключаем:

```html
<script
    type="module"
    src="./popup.js"
></script>
```

Это означает, что `popup.js` работает как ES module.

Мы можем использовать:

```javascript
import ...
export ...
```

и современную ESM-модель JavaScript.

Для Manifest V3 это естественный подход.

# 41.14. Важный момент: это Extension Page

Popup не является обычной web page.

Он принадлежит extension.

У него собственный extension origin:

```text
chrome-extension://<extension-id>/
```

Концептуально:

```text
Web
├── https://example.com
│
└── Extension
    └── chrome-extension://...
```

Поэтому Popup является частью extension security boundary.

---

# 41.15. Нам пока не нужен Service Worker

Это принципиально важно.

Наш первый extension **не содержит**:

```json
"background": {
    "service_worker": "background.js"
}
```

И это нормально.

Почему?

Потому что пока нам не требуется background processing.

Наше приложение:

```text
Action
  ↓
Popup
  ↓
DOM
```

полностью работает без Service Worker.

Это хороший архитектурный принцип:

> Не добавляйте extension context до тех пор, пока он действительно не нужен.

---

# 41.16. Нам пока не нужны permissions

Наш Manifest также не содержит:

```json
"permissions": [...]
```

и:

```json
"host_permissions": [...]
```

Это тоже правильно.

Наш extension не:

* читает tabs;
* изменяет websites;
* делает cross-origin requests;
* использует storage;
* injects content scripts.

Следовательно, permissions ему не нужны.

Получаем:

```text
Permissions = 0
```

# 41.29. Почему Console может быть пустой

Popup имеет короткий lifecycle.

Когда Popup закрывается:

```text
Popup
  ↓
closed
  ↓
context destroyed
```

Поэтому нельзя относиться к Popup как к постоянно работающему приложению.

Это одна из самых важных особенностей extension UI.

---

# 41.30. Popup lifecycle

Наше приложение работает примерно так:

```text
click icon
    ↓
create popup context
    ↓
load HTML
    ↓
load JS
    ↓
user interaction
    ↓
popup closes
    ↓
context destroyed
```

Поэтому state:

```javascript
let counter = 10;
```

не является persistent state.

После следующего открытия:

```text
counter
  ↓
new JavaScript context
  ↓
initial value
```

# 41.31. Первый эксперимент со state

Добавим:

```javascript
let count = 0;

    count++;

    message.textContent =
        `Clicked ${count} times`;

```

Теперь:

```text

→ Clicked 1 times

→ Clicked 2 times

→ Clicked 3 times
```

Но закройте Popup и откройте снова.

Получите:

```text

```

Почему?

Потому что:

```text

    ↓
destroyed
    ↓
count destroyed
```

# 41.37. Первый архитектурный вывод

Самое важное в этом проекте — даже не кнопка.

Мы увидели, что browser extension состоит из **контекстов выполнения**, а не является одной веб-страницей.

В нашем первом проекте есть:

```text
Extension
    │
    └── Popup Context
```

В следующих проектах появятся:

```text
Extension
    │
    ├── Popup
    │
    ├── Service Worker
    │
    ├── Content Script
    │
    └── Side Panel
```

И между ними появится communication layer:

```text
Popup
  │
  ▼
Service Worker
  │
  ▼
Content Script
  │
  ▼
Web Page
```

# 41.38. Следующий шаг

`Hello Extension` намеренно является минимальным.

Следующий практический проект должен добавить первый реальный browser capability.

Например:

```text
Hello Extension
      ↓
Service Worker
      ↓
Tabs API
      ↓
Active Tab
```

Тогда extension перестанет быть просто маленькой HTML-страницей и начнёт взаимодействовать с браузером как с платформой.

Это и есть следующий уровень развития:

```text
Level 1
HTML + CSS + JS
      ↓
Level 2
Extension APIs
      ↓
Level 3
Multiple Contexts
      ↓
Level 4
Content Scripts
      ↓
Level 5
Distributed Extension Runtime
```

# Итог главы

`Hello Extension` — это минимальная точка входа в разработку Manifest V3.

Мы создали extension без permissions, без background runtime и без content scripts:

```text
manifest.json
      │
      ▼
    action
      │
      ▼
    popup
      │
      ├── HTML
      ├── CSS
      └── JavaScript
```

Именно такая минимальность полезна для обучения.

Она позволяет отделить фундаментальную механику:

```text
Manifest
   ↓
Install
   ↓
Action
   ↓
Extension Page
   ↓
JavaScript
   ↓
DOM
```

от более сложных возможностей Manifest V3.

**Первый extension должен быть маленьким. Но архитектурный урок из него большой: browser extension — это не веб-сайт, установленный в браузер. Это отдельная программная система, runtime которой постепенно получает доступ к browser capabilities через специализированные execution contexts и APIs.**
