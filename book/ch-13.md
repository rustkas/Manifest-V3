# Глава 13. Background Architecture

В предыдущих главах мы рассмотрели Service Worker как **ephemeral runtime**, который запускается для обработки событий, выполняет необходимую работу и может быть остановлен браузером.

Теперь необходимо перейти от lifecycle к архитектуре.

Небольшое расширение можно написать в одном файле:

```text
service-worker.js
```

Но как только extension начинает работать с:

* Content Scripts;
* Popup;
* Options Page;
* Side Panel;
* Tabs;
* Windows;
* Storage;
* Network;
* Commands;
* Alarms;
* Permissions;

один файл быстро превращается в архитектурный монолит.

Поэтому в Manifest V3 важно отделить:

```text
Event handling
Business logic
State
Storage
Network
Scheduling
Context coordination
```

Главная идея этой главы:

> **Service Worker должен быть orchestrator, а не местом, где находится вся логика extension.**

---

# 13.1. Service Worker как orchestrator

Слово **orchestrator** означает координатор.

Service Worker не обязательно должен сам выполнять всю работу.

Его задача — координировать различные части extension:

```text
                     ┌───────────────┐
                     │Service Worker │
                     │ Orchestrator  │
                     └───────┬───────┘
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
       Storage            Network             Tabs
          │                  │                  │
          ▼                  ▼                  ▼
       State             External API       Browser UI
```

А взаимодействие с другими contexts:

```text
                   Service Worker
                   /      |      \
                  /       |       \
                 ▼        ▼        ▼
             Content    Popup    SidePanel
             Script
```

---

## Почему orchestrator?

Потому что Service Worker имеет доступ к большому количеству extension APIs и способен выступать центральным координатором.

Например:

```text
Popup
  │
  │ request
  ▼
Service Worker
  │
  ├── read storage
  ├── query tabs
  ├── perform network request
  └── save result
  │
  ▼
Popup
```

Popup не обязан самостоятельно реализовывать всю эту логику.

---

# Но orchestrator ≠ monolith

Очень важно не перепутать эти понятия.

Плохая архитектура:

```javascript
chrome.runtime.onMessage.addListener(async message => {

    // validation

    // storage

    // network

    // tabs

    // business logic

    // permissions

    // UI logic

    // 1000 lines...

});
```

Формально это работает.

Архитектурно — плохо.

Лучше:

```text
Service Worker
      │
      ├── Event Router
      │
      ├── Message Router
      │
      ├── State Manager
      │
      ├── Storage Layer
      │
      ├── Network Layer
      │
      ├── Scheduling
      │
      └── Context Coordinator
```

---

# Service Worker как composition root

В production-like extension можно сделать:

```text
background/
│
├── service-worker.js
│
├── events/
│
├── messaging/
│
├── state/
│
├── storage/
│
├── network/
│
├── scheduling/
│
├── tabs/
│
├── windows/
│
└── domain/
```

Тогда:

```javascript
// service-worker.js

import "./events/index.js";
import "./messaging/index.js";
import "./scheduling/index.js";
```

Service Worker становится **точкой сборки background runtime**.

---

# 13.2. Event routing

Service Worker получает множество событий:

```text
onInstalled
onStartup
onMessage
onCommand
onAlarm
action.onClicked
tabs.onUpdated
tabs.onRemoved
windows.onCreated
...
```

Если всё помещать в один файл:

```text
service-worker.js
    5000 lines
```

становится трудно понять, какой код отвечает за какое событие.

Поэтому нужен **event routing**.

---

# Event router

Упрощённая модель:

```text
                    Event
                      │
                      ▼
                Event Router
                      │
       ┌──────────────┼──────────────┐
       │              │              │
       ▼              ▼              ▼
    Command         Message        Alarm
     Handler        Handler        Handler
```

Например:

```javascript
chrome.commands.onCommand.addListener(
    command => {
        routeCommand(command);
    }
);
```

---

# Routing по типу события

Допустим, extension получает сообщения:

```javascript
{
    type: "GET_SETTINGS"
}
```

```javascript
{
    type: "START_SCAN"
}
```

```javascript
{
    type: "SAVE_RESULT"
}
```

Можно создать router:

```javascript
async function routeMessage(message, sender) {

    switch (message.type) {

        case "GET_SETTINGS":
            return getSettings();

        case "START_SCAN":
            return startScan(message, sender);

        case "SAVE_RESULT":
            return saveResult(message);

        default:
            throw new Error(
                `Unknown message type: ${message.type}`
            );
    }
}
```

---

# Почему routing полезен?

Потому что появляется чёткая граница:

```text
Event API
     ↓
Router
     ↓
Application logic
```

Вместо:

```text
Event API
     ↓
everything
```

---

# Event → Command → Handler

Можно использовать ещё более строгую модель:

```text
Browser Event
      ↓
Command
      ↓
Handler
      ↓
Service
      ↓
Repository
```

Например:

```text
onAlarm
   ↓
SYNC_REQUESTED
   ↓
SyncHandler
   ↓
SyncService
   ↓
Storage + Network
```

Это уже напоминает архитектуру обычного backend-приложения.

---

# 13.3. Message handling

Messaging станет одной из центральных частей архитектуры MV3.

Различные contexts могут обмениваться сообщениями:

```text
Popup
  │
  ▼
Service Worker
  │
  ▼
Content Script
```

или:

```text
Content Script
      │
      ▼
Service Worker
      │
      ▼
Popup
```

---

# Message как API

Очень полезно воспринимать message protocol как внутренний API extension.

Например:

```javascript
{
    type: "GET_PAGE_DATA"
}
```

или:

```javascript
{
    type: "SAVE_SETTINGS",
    settings: {
        enabled: true
    }
}
```

---

# Не передавайте произвольные объекты

Плохой подход:

```javascript
{
    doAnything: true,
    code: "...",
    arbitraryData: ...
}
```

Лучше иметь ограниченный protocol:

```text
GET_SETTINGS
SAVE_SETTINGS
START_SCAN
STOP_SCAN
GET_STATUS
```

---

# Message schema

Можно определить:

```javascript
{
    type: "START_SCAN",
    payload: {
        tabId: 123
    }
}
```

Service Worker:

```javascript
async function handleMessage(message) {

    if (
        message?.type !== "START_SCAN"
    ) {
        throw new Error("Invalid message");
    }

    return startScan(
        message.payload
    );
}
```

---

# Message routing

Архитектурно:

```text
             Incoming message
                    │
                    ▼
              Validation
                    │
                    ▼
              Message Router
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
 GET_SETTINGS   START_SCAN   GET_STATUS
       │            │            │
       ▼            ▼            ▼
 Settings       Scanner       Status
 Service        Service       Service
```

Это намного лучше масштабируется.

---

# Sender context

Message handler также получает информацию об отправителе.

Например:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender) => {
        console.log(sender);
    }
);
```

`sender` может содержать информацию, позволяющую понять, откуда пришло сообщение.

Это особенно важно для security.

Не следует считать:

```text
message.type
```

достаточным основанием для выполнения чувствительной операции.

---

# Message security

Нужно проверять:

```text
Who sent it?
What operation is requested?
Is the payload valid?
Does this context have permission?
```

То есть:

```text
Message
   ↓
Authentication / origin checks
   ↓
Validation
   ↓
Authorization
   ↓
Handler
```

---

# 13.4. State management

Следующий слой — состояние.

Extension может иметь:

```text
settings
current jobs
user preferences
feature flags
cache
last sync
selected tab
runtime status
```

Но не всё состояние должно храниться одинаково.

---

# Два основных типа state

```text
State
 │
 ├── Ephemeral
 │
 └── Durable
```

### Ephemeral

```text
RAM
Map
Set
temporary variables
```

### Durable

```text
chrome.storage
IndexedDB
```

---

# State manager

Вместо того чтобы обращаться к storage из каждого handler:

```javascript
chrome.storage.local.get(...)
```

можно создать:

```text
State Manager
      │
      ├── getSettings()
      ├── updateSettings()
      ├── getJob()
      ├── updateJob()
      └── getStatus()
```

---

# State transitions

Особенно полезно моделировать состояние явно.

Например job:

```text
pending
   ↓
running
   ↓
completed
```

или:

```text
pending
   ↓
running
   ↓
failed
```

---

# Почему это важно?

Service Worker может перезапуститься между двумя операциями.

Поэтому:

```javascript
let status = "running";
```

не является надёжным источником истины.

Лучше:

```javascript
await chrome.storage.local.set({
    job: {
        status: "running"
    }
});
```

---

# 13.5. Storage layer

Storage layer должен скрывать детали конкретного storage API.

Например:

```text
Application
     │
     ▼
Repository
     │
     ▼
Storage Layer
     │
     ▼
chrome.storage.local
```

---

# Почему abstraction?

Сегодня:

```text
chrome.storage.local
```

завтра вам может понадобиться:

```text
IndexedDB
```

или:

```text
chrome.storage.sync
```

или комбинация:

```text
local + sync + cache
```

Если application code напрямую зависит от API:

```javascript
chrome.storage.local.get(...)
```

замена становится сложнее.

---

# Repository

Например:

```javascript
export async function getSettings() {

    const result =
        await chrome.storage.local.get(
            "settings"
        );

    return result.settings ?? {};
}
```

Теперь business logic:

```javascript
const settings =
    await settingsRepository.get();
```

не знает, где именно находятся данные.

---

# Storage architecture

```text
                 Application
                      │
                      ▼
                State Manager
                      │
                      ▼
                Repository
                      │
                      ▼
                Storage Layer
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       local        sync       IndexedDB
```

---

# 13.6. Network layer

Extension часто взаимодействует с внешними API:

```text
Extension
    ↓
HTTP
    ↓
External API
```

Но network logic также не стоит помещать непосредственно в event handler.

Плохой вариант:

```javascript
chrome.runtime.onMessage.addListener(
    async message => {

        const response =
            await fetch(
                "https://api.example.com/data"
            );

        // 200 lines...

    }
);
```

---

# Network service

Лучше:

```text
Message Handler
      ↓
Application Service
      ↓
Network Service
      ↓
fetch()
```

Например:

```javascript
export async function fetchUserData() {

    const response = await fetch(
        "https://api.example.com/user"
    );

    if (!response.ok) {
        throw new Error(
            `HTTP ${response.status}`
        );
    }

    return response.json();
}
```

---

# Почему network layer?

Потому что здесь можно централизовать:

* authentication;
* headers;
* error handling;
* retries;
* timeout strategy;
* serialization;
* API URLs.

---

# Network и permissions

Network requests также связаны с permission model extension.

Поэтому архитектура должна учитывать:

```text
Network request
      │
      ▼
Host permission
      │
      ▼
Request allowed?
```

При проектировании extension нужно заранее определить, какие внешние origins действительно необходимы.

---

# 13.7. Scheduling

Extension иногда должен выполнять работу не только в ответ на пользовательское действие.

Например:

```text
every 30 minutes
every hour
tomorrow
after installation
after browser event
```

Но Service Worker не является постоянно работающим процессом.

Поэтому scheduling должен быть event-driven.

---

# Неправильная модель

```text
Worker
  │
  ▼
setInterval()
  │
  ▼
forever
```

Правильнее:

```text
Scheduler
   │
   ▼
Scheduled event
   │
   ▼
Service Worker
   │
   ▼
Task
```

---

# Scheduling abstraction

Можно сделать:

```text
scheduling/
    alarms.js
    scheduler.js
```

И application code:

```javascript
await scheduler.scheduleSync();
```

а конкретная реализация:

```text
scheduler
   ↓
chrome.alarms
```

---

# 13.8. Alarms

Для extension scheduling используется API:

```text
chrome.alarms
```

Например:

```javascript
chrome.alarms.create(
    "sync",
    {
        periodInMinutes: 30
    }
);
```

Затем:

```javascript
chrome.alarms.onAlarm.addListener(
    async alarm => {

        if (alarm.name === "sync") {
            await sync();
        }

    }
);
```

---

# Alarm как event source

Архитектурно:

```text
             chrome.alarms
                   │
                   ▼
                onAlarm
                   │
                   ▼
             Event Router
                   │
                   ▼
              SyncHandler
                   │
          ┌────────┴────────┐
          ▼                 ▼
       Network           Storage
```

Это намного лучше соответствует MV3, чем постоянный timer.

---

# Alarm names

Не следует использовать произвольные строки повсюду:

```javascript
"something"
"update"
"task"
```

Лучше централизовать:

```javascript
const ALARMS = {
    SYNC: "sync",
    CLEANUP: "cleanup",
    REFRESH: "refresh"
};
```

---

# Alarm handler

```javascript
chrome.alarms.onAlarm.addListener(
    async alarm => {

        switch (alarm.name) {

            case ALARMS.SYNC:
                await sync();
                break;

            case ALARMS.CLEANUP:
                await cleanup();
                break;
        }
    }
);
```

При большой системе лучше направлять события через отдельный router.

---

# Scheduling должен быть идемпотентным

Если задача синхронизации запускается повторно:

```text
SYNC
SYNC
```

результат не должен приводить к повреждению данных.

То есть:

```text
scheduled operation
        ↓
safe to repeat
```

---

# 13.9. Tabs

`chrome.tabs` — один из центральных API для browser extensions.

Он позволяет работать с вкладками:

```text
query
create
update
remove
reload
send messages
```

---

# Получение активной вкладки

Например:

```javascript
const tabs =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });
```

Получаем:

```javascript
const tab = tabs[0];
```

---

# Архитектурно Tabs — отдельный слой

Вместо:

```javascript
chrome.tabs.query(...)
```

в каждом handler:

```text
tabs/
    service.js
```

Например:

```javascript
export async function getActiveTab() {

    const tabs =
        await chrome.tabs.query({
            active: true,
            currentWindow: true
        });

    return tabs[0] ?? null;
}
```

---

# Tab lifecycle

Вкладки сами являются динамическими объектами.

Могут произойти:

```text
tab created
tab updated
tab navigated
tab reloaded
tab removed
```

Поэтому background architecture должна учитывать, что:

```text
tabId
```

не следует считать вечным идентификатором объекта.

---

# Tab events

Например:

```javascript
chrome.tabs.onUpdated.addListener(
    (tabId, changeInfo, tab) => {

        if (changeInfo.status === "complete") {
            // ...
        }

    }
);
```

Но не следует превращать `onUpdated` в универсальный event bus.

Нужно чётко определить:

```text
What event matters?
What state changed?
What action is required?
```

---

# Message to tab

Service Worker может взаимодействовать с Content Script через messaging.

Концептуально:

```text
Service Worker
      │
      │ message
      ▼
Content Script
```

Например:

```javascript
await chrome.tabs.sendMessage(
    tabId,
    {
        type: "SCAN_PAGE"
    }
);
```

Но Content Script может отсутствовать:

```text
tab exists
     ↓
content script does not exist
```

Поэтому architecture должна корректно обрабатывать такие случаи.

---

# 13.10. Windows

Browser extension работает не только с вкладками, но и с окнами браузера.

API:

```text
chrome.windows
```

Позволяет получать информацию о:

```text
browser windows
window state
focused window
tabs in window
```

---

# Window и Tab

Полезно понимать иерархию:

```text
Browser
 │
 ├── Window
 │    ├── Tab
 │    ├── Tab
 │    └── Tab
 │
 └── Window
      ├── Tab
      └── Tab
```

Поэтому architecture может выглядеть:

```text
Window Service
      │
      ▼
Tab Service
      │
      ▼
Content Script
```

---

# Получение текущего окна

Например:

```javascript
const window =
    await chrome.windows.getCurrent();
```

Для конкретных задач иногда удобнее использовать `tabs.query()` с подходящими параметрами, чем сначала получать окно, а затем искать вкладку.

---

# Почему Windows важны?

Некоторые extensions работают с:

```text
current window
focused window
all windows
window-specific state
```

Например, tab manager может хранить:

```text
Window A
 ├── Tab 1
 ├── Tab 2
 └── Tab 3

Window B
 ├── Tab 4
 └── Tab 5
```

---

# Window lifecycle

Окна также динамичны:

```text
created
focused
updated
removed
```

Поэтому:

```text
Window ID
```

также следует рассматривать как runtime identifier, а не как вечный объект.

---

# 13.11. Context coordination

Теперь мы можем объединить всё.

Современное extension может содержать:

```text
                    Extension
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
    Popup           Side Panel       Options
       │               │                │
       └───────────────┼────────────────┘
                       │
                    Messaging
                       │
                       ▼
                Service Worker
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
       Storage       Network       Browser
                                    │
                             ┌──────┴──────┐
                             ▼             ▼
                           Tabs         Windows
                             │
                             ▼
                       Content Scripts
```

Service Worker выступает координатором.

---

# Contexts не должны быть тесно связаны

Плохая архитектура:

```text
Popup
  ↓
directly controls everything
```

Например:

```text
Popup
 ↓
Storage
 ↓
Network
 ↓
Tabs
 ↓
Content Script
```

Popup становится центральным application runtime.

Это неправильно.

Popup — временный UI context.

Пользователь закрыл popup:

```text
Popup disappears
```

Extension не должен потерять application state.

---

# Правильная архитектура

```text
                  UI Contexts
               /      |       \
              /       |        \
          Popup     Options    SidePanel
              \       |        /
               \      |       /
                Messaging
                    │
                    ▼
             Service Worker
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     State       Network       Browser
        │                         │
        ▼                    ┌────┴────┐
     Storage                Tabs   Windows
```

---

# Service Worker как coordination hub

Service Worker может:

```text
receive command
      ↓
validate
      ↓
load state
      ↓
query tab
      ↓
send command to Content Script
      ↓
receive result
      ↓
process result
      ↓
save state
      ↓
notify UI
```

Это уже полноценная application architecture.

---

Представим extension:

> пользователь нажимает кнопку "Analyze Page".

---

## Шаг 1. Popup

Popup отправляет:

```javascript
{
    type: "ANALYZE_PAGE"
}
```

---

## Шаг 2. Service Worker

Получает сообщение:

```text
Popup
 ↓
Service Worker
```

---

## Шаг 3. Router

```text
ANALYZE_PAGE
      ↓
AnalysisHandler
```

---

## Шаг 4. Tabs

Handler получает текущую вкладку:

```text
AnalysisHandler
      ↓
TabService
      ↓
active tab
```

---

## Шаг 5. Content Script

Service Worker отправляет:

```text
SCAN_PAGE
```

```text
Service Worker
      │
      ▼
Content Script
```

---

## Шаг 6. Content Script

Content Script анализирует DOM:


# Context coordination — главное правило

Каждый context должен иметь **свою ответственность**.

Например:

| Context        | Основная роль                 |
| -------------- | ----------------------------- |
| Popup          | краткоживущий UI              |
| Options        | configuration UI              |
| Side Panel     | persistent-ish UI interaction |
| Content Script | работа с DOM страницы         |
| Service Worker | background coordination       |
| Storage        | durable state                 |

Это позволяет избежать архитектурного хаоса.

---

# Что не должен делать Popup

Popup не должен быть:

```text
database
background scheduler
network backend
global state manager
```

---

# Что не должен делать Content Script

Content Script не должен быть:

```text
persistent database
background scheduler
extension-wide state manager
```

Он прежде всего работает с:

```text
web page
DOM
page interaction
```

---

# Что не должен делать Service Worker

Service Worker также не должен превращаться в:

```text
UI
HTML renderer
giant business monolith
permanent process
```

Он должен **координировать**.

# Extension как распределённая система

Это один из наиболее важных архитектурных выводов.

Большое Manifest V3 extension можно рассматривать почти как **маленькую распределённую систему**.

У него есть:

```text

different lifecycles
```

# Главное правило

Не спрашивайте:

> «В какой файл положить `chrome.tabs`?»

Лучше спрашивать:

> «Какая ответственность у этого кода?»

Например:

```text
chrome.tabs.query()
```

сам по себе — API call.

Но:

```text
getCurrentPage()
```

— уже application capability.

Это важная разница.

# Итог главы

Background architecture Manifest V3 можно свести к следующей модели:

```text
                       BROWSER EVENTS
                              │
                              ▼
                      ┌──────────────┐
                      │ Event Router │
                      └──────┬───────┘
                             │
                             ▼
                     ┌──────────────┐
                     │Service Worker│
                     │ Orchestrator │
                     └──────┬───────┘
                            │
          ┌─────────────────┼──────────────────┐
          │                 │                  │
          ▼                 ▼                  ▼
      Messaging          Domain             Scheduler
          │                 │                  │
          │                 │                Alarms
          │                 │
          │         ┌───────┴───────┐
          │         │               │
          ▼         ▼               ▼
      Context    Storage         Network
   Coordination    │               │
          │        ▼               ▼
          │    Durable State   External APIs
          │
    ┌─────┼──────────┐
    ▼     ▼          ▼
 Popup  Content   Side Panel
        Script
          │
          ▼
         DOM
```

И несколько принципов становятся фундаментальными:

1. **Service Worker — orchestrator, а не монолит.**
2. **Events должны маршрутизироваться к специализированным handlers.**
3. **Messages следует рассматривать как внутренний API extension.**
4. **Durable state не должен зависеть от памяти Service Worker.**
5. **Storage и Network желательно скрывать за отдельными слоями.**
6. **Scheduling должен быть event-driven.**
7. **`chrome.alarms` подходит для extension scheduling лучше, чем попытка построить постоянный scheduler на `setInterval()`.**
8. **Tabs и Windows — динамические browser resources.**
9. **Каждый execution context должен иметь чёткую ответственность.**
10. **Contexts должны координироваться через сообщения и состояние, а не через предположение о совместной памяти или постоянной жизни друг друга.**

Самая важная архитектурная формула этой главы:

```text
Event
  ↓
Router
  ↓
Handler
  ↓
Domain Logic
  ↓
Services
  ↓
Storage / Network / Browser APIs
  ↓
Persistent Result
```

И именно такая модель позволяет превратить набор отдельных Manifest V3 API в **настоящую архитектуру браузерного приложения**, а не просто коллекцию обработчиков событий.
