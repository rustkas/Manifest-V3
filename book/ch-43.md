# Глава 43. Project 3 — Background Extension

В предыдущем проекте мы научились запускать **Content Script непосредственно внутри веб-страницы** и изменять её DOM.

Теперь сделаем следующий архитектурный шаг.

Создадим extension, в котором появится **Service Worker** — центральный background runtime Manifest V3.

Наш проект будет называться:

```text
Background Extension
```

Он будет демонстрировать взаимодействие сразу нескольких компонентов:

```text
┌─────────────────────────────────────────────┐
│                  Browser                    │
│                                             │
│  ┌──────────────┐      ┌───────────────┐   │
│  │ Action       │─────►│ Service       │   │
│  │              │      │ Worker        │   │
│  └──────────────┘      └───────┬───────┘   │
│                                │           │
│                                │ message   │
│                                ▼           │
│                         ┌───────────────┐  │
│                         │ Content       │  │
│                         │ Script       │  │
│                         └───────┬───────┘  │
│                                 │          │
│                                 ▼          │
│                               DOM          │
└─────────────────────────────────────────────┘
```

В этом проекте мы впервые создадим extension, построенное вокруг принципа:

> **Service Worker — orchestrator, а не постоянно работающий background application.**

---

# 43.1. Цель проекта

Наш extension будет выполнять простую задачу.

Пользователь нажимает кнопку extension:

```text
Extension Action
       ↓
Service Worker
       ↓
message
       ↓
Content Script
       ↓
DOM
       ↓
страница изменяется
```

Например, при нажатии на Action Content Script добавляет на страницу:

```text
┌────────────────────────────────────┐
│ Background Extension               │
│                                    │
│ Message received from Service      │
│ Worker                             │
└────────────────────────────────────┘
```

При повторном нажатии:

```text
Extension Action
       ↓
Service Worker
       ↓
message
       ↓
Content Script
       ↓
remove panel
```

Таким образом, Action сам не работает с DOM.

Он передаёт команду Service Worker.

Service Worker передаёт команду Content Script.

Content Script изменяет страницу.

---

# 43.2. Архитектура проекта

Наше extension будет состоять из трёх основных runtime-компонентов:

```text
┌──────────────┐
│ Action       │
│ user input   │
└──────┬───────┘
       │
       ▼
┌──────────────────┐
│ Service Worker   │
│ orchestration    │
└──────┬───────────┘
       │
       │ message
       ▼
┌──────────────────┐
│ Content Script   │
│ page integration │
└──────┬───────────┘
       │
       ▼
      DOM
```

Каждый компонент имеет свою ответственность.

| Component      | Ответственность          |
| -------------- | ------------------------ |
| Action         | пользовательская команда |
| Service Worker | orchestration            |
| Content Script | работа со страницей      |
| DOM            | состояние веб-страницы   |

Это уже гораздо ближе к production architecture.

# 43.5. Что такое `background.service_worker`

Поле:

```json
"background": {
    "service_worker": "background.js"
}
```

говорит браузеру:

> Используй `background.js` как Service Worker extension.

В Manifest V2 существовала модель постоянного background page.

В Manifest V3 background runtime построен вокруг Service Worker.

Концептуально:

```text
Manifest V2

Background Page
       │
       │
       ▼
    постоянно
    существует
```

В Manifest V3:

```text
Manifest V3

Service Worker
       │
       ▼
 event
       │
       ▼
 execute
       │
       ▼
 suspend
```

---

# 43.6. Service Worker не является обычной страницей

Очень важно не воспринимать:

```text
background.js
```

как:

```text
app.js
```

обычного web application.

Service Worker — это event-driven runtime.

Например:

```javascript
chrome.action.onClicked.addListener(
    (tab) => {
        // ...
    }
);
```

Здесь мы не запускаем:

```javascript
while (true) {
    // ...
}
```

и не ожидаем, что Service Worker будет постоянно выполнять код.

Вместо этого браузер активирует worker при необходимости.

# 43.18. Почему сообщение содержит `type`

Можно было бы написать:

```javascript
{
    action: "toggle"
}
```

Но лучше использовать:

```javascript
{
    type: "TOGGLE_PANEL"
}
```

`type` становится идентификатором сообщения.

Позже protocol может выглядеть так:

```javascript
{
    type: "TOGGLE_PANEL"
}

{
    type: "GET_STATE"
}

{
    type: "SET_STATE",
    payload: {
        enabled: true
    }
}

{
    type: "OPEN_SETTINGS"
}
```

Таким образом, message passing постепенно превращается в protocol.

---

# 43.19. Message как command

В нашем случае:

```javascript
{
    type: "TOGGLE_PANEL"
}
```

это фактически команда:

```text
Command:
TOGGLE_PANEL
```

Service Worker говорит Content Script:

> Выполни команду `TOGGLE_PANEL`.

Это хороший архитектурный подход.

Не нужно передавать JavaScript-код.

Нужно передавать **данные, описывающие намерение**.

---

# 43.20. Почему нельзя передавать функцию

Нельзя делать:

```javascript
{
    type: "RUN",
    function: () => {
        ...
    }
}
```

Message passing предназначен для передачи данных.

Правильнее:

```javascript
{
    type: "SET_COLOR",
    color: "blue"
}
```

а Content Script сам решает, как выполнить команду.

Получаем:

```text
Command
   ↓
Validation
   ↓
Handler
   ↓
Effect
```

---

# 43.21. Message schema

Наш первый message schema:

```text
TOGGLE_PANEL
```

не содержит payload.

Но можно создать более сложную структуру:

```javascript
{
    type: "SET_PANEL",
    payload: {
        visible: true,
        title: "Hello"
    }
}
```

Это уже напоминает API protocol.

---

# 43.22. Message validation

Content Script не должен безусловно доверять входящему сообщению.

Например:

```javascript
chrome.runtime.onMessage.addListener(
    (message) => {

        if (
            !message ||
            typeof message.type !== "string"
        ) {
            return;
        }

        if (
            message.type ===
            "TOGGLE_PANEL"
        ) {
            togglePanel();
        }
    }
);
```

Для маленького проекта этого достаточно.

В production application можно использовать более строгую схему.

# 43.23. Неизвестные сообщения

Хороший handler должен спокойно игнорировать неизвестные команды:

```javascript
switch (message.type) {

    case "TOGGLE_PANEL":
        togglePanel();
        break;

    default:
        console.warn(
            "Unknown message type:",
            message.type
        );
}
```

Это лучше, чем:

```javascript
throw new Error(...)
```

для любого неизвестного сообщения.

---

# 43.24. Почему Service Worker должен быть orchestrator

Можно было бы попытаться сделать всё в Content Script:

```text
Content Script
├── network
├── storage
├── tabs
├── business logic
├── DOM
└── UI
```

Но это быстро превращается в монолит.

Лучше:

```text
Service Worker
├── orchestration
├── state
├── network
├── scheduling
└── cross-context communication

Content Script
├── DOM
├── page events
└── page UI
```

Это разделяет responsibilities.

---

# 43.25. Action не должен напрямую управлять DOM

Action находится в другом extension context.

Поэтому архитектурно:

```text
Action
    │
    ▼
Service Worker
    │
    ▼
Content Script
    │
    ▼
DOM
```

лучше, чем попытка сделать Action центром всей системы.

Action — это **input surface**.

Content Script — **page integration layer**.

Service Worker — **orchestration layer**.

---

# 43.26. Что произойдёт, если Content Script отсутствует

Представим, пользователь находится на:

```text
chrome://extensions
```

или:

```text
https://another-domain.example/
```

где Content Script не был injected.

Service Worker выполнит:

```javascript
chrome.tabs.sendMessage(...)
```

но получит ошибку, потому что в этой вкладке нет получателя.

Поэтому мы используем:

```javascript
try {
    await chrome.tabs.sendMessage(...);
} catch (error) {
    ...
}
```

---

# 43.27. Это нормальная ситуация

Не следует считать отсутствие Content Script исключительной ошибкой.

Архитектура extension предполагает:

```text
Service Worker
      │
      ├── Tab A → Content Script
      │
      ├── Tab B → Content Script
      │
      ├── Tab C → no Content Script
      │
      └── Tab D → Content Script
```

Service Worker должен учитывать это.

# 43.29. Service Worker lifecycle

Теперь мы подошли к одному из самых важных принципов Manifest V3.

Нельзя предполагать:

```javascript
let counter = 0;
```

и считать:

```text
counter
```

вечным состоянием extension.

Service Worker может быть остановлен.

Например:

```text
Worker starts
     ↓
counter = 0
     ↓
events
     ↓
worker suspended
     ↓
worker terminated
     ↓
worker starts again
     ↓
counter = 0
```

Глобальная память worker не является persistent storage.

---

# 43.30. В нашем проекте это пока не заметно

Потому что сейчас Service Worker делает только:

```text
event
 ↓
send message
 ↓
finish
```

Это именно тот стиль работы, для которого MV3 Service Worker подходит особенно хорошо.

```text
Event
  ↓
Short task
  ↓
Return
```

---

# 43.31. Event-driven architecture

Наш extension теперь является event-driven системой.

Основное событие:

```text
action.onClicked
```

которое вызывает:

```text
sendMessage
```

а Content Script получает:

```text
runtime.onMessage
```

Получаем цепочку событий:

```text
User click
    ↓
Action event
    ↓
Service Worker handler
    ↓
Message
    ↓
Content Script event
    ↓
DOM update
```

---

# 43.32. Это уже distributed-like architecture

Наш extension физически находится внутри одного браузера.

Но логически:

```text
Action
Service Worker
Content Script
```

являются независимыми execution contexts.

Между ними нет общего JavaScript heap.

Поэтому:

```text
Context A
    │
    │ message
    ▼
Context B
```

в некотором смысле напоминает распределённую систему.

Именно поэтому:

* сообщения должны иметь schema;
* состояние нельзя считать глобальным;
* ошибки доставки нужно учитывать;
* lifecycle каждого context нужно понимать отдельно.

---

# 43.33. Добавляем response

До сих пор сообщение было one-way:

```text
Service Worker
      │
      ▼
Content Script
```

Теперь сделаем:

```text
Service Worker
      │
      │ request
      ▼
Content Script
      │
      │ response
      ▼
Service Worker
```

Например:

```javascript
const response =
    await chrome.tabs.sendMessage(
        tab.id,
        {
            type: "GET_PAGE_TITLE"
        }
    );

console.log(
    "Page title:",
    response.title
);
```

---

# 43.34. Handler с response

Content Script:

```javascript
chrome.runtime.onMessage.addListener(
    (message) => {

        if (
            message.type ===
            "GET_PAGE_TITLE"
        ) {
            return {
                title: document.title
            };
        }
    }
);
```

Однако для корректной работы с современными Promise-based API и более сложными асинхронными обработчиками лучше явно проектировать response protocol и учитывать ограничения конкретного browser API.

Для нашего первого проекта лучше использовать простой синхронный response.

# 43.36. Команды и запросы — разные вещи

Полезно различать:

### Command

```text
TOGGLE_PANEL
```

Означает:

> Сделай действие.

### Query

```text
GET_PAGE_TITLE
```

Означает:

> Верни данные.

### Mutation

```text
SET_PANEL_STATE
```

Означает:

> Измени состояние.

Это разделение становится очень полезным в больших extensions.

```javascript
                {
                    type: "SET_ENABLED",
                    enabled
                }
            );

            await chrome.action.setBadgeText({
                text: enabled
                    ? "ON"
                    : ""
            });

        } catch (error) {

            console.warn(
                "Content Script unavailable",
                error
            );
        }
    }
);
```

Теперь:

```text
Click
 ↓
enabled = true
 ↓
message
 ↓
Content Script
 ↓
UI ON
```

Повторный click:

```text
Click
 ↓
enabled = false
 ↓
message
 ↓
Content Script
 ↓
UI OFF
```

# 43.39. Но здесь есть архитектурная ошибка

Мы сделали:

```javascript
let enabled = false;
```

Это демонстрационный пример, но **не production state**.

Почему?

Потому что Service Worker ephemeral.

Если worker будет остановлен:

```text
enabled = false
```

будет потеряно.

В production нужно использовать:

```text
chrome.storage
```

для persistent state.

Это мы подробно будем изучать в части Storage.

# 43.40. Более правильная архитектура

В production:

```text
Action
   │
   ▼
Service Worker
   │
   ├── read state
   │       ↓
   │   chrome.storage
   │
   └── message
          ↓
    Content Script
```

То есть:


```javascript
let panel = null;

chrome.runtime.onMessage.addListener(
    (message) => {

        if (!message) {
            return;
        }

        switch (message.type) {

            case "TOGGLE_PANEL":
                togglePanel();
                break;

            default:
                console.warn(
                    "Unknown message:",
                    message.type
                );
        }
    }
);

    if (panel) {

        return;

        document.createElement("div");

        "background-extension-panel";

        "Hello from Service Worker";

    document.body.prepend(panel);
}
```

# 43.53. Следующий уровень

Пока коммуникация выглядит:

```text
Action
   ↓
Service Worker
   ↓
Content Script
```

Но реальное extension может иметь гораздо больше contexts:

```text
                       Service Worker
                     /       │       \
                    /        │        \
                   ▼         ▼         ▼
              Content      Side      Options
              Script      Panel       Page
                 │
                 ▼
              Web Page
```

И каждый context имеет:

* собственный lifecycle;
* собственную память;
* собственные API;
* собственные ограничения;
* собственные failure modes.

Поэтому следующий важный шаг — научиться проектировать **устойчивую коммуникационную архитектуру между несколькими contexts**.

Именно она превращает набор отдельных extension scripts в настоящее приложение.
