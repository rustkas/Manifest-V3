# Глава 1. Что такое Browser Extension

## 1.1. Расширение как отдельное приложение внутри браузера

Когда вы открываете веб-страницу, вы взаимодействуете с приложением, которое принадлежит конкретному сайту. Браузер выступает в роли среды исполнения для этого сайта.

Расширение — это принципиально иная сущность. Это **приложение, которое принадлежит вам (разработчику) и работает внутри браузера**, но не привязано к какому-либо конкретному сайту. Оно запускается в контексте браузера и имеет доступ к системным возможностям, недоступным обычным веб-страницам.

Представьте себе браузер как операционную систему, а расширения — как приложения, которые могут:
- Наблюдать за другими приложениями (вкладками)
- Модифицировать их поведение
- Добавлять новые возможности в среду
- Работать в фоне, даже когда пользователь находится на других сайтах

Расширение — это **суверенная единица программного обеспечения** внутри браузерной среды.

## 1.2. Extension Platform vs Web Platform

Чтобы понять, что такое расширение, необходимо осознать фундаментальное различие между двумя платформами, которые предоставляет браузер:

### Web Platform
- **Модель исполнения**: страница загружается, выполняется и уничтожается вместе с вкладкой
- **Модель безопасности**: изолированная среда (same-origin policy), доступ только к ресурсам своего происхождения
- **Срок жизни**: пока открыта вкладка
- **Доступ к системе**: минимальный (через ограниченные Web APIs)
- **Разрешения**: пользователь не даёт явных разрешений сайту
- **Цель**: отображение и интерактивность контента

### Extension Platform
- **Модель исполнения**: фоновый процесс (Service Worker) + множество контекстов
- **Модель безопасности**: расширение имеет собственное происхождение (extension://) и запрашивает явные разрешения
- **Срок жизни**: управляется браузером, может быть долгоживущим
- **Доступ к системе**: широкий (доступ ко всем вкладкам, истории, закладкам, сети)
- **Разрешения**: пользователь явно предоставляет расширению доступ к возможностям
- **Цель**: расширение функциональности самого браузера

Это различие критически важно, потому что оно определяет всё: от того, как вы пишете код, до того, как вы думаете о безопасности.

## 1.3. Из чего состоит современное расширение

Расширение Manifest V3 — это не монолит. Это **система взаимодействующих компонентов**, каждый из которых имеет свою роль, свой контекст выполнения и свои ограничения.

```javascript
// Это не один скрипт. Это оркестр.
```

Основные компоненты:

1. **Service Worker** (background) — "мозг" расширения. Единственный компонент, который может жить в фоне, обрабатывать события, управлять состоянием и координировать остальные части. Эфемерен — запускается по событию и может быть остановлен.

2. **Popup** — небольшое окно, которое появляется при клике на иконку расширения. Живёт только пока открыто. Интерфейс быстрого доступа.

3. **Content Scripts** — код, который внедряется в страницы сайтов. Живёт внутри страницы, но в изолированном мире. Получает доступ к DOM страницы.

4. **Options Page** — полноценная страница настроек расширения.

5. **Side Panel** — панель, закреплённая сбоку от основного окна браузера. Может существовать дольше, чем popup.

6. **DevTools Page** — интеграция с инструментами разработчика.

Эти компоненты не имеют общего состояния. Они общаются через **message passing**.

## 1.4. Extension Contexts

**Context (контекст)** — это одно из самых важных понятий в разработке расширений.

Контекст — это среда выполнения со своим:
- JavaScript environment (глобальный объект, scope)
- Доступом к API (разный набор доступен в разных контекстах)
- Сроком жизни
- Происхождением (origin)

Расширение — это **мультиконтекстное приложение**.

Когда вы пишете код для расширения, вы всегда должны задавать вопрос: **"В каком контексте это выполняется?"**

Потому что:
- `window` в content script — это не то же самое, что `window` в popup
- `localStorage` в Service Worker недоступен
- DOM API в Service Worker нет
- `chrome.runtime.sendMessage()` ведёт себя по-разному из разных контекстов

Игнорирование контекстов — основная причина багов в расширениях.

## 1.5. Почему Manifest V3 изменил архитектуру расширений

Manifest V3 — не просто новая версия формата. Это **смена архитектурной парадигмы**.

### Основные изменения:

| Аспект | MV2 | MV3 |
|--------|-----|-----|
| Background | Persistent background page | Ephemeral Service Worker |
| Сеть | `webRequest` (блокирующий) | `declarativeNetRequest` |
| Инъекция | `tabs.executeScript` | `scripting.executeScript` |
| Безопасность | `eval()` разрешён | `eval()` запрещён |
| Удалённый код | Можно загружать | Запрещён |
| Разрешения | Широкие | Принцип наименьших привилегий |

### Почему это произошло?

1. **Производительность** — persistent background pages потребляли память постоянно. Service Worker запускается по требованию.

2. **Безопасность** — удалённый код и `eval()` — векторы атак. MV3 ужесточает ограничения.

3. **Приватность** — пользователи должны знать, какие данные и когда расширение использует.

4. **Платформа** — браузеры движутся к модели, где больше логики выполняется на уровне браузера, а не в JavaScript (declarative APIs).

Manifest V3 требует **переосмысления** того, как вы проектируете расширение.

## 1.6. Жизненный цикл расширения

Расширение в MV3 имеет сложный жизненный цикл:

```
Установка → Регистрация Service Worker → Ожидание событий → 
Обработка события → Service Worker может быть остановлен → 
Повторный запуск при новом событии → ...
```

**Ключевые моменты:**

- **Service Worker не живёт постоянно** — он запускается, когда происходит событие (например, клик на иконку, вкладка обновлена), и может быть остановлен через несколько секунд бездействия.

- **Это не баг, это фича** — вы должны проектировать расширение так, чтобы оно не полагалось на постоянное состояние в памяти.

- **Состояние должно быть сохранено** — в `chrome.storage`, а не в глобальных переменных.

- **Расширение не перезапускается при остановке Service Worker** — оно просто «засыпает» и просыпается при необходимости.

Понять жизненный цикл — значит понять, почему ваши глобальные переменные исчезают, почему слушатели событий должны быть зарегистрированы на верхнем уровне, и почему вы не можете рассчитывать на `setTimeout` как на способ сохранить состояние.

## 1.7. Модель безопасности расширений

Безопасность в MV3 строится на нескольких уровнях:

### 1. Происхождение (Extension Origin)
Расширение имеет собственное происхождение `chrome-extension://<id>`. Это изолирует его от сайтов и других расширений.

### 2. Разрешения (Permissions)
Расширение запрашивает доступ к возможностям браузера. Пользователь должен явно одобрить эти запросы при установке. В MV3 — принцип наименьших привилегий (запрашивай только то, что нужно).

### 3. Content Security Policy
Строгая политика, запрещающая `eval()`, inline-скрипты и загрузку удалённого кода. Всё должно быть статически определено в пакете расширения.

### 4. Изоляция контекстов
Content scripts выполняются в **изолированном мире** — они имеют доступ к DOM страницы, но их JavaScript среда изолирована от скриптов страницы. Страница не может получить доступ к API расширения.

### 5. Trust Boundaries
Вы должны чётко разделять:
- **Доверенный код** — внутри расширения
- **Недоверенный контент** — страницы, с которыми расширение взаимодействует

Message passing между контекстами должен быть валидирован. Никогда не доверяйте данным из content script без проверки.

### 6. Удалённый код запрещён
В MV3 вы не можете загружать и выполнять JavaScript извне. Всё должно быть частью пакета расширения. Это радикально меняет подход к обновлениям и разработке.

## Итог: что важно усвоить из этой главы

1. **Расширение — это не сайт**. У него другая модель безопасности, другие возможности, другой срок жизни.

2. **Мультиконтекстность** — ключевая характеристика. Вы не работаете в единой среде; вы координируете множество изолированных сред.

3. **Service Worker — эфемерен**. Все архитектурные решения должны учитывать, что фон может «уснуть».

4. **Безопасность встроена в архитектуру**. MV3 вынуждает вас проектировать безопасно, ограничивая возможности, которые были векторами атак.

5. **Архитектура — это про границы**. Границы между контекстами, границы доверия, границы времени жизни. Умение управлять этими границами — главный навык разработчика расширений на Manifest V3.
