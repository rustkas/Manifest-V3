# Часть VII. Options и Side Panel

# Глава 19. Options Page

Options Page — это интерфейс настроек browser extension.

Если Popup отвечает прежде всего на вопрос:

> «Что пользователь хочет сделать **прямо сейчас**?»

то Options Page отвечает на другой вопрос:

> «**Как должно работать расширение?**»

Это принципиально разные UI roles.

Типичная архитектура может выглядеть так:

```text
                         Extension
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
        Popup             Options            Side Panel
          │                  │                  │
     quick actions       configuration      persistent UI
                             │
                             ▼
                        chrome.storage
```

Options Page обычно используется для настроек, которые:

* сохраняются между запусками;
* редко изменяются;
* имеют несколько параметров;
* требуют больше места, чем Popup;
* не должны зависеть от короткого lifecycle Popup.

---

# 19.1. Зачем нужна Options Page

У расширения почти всегда появляются настройки.

Например:

```text
General
────────────────────────

☑ Enable extension

Language:
[ English ▼ ]

Theme:
[ System ▼ ]

Notifications:
☑ Enable notifications

Scanning
────────────────────────

☑ Scan pages automatically

Interval:
[ 30 seconds ]

Advanced
────────────────────────

☐ Debug mode
```

Помещать такой интерфейс в Popup обычно неудобно.

Popup предназначен для быстрых действий:

```text
Open
 ↓
Understand
 ↓
Act
 ↓
Close
```

Options Page предназначена для настройки:

```text
Open
 ↓
Configure
 ↓
Save
 ↓
Leave
```

---

# Popup и Options Page

Полезно сразу установить архитектурное различие:

| UI             | Основная задача           |
| -------------- | ------------------------- |
| Action         | точка входа               |
| Popup          | быстрые действия          |
| Options Page   | конфигурация              |
| Side Panel     | длительное взаимодействие |
| Extension Page | полноценный UI            |

Например:

```text
Popup:

Scanner
────────────
Status: Ready

[ Start ]

12 items
```

А Options:

```text
Scanner Settings
────────────────────────

☑ Automatic scanning

Scan interval:
[ 30 seconds ]

Maximum items:
[ 100 ]

☑ Notifications

[ Save ]
```

---

# Options Page — не просто «ещё одна страница»

Options Page имеет особую семантику.

Она представляет **configuration layer** extension.

Можно представить архитектуру так:

```text
                 User
                  │
                  ▼
            Options Page
                  │
                  ▼
           Settings API
                  │
                  ▼
          chrome.storage
                  │
                  ▼
          Application State
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
      Popup    Service    Content
               Worker     Scripts
```

Options Page изменяет конфигурацию, а остальные contexts используют эту конфигурацию.

---

# 19.2. `options_page`

Manifest V3 поддерживает простой вариант указания Options Page:

```json
{
    "manifest_version": 3,

    "name": "My Extension",
    "version": "1.0.0",

    "options_page": "options.html"
}
```

Структура:

```text
extension/
│
├── manifest.json
│
├── options.html
├── options.css
└── options.js
```

---

# Минимальная Options Page

`options.html`:

```html
<!doctype html>

<html>
<head>
    <meta charset="utf-8">
    <title>Extension Settings</title>

    <link rel="stylesheet" href="options.css">
</head>

<body>

    <h1>Extension Settings</h1>

    <label>
        <input type="checkbox" id="enabled">
        Enable extension
    </label>

    <script type="module" src="options.js"></script>

</body>
</html>
```

JavaScript:

```javascript
const enabled = document.querySelector("#enabled");

enabled.addEventListener("change", async () => {

    await chrome.storage.local.set({
        enabled: enabled.checked
    });

});
```

---

# `options_page` — простой механизм

`options_page` говорит браузеру:

> «У этого extension есть страница настроек, находящаяся по этому URL».

Например:

```text
chrome-extension://<extension-id>/options.html
```

Браузер может открыть её как страницу настроек расширения.

---

# Ограничения простого `options_page`

`options_page` — минимальный механизм.

Он сообщает браузеру только:

```text
Options Page URL
```

Но не задаёт дополнительное поведение интерфейса.

Для более современной интеграции используется:

```text
options_ui
```

---

# 19.3. `options_ui`

`options_ui` позволяет объявить Options Page более декларативно.

Например:

```json
{
    "options_ui": {
        "page": "options.html",
        "open_in_tab": true
    }
}
```

Здесь:

```text
page
    ↓
options.html
```

а:

```text
open_in_tab
    ↓
browser tab
```

---

# `open_in_tab`

Это важный параметр.

Если:

```json
{
    "options_ui": {
        "page": "options.html",
        "open_in_tab": true
    }
}
```

то настройки открываются как обычная browser tab.

Условно:

```text
┌─────────────────────────────────────────────┐
│ Browser                                     │
├─────────────────────────────────────────────┤
│ Tab 1 │ Tab 2 │ Extension Settings         │
├─────────────────────────────────────────────┤
│                                             │
│        Extension Settings                   │
│                                             │
│        General                              │
│        Notifications                        │
│        Advanced                             │
│                                             │
└─────────────────────────────────────────────┘
```

Для сложных настроек это обычно гораздо удобнее Popup.

---

# `open_in_tab: false`

В таком случае браузер может использовать собственное представление Options Page в extension management UI.

Например:

```json
{
    "options_ui": {
        "page": "options.html",
        "open_in_tab": false
    }
}
```

Это особенно подходит для небольших настроек.

---

# `options_page` и `options_ui`

В современном Manifest V3 проекте обычно стоит предпочитать `options_ui`, когда вам нужна полноценная интеграция настроек с браузером.

Концептуально:

```text
options_page
    ↓
простое указание страницы
```

а:

```text
options_ui
    ↓
описание Options UI
```

Не следует без необходимости объявлять обе модели одновременно.

---

# Доступ к Options Page программно

Расширение может открыть страницу настроек через API:

```javascript
await chrome.runtime.openOptionsPage();
```

Например, Popup:

```javascript
document.querySelector("#settings")
    .addEventListener("click", async () => {

        await chrome.runtime.openOptionsPage();

    });
```

Архитектура:

```text
Popup
  │
  │ Settings
  ▼
runtime.openOptionsPage()
  │
  ▼
Options Page
```

Это очень удобный способ связать быстрый UI и конфигурацию.

---

# Почему лучше `openOptionsPage()`

Не стоит вручную строить URL:

```javascript
window.open(
    chrome.runtime.getURL("options.html")
);
```

если задача именно открыть страницу настроек.

Лучше использовать специализированный API:

```javascript
chrome.runtime.openOptionsPage();
```

Он выражает намерение явно:

> открыть Options Page этого extension.

# 19.4. Страница настроек

Options Page — это обычная extension page с точки зрения HTML/JavaScript.

Можно использовать:

* HTML;
* CSS;
* JavaScript;
* ES modules;
* DOM API;
* extension APIs;
* `chrome.storage`;
* messaging;
* другие разрешённые API.

Например:

```html
<section>
    <h2>General</h2>

    <label>
        <input type="checkbox" id="enabled">
        Enable extension
    </label>
</section>
```

---

# Settings form

Для настроек удобно использовать обычные HTML controls:

```html
<label>
    Theme:

    <select id="theme">
        <option value="system">System</option>
        <option value="light">Light</option>
        <option value="dark">Dark</option>
    </select>
</label>
```

И:

```html
<label>
    Maximum results:

    <input
        id="maxResults"
        type="number"
        min="1"
        max="1000"
    >
</label>
```

Это обычный Web Platform.

Не требуется специальный «Extension UI framework».

---

# HTML First

Для Manifest V3 очень естественный подход:

```text
HTML
 ↓
CSS
 ↓
DOM
 ↓
Web APIs
 ↓
Extension APIs
```

Например:

```javascript
const theme = document.querySelector("#theme");

theme.addEventListener("change", async () => {

    await chrome.storage.local.set({
        theme: theme.value
    });

});
```

Это обычный DOM event + extension storage.

---

# Автоматическое сохранение

Не обязательно иметь кнопку:

```text
[ Save ]
```

Настройки можно сохранять сразу:

```javascript
theme.addEventListener("change", async () => {

    await chrome.storage.local.set({
        theme: theme.value
    });

});
```

Получаем:

```text
User changes setting
        │
        ▼
change event
        │
        ▼
chrome.storage
```

Для небольших настроек это часто лучший UX.

---

# Или explicit Save

Для сложной формы можно использовать:

```text
[ Save changes ]
[ Cancel ]
```

Например:

```javascript
form.addEventListener("submit", async (event) => {

    event.preventDefault();

    await chrome.storage.local.set({
        theme: theme.value,
        enabled: enabled.checked
    });

});
```

Это особенно удобно, если несколько параметров должны изменяться как единая транзакция с точки зрения UI.

---

# Defaults

Очень важно определить значения по умолчанию.

Например:

```javascript
const DEFAULT_SETTINGS = {
    enabled: true,
    theme: "system",
    maxResults: 100
};
```

При загрузке:

```javascript
const settings = await chrome.storage.local.get(
    DEFAULT_SETTINGS
);
```

Если ключ отсутствует, используется default.

---

# Почему defaults важны

Нельзя рассчитывать, что:

```javascript
const settings = await chrome.storage.local.get();
```

вернёт полный объект настроек.

Пользователь мог:

* только что установить extension;
* удалить часть настроек;
* обновить extension;
* получить новую версию configuration schema.

Поэтому приложение должно иметь defaults.

---

# Settings schema

Лучше заранее определить структуру:

```javascript
const DEFAULT_SETTINGS = {
    enabled: true,
    theme: "system",
    notifications: true,
    scanInterval: 30
};
```

Тогда весь extension работает с понятной моделью:

```text
Settings
├── enabled
├── theme
├── notifications
└── scanInterval
```

---

# 19.5. Storage integration

Options Page практически всегда связана с Storage.

Основной API:

```text
chrome.storage
```

Наиболее часто используются:

```text
chrome.storage.local
chrome.storage.sync
```

---

# `storage.local`

```javascript
await chrome.storage.local.set({
    enabled: true
});
```

Получение:

```javascript
const result = await chrome.storage.local.get("enabled");

console.log(result.enabled);
```

---

# `storage.sync`

Если настройки должны синхронизироваться между браузерами пользователя, можно использовать:

```javascript
await chrome.storage.sync.set({
    theme: "dark"
});
```

Получение:

```javascript
const result = await chrome.storage.sync.get("theme");
```

Но `sync` следует использовать осознанно: это не замена обычной database, и для больших объёмов данных он не предназначен.

---

# `local` vs `sync`

Условно:

```text
storage.local
    ↓
локальное persistent storage

storage.sync
    ↓
настройки, которые имеет смысл синхронизировать
```

Например:

```text
local:
- cache
- large local data
- temporary persisted data

sync:
- theme
- language
- user preferences
```

Конкретный выбор зависит от данных.

---

# Options → Storage

Архитектура:

```text
┌──────────────────┐
│  Options Page    │
│                  │
│  checkbox        │
│  select          │
│  input           │
└────────┬─────────┘
         │
         │ set()
         ▼
┌──────────────────┐
│ chrome.storage   │
└────────┬─────────┘
         │
         ▼
 Application State
```

---

# Кто читает настройки?

Любой подходящий extension context может получать разрешённые storage data.

Например:

```text
             chrome.storage
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    Options       Popup     Service Worker
                               │
                               ▼
                         Content Scripts
```

Поэтому Options Page не должна передавать каждую настройку вручную всем остальным contexts.

Storage может быть общей точкой persistent configuration.

---

# Storage как source of truth

Для settings удобно использовать:

```text
chrome.storage
      │
      ▼
Settings source of truth
```

а не:

```text
Options variable
      ↓
Popup variable
      ↓
Service Worker variable
      ↓
Content Script variable
```

Последняя архитектура быстро приводит к рассинхронизации.

---

# Storage change events

Есть важный механизм:

```javascript
chrome.storage.onChanged
```

Он позволяет реагировать на изменение настроек.

Например:

```javascript
chrome.storage.onChanged.addListener(
    (changes, areaName) => {

        if (areaName !== "local") {
            return;
        }

        if (changes.theme) {
            console.log(
                "New theme:",
                changes.theme.newValue
            );
        }
    }
);
```

---

# Options и Service Worker

Service Worker может реагировать на изменение настроек:

```text
Options
   │
   │ set()
   ▼
chrome.storage
   │
   │ onChanged
   ▼
Service Worker
```

Например:

```javascript
chrome.storage.onChanged.addListener(
    (changes, area) => {

        if (area === "sync" && changes.enabled) {

            const enabled =
                changes.enabled.newValue;

            updateExtensionState(enabled);
        }
    }
);
```

---

# Это лучше, чем polling

Плохая модель:

```javascript
setInterval(async () => {

    const settings =
        await chrome.storage.local.get();

}, 1000);
```

Здесь extension постоянно спрашивает:

> «Изменились ли настройки?»

Лучше:

```text
settings changed
      ↓
event
      ↓
react
```

Это соответствует event-driven архитектуре Manifest V3.

---

# 19.6. Options lifecycle

Options Page имеет более длительный lifecycle, чем Popup.

Условно:

```text
User opens Settings
       │
       ▼
Options Page created
       │
       ▼
Load settings
       │
       ▼
Render UI
       │
       ▼
User edits
       │
       ▼
Save settings
       │
       ▼
Page remains open
       │
       ▼
User leaves
```

В отличие от Popup, Options Page обычно открывается как полноценная страница.

---

# Но Options Page тоже не persistent runtime

Это важно.

Нельзя делать:

```text
Options Page = always running
```

Пользователь может закрыть вкладку.

Поэтому важное состояние должно быть сохранено в:

```text
chrome.storage
```

а не только:

```javascript
let settings = {};
```

---

# Initialization

При загрузке страницы:

```javascript
async function init() {

    const settings = await chrome.storage.local.get(
        DEFAULT_SETTINGS
    );

    renderSettings(settings);
}

init();
```

Получаем:

```text
Options opens
     │
     ▼
load settings
     │
     ▼
render
```

---

# Save

После изменения:

```javascript
async function saveSettings(settings) {

    await chrome.storage.local.set(settings);

}
```

---

# Reload

Пользователь может:

```text
Open Options
 ↓
Change
 ↓
Close
 ↓
Open again
```

При повторном открытии:

```text
load from storage
```

и должен получить сохранённые настройки.

---

# Version update

Lifecycle становится интереснее после обновления extension.

Например, версия 1.0 имела:

```javascript
{
    enabled: true,
    theme: "dark"
}
```

Версия 2.0 добавила:

```javascript
{
    enabled: true,
    theme: "dark",
    notifications: true
}
```

Если пользователь обновил extension, старые данные могут не содержать:

```text
notifications
```

Поэтому defaults должны применяться и к старым данным.

---

# Settings migration

Для сложных extension полезно иметь версию схемы:

```javascript
{
    schemaVersion: 2,
    enabled: true,
    theme: "dark",
    notifications: true
}
```

При обновлении:

```text
schema v1
   ↓
migration
   ↓
schema v2
```

Это особенно важно для коммерческих extensions, которые могут жить годами.

# 19.7. Синхронизация настроек

Под синхронизацией можно понимать несколько разных вещей.

### 1. Storage sync

```text
chrome.storage.sync
```

Это синхронизация данных между поддерживаемыми browser profiles/environments.

---

### 2. Synchronization между contexts

Например:

```text
Options
   │
   ▼
Storage
   │
   ├── Popup
   ├── Service Worker
   └── Content Script
```

Это уже не обязательно network synchronization.

Это synchronization application state между extension contexts.

---

# `storage.onChanged`

Это один из лучших механизмов для такой синхронизации.

Например, пользователь изменил:

```text
Theme = Dark
```

в Options.

Происходит:

```text
Options
  │
  ▼
storage.sync.set()
  │
  ▼
storage.onChanged
  │
  ├── Popup
  ├── Service Worker
  └── other contexts
```

---

# Не копировать settings вручную

Плохой подход:

```text
Options
  │
  ├── send theme → Popup
  ├── send theme → Service Worker
  ├── send theme → Content Script
  └── send theme → Side Panel
```

Это создаёт множество каналов синхронизации.

Лучше:

```text
              Storage
                 │
      ┌──────────┼──────────┐
      ▼          ▼          ▼
   Popup       Worker    Content
```

Storage выступает как shared persistent configuration layer.

---

# Но storage не означает shared JavaScript state

Это принципиально.

Мы не получаем:

```javascript
// magic shared object

settings.theme
```

одновременно доступный во всех contexts.

Каждый context имеет собственный JavaScript environment.

Общим является не object reference, а **persisted data**.

```text
Context A
   │
   │ write
   ▼
Storage
   │
   │ read
   ▼
Context B
```

---

# Configuration synchronization model

Хорошая модель:

```text
                 ┌─────────────┐
                 │   Storage   │
                 └──────┬──────┘
                        │
             ┌──────────┼──────────┐
             ▼          ▼          ▼
         Options      Worker      Popup
             │          │
             │          │
             └────change┘
```

Storage является устойчивой точкой.

---

# Нужно ли использовать `storage.sync` для всех настроек?

Нет.

Например, если extension сохраняет:

```text
10 MB cache
```

не стоит автоматически помещать его в sync storage только потому, что он доступен.

Sync следует использовать прежде всего для данных, которые действительно имеют смысл синхронизировать.

---

# User preferences

Хорошие кандидаты:

```text
language
theme
enabled
notification preferences
UI preferences
```

Например:

```javascript
await chrome.storage.sync.set({
    theme: "dark",
    language: "en",
    notifications: true
});
```

---

# Local application data

Например:

```text
cache
recent results
local indexes
large datasets
```

может быть разумнее хранить локально:

```javascript
await chrome.storage.local.set({
    cache: data
});
```

Конкретная архитектура зависит от размера и характера данных.

# 19.8. Settings architecture

Теперь можно построить полноценную архитектуру настроек.

Предположим, у нас есть:

```text
enabled
theme
language
notifications
scanInterval
```

Создадим schema:

```javascript
const DEFAULT_SETTINGS = {
    enabled: true,
    theme: "system",
    language: "en",
    notifications: true,
    scanInterval: 30
};
```

---

# Settings Repository

Вместо того чтобы обращаться к Storage из каждого компонента напрямую, можно создать небольшой abstraction layer:

```javascript
export async function getSettings() {

    return chrome.storage.sync.get(
        DEFAULT_SETTINGS
    );
}
```

И:

```javascript
export async function updateSettings(
    changes
) {

    await chrome.storage.sync.set(changes);

}
```

Теперь:

```text
Options
   │
   ▼
Settings API
   │
   ▼
chrome.storage
```

---

# Почему abstraction полезна?

Без него код быстро превращается в:

```javascript
chrome.storage.sync.get(...)
chrome.storage.sync.set(...)
chrome.storage.sync.get(...)
chrome.storage.local.get(...)
chrome.storage.sync.set(...)
```

в десятках файлов.

Лучше иметь единый слой:

```text
settings/
├── defaults.js
├── repository.js
└── schema.js
```

---

# Пример

`defaults.js`:

```javascript
export const DEFAULT_SETTINGS = {
    enabled: true,
    theme: "system",
    language: "en",
    notifications: true,
    scanInterval: 30
};
```

`repository.js`:

```javascript
import {
    DEFAULT_SETTINGS
} from "./defaults.js";

export async function getSettings() {

    return chrome.storage.sync.get(
        DEFAULT_SETTINGS
    );
}

export async function updateSettings(
    changes
) {

    await chrome.storage.sync.set(changes);

}
```

Теперь Options:

```javascript
import {
    getSettings,
    updateSettings
} from "./settings/repository.js";
```

---

# Settings как отдельный слой

Получаем:

```text
                  UI
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      Popup     Options    Side Panel
        │          │          │
        └──────────┼──────────┘
                   ▼
             Settings API
                   │
                   ▼
             chrome.storage
```

Это гораздо более масштабируемая архитектура.

---

# Options Page не должна знать о business logic

Например, плохой код:

```javascript
button.addEventListener("click", async () => {

    const settings =
        await chrome.storage.sync.get();

    if (settings.enabled) {

        // 200 lines of scanner logic

    }

});
```

Options Page должна заниматься:

```text
render
input
validation
save
```

А не бизнес-логикой extension.

---

# Правильное разделение

```text
Options
 ├── renderSettings()
 ├── readForm()
 ├── validateSettings()
 └── saveSettings()

Settings Layer
 ├── getSettings()
 └── updateSettings()

Service Worker
 └── application logic
```

---

# Validation

Settings должны валидироваться.

Например:

```javascript
function validateSettings(settings) {

    if (
        settings.scanInterval < 5 ||
        settings.scanInterval > 3600
    ) {
        throw new Error(
            "Invalid scan interval"
        );
    }

}
```

Нельзя полностью полагаться на HTML:

```html
<input
    type="number"
    min="5"
    max="3600"
>
```

Потому что данные могут поступить из другого context.

---

# Почему validation нужна не только в Options

Потому что Settings могут быть изменены:

```text
Options
Popup
Service Worker
Migration
Old version
External workflow
```

Поэтому application layer должен иметь собственные гарантии.

---

# Settings и security

Настройки не следует автоматически считать trusted input.

Например:

```javascript
{
    endpoint: "..."
}
```

Если extension позволяет пользователю задавать URL, его нужно обрабатывать безопасно.

Особенно важно, если настройка влияет на:

* network requests;
* script injection;
* DOM insertion;
* permissions;
* navigation.

---

# Settings и permissions

Settings Page не должна использоваться как способ обхода permission model.

Например, нельзя сделать:

```text
User enters arbitrary domain
       ↓
Extension accesses everything
```

Если соответствующий доступ не разрешён архитектурой extension.

Permissions остаются отдельным security boundary.

---

# Settings и Content Scripts

Content Script может читать configuration:

```javascript
const settings =
    await chrome.storage.sync.get({
        enabled: true
    });
```

Но если логика сложная, лучше:

```text
Content Script
      │
      ▼
Service Worker
      │
      ▼
Settings
```

Конкретный выбор зависит от требований.

---

# Settings change propagation

Представим:

```text
Options:
notifications = true
```

Пользователь изменяет:

```text
notifications = false
```

Происходит:

```text
Options
   │
   ▼
Settings Repository
   │
   ▼
chrome.storage
   │
   ▼
storage.onChanged
   │
   ├── Service Worker
   ├── Popup
   └── Side Panel
```

Каждый context обновляет только своё представление.

---

# Settings event bus

Для большого extension можно дополнительно создать внутренний abstraction:

```text
Settings Store
      │
      ▼
Settings Changed
      │
 ┌────┼────┐
 ▼    ▼    ▼
SW  Popup  Panel
```

Но не следует создавать отдельный event bus только ради настроек, если `chrome.storage.onChanged` уже полностью решает задачу.

---

# Single Source of Truth

Это, пожалуй, главный архитектурный принцип Options Page:

> **Settings должны иметь один canonical source of truth.**

Например:

```text
chrome.storage.sync
```

Тогда:

```text
Options
    ↓
writes

Popup
    ↓
reads

Service Worker
    ↓
reads

Content Script
    ↓
reads
```

Все contexts работают с одной конфигурацией.

---

# Options Page как Configuration UI

В результате роль Options Page можно сформулировать следующим образом:

```text
                Options Page
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Display     Input     Validation
          │          │          │
          └──────────┼──────────┘
                     ▼
              Settings API
                     │
                     ▼
              chrome.storage
                     │
                     ▼
             Application State
```

Options Page **не является центром приложения**.

Она является интерфейсом конфигурации.

# Главные правила главы

## Правило 1. Options Page — для конфигурации

```text
Popup
→ What do I do now?

Options
→ How should extension work?
```

---

## Правило 2. Настройки должны быть persistent

Не:

```javascript
let settings = {};
```

а:

```text
chrome.storage
```

---

## Правило 3. Используйте `options_ui`

Для современной Manifest V3 архитектуры это основной декларативный способ описания Options UI:

```json
{
    "options_ui": {
        "page": "options.html",
        "open_in_tab": true
    }
}
```

---

## Правило 4. Используйте `runtime.openOptionsPage()`

Если другой UI должен открыть настройки:

```javascript
await chrome.runtime.openOptionsPage();
```

---

## Правило 5. Используйте defaults

```javascript
const DEFAULT_SETTINGS = {
    enabled: true,
    theme: "system"
};
```

Настройки никогда не должны предполагаться полностью заполненными.

---

## Правило 6. Используйте `storage.onChanged`

Для реакции на изменения:

```javascript
chrome.storage.onChanged.addListener(
    (changes, area) => {
        // react
    }
);
```

Это лучше постоянного polling.

---

## Правило 7. Разделяйте UI и settings layer

```text
Options UI
     ↓
Settings API
     ↓
Storage
```

---

## Правило 8. Settings имеют один source of truth

Не создавайте отдельные независимые копии конфигурации в каждом context.

```text
              Storage
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
     Popup       SW      Content
```

# Итог

Options Page — это не «большой Popup».

Это отдельный архитектурный слой расширения, предназначенный для **долгоживущей конфигурации**.

Её естественная роль:

```text
User
 │
 ▼
Options Page
 │
 ▼
Settings
 │
 ▼
chrome.storage
 │
 ├── Service Worker
 ├── Popup
 ├── Content Scripts
 └── Side Panel
```

Главное различие с Popup заключается в намерении пользователя и lifecycle.

**Popup** предназначен для краткого взаимодействия:

```text
Open → Act → Close
```

**Options Page** предназначена для конфигурации:

```text
Open → Configure → Persist → Leave
```

Именно поэтому в хорошо спроектированном Manifest V3 extension Options Page не содержит основную бизнес-логику. Она изменяет **configuration state**, а остальные части расширения используют эту конфигурацию независимо от того, открыта сейчас страница настроек или нет.

В следующей главе логично перейти к **Side Panel** — UI surface, которая занимает промежуточное положение между краткоживущим Popup и полноценной Extension Page и особенно хорошо подходит для длительного взаимодействия с расширением.
