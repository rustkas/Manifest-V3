# Глава 45. Project 5 — Side Panel Application

В предыдущем проекте мы создали первое относительно полноценное productivity extension:

```text
Popup
   ↓
Service Worker
   ↓
Content Script
   ↓
DOM

Storage
   ↑
persistent state
```

Но у Popup есть фундаментальное ограничение: **он является временным интерфейсом**.

Если пользователь хочет работать с расширением несколько минут, постоянно наблюдать состояние текущей страницы, переключаться между вкладками и управлять данными, Popup быстро становится неудобным.

Для такого сценария Manifest V3 предоставляет **Side Panel**.

В этой главе мы построим полноценное Side Panel application:

> **Focus Workspace**

Приложение будет находиться в боковой панели браузера и работать одновременно с:

* текущей вкладкой;
* несколькими вкладками;
* Content Scripts;
* Service Worker;
* `chrome.tabs`;
* `chrome.storage`;
* message passing.

Именно здесь мы впервые увидим extension не как «маленькую кнопку браузера», а как **постоянно работающий multi-context application**.

# 45.2. Почему Side Panel вместо Popup

Popup отлично подходит для:

```text
ON/OFF
small settings
quick action
status
```

Например:

```text
┌────────────────────┐
│ Focus Mode         │
│                    │
│ [ ON ]             │
│                    │
└────────────────────┘
```

Но если UI должен оставаться открытым:

```text
User
  ↓
works on page
  ↓
looks at extension
  ↓
changes state
  ↓
switches tab
  ↓
looks at extension again
```

Popup неудобен.

Его lifecycle:

```text
open
 ↓
use
 ↓
close
```

Side Panel:

```text
open
 ↓
use
 ↓
switch tabs
 ↓
use
 ↓
continue working
```

Поэтому Side Panel подходит для:

* productivity tools;
* research tools;
* AI assistants;
* note-taking;
* tab managers;
* developer tools;
* shopping assistants;
* CRM extensions;
* page analysis;
* persistent workflows.

# 45.9. Side Panel lifecycle

Side Panel имеет собственный execution context.

Когда Side Panel открывается:

```text
sidepanel.html
       ↓
sidepanel.js
       ↓
DOM
```

Как и Popup, Side Panel не является Content Script.

У него собственный:

```text
window
document
global scope
JavaScript state
```

Но отличие в UX заключается в том, что Side Panel предназначен для более длительной работы.

# 45.10. Первое состояние Side Panel

Нам нужно хранить:

```text
currentTab
focusedTabs
```

Например:

```javascript
{
    focusedTabs: {
        "101": true,
        "203": true
    }
}
```

Однако здесь возникает важный вопрос.

Нужно ли хранить `currentTab` в Storage?

Нет.

`currentTab` — это runtime state.

Он определяется браузером.

Поэтому:

```text
Persistent state
    ↓
focusedTabs

Runtime state
    ↓
currentTab
```

Это важное архитектурное разделение.

# 45.15. Отображение списка вкладок

```javascript
async function renderTabs() {

    const tabs =
        await getTabs();

    const list =
        document.querySelector(
            "#tabList"
        );

    list.replaceChildren();

    for (const tab of tabs) {

        const item =
            document.createElement(
                "li"
            );

        item.textContent =
            tab.title ||
            tab.url ||
            "Untitled";

        if (tab.active) {
            item.classList.add(
                "active"
            );
        }

        item.addEventListener(
            "click",
            async () => {

                if (
                    typeof tab.id !==
                    "number"
                ) {
                    return;
                }

                await chrome.tabs.update(
                    tab.id,
                    {
                        active: true
                    }
                );
            }
        );

        list.appendChild(item);
    }
}
```

Теперь Side Panel становится простым tab manager.

# 45.17. Tab events

Но список вкладок может измениться.

Например:

```text
User opens tab
User closes tab
User switches tab
User navigates
```

Side Panel должен реагировать.

Для этого есть события `chrome.tabs`.

Например:

```javascript
chrome.tabs.onActivated.addListener(
    async () => {

        await renderCurrentTab();

        await renderTabs();

        await renderFocusState();
    }
);
```

Но здесь возникает проблема.

Side Panel context должен подписываться на события, доступные ему напрямую, либо использовать Service Worker как централизованный event router.

Для более масштабируемой архитектуры мы выберем второй вариант.

---

# 45.18. Service Worker как Browser Event Router

Service Worker будет слушать:

```text
tabs.onActivated
tabs.onUpdated
tabs.onCreated
tabs.onRemoved
```

и уведомлять Side Panel.

Архитектура:

```text
Browser
   │
   ▼
Service Worker
   │
   │ event
   ▼
Side Panel
```

Это соответствует общей архитектуре:

> Browser events → Service Worker → application contexts.

В `background.js`:

```javascript
chrome.tabs.onActivated.addListener(
    async (activeInfo) => {

        await notifySidePanel({
            type: "ACTIVE_TAB_CHANGED",
            tabId: activeInfo.tabId
        });
    }

```

# 45.20. Передача события Side Panel

Service Worker может отправить сообщение:

```javascript
async function notifySidePanel(
    message
) {

    try {

        await chrome.runtime.sendMessage(
            message
        );

    } catch (error) {

        // Side Panel may not be open.
    }
}
```

Важно:

> Side Panel может быть закрыта.

Поэтому ошибка доставки сообщения не обязательно означает ошибку приложения.

# 45.27. Изменение Storage

```javascript
async function setTabFocus(
    tabId,
    enabled
) {

    if (
        typeof tabId !==
        "number"
    ) {
        return;
    }

    const state =
        await chrome.storage.local.get({
            focusedTabs: {}
        });

    const focusedTabs =
        state.focusedTabs;

    const key =
        String(tabId);

    if (enabled) {

        focusedTabs[key] = true;

    } else {

        delete focusedTabs[key];
    }

    await chrome.storage.local.set({
        focusedTabs
    });
}
```

Теперь Service Worker является владельцем mutation.


для Content Script.

# 45.32. Request/Response

Обработчик:

```javascript
case "GET_TAB_FOCUS_STATE": {

    const tabId =
        sender.tab?.id;

    if (
        typeof tabId !== "number"
    ) {
        return {
            enabled: false
        };
    }

    const state =
        await chrome.storage.local.get({
            focusedTabs: {}
        });

    return {
        enabled:
            Boolean(
                state.focusedTabs[
                    String(tabId)
                ]
            )
    };
}
```

Здесь мы используем request/response model.

# 45.33. Важный нюанс async messaging

При работе с `chrome.runtime.onMessage` нужно учитывать особенности асинхронного ответа.

Для максимально предсказуемой архитектуры можно использовать:

```text
message
  ↓
handler
  ↓
response
```

и соблюдать правила конкретного browser API.

В больших приложениях message protocol лучше централизовать, а не писать десятки независимых обработчиков.

# 45.34. Side Panel получает состояние

В `sidepanel.js`:

```javascript
async function getCurrentFocusState() {

    const tab =
        await getCurrentTab();

    if (
        !tab ||
        typeof tab.id !== "number"
    ) {
        return false;
    }

    const state =
        await chrome.runtime.sendMessage({
            type:
                "GET_TAB_FOCUS_STATE",
            tabId: tab.id
        });

    return Boolean(
        state?.enabled
    );
}
```

# 45.39. Storage change events

Теперь Side Panel может реагировать на изменения Storage:

```javascript
chrome.storage.onChanged.addListener(
    (
        changes,
        areaName
    ) => {

        if (
            areaName !== "local"
        ) {
            return;
        }

        if (
            changes.focusedTabs
        ) {

            renderFocusState();
            renderFocusedCount();
            renderTabs();
        }
    }

```

Получаем реактивную модель:

```text
             Storage
                │
                │ change
       ┌────────┼─────────┐
       ▼        ▼         ▼

```

# 45.40. Почему это лучше прямого обновления UI

Представим:

```text
Side Panel
     ↓
set state
```

Если UI вручную обновляется только после этой команды, состояние может стать рассинхронизированным.

Например, изменение произошло из другого context.

Storage event позволяет построить:

```text
State changed
     ↓
Subscribers react
```

То есть:

```text
State
  ↓
Event
  ↓
UI
```

# 45.42. Очистка состояния при закрытии Tab

Service Worker может использовать:

```javascript
chrome.tabs.onRemoved.addListener(
    async (tabId) => {

        const state =
            await chrome.storage.local.get({
                focusedTabs: {}
            });

        const focusedTabs =
            state.focusedTabs;

        delete focusedTabs[
            String(tabId)
        ];

        await chrome.storage.local.set({
            focusedTabs
        });

);
```

Теперь:

```text

    ↓

    ↓
remove tab state
    ↓
Storage
```

Это называется **state cleanup**.

# 45.49. Полный message protocol

```text

│ Message                │ Sender        │ Receiver       │
├────────────────────────┼───────────────┼────────────────┤
│ GET_TAB_FOCUS_STATE    │ Content      │ Worker         │
│ GET_TAB_FOCUS_STATE    │ Side Panel   │ Worker         │
```

# 45.50. Почему нужен message protocol

Без протокола быстро появляется:

```javascript

    foo: "bar"
```

```text

action
command
event
type
data
payload
```

становятся неуправляемыми.

Лучше использовать:

```javascript

    type: "SET_TAB_FOCUS",
    tabId: 123,
    enabled: true
}
```

То есть каждое сообщение должно иметь:

```text

```

и чётко определённый payload.
