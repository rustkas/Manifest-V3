# Глава 26. Declarative APIs как новый runtime

В предыдущих главах мы рассмотрели отдельные Declarative APIs Manifest V3:

* `declarativeContent`;
* `declarativeNetRequest`;
* rulesets;
* static rules;
* dynamic rules;
* session rules.

Теперь необходимо сделать следующий шаг и посмотреть на них не как на набор отдельных API, а как на **новую архитектурную модель выполнения extension**.

Это принципиально важно.

В традиционной модели расширение можно было представить следующим образом:

```text
Browser
   ↓
Event
   ↓
JavaScript
   ↓
Application logic
   ↓
Decision
   ↓
Browser API
```

В декларативной модели появляется другой путь:

```text
Developer
    ↓
Policy
    ↓
Rules
    ↓
Browser Engine
    ↓
Execution
```

То есть JavaScript постепенно перестаёт быть единственным местом, где находится runtime logic.

Возникает новая идея:

> **Declarative rules становятся частью runtime extension.**

Именно эту идею мы подробно разберём в данной главе.

---

# 26.1. Перенос логики из JavaScript в browser engine

Начнём с фундаментального изменения.

## Imperative extension

В imperative architecture разработчик описывает **алгоритм**.

Например:

```javascript
chrome.webRequest.onBeforeRequest.addListener(
    request => {

        if (request.url.includes("tracker")) {
            return { cancel: true };
        }

    },
    { urls: ["<all_urls>"] },
    ["blocking"]
);
```

Здесь extension получает request и самостоятельно принимает решение.

То есть:

```text
Request
   ↓
JavaScript
   ↓
if (...)
   ↓
Decision
   ↓
Action
```

JavaScript является runtime.

---

# Declarative extension

В декларативной модели мы описываем не алгоритм, а **политику**:

```json
{
  "id": 100,
  "priority": 1,
  "action": {
    "type": "block"
  },
  "condition": {
    "urlFilter": "tracker"
  }
}
```

Теперь архитектура:

```text
Rule
 ↓
Browser DNR engine
 ↓
Request matching
 ↓
Block
```

JavaScript вообще не обязан выполняться для каждого request.

---

# Это не просто другой синтаксис

Очень важно не воспринимать declarative API как:

> "тот же JavaScript, только в JSON".

Это было бы слишком поверхностное понимание.

Разница находится на уровне **execution ownership**.

В imperative модели:

```text
Extension owns execution
```

В declarative модели:

```text
Browser owns execution
```

Extension предоставляет policy.

Browser предоставляет execution engine.

---

# Смена ownership

Можно представить эволюцию следующим образом:

```text
                    MV2
                     │
                     ▼
             Extension JavaScript
                     │
                     ▼
              Browser decision
```

и:

```text
                    MV3
                     │
                     ▼
                Extension
                     │
              declares policy
                     │
                     ▼
              Browser engine
                     │
              executes policy
```

Это одно из наиболее важных архитектурных изменений Manifest V3.

---

# Почему браузер должен выполнять эту работу

Браузер знает гораздо больше о собственном runtime, чем extension.

Например browser engine уже контролирует:

* network stack;
* tabs;
* frames;
* navigation;
* security policies;
* resource loading;
* lifecycle;
* permissions.

Поэтому если определённую операцию можно выразить как policy, браузеру часто эффективнее выполнить её самостоятельно.

---

# Пример

Допустим, необходимо заблокировать:

```text
https://tracker.example.com/*
```

Imperative подход:

```text
100 requests
       ↓
100 callbacks
       ↓
100 JavaScript executions
       ↓
100 decisions
```

Declarative:

```text
100 requests
       ↓
Browser rule engine
       ↓
matching
       ↓
block
```

Вторая модель позволяет не превращать каждый request в событие для application runtime.

---

# Declarative APIs как browser capabilities

Таким образом:

```text
DNR
```

можно рассматривать как:

> browser-native network policy engine.

А:

```text
declarativeContent
```

как:

> browser-native page activation policy engine.

Это уже больше похоже не на набор JavaScript APIs, а на систему **browser capabilities**.

---

# 26.2. Compile-time generation of rules

Здесь появляется очень интересная концепция.

Если rules являются runtime representation политики, то возникает вопрос:

> Откуда эти rules берутся?

Для простого extension разработчик может написать их вручную.

Но для сложного extension правила могут быть **сгенерированы автоматически**.

---

# Source → Rules

Например:

```text
Configuration
     ↓
Compiler
     ↓
DNR Rules
```

Или:

```text
Filter List
     ↓
Parser
     ↓
Intermediate Representation
     ↓
Optimizer
     ↓
DNR Rules
```

Это уже напоминает настоящий compiler pipeline.

---

# Пример

Допустим, пользовательский язык policy выглядит так:

```text
BLOCK tracker.example.com
BLOCK ads.example.com
ALLOW tracker.example.com on trusted.example.com
```

Это не обязательно непосредственно DNR.

Можно определить собственный internal representation:

```json
{
  "policies": [
    {
      "effect": "block",
      "domain": "tracker.example.com"
    },
    {
      "effect": "block",
      "domain": "ads.example.com"
    },
    {
      "effect": "allow",
      "domain": "tracker.example.com",
      "initiator": "trusted.example.com"
    }
  ]
}
```

А затем скомпилировать это в DNR rules.

---

# Compiler pipeline

Получается:

```text
Human / Application Policy
            ↓
          Parser
            ↓
     Internal Representation
            ↓
         Validation
            ↓
        Optimization
            ↓
          Compiler
            ↓
       DNR Rules
            ↓
       Browser Engine
```

Это очень мощная архитектурная модель.

---

# Почему compile-time важен

Если policy можно вычислить заранее, нет необходимости вычислять её при каждом request.

Вместо:

```text
Request
 ↓
Compute policy
 ↓
Decision
```

получаем:

```text
Compile policy
 ↓
Rules
 ↓
Request
 ↓
Fast matching
```

---

# Compile once, execute many times

Это классический принцип compiler architecture:

```text
expensive work
     ↓
do once

cheap execution
     ↓
repeat many times
```

Для сетевого filtering это особенно важно.

Например:

```text
1 000 000 requests
```

могут быть обработаны на основании заранее подготовленной policy.

---

# Static generation

Самый простой вариант:

```text
Source
 ↓
Build
 ↓
rules.json
 ↓
Extension package
```

Например:

```text
src/
   policy/
      trackers.txt

build/
   rules/
      trackers.json
```

---

# Runtime generation

Но compile-time generation не означает, что всё должно происходить только во время build.

Можно иметь:

```text
User configuration
       ↓
Runtime compiler
       ↓
Dynamic rules
```

Например:

```text
User:
Block example.com
```

Service Worker может:

```text
parse
→ validate
→ compile
→ install dynamic rule
```

---

# Hybrid architecture

Для сложного extension наиболее интересна гибридная модель:

```text
                Policy
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
   Build-time              Runtime
    compiler                compiler
        │                     │
        ▼                     ▼
 Static rules           Dynamic rules
        │                     │
        └──────────┬──────────┘
                   ▼
              Browser engine
```

---

# 26.3. Минимизация background JavaScript

Теперь мы приходим к Service Worker.

В Manifest V3 Service Worker является ephemeral runtime.

Поэтому возникает естественный архитектурный вопрос:

> Зачем заставлять Service Worker выполнять работу, которую браузер способен выполнить сам?

---

# Плохая архитектура

Представим:

```text
Network
   ↓
Service Worker
   ↓
JavaScript
   ↓
Matching engine
   ↓
Decision
```

Service Worker превращается в:

```text
network runtime
```

Это плохое использование его роли.

---

# Лучше

```text
Service Worker
      │
      ├── configuration
      ├── rule management
      ├── user actions
      └── orchestration
              │
              ▼
             DNR
              │
              ▼
           Network
```

Service Worker не обрабатывает каждый request.

Он управляет policy.

---

# Service Worker как control plane

Это можно описать терминами distributed systems.

Service Worker:

> **control plane**

DNR engine:

> **data plane**

---

# Control plane

Service Worker:

```text
configure
manage
update
coordinate
persist
```

---

# Data plane

DNR:

```text
match
block
redirect
modify
```

---

# Архитектура

```text
             CONTROL PLANE
        ┌─────────────────────┐
        │   Service Worker    │
        │                     │
        │ configuration       │
        │ policy management   │
        │ user actions        │
        └──────────┬──────────┘
                   │
                   │ rules
                   ▼
             DATA PLANE
        ┌─────────────────────┐
        │      DNR Engine     │
        │                     │
        │ matching            │
        │ blocking            │
        │ redirecting         │
        └──────────┬──────────┘
                   │
                   ▼
                Network
```

Это очень хорошая архитектурная модель для MV3.

---

# Минимальный background runtime

Хорошее MV3 extension должно стремиться к тому, чтобы Service Worker выполнял:

```text
events
configuration
coordination
```

а не:

```text
continuous computation
```

---

# Принцип

Можно сформулировать правило:

> **Если задача может быть выражена через browser-native declarative API, не реализуйте её вручную в background JavaScript.**

Например:

```text
Block request
        ↓
DNR
```

а не:

```text
Service Worker → inspect → decide → block
```

---

# 26.4. Declarative rules как intermediate representation

Это, пожалуй, наиболее интересная концепция всей главы.

Declarative rules можно рассматривать как **Intermediate Representation — IR**.

---

# Что такое IR

В compiler architecture:

```text
Source code
    ↓
Parser
    ↓
IR
    ↓
Optimizer
    ↓
Machine code
```

IR является промежуточным представлением программы.

---

# Аналогичная модель для extension

Можно построить:

```text
Application Policy
       ↓
Extension IR
       ↓
DNR / Declarative API Rules
       ↓
Browser Engine
```

---

# Собственный Extension IR

Например:

```json
{
  "kind": "network-policy",
  "effect": "block",
  "resource": "script",
  "domain": "tracker.example.com"
}
```

Это ещё не обязательно DNR.

Это **универсальное описание намерения extension**.

---

# Затем:

```text
Extension IR
     │
     ├── Chrome DNR
     │
     ├── Firefox declarative APIs
     │
     └── Other browser representation
```

Это уже становится интересным с точки зрения cross-browser architecture.

---

# Universal Extension IR

Можно даже представить:

```text
                  Extension IR
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
          Chrome     Firefox    Other
             │         │         │
             ▼         ▼         ▼
           DNR       Rules       API
```

В этом случае application policy отделяется от конкретного browser API.

---

# Почему это полезно

Без IR:

```text
Application
    ↓
Chrome DNR
```

Application оказывается tightly coupled с Chrome API.

С IR:

```text
Application
    ↓
Universal Policy
    ↓
Compiler
    ↓
Browser-specific API
```

Получается более чистая архитектура.

---

# Emerge и Declarative IR

Для framework уровня Emerge это особенно интересно.

Можно представить:

```text
Emerge Extension
        ↓
Declarative IR
        ↓
Manifest V3 compiler
        ↓
manifest.json
        ↓
rulesets
        ↓
runtime
```

То есть разработчик работает не непосредственно с Manifest API, а с более высоким уровнем абстракции.

---

# Например

Вместо:

```json
{
  "action": {
    "type": "block"
  },
  "condition": {
    "urlFilter": "tracker"
  }
}
```

framework может предоставить:

```typescript
network.block({
    url: "*tracker*"
});
```

А compiler создаёт соответствующее DNR rule.

---

# Это уже не library

И здесь появляется принципиальная разница.

Library:

```text
Developer
   ↓
JavaScript API
   ↓
Runtime
```

Compiler-oriented framework:

```text
Developer
   ↓
High-level API
   ↓
Compiler
   ↓
Manifest / Rules / Runtime
```

---

# 26.5. Производительность

Declarative architecture потенциально позволяет существенно уменьшить runtime overhead.

Но важно понимать:

> Declarative ≠ автоматически fast.

Правильнее сказать:

> Declarative model позволяет браузеру использовать специализированный engine и избежать лишнего extension-level JavaScript execution.

---

# Где появляется выигрыш

В imperative architecture:

```text
Request
 ↓
Event dispatch
 ↓
Extension runtime
 ↓
JavaScript
 ↓
Logic
 ↓
Decision
```

В declarative:

```text
Request
 ↓
Browser rule engine
 ↓
Match
 ↓
Action
```

Сокращается путь выполнения.

---

# Особенно важно для массовых событий

Если событие возникает:

```text
1 раз
```

разница может быть несущественной.

Но если:

```text
100 000 events
```

разница становится архитектурно значимой.

Network requests — как раз такой случай.

---

# Browser optimization

Browser engine может оптимизировать declarative rules гораздо лучше, чем extension JavaScript.

Например browser знает:

```text
all rules
request structure
network pipeline
security context
```

и может использовать внутренние оптимизации.

Extension JavaScript этого не контролирует.

---

# Меньше wakeups

Для MV3 особенно важно:

```text
Service Worker wakeup
```

Каждый unnecessary wakeup:

```text
event
 ↓
worker startup
 ↓
JavaScript execution
```

увеличивает runtime activity.

Если работа выполняется декларативно:

```text
request
 ↓
browser engine
```

Service Worker вообще может не запускаться.

---

# Это особенно важно для ephemeral runtime

Мы уже видели:

```text
Service Worker
    ↓
startup
    ↓
work
    ↓
suspend
```

Чем меньше задач требует worker, тем лучше соответствует архитектуре MV3.

---

# Производительность — это не только CPU

Нужно учитывать:

```text
CPU
Memory
Wakeups
IPC
Startup
Battery
Lifecycle complexity
```

Declarative architecture может уменьшать сразу несколько факторов.

---

# 26.6. Безопасность

Declarative model имеет важное security преимущество:

> Она уменьшает количество произвольного extension code, выполняемого в чувствительных browser paths.

---

# Imperative model

Если extension получает network event:

```text
Request
 ↓
JavaScript
 ↓
Arbitrary logic
```

то JavaScript потенциально может выполнять большое количество операций.

Чем больше capability:

```text
network
tabs
storage
DOM
messages
```

тем больше attack surface.

---

# Declarative model

DNR ограничен predefined schema:

```text
condition
+
action
```

Например:

```text
block
redirect
modifyHeaders
```

Разработчик не получает произвольный network engine.

---

# Capability restriction

Это важный security principle:

> **Give the extension exactly the capability it needs, not arbitrary control.**

Например:

```text
Need:
block tracker

Capability:
DNR block rule
```

вместо:

```text
Capability:
arbitrary network interception
```

---

# Проверяемость

Declarative rule гораздо легче анализировать.

Например:

```json
{
  "action": {
    "type": "block"
  },
  "condition": {
    "urlFilter": "tracker.example.com"
  }
}
```

Человеку проще понять:

```text
IF tracker.example.com
THEN BLOCK
```

чем анализировать большой JavaScript event handler.

---

# Determinism

Declarative policy потенциально более детерминирована.

```text
condition
   ↓
action
```

вместо:

```text
event
 ↓
async code
 ↓
state
 ↓
network
 ↓
callback
 ↓
decision
```

Чем меньше скрытого runtime state, тем легче reasoning.

---

# Reduced attack surface

Можно представить:

```text
Imperative extension

          JavaScript
        /     |      \
       /      |       \
 Network    State     APIs
```

против:

```text
Declarative extension

        Policy
          │
          ▼
     Browser engine
```

Меньше произвольного runtime поведения — потенциально меньше поверхностей для ошибок.

---

# Но declarative API не делает extension автоматически secure

Это критически важно.

В extension всё ещё могут существовать:

```text
XSS
message injection
bad permissions
unsafe DOM
malicious configuration
supply-chain problems
```

Declarative API — это только один слой безопасности.

---

# Policy validation

Если rules генерируются автоматически, compiler должен валидировать их.

Например:

```text
User input
   ↓
Validation
   ↓
Normalization
   ↓
Policy compiler
```

Нельзя без проверки превращать произвольный пользовательский input в privileged browser rule.

---

# 26.7. Проектирование declarative extension

Теперь соберём всё в единый подход.

Первый принцип:

> **Начинайте не с API, а с policy.**

Не спрашивайте:

> Какой Chrome API мне вызвать?

Сначала спросите:

> Какое поведение я хочу выразить?

---

# Шаг 1. Определить policy

Например:

```text
Block trackers
```

---

# Шаг 2. Определить scope

```text
All sites?
Specific domains?
Specific resource types?
First-party only?
Third-party?
```

---

# Шаг 3. Определить action

```text
block
redirect
modify
allow
```

---

# Шаг 4. Определить lifecycle

Правило:

```text
Permanent?
```

→ static/dynamic.

Или:

```text
Temporary?
```

→ session.

---

# Шаг 5. Определить source of truth

Например:

```text
User settings
      ↓
Policy
```

а не:

```text
UI state
+
Storage state
+
DNR state
+
Worker globals
```

без чёткой модели.

---

# Шаг 6. Создать policy model

Например:

```typescript
type NetworkPolicy = {
    domain: string;
    resourceTypes?: string[];
    action: "block" | "allow";
};
```

---

# Шаг 7. Compile

```text
NetworkPolicy
      ↓
DNR Rule
```

---

# Шаг 8. Validate

```text
Policy
  ↓
Validation
  ↓
Rule
```

Проверяем:

* permissions;
* valid domains;
* valid actions;
* rule IDs;
* priorities;
* quotas.

---

# Шаг 9. Optimize

Например:

```text
1000 policies
      ↓
deduplicate
      ↓
merge
      ↓
reduce
      ↓
600 rules
```

---

# Шаг 10. Install

```text
Compiled rules
      ↓
DNR
```

Service Worker делает это только тогда, когда policy действительно меняется.

---

# Шаг 11. Keep Service Worker small

Хорошая архитектура:

```text
Service Worker
│
├── policy management
├── storage
├── messaging
├── lifecycle
└── orchestration
```

Плохая:

```text
Service Worker
│
├── network engine
├── DOM engine
├── parser
├── filtering engine
├── application runtime
└── everything else
```

---

# Declarative-first design

Полезно установить правило:

```text
Can browser do it declaratively?
        │
      YES
        ↓
Use declarative API
        │
      NO
        ↓
Use Service Worker / content script
```

Это один из лучших heuristics для Manifest V3.

---

# Hybrid architecture

Однако реальный extension почти никогда не является полностью declarative.

Лучше говорить:

> **Declarative-first architecture.**

Например:

```text
                    Extension
                        │
       ┌────────────────┼────────────────┐
       │                │                │
       ▼                ▼                ▼
  Declarative       Service Worker   Content Script
      APIs
       │                │                │
       ▼                ▼                ▼
   Browser           Control          Page
   Engine             Plane           Logic
```

---

# Разделение ответственности

### Declarative APIs

Используются для:

```text
policy
rules
activation
network filtering
```

### Service Worker

Используется для:

```text
orchestration
state
events
coordination
configuration
```

### Content Script

Используется для:

```text
DOM
page interaction
page observation
```

### Extension UI

Используется для:

```text
user interaction
settings
visualization
```

# Архитектурный шаблон

# Declarative Runtime

Теперь мы можем дать более точное определение.

**Declarative Runtime** — это часть поведения extension, которая представлена не исполняемым JavaScript-кодом, а структурированной policy, которую browser engine способен непосредственно интерпретировать и выполнять.

Условно:

```text
JavaScript Runtime
```

и:

```text
Declarative Runtime
```

становятся двумя разными execution layers.

---

# Два runtime

```text
                 Extension
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
 Imperative Runtime        Declarative Runtime
        │                         │
        ▼                         ▼
 JavaScript                  Rules / Policy
        │                         │
        ▼                         ▼
Extension contexts         Browser engines
```

Это очень важная концепция для дальнейшего проектирования.

---

# JavaScript Runtime

Он нужен там, где необходимы:

```text
complex algorithms
dynamic state
user interaction
DOM manipulation
message handling
external services
```

---

# Declarative Runtime

Он нужен там, где поведение можно выразить:

```text
condition
+
policy
+
action
```

Например:

```text
IF request matches X
THEN block
```

или:

```text
IF page matches X
THEN enable action
```

---

# Главный критерий выбора

Можно сформулировать его так:

> **Если поведение можно описать как policy, предпочитайте declarative representation. Если требуется algorithmic computation — используйте JavaScript.**

---

# От JavaScript-centric к Policy-centric

Традиционное мышление:

```text
What code should run?
```

Manifest V3 требует всё чаще задавать другой вопрос:

```text
What policy should the browser enforce?
```

Это очень существенный сдвиг.

---

# Следующая ступень: compiler-oriented extensions

Если принять declarative model всерьёз, возникает ещё одна идея.

Почему разработчик должен вручную писать:

```text
manifest.json
rules.json
permissions
content scripts
declarative rules
```

Можно построить compiler:

```text
High-level Extension Definition
             ↓
             IR
             ↓
      Manifest compiler
             ↓
      Rules compiler
             ↓
      Runtime generation
             ↓
        Extension
```

---

# Extension как программа

В таком подходе extension начинает выглядеть почти как компилируемая программа:

```text
Source
  ↓
Compiler
  ↓
Manifest
  ↓
Declarative rules
  ↓
JavaScript runtime
  ↓
Browser
```

А не просто как:

```text
manifest.json
+
some JavaScript
```

---

# Это особенно важно для framework

Framework следующего поколения может предоставить:

```typescript
extension({
    permissions: [...],

    network: {
        block: [...]
    },

    pages: {
        content: [...]
    },

    commands: {
        ...
    }
});
```

и затем сгенерировать:

```text
manifest.json
rules/*.json
service-worker.js
content-scripts/*
options/*
side-panel/*
```

---

# Compile More, Execute Less

Для современной extension architecture можно сформулировать принцип:

> **Compile more, execute less.**

То есть:

```text
Больше работы
    ↓
на этапе генерации

Меньше работы
    ↓
во время runtime
```

---

# Это хорошо согласуется с MV3

MV3 фактически подталкивает разработчика к:

```text
Static
Declarative
Event-driven
Ephemeral
Browser-managed
```

вместо:

```text
Permanent
Imperative
Background-heavy
JavaScript-controlled
```

# Итоговая архитектура

К концу этой части учебника мы можем представить современное MV3 extension так:

```text
                           EXTENSION
                               │
                ┌──────────────┴──────────────┐
                │                             │
                ▼                             ▼
         Declarative Layer              Imperative Layer
                │                             │
        ┌───────┼───────┐             ┌───────┼────────┐
        │       │       │             │       │        │
```

И между ними находится policy:

```text
              Application Intent
                      │

            │
            ▼
      Browser-specific
          rules
```

# Что нужно запомнить

### 1. Declarative API — это не просто JSON

Это другая модель исполнения:

```text
Extension declares
Browser executes
```

### 2. JavaScript не должен делать всю работу

Если browser engine способен выполнить policy самостоятельно, лучше передать работу ему.

### 3. Rules можно генерировать

```text
Policy
 ↓
Compiler
 ↓
Rules
```

### 4. Rules можно рассматривать как IR

```text
High-level policy
 ↓
Intermediate representation
 ↓
Browser-specific rules
```

### 5. Service Worker превращается в control plane

Он управляет policy, а не обязательно выполняет её сам.

### 6. DNR становится data plane

```text
Service Worker → configure
DNR → enforce
```

### 7. Declarative execution потенциально эффективнее

Особенно для массовых событий:

```text
network requests
page conditions
resource filtering
```

### 8. Declarative model уменьшает runtime surface

Меньше:

```text
JavaScript
callbacks
wakeups
arbitrary execution
```

может означать более простой и предсказуемый runtime.

### 9. Лучший подход — declarative-first

Не:

```text
"Какой API вызвать?"
```

а:

```text
"Какую policy я хочу выразить?"
```

### 10. Будущее сложных extensions — hybrid

```text
Declarative APIs
       +
Service Worker
       +
Content Scripts
       +
Extension UI
```

Каждый слой должен выполнять **свою** работу.

# Финальная модель

Главную идею главы можно свести к одной схеме:

```text
                    DEVELOPER
                        │
                        ▼
                 Application Intent
                        │
                        ▼
                      POLICY
                        │
                        ▼
               ┌─────────────────┐
               │  Policy / IR    │
               └────────┬────────┘
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
       Declarative Layer    Imperative Layer
              │                   │
              ▼                   ▼
        Browser Engine       JS Runtime
              │                   │
              ▼                   ▼
        Native execution     Extension logic
              │                   │
              └─────────┬─────────┘
                        ▼
                     BROWSER
```

Именно это является фундаментальной архитектурной идеей Declarative APIs в Manifest V3:

> **Современное browser extension — это уже не просто набор JavaScript-файлов, реагирующих на события браузера. Это комбинация декларативной policy, browser-managed execution и небольшого imperative runtime, который координирует систему.**

Отсюда появляется совершенно новый подход к разработке расширений:

```text
                    OLD
             "Write more code"

                        ↓

                    MV3
             "Declare more policy"

                        ↓

              NEXT GENERATION
             "Compile more,
              execute less."
```

И именно этот принцип впоследствии может стать фундаментом для **framework/compiler над Manifest V3**, который будет скрывать низкоуровневые `manifest.json`, rulesets, message protocols и lifecycle management, предоставляя разработчику более высокий уровень — **Extension Application Model**.
