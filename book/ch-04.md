# Часть II. Permissions и модель безопасности

# Глава 4. Permissions

Permissions — одна из фундаментальных концепций Manifest V3.

До этого мы создали простое расширение и использовали:

```json
{
  "permissions": [
    "activeTab"
  ]
}
```

На первый взгляд это всего лишь строка в `manifest.json`.

На самом деле permission определяет **границу возможностей расширения**.

Браузер не должен предоставлять extension полный контроль над браузером, вкладками, страницами, cookies, загрузками и другими ресурсами только потому, что пользователь установил несколько JavaScript-файлов.

Поэтому Manifest V3 использует capability-based модель:

```text
Extension
    │
    ├── declared permissions
    │
    ▼
Browser
    │
    └── grants only requested capabilities
```

Эту модель важно понять глубже, потому что практически каждая серьёзная архитектура browser extension начинается с вопроса:

> **Какие capabilities действительно нужны этому расширению?**

---

# 4.1. Зачем расширениям нужны permissions

Обычная веб-страница работает в сильно ограниченной sandbox-модели.

Например, сайт:

```text
https://example.com
```

не может просто получить:

* список всех открытых вкладок;
* историю браузера;
* bookmarks;
* cookies других сайтов;
* содержимое произвольной вкладки;
* доступ к downloads;
* управление окнами браузера.

Это было бы серьёзным нарушением модели безопасности.

Browser extension, напротив, специально создано для расширения возможностей браузера.

Например, extension может быть:

* менеджером вкладок;
* password manager;
* блокировщиком рекламы;
* инструментом автоматизации;
* web scraper;
* developer tool;
* productivity application;
* интеграцией с CRM;
* инструментом анализа веб-страниц.

Но расширение получает дополнительные возможности **не автоматически**.

Оно должно объявить необходимые permissions.

---

## Permission как capability

Полезно мыслить не так:

> Permission — это разрешение пользователя.

А несколько точнее:

> **Permission — это capability, которую extension запрашивает у браузерной платформы.**

Например:

```json
{
  "permissions": [
    "storage"
  ]
}
```

означает, что extension запрашивает capability для работы с extension storage.

Другой пример:

```json
{
  "permissions": [
    "tabs"
  ]
}
```

запрашивает дополнительные возможности Tabs API.

Таким образом:

```text
Permission
    ↓
Capability
    ↓
Extension API
```

---

# 4.2. Permission model Manifest V3

В Manifest V3 разрешения разделяются на несколько концептуальных категорий.

Главные:

```text
permissions
host_permissions
optional_permissions
optional_host_permissions
```

Их можно представить так:

```text
                 Extension
                     │
              Permission Model
                     │
       ┌─────────────┴─────────────┐
       │                           │
 API permissions             Host permissions
       │                           │
   storage                    example.com
   tabs                       github.com
   alarms                     ...
   scripting
   ...
```

Но существует ещё один важный аспект:

```text
Declared
    ↓
Optional
    ↓
Requested at runtime
```

То есть permission может быть:

1. необходимым с самого начала;
2. опциональным;
3. запрошенным только тогда, когда пользователь запускает соответствующую функцию.

---

# 4.3. `permissions`

Поле:

```json
{
  "permissions": [
    "storage"
  ]
}
```

описывает дополнительные extension API capabilities.

Например:

```json
{
  "permissions": [
    "storage",
    "alarms",
    "tabs"
  ]
}
```

Здесь extension заявляет, что ему нужны соответствующие API.

---

## Пример: Storage

Если extension использует:

```javascript
chrome.storage.local
```

ему требуется соответствующее разрешение `storage`.

Например:

```json
{
  "manifest_version": 3,
  "name": "Settings Demo",
  "version": "1.0.0",

  "permissions": [
    "storage"
  ]
}
```

Теперь приложение может работать с extension storage.

Например:

```javascript
await chrome.storage.local.set({
  theme: "dark"
});
```

и:

```javascript
const result = await chrome.storage.local.get("theme");

console.log(result.theme);
```

---

## Пример: Alarms

Если extension должен выполнять действия по расписанию, используется соответствующий API:

```json
{
  "permissions": [
    "alarms"
  ]
}
```

Это позволяет использовать:

```javascript
chrome.alarms
```

---

## Пример: Tabs

Для некоторых операций с вкладками требуется:

```json
{
  "permissions": [
    "tabs"
  ]
}
```

После этого extension получает расширенные возможности работы с Tabs API.

Но здесь появляется важный вопрос:

> Нужно ли действительно permission `tabs`?

Иногда — нет.

Например, для определённых действий с текущей вкладкой может быть достаточно:

```json
{
  "permissions": [
    "activeTab"
  ]
}
```

Поэтому permission нельзя выбирать просто по принципу:

> "Этот API существует — значит, нужно добавить соответствующее permission."

Сначала необходимо определить **конкретную capability**, которая нужна приложению.

---

# 4.4. `host_permissions`

`host_permissions` отличаются от обычных API permissions.

Например:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

означает, что extension запрашивает host access для соответствующего URL pattern.

Это позволяет extension взаимодействовать с определёнными веб-ресурсами в сценариях, где такой доступ требуется.

---

## API permission vs Host permission

Очень важно различать:

```text
permissions
    │
    └── What APIs can extension use?

host_permissions
    │
    └── Which web origins can extension access?
```

Например:

```json
{
  "permissions": [
    "storage"
  ],

  "host_permissions": [
    "https://example.com/*"
  ]
}
```

можно читать так:

> Extension использует Storage API и получает host access к страницам `example.com`.

---

## Match patterns

Host permissions используют специальные match patterns.

Например:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

означает соответствующие HTTPS URL на этом host.

Можно использовать wildcard для поддоменов:

```json
{
  "host_permissions": [
    "https://*.example.com/*"
  ]
}
```

Например:

```text
https://example.com/
https://www.example.com/
https://app.example.com/
```

могут соответствовать такому pattern.

Но host patterns — отдельная большая тема, которую мы подробно разберём позже.

---

## Почему `<all_urls>` требует осторожности

Иногда встречается:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

Это очень широкое разрешение.

Оно означает, что extension запрашивает доступ к широкому набору URL.

Для extension типа:

> "работать на любых веб-страницах"

это может быть оправдано.

Но если приложение работает только с:

```text
https://example.com/*
```

то запрашивать:

```text
<all_urls>
```

необходимо.

Это уже вопрос архитектуры безопасности.

---

# 4.5. Optional permissions

Не все permissions должны быть обязательными при установке.

Представим extension для работы с изображениями.

Основная функция:

```text
Resize image
```

не требует доступа к bookmarks.

Но в extension есть дополнительная функция:

```text
Save result to browser bookmarks
```

Тогда нет необходимости запрашивать bookmarks permission у каждого пользователя с самого начала.

Можно сделать permission optional.

В manifest используется:

```json
{
  "optional_permissions": [
    "bookmarks"
  ]
}
```

Идея:

```text
Install extension
       │
       ▼
Basic functionality
       │
       │
       └── User activates advanced feature
                    │
                    ▼
             Request permission
```

Это гораздо лучше, чем:

```text
Install
  ↓
Request every possible permission
  ↓
User sees huge permission scope
```

---

## Optional host permissions

Аналогично существуют optional host permissions.

Концептуально:

```json
{
  "optional_host_permissions": [
    "https://*.example.com/*"
  ]
}
```

Теперь extension может запросить этот host access только при необходимости.

Например:

```text
User opens feature
        ↓
Feature requires access to example.com
        ↓
Request host permission
        ↓
User grants
        ↓
Feature becomes available
```

---

# 4.6. Runtime permissions

Runtime permission request означает, что extension не получает optional capability сразу, а запрашивает её во время работы.

Для этого используется Permissions API.

Например, архитектурно:

```javascript
const granted = await chrome.permissions.request({
  permissions: ["bookmarks"]
});
```

После этого можно проверить результат:

```javascript
if (granted) {
  // Permission granted
}
```

Для host access концепция аналогична:

```javascript
const granted = await chrome.permissions.request({
  origins: ["https://*.example.com/*"]
});
```

---

## Почему runtime request важен?

Потому что permission теперь связан с **конкретным действием пользователя**.

Например:

```text
Extension installed
        │
        ▼
No bookmarks permission
        │
        ▼
User clicks:
"Save to bookmarks"
        │
        ▼
Extension requests permission
        │
        ▼
User approves
        │
        ▼
Feature executes
```

Это значительно лучше объясняет пользователю:

> Почему extension сейчас просит дополнительный доступ?

---

## Permission request не должен быть неожиданным

Плохой UX:

```text
User opens extension
        ↓
Unexpected permission dialog
```

Лучше:

```text
User clicks:
"Enable cloud sync"
        ↓
Explain why permission is needed
        ↓
Request permission
```

То есть permission request должен быть связан с **намерением пользователя**.

---

# 4.7. Минимизация разрешений

Один из важнейших принципов Manifest V3:

> **Не запрашивайте permission, если без него можно обойтись.**

Представим три архитектуры.

### Вариант A

```json
{
  "permissions": [
    "tabs"
  ]
}
```

### Вариант B

```json
{
  "permissions": [
    "activeTab"
  ]
}
```

### Вариант C

```json
{
  "permissions": [],
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

Нельзя сказать, что один вариант всегда лучше.

Всё зависит от функциональности.

Например, если extension должен:

> получать информацию только о текущей странице после действия пользователя,

`activeTab` может быть значительно более подходящей capability, чем постоянный широкий доступ.

---

# 4.8. Permission warnings

Permissions имеют ещё один важный аспект — **пользовательское доверие**.

Некоторые permissions могут приводить к отображению предупреждений при установке или запросе доступа.

Например, пользователь может увидеть сообщение о том, что extension получает возможность работать с определёнными данными или сайтами.

Поэтому permission влияет не только на техническую архитектуру.

Он влияет на:

```text
Security
   +
Privacy
   +
UX
   +
Store Review
   +
User Trust
```

---

## Почему слишком широкие permissions вредны

Предположим, существует extension:

> "Simple page counter"

и он запрашивает:

```json
{
  "permissions": [
    "tabs",
    "history",
    "bookmarks",
    "downloads",
    "cookies"
  ],
  "host_permissions": [
    "<all_urls>"
  ]
}
```

Пользователь вполне может спросить:

> Почему простой счётчик страниц хочет доступ практически ко всему браузеру?

Даже если extension технически безопасен, его permission model выглядит подозрительно.

Поэтому хороший extension должен иметь **понятную связь между функцией и permission**.

Например:

```text
Feature
   ↓
Required capability
   ↓
Minimal permission
```

---

# 4.9. Principle of Least Privilege

Principle of Least Privilege — принцип минимальных привилегий.

Он означает:

> Каждый компонент системы должен иметь только те права, которые необходимы ему для выполнения своей задачи.

Это один из фундаментальных принципов computer security.

Для browser extensions он особенно важен.

---

## Плохая модель

```text
Extension
    │
    ├── all tabs
    ├── all websites
    ├── history
    ├── bookmarks
    ├── cookies
    └── downloads
```

Даже если extension использует только одну из этих capabilities.

---

## Хорошая модель

```text
Extension
    │
    ├── storage
    │
    └── activeTab
```

если именно этого достаточно для приложения.

---

## Least Privilege применяется не только к manifest

Это очень важная мысль.

Принцип распространяется на всю архитектуру.

Например:

```text
Permissions
    ↓
Contexts
    ↓
Messages
    ↓
Storage
    ↓
Network
    ↓
DOM access
```

Нужно спрашивать:

> Какой компонент действительно должен иметь этот доступ?

Например, не обязательно давать одному компоненту весь state приложения.

Можно иметь:

```text
Popup
   │
   └── request
          ↓
     Service Worker
          │
          └── storage
```

вместо:

```text
Every context
      ↓
Direct access to everything
```

Таким образом, Least Privilege становится **архитектурным принципом**, а не только настройкой manifest.

---

# 4.10. Проектирование permission model

Теперь соберём всё вместе.

Permission model следует проектировать **до написания основной части extension**.

Начинать лучше не с вопроса:

> Какие permissions существуют?

А с вопроса:

> Что должно делать приложение?

---

## Шаг 1. Определить функции

Например, создаём extension для анализа веб-страницы.

Функции:

```text
1. Read current page
2. Extract headings
3. Save results
4. Show results in Side Panel
5. Run analysis on demand
```

---

## Шаг 2. Определить capabilities

Теперь:

```text
Read current page
        ↓
activeTab / appropriate host access

Save results
        ↓
storage

Side Panel
        ↓
side_panel API / manifest declaration

Run on demand
        ↓
action
```

---

## Шаг 3. Разделить обязательные и optional capabilities

Например:

```text
Required:
    storage

Optional:
    access to additional websites
    bookmarks
```

Получаем:

```json
{
  "permissions": [
    "storage"
  ],

  "optional_permissions": [
    "bookmarks"
  ]
}
```

---

## Шаг 4. Ограничить hosts

Если extension работает только с:

```text
https://example.com/*
```

не следует автоматически писать:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

Лучше:

```json
{
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

---

## Шаг 5. Проверить каждое permission

Полезно создать таблицу:

| Feature          | Capability  | Permission                  | Required? |
| ---------------- | ----------- | --------------------------- | --------- |
| Save settings    | Storage     | `storage`                   | Да        |
| Read current tab | Active tab  | `activeTab`                 | Да        |
| Save bookmarks   | Bookmarks   | `bookmarks`                 | Нет       |
| Access CRM       | Host access | `https://crm.example.com/*` | Нет       |

Такой подход заставляет нас проектировать permissions рационально.

---

# Permission Architecture

В результате можно построить следующую модель:

```text
                    Extension
                        │
                  Permission Model
                        │
          ┌─────────────┴─────────────┐
          │                           │
       Required                    Optional
          │                           │
     ┌────┴────┐                 ┌────┴────┐
     │         │                 │         │
    APIs      Hosts             APIs      Hosts
     │         │                 │         │
 storage   example.com       bookmarks   CRM
 alarms
```

А runtime выглядит:

```text
             Extension installed
                     │
                     ▼
              Basic permissions
                     │
                     ▼
             Basic functionality
                     │
                     ▼
             User requests feature
                     │
                     ▼
          Optional permission needed?
                /           \
              No             Yes
              │               │
              ▼               ▼
            Run       Request permission
                              │
                        ┌─────┴─────┐
                        │           │
                     Granted     Denied
                        │           │
                        ▼           ▼
                      Run       Explain limitation
```

Это уже не просто конфигурация.

Это **permission architecture**.

# Практический пример

Предположим, мы создаём extension:

> **Web Research Assistant**

Он должен:

1. читать текущую страницу;
2. извлекать заголовки;
3. сохранять заметки;
4. показывать заметки в Side Panel;
5. по желанию сохранять страницы в bookmarks.

Можно спроектировать permissions следующим образом:

```json
{
  "manifest_version": 3,

  "name": "Web Research Assistant",
  "version": "1.0.0",

  "permissions": [
    "storage",
    "activeTab"
  ],

  "optional_permissions": [
    "bookmarks"
  ]
}
```

А bookmarks запрашивать только тогда, когда пользователь нажмёт:

```text
Save to bookmarks
```

Это гораздо лучше, чем сразу запросить:

```json
{
  "permissions": [
    "storage",
    "activeTab",
    "bookmarks",
    "tabs",
    "history",
    "downloads"
  ]
}
```

# Permission Model как часть архитектуры

На этом этапе появляется важная идея, которая будет использоваться во всей дальнейшей книге.

Manifest V3 extension можно рассматривать как систему:

```text
                    Extension
                        │
               ┌────────┴────────┐
               │                 │
          Capabilities        Contexts
               │                 │
          permissions      popup / SW / CS
               │                 │
               └────────┬────────┘
                        │
                    Messaging
                        │
                        ▼
                      State
                        │
                        ▼
                     Storage
```

Permissions определяют **что extension может делать**.

Contexts определяют **где код может выполняться**.

Messaging определяет **как contexts взаимодействуют**.

Storage определяет **как сохраняется состояние**.

Именно эти четыре понятия вместе образуют фундаментальную архитектуру Manifest V3.

---

# Главные выводы главы

### 1. Permission — это capability

```text
Permission
    ↓
Capability
    ↓
API access
```

### 2. `permissions` и `host_permissions` — разные вещи

```text
permissions
    ↓
Extension APIs

host_permissions
    ↓
Web origins
```

### 3. Не все permissions должны быть обязательными

Можно использовать:

```text
optional_permissions
optional_host_permissions
```

и запрашивать их при необходимости.

### 4. Runtime permission — часть UX

Permission следует запрашивать в контексте действия пользователя.

### 5. Чем меньше permissions, тем лучше

Но только если функциональность extension при этом сохраняется.

### 6. Least Privilege — архитектурный принцип

Он относится не только к manifest, но и к:

* contexts;
* messaging;
* storage;
* network;
* DOM access.

### 7. Permission model необходимо проектировать заранее

Правильный процесс:

```text
Features
   ↓
Capabilities
   ↓
Required permissions
   ↓
Optional permissions
   ↓
Host access
   ↓
Runtime requests
```

# Практическое задание

Создайте extension со следующими требованиями:

```text
Extension: Page Notes

Функции:

1. Показывает popup.
2. Может получить информацию о текущей вкладке.
3. Может сохранить заметку.
4. Может загрузить сохранённую заметку.
5. Не должен иметь доступа ко всем сайтам.
6. Дополнительная функция "Save to bookmarks"
   должна быть optional.
```

Попробуйте самостоятельно определить:

