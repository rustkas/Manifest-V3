# Часть XI. Network и Web Platform

# Глава 29. Network Requests

Сетевое взаимодействие — одна из наиболее важных возможностей браузерного расширения.

Расширение может:

* обращаться к API;
* отправлять данные на сервер;
* получать конфигурацию;
* работать с SaaS;
* синхронизировать состояние;
* выполнять authentication;
* обращаться к нескольким доменам;
* взаимодействовать с REST, GraphQL или другими HTTP API.

Но в Manifest V3 network requests имеют важную особенность:

> **Сетевой запрос зависит не только от URL, но и от execution context, origin, CORS, host permissions, cookies и политики безопасности.**

Поэтому архитектура network layer должна учитывать структуру самого extension:

```text
                         Extension
                             │
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼
          Popup         Service Worker   Content Script
             │               │               │
             └───────┬───────┘               │
                     ▼                       ▼
                   fetch()               Page network
                     │
                     ▼
                  Network
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
         API       Auth       Cookies
```

Главная задача этой главы — понять, **как правильно организовать network layer Manifest V3 extension**, а не просто научиться вызывать `fetch()`.

---

# 29.1. `fetch()`

`fetch()` — основной Web Platform API для выполнения HTTP-запросов.

Минимальный пример:

```javascript
const response = await fetch(
    "https://api.example.com/users"
);

const data = await response.json();

console.log(data);
```

В расширении синтаксис практически такой же, как на обычной веб-странице.

---

# GET request

Например:

```javascript
const response = await fetch(
    "https://api.example.com/data"
);

if (!response.ok) {
    throw new Error(
        `HTTP ${response.status}`
    );
}

const data = await response.json();
```

---

# POST request

```javascript
const response = await fetch(
    "https://api.example.com/data",
    {
        method: "POST",

        headers: {
            "Content-Type": "application/json"
        },

        body: JSON.stringify({
            name: "Extension"
        })
    }
);
```

---

# Request object

Для более сложной архитектуры можно использовать `Request`:

```javascript
const request = new Request(
    "https://api.example.com/data",
    {
        method: "GET",
        headers: {
            "Accept": "application/json"
        }
    }
);

const response = await fetch(request);
```

Это позволяет отделить создание запроса от его выполнения.

---

# Response

`fetch()` возвращает:

```text
Response
```

Например:

```javascript
const response = await fetch(url);
```

У него есть:

```javascript
response.status
response.ok
response.headers
response.url
```

и методы чтения body:

```javascript
response.json()
response.text()
response.blob()
response.arrayBuffer()
response.formData()
```

---

# HTTP error и `fetch()`

Важная особенность:

`fetch()` обычно не выбрасывает исключение только потому, что сервер вернул:

```text
400
404
500
```

Например:

```javascript
const response = await fetch(url);

console.log(response.status);
```

может вывести:

```text
404
```

Поэтому production code должен проверять:

```javascript
if (!response.ok) {
    throw new Error(
        `Request failed: ${response.status}`
    );
}
```

---

# Network error

Совсем другая ситуация:

```javascript
try {
    const response = await fetch(url);
} catch (error) {
    console.error(error);
}
```

`catch` может сработать при проблемах самого network operation:

```text
DNS failure
connection failure
blocked request
CORS failure
aborted request
```

---

# AbortController

Для cancellation:

```javascript
const controller = new AbortController();

const response = await fetch(
    url,
    {
        signal: controller.signal
    }
);
```

Затем:

```javascript
controller.abort();
```

Это особенно полезно для UI.

Например:

```text
User starts search
       ↓
request #1
       ↓
User changes query
       ↓
abort #1
       ↓
request #2
```

# 29.2. Extension origin

Одно из ключевых понятий network architecture — **origin extension**.

Extension имеет собственный origin.

Например:

```text
chrome-extension://abcdefghijklmnop
```

В Chromium-based browsers конкретный ID зависит от установки extension.

Таким образом:

```text
Web page
https://example.com
```

и:

```text
Extension
chrome-extension://abcdefghijklmnop
```

— разные origins.

---

# Origin состоит из

Концептуально origin определяется:

```text
scheme
host
port
```

Для extension:

```text
chrome-extension://extension-id
```

используется специальная схема.

---

# Почему это важно

Когда extension выполняет:

```javascript
fetch("https://api.example.com")
```

request начинается не с:

```text
https://example.com
```

а из extension context.

То есть browser видит:

```text
Origin:
chrome-extension://abcdefghijklmnop
```

Это принципиально важно для CORS.

---

# Extension origin как security boundary

Можно представить:

```text
               Browser
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 Web origin             Extension origin
https://site.com    chrome-extension://...
```

Это разные security contexts.

---

# Extension pages

Например:

```text
popup.html
options.html
sidepanel.html
```

работают в extension origin.

Поэтому network requests из них рассматриваются как requests extension context.

---

# Service Worker

Service Worker также принадлежит extension origin.

Это делает его особенно удобным местом для central network layer:

```text
Popup
   │
   ▼
Service Worker
   │
   ▼
fetch()
   │
   ▼
API
```

---

# Content Script

Content Script — более интересный случай.

Он выполняется в контексте страницы с точки зрения DOM, но имеет isolated JavaScript environment.

Это не означает, что его network semantics полностью идентичны extension page.

Поэтому network logic не следует автоматически размещать в Content Script.

---

# Практическое правило

Если запрос относится к:

```text
extension backend
authentication
subscription
configuration
private API
```

обычно разумно рассмотреть:

```text
Content Script
      ↓
Service Worker
      ↓
Backend
```

вместо:

```text
Content Script
      ↓
Backend
```

---

# 29.3. CORS

**CORS — Cross-Origin Resource Sharing**.

Это механизм, с помощью которого сервер сообщает браузеру:

> какие cross-origin requests разрешены.

---

# Почему CORS существует

Представим страницу:

```text
https://example.com
```

которая пытается выполнить:

```javascript
fetch(
    "https://api.other.com/data"
);
```

Это cross-origin request.

Browser применяет соответствующие security rules.

---

# Origin comparison

Например:

```text
https://example.com
```

и:

```text
https://api.example.com
```

имеют разные origins.

То же самое:

```text
https://example.com
```

и:

```text
http://example.com
```

разные origins.

---

# CORS response headers

Сервер может вернуть:

```http
Access-Control-Allow-Origin: https://example.com
```

или соответствующее разрешение для допустимого origin.

Для extension сервер может учитывать extension origin.

---

# Важное различие

Наличие:

```text
host_permissions
```

не означает автоматически:

> любой произвольный Web page context может делать CORS requests куда угодно.

Нужно различать:

```text
extension privileges
```

и:

```text
page CORS model
```

---

# Почему Service Worker важен

Для расширения часто лучше строить:

```text
Content Script
       │
       │ message
       ▼
Service Worker
       │
       │ fetch
       ▼
Backend
```

Таким образом network operation находится в extension-controlled context.

---

# CORS ≠ authentication

Это ещё одно важное различие.

CORS отвечает на вопрос:

> Разрешает ли browser данный cross-origin interaction?

Authentication отвечает:

> Кто выполняет запрос?

Например:

```text
CORS
 ↓
permission to interact
```

а:

```text
Authentication
 ↓
identity
```

Это разные уровни.

---

# Preflight

Некоторые cross-origin requests требуют предварительный:

```text
OPTIONS
```

request.

Например, при определённых комбинациях:

```text
method
headers
content type
```

browser может сначала выполнить:

```text
OPTIONS /api/data
```

и только после успешной проверки:

```text
POST /api/data
```

---

# CORS architecture

Можно представить:

```text
Extension
    │
    │ fetch
    ▼
Browser networking layer
    │
    │ CORS checks
    ▼
Server
    │
    │ CORS response
    ▼
Browser
```

---

# 29.4. Host permissions

Host permissions определяют, с какими hosts extension получает дополнительные возможности.

Например:

```json
{
    "host_permissions": [
        "https://api.example.com/*"
    ]
}
```

Это говорит браузеру, что extension заявляет доступ к соответствующему host pattern.

---

# Host permissions ≠ URL whitelist приложения

Это не просто список:

```text
allowed API URLs
```

Host permissions являются частью security model extension.

Они могут использоваться в нескольких механизмах.

Например:

```text
content scripts
network requests
tab-related capabilities
```

в зависимости от API и browser behavior.

---

# Пример

```json
{
    "permissions": [
        "storage"
    ],

    "host_permissions": [
        "https://api.example.com/*"
    ]
}
```

Теперь архитектурно видно:

```text
storage
    ↓
extension permission

api.example.com
    ↓
host permission
```

---

# Минимизация hosts

Не стоит писать:

```json
{
    "host_permissions": [
        "<all_urls>"
    ]
}
```

если extension действительно работает только с:

```text
api.example.com
```

Лучше:

```json
{
    "host_permissions": [
        "https://api.example.com/*"
    ]
}
```

---

# Host permission как часть архитектуры

До реализации network layer нужно определить:

```text
Какие backend hosts реально необходимы?
```

Например:

```text
api.example.com
auth.example.com
cdn.example.com
```

а не:

```text
*
```

---

# 29.5. Cross-origin requests

Cross-origin request — request между различными origins.

Например:

```text
Extension
chrome-extension://abc
       │
       ▼
https://api.example.com
```

Это cross-origin interaction.

---

# Архитектура

Есть два основных варианта.

### Вариант A

```text
Content Script
       ↓
fetch()
       ↓
API
```

### Вариант B

```text
Content Script
       ↓
Message
       ↓
Service Worker
       ↓
fetch()
       ↓
API
```

В сложном extension второй вариант обычно легче контролировать.

---

# Почему central network layer полезен

Если каждый context самостоятельно вызывает API:

```text
Popup ───────→ API
Options ─────→ API
Side Panel ──→ API
Content ─────→ API
Worker ───────→ API
```

возникает duplication.

Например:

```text
authentication
retry
logging
error handling
headers
serialization
```

дублируются.

---

# Лучше

```text
Popup ──────┐
Panel ──────┤
Options ────┤
Content ────┤
            ▼
      Network Layer
            │
            ▼
          API
```

---

# Network Service

Например:

```javascript
class ApiClient {

    async get(path) {
        return this.request(path, {
            method: "GET"
        });
    }

    async post(path, body) {
        return this.request(path, {
            method: "POST",
            body: JSON.stringify(body)
        });
    }

    async request(path, options) {
        const response = await fetch(
            `https://api.example.com${path}`,
            {
                ...options,
                headers: {
                    "Content-Type": "application/json",
                    ...options.headers
                }
            }
        );

        if (!response.ok) {
            throw new Error(
                `HTTP ${response.status}`
            );
        }

        return response.json();
    }
}
```

---

# Service Worker как network gateway

Более архитектурный вариант:

```text
Content Script
      │
      │ GET_USER
      ▼
Service Worker
      │
      ▼
ApiClient
      │
      ▼
Backend
```

Ответ:

```text
Backend
   ↓
ApiClient
   ↓
Service Worker
   ↓
Content Script
```

---

# 29.6. Authentication

Network architecture почти всегда связана с authentication.

Типичные модели:

```text
API key
Bearer token
OAuth
session cookie
signed request
extension identity
```

---

# Не храните secrets в extension

Это один из важнейших принципов.

Extension code находится на стороне пользователя.

Поэтому нельзя считать секретом:

```javascript
const SECRET_API_KEY =
    "super-secret-value";
```

---

# Почему

Пользователь может:

```text
inspect extension
read source
inspect network
debug Service Worker
```

Следовательно:

> Всё, что поставлено в extension client, потенциально доступно пользователю.

---

# API key

API key, встроенный в extension:

```text
Extension
   ↓
hardcoded API key
   ↓
Backend
```

не является настоящим server-side secret.

---

# Backend architecture

Для коммерческого extension лучше:

```text
Extension
    ↓
Authentication
    ↓
User-specific token
    ↓
Backend
    ↓
Protected services
```

а настоящий secret:

```text
Backend secret
```

остаётся на сервере.

---

# Bearer token

Например:

```javascript
const response = await fetch(
    "https://api.example.com/me",
    {
        headers: {
            Authorization:
                `Bearer ${token}`
        }
    }
);
```

---

# Token storage

Token может быть частью extension state.

Но его storage нужно проектировать отдельно.

Например:

```text
short-lived access token
        ↓
memory

refresh/session state
        ↓
appropriate persistent storage
```

Конкретная схема зависит от authentication provider.

---

# Token lifecycle

Нельзя предполагать:

```text
login
 ↓
token forever
```

Реальная система может иметь:

```text
login
 ↓
access token
 ↓
expiration
 ↓
refresh
 ↓
new token
```

---

# Authentication layer

Хорошая архитектура:

```text
UI
 │
 ▼
Auth command
 │
 ▼
Auth Service
 │
 ├── login
 ├── logout
 ├── refresh
 └── getSession
```

Network layer не должен знать всю бизнес-логику authentication.

---

# 401

Например:

```javascript
if (response.status === 401) {
    // token expired
}
```

Можно выполнить:

```text
401
 ↓
refresh token
 ↓
retry request
```

Но retry должен иметь ограничения, чтобы не создать бесконечный цикл.

---

# Retry

Например:

```text
request
 ↓
network error
 ↓
retry
 ↓
network error
 ↓
retry
 ↓
failure
```

Нужно использовать:

```text
max retries
backoff
timeout
abort
```

# 29.7. Cookies

Cookies — отдельный механизм хранения session information.

Например:

```http
Cookie: session=abc123
```

может использоваться сервером для authentication.

---

# Cookie-based authentication

Типичная архитектура:

```text
Extension
    ↓
request
    ↓
Browser cookie jar
    ↓
Server session
```

Но поведение cookies зависит от:

```text
origin
domain
path
SameSite
Secure
credentials
```

---

# `credentials`

При необходимости можно явно указать:

```javascript
fetch(url, {
    credentials: "include"
});
```

Вопрос cookies нельзя рассматривать отдельно от credentials policy.

---

# Cookie access

Manifest V3 также предоставляет специальный Cookies API при соответствующих разрешениях.

Например, extension может работать с:

```text
chrome.cookies
```

Но это отдельный механизм от обычного `fetch()`.

---

# `fetch()` и Cookies API — не одно и то же

Важно разделять:

```text
fetch()
```

— выполняет HTTP request.

А:

```text
chrome.cookies
```

— предоставляет API для управления/чтения cookies при наличии соответствующих permissions.

---

# Cookie security

Нельзя считать cookie автоматически безопасной.

Особенно важны:

```text
Secure
HttpOnly
SameSite
Domain
Path
```

---

# HttpOnly

Если cookie имеет:

```text
HttpOnly
```

она недоступна обычному JavaScript через:

```javascript
document.cookie
```

Это важная защита от части client-side attacks.

---

# SameSite

`SameSite` контролирует поведение cookie в cross-site scenarios.

Типичные значения:

```text
Strict
Lax
None
```

`SameSite=None` требует соответствующих secure conditions.

---

# Extension и cookies

Cookies extension architecture может быть достаточно сложной:

```text
Extension origin
      │
      ├── extension cookies
      │
      └── requests to external domains
                │
                ▼
             site cookies
```

Поэтому нельзя предполагать:

> «Если пользователь залогинен в сайте, extension автоматически имеет ту же session.»

Это зависит от контекста и cookie policy.

# 29.8. Network architecture

Теперь соберём всё вместе.

Правильная network architecture должна разделять:

```text
UI
Messaging
Network
Authentication
Persistence
Backend
```

---

# Плохая архитектура

Например:

```text
Popup
 ├── fetch()
 ├── token handling
 ├── retry
 ├── cookies
 ├── error handling
 └── state update
```

И отдельно:

```text
Side Panel
 ├── fetch()
 ├── token handling
 ├── retry
 └── error handling
```

Это быстро приводит к duplication.

---

# Хорошая архитектура

```text
                         Extension
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
            Popup        Side Panel       Content
              │              │              │
              └──────────────┼──────────────┘
                             │
                         Messaging
                             │
                             ▼
                       Service Worker
                             │
                ┌────────────┼────────────┐
                ▼            ▼            ▼
             Auth         API Client    Cache
                │            │            │
                └────────────┼────────────┘
                             ▼
                           fetch()
                             │
                             ▼
                          Backend
```

---

# Network layer

Network layer отвечает за:

```text
HTTP
serialization
headers
timeouts
retry
errors
authentication integration
```

Например:

```text
src/
├── network/
│   ├── client.js
│   ├── errors.js
│   ├── retry.js
│   └── endpoints.js
│
├── auth/
│   ├── auth-service.js
│   └── token-store.js
│
└── background/
    └── service-worker.js
```

---

# API Client

Хороший API client должен скрывать детали `fetch()`.

Вместо:

```javascript
fetch(
    "https://api.example.com/users"
);
```

application code может использовать:

```javascript
api.users.getCurrent();
```

---

# Например

```javascript
class UsersApi {

    constructor(client) {
        this.client = client;
    }

    getCurrent() {
        return this.client.get("/me");
    }
}
```

---

# Network error model

Не стоит возвращать UI случайные native exceptions.

Лучше определить собственные ошибки:

```javascript
class NetworkError extends Error {}

class AuthenticationError extends Error {}

class ApiError extends Error {
    constructor(status, message) {
        super(message);
        this.status = status;
    }
}
```

Теперь UI может реагировать:

```javascript
try {
    await api.users.getCurrent();
} catch (error) {

    if (error instanceof AuthenticationError) {
        showLogin();
    }
}
```

---

# Timeout

`fetch()` сам по себе не должен рассматриваться как бесконечно ожидающая операция.

Используйте `AbortController`:

```javascript
const controller =
    new AbortController();

const timeout = setTimeout(
    () => controller.abort(),
    10_000
);

try {

    const response = await fetch(
        url,
        {
            signal: controller.signal
        }
    );

} finally {

    clearTimeout(timeout);
}
```

---

# Retry architecture

Не каждый request можно повторять.

Например:

```text
GET
```

обычно проще повторить.

А:

```text
POST /purchase
```

может привести к повторной операции.

Поэтому retry policy должна учитывать:

```text
HTTP method
idempotency
status code
network error
request semantics
```

---

# Cache

Network layer может использовать cache:

```text
UI
 ↓
API Client
 ↓
Cache
 ↓
Network
```

Например:

```text
GET /settings
```

может сначала читать:

```text
runtime cache
```

и только затем обращаться к server.

---

# Но cache — тоже state

Поэтому необходимо решить:

```text
Cache lifetime?
Cache owner?
Persistence?
Invalidation?
```

Например:

```text
runtime cache
```

может быть:

```text
memory
```

а более долгоживущий cache:

```text
storage.local
```

# Network requests и Service Worker lifecycle

Service Worker может быть остановлен.

Поэтому нельзя проектировать network layer так:

```text
global connection
global state
global session
```

как будто worker работает постоянно.

Вместо этого:

```text
event
 ↓
worker starts
 ↓
initialize required state
 ↓
request
 ↓
response
 ↓
worker may stop
```

---

# Long-running requests

Особое внимание требуется для:

```text
large downloads
streaming
long-lived connections
```

Нужно учитывать lifecycle Service Worker и особенности конкретного API.

Нельзя считать:

```text
Service Worker
    ↓
"работает всегда"
```

гарантированным поведением.

---

# Network request flow

Надёжный flow выглядит так:

```text
Event
  ↓
Service Worker starts
  ↓
Load required state
  ↓
Resolve authentication
  ↓
Build request
  ↓
fetch()
  ↓
Validate response
  ↓
Update state
  ↓
Send result
  ↓
Context receives result
```

---

# Network boundary

Очень полезно рассматривать backend как отдельную trust boundary:

```text
                 Extension
                     │
                     │ HTTPS
                     ▼
              ┌──────────────┐
              │   Backend    │
              └──────────────┘
```

Extension нельзя считать trusted server environment.

И наоборот:

> Backend не должен доверять extension только потому, что запрос пришёл от официального extension.

---

# Extension authentication

Правильнее идентифицировать пользователя через:

```text
account
session
token
OAuth identity
```

а не через:

```text
extension ID
```

Сам по себе extension ID не является authentication identity пользователя.

---

# Backend validation

Server должен самостоятельно проверять:

```text
authentication
authorization
request schema
rate limits
business rules
```

Нельзя переносить security logic исключительно в extension.

---

# HTTPS

Для production API необходимо использовать:

```text
https://
```

а не:

```text
http://
```

Это особенно важно для:

```text
authentication
tokens
personal data
payments
private API
```

> «Когда-нибудь может понадобиться API».

# Основные ошибки

## Ошибка 1. API calls из каждого context

```text
Popup → API
Panel → API
Options → API
Content → API
```

**Проблема:** duplication и сложность authentication.

---

## Ошибка 2. Hardcoded secret

```javascript
const SECRET = "...";
```

**Проблема:** secret находится у пользователя.

---

## Ошибка 3. Игнорирование CORS

```text
fetch()
 ↓
"почему браузер заблокировал?"
```

Нужно понимать origin и CORS model.

---

## Ошибка 4. Использование `<all_urls>` без необходимости

Это увеличивает permission surface.

---

## Ошибка 5. Хранение всего network state в Service Worker memory

Worker может завершиться.

---

## Ошибка 6. Бесконечный retry

```text
request
 ↓
fail
 ↓
retry
 ↓
fail
 ↓
retry
```

может превратить одну проблему в постоянную нагрузку.

---

## Ошибка 7. Смешивание authentication и API logic

Лучше:

```text
Auth Service
      +
API Client
```

чем один огромный объект.

---

## Ошибка 8. Игнорирование HTTP status

```javascript
const data = await response.json();
```

без:

```javascript
if (!response.ok)
```

может привести к неправильной обработке ошибок.

---

## Ошибка 9. Передача необработанных server responses в UI

Лучше иметь нормализованный error model.

---

## Ошибка 10. Отсутствие timeout

Network request не должен бездумно считаться бесконечным.

# Главная идея главы

`fetch()` — это только самый нижний уровень.

Профессиональная разработка Manifest V3 extension требует мыслить следующим образом:

```text
fetch()
   ↓
Network Client
   ↓
Authentication
   ↓
State
   ↓
Messaging
   ↓
Execution Context
```

И наоборот:

```text
User action
    ↓
Context
    ↓
Message
    ↓
Service Worker
    ↓
Network Layer
    ↓
Authentication
    ↓
fetch()
    ↓
Backend
```

Поэтому network subsystem расширения следует проектировать как **отдельный слой приложения**, а не как случайные вызовы `fetch()` из Popup, Content Script и Side Panel.

Главный принцип:

> **UI должен знать, что ему нужен результат сетевой операции. Он не должен знать все детали того, как extension устанавливает соединение с backend.**

Именно такое разделение позволяет построить расширение, которое остаётся управляемым при добавлении authentication, subscription, caching, retry, offline behavior и нескольких execution contexts.
