# Глава 44. Project 4 — Productivity Extension

В предыдущем проекте мы построили первое расширение с **Service Worker**, Action и message passing.

Теперь сделаем следующий шаг.

Мы создадим небольшое, но уже практически полезное расширение для повышения продуктивности:

> **Focus Mode Extension**

Расширение будет позволять пользователю включать и выключать режим концентрации на текущей странице.

В режиме Focus Mode расширение будет:

* изменять внешний вид страницы;
* скрывать отвлекающие элементы;
* показывать статус режима;
* сохранять настройку в `chrome.storage`;
* восстанавливать состояние после перезагрузки страницы;
* управляться через Popup.

Архитектура будет следующей:

```text
                    ┌──────────────────┐
                    │      Popup       │
                    │                  │
                    │  Focus: ON/OFF   │
                    └────────┬─────────┘
                             │
                             │ message
                             ▼
                    ┌──────────────────┐
                    │  Service Worker  │
                    │                  │
                    │  orchestration   │
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │     Storage      │
                    │                  │
                    │ focusEnabled     │
                    └────────┬─────────┘
                             │
                             │ state
                             ▼
                    ┌──────────────────┐
                    │  Content Script  │
                    │                  │
                    │  DOM / CSS       │
                    └────────┬─────────┘
                             │
                             ▼
                         Web Page
```

Этот проект особенно важен, потому что здесь впервые появляется полноценная цепочка:

```text
UI
 ↓
State
 ↓
Runtime
 ↓
Page
```

# 44.4. Архитектура runtime

На первый взгляд может показаться, что:

```text
popup.js
```

может напрямую управлять страницей.

Но это плохая архитектурная модель.

Правильнее:

```text
Popup
   │
   │ message
   ▼
Service Worker
   │
   │ message
   ▼
Content Script
   │
   ▼
DOM
```

Почему?

Потому что Popup — это временный UI.

После его закрытия:

```text
Popup
   ↓
destroy
```

Поэтому Popup не должен быть центром persistent application state.

# 44.6. Почему Popup является отдельным context

Popup — это не часть веб-страницы.

У нас существуют:

```text
Web Page
    │
    └── Content Script

Extension
    │
    ├── Popup
    └── Service Worker
```

Popup имеет собственный:

* DOM;
* JavaScript environment;
* lifecycle;
* global state.

Поэтому:

```javascript
document.querySelector(...)
```

в Popup работает с DOM Popup, а не с DOM текущей вкладки.

Это принципиально важно.

# 44.9. Popup lifecycle

Очень важно понимать жизненный цикл Popup.

Примерно:

```text
User clicks Action
        ↓
Popup created
        ↓
popup.html loaded
        ↓
popup.js executed
        ↓
User interacts
        ↓
User clicks outside
        ↓
Popup closes
        ↓
Popup destroyed
```

Поэтому нельзя рассчитывать на:

```javascript
let state = {
    enabled: true
};
```

как на persistent state.

После закрытия Popup этот объект исчезает.

# 44.10. Storage как источник persistent state

Наше состояние:

```text
focusEnabled
```

должно храниться не в Popup.

Не здесь:

```javascript
let focusEnabled = false;
```

а в:

```text
chrome.storage
```

Например:

```javascript
await chrome.storage.local.set({
    focusEnabled: true
});
```

Теперь состояние переживает:

* закрытие Popup;
* перезапуск Popup;
* перезагрузку страницы;
* перезапуск Service Worker.

---

# 44.11. Чтение состояния

Получить состояние:

```javascript
const result =
    await chrome.storage.local.get(
        "focusEnabled"
    );
```

Получим:

```javascript
{
    focusEnabled: true
}
```

Если значения ещё нет:

```javascript
{
    focusEnabled: undefined
}
```

Поэтому обычно используем default:

```javascript
const result =
    await chrome.storage.local.get({
        focusEnabled: false
    });
```

Теперь:

```javascript
result.focusEnabled
```

всегда будет иметь значение.

# 44.12. Почему `storage.local`

Manifest V3 предоставляет несколько storage areas.

В нашем проекте:

```text
storage.local
```

подходит лучше всего.

Она предназначена для локального persistent state extension.

Мы пока не будем использовать:

```text
storage.sync
storage.session
storage.managed
```

Подробно они рассматриваются в части Storage.

# 44.13. Первый Popup script

Создадим:

```text
popup.js
```

```javascript
const toggle =
    document.querySelector(
        "#focusToggle"
    );

const status =
    document.querySelector(
        "#status"
    );

init();

async function init() {

    const result =
        await chrome.storage.local.get({
            focusEnabled: false
        });

    toggle.checked =
        result.focusEnabled;

    updateStatus(
        result.focusEnabled

function updateStatus(enabled) {

    status.textContent =

            : "Focus mode is disabled";
}
```

Теперь Popup при открытии читает состояние из Storage.

# 44.19. Service Worker

Создадим:

```text
background.js
```

```javascript
chrome.runtime.onMessage.addListener(
    async (message) => {

        if (!message) {
            return;
        }

        switch (message.type) {

            case "SET_FOCUS_MODE":
                await setFocusMode(
                    message.enabled
                );
                break;
        }
    }
);
```

Теперь Service Worker является router.

# 44.20. Service Worker как orchestrator

Service Worker получает:

```javascript
{
    type: "SET_FOCUS_MODE",
    enabled: true
}
```

и должен:

1. проверить команду;
2. сохранить состояние;
3. найти нужную вкладку;
4. передать состояние Content Script.

То есть:

```text
Popup
  │
  ▼
Service Worker
  │
  ├── validate
  │
  ├── persist
  │
  └── dispatch
       │
       ▼
Content Script
```

# 44.32. Полный `background.js`

```javascript
chrome.runtime.onMessage.addListener(
    async (message) => {

        if (!message) {
            return;
        }

        switch (message.type) {

            case "SET_FOCUS_MODE":

                await setFocusMode(
                    message.enabled
                );

                break;
        }
    }
);

async function setFocusMode(enabled) {

    await chrome.storage.local.set({
        focusEnabled: enabled
    });

    const tabs =
        await chrome.tabs.query({
            active: true,
            currentWindow: true
        });

    const tab = tabs[0];

    if (
        typeof tab?.id !== "number"
    ) {
        return;
    }

    try {

        await chrome.tabs.sendMessage(
            tab.id,
            {
                type: "SET_FOCUS_MODE",
                enabled
            }
        );

    } catch (error) {

        console.warn(
            "Content Script unavailable:",
            error
        );
    }
}
```

# 44.35. Важная проблема архитектуры

Сейчас состояние записывается в Storage в двух местах:

```text
Popup
   ↓
storage.local.set()

Service Worker
   ↓
storage.local.set()
```

Это дублирование.

Лучше определить:

> Кто является владельцем state mutation?

Для более масштабной архитектуры логично сделать:

```text
Popup
  │
  │ command
  ▼
Service Worker
  │
  ▼
Storage
```

То есть Popup только отправляет намерение:

```javascript
{
    type: "SET_FOCUS_MODE",
    enabled: true
}
```

А Service Worker:

```text
validate
   ↓
persist
   ↓
notify
```

становится владельцем изменения состояния.

# 44.36. Улучшаем Popup

Тогда в Popup больше не нужно:


Оставляем:

```javascript
toggle.addEventListener(
```

Получаем:

```text
                     command
                        │

              ▼                   ▼
```

Это уже лучше.

# 44.37. Storage как Single Source of Truth


становится источником истины.

Не:

```text
Popup state
```

Не:

```text
Service Worker global variable
```

Не:


а:


# 44.38. Storage events

Есть ещё более интересный механизм.

Storage генерирует событие:

```javascript
chrome.storage.onChanged
```

Например:

```javascript
chrome.storage.onChanged.addListener(
    (changes, areaName) => {

        if (
            areaName !== "local"
        ) {
            return;
        }

        if (
            changes.focusEnabled
        ) {

            console.log(
                "Focus mode changed:",
                changes.focusEnabled.newValue
            );
        }
    }
);
```

Это позволяет contexts реагировать на изменения состояния.

# 44.45. Несколько вкладок

Теперь появляется интересная проблема.

Пользователь может иметь:

```text

Tab B
Tab C
```

Если:

```text
focusEnabled = true
```

хранится глобально, что означает:

> Focus Mode включён на всех вкладках?

Или:

> Только на текущей вкладке?

Наш текущий дизайн хранит:

```text
focusEnabled
```

как глобальное состояние extension.

Это означает:

```text

       │
       └── focusEnabled
```

Но реальное приложение может требовать:

```text

│

├── tab 102 → false
└── tab 103 → true
```

# 44.46. Global state vs tab state

Это фундаментальная архитектурная задача.

### Global state

```text
focusEnabled = true
```

Подходит, если режим глобальный.

### Per-tab state

```text
tabs[123].focusEnabled = true
```

Подходит, если каждая вкладка управляется независимо.

### Per-site state

```text
example.com → true
github.com  → false
```

Подходит, если настройки зависят от сайта.

Архитектуру state необходимо выбрать **до реализации storage model**.

# 44.60. Что нужно запомнить

После этой главы следует уметь объяснить следующие вопросы.

### Почему нужен Popup?

Потому что extension должен иметь временный пользовательский UI.

### Почему Popup не должен хранить persistent state?

Потому что его lifecycle очень короткий.

### Зачем нужен Service Worker?

Для background orchestration и обработки событий.

### Зачем нужен Content Script?

Для работы непосредственно с DOM веб-страницы.

### Зачем нужен Storage?

Для persistent state, который должен переживать lifecycle отдельных contexts.

### Зачем нужны messages?

Для коммуникации между независимыми execution contexts.

И главное:

```text
Popup
    ↓
Command
    ↓
Service Worker
    ↓
State
    ↓
Content Script
    ↓
DOM
```

— это один из базовых архитектурных шаблонов Manifest V3.

В следующем проекте эту архитектуру можно расширить до более реалистичного **Multi-tab Productivity Extension**, где состояние будет разделено на **global state, per-tab state и persistent settings**, а Service Worker начнёт координировать несколько одновременно работающих вкладок.
