# Часть XVI. Manifest V3 как платформа

# Глава 52. Manifest V3 и будущее Browser Extensions

Manifest V3 следует рассматривать не только как очередную версию manifest format.

За изменениями Manifest V3 стоит более глубокий переход в архитектуре browser extensions:

```text
Manifest V2
    │
    │  more imperative JavaScript
    │  persistent background
    │  browser-controlled interception
    ▼
Manifest V3
    │
    │  event-driven execution
    │  declarative APIs
    │  ephemeral runtime
    │  stronger isolation
    ▼
Future Extension Platform
```

Это не означает, что JavaScript исчезнет или что все extensions станут полностью declarative.

Смысл изменения в другом:

> **Чем больше логики браузер способен безопасно и эффективно выполнять сам, тем меньше extension должен реализовывать через постоянно работающий JavaScript runtime.**

Поэтому современная архитектура extension постепенно смещается от:

```text
Extension JavaScript
       ↓
Browser
```

к:

```text
Extension
   ↓
Declarative / Capability Model
   ↓
Browser Engine
```

Это изменение особенно важно для разработчика framework.

Если framework просто скрывает Manifest API за более удобным JavaScript API, он решает преимущественно проблему developer experience.

Если же framework умеет:

```text
analyze application
        ↓
determine capabilities
        ↓
generate manifest
        ↓
generate declarative rules
        ↓
generate minimal runtime
        ↓
package extension
```

он уже начинает работать на уровне **архитектуры платформы**.

---

# 52.1. Declarative future

Одно из наиболее важных направлений развития extensions — переход от imperative execution к declarative execution.

---

## 52.1.1. Imperative model

В imperative модели разработчик говорит браузеру:

```text
"Когда произойдёт событие,
запусти JavaScript,
проверь условие,
выполни действие."
```

Например:

```javascript
chrome.tabs.onUpdated.addListener((tabId, changeInfo, tab) => {
    if (tab.url?.includes("example.com")) {
        // perform action
    }
});
```

Логика выглядит так:

```text
Browser event
     ↓
JavaScript runtime
     ↓
Condition
     ↓
JavaScript logic
     ↓
Action
```

---

## 52.1.2. Declarative model

Declarative API позволяет описать:

```text
IF condition
THEN action
```

Например:

```text
URL matches X
        ↓
apply rule Y
```

Браузеру не обязательно запускать extension JavaScript для каждого события.

Он может выполнить правило непосредственно внутри browser engine.

---

## 52.1.3. Почему это важно

Представим extension, которое должно проверять каждый network request.

Imperative подход:

```text
Request
   ↓
Extension
   ↓
JavaScript
   ↓
Check
   ↓
Decision
   ↓
Browser
```

Declarative подход:

```text
Request
   ↓
Browser rule engine
   ↓
Decision
```

Второй путь потенциально:

* быстрее;
* дешевле по ресурсам;
* проще контролируется;
* меньше зависит от lifecycle extension;
* безопаснее.

---

## 52.1.4. Declarative API как browser-native runtime

Это приводит к важной архитектурной идее:

> Declarative rules можно рассматривать как программу, которую выполняет browser engine.

Например:

```text
Rule:

IF
    URL = *.example.com/*
AND
    resourceType = script

THEN
    BLOCK
```

Это уже почти мини-программа.

Но вместо:

```javascript
if (...) {
    ...
}
```

мы имеем:

```text
Rule → Browser Engine
```

---

# 52.1.5. Declarative APIs — не просто удобный API

Очень важно не воспринимать declarative API как синтаксический сахар.

Разница архитектурная.

Imperative:

```text
Extension owns execution
```

Declarative:

```text
Browser owns execution
```

Это фундаментальное изменение ownership.

---

# 52.1.6. Будущая архитектура

Можно ожидать всё более явного разделения:

```text
                 Extension
                     │
          ┌──────────┴──────────┐
          │                     │
   Declarative Logic       Imperative Logic
          │                     │
          ▼                     ▼
   Browser Engine        Extension Runtime
```

И хороший extension будет использовать imperative JavaScript только там, где declarative model недостаточна.

---

# 52.2. Less JavaScript

Manifest V3 не означает:

> «JavaScript больше не нужен».

Правильнее:

> **JavaScript должен использоваться там, где он действительно необходим.**

---

## 52.2.1. Почему JavaScript дорог

Каждый дополнительный runtime создаёт стоимость.

Например:

```text
JavaScript
   ↓
parse
   ↓
compile
   ↓
execute
   ↓
memory
   ↓
lifecycle management
```

Для небольшого действия это может быть избыточно.

---

## 52.2.2. Content Script тоже имеет стоимость

Если extension автоматически injects content script на каждую страницу:

```text
100 tabs
   ↓
100 page contexts
   ↓
100 content-script executions
```

Это уже существенная runtime surface.

Поэтому следует задавать вопрос:

> Действительно ли этот код должен выполняться на каждой странице?

---

## 52.2.3. Минимальный runtime

Хорошая архитектура стремится к:

```text
Browser
   ↓
Declarative capabilities
   ↓
Small JavaScript runtime
```

а не:

```text
Browser
   ↓
Large always-active JavaScript application
```

---

## 52.2.4. Less JavaScript ≠ less functionality

Это важное различие.

Можно иметь:

```text
less JavaScript
+
more browser capabilities
```

и получить:

```text
same functionality
+
better efficiency
```

Например, вместо реализации части request filtering через JavaScript можно использовать DNR rules.

---

## 52.2.5. JavaScript становится orchestration layer

В такой архитектуре JavaScript всё чаще выполняет роль:

```text
orchestrator
coordinator
UI logic
state management
business logic
integration layer
```

а не:

```text
low-level browser event processor
```

Это очень похожий переход на тот, который происходит в других системах:

```text
Manual execution
       ↓
Runtime
       ↓
Declarative configuration
       ↓
Engine-managed execution
```

---

# 52.3. Browser-managed execution

Это естественное продолжение предыдущего принципа.

---

## 52.3.1. Кто выполняет операцию?

В классической архитектуре:

```text
Extension
   ↓
JavaScript
   ↓
Browser API
```

В declarative architecture:

```text
Extension
   ↓
Rule / Capability
   ↓
Browser Engine
```

---

## 52.3.2. Browser знает больше

Браузер уже знает:

* состояние вкладок;
* navigation;
* network requests;
* frames;
* security boundaries;
* permissions;
* lifecycle;
* rendering;
* process state.

Поэтому нет необходимости заставлять extension дублировать часть этой логики.

---

## 52.3.3. Browser как execution engine

Можно представить будущую extension platform так:

```text
                    Browser
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
   Web Engine     Extension Engine   Rule Engine
       │               │                │
       ▼               ▼                ▼
      DOM          JavaScript       Declarative
                                     rules
```

Extension становится описанием capabilities, а browser выполняет большую часть низкоуровневой работы.

---

## 52.3.4. Преимущества

Browser-managed execution может дать:

### Performance

Меньше:

```text
IPC
JavaScript startup
event dispatch
context switching
```

### Security

Браузер лучше контролирует:

```text
permissions
rules
execution
isolation
```

### Lifecycle independence

Правило не обязательно зависит от того, запущен ли Service Worker.

### Resource efficiency

Не нужно держать дополнительный JavaScript runtime для каждой операции.

---

# 52.4. Capability-based architecture

Следующий важный шаг — мыслить не API, а capabilities.

---

## 52.4.1. Что такое capability

Capability — это конкретная возможность системы.

Например:

```text
read current tab
modify page
access storage
observe tabs
modify network requests
create side panel
receive keyboard command
```

Вместо вопроса:

> «Какой API мне вызвать?»

архитектор должен сначала спросить:

> **Какую capability требует приложение?**

---

# 52.4.2. Capability graph

Extension можно представить графом:

```text
Application
    │
    ├── Storage
    │
    ├── Tabs
    │
    ├── Content Script
    │
    ├── Network Rules
    │
    └── Side Panel
```

Каждая capability требует определённого механизма.

Например:

```text
Network filtering
       ↓
DNR
```

а:

```text
DOM modification
       ↓
Content Script
```

---

# 52.4.3. Permissions становятся capability declarations

Manifest можно рассматривать как декларацию capabilities:

```json
{
    "permissions": [
        "storage",
        "tabs"
    ],
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

То есть manifest говорит:

```text
This extension needs these capabilities.
```

---

# 52.4.4. Capability minimization

Если приложению требуется:

```text
storage
```

не следует автоматически давать:

```text
tabs
history
bookmarks
webNavigation
```

Capability-based design естественным образом приводит к принципу:

```text
Required capability
       ↓
Minimal permission
```

Это является продолжением Principle of Least Privilege.

---

# 52.4.5. Framework должен работать с capabilities

Современный framework может позволить разработчику писать:

```typescript
extension.capability("storage");
extension.capability("activeTab");
extension.capability("sidePanel");
```

а затем сам определить:

```text
required permissions
manifest entries
runtime APIs
generated files
```

Например:

```text
Application
     ↓
Capability analysis
     ↓
┌─────────────────────┐
│ storage              │
│ activeTab            │
│ sidePanel            │
└─────────────────────┘
     ↓
Manifest generation
```

Это уже значительно более мощная абстракция, чем просто wrapper вокруг `chrome.*`.

---

# 52.5. Compile-time extension development

Здесь появляется особенно интересное направление.

Если browser extension состоит из:

```text
Manifest
+
Declarative rules
+
Content Scripts
+
Service Worker
+
Extension Pages
```

то значительную часть архитектуры можно определить **до запуска extension**.

---

## 52.5.1. Runtime-centric development

Традиционный подход:

```text
Source Code
    ↓
Build
    ↓
JavaScript
    ↓
Browser
    ↓
Runtime decides what to do
```

---

## 52.5.2. Compile-time-centric development

Более современный подход:

```text
Source Application
       ↓
Compiler
       │
       ├── manifest.json
       ├── declarative rules
       ├── content scripts
       ├── service worker
       ├── extension pages
       └── permissions
              ↓
         Browser Runtime
```

Здесь compiler становится частью архитектуры extension.

---

# 52.5.3. Manifest как build artifact

Вместо ручного написания:

```json
{
    "manifest_version": 3,
    "permissions": [
        "storage"
    ]
}
```

framework может генерировать manifest:

```text
Application capabilities
        ↓
Manifest compiler
        ↓
manifest.json
```

Это позволяет:

* исключить ненужные permissions;
* автоматически генерировать paths;
* проверять dependencies;
* валидировать architecture;
* создавать разные builds.

---

# 52.5.4. Declarative rules как compiled output

Допустим, разработчик описывает:

```typescript
block({
    host: "*.ads.example.com",
    resourceTypes: ["script", "image"]
});
```

Compiler может создать:

```text
rules.json
```

который затем загружается browser engine.

Получается:

```text
High-level source
       ↓
Compiler
       ↓
Declarative IR
       ↓
Browser rule engine
```

---

# 52.5.5. Universal Extension IR

Здесь можно сделать ещё один шаг.

Вместо непосредственной генерации Chrome-specific файлов framework может иметь внутреннее intermediate representation:

```text
Extension Source
       ↓
Extension IR
       ↓
┌──────┼────────┐
▼      ▼        ▼
Chrome Firefox  Edge
```

Например:

```text
ExtensionIR
 ├── capabilities
 ├── contexts
 ├── permissions
 ├── routes
 ├── messages
 ├── storage
 ├── declarative rules
 └── UI
```

Затем compiler преобразует IR в конкретную browser implementation.

Это особенно важно для cross-browser framework.

---

# 52.5.6. Static analysis

Compile-time architecture позволяет проверять ошибки заранее.

Например:

```text
Content Script
      ↓
requires scripting capability
```

Compiler может сообщить:

```text
Missing permission: scripting
```

или:

```text
Content script references unavailable API
```

или:

```text
MAIN world requested without explicit declaration
```

Вместо обнаружения ошибки только во время выполнения:

```text
runtime error
```

получаем:

```text
compile-time error
```

---

# 52.5.7. Compile-time optimization

Compiler может анализировать:

```text
contexts
permissions
messages
rules
dependencies
assets
```

и удалять ненужный код.

Например:

```text
Application
    │
    ├── feature A ✓
    ├── feature B ✓
    ├── feature C ✗
    └── feature D ✗
```

После compilation:

```text
Production Extension
    │
    ├── feature A
    └── feature B
```

Это классический принцип:

> **Compile more, execute less.**

---

# 52.6. Extension frameworks

Появление Manifest V3 создаёт естественную потребность в новых abstraction layers.

---

## 52.6.1. Уровень 1 — API wrapper

Самый простой framework:

```text
Developer
   ↓
Framework API
   ↓
chrome.*
```

Например:

```typescript
tabs.query(...)
```

вместо:

```javascript
chrome.tabs.query(...)
```

Это удобно, но архитектурно неглубоко.

---

# 52.6.2. Уровень 2 — Component framework

Следующий уровень:

```text
Popup
SidePanel
Options
ContentScript
ServiceWorker
```

framework помогает организовать их как application components.

Например:

```text
Extension Application
│
├── Popup
├── SidePanel
├── Content
└── Background
```

Это уже значительно полезнее.

---

# 52.6.3. Уровень 3 — Runtime framework

Здесь framework начинает управлять:

```text
Lifecycle
Messaging
State
Storage
Events
Permissions
Contexts
```

Получается:

```text
Application
      ↓
Extension Runtime
      ↓
Manifest V3
```

---

# 52.6.4. Уровень 4 — Platform compiler

Это наиболее интересный уровень.

Framework получает:

```text
Application definition
```

и генерирует:

```text
manifest
contexts
permissions
messages
rules
runtime
assets
```

То есть:

```text
Developer
   ↓
Extension Framework
   ↓
Compiler / Build System
   ↓
Manifest V3
   ↓
Browser
```

---

# 52.6.5. Extension framework будущего

Можно представить:

```text
                 Developer
                     │
                     ▼
             Extension Framework
                     │
             ┌───────┴────────┐
             ▼                ▼
       Application IR    Static Analysis
             │
             ▼
          Compiler
             │
     ┌───────┼────────┐
     ▼       ▼        ▼
 Manifest   Rules   Runtime
     │       │        │
     └───────┼────────┘
             ▼
          Browser
```

Это уже не просто библиотека.

Это **platform toolchain**.

---

# 52.7. Почему современный extension framework должен быть Platform-first

Это главный вывод всей главы.

---

## 52.7.1. Что означает Platform-first

Platform-first означает:

> **Framework не пытается заменить Browser Platform. Он строится поверх неё и использует её возможности максимально эффективно.**

Архитектура:

```text
HTML
CSS
JavaScript
Web APIs
        ↓
Manifest V3
        ↓
Extension Framework
        ↓
Application
```

а не:

```text
Framework
   ↓
собственный runtime
   ↓
собственный DOM model
   ↓
собственный event system
   ↓
собственная platform abstraction
```

---

# 52.7.2. Не следует создавать «React для extensions»

Это очень важное архитектурное предостережение.

Можно создать:

```text
Extension React
```

который принесёт:

* virtual DOM;
* component runtime;
* reactive state;
* router;
* lifecycle;
* event abstraction.

Но если browser уже предоставляет большую часть необходимой инфраструктуры, framework может добавить значительный runtime overhead.

---

# 52.7.3. Framework должен усиливать browser

Лучше:

```text
Browser
   ↓
Native capabilities
   ↓
Framework
   ↓
Application
```

чем:

```text
Browser
   ↓
Framework runtime
   ↓
Framework abstractions
   ↓
Application
```

Первый вариант ближе к платформе.

---

# 52.7.4. HTML-first

Extension framework должен уважать HTML.

Например:

```html
<side-panel>
    <product-analysis></product-analysis>
</side-panel>
```

не обязательно превращать в огромную JavaScript abstraction.

Web Platform уже предоставляет:

```text
HTML
DOM
Custom Elements
Shadow DOM
CSS
Events
```

Framework должен использовать эти механизмы, а не обязательно заменять их.

---

# 52.7.5. Web API first

Если задача решается:

```javascript
fetch()
```

не нужно обязательно создавать:

```text
FrameworkFetchService
```

Если достаточно:

```javascript
localStorage
```

не всегда нужен:

```text
SuperStorageManager
```

Если нужен:

```javascript
MutationObserver
```

framework не должен скрывать его только ради сокрытия.

Абстракция оправдана тогда, когда она **действительно решает архитектурную проблему**.

---

# 52.7.6. Declarative-first

Если операция может быть реализована declaratively:

```text
Declarative API
```

должен иметь приоритет над:

```text
Service Worker
   ↓
JavaScript
   ↓
Imperative logic
```

Это можно выразить как:

```text
Declarative
    ↓
Native Web API
    ↓
Extension API
    ↓
Custom Runtime
```

Использовать следует самый нижний подходящий уровень.

---

# 52.7.7. Zero Replacement

Хороший framework не должен заставлять разработчика отказаться от:

```text
HTML
CSS
DOM
Web APIs
ESM
Web Components
Browser APIs
```

Он должен добавлять возможности:

```text
+
typed messaging
+
lifecycle management
+
capability system
+
build system
+
manifest generation
+
declarative compilation
```

Это принцип:

> **Add capabilities, don't replace the platform.**

---

# 52.7.8. Compile-time over runtime

Если проблему можно решить на этапе build:

```text
BUILD TIME
```

не следует решать её во время:

```text
RUNTIME
```

Например:

```text
permissions
manifest
context graph
message schemas
declarative rules
asset graph
```

могут быть статически известны.

Значит, framework может проверять и генерировать их заранее.

---

# 52.7.9. Минимальный runtime

Идеальный результат:

```text
Developer Code
      ↓
Compiler
      ↓
Optimized Extension
      ↓
Browser
```

а не:

```text
Developer Code
      ↓
Huge Framework Runtime
      ↓
Extension Runtime
      ↓
Browser
```

---

# 52.7.10. Platform-first architecture

В конечном счёте современный extension framework должен выглядеть примерно так:

```text
                    Application
                        │
                        ▼
               Extension Framework
                        │
        ┌───────────────┼────────────────┐
        │               │                │
        ▼               ▼                ▼
   Compiler         Runtime         Tooling
        │               │                │
        ▼               ▼                ▼
 Manifest / IR     Messaging        Debugging
 Rules generation  State            Testing
 Permissions       Lifecycle        Packaging
        │               │                │
        └───────────────┼────────────────┘
                        ▼
                 Manifest V3
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      Web Platform  Extension APIs  Browser Engine
```

---

# 52.8. Новая модель разработки

Из всех идей этой главы можно вывести новую development model.

Традиционный подход:

```text
Write JavaScript
       ↓
Call browser APIs
       ↓
Handle events
       ↓
Manage runtime
```

Современный подход:

```text
Describe application
        ↓
Declare capabilities
        ↓
Declare contexts
        ↓
Declare communication
        ↓
Declare rules
        ↓
Compiler
        ↓
Minimal runtime
        ↓
Browser-managed execution
```

Это очень близко к тому, как современные компиляторы превращают высокоуровневое описание программы в специализированный runtime.

# 52.9. Extension как compiled application

В результате extension можно рассматривать не просто как набор файлов:

```text
manifest.json
background.js
content.js
popup.html
```

а как **скомпилированное описание browser application**:

```text
                 Extension Source
                       │
                       ▼
              Extension Compiler
                       │
                       ▼
                Extension IR
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
    Manifest       Declarative       Runtime
                    Rules
        │              │               │
        └──────────────┼───────────────┘
                       ▼
                  Browser
```

Это открывает гораздо более интересную область для framework development.

# 52.10. Ключевые принципы будущего

На основании всего материала книги можно сформулировать несколько принципов.

### 1. Platform First

```text
Use the browser before building your own runtime.
```

### 2. Declarative First

```text
Prefer rules over continuously running JavaScript.
```

### 3. Compile More

```text
Move known decisions to build time.
```

### 4. Execute Less

```text
Minimize runtime work.
```

### 5. Least Privilege

```text
Request only required capabilities.
```

### 6. Browser Managed

```text
Let the browser own lifecycle and low-level execution.
```

### 7. Native Web

```text
HTML + CSS + DOM + Web APIs remain first-class.
```

### 8. Context Explicitness

```text
Know where every piece of code executes.
```

### 9. Typed Communication

```text
Treat context communication as a protocol.
```

### 10. Minimal Runtime

```text
The framework should disappear as much as possible at runtime.
```

# 52.11. Manifest V3 как переход к Platform Engineering

Самое важное изменение, которое Manifest V3 приносит разработчику, заключается не в отдельных API.

Оно заключается в изменении вопроса.

Старый вопрос:

> **Как мне написать JavaScript, который будет делать это в браузере?**

Новый вопрос:

> **Какую часть этой задачи я могу передать самому браузеру?**

Например:

```text
Network filtering
       ↓
DNR

Keyboard command
       ↓
Commands

Browser activation
       ↓
Declarative APIs

Persistent state
       ↓
Storage

Page integration
       ↓
Content Scripts

Long-lived application UI
       ↓
Side Panel
```

А JavaScript остаётся там, где действительно нужна динамическая логика:

```text
Business logic
Complex UI
State coordination
External APIs
User interaction
Application-specific computation
```

# 52.12. Итог главы

Будущее Browser Extensions, вероятно, будет развиваться не в сторону:

```text
more JavaScript
more runtime
more abstraction
```

а скорее:

```text
more capabilities
more declarative execution
more browser-managed operations
less unnecessary runtime
more compile-time analysis
```

Архитектурная модель постепенно выглядит так:

```text
                Developer
                    │
                    ▼
             Extension Framework
                    │
             Compile / Analyze
                    │
                    ▼
              Extension IR
                    │
        ┌───────────┼────────────┐
        ▼           ▼            ▼
     Manifest     Rules        Runtime
        │           │            │
        └───────────┼────────────┘
                    ▼
              Manifest V3
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 Web Platform              Browser Engine
        │                       │
        └───────────┬───────────┘
                    ▼
               Application
```

И именно поэтому **современный extension framework должен быть Platform-first**.

Его задача — не спрятать браузер за огромным runtime.

Его задача — **превратить возможности браузера в более высокий, типобезопасный, декларативный и компилируемый programming model**, сохранив при этом прямой доступ к Web Platform.

В идеальном случае framework работает по принципу:

```text
Developer writes less infrastructure
             ↓
Compiler generates more
             ↓
Browser executes more
             ↓
Extension runtime executes less
```

И это приводит к главной формуле современной разработки Manifest V3:

> **Describe more. Compile more. Execute less. Let the browser do the work.**

На этом уровне Manifest V3 перестаёт быть просто форматом `manifest.json` и начинает выглядеть как **платформа для создания browser-native applications**.
