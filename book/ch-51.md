# Часть XVI. Manifest V3 как платформа

# Глава 51. Manifest V3 vs обычное Web Application

На первый взгляд browser extension и обычное web application могут выглядеть почти одинаково.

Оба могут использовать:

* HTML;
* CSS;
* JavaScript;
* TypeScript;
* ESM;
* DOM;
* Fetch;
* Web Components;
* IndexedDB;
* Web APIs;
* современные frontend frameworks.

Поэтому у разработчика, впервые работающего с Manifest V3, возникает естественный вопрос:

> **Зачем вообще создавать Extension, если ту же функциональность можно реализовать как обычный web application?**

Это один из важнейших вопросов архитектуры.

Ответ заключается в том, что Extension — это не просто web application, упакованное в специальный формат.

У него другая:

* runtime model;
* security model;
* permission model;
* lifecycle;
* модель интеграции с браузером;
* модель доступа к страницам;
* набор privileged APIs.

Удобно представить это так:

```text
Web Application
      ↓
Web Platform
      ↓
Browser

Extension
      ↓
Web Platform
      +
Extension Platform
      ↓
Browser
```

Extension находится на другом уровне взаимодействия с браузером.

---

# 51.1. HTML Application

Начнём с наиболее фундаментального случая — обычного web application.

---

## 51.1.1. Что такое обычное web application

В простейшем случае это:

```text
index.html
style.css
app.js
```

Например:

```text
my-app/
├── index.html
├── styles.css
└── app.js
```

`index.html`:

```html
<!doctype html>
<html>
<head>
    <meta charset="UTF-8">
    <title>My Application</title>
</head>
<body>

    <h1>Hello Web</h1>

    <script type="module" src="./app.js"></script>
</body>
</html>
```

Приложение запускается через URL:

```text
https://example.com/
```

Browser рассматривает его как web origin:

```text
https://example.com
```

---

# 51.1.2. Основная модель

Упрощённо:

```text
URL
 ↓
Web Server
 ↓
HTML
 ↓
JavaScript
 ↓
Browser
 ↓
DOM
```

Приложение существует внутри конкретного web origin.

Например:

```text
https://example.com
```

Все ресурсы приложения принадлежат этому origin.

---

# 51.1.3. Что получает обычное web application

Web application получает стандартные возможности Web Platform:

```text
DOM
CSS
JavaScript
Fetch
Web Storage
IndexedDB
Web Workers
Web Crypto
Web Components
Service Workers
```

Но оно находится в рамках обычной web security model.

Например, приложение не может просто получить произвольный доступ к:

```text
browser tabs
other origins
browser history
extension APIs
```

---

# 51.1.4. Главный boundary — origin

Web application в первую очередь ограничено своим origin.

Например:

```text
https://app.example.com
```

не получает автоматический доступ к:

```text
https://bank.example.com
```

или:

```text
https://other-site.com
```

Это фундаментальный принцип безопасности Web Platform.

---

# 51.1.5. Обычное web application не является частью браузера

Оно работает **в браузере**, но не является privileged-компонентом браузера.

Это важное различие.

```text
Browser
│
├── Tabs
├── Windows
├── History
├── Bookmarks
├── Web pages
│
└── Web Application
```

Web application является одним из web consumers браузера.

---

# 51.2. PWA

Progressive Web App находится между обычным web application и более интегрированным browser application.

---

## 51.2.1. Что такое PWA

PWA использует Web Platform для создания приложения, которое может выглядеть и ощущаться более похоже на native application.

Обычно используются:

```text
Web App
+
Web App Manifest
+
Service Worker
+
Cache / Storage
+
Installability
```

Например:

```text
Browser
   ↓
Web Application
   ↓
Service Worker
   ↓
Offline/cache capabilities
```

---

# 51.2.2. PWA остаётся web application

Это принципиально.

PWA не превращается автоматически в browser extension.

У неё всё ещё действует обычная web security model.

Например:

```text
PWA
  ↓
https://example.com
```

не получает автоматически право:

```text
read arbitrary tabs
modify arbitrary websites
access browser history
```

---

# 51.2.3. Service Worker PWA и Service Worker Extension — разные концепции

Названия одинаковые, но архитектурная роль отличается.

### PWA

```text
Web Application
       ↓
Web Service Worker
       ↓
Cache / Fetch / Offline
```

### Manifest V3 Extension

```text
Extension
       ↓
Extension Service Worker
       ↓
Browser events / APIs / orchestration
```

Service Worker в обоих случаях является event-driven runtime, но окружение и доступные возможности различаются.

---

# 51.2.4. PWA ориентирована на приложение

PWA обычно отвечает на вопрос:

> Как сделать web application более похожим на установленное приложение?

Extension отвечает на другой вопрос:

> Как добавить браузеру новую возможность или интегрироваться с уже открытыми страницами?

Это очень важное различие.

---

# 51.3. Browser Extension

Browser Extension также использует Web Platform, но получает дополнительный слой возможностей.

Упрощённая модель:

```text
                Browser
                   │
        ┌──────────┴──────────┐
        │                     │
   Web Platform       Extension Platform
        │                     │
        └──────────┬──────────┘
                   ▼
              Extension
```

---

## 51.3.1. Extension имеет собственный origin

Extension получает собственный origin.

Упрощённо его можно представить как:

```text
chrome-extension://<extension-id>
```

В зависимости от браузера схема URL может отличаться, но концепция одна:

> Extension имеет собственную защищённую область ресурсов.

Например:

```text
chrome-extension://abc123/options.html
```

или:

```text
chrome-extension://abc123/popup.html
```

---

# 51.3.2. Extension состоит из нескольких contexts

Вместо одной web page extension может иметь:

```text
Service Worker
Content Scripts
Popup
Options Page
Side Panel
DevTools Page
Extension Pages
```

Поэтому:

```text
Web Application
     ↓
one application runtime
```

а:

```text
Extension
     ↓
multiple execution contexts
```

---

# 51.3.3. Extension может взаимодействовать с browser UI

Например:

```text
Toolbar
   ↓
Action
```

или:

```text
Keyboard
   ↓
Commands
```

или:

```text
Browser Side Panel
   ↓
Side Panel API
```

Это уже возможности, которых обычное web application в общем случае не имеет.

---

# 51.3.4. Extension может взаимодействовать с web pages

Это одно из главных отличий.

Например:

```text
User opens:
https://example.com

Extension
    ↓
Content Script
    ↓
DOM
```

Extension может реализовать:

* изменение страницы;
* добавление UI;
* анализ DOM;
* автоматизацию;
* contextual tools;
* page-specific functionality.

---

# 51.4. Различия runtime model

Это одно из самых важных различий.

---

## 51.4.1. Web application

Типичная модель:

```text
URL
 ↓
HTML
 ↓
Application
 ↓
Runtime
```

Пока пользователь находится на странице, application runtime существует.

Конечно, browser может ограничивать ресурсы, замораживать background tabs и т. д., но концептуально приложение является page-oriented.

---

## 51.4.2. Extension

Extension имеет несколько независимых runtime.

```text
Extension
│
├── Popup
├── Side Panel
├── Options
├── Content Scripts
├── Service Worker
└── DevTools
```

У каждого есть собственный lifecycle.

---

# 51.4.3. Extension runtime — event-driven

Особенно важен Service Worker:

```text
event
 ↓
startup
 ↓
handler
 ↓
operation
 ↓
suspend/termination
```

Нельзя предполагать:

```text
Service Worker
      ↓
always running
```

---

# 51.4.4. Web application — page-oriented

Упрощённо:

```text
open page
    ↓
application starts
    ↓
user interacts
    ↓
page remains open
    ↓
page closes
    ↓
application ends
```

Extension:

```text
browser event
     ↓
context starts
     ↓
operation
     ↓
context may stop
```

---

# 51.4.5. Runtime architecture

Можно сравнить так:

| Web App                 | Extension                           |
| ----------------------- | ----------------------------------- |
| Page-centric            | Multi-context                       |
| URL-centric             | Browser-centric                     |
| Origin-centric          | Extension-origin + page integration |
| Page lifecycle          | Multiple lifecycles                 |
| Mostly user page driven | Event + browser driven              |
| Standard Web APIs       | Web APIs + Extension APIs           |

---

# 51.5. Различия security model

Это ещё более фундаментальное различие.

---

## 51.5.1. Web application

Web application в основном защищается механизмами Web Platform:

```text
Origin
Same-Origin Policy
CORS
CSP
Sandboxing
Permissions Policy
```

Основной принцип:

> Один origin не должен получать произвольный доступ к другому origin.

---

# 51.5.2. Extension

Extension получает дополнительную security boundary.

Можно представить:

```text
Extension Origin
      │
      ├── Extension Pages
      ├── Service Worker
      └── Extension APIs
```

отдельно:

```text
Web Page
      │
      └── Content Script
```

И ещё:

```text
Page JavaScript
      ↕
MAIN world
```

Эти boundaries необходимо проектировать явно.

---

# 51.5.3. Content Script является особым boundary

Content Script может взаимодействовать с DOM страницы:

```text
Content Script
      ↓
DOM
```

но не должен рассматриваться как обычный page script.

У него есть доступ к определённым extension APIs, но он находится в контексте конкретной страницы.

---

# 51.5.4. Extension получает больше возможностей — значит, нужен больший уровень осторожности

Обычный web application:

```text
limited capabilities
        ↓
smaller privilege surface
```

Extension:

```text
more capabilities
        ↓
greater potential impact
```

Поэтому Manifest V3 усиливает значение:

* permissions;
* host permissions;
* isolated worlds;
* CSP;
* declarative APIs;
* restricted remote code execution.

---

# 51.5.5. Trust boundaries

Хорошее extension можно представить как набор зон доверия:

```text
                 Extension
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
 Extension      Service Worker   Content
   Pages                             Script
                                      │
                                      ▼
                                   Web Page
                                      │
                                      ▼
                                 Page Script
```

Чем ближе к внешней странице, тем осторожнее необходимо относиться к данным.

---

# 51.6. Различия permissions

В обычном web application нет эквивалента Manifest permissions в том же смысле.

Web application получает возможности через:

* Web APIs;
* user gestures;
* browser permission prompts;
* origin-based security;
* отдельные browser permission mechanisms.

Extension имеет явную permission model.

---

# 51.6.1. Extension permissions

Например:

```json
{
    "permissions": [
        "storage",
        "tabs"
    ]
}
```

И:

```json
{
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

Это является частью архитектуры extension.

---

# 51.6.2. Permission — часть контракта extension

Можно представить:

```text
Extension
   │
   ├── Functional requirements
   │
   ├── Permissions
   │
   └── Host permissions
```

Permissions определяют:

> какие возможности extension разрешено использовать.

---

# 51.6.3. Web application ограничивается origin

Например:

```text
https://myapp.com
```

имеет определённые возможности внутри browser security model.

Но это не означает:

```text
myapp.com
   ↓
access all browser tabs
```

Extension при наличии соответствующих capabilities может получить значительно более глубокую интеграцию.

---

# 51.6.4. Permission model должна быть минимальной

Это возвращает нас к принципу из главы 50:

```text
Required capability
        ↓
Required permission
```

а не:

```text
Let's request everything
```

---

# 51.7. Различия lifecycle

Lifecycle — одно из наиболее недооценённых различий.

---

## 51.7.1. Web application lifecycle

Упрощённо:

```text
Navigation
    ↓
Document created
    ↓
JavaScript startup
    ↓
Application running
    ↓
Navigation / close
    ↓
Document destroyed
```

---

# 51.7.2. Extension lifecycle

Extension имеет множество lifecycle.

Например:

### Popup

```text
open
 ↓
initialize
 ↓
user interaction
 ↓
close
```

### Content Script

```text
injection
 ↓
execute
 ↓
page remains
 ↓
navigation
 ↓
destroy
```

### Service Worker

```text
event
 ↓
startup
 ↓
execute
 ↓
idle
 ↓
termination
```

### Side Panel

```text
open
 ↓
active
 ↓
background
 ↓
close
```

---

# 51.7.3. Один extension — много lifecycles

Поэтому нельзя проектировать extension как:

```text
Application lifecycle
```

Нужно проектировать:

```text
Runtime lifecycle
+
Context lifecycle
+
State lifecycle
+
Communication lifecycle
```

---

# 51.7.4. State должен соответствовать lifecycle

Например:

```text
Popup state
    ↓
ephemeral
```

А:

```text
User settings
    ↓
persistent
```

А:

```text
Service Worker cache
    ↓
potentially ephemeral
```

Поэтому:

```text
Lifecycle
    ↓
determines state strategy
```

---

# 51.7.5. Navigation особенно важна

Обычное web application обычно управляет собственной страницей.

Extension может наблюдать за множеством вкладок:

```text
Tab 1
Tab 2
Tab 3
Tab 4
...
```

Каждая из них имеет собственную navigation lifecycle.

Поэтому extension может быть одновременно связано с большим количеством независимых web contexts.

---

# 51.8. Сравнение архитектуры

Рассмотрим одну и ту же задачу.

Допустим, мы хотим создать инструмент:

> «Показывать дополнительную информацию о товарах на Amazon».

---

## 51.8.1. Web application

Можно сделать:

```text
https://my-product-tool.com
```

Пользователь:

```text
Amazon
   ↓
copy product URL
   ↓
open application
   ↓
paste URL
   ↓
analyze
```

Архитектура:

```text
Browser
   ↓
Web App
   ↓
Backend/API
```

---

## 51.8.2. Extension

Extension может работать непосредственно на Amazon:

```text
Amazon page
      ↓
Content Script
      ↓
Read DOM
      ↓
Service Worker
      ↓
API
      ↓
Content Script
      ↓
Inject result
```

Пользователь вообще не покидает страницу.

Это совершенно другой UX.

---

# 51.8.3. Side Panel extension

Можно пойти ещё дальше:

```text
Amazon
│
├── Page
│
└── Side Panel
       │
       ├── Product data
       ├── Analysis
       └── Actions
```

Теперь extension становится companion application для текущей страницы.

---

# 51.9. Когда Web Application лучше

Extension не является автоматически лучшим выбором.

Web application предпочтительнее, если:

### 1. Приложению не нужен доступ к browser UI

Например:

```text
CRM
Dashboard
SaaS
Blog
Online editor
Analytics
```

---

### 2. Приложение работает с собственными данными

Например:

```text
Database
API
User account
Cloud storage
```

и не требует анализа других страниц.

---

### 3. Нужна максимальная доступность

Web application:

```text
URL
 ↓
Browser
 ↓
Application
```

не требует установки extension.

---

### 4. Основной runtime находится на сервере

Если приложение представляет собой:

```text
Browser
 ↓
Web App
 ↓
Backend
 ↓
Database
```

extension может быть совершенно не нужен.

---

### 5. Основной UX не связан с browsing

Например:

```text
Project management
Accounting
Documentation
Education platform
E-commerce
```

обычный web application обычно естественнее.

---

# 51.10. Когда PWA лучше

PWA особенно интересна, если нужны:

```text
Installability
Offline support
App-like UX
Caching
Local data
Push capabilities
```

но при этом не требуется глубокая интеграция с произвольными web pages или browser chrome.

Например:

```text
Task manager
Notes
Calendar
Inventory
Field application
Offline tool
```

могут быть хорошими PWA.

---

# 51.11. Когда Extension лучше

Extension становится особенно привлекательным, когда приложение должно **изменять или расширять browsing experience**.

---

## 51.11.1. Работа с текущей страницей

Например:

```text
Page
 ↓
Analyze
 ↓
Enhance
```

---

## 51.11.2. Работа с множеством вкладок

Например:

```text
Tabs
 ↓
collect
 ↓
organize
 ↓
search
 ↓
automate
```

---

## 51.11.3. Browser automation

Если пользователь хочет:

```text
shortcut
 ↓
extension
 ↓
perform browser action
```

Extension естественнее web application.

---

## 51.11.4. Contextual tools

Например:

```text
select text
 ↓
Extension
 ↓
translate / analyze / transform
```

---

## 51.11.5. Content modification

Например:

```text
Website
 ↓
Content Script
 ↓
DOM modification
```

---

## 51.11.6. Browser-wide utilities

Например:

```text
password tools
tab managers
developer tools
productivity tools
page analyzers
accessibility tools
privacy tools
```

Это естественная территория extensions.

---

# 51.12. Extension как browser augmentation

Это, пожалуй, наиболее полезное определение.

Web application:

> **Application running inside the browser.**

Extension:

> **Application extending the browser.**

Разница всего в одном слове, но архитектурно она огромна.

Можно представить:

```text
             Web Application

Browser ──────────────────────────┐
                                  │
                         Application
```

и:

```text
             Browser Extension

Browser
   │
   ├── Web Pages
   ├── Tabs
   ├── Windows
   ├── Browser UI
   │
   └── Extension
          │
          ├── Content Scripts
          ├── Service Worker
          ├── Side Panel
          └── Commands
```

Extension находится **рядом с браузером**, а не только внутри одной web page.

---

# 51.13. Главное архитектурное различие

Можно сформулировать различие одной строкой.

### Web Application

```text
I control my application.
```

### Browser Extension

```text
I participate in the browser runtime.
```

Это фундаментально разные модели.

Web application контролирует в основном:

```text
собственный UI
собственный state
собственный origin
```

Extension взаимодействует с:

```text
browser
tabs
windows
pages
events
browser UI
permissions
multiple contexts
```

# 51.15. Как выбирать технологию

Вместо вопроса:

> «Что сейчас популярнее — PWA или Extension?»

лучше задать несколько архитектурных вопросов.

### Вопрос 1

Нужно ли приложение работать с произвольными web pages?

```text
YES → Extension
NO  → Web App/PWA
```

### Вопрос 2

Нужно ли приложение взаимодействовать с tabs/windows?

```text
YES → Extension
NO  → Web App/PWA
```

### Вопрос 3

Нужна ли интеграция с browser UI?

```text
YES → Extension
NO  → Web App/PWA
```

### Вопрос 4

Нужны ли host permissions?

```text
YES → Extension
```

### Вопрос 5

Нужна ли только автономность/offline/installability?

```text
YES → PWA может быть достаточно
```

### Вопрос 6

Можно ли решить задачу стандартными Web APIs?

```text
YES → сначала рассмотреть Web App/PWA
NO  → рассмотреть Extension
```

---

# 51.16. Extension не заменяет Web Platform

Очень важно не сделать обратную ошибку.

После изучения Manifest V3 может возникнуть ощущение:

> «Теперь для любого web application нужно использовать Extension».

Это неправильно.

Extension следует использовать тогда, когда **browser integration является частью requirements**.

Если приложение может существовать как:

```text
HTML
+
CSS
+
JavaScript
+
Web APIs
```

то extension может быть ненужным усложнением.

---

# 51.17. Правило архитектурного выбора

Полезно использовать следующую последовательность:

```text
                Требование
                    │
                    ▼
       Можно решить Web Platform?
              /            \
            YES             NO
             │               │
             ▼               ▼
         Web App       Нужна browser
                         integration?
                           /      \
                         NO        YES
                         │          │
                         ▼          ▼
                      Web App   Extension
                                   │
                                   ▼
                             Manifest V3
```

Если требуется только:

```text
offline
install
local storage
notifications
app-like UX
```

сначала следует рассмотреть PWA.

Если требуется:

```text
content scripts
tabs
windows
browser UI
host permissions
commands
declarative browser APIs
```

Extension становится естественным выбором.

---

# 51.18. Итог

Обычное Web Application, PWA и Manifest V3 Extension используют одну фундаментальную технологическую основу — **Web Platform**, но находятся на разных уровнях интеграции с браузером.

Упрощённо:

```text
                    Browser
                       │
             ┌─────────┴─────────┐
             │                   │
        Web Platform       Extension Platform
             │                   │
       ┌─────┴─────┐             │
       │           │             │
    Web App       PWA        Manifest V3
```

### Web App

Предназначено для:

```text
application on the web
```

### PWA

Предназначено для:

```text
web application
+
app-like capabilities
```

### Extension

Предназначено для:

```text
browser augmentation
```

Именно последнее понятие является ключевым.

**Extension следует выбирать не потому, что это «ещё один способ сделать frontend», а потому, что задача требует участия приложения в browser runtime.**

Если приложение должно:

```text
observe pages
modify pages
coordinate tabs
react to browser events
provide browser UI
handle keyboard commands
run privileged browser operations
use host permissions
```

— Manifest V3 предоставляет архитектурную модель, которой обычное web application не обладает.

И наоборот, если приложение просто представляет собой:

```text
UI
+
API
+
Database
+
User account
```

то чаще всего правильнее оставить его обычным Web App или PWA.

**Главный критерий выбора можно выразить очень просто:**

```text
Does the application extend the web?

        ↓ YES

       Web App

Does the application extend the browser?

        ↓ YES

    Browser Extension
```

Это различие должно стать исходной точкой для всех последующих архитектурных решений.
