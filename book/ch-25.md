# Глава 25. Declarative Net Request

`declarativeNetRequest` — один из центральных API Manifest V3.

Если `declarativeContent` позволяет декларативно описывать **когда extension должен быть активен на странице**, то `declarativeNetRequest` переносит декларативную модель на другой фундаментальный уровень:

> **Что браузер должен делать с сетевыми запросами, соответствующими определённым правилам.**

Это особенно важно для:

* ad blockers;
* privacy extensions;
* tracker blockers;
* security extensions;
* URL redirectors;
* request filtering;
* некоторых proxy-like сценариев.

Главное отличие DNR от обычного JavaScript-подхода состоит в том, что extension не должен получать каждый сетевой запрос, запускать JavaScript и самостоятельно принимать решение.

Вместо этого extension регистрирует правила:

```text
IF request matches X
THEN perform Y
```

А браузер применяет эти правила самостоятельно.

---

# 25.1. DNR architecture

Начнём с архитектуры.

В imperative модели можно представить сетевую обработку так:

```text
Network Request
       ↓
Browser
       ↓
Extension
       ↓
JavaScript
       ↓
Inspect Request
       ↓
Decision
       ↓
Block / Redirect / Modify
```

Extension оказывается непосредственно вовлечённым в обработку каждого запроса.

---

# Declarative модель

DNR работает иначе:

```text
                    Extension
                        │
                        ▼
                     Rules
                        │
                        ▼
                 Browser DNR engine
                        │
                        ▼
                  Network Request
                        │
                  Rule matching
                        │
              ┌─────────┼─────────┐
              ▼         ▼         ▼
            Allow      Block    Redirect
```

Extension задаёт **правила**, а browser runtime занимается их применением.

---

# Почему это архитектурно важно

Рассмотрим страницу:

```text
https://example.com
```

Она может загрузить:

```text
HTML
CSS
JavaScript
Images
Fonts
XHR
Fetch
Analytics
Ads
Trackers
```

Одна страница может породить десятки или сотни requests.

Если extension должен обрабатывать каждый запрос через JavaScript:

```text
Request 1 → JS
Request 2 → JS
Request 3 → JS
...
Request 100 → JS
```

это создаёт существенную runtime нагрузку.

DNR позволяет сделать:

```text
Request
   ↓
Browser rule engine
   ↓
Match
   ↓
Action
```

без необходимости запускать extension JavaScript для каждого запроса.

---

# DNR как policy engine

На архитектурном уровне DNR можно представить как:

```text
Extension policy
       ↓
Rule representation
       ↓
Browser policy engine
       ↓
Network enforcement
```

Extension говорит:

> Эти requests должны обрабатываться определённым образом.

Браузер отвечает за enforcement этой политики.

---

# Permission

Для использования DNR требуется соответствующее permission:

```json
{
  "permissions": [
    "declarativeNetRequest"
  ]
}
```

В зависимости от конкретной модели использования также могут потребоваться host permissions.

Например:

```json
{
  "manifest_version": 3,
  "name": "Request Filter",
  "version": "1.0",
  "permissions": [
    "declarativeNetRequest"
  ],
  "host_permissions": [
    "https://example.com/*"
  ]
}
```

Конкретная permission model зависит от используемых возможностей и типа правил.

---

# Главная идея DNR

Вместо:

```javascript
onRequest(request => {

    if (matches(request)) {
        block(request);
    }

});
```

мы описываем:

```text
Rule:

IF
    request matches condition

THEN
    block
```

Это и есть декларативное программирование сетевого поведения.

---

# 25.2. `declarativeNetRequest`

API доступен через:

```javascript
chrome.declarativeNetRequest
```

Он предоставляет механизмы:

* работы с правилами;
* управления dynamic rules;
* управления session rules;
* управления rulesets;
* получения информации о правилах;
* анализа доступных возможностей API.

---

# Три основных типа правил

Практически важно сразу разделить правила на три категории:

```text
Declarative Net Request
│
├── Static rules
├── Dynamic rules
└── Session rules
```

Они отличаются lifecycle и способом управления.

---

# Static rules

Static rules поставляются вместе с extension.

Например:

```text
rules_1.json
```

и подключаются через manifest.

Их можно представить как:

```text
Extension package
       │
       └── rules.json
              ↓
         Browser
```

Они подходят для большого заранее известного набора правил.

Например:

```text
ads
trackers
known malicious domains
```

---

# Dynamic rules

Dynamic rules изменяются во время работы extension.

Например:

```text
User adds custom block rule
       ↓
Extension
       ↓
Dynamic rule
```

Они подходят для:

* пользовательских настроек;
* custom filters;
* правил, загруженных из configuration;
* персонализированного поведения.

---

# Session rules

Session rules существуют только в рамках текущей browser session.

Это полезно для временных правил.

Например:

```text
Temporary rule
       ↓
Current session
       ↓
Browser restart
       ↓
Rule disappears
```

Такой lifecycle особенно удобен для временных режимов.

---

# 25.3. Rulesets

Большой набор DNR rules обычно организуется в **ruleset**.

Можно представить:

```text
Ruleset
│
├── Rule 1
├── Rule 2
├── Rule 3
├── ...
└── Rule N
```

Например:

```text
ads.json
```

может содержать:

```text
10 000 rules
```

А extension может иметь несколько rulesets:

```text
Extension
│
├── Ads rules
├── Tracking rules
├── Privacy rules
└── Security rules
```

---

# Почему нужны rulesets

Без группировки пришлось бы работать с огромным плоским набором правил.

Ruleset позволяет логически организовать policy.

Например:

```text
rules/
    ads.json
    trackers.json
    privacy.json
    security.json
```

Концептуально:

```text
                  Extension
                      │
             ┌────────┼────────┐
             ▼        ▼        ▼
            Ads   Trackers  Privacy
          ruleset  ruleset   ruleset
```

---

# Static ruleset в Manifest

Static rulesets описываются через:

```json
{
  "declarative_net_request": {
    "rule_resources": [
      {
        "id": "ads",
        "enabled": true,
        "path": "rules/ads.json"
      }
    ]
  }
}
```

Здесь:

```text
id
```

идентифицирует ruleset,

```text
enabled
```

определяет его первоначальное состояние,

а:

```text
path
```

указывает файл с правилами.

---

# Rule file

Пример отдельного правила:

```json
{
  "id": 1,
  "priority": 1,
  "action": {
    "type": "block"
  },
  "condition": {
    "urlFilter": "ads.example.com"
  }
}
```

Теперь рассмотрим его по частям.

---

# Rule ID

```json
"id": 1
```

Каждое правило должно иметь идентификатор в рамках соответствующего ruleset.

Он используется browser runtime для идентификации правила.

---

# Priority

```json
"priority": 1
```

Priority определяет относительный приоритет правил.

Это важно, когда несколько правил потенциально соответствуют одному request.

Например:

```text
Rule A
priority = 1

Rule B
priority = 10
```

Приоритет влияет на разрешение конкурирующих правил в соответствии с моделью DNR.

---

# Action

```json
"action": {
  "type": "block"
}
```

описывает:

> Что делать с matching request?

---

# Condition

```json
"condition": {
  "urlFilter": "ads.example.com"
}
```

описывает:

> Когда правило должно сработать?

Получается:

```text
Rule
│
├── condition
│      ↓
│   WHEN
│
└── action
       ↓
     THEN
```

---

# 25.4. Static rules

Static rules являются частью extension package.

Например:

```text
extension/
├── manifest.json
├── service-worker.js
└── rules/
    └── ads.json
```

Manifest:

```json
{
  "manifest_version": 3,

  "name": "Simple Blocker",
  "version": "1.0.0",

  "permissions": [
    "declarativeNetRequest"
  ],

  "host_permissions": [
    "<all_urls>"
  ],

  "declarative_net_request": {
    "rule_resources": [
      {
        "id": "ads",
        "enabled": true,
        "path": "rules/ads.json"
      }
    ]
  }
}
```

---

# Static rules как immutable policy

Смысл static rules:

```text
Build time
    ↓
rules.json
    ↓
Extension package
    ↓
Browser
```

Это хорошо подходит для:

* известных ad lists;
* tracker lists;
* security lists;
* заранее подготовленных policies.

---

# Advantages

Static rules имеют несколько важных преимуществ:

* поставляются вместе с extension;
* известны заранее;
* хорошо подходят для больших rule collections;
* не требуют генерации каждого правила в runtime.

---

# Но static не означает immutable навсегда

При обновлении extension package правила могут измениться.

Например:

```text
Version 1
    ↓
ads.json v1

Extension update

Version 2
    ↓
ads.json v2
```

Поэтому:

```text
static
```

означает прежде всего:

> rules are part of the extension's static resources.

---

# 25.5. Dynamic rules

Dynamic rules позволяют изменять правила без изменения самого extension package.

Например, пользователь нажал:

```text
Block this domain
```

Extension может добавить dynamic rule.

Архитектура:

```text
User
 ↓
UI
 ↓
Service Worker
 ↓
updateDynamicRules()
 ↓
Browser
 ↓
Dynamic rule
```

---

# Почему dynamic rules нужны

Представим privacy extension.

У каждого пользователя могут быть свои настройки:

```text
Block:
    tracker-a.com
    tracker-b.com

Allow:
    trusted-site.com
```

Невозможно заранее включить все пользовательские решения в static rules.

Поэтому нужны dynamic rules.

---

# Управление

Концептуально API позволяет:

```javascript
chrome.declarativeNetRequest.updateDynamicRules({
    addRules: [
        // new rules
    ],

    removeRuleIds: [
        // IDs
    ]
});
```

То есть extension может:

```text
add
+
remove
```

dynamic rules.

---

# Dynamic rules и storage

Важно различать:

```text
chrome.storage
```

и:

```text
DNR dynamic rules
```

Storage хранит application data:

```text
user settings
preferences
state
```

DNR хранит browser-level request policy.

Например:

```text
Storage:
    blockTracking = true

DNR:
    rule #1001
    rule #1002
    rule #1003
```

---

# Не нужно дублировать состояние без причины

Плохая архитектура:

```text
Storage
    ↓
1000 settings

DNR
    ↓
1000 equivalent rules
```

и extension постоянно синхронизирует их без необходимости.

Лучше определить источник истины:

```text
User configuration
        ↓
Policy compiler
        ↓
DNR rules
```

---

# DNR как compiled policy

Очень интересная архитектурная модель:

```text
User configuration
        ↓
Policy
        ↓
Compile
        ↓
DNR rules
        ↓
Browser
```

Например:

```text
User:
"Block social trackers"

        ↓

Policy:
tracker category = social

        ↓

Generated rules:
rule 1
rule 2
rule 3
...

        ↓

DNR engine
```

Это уже напоминает compiler pipeline.

---

# 25.6. Session rules

Session rules похожи на dynamic rules, но имеют другой lifecycle.

Их смысл:

> правила должны существовать временно.

Например:

```text
User enables:
"Block this domain for this session"
```

Extension создаёт session rule:

```text
Current browser session
       ↓
rule active
```

После окончания соответствующей session правило больше не применяется.

---

# Когда session rules полезны

### Temporary blocking

```text
Block example.com
until browser restart
```

### Debugging

```text
Temporary redirect
```

### Temporary user mode

```text
Privacy mode
```

### Tab/session specific policies

Когда правило не имеет смысла сохранять постоянно.

---

# Сравнение

| Тип     | Lifecycle         | Основное назначение                 |
| ------- | ----------------- | ----------------------------------- |
| Static  | Extension version | Базовые правила                     |
| Dynamic | Persistent        | Пользовательские/изменяемые правила |
| Session | Current session   | Временные правила                   |

---

# 25.7. Request matching

Теперь самое важное: как DNR определяет, соответствует ли request правилу?

Rule содержит:

```json
"condition": {
  ...
}
```

В condition могут использоваться различные параметры.

---

# URL filtering

Например:

```json
{
  "condition": {
    "urlFilter": "tracker"
  }
}
```

Это означает, что URL request проверяется на соответствие filter.

---

# Regex

Для некоторых сценариев возможно использовать регулярное выражение:

```json
{
  "condition": {
    "regexFilter": ".*tracker.*"
  }
}
```

Но regex следует использовать осторожно.

Он может быть:

* сложнее;
* дороже;
* труднее для сопровождения;
* ненужным, если достаточно обычного `urlFilter`.

---

# Resource types

Можно ограничивать правило определёнными типами ресурсов.

Например концептуально:

```text
script
image
stylesheet
font
xmlhttprequest
sub_frame
```

Тогда:

```text
Block tracker scripts
```

не обязательно означает:

```text
Block every request to tracker domain
```

Можно ограничить правило только:

```text
script
```

---

# Request domains

Можно ограничивать:

```text
initiatorDomains
requestDomains
excludedRequestDomains
```

Это позволяет различать:

```text
Кто инициировал request?
```

и:

```text
Куда направляется request?
```

Это очень важное различие для ad blockers.

---

# Initiator

Например:

```text
page:
example.com

request:
tracker.com
```

Здесь:

```text
initiator = example.com
request domain = tracker.com
```

Ad blocker может захотеть заблокировать:

```text
tracker.com
```

только когда запрос инициирован определёнными сайтами.

---

# Tab context

В некоторых сценариях правила также могут быть ограничены определённым tab context.

Это полезно для:

* временных правил;
* пользовательских действий;
* контекстного поведения.

---

# Request method

Можно учитывать HTTP method.

Например:

```text
GET
POST
PUT
DELETE
```

Это позволяет создавать более специфичные правила.

---

# First-party vs third-party

Для privacy extensions особенно важна идея:

```text
First-party
```

против:

```text
Third-party
```

Например:

```text
example.com
   ↓
tracker.com
```

может рассматриваться как third-party request.

Ad blocker может применять более строгую policy к third-party traffic.

---

# Matching pipeline

Можно представить процесс:

```text
Request
   │
   ▼
URL
   │
   ▼
Domain
   │
   ▼
Resource type
   │
   ▼
Initiator
   │
   ▼
Other conditions
   │
   ▼
Matching rules
```

После этого браузер выбирает соответствующее действие по правилам DNR.

---

# 25.8. Blocking rules

Самая известная action:

```json
{
  "action": {
    "type": "block"
  }
}
```

Она означает:

> matching request должен быть заблокирован.

---

# Пример

```json
[
  {
    "id": 1,
    "priority": 1,
    "action": {
      "type": "block"
    },
    "condition": {
      "urlFilter": "ads.example.com"
    }
  }
]
```

Теперь:

```text
Request
https://ads.example.com/banner.js
```

может соответствовать:

```text
urlFilter
```

и получить:

```text
block
```

---

# Blocking pipeline

```text
Network Request
      ↓
DNR
      ↓
Match?
   ┌──┴──┐
  No     Yes
   │       │
   ▼       ▼
Continue  Block
```

---

# Почему blocking — мощный механизм

Extension может вмешиваться в сетевое поведение ещё до того, как ресурс будет нормально обработан страницей.

Это делает DNR особенно полезным для:

* advertising;
* tracking;
* malware domains;
* unwanted resources.

---

# Но block должен быть точным

Слишком широкое правило:

```text
urlFilter = "ads"
```

может заблокировать совершенно неожиданные requests.

Например:

```text
https://example.com/advertisement-guide
```

может случайно соответствовать filter.

Поэтому хорошие filters должны быть максимально точными.

---

# 25.9. Redirect rules

Другой важный action:

```json
{
  "action": {
    "type": "redirect"
  }
}
```

Теперь request не блокируется, а перенаправляется.

Концептуально:

```text
Request A
   ↓
DNR
   ↓
redirect
   ↓
Resource B
```

---

# Пример

```json
{
  "id": 10,
  "priority": 1,
  "action": {
    "type": "redirect",
    "redirect": {
      "url": "https://example.com/replacement"
    }
  },
  "condition": {
    "urlFilter": "old.example.com"
  }
}
```

Теперь:

```text
old.example.com
       ↓
redirect
       ↓
example.com/replacement
```

---

# Redirect use cases

Redirect полезен для:

### Canonical URLs

```text
old-url
   ↓
new-url
```

### Privacy

```text
tracking URL
   ↓
clean URL
```

### Security

```text
unsafe resource
   ↓
safe replacement
```

### Custom workflows

```text
external URL
   ↓
extension-controlled resource
```

---

# Redirect к extension resource

В некоторых сценариях extension может перенаправить request на ресурс самого extension.

Например:

```text
Request
   ↓
DNR
   ↓
extension resource
```

Для этого нужно учитывать ограничения `web_accessible_resources`.

---

# Redirect ≠ navigation API

Важно не путать:

```text
DNR redirect
```

с:

```text
chrome.tabs.update()
```

Первый работает на уровне network request policy.

Второй управляет вкладкой.

Это разные архитектурные уровни.

---

# 25.10. Header modification

DNR также позволяет в определённых сценариях модифицировать HTTP headers.

Концептуально:

```text
Request
   ↓
DNR
   ↓
Modify headers
   ↓
Continue request
```

---

# Request headers

Например, extension может добавить, удалить или изменить определённые request headers, если это разрешено соответствующей моделью API.

Концептуально:

```json
{
  "action": {
    "type": "modifyHeaders",
    "requestHeaders": [
      {
        "header": "X-Example",
        "operation": "set",
        "value": "1"
      }
    ]
  }
}
```

---

# Response headers

Аналогично существуют сценарии изменения response headers.

Например:

```text
Response
   ↓
DNR
   ↓
Modify response headers
   ↓
Browser
```

---

# Почему header modification полезен

Например:

```text
Security
Privacy
Compatibility
CORS-related workflows
Request normalization
```

Но header modification имеет дополнительные ограничения и требует особенно осторожного проектирования.

---

# Не превращайте DNR в proxy

Важно понимать:

> DNR не является универсальным HTTP proxy.

Нельзя ожидать, что extension сможет произвольно:

```text
intercept
read
rewrite
reconstruct
```

любой request и response так, как это сделал бы полноценный network proxy.

API намеренно ограничен.

---

# 25.11. Rule limits

Declarative архитектура имеет цену:

> **browser должен контролировать размер и сложность rule set.**

Поэтому существуют ограничения на количество и типы правил.

---

# Почему существуют limits

Без ограничений extension мог бы создать:

```text
10
100
1 000
100 000
1 000 000
...
```

сложных правил.

Это могло бы негативно влиять на:

* память;
* CPU;
* browser startup;
* rule evaluation;
* безопасность.

Поэтому браузер устанавливает quotas.

---

# Static rules limits

Для static rules существуют ограничения на:

* количество rulesets;
* количество enabled rulesets;
* количество статических правил;
* дополнительные особенности browser implementation.

---

# Dynamic rules limits

Dynamic rules также имеют quota.

Это важно, если extension генерирует большое количество пользовательских правил.

Например:

```text
User configuration
      ↓
Generate 100 000 rules
```

может оказаться невозможным.

---

# Session rules limits

Для session rules существуют отдельные ограничения.

Поэтому нельзя предполагать:

```text
session rules = unlimited
```

---

# Regex limits

Regex rules особенно важны.

Слишком сложные регулярные выражения могут иметь ограничения и дополнительные требования.

Поэтому:

```text
urlFilter
```

часто предпочтительнее:

```text
regexFilter
```

если задача может быть решена без regex.

---

# Архитектурный вывод

Rule engine необходимо проектировать как **ограниченный ресурс**.

Поэтому:

```text
Bad:

Generate everything
```

лучше заменить на:

```text
Good:

Generate only meaningful rules
```

---

# Rule compilation

Для большого extension полезно иметь внутренний compiler:

```text
User policy
      ↓
Normalize
      ↓
Optimize
      ↓
Deduplicate
      ↓
Compile
      ↓
DNR rules
```

Например:

```text
100 user preferences
       ↓
300 raw rules
       ↓
optimization
       ↓
120 actual rules
```

---

# Rule deduplication

Если два правила эквивалентны:

```text
Rule A
example.com/ads

Rule B
example.com/ads
```

нет смысла хранить оба.

Поэтому compiler должен уметь:

```text
normalize
+
deduplicate
```

---

# Rule specificity

Лучше использовать:

```text
specific rule
```

вместо:

```text
global rule
```

если это возможно.

Например:

```text
Block script from tracker.com
```

лучше, чем:

```text
Block everything containing "tracker"
```

---

# 25.12. DNR vs `webRequest`

Это одно из самых важных сравнений Manifest V3.

---

# `webRequest`

`webRequest` исторически позволял extension получать информацию о сетевых requests и реагировать на них через JavaScript.

Концептуально:

```text
Request
   ↓
webRequest event
   ↓
Extension JavaScript
   ↓
Decision
```

Это imperative model.

---

# DNR

DNR:

```text
Rules
   ↓
Browser
   ↓
Request
   ↓
Match
   ↓
Action
```

Это declarative model.

---

# Главное различие

| Характеристика        | `webRequest`       | DNR                 |
| --------------------- | ------------------ | ------------------- |
| Model                 | Imperative         | Declarative         |
| Logic                 | JavaScript         | Rules               |
| Runtime               | Extension          | Browser             |
| Flexibility           | Очень высокая      | Ограниченная        |
| Performance model     | JS event handling  | Browser rule engine |
| Lifecycle             | Зависит от runtime | Browser-managed     |
| Arbitrary logic       | Да                 | Нет                 |
| Blocking architecture | Event-driven       | Rule-driven         |
| MV3 direction         | Ограниченнее       | Основной подход     |

---

# Почему MV3 предпочитает DNR

Причина не только в performance.

Есть более глубокая архитектурная идея:

```text
MV2:

Extension controls network logic
```

против:

```text
MV3:

Browser controls network policy
```

Это уменьшает количество произвольного extension code, который должен участвовать в критическом browser path.

---

# `webRequest` всё ещё существует

Важно не делать ошибочный вывод:

> "`webRequest` полностью исчез."

Нет.

API продолжает существовать, но его возможности и особенно blocking use cases в MV3 ограничены иначе, чем в MV2.

Для большинства типичных блокировочных сценариев MV3 предполагает использование DNR.

---

# Когда DNR лучше

Используйте DNR, если задача:

```text
IF request matches X
THEN block/redirect/modify
```

---

# Когда нужен imperative network logic

Если задача требует:

```text
Request
 ↓
Complex computation
 ↓
External service
 ↓
Dynamic decision
 ↓
Custom algorithm
```

DNR может оказаться недостаточно гибким.

Тогда необходимо смотреть на другие APIs и архитектурные подходы.

---

# DNR как security boundary

DNR предоставляет важную архитектурную границу:

```text
Extension
     │
     │ declares policy
     ▼
Browser
     │
     │ enforces policy
     ▼
Network
```

Extension не получает полный контроль над network stack.

Он получает **ограниченный декларативный capability**.

---

# 25.13. Архитектура ad blocker

Теперь соберём все идеи в реальный пример.

Ad blocker — один из лучших способов понять DNR.

---

# Требования

Представим extension:

> Emerge Blocker

Он должен:

1. блокировать advertising requests;
2. блокировать trackers;
3. разрешать пользовательские исключения;
4. поддерживать custom rules;
5. показывать статистику;
6. иметь UI;
7. минимально использовать Service Worker.

---

# Плохая архитектура

Наивный вариант:

```text
Every Request
     ↓
Service Worker
     ↓
JavaScript
     ↓
Check against filter list
     ↓
Decision
     ↓
Block
```

Проблемы:

* огромное количество events;
* постоянная runtime activity;
* сложная lifecycle model;
* больше JavaScript execution;
* больше IPC/runtime overhead;
* необходимость самостоятельно реализовывать matching engine.

---

# Хорошая MV3 architecture

```text
                  Ad Blocker
                      │
          ┌───────────┼───────────┐
          │           │           │
          ▼           ▼           ▼
       Static       Dynamic      Session
       rules        rules        rules
          │           │           │
          └───────────┼───────────┘
                      ▼
                 DNR Engine
                      │
                      ▼
                Network Requests
```

---

# Static filter lists

Основная база:

```text
ads
trackers
malware
privacy
```

может быть представлена static rules.

Например:

```text
rules/
    ads.json
    trackers.json
    privacy.json
```

---

# User custom rules

Пользователь добавляет:

```text
Block:
example-ad.com
```

Extension:

```text
UI
 ↓
Service Worker
 ↓
Dynamic DNR rule
```

---

# Temporary rules

Пользователь нажимает:

```text
Disable tracking for this session
```

Extension:

```text
Session rule
```

---

# UI

Popup или Side Panel показывает:

```text
Blocked today: 1,284

Trackers: 723
Ads:      481
Other:    80
```

Но здесь важно разделять:

```text
DNR
```

и:

```text
Statistics
```

DNR отвечает за enforcement.

Service Worker отвечает за application logic и сбор необходимой статистики в рамках доступных API.

---

# Архитектура

```text
                         USER
                          │
                          ▼
                  Popup / Side Panel
                          │
                          ▼
                    Service Worker
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
          Storage       DNR API      Tabs API
             │            │
             │            ▼
             │        Rule engine
             │            │
             │            ▼
             │       Network requests
             │
             ▼
           State
```

---

# Filter list pipeline

Пусть у нас есть внешний filter list:

```text
Filter List
```

Например:

```text
||ads.example.com^
||tracker.example.net^
```

Нельзя просто считать его внутренним DNR ruleset.

Необходимо преобразование:

```text
Filter syntax
      ↓
Parser
      ↓
Normalized rule
      ↓
DNR rule
```

---

# Compiler architecture

Для большого ad blocker это может выглядеть так:

```text
External Filter List
        │
        ▼
      Parser
        │
        ▼
   Intermediate Model
        │
        ▼
   Rule Optimizer
        │
        ▼
   DNR Compiler
        │
        ▼
    DNR Rules
        │
        ▼
      Browser
```

Это очень интересная архитектурная задача.

Фактически extension становится:

> **compiler from filtering policy to browser-native network rules.**

---

# Почему это лучше

Browser уже умеет:

```text
match URL
match domain
match resource type
match initiator
block
redirect
modify headers
```

Не нужно реализовывать собственный network engine.

Extension предоставляет policy.

Browser предоставляет execution.

---

# Ad blocker как policy compiler

Полная архитектура:

```text
                    Filter Lists
                         │
                         ▼
                      Parser
                         │
                         ▼
                 Internal Policy
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
          Optimizer             Exceptions
              │                     │
              └──────────┬──────────┘
                         ▼
                   DNR Compiler
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Static         Dynamic        Session
        Rules          Rules           Rules
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                     DNR Engine
                         │
                         ▼
                      Network
```

---

# Exceptions

Ad blocker обязательно должен поддерживать:

```text
Allow example.com
```

То есть:

```text
Block rule
+
Allow rule
```

Архитектура становится:

```text
Request
   ↓
Rules
   ↓
Priority / matching
   ↓
Exception?
   ├── yes → allow
   └── no  → block
```

---

# Почему priority важен

Представим:

```text
Rule 1:
Block tracker.com

Rule 2:
Allow tracker.com on trusted.com
```

Без механизмов приоритета и исключений невозможно выразить:

> блокировать tracker.com вообще, кроме trusted.com.

Поэтому rule precedence является фундаментальной частью архитектуры DNR.

---

# First-party exceptions

Типичная ad blocker policy:

```text
Block third-party trackers
```

но:

```text
Allow first-party analytics
```

Это требует более точного request matching.

                 ┌────────┴────────┐
                 ▼                 ▼
              Popup            Side Panel
                 │                 │
                 └────────┬────────┘
                          ▼
                    Service Worker
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
       Storage          DNR API          Tabs

# Где находится Service Worker

И здесь проявляется главный принцип MV3.

Service Worker **не является network filter**.

Он является:

```text
orchestrator
```

Он:

* устанавливает rules;
* обновляет rules;
* обрабатывает user actions;
* управляет configuration;
* координирует contexts;
* работает со storage.

А DNR:

```text
enforces network policy
```

---

# Очень важное разделение ответственности

```text
Service Worker
──────────────────────────
"Что должна делать система?"

DNR
──────────────────────────
"Какие network requests разрешены?"

Content Script
──────────────────────────
"Что делать с DOM?"

Popup / Side Panel
──────────────────────────
"Как пользователь управляет системой?"
```

Это гораздо более чистая архитектура.

# DNR и философия MV3

Теперь можно увидеть общую картину.

В предыдущих главах:

```text
declarativeContent
```

позволил передать браузеру:

```text
Page context policy
```

Теперь:

```text
declarativeNetRequest
```

позволяет передать браузеру:

```text
Network policy
```

Получается:

```text
                 Manifest V3
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
 Declarative Content      Declarative Net Request
          │                       │
          ▼                       ▼
   Page policy              Network policy
          │                       │
          └───────────┬───────────┘
                      ▼
                Browser Runtime
```

---

# Главный архитектурный вывод

DNR показывает, что Declarative API — это не просто более удобный синтаксис.

Это изменение **ownership**:

```text
Before:

Extension
    ↓
detect
    ↓
decide
    ↓
execute
```

После перехода к declarative model:

```text
Extension
    ↓
declare policy
    ↓
Browser
    ↓
evaluate
    ↓
enforce
```

---

# DNR как browser-native firewall

Для некоторых задач DNR концептуально можно представить как:

```text
Extension Policy
       ↓
Browser Firewall-like Rule Engine
       ↓
Network
```

Это не полноценный OS firewall и не proxy, но архитектурная аналогия полезна.

Extension определяет policy:

```text
ALLOW
BLOCK
REDIRECT
MODIFY
```

а браузер применяет её к network traffic.

---

# Что нужно запомнить

### 1. DNR — declarative

```text
Rules
+
Conditions
+
Actions
```

а не:

```text
Request
+
JavaScript callback
```

### 2. Browser выполняет rules

Extension не обязан обрабатывать каждый request самостоятельно.

### 3. Есть три основных типа правил

```text
Static
Dynamic
Session
```

### 4. Rules организуются в rulesets

```text
Ruleset
   ↓
Rules
```

### 5. Основные действия

```text
block
redirect
modifyHeaders
```

### 6. Matching может учитывать различные характеристики request

Например:

```text
URL
domain
initiator
resource type
method
```

### 7. DNR имеет ограничения

Это намеренно ограниченный rule engine, а не произвольный JavaScript runtime.

### 8. DNR и `webRequest` — разные архитектурные модели

```text
webRequest → imperative
DNR        → declarative
```

### 9. Service Worker не заменяет DNR

Лучшее разделение:

```text
Service Worker
    = orchestration

DNR
    = network policy enforcement
```

### 10. Ad blocker — идеальный пример

```text
Filter Lists
     ↓
Policy
     ↓
Compiler
     ↓
DNR Rules
     ↓
Browser
     ↓
Network
```

# Финальная модель главы

После изучения `declarativeContent` и `declarativeNetRequest` архитектура Manifest V3 начинает выглядеть гораздо яснее:

```text
                         EXTENSION
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
   Declarative Content   Service Worker   Declarative Net Request
          │                  │                  │
          ▼                  ▼                  ▼
     Page Policy        Application       Network Policy
                             Logic
          │                  │                  │
          └──────────────────┼──────────────────┘
                             ▼
                       Browser Runtime
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
            Pages          Tabs          Network
```

Именно здесь проявляется одна из главных идей Manifest V3:

> **Extension не должен самостоятельно управлять всем браузером. Extension должен описывать намерение, а браузер должен выполнять ту часть работы, которую он способен выполнить безопаснее, эффективнее и предсказуемее.**

DNR — один из самых ярких примеров этой философии. Он превращает сетевую обработку из потенциально произвольного JavaScript-кода в **ограниченную, проверяемую и browser-managed policy system**.

Следующим естественным шагом является изучение **остальных Declarative APIs и их границ**, после чего можно перейти к следующему крупному уровню MV3 — **Storage и состояние extension**, поскольку именно там возникает фундаментальная проблема: если Service Worker ephemeral, **где и как должно жить состояние приложения?**
