# Глава 39. Performance

Производительность browser extension имеет несколько особенностей, которых нет у обычного web application.

Обычное веб-приложение в основном контролирует собственный runtime:

```text
Browser
   ↓
Web Application
   ↓
JavaScript Runtime
   ↓
UI
```

Manifest V3 extension работает иначе:

```text
                         Browser
                            │
            ┌───────────────┼───────────────┐
            │               │               │
            ▼               ▼               ▼
       Service Worker   Content Script    Extension UI
            │               │               │
            ▼               ▼               ▼
        Browser APIs     Page DOM        Extension DOM
```

При этом браузер сам управляет значительной частью жизненного цикла extension.

Service Worker может быть остановлен.

Content Script может запускаться на множестве страниц и frames.

Popup существует очень недолго.

Side Panel может оставаться открытой долгое время.

Поэтому performance extension — это не просто вопрос:

> «Насколько быстро выполняется JavaScript?»

Нужно рассматривать как минимум:

```text
Startup
Lifecycle
CPU
Memory
DOM
Messaging
Storage
Network
Injection
```

Главный принцип этой главы:

> **Хорошее Manifest V3 extension выполняет как можно меньше работы, как можно позже, как можно ближе к месту, где эта работа действительно нужна.**

---

# 39.1. Startup performance

Startup performance — это время и стоимость запуска extension.

У extension существует несколько типов startup.

Например:

```text
Browser startup
      ↓
Extension initialization
      ↓
Service Worker startup
```

Но Service Worker может также запускаться значительно позже:

```text
Browser running
      ↓
User event
      ↓
Worker cold start
      ↓
Event handler
```

Поэтому важно различать:

```text
initial startup
```

и:

```text
event-driven startup
```

---

# Что происходит при startup

Упрощённо:

```text
Event
  ↓
Service Worker starts
  ↓
JavaScript loads
  ↓
Modules initialize
  ↓
Listeners become available
  ↓
Event handler executes
```

Каждая стадия имеет стоимость.

Если extension содержит большой bundle:

```text
worker.js
   ↓
2 MB JavaScript
   ↓
parse
   ↓
compile
   ↓
initialize
```

даже простое событие становится дороже.

---

# Startup budget

Полезно мыслить о startup как о бюджете:

```text
Cold Start Budget
├── Load JS
├── Parse JS
├── Compile JS
├── Initialize modules
├── Load state
└── Process event
```

Чем меньше этот бюджет, тем быстрее extension реагирует.

---

# Не загружайте всё сразу

Плохая архитектура:

```javascript
import "./analytics.js";
import "./network.js";
import "./dom.js";
import "./database.js";
import "./rules.js";
import "./ui.js";
import "./debug.js";
```

Даже если конкретному event требуется только:

```text
storage
```

весь dependency graph может участвовать в startup.

---

# Lazy loading

Лучше загружать тяжёлую функциональность только при необходимости.

Например:

```javascript
chrome.runtime.onMessage.addListener(async message => {
    if (message.type === "ANALYZE") {
        const { analyze } = await import("./analyzer.js");

        return analyze(message.data);
    }
});
```

Архитектура:

```text
Worker startup
     │
     ├── core
     │
     └── event
            │
            └── ANALYZE
                   ↓
              load analyzer
```

Это особенно полезно для редко используемых функций.

---

# Минимальный bootstrap

Хороший Service Worker может начинаться примерно так:

```javascript
import { registerListeners } from "./runtime/listeners.js";

registerListeners();
```

А не:

```text
startup
 ↓
initialize entire application
 ↓
load everything
 ↓
connect everything
 ↓
load everything from storage
 ↓
initialize all services
```

---

# 39.2. Service Worker cold starts

Service Worker в Manifest V3 — ephemeral runtime.

Он может существовать:

```text
Event
  ↓
Worker
  ↓
Work
  ↓
Suspension
```

а затем снова:

```text
New Event
  ↓
New Worker Instance
```

Поэтому cold start — нормальный сценарий, а не исключение.

---

# Cold start cost

Условно:

```text
Cold Start
    │
    ├── Worker creation
    ├── Script loading
    ├── Module initialization
    ├── State restoration
    └── Event handling
```

Если каждая операция дорогая, пользователь почувствует задержку.

---

# Плохая модель

Нельзя проектировать worker как:

```javascript
let application = initializeHugeApplication();
```

с ожиданием, что этот объект будет жить постоянно.

Вместо этого:

```text
Persistent State
       ↓
Storage
       ↓
Ephemeral Runtime
```

---

# Быстрый bootstrap

Service Worker должен делать только то, что необходимо для обработки событий.

Например:

```javascript
chrome.runtime.onMessage.addListener(handleMessage);

chrome.action.onClicked.addListener(handleAction);

chrome.alarms.onAlarm.addListener(handleAlarm);
```

А тяжёлые компоненты можно загружать по требованию.

---

# Избегайте startup I/O без необходимости

Плохой вариант:

```javascript
const settings = await chrome.storage.local.get();
const profile = await loadProfile();
const cache = await loadCache();
const rules = await loadRules();
const remoteConfig = await fetchConfig();
```

и только после этого:

```javascript
registerListeners();
```

Это создаёт проблему:

```text
Worker starts
    ↓
many async operations
    ↓
listeners not ready
```

Лучше зарегистрировать listeners как можно раньше:

```javascript
chrome.runtime.onMessage.addListener(handleMessage);
chrome.action.onClicked.addListener(handleAction);
```

а состояние загружать непосредственно перед использованием.

---

# Cold start и state

Очень полезная модель:

```text
Event
  ↓
Load only required state
  ↓
Process event
  ↓
Persist result
```

Например:

```javascript
async function handleAction() {
    const { settings } =
        await chrome.storage.local.get("settings");

    // use settings
}
```

а не:

```text
startup
 ↓
load entire database
 ↓
load all settings
 ↓
load all cached data
 ↓
wait
```

---

# Cold start measurement

Не следует оптимизировать cold start на основе ощущений.

Измеряйте:

```text
worker start
    ↓
handler begin
    ↓
handler complete
```

Например:

```javascript
const start = performance.now();

await processEvent();

console.log(
    `Event processing: ${performance.now() - start}ms`
);
```

---

# 39.3. Content Script cost

Content Script — один из самых дорогих компонентов extension, потому что он работает **в контексте web pages**.

Если extension использует:

```json
{
    "content_scripts": [
        {
            "matches": ["<all_urls>"],
            "js": ["content.js"]
        }
    ]
}
```

то код потенциально запускается на огромном количестве страниц.

---

# Cost multiplication

Предположим:

```text
Content Script = 20 KB
```

Сам по себе это немного.

Но extension работает на:

```text
100 tabs
```

и:

```text
10 frames per page
```

потенциально получаем множество execution contexts.

Поэтому стоимость content script нужно рассматривать не как:

```text
20 KB
```

а как:

```text
20 KB × number of execution contexts
```

---

# Чем меньше content script, тем лучше

Content Script не должен превращаться в:

```text
Entire Application
```

Плохая архитектура:

```text
Content Script
├── UI framework
├── router
├── state management
├── network client
├── analytics
├── database
└── business logic
```

Лучше:

```text
Content Script
├── DOM integration
├── small runtime
└── messaging
```

а тяжёлую работу переносить:

```text
Service Worker
или
Web Worker
```

где это архитектурно оправдано.

---

# Match patterns как performance control

Это не только вопрос permissions.

Если extension нужен только на:

```text
https://example.com/*
```

не стоит использовать:

```text
<all_urls>
```

без необходимости.

Лучше:

```json
{
    "matches": [
        "https://example.com/*"
    ]
}
```

Это уменьшает количество страниц, на которых браузеру приходится активировать extension logic.

---

# `run_at`

Время запуска content script влияет на page performance.

Например:

```json
{
    "run_at": "document_start"
}
```

означает раннюю инъекцию.

Это необходимо только тогда, когда extension действительно должен работать очень рано.

Если раннее выполнение не требуется:

```json
{
    "run_at": "document_idle"
}
```

часто является более разумным вариантом.

---

# Не сканируйте весь DOM без необходимости

Плохой вариант:

```javascript
const nodes = document.querySelectorAll("*");
```

Затем:

```javascript
for (const node of nodes) {
    // ...
}
```

На большой странице это может быть очень дорого.

Лучше:

```javascript
document.querySelectorAll(".product");
```

или:

```javascript
document.querySelectorAll("[data-product]");
```

---

# MutationObserver

MutationObserver очень полезен для динамических сайтов:

```javascript
const observer = new MutationObserver(records => {
    // process changes
});

observer.observe(document.body, {
    childList: true,
    subtree: true
});
```

Но это мощный механизм, который легко использовать неправильно.

---

# Плохой MutationObserver

Например:

```javascript
new MutationObserver(() => {
    scanEntirePage();
}).observe(document.body, {
    childList: true,
    subtree: true
});
```

Если сайт постоянно изменяет DOM:

```text
DOM mutation
 ↓
full scan
 ↓
DOM mutation
 ↓
full scan
 ↓
...
```

может возникнуть огромная нагрузка.

---

# Debouncing

Лучше группировать изменения:

```text
Mutation
Mutation
Mutation
Mutation
     ↓
 debounce
     ↓
single scan
```

Например:

```javascript
let scheduled = false;

const observer = new MutationObserver(() => {
    if (scheduled) return;

    scheduled = true;

    queueMicrotask(() => {
        scheduled = false;
        processChanges();
    });
});
```

Для более крупных batches можно использовать другие scheduling strategies.

---

# 39.4. DOM performance

DOM — один из наиболее дорогих ресурсов content script.

Проблема возникает не только при чтении DOM, но и при его изменении.

---

# DOM read

Например:

```javascript
element.getBoundingClientRect();
```

или:

```javascript
getComputedStyle(element);
```

может заставить браузер синхронизировать layout в определённых сценариях.

---

# DOM write

Например:

```javascript
element.style.width = "...";
element.style.height = "...";
```

может привести к layout/recalculation.

Если чтения и записи постоянно перемешиваются:

```text
read
write
read
write
read
write
```

браузеру сложнее оптимизировать rendering pipeline.

---

# Batch operations

Лучше группировать операции:

```text
Read
Read
Read
   ↓
Calculate
   ↓
Write
Write
Write
```

а не:

```text
Read
Write
Read
Write
Read
Write
```

---

# Используйте CSS вместо JavaScript

Если нужно только изменить визуальное состояние:

Плохо:

```javascript
element.style.display = "none";
element.style.color = "red";
element.style.opacity = "0.5";
```

Иногда лучше:

```javascript
element.classList.add("extension-hidden");
```

а CSS:

```css
.extension-hidden {
    display: none;
}
```

Это делает presentation logic проще.

---

# Не создавайте тысячи DOM nodes

Если extension отображает список из:

```text
10 000 items
```

не нужно обязательно создавать:

```text
10 000 DOM elements
```

Можно использовать:

```text
pagination
virtualization
incremental rendering
```

---

# Shadow DOM

Shadow DOM может быть полезен для изоляции UI extension:

```text
Page
 │
 ├── Page DOM
 │
 └── Extension Shadow Root
```

Это уменьшает конфликты CSS.

Но Shadow DOM не делает работу бесплатной.

Большой сложный UI внутри страницы всё равно имеет стоимость.

---

# 39.5. Message overhead

Contexts общаются через message passing:

```text
Popup
   ↓
sendMessage()
   ↓
Service Worker
```

или:

```text
Content Script
   ↓
Port
   ↓
Service Worker
```

Каждое сообщение имеет стоимость.

---

# Message lifecycle

Условно:

```text
sender
   ↓
serialize
   ↓
browser transport
   ↓
deserialize
   ↓
receiver
```

Поэтому не следует передавать огромные объекты без необходимости.

---

# Плохое сообщение

Например:

```javascript
chrome.runtime.sendMessage({
    type: "PAGE_STATE",
    html: document.documentElement.outerHTML
});
```

Если HTML страницы огромный, сообщение становится тяжёлым.

---

# Лучше передавать идентификаторы

Вместо:

```javascript
{
    type: "ANALYZE",
    entirePage: hugeObject
}
```

можно:

```javascript
{
    type: "ANALYZE_PAGE",
    tabId: 123
}
```

а worker уже определяет, что необходимо получить.

Но выбор зависит от архитектуры и доступности данных.

---

# Не превращайте messaging в data bus

Плохая архитектура:

```text
Content Script
   ↓
10 MB state
   ↓
Service Worker
   ↓
5 MB result
   ↓
Side Panel
```

Message passing должен использоваться прежде всего для:

```text
commands
events
small data
references
results
```

а не для постоянной передачи огромных state snapshots.

---

# Batch messages

Вместо:

```text
message 1
message 2
message 3
message 4
message 5
```

можно иногда использовать:

```text
single batch message
```

Например:

```javascript
{
    type: "BATCH",
    items: [...]
}
```

Это уменьшает количество communication events.

---

# Long-lived Port

Если требуется постоянный поток данных:

```text
Content Script
     │
     │ Port
     ▼
Service Worker
```

может быть эффективнее, чем множество независимых сообщений.

Но Port нельзя использовать только ради производительности.

Если коммуникация редкая:

```text
sendMessage()
```

обычно проще.

---

# Request/response size

Нужно измерять не только количество сообщений:

```text
messages/sec
```

но и размер:

```text
bytes/message
```

Потому что:

```text
1 × 10 MB
```

может быть хуже, чем:

```text
100 × 10 KB
```

в зависимости от workload.

---

# 39.6. Storage performance

`chrome.storage` удобен, но его нельзя воспринимать как обычную in-memory variable.

Например:

```javascript
await chrome.storage.local.get("settings");
```

имеет стоимость.

---

# Не читать storage постоянно

Плохой код:

```javascript
for (const item of items) {
    const settings =
        await chrome.storage.local.get("settings");

    process(item, settings);
}
```

Это создаёт:

```text
N storage operations
```

Лучше:

```javascript
const { settings } =
    await chrome.storage.local.get("settings");

for (const item of items) {
    process(item, settings);
}
```

---

# Batch storage operations

Вместо:

```javascript
await chrome.storage.local.set({ a });
await chrome.storage.local.set({ b });
await chrome.storage.local.set({ c });
```

часто лучше:

```javascript
await chrome.storage.local.set({
    a,
    b,
    c
});
```

Это уменьшает количество операций.

---

# Storage как persistence layer

Хорошая архитектура:

```text
Fast Runtime State
       │
       ▼
Memory
       │
       ▼
Persistent State
       │
       ▼
chrome.storage
```

Но для Service Worker нельзя полагаться на memory как на единственный источник истины.

Поэтому:

```text
memory
= cache

storage
= persistence
```

в подходящих сценариях.

---

# Storage cache

Например:

```javascript
let settingsCache;
```

После первого чтения:

```text
storage
  ↓
cache
  ↓
many reads
```

Это может быть существенно быстрее.

Но нужно учитывать синхронизацию:

```text
storage.onChanged
        ↓
update cache
```

---

# Не храните всё в storage

`chrome.storage` не является заменой полноценной database system.

Если нужно хранить большие объёмы структурированных данных, стоит рассмотреть:

```text
IndexedDB
```

или другую подходящую архитектуру.

---

# `storage.session`

Для ephemeral state можно использовать:

```text
chrome.storage.session
```

если семантика данных подходит.

Это позволяет избежать необходимости сохранять некоторые временные данные как долгоживущие persistent state.

---

# Storage events

Если несколько contexts используют один state:

```text
Popup
   │
   ├── storage
   │
Worker
   │
Side Panel
```

изменения можно синхронизировать через:

```javascript
chrome.storage.onChanged
```

Это часто лучше, чем постоянно пересылать state через messages.

---

# 39.7. Network performance

Network является ещё одним большим источником latency.

Например:

```text
Content Script
      ↓
Worker
      ↓
fetch()
      ↓
Server
      ↓
response
      ↓
Worker
      ↓
Content Script
```

Каждый шаг добавляет стоимость.

---

# Не делайте network request без необходимости

Плохая архитектура:

```text
every DOM mutation
       ↓
fetch()
```

На динамическом сайте это может создать:

```text
hundreds of requests
```

---

# Debounce network

Вместо:

```text
change
 ↓
request

change
 ↓
request

change
 ↓
request
```

используйте:

```text
change
change
change
change
   ↓
debounce
   ↓
single request
```

---

# Cache

Если данные редко меняются:

```text
Request
  ↓
Cache?
  ├── yes → return
  └── no
        ↓
      Network
        ↓
      Cache
```

Это особенно полезно для:

```text
configuration
metadata
API responses
rules
```

---

# Request deduplication

Если одновременно возникают:

```text
request A
request A
request A
```

не обязательно выполнять три network operations.

Можно использовать:

```text
in-flight request
```

архитектуру:

```text
Request A
   ↓
Promise
   ├── caller 1
   ├── caller 2
   └── caller 3
```

Все получают один результат.

---

# Network timeout

Любой внешний network request должен иметь понятную стратегию timeout.

Плохая архитектура:

```text
fetch()
   ↓
wait forever
```

Лучше:

```text
fetch
 ↓
timeout
 ├── success
 └── failure
```

---

# Retry

Retry также имеет стоимость.

Плохой сценарий:

```text
request
 ↓
failure
 ↓
retry
 ↓
failure
 ↓
retry
 ↓
retry
 ↓
...
```

Нужно использовать:

```text
limited retries
backoff
```

и учитывать тип ошибки.

---

# Не отправляйте страницу целиком

Если серверу нужен только:

```text
title
url
selected text
```

не нужно отправлять:

```text
document.documentElement.outerHTML
```

Вместо:

```javascript
{
    html: hugeHTML
}
```

лучше:

```javascript
{
    title,
    url,
    text
}
```

если этого достаточно.

---

# Network batching

Если сервер поддерживает batch API:

```text
request 1
request 2
request 3
```

можно иногда преобразовать в:

```text
batch request
```

Но batching имеет смысл только тогда, когда задержка ожидания batch не ухудшает UX.

---

# 39.8. Minimizing extension runtime

Это один из наиболее важных принципов Manifest V3.

Extension не должна постоянно работать просто потому, что она установлена.

---

# Плохая модель

```text
Browser starts
      ↓
Extension starts
      ↓
Extension runs forever
      ↓
polling
polling
polling
polling
```

Это больше похоже на старую background-script модель.

---

# Хорошая модель

```text
Extension installed
        │
        ▼
      Idle
        │
        ▼
      Event
        │
        ▼
    Minimal work
        │
        ▼
      Persist
        │
        ▼
      Idle
```

Это естественная модель Manifest V3.

Вместо polling:

    ↓

Extension JavaScript вообще не требуется на каждом request.

# Instrumentation

Можно создать небольшую telemetry abstraction:

```javascript
function measure(name, fn) {
    const start = performance.now();

    return Promise.resolve(fn())
        .finally(() => {
            console.log(
                name,
                performance.now() - start
            );
        });
}
```

Например:

```javascript
await measure(
    "analyze-page",
    () => analyzePage()
);
```

Для Manifest V3 особенно опасны:

   ↓

   ↓

 ↓

```text

 ↓
extension JS
 ↓
decision
```

когда решение мог выполнить сам browser engine.

# Performance checklist

Перед release полезно проверить:

### Service Worker

```text
□ Минимальный startup
□ Минимальный bundle
□ Нет ненужного global initialization
□ Нет постоянного polling
□ Cold start работает корректно
□ State не зависит от global variables
```

### Content Script

```text
□ Ограничены matches
□ Минимальный bundle
□ Нет полного DOM scanning
□ MutationObserver используется осторожно
□ Нет лишних listeners
□ Есть cleanup
```

### Messaging

```text
□ Payload небольшой
□ Нет огромных state snapshots
□ Используется batching где необходимо
□ Есть timeout/error handling
```

### Storage

```text
□ Нет storage operation внутри tight loops
□ Используется batching
□ Есть cache где это оправдано
□ Persistent state отделён от ephemeral state
```

### Network

```text
□ Нет ненужных requests
□ Есть caching
□ Есть timeout
□ Есть retry policy
□ Нет отправки лишних данных
```

### UI

```text
□ Popup быстро открывается
□ Side Panel не загружает всё заранее
□ Нет лишнего DOM
□ Нет тяжёлых операций на main thread
```

# Итог

Performance Manifest V3 нельзя свести к оптимизации JavaScript.

Главная задача — **правильно спроектировать границы runtime**.

Хорошая extension architecture стремится к следующей модели:

```text
Install
  ↓
Idle
  ↓
Event
  ↓
Minimal startup
  ↓
Minimal processing
  ↓
Minimal communication
  ↓
Persist
  ↓
Idle
```

А ещё лучше:

```text
Can browser do it?
      │
     yes
      ↓
Declarative API

     no
      ↓
Can it be done without JS?
      │
     yes
      ↓
Web Platform

     no
      ↓
Use minimal extension JS
```

Отсюда следует главный performance principle Manifest V3:

> **Не пытайтесь сделать extension быстрым после того, как построили большой runtime. Проектируйте extension так, чтобы большой runtime вообще не требовался.**

Именно поэтому наиболее эффективная MV3-архитектура обычно сочетает:

```text
Web Platform
      +
Declarative APIs
      +
Small Service Worker
      +
Small Content Scripts
      +
Lazy-loaded UI
      +
Efficient messaging
      +
Persistent state
```

Такой подход одновременно уменьшает **CPU usage, memory usage, startup latency, network traffic и количество выполняемого JavaScript** — то есть оптимизирует не отдельную функцию, а всю архитектуру extension.
