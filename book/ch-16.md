# Глава 16. Архитектура коммуникации

В предыдущих главах мы рассмотрели отдельные механизмы взаимодействия между extension contexts:

* `chrome.runtime.sendMessage()`;
* `chrome.runtime.onMessage`;
* `chrome.runtime.connect()`;
* `Port`;
* `chrome.runtime.onConnect`.

Теперь необходимо перейти от API к **архитектуре**.

В небольшом расширении можно просто написать:

```text
Popup → sendMessage() → Service Worker
```

и этого будет достаточно.

Но по мере роста extension появляются:

```text
Popup
Content Script
Side Panel
Options Page
Service Worker
Page
DevTools
```

И сразу возникает вопрос:

> Кто с кем должен разговаривать?

Если каждый context начинает напрямую обращаться к каждому другому context, архитектура быстро превращается в запутанную сеть.

Поэтому задача этой главы — построить понятную **communication architecture** для Manifest V3.

---

# 16.1. Popup → Service Worker

Это один из самых распространённых communication paths.

```text
┌─────────┐
│  Popup  │
└────┬────┘
     │
     │ message
     ▼
┌───────────────┐
│ Service Worker│
└───────────────┘
```

Popup обычно является UI.

Service Worker выполняет роль background coordinator.

Поэтому естественная модель:

```text
Popup
  │
  │ command
  ▼
Service Worker
  │
  │ operation
  ▼
Extension state
```

---

## Пример

Popup:

```javascript
const response = await chrome.runtime.sendMessage({
    type: "GET_STATUS"
});

console.log(response);
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        if (message.type === "GET_STATUS") {

            sendResponse({
                status: "ready"
            });

        }

    }
);
```

---

## Почему Popup не должен напрямую управлять всей системой?

Можно написать в Popup:

```javascript
chrome.tabs.query(...);
chrome.storage.local.get(...);
fetch(...);
```

Но это быстро приводит к проблеме.

Popup становится одновременно:

```text
UI
+
business logic
+
state management
+
network layer
+
browser coordination
```

Это плохое разделение ответственности.

Лучше:

```text
Popup
   │
   │ commands
   ▼
Service Worker
   │
   ├── Storage
   ├── Tabs
   ├── Windows
   ├── Network
   └── Business logic
```

---

## Popup как thin client

Хорошая архитектурная модель:

```text
Popup = UI
Service Worker = coordinator
```

Popup сообщает:

```text
START
STOP
GET_STATUS
SAVE_SETTINGS
```

а Service Worker решает, что делать.

---

# Popup → Service Worker через Port

Если Popup должен получать поток событий:

```javascript
const port = chrome.runtime.connect({
    name: "popup"
});

port.postMessage({
    type: "SUBSCRIBE"
});
```

Service Worker:

```javascript
chrome.runtime.onConnect.addListener(port => {

    if (port.name !== "popup") {
        return;
    }

    port.onMessage.addListener(message => {

        if (message.type === "SUBSCRIBE") {

            port.postMessage({
                type: "STATE",
                payload: getCurrentState()
            });

        }

    });

});
```

Но для обычного запроса Port здесь не нужен.

---

# 16.2. Content Script → Service Worker

Это второй фундаментальный communication path:

```text
Web Page
    │
    ▼
Content Script
    │
    │ message
    ▼
Service Worker
```

Content Script находится рядом с DOM страницы, но не должен автоматически становиться центром всей extension logic.

Например, Content Script обнаружил:

```javascript
const title = document.title;
```

и передаёт результат:

```javascript
chrome.runtime.sendMessage({
    type: "PAGE_TITLE",
    payload: {
        title
    }
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender) => {

        if (message.type === "PAGE_TITLE") {

            console.log(
                sender.tab?.id,
                message.payload.title
            );

        }

    }
);
```

---

# Почему Content Script → Service Worker является важным направлением?

Content Script имеет доступ к:

* DOM;
* событиям страницы;
* Web APIs страницы;
* extension APIs, доступным content scripts.

Но Content Script не является хорошим местом для глобальной координации extension.

Например:

```text
Content Script
    │
    ├── DOM
    ├── page events
    └── extraction
           │
           ▼
     Service Worker
           │
           ├── storage
           ├── tabs
           ├── alarms
           └── application state
```

---

# `sender`

Service Worker получает информацию об отправителе:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender) => {

        console.log(sender);

    }
);
```

Это особенно важно для Content Script.

Можно получить информацию о вкладке и frame, откуда пришло сообщение.

Например:

```javascript
sender.tab?.id
```

Таким образом Service Worker может понимать:

```text
какая вкладка
какой context
какой frame
```

является источником сообщения.

---

# Безопасность

Нельзя автоматически считать:

```text
Content Script → Service Worker
```

доверенным RPC.

Сообщение всё равно должно быть проверено.

Например:

```javascript
if (
    !message ||
    typeof message.type !== "string"
) {
    return;
}
```

А для каждого типа сообщения необходимо проверять payload.

---

# 16.3. Side Panel → Service Worker

Side Panel имеет важное преимущество по сравнению с Popup:

> Side Panel может оставаться открытой значительно дольше.

Поэтому здесь особенно естественен long-lived communication.

```text
┌────────────┐
│ Side Panel │
└─────┬──────┘
      │
      │ Port
      ▼
┌───────────────┐
│ Service Worker│
└───────────────┘
```

---

# Первичное подключение

```javascript
const port = chrome.runtime.connect({
    name: "side-panel"
});
```

Service Worker:

```javascript
chrome.runtime.onConnect.addListener(port => {

    if (port.name !== "side-panel") {
        return;
    }

    console.log("Side panel connected");

});
```

---

# Snapshot + events

Для Side Panel хорошо работает архитектура:

```text
connect
   ↓
request state
   ↓
receive snapshot
   ↓
subscribe
   ↓
receive events
```

Например:

```javascript
port.postMessage({
    type: "GET_STATE"
});
```

Ответ:

```javascript
port.postMessage({
    type: "STATE",
    payload: {
        status: "ready"
    }
});
```

После этого:

```text
STATE_CHANGED
STATE_CHANGED
STATE_CHANGED
```

могут поступать через тот же Port.

---

# Side Panel как application UI

В отличие от Popup, Side Panel можно рассматривать как полноценный extension UI:

```text
Side Panel
    │
    ├── State
    ├── Commands
    ├── Events
    └── User interaction
```

Но архитектурно всё равно желательно держать business logic вне UI.

---

# 16.4. Options → Service Worker

Options Page обычно отвечает за configuration:

```text
Options
   │
   │ settings
   ▼
Service Worker
   │
   ▼
Storage
```

Например:

```javascript
await chrome.runtime.sendMessage({
    type: "SAVE_SETTINGS",
    payload: {
        enabled: true
    }
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    async (message, sender, sendResponse) => {

        if (message.type === "SAVE_SETTINGS") {

            await chrome.storage.local.set({
                settings: message.payload
            });

            sendResponse({
                ok: true
            });
        }

        return true;
    }
);
```

---

# Но нужен ли Service Worker вообще?

Не всегда.

Options Page может напрямую работать с:

```javascript
chrome.storage.local
```

Например:

```javascript
await chrome.storage.local.set({
    enabled: true
});
```

Это нормально.

Поэтому здесь существует два подхода.

### Прямой

```text
Options
   │
   ▼
Storage
```

### Через Service Worker

```text
Options
   │
   ▼
Service Worker
   │
   ▼
Storage
```

---

# Когда использовать Service Worker?

Если изменение настройки требует дополнительной логики:

```text
SAVE_SETTINGS
     ↓
validate
     ↓
persist
     ↓
reconfigure
     ↓
notify contexts
```

тогда Service Worker становится естественным coordinator.

---

# 16.5. Service Worker → Content Script

Обратное направление тоже очень важно:

```text
Service Worker
      │
      │ message
      ▼
Content Script
```

Например, пользователь нажал кнопку в Popup:

```text
Popup
  │
  │ START
  ▼
Service Worker
  │
  │ EXECUTE
  ▼
Content Script
```

---

# Поиск вкладки

Service Worker может получить нужную вкладку:

```javascript
const tabs = await chrome.tabs.query({
    active: true,
    currentWindow: true
});
```

Затем отправить сообщение:

```javascript
await chrome.tabs.sendMessage(
    tabs[0].id,
    {
        type: "START"
    }
);
```

---

# Архитектурный flow

Получается:

```text
User
 │
 ▼
Popup
 │
 │ START
 ▼
Service Worker
 │
 │ tabs.sendMessage()
 ▼
Content Script
 │
 ▼
DOM
```

Это очень распространённая архитектура.

---

# Почему Service Worker является посредником?

Потому что Popup не должен становиться центром extension.

Popup может исчезнуть:

```text
Popup opened
    ↓
User clicks
    ↓
Popup closes
```

Service Worker при этом является отдельным runtime context.

Поэтому:

```text
Popup
   ↓
Service Worker
   ↓
Content Script
```

обычно устойчивее, чем попытка строить сложную логику вокруг Popup.

---

# Важный нюанс

`tabs.sendMessage()` отправляет сообщение content script.

Но если в данной вкладке content script ещё не существует, сообщение не сможет выполнить ожидаемую работу.

Поэтому архитектура должна учитывать:

```text
content script installed?
content script ready?
correct frame?
correct page?
```

---

# Handshake

Для сложных расширений можно использовать handshake:

```text
Content Script
      │
      │ READY
      ▼
Service Worker
      │
      │ command
      ▼
Content Script
```

Например:

```javascript
chrome.runtime.sendMessage({
    type: "CONTENT_READY"
});
```

Service Worker может хранить информацию о готовности конкретного context в runtime state или получать её повторно при необходимости.

---

# 16.6. Content Script → Page

Теперь мы переходим к другому типу коммуникации.

Здесь уже нет:

```text
Extension context → Extension context
```

Вместо этого:

```text
Content Script
      │
      ▼
Web Page
```

Это принципиально другая граница.

---

# Почему это сложно?

Content Script работает в isolated world.

Page script работает в page's JavaScript world.

У них:

```text
общий DOM
```

но:

```text
разные JavaScript environments
```

Поэтому Content Script не может просто сделать:

```javascript
pageFunction();
```

и вызвать произвольную функцию JavaScript страницы как обычную функцию своего environment.

---

# DOM как communication boundary

Один из фундаментальных механизмов взаимодействия:

```text
Content Script
      │
      │ DOM
      ▼
Page
```

Например, Content Script может изменить DOM:

```javascript
document.documentElement.dataset.extensionReady =
    "true";
```

Page script может наблюдать это изменение.

---

# Custom Events

Другой механизм:

```javascript
document.dispatchEvent(
    new CustomEvent("my-extension-event", {
        detail: {
            value: 123
        }
    })
);
```

Page может слушать:

```javascript
document.addEventListener(
    "my-extension-event",
    event => {

        console.log(event.detail);

    }
);
```

Это позволяет построить канал:

```text
Content Script
      │
      │ CustomEvent
      ▼
    DOM
      │
      ▼
Page Script
```

---

# Но DOM не является trusted channel

Очень важно.

Если страница контролируется внешним сайтом, нельзя считать:

```text
DOM event = trusted extension message
```

Страница может:

* изменить DOM;
* вызвать события;
* передать неправильные данные;
* подделать payload.

Поэтому данные, пришедшие от страницы, должны рассматриваться как **untrusted input**.

---

# 16.7. Page → Content Script

Обратное направление:

```text
Page
  │
  ▼
Content Script
```

Можно использовать Custom Events.

Page:

```javascript
document.dispatchEvent(
    new CustomEvent(
        "page-to-extension",
        {
            detail: {
                type: "DATA",
                value: 123
            }
        }
    )
);
```

Content Script:

```javascript
document.addEventListener(
    "page-to-extension",
    event => {

        const data = event.detail;

        console.log(data);

    }
);
```

---

# Почему нужна валидация?

Потому что источник:

```text
Page
```

не является доверенным extension context.

Поэтому Content Script должен проверять:

```javascript
if (
    !event.detail ||
    event.detail.type !== "DATA"
) {
    return;
}
```

И дополнительно проверять payload.

---

# Page → Content Script → Service Worker

Это очень важный communication chain:

```text
Page
  │
  │ page event
  ▼
Content Script
  │
  │ runtime message
  ▼
Service Worker
```

Например:

```text
Web application
       │
       ▼
Page event
       │
       ▼
Content Script
       │
       ▼
Service Worker
       │
       ▼
Storage / Network / Logic
```

---

# Обратный путь

Также:

```text
Service Worker
      │
      ▼
Content Script
      │
      ▼
Page
```

Получается полноценная цепочка:

```text
Page
  ↕
Content Script
  ↕
Service Worker
  ↕
Extension UI
```

Это одна из фундаментальных архитектур Manifest V3.

---

# Content Script как bridge

Очень полезно рассматривать Content Script как **bridge**:

```text
                 Extension
                     │
              Service Worker
                     │
                     │
               Content Script
                     │
                     │
                  Web Page
```

Content Script находится на границе между двумя мирами:

```text
Web Platform
     │
     │
Content Script
     │
     │
Extension
```

---

# Но bridge не должен быть transparent

Очень плохая архитектура:

```text
Page
 │
 │ arbitrary object
 ▼
Content Script
 │
 │ forward everything
 ▼
Service Worker
```

Это превращает страницу в источник потенциально опасных команд.

Лучше:

```text
Page
 │
 ▼
Content Script
 │
 │ validate
 │ normalize
 │ authorize
 ▼
Typed message
 │
 ▼
Service Worker
```

---

# 16.8. Extension-wide event bus

Когда extension становится сложным, появляется необходимость доставлять события нескольким contexts.

Например:

```text
SCAN_PROGRESS
TAB_CHANGED
SETTINGS_CHANGED
AUTH_STATE_CHANGED
```

Есть несколько получателей:

```text
             Service Worker
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Popup      Side Panel   Content Script
```

Вместо того чтобы создавать десятки прямых connections:

```text
Popup → Content Script
Popup → Side Panel
Side Panel → Content Script
Content Script → Popup
...
```

можно сделать центральную модель:

```text
             Event Bus
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Popup    Side Panel   Content
```

---

# Service Worker как event hub

В Manifest V3 естественным кандидатом на роль event coordinator является Service Worker.

```text
                    Service Worker
                          │
                     Event Router
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
         Popup        Side Panel    Content Script
```

---

# Event bus не обязательно означает отдельный класс

Это может быть просто архитектурный слой.

Например:

```javascript
function publish(event) {

    // route event
}
```

и:

```javascript
function subscribe(...) {

    // register subscriber
}
```

Но внутри transport может использовать:

```text
sendMessage()
Port
tabs.sendMessage()
```

---

# Пример события

Допустим, изменилось состояние scanner:

```javascript
publish({
    type: "SCAN_PROGRESS",
    payload: {
        value: 50
    }
});
```

Event router решает:

```text
Popup       → send
Side Panel  → send
Content     → send
```

---

# Почему Event Bus полезен?

Он уменьшает coupling.

Без него:

```text
Popup
 │
 ├──→ Service Worker
 ├──→ Content Script
 └──→ Side Panel
```

Popup знает слишком много.

С event bus:

```text
Popup
 │
 ▼
Service Worker
 │
 ▼
Event Router
```

Popup знает только:

> "Я хочу отправить команду."

А не:

> "Кому именно и каким transport API её нужно доставить?"

---

# Command vs Event

Очень полезно разделять два понятия.

### Command

```text
START_SCAN
STOP_SCAN
SAVE_SETTINGS
```

Команда означает:

> Сделай что-то.

### Event

```text
SCAN_STARTED
SCAN_PROGRESS
SCAN_COMPLETED
SETTINGS_CHANGED
```

Событие означает:

> Что-то произошло.

---

# Направление

Command обычно имеет направление:

```text
UI
 │
 ▼
Service Worker
```

Event может распространяться:

```text
Service Worker
 │
 ├──→ Popup
 ├──→ Side Panel
 └──→ Content Script
```

Это очень полезное архитектурное разделение.

---

# Event bus и Service Worker lifecycle

Здесь снова появляется ключевая особенность MV3.

Нельзя считать:

```text
event bus
```

постоянно существующим JavaScript объектом.

Например:

```javascript
const subscribers = new Map();
```

может существовать только пока существует конкретный Service Worker instance.

Поэтому:

```text
Event Bus
```

— это runtime routing layer.

А не persistent state.

---

# Persistent event state

Если событие критично, можно хранить состояние отдельно:

```text
Service Worker
      │
      ├── Event Bus
      │
      └── Storage
```

Например:

```text
storage:
{
    scan: {
        status: "running",
        progress: 70
    }
}
```

После нового подключения UI получает snapshot:

```text
GET_STATE
```

а затем подписывается на новые events.

---

# Pub/Sub модель

Event bus можно концептуально представить как:

```text
Publisher
    │
    ▼
 Event Bus
    │
    ├── Subscriber A
    ├── Subscriber B
    └── Subscriber C
```

Например:

```text
Service Worker
    │
    │ SCAN_PROGRESS
    ▼
Event Bus
    │
    ├── Popup
    ├── Side Panel
    └── DevTools
```

---

# 16.9. Typed Message Protocol

До этого момента мы использовали сообщения вида:

```javascript
{
    type: "GET_STATUS"
}
```

Это уже неплохо.

Но для большого extension этого недостаточно.

Представьте:

```text
30 message types
15 contexts
10 event types
```

Если сообщения представляют собой произвольные JavaScript objects, быстро возникают ошибки.

---

# Проблема untyped messages

Например:

```javascript
chrome.runtime.sendMessage({
    type: "SCAN_PROGRESS",
    value: "50"
});
```

Получатель ожидает:

```javascript
value: number
```

Но получил:

```javascript
value: string
```

JavaScript не остановит такую ошибку автоматически.

---

# Message protocol

Поэтому полезно определить протокол.

Например:

```text
Message
├── type
├── requestId
├── payload
└── metadata
```

Пример:

```javascript
{
    type: "SCAN_PROGRESS",
    payload: {
        value: 50
    }
}
```

---

# TypeScript

Если extension написан на TypeScript, можно описать:

```typescript
type ScanProgressMessage = {
    type: "SCAN_PROGRESS";
    payload: {
        value: number;
    };
};
```

Другой тип:

```typescript
type StartScanMessage = {
    type: "START_SCAN";
    payload: {
        tabId: number;
    };
};
```

---

# Discriminated union

Самая удобная модель:

```typescript
type ExtensionMessage =
    | {
        type: "START_SCAN";
        payload: {
            tabId: number;
        };
    }
    | {
        type: "STOP_SCAN";
    }
    | {
        type: "GET_STATUS";
    }
    | {
        type: "SCAN_PROGRESS";
        payload: {
            value: number;
        };
    };
```

Теперь `type` является discriminator.

---

# Type-safe router

Можно построить routing:

```typescript
function handleMessage(
    message: ExtensionMessage
) {

    switch (message.type) {

        case "START_SCAN":
            return startScan(
                message.payload.tabId
            );

        case "STOP_SCAN":
            return stopScan();

        case "GET_STATUS":
            return getStatus();

        case "SCAN_PROGRESS":
            return handleProgress(
                message.payload.value
            );
    }
}
```

TypeScript может проверять соответствие payload конкретному `type`.

---

# Request и Event

Можно разделить protocol:

```typescript
type Command =
    | {
        type: "START_SCAN";
        payload: {
            tabId: number;
        };
    }
    | {
        type: "STOP_SCAN";
    };

type Event =
    | {
        type: "SCAN_STARTED";
    }
    | {
        type: "SCAN_PROGRESS";
        payload: {
            value: number;
        };
    }
    | {
        type: "SCAN_COMPLETED";
    };
```

Получаем:

```text
Command
   ↓
Service Worker
   ↓
Event
   ↓
Contexts
```

---

# Request ID

Для сложного request/response protocol полезен:

```typescript
type RequestMessage = {
    type: string;
    requestId: string;
    payload?: unknown;
};
```

Например:

```javascript
{
    type: "GET_STATUS",
    requestId: "req-123"
}
```

Ответ:

```javascript
{
    type: "GET_STATUS_RESULT",
    requestId: "req-123",
    payload: {
        status: "ready"
    }
}
```

Теперь можно сопоставить:

```text
requestId
```

запросу и ответу.

---

# Error protocol

Ошибки также следует сделать частью protocol.

Например:

```javascript
{
    type: "ERROR",
    requestId: "req-123",
    payload: {
        code: "SCAN_FAILED",
        message: "Unable to scan page"
    }
}
```

Тогда transport не смешивается с application error.

---

# Transport vs Protocol

Это одно из важнейших архитектурных разделений.

Transport:

```text
sendMessage()
Port
tabs.sendMessage()
```

Protocol:

```text
START_SCAN
GET_STATUS
SCAN_PROGRESS
ERROR
```

То есть:

```text
          Protocol
             │
             ▼
        Message object
             │
             ▼
          Transport
             │
       ┌─────┴─────┐
       ▼           ▼
 sendMessage     Port
```

---

# Почему это важно?

Если protocol отделён от transport, его можно использовать разными способами.

Например:

```text
Popup → sendMessage()
Side Panel → Port
Content Script → tabs.sendMessage()
```

но protocol остаётся одним:

```text
GET_STATUS
START_SCAN
SCAN_PROGRESS
```

---

# Message validation

TypeScript защищает код **внутри compilation boundary**.

Но extension получает сообщения из runtime.

Поэтому одного TypeScript недостаточно.

Например:

```typescript
type Message = {
    type: "START_SCAN";
    payload: {
        tabId: number;
    };
};
```

не означает, что реальный runtime object действительно имеет такую структуру.

Поэтому на boundary необходима runtime validation.

---

# Runtime validation

Можно использовать собственный validator:

```javascript
function isStartScanMessage(message) {

    return (
        message &&
        message.type === "START_SCAN" &&
        message.payload &&
        Number.isInteger(
            message.payload.tabId
        )
    );

}
```

И затем:

```javascript
if (!isStartScanMessage(message)) {
    return;
}
```

---

# Более сложный protocol

В production extension сообщение можно представить так:

```text
Message
├── version
├── type
├── requestId
├── source
├── payload
└── metadata
```

Например:

```javascript
{
    version: 1,
    type: "START_SCAN",
    requestId: "abc123",
    source: "popup",
    payload: {
        tabId: 42
    }
}
```

---

# `source`

Поле:

```text
source
```

может помочь понимать origin логического сообщения:

```text
popup
content-script
side-panel
options
devtools
```

Но нельзя использовать произвольное `source` как единственный security mechanism.

Если источник важен для безопасности, его следует определять на основании реального context/sender information, а не просто доверять полю сообщения.

---

# Версия протокола

Для больших extensions полезно иметь:

```javascript
version: 1
```

Почему?

Потому что protocol может измениться.

Например:

```text
v1
START_SCAN
```

позже:

```text
v2
START_SCAN
payload:
{
    tabId,
    mode
}
```

Версионирование позволяет контролировать evolution communication layer.

# Общая архитектура

```text
                         ┌────────────┐
                         │   Popup    │
                         └─────┬──────┘
                               │
                               │ message / Port
                               ▼
┌────────────┐          ┌───────────────┐          ┌────────────┐
│   Options  │ ───────► │               │ ◄─────── │ Side Panel │
└────────────┘          │ Service Worker│          └────────────┘
                        │               │

└────────────┘          │               │
```

# Центральный принцип

Можно сформулировать архитектуру следующим образом:

> **Service Worker координирует extension-wide communication, Content Script связывает extension с Web Page, а UI contexts общаются с Service Worker через определённый message protocol.**

---

# Не создавайте mesh architecture

Плохая архитектура:

```text
Popup ─────── Content Script
 │  \          /     │
 │   \        /      │
 ▼    ▼      ▼       ▼
Side Panel ─ Options
 │          /
 ▼         /
Service Worker
```

Количество связей быстро растёт.

При `N` contexts потенциально можно получить порядка:

```text
N × (N - 1)
```

направлений взаимодействия.

---

# Лучше использовать hub architecture

```text
                 Popup
                   │
                   ▼
Content Script → Service Worker ← Side Panel
                   ▲
                   │
                Options
```

Service Worker становится communication hub.

---

# Но не абсолютно всё должно идти через Service Worker

Это тоже важный принцип.

Например:

```text
Page ↔ Content Script
```

может происходить напрямую через DOM/events.

Не нужно делать:

```text
Page
 ↓
Content Script
 ↓
Service Worker
 ↓
Content Script
 ↓
Page
```

если задача касается только DOM/page interaction.

---

# Выбор маршрута

### UI → Service Worker

```text
Popup

Options

        │
        ▼
Service Worker
```

### Content Script → Service Worker

```text
Page-related data
        │
        ▼
Content Script
        │
        ▼
Service Worker
```

### Service Worker → Content Script

```text

        │
        ▼
Service Worker
        │
        ▼
Content Script
```

### Page ↔ Content Script

```text

 ↕
DOM / Events / Page bridge
 ↕
Content Script
```

# Главные правила главы

Запомним несколько правил.

### Правило 1

**UI не должен быть центром extension architecture.**

```text
UI → Service Worker
```

---

### Правило 2

**Service Worker — coordinator, но не permanent state container.**

```text
Service Worker
      │
      ├── orchestration
      └── communication
```

Persistent state должен находиться отдельно.

---

### Правило 3

**Content Script — bridge между Web Page и Extension.**

```text
Page
 ↕
Content Script
 ↕
Extension
```

---

### Правило 4

**Page нельзя считать trusted extension context.**

Любые данные:

```text
Page → Content Script
```

должны проходить validation.

---

### Правило 5

**Command и Event — разные понятия.**

```text
Command:
"сделай"

Event:
"произошло"
```

---

### Правило 6

**Protocol отделяйте от transport.**

```text
Protocol
   ↓
Transport
```

А не наоборот.

---

### Правило 7

**`sendMessage()` используйте для коротких взаимодействий.**

```text
request → response
```

---

### Правило 8

**`Port` используйте для длительных каналов.**

```text
connect
  ↓
messages
  ↓
events
  ↓
disconnect
```

---

### Правило 9

**Event Bus должен быть runtime routing layer, а не persistent storage.**

```text
Event Bus ≠ Database
```

---

### Правило 10

**Typed protocol должен существовать независимо от конкретного context.**

Один protocol:

```text
START_SCAN
STOP_SCAN
GET_STATUS
SCAN_PROGRESS
SCAN_COMPLETED
ERROR
```

может использоваться:

```text
Popup
Side Panel
Content Script
Service Worker
DevTools
```

# Финальная модель

В хорошо спроектированном Manifest V3 extension communication выглядит не как набор случайных вызовов API:

```javascript
chrome.runtime.sendMessage(...)
chrome.tabs.sendMessage(...)
chrome.runtime.connect(...)
```

а как **слоистая система**:

```text
                    APPLICATION
                         │
                         ▼
                  MESSAGE PROTOCOL
                         │
                         ▼
                COMMUNICATION ROUTER
                    /           \
                   /             \
              Messages          Ports
                 │                 │
                 └────────┬────────┘
                          ▼
                   SERVICE WORKER
                          │
                 ┌────────┴────────┐
                 ▼                 ▼
              Storage           Browser APIs
                 │
                 ▼
             Persistent
               State
```

А на границе с Web Page:

```text
                    EXTENSION
                        │
                Service Worker
                        │
                 runtime message
                        │
                        ▼
                 Content Script
                        │
                DOM / Page Bridge
                        │
                        ▼
                      PAGE
```

Именно такая модель позволяет перейти от «расширения, в котором несколько скриптов обмениваются сообщениями» к **настоящей архитектуре распределённого runtime**, где каждый execution context имеет определённую роль, communication происходит через формальный protocol, а transport и состояние разделены.

Это особенно важно для больших Manifest V3 extensions: когда число contexts растёт, архитектура коммуникации становится не вспомогательной деталью, а одним из центральных элементов всей системы.
