# Глава 49. Extension Platform API

До этой главы мы изучали Manifest V3 как набор отдельных механизмов:

* `manifest.json`;
* permissions;
* Content Scripts;
* Service Worker;
* Action;
* Popup;
* Side Panel;
* Options;
* Messaging;
* Storage;
* Declarative APIs;
* Tabs и Windows;
* lifecycle.

Теперь необходимо сделать следующий шаг.

Нужно перестать воспринимать Manifest V3 как коллекцию API и увидеть его как **платформу выполнения приложений внутри браузера**.

Именно это является центральной темой данной главы.

---

# 49.1. Browser APIs

Manifest V3 extension существует внутри браузера.

Поэтому первым слоем платформы являются обычные **Web Platform APIs**.

Это APIs, которые существуют независимо от того, является ли код частью extension.

Например:

```text
DOM
CSS
JavaScript
Fetch
Web Crypto
IndexedDB
Web Components
ES Modules
Web Workers
Streams
URL
Timers
Events
```

Упрощённо:

```text
Browser
│
├── Web Platform
│
└── Extension Platform
```

Extension Platform не заменяет Web Platform.

Она расширяет её.

---

## 49.1.1. Web Platform как фундамент

Например, Extension Page может использовать:

```javascript
const button =
    document.querySelector("#save");

button.addEventListener(
    "click",
    () => {
        console.log("saved");
    }
);
```

Здесь нет ничего специфичного для Chrome Extension.

Это обычный DOM API.

А:

```javascript
await fetch(
    "https://api.example.com/data"
);
```

использует Web Platform Fetch API.

И:

```javascript
const database =
    indexedDB.open("workspace");
```

использует IndexedDB.

---

## 49.1.2. Extension APIs добавляют специальные возможности

Extension APIs позволяют делать то, что обычная веб-страница делать не может.

Например:

```javascript
chrome.tabs.query(...)
```

или:

```javascript
chrome.storage.local.get(...)
```

или:

```javascript
chrome.runtime.sendMessage(...)
```

или:

```javascript
chrome.scripting.executeScript(...)
```

Таким образом:

```text
Web Platform
      +
Extension APIs
      =
Extension Application Platform
```

---

# 49.2. Extension APIs

Extension APIs — это специализированный слой браузерных API, предназначенный для расширений.

К нему относятся:

```text
chrome.runtime
chrome.tabs
chrome.windows
chrome.storage
chrome.scripting
chrome.action
chrome.commands
chrome.sidePanel
chrome.permissions
chrome.alarms
chrome.contextMenus
chrome.notifications
chrome.declarativeNetRequest
...
```

В некоторых браузерах также существует namespace:

```javascript
browser.*
```

В экосистеме Chromium традиционно используется:

```javascript
chrome.*
```

---

## 49.2.1. Extension API как capability layer

Очень важно понимать:

> Extension API — это не просто удобные функции. Это механизм предоставления расширению дополнительных capabilities.

Например:

```javascript
chrome.tabs.query(...)
```

предоставляет возможность получать информацию о вкладках.

```javascript
chrome.storage.local
```

предоставляет persistent storage.

```javascript
chrome.scripting
```

предоставляет механизм programmatic injection.

```javascript
chrome.tabs.update(...)
```

позволяет управлять вкладками.

Таким образом:

```text
API
 ↓
Capability
```

---

## 49.2.2. Capability зависит от permission

Не каждый API автоматически доступен в полном объёме.

Например, некоторые операции требуют:

```json
{
    "permissions": [
        "tabs"
    ]
}
```

или соответствующих host permissions.

Поэтому архитектура extension определяется не только кодом:

```text
Code
+
Manifest
+
Permissions
```

# 49.3. Declarative APIs

Одно из наиболее важных архитектурных изменений Manifest V3 — переход от imperative execution к declarative execution.

Imperative модель:

```text
Browser Event
     ↓
JavaScript
     ↓
Extension logic
     ↓
Browser API
```

Например:

```javascript
chrome.webRequest.onBeforeRequest.addListener(
    handler
);
```

Extension JavaScript должен участвовать в обработке события.

Declarative модель выглядит иначе:

```text
Extension
   ↓
Rules
   ↓
Browser Engine
   ↓
Action
```

Например:

```text
Request
   ↓
Browser
   ↓
Rule matching
   ↓
Block / Redirect / Modify
```

---

## 49.3.1. Почему это важно

Declarative API позволяет браузеру самому выполнять заранее определённую логику.

Например:

```text
Rule:
IF request matches X
THEN block
```

вместо:

```javascript
onRequest(request => {

    if (matches(request)) {
        return block();
    }

});
```

Браузеру больше не требуется запускать extension JavaScript для каждого запроса.

---

## 49.3.2. Declarative API как browser runtime

Можно представить:

```text
                Extension
                    │
                    │ rules
                    ▼
             Browser Engine
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Matching            Execution
          │                   │
          └─────────┬─────────┘
                    ▼
                 Result
```

Это особенно важно для:

* производительности;
* безопасности;
* lifecycle;
* снижения нагрузки на Service Worker.

---

## 49.3.3. Declarative rules как IR

В предыдущей главе мы рассматривали extension как multi-context application.

Теперь можно сделать ещё один шаг.

Declarative rules можно рассматривать как своеобразное:

```text
Intermediate Representation
```

Например:

```text
Application Intent
        ↓
Rule Compiler
        ↓
Declarative Rules
        ↓
Browser Engine
```

Получается очень интересная архитектура:

```text
JavaScript
    ↓
Compile
    ↓
Declarative representation
    ↓
Browser runtime
```

Часть логики переносится из extension runtime непосредственно в браузерный engine.

---

# 49.4. Permissions

Permissions являются отдельным фундаментальным слоем платформы.

Их задача — контролировать capabilities extension.

Например:

```json
{
    "permissions": [
        "storage",
        "tabs",
        "alarms"
    ]
}
```

означает, что extension заявляет определённые возможности.

Host permissions:

```json
{
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

определяют доступ к конкретным origins.

---

## 49.4.1. Permission model

Можно представить модель следующим образом:

```text
                 Extension
                     │
                     ▼
               Permissions
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Storage      Tabs       Hosts
```

Permissions являются частью security boundary.

---

## 49.4.2. Principle of Least Privilege

Хорошее extension не должно просить:

```text
<all_urls>
```

если ему требуется:

```text
https://example.com/*
```

Не следует запрашивать:

```text
tabs
```

если конкретной задаче достаточно более узкого API.

И не следует предоставлять Content Script всем страницам:

```text
<all_urls>
```

если реально используются:

```text
example.com
github.com
```

Минимальные permissions дают:

* меньшую поверхность атаки;
* меньшее доверие требуется от пользователя;
* меньше permission warnings;
* более понятную архитектуру.

---

# 49.5. Contexts

Одна из главных особенностей Manifest V3 — наличие нескольких execution contexts.

Типичное extension может содержать:

```text
Extension
│
├── Service Worker
├── Popup
├── Options
├── Side Panel
├── Content Script
└── DevTools
```

Это принципиально отличается от обычного веб-приложения.

---

## 49.5.1. Context — это runtime boundary

Каждый context имеет собственное окружение.

Например:

```text
Popup
```

имеет свой:

```text
window
document
globalThis
```

Side Panel имеет другое:

```text
window
document
globalThis
```

Content Script имеет отдельный JavaScript environment относительно page script.

Service Worker вообще не имеет DOM.

---

## 49.5.2. Не существует единого JavaScript runtime

Нельзя представить extension так:

```text
Extension
│
└── globalState
```

и ожидать:

```javascript
globalState.counter
```

в каждом context.

Правильная модель:

```text
                 Extension
                     │
      ┌──────────────┼──────────────┐
      ▼              ▼              ▼
    Popup         Side Panel     Service Worker
      │              │              │
      ▼              ▼              ▼
    Context        Context        Context
```

---

## 49.5.3. Context как distributed runtime

Contexts взаимодействуют через:

```text
messages
events
storage
ports
browser APIs
```

Поэтому extension можно рассматривать как небольшую распределённую систему:

```text
Context A
   │
   │ message
   ▼
Context B
```

---

# 49.6. Events

Manifest V3 построен вокруг event-driven architecture.

Вместо постоянного выполнения:

```text
while extension is running:
    ...
```

используется:

```text
event
 ↓
handler
 ↓
work
 ↓
runtime may stop
```

---

## 49.6.1. Browser events

Например:

```javascript
chrome.tabs.onActivated.addListener(
    handler
);
```

или:

```javascript
chrome.tabs.onUpdated.addListener(
    handler
);
```

или:

```javascript
chrome.runtime.onMessage.addListener(
    handler
);
```

или:

```javascript
chrome.storage.onChanged.addListener(
    handler
);
```

---

## 49.6.2. Event-driven architecture

Общая модель:

```text
               Browser
                  │
                  │ event
                  ▼
           Service Worker
                  │
                  ▼
              Handler
                  │
             ┌────┴────┐
             ▼         ▼
          Storage     Message
```

Service Worker просыпается, обрабатывает событие и после этого может быть остановлен.

---

## 49.6.3. Event source

Источником события может быть:

```text
User
Browser
Tab
Window
Timer
Alarm
Content Script
Popup
Side Panel
Storage
Network
Command
```

Например:

```text
Keyboard shortcut
       ↓
chrome.commands
       ↓
Service Worker
       ↓
Content Script
```

---

# 49.7. Messaging

Contexts не имеют общего JavaScript state.

Поэтому им нужен communication layer.

Основные механизмы:

```text
chrome.runtime.sendMessage()
chrome.tabs.sendMessage()
runtime.connect()
Port
```

---

## 49.7.1. Short-lived messaging

Для request/response:

```javascript
const response =
    await chrome.runtime.sendMessage({
        type: "GET_STATE"
    });
```

Архитектура:

```text
Sender
  │
  │ request
  ▼
Receiver
  │
  │ response
  ▼
Sender
```

---

## 49.7.2. Long-lived connection

Для продолжительного взаимодействия:

```javascript
const port =
    chrome.runtime.connect({
        name: "workspace"
    });
```

Теперь:

```text
Popup
  │
  │ Port
  ▼
Service Worker
```

Port особенно полезен для:

* streaming;
* интерактивных процессов;
* большого количества сообщений;
* двустороннего communication channel.

---

## 49.7.3. Messaging как transport layer

Важно разделять:

```text
Transport
```

и:

```text
Protocol
```

Например:

```text
Transport:
chrome.runtime.sendMessage()

Protocol:
{
    type: "UPDATE_PAGE_STATE",
    payload: {...}
}
```

Это разные уровни.

---

# 49.8. Storage

Storage является фундаментальным механизмом сохранения состояния.

Основные области:

```text
chrome.storage.local
chrome.storage.sync
chrome.storage.session
chrome.storage.managed
```

---

## 49.8.1. Persistent state

Service Worker является ephemeral runtime.

Поэтому:

```javascript
let state = {};
```

не может быть основным persistent storage.

Вместо этого:

```javascript
await chrome.storage.local.set({
    state
});
```

---

## 49.8.2. Storage как shared state layer

Несколько contexts могут работать с одним storage:

```text
             Storage
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
     Popup   SidePanel  Options
                │
                ▼
          Service Worker
```

Таким образом Storage становится механизмом state synchronization.

---

## 49.8.3. Storage events

После изменения:

```javascript
chrome.storage.onChanged.addListener(
    changes => {
        // update UI
    }
);
```

можно распространить изменения на другие contexts.

Получается:

```text
State mutation
      ↓
Storage
      ↓
Change event
      ↓
Contexts
```

---

# 49.9. Lifecycle

Lifecycle — один из наиболее важных компонентов платформы.

Extension не является процессом, который:

```text
start
 ↓
run forever
```

Manifest V3 использует event-driven lifecycle.

Особенно это относится к Service Worker.

---

## 49.9.1. Service Worker lifecycle

Упрощённая модель:

```text
Dormant
   │
   │ event
   ▼
Start
   │
   ▼
Execute
   │
   ▼
Idle
   │
   ▼
Suspended
```

Позднее:

```text
event
 ↓
restart
```

---

## 49.9.2. Почему это важно

Нельзя строить архитектуру вокруг:

```javascript
let cache = {};
let currentUser = null;
let activeJob = null;
```

как будто Service Worker будет существовать постоянно.

Такие значения могут исчезнуть.

Поэтому:

```text
Persistent state
       ↓
Storage

Ephemeral state
       ↓
Memory
```

---

# 49.9.3. Lifecycle independence

Другие contexts также имеют собственный lifecycle.

Popup:

```text
open
 ↓
execute
 ↓
close
```

Content Script:

```text
page loaded
 ↓
injected
 ↓
page navigated
 ↓
destroyed
```

Side Panel:

```text
open
 ↓
active
 ↓
closed
```

Options:

```text
open
 ↓
configuration
 ↓
close
```

Поэтому extension architecture должна быть **lifecycle-aware**.

---

# 49.9.4. Lifecycle как часть API

Можно сказать, что Manifest V3 API состоит не только из функций.

Платформа также задаёт:

```text
WHEN code runs
WHEN code stops
WHAT can wake it
WHAT state survives
WHAT context exists
```

Это фундаментальная часть программной модели.

# 49.11. Extension Platform как operating environment

Полезно провести аналогию с операционной системой.

ОС предоставляет:

```text
Processes
Memory
Files
Networking
Permissions
Events
IPC

```

Manifest V3 предоставляет extension:

```text
Contexts
Storage
Network
Permissions
Events
Messaging
Browser APIs
Lifecycle
```

Поэтому extension можно рассматривать как приложение, работающее внутри специальной browser-controlled runtime environment.

---

# 49.12. Browser-controlled runtime

Ключевой принцип Manifest V3:

> **Расширение не полностью контролирует свой runtime.**

Браузер решает:

* когда запустить Service Worker;
* когда его остановить;
* какие permissions предоставить;
* какие страницы доступны;
* когда Content Script может быть injected;
* какие declarative rules выполняются;
* какие API разрешены конкретному context.

Получается:

```text
Application
     ↓
Extension Platform
     ↓
Browser
```

а не:

```text
Application
     ↓
Own Runtime
```

# 49.13. Extension Platform и security

Security является частью самой платформы.

Она строится вокруг нескольких границ:

```text
Manifest
   ↓
Permissions
   ↓
Origins
   ↓
Contexts
   ↓
CSP
   ↓
Message boundaries
```

Например:

```text
Page
 │
 │ untrusted input
 ▼
Content Script
 │
 │ validated message
 ▼
Service Worker
 │
 │ privileged API
 ▼
Browser
```

Каждый переход является security boundary.

# 49.14. Extension Platform и performance

Manifest V3 также определяет performance model.

Основные идеи:

```text
short-lived execution
event-driven processing
declarative execution
minimal background work
browser-controlled scheduling
```

Вместо:

```text
permanent JavaScript runtime
```

получаем:

```text
event
 ↓
small computation
 ↓
stop
```

# 49.15. Imperative и declarative runtime

Теперь можно сравнить две архитектуры.

### Imperative

```text
Browser
  ↓
Event
  ↓
JavaScript
  ↓
Decision
  ↓
Browser API
```

### Declarative

```text
Extension
  ↓
Rule
  ↓
Browser Engine
  ↓
Decision
  ↓
Action
```

Manifest V3 активно использует обе модели.

Это важно.

Manifest V3 **не означает, что JavaScript исчезает**.

Он означает, что для некоторых задач browser-controlled declarative execution становится предпочтительнее.

---

# 49.16. Где использовать JavaScript

JavaScript нужен там, где требуется:

```text
complex business logic
UI
DOM interaction
state coordination
external APIs
user interaction
custom algorithms
```

Например:

```text
Side Panel
    ↓
JavaScript
    ↓
Application logic
```

---

# 49.17. Где использовать declarative APIs

Declarative APIs особенно полезны там, где логика имеет форму:

```text
IF condition
THEN action
```

Например:

```text
request matches rule
        ↓
block
```

или:

```text
page condition
        ↓
activate capability
```

В таких случаях браузер может выполнять работу эффективнее, чем JavaScript runtime.

# 49.19. Как проектировать extension как платформенное приложение

При создании нового extension полезно задавать вопросы не в таком порядке:

```text
Какой API использовать?
```

а:

### 1. Где должна выполняться логика?

```text
Page?
Content Script?
Service Worker?
Side Panel?
Options?
```

### 2. Какой lifecycle нужен?

```text
persistent UI?
ephemeral UI?
event-driven background?
```

### 3. Какой capability требуется?

```text
tabs?
storage?
network?
scripting?
host access?
```

### 4. Можно ли использовать declarative API?

```text
JavaScript?
или
browser-controlled rules?
```

### 5. Где находится canonical state?

```text
storage.local?
storage.sync?
session?
IndexedDB?
```

### 6. Как contexts будут взаимодействовать?

```text
sendMessage?
Port?
storage events?
```

Такое проектирование значительно лучше, чем начинать с написания `background.js`.

# 49.20. Extension Platform Contract

Можно сформулировать платформенный контракт следующим образом:

```text
Manifest
    defines capabilities

Permissions
    define access

Contexts
    define execution boundaries

Events
    define activation

Messaging
    defines communication

Storage
    defines persistence

Declarative APIs
    define browser-executed logic

Lifecycle
    defines runtime lifetime
```

# 49.25. Основные принципы

Из этой модели можно вывести десять фундаментальных принципов Manifest V3.

### Принцип 1. Browser First

Extension работает внутри браузера и подчиняется его runtime model.

### Принцип 2. Capability Based

Permissions определяют предоставленные capabilities.

### Принцип 3. Contextual

Разные задачи выполняются в разных contexts.

### Принцип 4. Event Driven

Extension реагирует на события вместо постоянного выполнения background code.

### Принцип 5. Message Based

Contexts взаимодействуют через явные communication channels.

### Принцип 6. Persistent State

Долгоживущие данные должны находиться в подходящем storage layer.

### Принцип 7. Declarative Where Possible

Логику, которую браузер способен выполнять декларативно, выгодно передавать browser engine.

### Принцип 8. Least Privilege

Extension должно получать минимально необходимый набор capabilities.

### Принцип 9. Lifecycle Aware

Любой context может появиться и исчезнуть.

### Принцип 10. Browser Controlled

Финальный контроль над runtime остаётся у браузера.
