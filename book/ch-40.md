# Глава 40. Packaging и Distribution

До этого момента мы рассматривали extension как программную систему:

```text
Manifest
   ↓
Contexts
   ↓
Service Worker
   ↓
Content Scripts
   ↓
UI
   ↓
Storage
   ↓
Network
   ↓
Architecture
   ↓
Performance
```

Но production extension существует не только как исходный код.

Пользователь должен получить:

```text
source code
    ↓
build
    ↓
package
    ↓
distribution
    ↓
installation
    ↓
updates
```

Поэтому packaging и distribution — это часть архитектуры extension, а не последняя техническая формальность.

Типичный production pipeline выглядит так:

```text
Developer
    ↓
Source Code
    ↓
Build
    ↓
Validation
    ↓
Package
    ↓
Store / Enterprise Distribution
    ↓
User Browser
    ↓
Extension Runtime
```

При этом необходимо учитывать сразу несколько факторов:

* Manifest V3;
* browser compatibility;
* signing;
* extension ID;
* permissions;
* versioning;
* update mechanisms;
* store policies;
* enterprise deployment.

---

# 40.1. Production build

В development extension часто выглядит очень просто:

```text
extension/
├── manifest.json
├── background.js
├── content.js
├── popup.html
├── popup.js
└── styles.css
```

Для небольшого extension этого может быть достаточно.

Но production application обычно имеет build pipeline:

```text
src/
  ↓
compiler / bundler
  ↓
dist/
  ↓
validation
  ↓
package
```

---

## Development и production

Важно различать:

```text
Development
    ↓
fast iteration
debugging
source maps
verbose logs
```

и:

```text
Production
    ↓
optimized assets
minimal logging
validated manifest
stable dependencies
packaged files
```

---

## Пример структуры проекта

Например:

```text
my-extension/
│
├── src/
│   ├── background/
│   │   └── index.js
│   ├── content/
│   │   └── index.js
│   ├── popup/
│   │   ├── index.html
│   │   └── index.js
│   ├── options/
│   │   ├── index.html
│   │   └── index.js
│   └── shared/
│       └── messages.js
│
├── public/
│   ├── icons/
│   └── manifest.json
│
├── package.json
└── dist/
```

Build:

```text
src + public
      ↓
    build
      ↓
     dist
```

---

# Manifest должен попасть в production package

После build в package должен находиться:

```text
dist/
├── manifest.json
├── background.js
├── content.js
├── popup.html
└── ...
```

Браузер загружает extension именно из этой структуры.

---

# Не путайте source project и extension package

Source project:

```text
src/
node_modules/
tests/
scripts/
package.json
```

не обязательно должен совпадать с тем, что получает браузер.

Production package:

```text
manifest.json
runtime files
assets
```

должен содержать только необходимые extension resources.

Например:

```text
dist/
├── manifest.json
├── background.js
├── content.js
├── popup.html
├── popup.js
└── icons/
```

а:

```text
node_modules/
tests/
README.md
.git/
```

туда обычно не попадают.

---

# Bundling

Можно использовать bundler:

```text
TypeScript
   ↓
Bundler
   ↓
JavaScript
   ↓
Extension package
```

Например, архитектура build system может включать:

```text
TypeScript
    ↓
ESBuild / Rollup / Vite / Webpack
    ↓
dist/
```

Но bundler не является обязательным требованием Manifest V3.

Для небольшого extension можно использовать обычные:

```html
<script type="module" src="./popup.js"></script>
```

и:

```javascript
import { foo } from "../shared/foo.js";
```

---

# Что должен делать production build

Хороший build pipeline должен:

```text
Compile
   ↓
Bundle
   ↓
Copy static assets
   ↓
Generate manifest
   ↓
Validate manifest
   ↓
Check permissions
   ↓
Generate package
```

---

# Environment configuration

Production и development могут использовать разные configuration values.

Например:

```text
development
API = development server

production
API = production server
```

Но нельзя забывать о Manifest V3 security restrictions.

Особенно важно:

> **Production extension не должен загружать удалённый JavaScript как часть runtime.**

Например, архитектура:

```text
Extension
   ↓
fetch()
   ↓
remote.js
   ↓
eval()
```

не является нормальным production-подходом для MV3.

Код должен поставляться вместе с extension package.

---

# Source maps

Во время разработки source maps чрезвычайно полезны:

```text
Browser error
    ↓
compiled.js:10234
    ↓
source map
    ↓
src/background/index.ts:57
```

В production необходимо осознанно решать:

```text
source maps included?
source maps private?
source maps omitted?
```

Это связано не только с debugging, но и с раскрытием исходного кода.

---

# Build validation

Перед packaging полезно автоматически проверять:

```text
□ manifest.json valid
□ required files exist
□ referenced files exist
□ icons exist
□ permissions expected
□ version valid
□ no accidental secrets
□ no development endpoints
□ no test files
□ no forbidden remote code
```

# 40.2. Packaging extension

После production build необходимо создать пакет.

Для большинства store-based workflows используется ZIP-архив с файлами extension.

Например:

```text
dist/
├── manifest.json
├── background.js
├── content.js
├── popup.html
└── icons/
```

становится:

```text
my-extension-1.4.0.zip
```

---

# Важен корень архива

Обычно `manifest.json` должен находиться в корне package:

```text
my-extension.zip
├── manifest.json
├── background.js
├── content.js
└── ...
```

а не:

```text
my-extension.zip
└── my-extension/
    ├── manifest.json
    └── ...
```

Если упаковка сделана неправильно, distribution system может не принять extension.

---

# Package должен быть воспроизводимым

Хорошая production система позволяет получить один и тот же результат из одного source revision.

Например:

```text
Git commit
    ↓
build
    ↓
package
```

Это позволяет установить связь:

```text
version
   ↕
Git commit
   ↕
build artifact
```

---

# Artifact

Production package лучше рассматривать как artifact:

```text
Source
   ↓
Build
   ↓
Artifact
```

Например:

```text
my-extension-1.4.0.zip
```

может быть сохранён в CI/CD system.

---

# Package validation

Перед публикацией полезно выполнить:

```text
unzip
   ↓
check manifest
   ↓
check files
   ↓
check size
   ↓
load unpacked
   ↓
run smoke tests
```

---

# 40.3. Versioning

Manifest содержит:

```json
{
    "version": "1.4.0"
}
```

Version — это не просто текст.

Он используется для идентификации версии extension и его обновлений.

---

# Semantic Versioning

Практически удобно использовать:

```text
MAJOR.MINOR.PATCH
```

Например:

```text
1.4.0
```

где:

```text
1 = major
4 = minor
0 = patch
```

Можно придерживаться такой политики:

```text
1.4.0 → 1.4.1
bug fix

1.4.0 → 1.5.0
new feature

1.4.0 → 2.0.0
breaking architecture/API change
```

Но важно понимать:

> SemVer — это ваша release policy. Browser update mechanism имеет собственные правила version comparison.

---

# Версия должна быть управляемой

Не стоит вручную изменять:

```text
package.json
manifest.json
README
```

в разных местах без автоматизации.

Лучше иметь единый source of truth:

```text
version
   ↓
build
   ├── manifest
   ├── package
   └── release metadata
```

---

# Git tags

Хорошая практика:

```text
commit
   ↓
tag v1.4.0
   ↓
build
   ↓
release artifact
```

Например:

```text
v1.4.0
v1.4.1
v1.5.0
```

---

# Версии и миграции данных

Version update может означать изменение storage schema.

Например:

```text
1.0
settings:
{
    theme: "dark"
}
```

В версии:

```text
2.0
```

структура может стать:

```javascript
{
    appearance: {
        theme: "dark"
    }
}
```

Тогда upgrade должен выполнять migration:

```text
Old state
   ↓
detect version
   ↓
migration
   ↓
new state
```

---

# Никогда не предполагайте чистую установку

Production extension работает у пользователей, которые обновляют его месяцами.

Поэтому код должен учитывать:

```text
new installation
existing installation
old version
partial migration
corrupted state
```

---

# 40.4. Extension updates

После публикации extension пользователь получает новые версии через distribution mechanism браузера.

Архитектурно:

```text
Installed v1.0
      ↓
new version available
      ↓
update
      ↓
v1.1
```

---

# Update ≠ reinstall

Обновление не должно проектироваться как:

```text
delete everything
install everything
```

Extension должен корректно переживать:

```text
update
restart
worker recreation
state migration
```

---

# Update lifecycle

Упрощённо:

```text
New package
    ↓
Browser accepts update
    ↓
New extension version installed
    ↓
Runtime restarts/reloads as appropriate
    ↓
New version becomes active
```

---

# Service Worker после update

Нельзя рассчитывать, что старый Service Worker продолжит жить.

Новая версия должна быть полностью самостоятельной:

```text
v1 worker
    ↓
update
    ↓
v2 worker
```

Поэтому persistent state должен находиться вне memory:

```text
worker memory
     ≠
persistent state
```

---

# Storage migration

При update:

```text
v1 storage
   ↓
migration
   ↓
v2 storage
```

Например:

```javascript
async function migrate(state) {
    if (state.version === 1) {
        state.settings = {
            theme: state.theme
        };

        delete state.theme;
        state.version = 2;
    }

    return state;
}
```

---

# Compatibility during migration

Если contexts существуют одновременно в переходный период, нужно осторожно проектировать state protocol.

Например:

```text
Popup v2
Worker v2
Content Script v2
```

обычно должны использовать согласованный protocol.

Нельзя бездумно менять:

```text
message schema
storage schema
API contract
```

без migration strategy.

---

# Update rollback

Хорошая production система должна предполагать, что новая версия может содержать bug.

Поэтому полезно иметь:

```text
release
   ↓
monitor
   ↓
problem?
   ├── no → continue
   └── yes → hotfix
```

Для store-distributed extensions возможности rollback контролируются distribution platform, поэтому особенно важно тестировать release до публикации.

---

# 40.5. Chrome Web Store

Для Chrome-based distribution основной публичный канал — Chrome Web Store.

Архитектура:

```text
Developer
    ↓
Package
    ↓
Chrome Web Store
    ↓
Review / validation
    ↓
Publication
    ↓
Users
```

---

# Store listing

Extension обычно имеет не только package, но и metadata:

```text
name
description
icons
screenshots
category
privacy information
permissions explanation
```

Store listing становится частью продукта.

Пользователь должен понимать:

```text
What does it do?
Why does it need these permissions?
What data does it access?
```

---

# Permissions и store review

Чем больше permissions:

```text
permissions
host_permissions
```

тем больше вопросов возникает относительно security и privacy.

Поэтому принцип:

> **Request only permissions that the extension actually needs.**

имеет значение не только для runtime security, но и для distribution.

---

# Store package ≠ source repository

GitHub repository может содержать:

```text
src/
tests/
docs/
scripts/
```

Chrome Web Store получает:

```text
production artifact
```

Это два разных продукта:

```text
Developer Artifact
       │
       ├── source
       ├── tests
       └── docs

Distribution Artifact
       │
       └── runtime files
```

---

# Automated publishing

Для production проекта можно построить:

```text
git tag
   ↓
CI
   ↓
build
   ↓
test
   ↓
package
   ↓
publish
```

Это уменьшает вероятность ручной ошибки.

---

# 40.6. Firefox Add-ons

Firefox использует собственную distribution ecosystem — Firefox Add-ons.

Архитектура аналогична:

```text
Source
  ↓
Build
  ↓
Package
  ↓
Firefox Add-ons
  ↓
Users
```

Но:

> **Manifest V3 не означает абсолютную идентичность runtime поведения Chrome и Firefox.**

Это принципиальный момент.

---

# Cross-browser ≠ same browser

Можно иметь один source tree:

```text
src/
```

но разные browser adapters:

```text
src/
   │
   ├── core/
   │
   └── browser/
          ├── chrome/
          └── firefox/
```

---

# Browser API compatibility

Например:

```javascript
browser.tabs.query(...)
```

и:

```javascript
chrome.tabs.query(...)
```

могут иметь различия в API behavior, Promise support и compatibility details.

Поэтому полезно создать abstraction layer:

```text
Application
     ↓
Browser Adapter
     ↓
Chrome / Firefox / Other
```

---

# WebExtension API

Если extension рассчитан на несколько браузеров, полезно ориентироваться на общую WebExtensions model там, где это возможно.

Например:

```text
Core
 ├── tabs
 ├── storage
 ├── runtime
 └── scripting
```

и отдельно:

```text
Browser-specific APIs
```

---

# Polyfill

Можно использовать compatibility layer, который предоставляет единый API:

```javascript
import browser from "webextension-polyfill";
```

Тогда application code может использовать единый стиль:

```javascript
await browser.storage.local.get("settings");
```

а adapter скрывает browser-specific differences.

Но polyfill не устраняет различия в самих возможностях браузеров.

---

# Feature detection

Надёжнее проверять возможность API, чем предполагать её наличие.

Например концептуально:

```javascript
if (browser.someFeature) {
    // use feature
}
```

Архитектура:

```text
Feature available?
       │
   ┌───┴───┐
  yes      no
   │        │
 use      fallback
```

---

# Browser compatibility matrix

Production extension желательно тестировать хотя бы в:

```text
Chrome
Firefox
```

и, при необходимости, других Chromium-based browsers.

Матрица может выглядеть:

| Feature         | Chrome | Firefox | Other |
| --------------- | -----: | ------: | ----: |
| Manifest V3     |      ✓ |      ✓* |    ✓* |
| Service Worker  |      ✓ |      ✓* |    ✓* |
| Content Scripts |      ✓ |       ✓ |     ✓ |
| Storage         |      ✓ |       ✓ |     ✓ |
| Side Panel      |     ✓* |      ✓* |    ✓* |
| DNR             |      ✓ |      ✓* |    ✓* |

`*` означает: необходимо проверять конкретную версию браузера и актуальную реализацию API.

---

# Не используйте browser name как единственный критерий

Лучше мыслить feature capability:

```text
Browser
   ↓
Capabilities
   ├── scripting
   ├── sidePanel
   ├── dnr
   └── ...
```

Это масштабируется лучше:

```javascript
if (supportsSidePanel()) {
    enableSidePanel();
}
```

чем:

```javascript
if (browserName === "Chrome") {
    ...
}
```

# 40.7. Browser compatibility

Cross-browser development имеет три уровня.

## Уровень 1. Shared Web Platform

```text
HTML
CSS
DOM
Fetch
ESM
Web Crypto
IndexedDB
```

Эти технологии обычно являются наиболее переносимой частью extension.

---

## Уровень 2. WebExtensions APIs

```text
runtime
storage
tabs
scripting
commands
```

Здесь совместимость обычно высокая, но детали могут различаться.

---

## Уровень 3. Browser-specific APIs

```text
Chrome-specific
Firefox-specific
Edge-specific
Safari-specific
```

Здесь необходим adapter/fallback.

---

# Хорошая архитектура

```text
                    Extension
                       │
                 Application Core
                       │
              ┌────────┴────────┐
              │                 │
       Web Platform       Browser Adapter
                                │
                    ┌───────────┼───────────┐
                    ▼           ▼           ▼
                 Chrome      Firefox      Other
```

Это позволяет избежать browser-specific logic по всему application code.

---

# Не абстрагируйте всё

Есть и обратная проблема.

Плохая архитектура:

```text
BrowserAdapter
   ↓
AdapterAdapter
   ↓
PlatformService
   ↓
RuntimeProvider
   ↓
BrowserFacade
   ↓
...
```

слишком много abstraction layers.

Абстрагировать стоит только реальные differences.

---

# Shared core

Идеальная cross-browser архитектура:

```text
src/
├── core/
│   ├── state/
│   ├── messaging/
│   ├── business/
│   └── storage/
│
├── browser/
│   ├── chrome/
│   └── firefox/
│
└── ui/
```

В результате:

```text
business logic
        ↓
browser-independent
```

а platform-specific код локализован.

---

# 40.8. Enterprise deployment

Не все extensions распространяются через публичный store.

В enterprise environment организация может централизованно управлять extensions.

Например:

```text
Company
   ↓
Browser Policy
   ↓
Managed Extension
   ↓
Employees
```

---

# Enterprise requirements

Enterprise extension может потребовать:

```text
forced installation
allowed extensions
blocked extensions
managed configuration
update control
permissions policy
```

---

# Managed configuration

Manifest V3 поддерживает:

```text
chrome.storage.managed
```

для policy-controlled configuration.

Архитектура:

```text
Administrator
      ↓
Browser Policy
      ↓
Managed Storage
      ↓
Extension
```

Extension получает configuration, которую пользователь не должен изменять обычным UI.

---

# Пример

Администратор может определить:

```json
{
    "apiEndpoint": "https://company.example/api",
    "enabled": true
}
```

Extension читает:

```javascript
const config =
    await chrome.storage.managed.get();
```

и использует:

```text
managed configuration
```

---

# User settings vs enterprise settings

Хорошая архитектура разделяет:

```text
User Settings
      +
Managed Settings
```

Например:

```text
User:
theme = dark

Admin:
featureEnabled = false
```

В результате:

```text
Effective Configuration
```

вычисляется как комбинация двух источников.

---

# Не позволяйте пользователю переопределять policy

Если administrator отключил функцию:

```text
managed:
featureEnabled = false
```

нельзя просто позволить:

```text
local:
featureEnabled = true
```

и использовать local значение.

Нужна явная precedence model:

```text
Managed Policy
      ↓
User Configuration
      ↓
Default Configuration
```

---

# Enterprise architecture

Можно представить:

```text
                Administrator
                      │
                      ▼
                Browser Policy
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    Forced Install          Managed Storage
          │                       │
          └───────────┬───────────┘
                      ▼
                   Extension
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Worker      Content       UI
```

---

# Enterprise и security

Enterprise deployment особенно чувствителен к:

```text
permissions
host_permissions
network access
data handling
updates
configuration
```

Если extension получает доступ к:

```text
<all_urls>
```

это уже серьёзная организационная security concern.

Поэтому enterprise extension должен следовать принципу:

```text
minimum permissions
+
minimum hosts
+
minimum data
```

# Production release checklist

Перед публикацией extension необходимо проверить:

## Build

```text
□ Production build
□ No development code
□ No debug secrets
□ No test artifacts
□ Correct environment
□ Correct manifest
```

## Manifest

```text
□ manifest_version = 3
□ Correct version
□ Correct permissions
□ Correct host permissions
□ Correct CSP
□ Correct icons
□ All referenced files exist
```

## Security

```text
□ No remote executable code
□ No secrets in package
□ Minimal permissions
□ Safe message handling
□ No unnecessary host access
```

## Runtime

```text
□ Service Worker starts correctly
□ Content Scripts load correctly
□ Popup works
□ Options work
□ Side Panel works
□ Commands work
```

## Upgrade

```text
□ Existing state survives update
□ Storage migrations tested
□ Old configurations handled
□ New configuration has defaults
```

## Browser compatibility

```text
□ Chrome tested
□ Firefox tested if supported
□ Browser-specific APIs isolated
□ Feature detection implemented
```

# Distribution как часть архитектуры

Важно понимать, что distribution влияет на runtime architecture.

Например:

```text
Public Store
    ↓
broad audience
    ↓
maximum compatibility
```

против:

```text
Enterprise
    ↓
controlled environment
    ↓
managed configuration
    ↓
organization-specific requirements
```

Поэтому нельзя полностью отделять:

```text
architecture
```

от:

```text
distribution strategy
```

# Итог

Packaging и distribution — это последний слой production architecture browser extension.

Но это не просто:

> «Сделать ZIP и загрузить его в магазин».

Полный production lifecycle выглядит так:

```text
Source
  ↓
Build
  ↓
Validation
  ↓
Testing
  ↓
Package
  ↓
Distribution
  ↓
Installation
  ↓
Runtime
  ↓
Update
  ↓
Migration
```

При этом необходимо разделять три уровня:

```text
                    EXTENSION
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   Application       Platform       Distribution
        │               │               │
        ▼               ▼               ▼
     Business       Chrome/Firefox   Store/Enterprise
      Logic            APIs
```

Главный принцип production packaging:

> **Source code — это не distribution artifact.**

Исходный проект должен быть организован для разработчика:

```text
src
tests
scripts
docs
```

а production package — для браузера:

```text
manifest.json
runtime code
assets
```

Главный принцип versioning:

> **Каждая версия должна быть воспроизводимым artifact, связанным с конкретным source revision.**

Главный принцип updates:

> **Extension должен быть способен переживать обновление без потери состояния и с корректной миграцией данных.**

Главный принцип cross-browser development:

> **Общий application core следует отделять от browser-specific capabilities.**

И наконец, главный принцип distribution:

> **Архитектура extension должна учитывать не только то, как программа работает, но и то, как она будет собираться, распространяться, обновляться и управляться после установки.**

После этого жизненный цикл нашего Manifest V3 extension выглядит уже не как набор отдельных API, а как полноценная система:

```text
                 ┌──────────────────────┐
                 │      SOURCE CODE     │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │        BUILD         │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │       PACKAGE        │
                 └──────────┬───────────┘
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
     Chrome Store      Firefox Add-ons    Enterprise
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                     ┌─────────────┐
                     │   INSTALL   │
                     └──────┬──────┘
                            │
                            ▼
                     ┌─────────────┐
                     │   RUNTIME   │
                     └──────┬──────┘
                            │
                            ▼
                     ┌─────────────┐
                     │    UPDATE   │
                     └──────┬──────┘
                            │
                            ▼
                     ┌─────────────┐
                     │  MIGRATION  │
                     └──────┬──────┘
                            │
                            └──────► RUNTIME
```

**Manifest V3 extension — это не просто JavaScript, который запускается в браузере. Это распространяемый, обновляемый и управляемый программный продукт.**
