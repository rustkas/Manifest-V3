# Глава 15. Long-Lived Connections

В предыдущей главе мы рассмотрели модель:

```text
Context A
    │
    │ message
    ▼
Context B
```

Для однократного взаимодействия этого достаточно.

Например:

```text
Popup → Service Worker
GET_STATUS
```

или:

```text
Content Script → Service Worker
PAGE_DATA
```

Но существуют ситуации, когда contexts должны взаимодействовать **длительное время**.

Например:

* Popup постоянно получает изменения состояния;
* Content Script отправляет поток событий;
* Side Panel наблюдает за активной вкладкой;
* DevTools Page взаимодействует с extension;
* один context подписывается на события другого;
* нужно реализовать двусторонний канал связи.

Для таких сценариев Manifest V3 предоставляет **long-lived connections**.

Основной API:

```javascript
chrome.runtime.connect()
```

Он создаёт объект:

```javascript
Port
```

который представляет собой двусторонний коммуникационный канал.

---

# 15.1. `runtime.connect()`

`chrome.runtime.connect()` используется для создания **долгоживущего соединения** между extension contexts.

Вместо:

```text
request
   ↓
response
```

получаем:

```text
Context A
   │
   │
   │  Port
   │
   ▼
Context B
```

Канал остаётся доступным для обмена несколькими сообщениями.

---

# Однократное сообщение

При использовании `sendMessage()` модель выглядит так:

```text
Popup
  │
  │ GET_STATUS
  ▼
Service Worker
  │
  │ response
  ▼
Popup
```

После завершения операции конкретное взаимодействие закончено.

---

# Long-lived connection

С `connect()`:

```text
Popup
  │
  │ connect()
  ▼
Service Worker
  │
  │ Port
  ├──────────────► message 1
  ├──────────────► message 2
  ◄────────────── message 3
  ├──────────────► message 4
  ◄────────────── message 5
  │
  │ disconnect
  ▼
```

Это уже не request/response, а **канал связи**.

---

# Создание соединения

Например, в Popup:

```javascript
const port = chrome.runtime.connect({
    name: "popup"
});
```

Метод возвращает:

```javascript
Port
```

---

# `Port`

`Port` — это объект, представляющий соединение.

У него есть важные возможности:

```javascript
port.postMessage(...)
```

для отправки сообщений:

```javascript
port.onMessage.addListener(...)
```

для получения сообщений:

```javascript
port.onDisconnect.addListener(...)
```

для отслеживания закрытия соединения.

---

# Простая схема

```text
             Port
              │
      ┌───────┴───────┐
      │               │
      ▼               ▼
 postMessage      onMessage
```

Именно поэтому `Port` можно рассматривать как объект коммуникационного канала.

---

# Отправка сообщения через Port

Например:

```javascript
const port = chrome.runtime.connect({
    name: "popup"
});

port.postMessage({
    type: "GET_STATUS"
});
```

Получатель получает это сообщение через:

```javascript
port.onMessage.addListener(
    message => {
        console.log(message);
    }
);
```

---

# Несколько сообщений через один Port

Главное отличие от обычного `sendMessage()` состоит в том, что один Port можно использовать многократно.

```javascript
port.postMessage({
    type: "START"
});

port.postMessage({
    type: "PROGRESS",
    value: 10
});

port.postMessage({
    type: "PROGRESS",
    value: 50
});

port.postMessage({
    type: "PROGRESS",
    value: 100
});

port.postMessage({
    type: "DONE"
});
```

Получается:

```text
START
  ↓
PROGRESS 10
  ↓
PROGRESS 50
  ↓
PROGRESS 100
  ↓
DONE
```

---

# 15.2. `Port`

Объект `Port` является центральным элементом long-lived communication.

Основные свойства и методы:

```text
Port
├── name
├── postMessage()
├── onMessage
└── onDisconnect
```

---

# `port.name`

При создании соединения можно указать имя:

```javascript
const port =
    chrome.runtime.connect({
        name: "scanner"
    });
```

На стороне получателя можно определить:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        console.log(port.name);

    }
);
```

Результат:

```text
scanner
```

---

# Зачем нужен `name`?

Имя позволяет определить назначение соединения.

Например:

```text
popup
side-panel
devtools
content-script
scanner
logger
```

Можно построить routing:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        switch (port.name) {

            case "popup":
                handlePopupPort(port);
                break;

            case "scanner":
                handleScannerPort(port);
                break;

            case "devtools":
                handleDevToolsPort(port);
                break;
        }
    }
);
```

---

# `postMessage()`

Для отправки данных:

```javascript
port.postMessage({
    type: "STATUS",
    value: "running"
});
```

Сообщение поступит другой стороне соединения.

---

# `onMessage`

Получение:

```javascript
port.onMessage.addListener(
    message => {

        console.log(message);

    }
);
```

Это callback, который вызывается для каждого сообщения, поступившего через Port.

---

# Двунаправленная связь

Очень важная особенность Port:

```text
A ─────────► B
A ◄───────── B
```

Обе стороны могут отправлять сообщения.

Например:

```text
Popup
  │
  │ START_SCAN
  ▼
Service Worker
  │
  │ PROGRESS 10%
  ▼
Popup
  │
  │ PROGRESS 50%
  ▼
Popup
  │
  │ PROGRESS 100%
  ▼
Popup
```

При этом используется один канал.

---

# Port не является RPC

Важно не путать Port с обычным:

```text
function call()
```

Port — это communication channel.

То есть вместо:

```javascript
const result = await calculate();
```

можно иметь:

```javascript
port.postMessage({
    type: "CALCULATE",
    payload: {
        value: 10
    }
});
```

а затем получать:

```javascript
port.onMessage.addListener(
    message => {

        if (message.type === "RESULT") {
            console.log(message.value);
        }

    }
);
```

---

# 15.3. `onConnect`

На принимающей стороне используется:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        console.log(
            "Connection:",
            port.name
        );

    }
);
```

Каждый новый `runtime.connect()` создаёт новое соединение, которое может быть обработано этим listener.

---

# Полный минимальный пример

### Popup

```javascript
const port =
    chrome.runtime.connect({
        name: "popup"
    });

port.postMessage({
    type: "HELLO"
});
```

### Service Worker

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        console.log(
            "Connected:",
            port.name
        );

        port.onMessage.addListener(
            message => {

                console.log(
                    "Received:",
                    message
                );

            }
        );

    }
);
```

---

# Ответ через Port

Service Worker может отправить ответ:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        port.onMessage.addListener(
            message => {

                if (message.type === "HELLO") {

                    port.postMessage({
                        type: "HELLO_ACK"
                    });

                }

            }
        );

    }
);
```

Popup:

```javascript
port.onMessage.addListener(
    message => {

        if (message.type === "HELLO_ACK") {
            console.log("Connected");
        }

    }
);
```

---

# Request/response поверх Port

Можно построить и обычную request/response модель:

```text
Client
  │
  │ REQUEST
  ▼
Port
  │
  ▼
Server
  │
  │ RESPONSE
  ▼
Client
```

Но это не главное преимущество Port.

Главная ценность появляется тогда, когда канал используется **для последовательности сообщений**.

---

# 15.4. Streaming communication

Одно из наиболее интересных применений long-lived connections — **streaming communication**.

Например:

```text
Content Script
      │
      │ connect
      ▼
Service Worker
      │
      ├── EVENT
      ├── EVENT
      ├── EVENT
      ├── EVENT
      └── EVENT
```

Вместо:

```text
sendMessage()
sendMessage()
sendMessage()
sendMessage()
```

можно логически представить это как один поток:

```text
Port
 │
 ├── event
 ├── event
 ├── event
 ├── event
 └── event
```

---

# Пример: progress stream

Предположим, расширение выполняет длительное сканирование страницы.

Popup открывает соединение:

```javascript
const port =
    chrome.runtime.connect({
        name: "scanner"
    });
```

Запускает операцию:

```javascript
port.postMessage({
    type: "START_SCAN"
});
```

Service Worker сообщает progress:

```javascript
port.postMessage({
    type: "PROGRESS",
    value: 10
});

port.postMessage({
    type: "PROGRESS",
    value: 40
});

port.postMessage({
    type: "PROGRESS",
    value: 70
});

port.postMessage({
    type: "PROGRESS",
    value: 100
});
```

Popup получает поток:

```javascript
port.onMessage.addListener(
    message => {

        if (message.type === "PROGRESS") {

            updateProgress(
                message.value
            );

        }

    }
);
```

---

# Port как subscription

Другой распространённый сценарий:

```text
Side Panel
    │
    │ connect
    ▼
Service Worker
    │
    │ subscribe
    ▼
Events
```

Например, Side Panel хочет получать изменения активной вкладки.

После подключения:

```javascript
const port =
    chrome.runtime.connect({
        name: "side-panel"
    });
```

Service Worker может хранить Port и отправлять события:

```javascript
port.postMessage({
    type: "TAB_CHANGED",
    payload: {
        tabId: 123
    }
});
```

---

# Но здесь возникает важная проблема

Если Service Worker хранит:

```javascript
const connectedPorts = [];
```

то это состояние находится только в памяти текущего Service Worker instance.

При его остановке:

```text
Service Worker
      │
      X
  terminated
```

Port больше не может считаться вечным.

Это критически важная особенность Manifest V3.

---

# Long-lived не означает immortal

Название **long-lived connection** может создать неправильное впечатление.

Port не означает:

```text
connection forever
```

Он означает:

> канал, который можно использовать для последовательного обмена сообщениями, пока соединение существует.

Service Worker остаётся ephemeral runtime.

---

# Streaming и Service Worker

Поэтому архитектура:

```text
Port
  ↓
Service Worker
  ↓
long-running operation
```

требует особого внимания.

Нельзя предполагать:

```text
Port exists
    ↓
Service Worker will always remain alive
```

Это неправильная модель.

---

# Длительная операция

Например:

```text
START_SCAN
    ↓
scan for 10 minutes
    ↓
PROGRESS
PROGRESS
PROGRESS
...
```

Если вся архитектура зависит от того, что Service Worker будет постоянно жить ради этого соединения, её необходимо тщательно проверять на актуальном поведении браузера и соответствующего API.

Для фоновых задач, которые должны переживать lifecycle worker, следует использовать подходящие persistence и scheduling mechanisms, а не только удержание JavaScript state.

---

# Port для событий

Port особенно хорошо подходит для:

```text
event stream
subscription
progress
interactive communication
```

Например:

```text
START
PROGRESS
PROGRESS
PROGRESS
COMPLETE
```

# 15.5. Connection lifecycle

Каждый Port имеет собственный lifecycle.

Упрощённо:

```text
CONNECT
   │
   ▼
CONNECTED
   │
   ├── message
   ├── message
   ├── message
   │
   ▼
DISCONNECTED
```

---

# Подключение

```javascript
const port =
    chrome.runtime.connect({
        name: "scanner"
    });
```

После этого принимающая сторона получает событие:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        // connected

    }
);
```

---

# Работа соединения

Во время существования Port:

```javascript
port.postMessage({
    type: "PING"
});
```

и:

```javascript
port.onMessage.addListener(
    message => {
        // receive
    }
);
```

---

# Отключение

Port предоставляет:

```javascript
port.onDisconnect
```

Например:

```javascript
port.onDisconnect.addListener(
    () => {

        console.log(
            "Port disconnected"
        );

    }
);
```

Это очень важный event.

---

# Почему Port может отключиться?

Причины могут быть разные:

* context был закрыт;
* вкладка была закрыта;
* extension context был уничтожен;
* Service Worker был завершён;
* произошла ошибка;
* соединение было закрыто другой стороной.

Поэтому:

```javascript
port.onDisconnect
```

следует рассматривать как нормальную часть lifecycle.

---

# Cleanup

Если Service Worker хранит данные о connections:

```javascript
const ports = new Set();
```

при подключении:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        ports.add(port);

        port.onDisconnect.addListener(
            () => {

                ports.delete(port);

            }
        );

    }
);
```

Это предотвращает накопление неактуальных references.

---

# Почему cleanup особенно важен?

Без cleanup:

```text
ports
 ├── old port
 ├── old port
 ├── old port
 ├── old port
 └── active port
```

Можно получить:

* лишние попытки отправки;
* ошибки;
* неправильное состояние;
* unnecessary memory usage.

---

# Connection state

Можно представить lifecycle как state machine:

```text
              connect()
                  │
                  ▼
             CONNECTED
              │     │
              │     │ message
              │     ▼
              │  ACTIVE
              │
              ▼
          DISCONNECTED
```

Для production architecture полезно явно понимать эти состояния.

---

# `onDisconnect` не всегда означает "ошибка"

Это очень важное правило.

Закрытие Popup:

```text
User closes Popup
       ↓
Port disconnects
```

Это может быть абсолютно нормальным событием.

Поэтому не следует автоматически логировать каждое отключение как critical error.

---

# Reconnection

Если connection необходим для работы UI, необходимо предусмотреть возможность повторного подключения.

Например:

```text
Popup
  │
  │ connect
  ▼
Service Worker
  │
  X
disconnect
  │
  ▼
Popup reconnects
  │
  │ connect
  ▼
Service Worker
```

---

# 15.6. Reconnection

Reconnection особенно важен для contexts с длительным временем жизни:

* Side Panel;
* DevTools;
* отдельная extension page;
* долгоживущий UI;
* приложения, использующие Port как subscription.

---

# Простой reconnect

Например:

```javascript
let port;

function connect() {

    port = chrome.runtime.connect({
        name: "side-panel"
    });

    port.onDisconnect.addListener(
        () => {

            setTimeout(
                connect,
                1000
            );

        }
    );
}

connect();
```

Это простая модель.

Но production implementation должна быть осторожнее.

---

# Почему нельзя делать бесконечный reconnect без контроля?

Представим:

```text
disconnect
   ↓
reconnect
   ↓
disconnect
   ↓
reconnect
   ↓
disconnect
   ↓
...
```

Можно получить busy loop.

Поэтому лучше использовать:

```text
backoff
maximum attempts
lifecycle awareness
```

---

# Exponential backoff

Например:

```text
1 sec
2 sec
4 sec
8 sec
16 sec
```

Это называется **exponential backoff**.

Концептуально:

```javascript
const delay =
    Math.min(
        1000 * 2 ** attempts,
        30000
    );
```

---

# Но reconnect должен учитывать lifecycle UI

Например, пользователь закрыл Side Panel.

Нет смысла:

```text
Side Panel closed
     ↓
reconnect forever
```

Поэтому reconnect должен быть связан с lifecycle самого context.

---

# Reconnection и state

После восстановления соединения нельзя предполагать, что Service Worker помнит всё состояние.

Например:

```text
Before disconnect:

currentJob = 123
progress = 70
```

После restart worker:

```text
currentJob = undefined
```

Поэтому состояние должно находиться там, где оно переживает lifecycle.

Например:

```text
Port
  │
  ▼
Service Worker
  │
  ▼
chrome.storage / IndexedDB
```

---

# Reconnect + resynchronization

Правильная модель:

```text
connect
   ↓
HELLO
   ↓
GET_CURRENT_STATE
   ↓
receive snapshot
   ↓
subscribe to events
```

То есть после восстановления не просто:

```text
CONNECT
```

а:

```text
CONNECT
  ↓
SYNC
  ↓
SUBSCRIBE
```

---

# Snapshot + events

Это особенно полезная архитектурная модель.

Сначала context получает полное состояние:

```javascript
{
    type: "STATE",
    payload: {
        status: "running",
        progress: 70
    }
}
```

Затем получает изменения:

```javascript
{
    type: "PROGRESS",
    payload: {
        value: 80
    }
}
```

Таким образом:

```text
Initial snapshot
       ↓
Event stream
       ↓
Current state
```

Это значительно устойчивее, чем предположение:

> «Я просто подключусь и получу все будущие события».

---

# Что происходит с сообщениями при disconnect?

Не следует проектировать систему так, будто Port является надёжной очередью.

Если context отключился:

```text
event
  ↓
Port
  X
```

сообщение не должно считаться гарантированно доставленным после закрытия канала.

Если событие важно, его нужно сохранять в подходящем состоянии/хранилище или уметь восстановить через resynchronization.

---

# Port и event bus

Port можно использовать как transport для собственного event bus:

```text
Service Worker
      │
      ├── STATE_CHANGED
      ├── TAB_CHANGED
      ├── SCAN_PROGRESS
      ├── SCAN_COMPLETE
      └── ERROR
```

Side Panel подписывается:

```text
Side Panel
      │
      └──── Port ────► Event Bus
```

Но сам event bus не должен зависеть исключительно от существования конкретного Port.

---

# 15.7. Когда использовать Port вместо messages

Теперь главный практический вопрос.

Когда использовать:

```javascript
chrome.runtime.sendMessage()
```

а когда:

```javascript
chrome.runtime.connect()
```

---

# `sendMessage()` — короткая операция

Используйте обычное message passing, когда:

```text
request
   ↓
response
```

Например:

```text
GET_SETTINGS
GET_STATUS
SAVE_SETTINGS
START_OPERATION
```

---

# Port — длительное взаимодействие

Используйте Port, когда:

```text
connect
   ↓
many messages
   ↓
disconnect
```

Например:

```text
subscription
stream
progress
interactive session
```

---

# Сравнение

| Характеристика        | `sendMessage()`     | `connect()` / `Port` |
| --------------------- | ------------------- | -------------------- |
| Однократный запрос    | Отлично             | Избыточно            |
| Request/response      | Отлично             | Можно                |
| Несколько сообщений   | Можно, но неудобнее | Отлично              |
| Streaming             | Не лучший выбор     | Отлично              |
| Subscription          | Не лучший выбор     | Отлично              |
| Двунаправленный канал | Ограниченно         | Да                   |
| Lifecycle             | Короткий            | Длительный           |
| Reconnection          | Обычно не требуется | Часто требуется      |
| Connection state      | Нет                 | Есть                 |
| Complexity            | Низкая              | Выше                 |

---

# Пример 1 — GET_SETTINGS

Используем:

```javascript
chrome.runtime.sendMessage({
    type: "GET_SETTINGS"
});
```

Port здесь не нужен.

---

# Пример 2 — START_SCAN

Если операция просто запускается:

```javascript
chrome.runtime.sendMessage({
    type: "START_SCAN"
});
```

может быть вполне достаточно.

Но если Popup должен получать:

```text
10%
20%
30%
40%
...
100%
```

тогда Port может быть естественным выбором для event stream.

---

# Пример 3 — Side Panel

Side Panel может быть постоянно открыта:

```text
Side Panel
     │
     │ connect
     ▼
Service Worker
     │
     ├── TAB_CHANGED
     ├── PAGE_UPDATED
     ├── SCAN_PROGRESS
     └── STATUS_CHANGED
```

Здесь Port подходит значительно лучше, чем постоянные независимые запросы.

---

# Пример 4 — Content Script

Content Script может один раз запросить настройки:

```javascript
const settings =
    await chrome.runtime.sendMessage({
        type: "GET_SETTINGS"
    });
```

`sendMessage()` — правильный выбор.

Но если Content Script должен подписаться на поток событий:

```text
DOM changes
network state
scan progress
application events
```

Port может оказаться удобнее.

---

# Не используйте Port только потому, что он "мощнее"

Это важное правило.

Port создаёт дополнительную архитектурную сложность:

```text
connect
   ↓
connection state
   ↓
disconnect
   ↓
cleanup
   ↓
reconnect
   ↓
resync
```

Если вам нужен один запрос:

```text
GET_STATUS
```

всё это совершенно не нужно.

Используйте:

```javascript
chrome.runtime.sendMessage()
```

---

# Простое правило

Можно запомнить:

```text
ONE REQUEST
     ↓
sendMessage()
```

и:

```text
ONGOING COMMUNICATION
     ↓
connect() + Port
```

---

# Но есть важное уточнение

Количество сообщений само по себе не является единственным критерием.

Например, можно отправить десять независимых событий через:

```javascript
chrome.runtime.sendMessage()
```

и это не автоматически означает, что нужен Port.

Главный вопрос:

> **Нужен ли вам логически единый длительный канал связи?**

Если нет — обычные messages могут быть лучше.

# Архитектурная модель

Хорошая extension architecture может использовать оба механизма одновременно:

```text
                    Extension
                        │
          ┌─────────────┴─────────────┐
          │                           │
          ▼                           ▼
    Short-lived RPC             Long-lived
    sendMessage()               Port
          │                           │
          │                           │
    ┌─────┴─────┐              ┌──────┴──────┐
    ▼           ▼              ▼             ▼
 GET_STATUS  SAVE_CONFIG   PROGRESS      EVENTS
```

# Гибридный подход

Например, Side Panel:

### Открытие

```text
connect()
```

### Первичная синхронизация

```text
GET_STATE
```

### Далее

```text
Port
  ↓
STATE_CHANGED
STATE_CHANGED
STATE_CHANGED
```

### Закрытие

```text
disconnect
```

Это очень хорошая модель:

```text
Connect
   ↓
Snapshot
   ↓
Subscribe
   ↓
Events
   ↓
Disconnect
```

# Production-like пример

Предположим, у нас есть Scanner Extension.

Architecture:

```text
                 Side Panel
                     │
                     │ Port
                     ▼
              Service Worker
                     │
              ┌──────┴──────┐
              │             │
              ▼             ▼
           Scanner       Storage
              │
              ▼
         Progress events
              │
              ▼
             Port
              │
              ▼
          Side Panel
```

# Service Worker

Условно:

```javascript
chrome.runtime.onConnect.addListener(
    port => {

        if (port.name !== "scanner") {
            return;
        }

        port.onMessage.addListener(
            async message => {

                if (
                    message.type ===
                    "START"
                ) {

                    await startScan(port);

                }

            }
        );

    }
);
```

---

# Streaming progress

```javascript
async function startScan(port) {

    for (let progress = 0;
         progress <= 100;
         progress += 10) {

        port.postMessage({
            type: "PROGRESS",
            payload: {
                value: progress
            }
        });

    }

}
```

Это только учебный пример. В реальном расширении долгую работу нельзя проектировать с предположением, что Service Worker будет постоянно удерживаться в памяти только потому, что существует Port.

---

# Более надёжная архитектура

Лучше:

```text
Scanner
   │
   ▼
Persistent state
   │
   ▼
Service Worker
   │
   ▼
Port
   │
   ▼
UI
```

То есть:

```text
Port = transport
```

а не:

```text
Port = source of truth
```

Это очень важное архитектурное различие.

---

# Port не должен быть database

Плохая архитектура:

```text
Port
 │
 └── contains all application state
```

Хорошая:

```text
                Application State
                       │
              ┌────────┴────────┐
              ▼                 ▼
           Storage             Runtime
                                │
                                ▼
                              Port
                                │
                                ▼
                                UI
```

Port — коммуникационный механизм.

---

# Главный принцип

> **Persistent state и communication channel — разные вещи.**

Например:

```text
chrome.storage
       │
       │ state
       ▼
Service Worker
       │
       │ events
       ▼
Port
       │
       ▼
Side Panel
```

Если Side Panel исчезнет:

```text
Port disappears
```

но:

```text
State remains
```

```text

   ↓

   ↓
SUBSCRIBE
   ↓
```

Для сложного extension это может стать полноценным внутренним communication protocol.

# Типичная ошибка №1

Использовать Port для каждого сообщения.

```text
connect
   ↓
message
   ↓
disconnect
```

Это фактически превращает Port в дорогой вариант:

```javascript
sendMessage()
```

Если communication действительно короткая — используйте `sendMessage()`.

---

# Типичная ошибка №2

Считать Port гарантированно постоянным.

```text
connect()
   ↓
"Теперь Service Worker всегда работает"
```

Это неверно.

Manifest V3 использует event-driven Service Worker architecture.

---

# Типичная ошибка №3

Хранить всё состояние в памяти Service Worker.

```javascript
let state = {};
```

и считать его доступным всегда.

При lifecycle restart:

```text
state disappears
```

---

# Типичная ошибка №4

Не обрабатывать `onDisconnect`.

```javascript
port.postMessage(...);
```

без понимания того, существует ли ещё connection.

Нужно учитывать:

```javascript
port.onDisconnect
```

---

# Типичная ошибка №5

Не делать resynchronization

После reconnect нельзя предполагать:

```text
"I know the current state."
```

Лучше:

```text
reconnect
   ↓
request snapshot
   ↓
apply state
   ↓
continue events
```

---

# Типичная ошибка №6

Считать события надёжной очередью

Port не является persistent message queue.

Если событие критично:

```text
EVENT
```

его состояние должно быть сохранено отдельно.

Например:

```text
Storage:
scan.status = "completed"
scan.progress = 100
```

После reconnect UI может получить:

```text
GET_STATE
```

и восстановить отображение.

# Message vs Port: окончательная модель

Можно сформулировать следующим образом.

### Message

```text
"I want to communicate something."
```

То есть:

> У меня есть конкретное сообщение.

### Port

```text
"I want to establish a communication channel."
```

То есть:

> Я хочу создать канал, через который мы будем взаимодействовать некоторое время.

Это концептуально разные уровни.

# Итог главы

Long-lived connections являются вторым фундаментальным механизмом communication в Manifest V3 после обычного message passing.

Основные идеи:

1. **`chrome.runtime.connect()` создаёт долгоживущий communication channel.**
2. **Результатом является объект `Port`.**
3. **`Port.postMessage()` отправляет сообщения через существующее соединение.**
4. **`Port.onMessage` принимает сообщения.**
5. **`Port.onDisconnect` позволяет отслеживать завершение соединения.**
6. **`chrome.runtime.onConnect` используется для обработки новых connections.**
7. **Один Port может использоваться для множества сообщений.**
8. **Port особенно полезен для streaming, subscriptions и progress events.**
9. **Port является communication channel, а не persistent storage.**
10. **Long-lived connection не означает, что Service Worker будет жить бесконечно.**
11. **После disconnect может потребоваться reconnection.**
12. **Reconnection должен сопровождаться resynchronization состояния.**
13. **Для устойчивой архитектуры следует разделять transport и persistent state.**
14. **Для короткого request/response лучше использовать `sendMessage()`.**
15. **Для длительного взаимодействия и потока событий лучше использовать `Port`.**

Главная формула:

```text
sendMessage()

    ONE-OFF COMMUNICATION
           │
           ▼
       Request
           │
           ▼
        Response
```

против:

```text
connect()

    LONG-LIVED COMMUNICATION
           │
           ▼
        Connect
           │
           ├── Message
           ├── Message
           ├── Message
           ├── Message
           │
           ▼
       Disconnect
```

А для production-like Manifest V3 extension наиболее надёжная архитектура выглядит так:

```text
                  Context
                     │
                     ▼
                  Connect
                     │
                     ▼
                   Port
                     │
                     ▼
               Message Router
                     │
             ┌───────┴───────┐
             ▼               ▼
          Handler          Storage
             │               │
             └───────┬───────┘
                     ▼
                   State
                     │
                     ▼
                  Snapshot
                     │
                     ▼
                  Port/UI
```

**Ключевая мысль:** `sendMessage()` — это передача сообщения, а `Port` — создание канала связи. Именно это различие следует держать в голове при проектировании архитектуры расширения.
