# Часть XIV. Production Development

# Глава 37. Debugging

Browser extension существенно сложнее обычного веб-приложения с точки зрения отладки.

В обычном веб-приложении мы чаще всего имеем:

```text
Browser Tab
    │
    ├── HTML
    ├── CSS
    └── JavaScript
```

И DevTools фактически предоставляет единую среду:

```text
Elements
Console
Sources
Network
Application
```

У Manifest V3 extension ситуация совершенно иная.

Extension может одновременно содержать:

```text
                         Extension
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
 Popup              Service Worker         Content Script
        │                    │                    │
        ▼                    ▼                    ▼
   Popup DOM            Worker runtime       Page DOM
        │                                         │
        ▼                                         ▼
   Popup DevTools                           Page DevTools
```

Кроме того, у extension могут быть:

```text
Side Panel
Options Page
DevTools Page
Injected scripts
MAIN-world code
```

Поэтому debugging extension — это прежде всего задача **определения правильного execution context**.

Главный вопрос при любой ошибке:

> **В каком context произошла проблема?**

Только после этого имеет смысл открывать соответствующие DevTools.

---

# 37.1. Extensions page

Первый инструмент разработчика — специальная страница управления расширениями браузера.

В Chromium-браузерах это:

```text
chrome://extensions
```

Именно здесь разработчик управляет установленными extension и загружает extension в режиме разработки.

Для локальной разработки обычно включается:

```text
Developer mode
```

После этого появляется возможность:

```text
Load unpacked
```

и выбрать каталог проекта.

---

# Extension card

После загрузки extension браузер показывает его карточку.

В ней обычно можно увидеть:

```text
Extension name
Extension ID
Version
Permissions
Errors
Service Worker
Inspect views
Reload
Remove
```

Конкретный набор элементов может зависеть от типа extension и версии браузера.

---

# Extension ID

Extension ID чрезвычайно важен при debugging.

Например:

```text
abcdefghijklmnopabcdefghijklmnop
```

Он используется браузером для идентификации extension.

Extension URL может выглядеть примерно так:

```text
chrome-extension://abcdefghijklmnop/
```

Поэтому при debugging полезно понимать:

```text
Extension
   │
   └── ID
        │
        └── chrome-extension://<id>/
```

---

# Почему Extension ID важен

Он позволяет понять:

* какой extension выполняет код;
* какой origin используется;
* какой extension-owned resource открыт;
* какое сообщение относится к конкретному extension;
* почему URL имеет определённый `chrome-extension://` origin.

Особенно важно это при работе с несколькими локальными extension.

---

# Errors

Страница `chrome://extensions` — одно из первых мест, куда следует смотреть после изменения extension.

Например:

```text
manifest.json invalid
```

или:

```text
Service worker registration failed
```

или:

```text
Permission error
```

Если extension вообще не запускается, бессмысленно начинать debugging popup или content script.

Сначала нужно проверить сам extension.

---

# Reload

После изменения файлов extension часто необходимо перезагрузить extension.

Например:

```text
Edit source
    ↓
Save
    ↓
Reload extension
```

Но важно понимать:

> **Reload extension не равен reload текущей web page.**

Если extension изменяет content scripts, после reload extension уже существующий tab может потребовать обновления страницы для получения нового автоматически инъецируемого content script.

---

# Development loop

Практический цикл:

```text
Modify
   ↓
Save
   ↓
Reload extension
   ↓
Reload affected page/context
   ↓
Reproduce
   ↓
Inspect
```

Для разных компонентов этот цикл отличается.

---

# 37.2. Service Worker DevTools

Service Worker — один из наиболее важных и одновременно наиболее необычных contexts Manifest V3.

Вместо постоянно работающего:

```text
background.js
```

мы имеем:

```text
Service Worker
    │
    ├── starts
    ├── handles event
    ├── becomes idle
    └── may stop
```

Поэтому debugging должен учитывать lifecycle.

---

# Inspect Service Worker

На странице extension management обычно можно перейти к инспектированию Service Worker.

Это открывает DevTools для worker context.

Там доступны привычные инструменты:

```text
Console
Sources
Network
Application
```

Однако execution environment отличается от обычной web page.

---

# Console Service Worker

Например:

```javascript
console.log("Worker started");
```

будет отображаться в console Service Worker.

Это не обязательно та же Console, которую вы видите на web page.

Поэтому если:

```text
content.js
```

выводит:

```text
console.log("content");
```

а:

```text
service-worker.js
```

выводит:

```text
console.log("worker");
```

не следует ожидать, что оба сообщения окажутся в одной Console.

---

# Service Worker startup debugging

Очень полезно поставить logging на начало worker:

```javascript
console.log("[worker] startup");
```

И затем на events:

```javascript
chrome.runtime.onMessage.addListener((message) => {
    console.log("[worker] message", message);
});
```

Получается:

```text
[worker] startup
[worker] message { ... }
```

Это позволяет понять:

1. был ли worker запущен;
2. пришло ли сообщение;
3. какой message был получен.

---

# Worker termination

При debugging необходимо помнить:

> Service Worker не является постоянно работающим background process.

Поэтому отсутствие старого global state не обязательно означает bug.

Например:

```javascript
let cache = {};
```

не должен рассматриваться как permanent state.

После нового запуска:

```text
cache === {}
```

может быть совершенно нормальным поведением.

---

# Debugging lifecycle

Полезно логировать lifecycle:

```javascript
console.log("[worker] initialized");
```

и ключевые operations:

```javascript
console.log("[worker] loading state");
console.log("[worker] handling command");
console.log("[worker] saving state");
```

Но не следует пытаться строить архитектуру, зависящую от наличия конкретного startup event.

Надёжный worker должен уметь восстановиться из persistent state.

---

# Debugging asynchronous code

Service Worker часто выполняет:

```text
message
   ↓
storage
   ↓
fetch
   ↓
process
   ↓
response
```

Поэтому простой:

```javascript
console.log("start");
console.log("finish");
```

часто недостаточен.

Лучше:

```javascript
console.log("[worker] request start", requestId);

const data = await loadData();

console.log("[worker] data loaded", requestId);

const result = await process(data);

console.log("[worker] processing complete", requestId);
```

Так можно увидеть, где именно остановилась операция.

---

# 37.3. Content Script DevTools

Content Script работает на web page, но находится в extension-controlled isolated world.

Это создаёт важную особенность:

```text
Web Page
   │
   ├── Page JavaScript
   │
   └── Content Script
```

Они могут работать с одним DOM, но их JavaScript environments различаются.

---

# Где искать console.log()

Если content script содержит:

```javascript
console.log("[content] loaded");
```

сообщение обычно нужно искать в DevTools соответствующей web page.

Открываем:

```text
Target Web Page
    ↓
DevTools
    ↓
Console
```

а не DevTools Service Worker.

---

# Почему это важно

Можно легко сделать ошибочный вывод:

```text
"Content script не работает,
потому что я не вижу его console.log()."
```

Но на самом деле developer может смотреть:

```text
Service Worker Console
```

вместо:

```text
Web Page Console
```

---

# Проверка инъекции

Первый шаг debugging content script:

```javascript
console.log("[content] injected");
```

Если сообщения нет, проверяем:

```text
manifest
   ↓
matches
   ↓
host permissions
   ↓
target URL
   ↓
run_at
   ↓
frame
```

---

# Проверка DOM

После этого:

```javascript
console.log(document.location.href);
console.log(document.title);
console.log(document.body);
```

Можно убедиться, что script действительно выполняется на ожидаемой странице.

---

# Проверка frames

Если:

```text
all_frames: true
```

content script может выполняться в нескольких frames.

Тогда полезно логировать:

```javascript
console.log(
    "frame",
    window.top === window,
    location.href
);
```

Это помогает понять:

```text
top frame
iframe
nested iframe
```

---

# Content Script и page JavaScript

При debugging необходимо помнить:

```text
Content Script
      │
      └── isolated world
```

и:

```text
Page Script
      │
      └── page world
```

Поэтому одинаковые имена глобальных variables не обязательно конфликтуют напрямую.

Например:

```javascript
window.myExtensionState = {};
```

в content script не следует автоматически воспринимать как то же самое значение, которое видит page script.

---

# DOM debugging

При этом DOM является общей точкой взаимодействия.

Поэтому можно видеть:

```text
Elements
   ↓
DOM inserted by content script
```

в обычном DevTools Elements panel.

Это очень полезно:

```text
JavaScript context
       │
       ▼
     DOM
       │
       ▼
Elements panel
```

---

# 37.4. Popup DevTools

Popup — отдельный extension page.

Это означает:

```text
Popup
   ↓
own DOM
   ↓
own JavaScript runtime
```

и соответственно:

```text
Popup DevTools
```

отдельны от:

```text
Page DevTools
Service Worker DevTools
```

---

# Popup inspection

Когда popup открыт, его DevTools можно открыть средствами браузера, обычно через контекстное меню или inspection action, в зависимости от браузера.

После открытия popup DevTools доступны:

```text
Elements
Console
Sources
Network
Application
```

---

# Главная проблема Popup

Popup имеет короткий lifecycle.

Типичный flow:

```text
click icon
   ↓
popup opens
   ↓
user interacts
   ↓
popup closes
   ↓
popup context destroyed
```

Поэтому debugging popup иногда неудобен.

---

# Почему console может исчезнуть

Если popup закрывается:

```text
Popup
  ↓
closed
  ↓
runtime destroyed
```

его DevTools context также может исчезнуть или потерять состояние.

Поэтому для сложной логики popup желательно:

* держать application state вне popup;
* отправлять operations в Service Worker;
* минимизировать business logic в popup;
* использовать Side Panel для более длительных workflows.

---

# Popup debugging pattern

Например:

```javascript
console.log("[popup] opened");
```

и:

```javascript
console.log("[popup] command", command);
```

Service Worker:

```javascript
console.log("[worker] command received", command);
```

Получается:

```text
Popup Console:
[popup] opened
[popup] command SAVE

Worker Console:
[worker] command received SAVE
```

Это сразу показывает границу communication.

---

# Popup → Worker debugging

Если popup делает:

```javascript
const response =
    await chrome.runtime.sendMessage({
        type: "GET_STATE"
    });
```

логируйте обе стороны:

```text
Popup:
SEND GET_STATE
```

и:

```text
Worker:
RECEIVE GET_STATE
```

а затем:

```text
Worker:
SEND RESPONSE

Popup:
RECEIVE RESPONSE
```

---

# Request IDs

При сложном debugging особенно полезен `requestId`.

```javascript
{
    type: "GET_STATE",
    requestId: "req-42"
}
```

Logs:

```text
[popup] SEND req-42
[worker] RECEIVE req-42
[worker] LOAD req-42
[worker] RESPONSE req-42
[popup] RECEIVE req-42
```

Теперь весь request можно проследить через несколько contexts.

---

# 37.5. Side Panel DevTools

Side Panel похож на обычную extension page значительно больше, чем Popup.

Он имеет:

```text
HTML
CSS
JavaScript
DOM
lifecycle
```

и собственный DevTools context.

---

# Почему Side Panel проще debug

Side Panel обычно остаётся открытым значительно дольше:

```text
open
   ↓
work
   ↓
work
   ↓
close
```

Поэтому можно:

* поставить breakpoints;
* исследовать DOM;
* наблюдать state;
* анализировать events;
* выполнять команды в Console.

---

# Side Panel → Service Worker

Например:

```javascript
await chrome.runtime.sendMessage({
    type: "LOAD_DOCUMENT"
});
```

В Side Panel:

```text
[panel] SEND LOAD_DOCUMENT
```

В worker:

```text
[worker] RECEIVE LOAD_DOCUMENT
```

Результат:

```text
[worker] RESPONSE
[panel] UPDATE UI
```

Такой logging значительно упрощает диагностику.

---

# Side Panel → Content Script

Более сложная цепочка:

```text
Side Panel
     │
     │ message
     ▼
Service Worker
     │
     │ message
     ▼
Content Script
     │
     ▼
Page DOM
```

При debugging нужно проверять **каждый hop**.

Например:

```text
[panel] SEND ANALYZE
[worker] RECEIVE ANALYZE
[worker] SEND ANALYZE → tab 42
[content] RECEIVE ANALYZE
[content] DOM analysis complete
[worker] RECEIVE RESULT
[panel] RECEIVE RESULT
```

Если результат отсутствует, можно сразу определить границу failure.

---

# 37.6. Console isolation

Console isolation — одна из самых важных тем debugging extension.

Представим:

```text
Popup
Service Worker
Content Script
Page
Side Panel
```

У каждого может быть собственная Console.

```text
Popup Console
Worker Console
Page Console
Side Panel Console
```

Поэтому:

```javascript
console.log("hello");
```

не означает:

> "hello появится в общей консоли extension".

---

# Mental model

Всегда связывайте log с context:

```javascript
console.log("[popup]", message);
```

```javascript
console.log("[worker]", message);
```

```javascript
console.log("[content]", message);
```

```javascript
console.log("[panel]", message);
```

Это простое правило экономит огромное количество времени.

---

# Context-aware logging

Можно создать небольшой logger:

```javascript
const logger = {
    info(...args) {
        console.log("[worker]", ...args);
    },

    error(...args) {
        console.error("[worker]", ...args);
    }
};
```

Для разных contexts prefix будет разным.

---

# Request tracing

Для distributed architecture полезно иметь:

```text
requestId
```

Например:

```text
req-7f31
```

и включать его во все сообщения:

```text
[popup][req-7f31] SEND
[worker][req-7f31] RECEIVE
[content][req-7f31] EXECUTE
[worker][req-7f31] RESULT
[popup][req-7f31] DONE
```

Это превращает debugging в tracing.

---

# Error logging

Не следует ограничиваться:

```javascript
console.log(error);
```

Лучше:

```javascript
console.error(
    "[worker]",
    {
        requestId,
        error
    }
);
```

Для ошибок особенно важны:

```text
context
operation
requestId
tabId
frameId
error
```

если они доступны и релевантны.

---

# 37.7. Network debugging

Network debugging extension отличается от debugging обычного сайта.

Причина:

```text
Extension origin
```

может быть:

```text
chrome-extension://<extension-id>
```

а запрос:

```text
https://api.example.com
```

происходит из extension context.

---

# Fetch

Например:

```javascript
const response = await fetch(
    "https://api.example.com/data"
);
```

При debugging необходимо проверять:

```text
URL
Method
Status
Request headers
Response headers
Response body
Timing
```

---

# Где смотреть Network

Если запрос выполняется в:

```text
Service Worker
```

смотрите Network в:

```text
Service Worker DevTools
```

Если запрос выполняется в:

```text
Popup
```

смотрите:

```text
Popup DevTools → Network
```

Если в:

```text
Content Script
```

смотрите соответствующий page DevTools, учитывая особенности execution context.

---

# Network request tracing

Полезно логировать:

```javascript
console.log("[network] GET", url);
```

после response:

```javascript
console.log(
    "[network] response",
    response.status
);
```

и при ошибке:

```javascript
console.error(
    "[network] failed",
    error
);
```

---

# CORS debugging

Если запрос не работает, нельзя сразу делать вывод:

```text
"fetch сломан".
```

Нужно проверить:

```text
execution context
   ↓
extension origin
   ↓
host permissions
   ↓
CORS
   ↓
server response
```

Например:

```text
Popup
   ↓
fetch()
   ↓
API
```

может вести себя иначе, чем:

```text
Content Script
   ↓
fetch()
   ↓
API
```

потому что contexts имеют разные security characteristics.

---

# Authentication debugging

Если API требует authentication, проверяйте:

```text
Authorization
Cookie
credentials
origin
redirect
```

Особенно важно видеть реальный request.

Например:

```text
Request Headers
    Authorization: Bearer ...
```

или отсутствие ожидаемого header.

---

# Redirect debugging

API может возвращать:

```text
301
302
307
308
```

и затем переходить на другой URL.

При debugging полезно проверить:

```text
Request URL
Final URL
Response status
```

---

# Failed network request

Хороший debugging flow:

```text
fetch()
   ↓
Did request start?
   ↓
Did DNS/network work?
   ↓
What status?
   ↓
Did CORS/security reject?
   ↓
What response?
   ↓
Did parsing fail?
```

Например ошибка может произойти не в `fetch()`, а здесь:

```javascript
const data = await response.json();
```

---

# 37.8. Storage debugging

Storage является критически важной частью MV3 architecture.

Поскольку Service Worker ephemeral, persistent state часто находится в:

```text
chrome.storage
```

Поэтому при ошибке state нужно проверять не только JavaScript.

---

# Storage layers

Нужно понимать, какой storage используется:

```text
chrome.storage.local
chrome.storage.sync
chrome.storage.session
chrome.storage.managed
```

Каждый имеет свою семантику.

---

# Inspecting storage

Для extension-owned pages DevTools может предоставлять инструменты Application/Storage, но возможности и представление зависят от браузера и типа storage.

Кроме того, самый надёжный способ debugging — непосредственно запросить значения через API:

```javascript
const state = await chrome.storage.local.get(null);

console.log("[storage]", state);
```

---

# Debugging one key

Вместо:

```javascript
await chrome.storage.local.get(null);
```

можно запросить:

```javascript
const result =
    await chrome.storage.local.get("settings");

console.log(result.settings);
```

Это особенно удобно при большом state.

---

# Storage writes

Логируйте mutation:

```javascript
console.log(
    "[storage] SET settings",
    settings
);

await chrome.storage.local.set({
    settings
});
```

Теперь можно понять:

```text
кто
что
и когда
записал
```

---

# Storage events

Очень полезен:

```javascript
chrome.storage.onChanged.addListener(
    (changes, areaName) => {
        console.log(
            "[storage]",
            areaName,
            changes
        );
    }
);
```

Например:

```text
[storage]
local
{
    settings: {
        oldValue: {...},
        newValue: {...}
    }
}
```

Это помогает обнаружить неожиданные изменения.

---

# Debugging synchronization

Представим:

```text
Options
   ↓
storage.set()
   ↓
storage.onChanged
   ↓
Side Panel
```

Если Side Panel не обновляется:

```text
1. Did Options write?
2. Did storage change?
3. Did Side Panel receive event?
4. Did state manager update?
5. Did UI render?
```

Это гораздо эффективнее, чем искать проблему сразу в UI.

---

# Storage corruption

Если state имеет неправильную структуру:

```javascript
{
    settings: "hello"
}
```

вместо:

```javascript
{
    settings: {
        theme: "dark"
    }
}
```

проблема может проявиться значительно позже.

Поэтому state validation полезен и во время debugging.

---

# Versioned state

Например:

```javascript
{
    version: 3,
    settings: {...}
}
```

При загрузке:

```text
version 1
   ↓
migration
   ↓
version 2
   ↓
migration
   ↓
version 3
```

Логи migration помогают обнаруживать проблемы после обновления extension.

---

# 37.9. Permission debugging

Permissions — одна из наиболее сложных причин ошибок extension.

Особенно когда код выглядит абсолютно корректно:

```javascript
await chrome.tabs.query(...);
```

но browser возвращает:

```text
Permission denied
```

---

# Permission debugging model

Всегда задавайте четыре вопроса:

```text
1. Какой API используется?
2. Какое permission ему требуется?
3. В каком context выполняется код?
4. Для какого resource требуется access?
```

---

# `permissions` vs `host_permissions`

Это принципиально разные категории.

Например:

```json
{
    "permissions": [
        "storage",
        "tabs"
    ],
    "host_permissions": [
        "https://example.com/*"
    ]
}
```

Здесь:

```text
storage
tabs
```

и:

```text
https://example.com/*
```

решают разные задачи.

---

# Permission failure

При ошибке:

```javascript
chrome.runtime.lastError
```

или rejected Promise нужно внимательно читать error.

Например:

```javascript
try {
    const result = await chrome.tabs.query(...);
} catch (error) {
    console.error("[tabs]", error);
}
```

Не следует скрывать оригинальное сообщение браузера.

---

# Optional permissions

Если permission запрашивается динамически:

```text
User action
   ↓
request permission
   ↓
granted?
   ├── yes → continue
   └── no  → degrade
```

при debugging необходимо проверить обе ветки.

Не только:

```text
permission granted
```

но и:

```text
permission denied
```

---

# Host permission debugging

Если content script не запускается на:

```text
https://example.com/page
```

проверяйте:

```text
matches
host_permissions
```

и особенно match pattern.

Например:

```text
https://example.com/*
```

не означает автоматически:

```text
http://example.com/*
```

И:

```text
https://example.com/*
```

не является тем же самым, что:

```text
https://*.example.com/*
```

---

# Permission debugging checklist

При подозрении на permission issue:

```text
Manifest
   ↓
permissions
   ↓
host_permissions
   ↓
optional permissions
   ↓
runtime permission state
   ↓
target URL
   ↓
execution context
```

---

# Типичная ошибка: неправильный context

Иногда permission действительно существует, но API вызывается из context, где он недоступен или имеет другую семантику.

Например:

```text
Page JavaScript
```

не является:

```text
Extension Service Worker
```

И наличие permission у extension не означает, что обычный page script автоматически получает extension API.

---

# Debugging по цепочке

Для сложного extension особенно эффективен метод **hop-by-hop debugging**.

Например, пользователь нажимает кнопку:

```text
Side Panel
    │
    │ 1. command
    ▼
Service Worker
    │
    │ 2. message
    ▼
Content Script
    │
    │ 3. DOM operation
    ▼
Web Page
```

Debugging:

```text
Step 1
Did Side Panel send?

Step 2
Did Worker receive?

Step 3
Did Worker find correct tab?

Step 4
Did Content Script receive?

Step 5
Did DOM operation succeed?
```

Не следует отлаживать всю цепочку одновременно.

---

# Context-first debugging

Для любой проблемы можно использовать алгоритм:

```text
                    Bug
                     │
                     ▼
              Identify context
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      Popup        Worker      Content
        │            │            │
        ▼            ▼            ▼
      DevTools    DevTools     Page DevTools
```

После этого:

```text
Check lifecycle
Check permissions
Check messages
Check state
Check network
Check DOM
```

---

# Debugging distributed extension

Поскольку extension является multi-context application, полезно мыслить не только:

```text
"где ошибка?"
```

но:

```text
"на какой границе произошла ошибка?"
```

Например:

```text
Popup
   │ ✓
   ▼
Worker
   │ ✓
   ▼
Content Script
   │ ✗
   ▼
Page
```

Тогда проблема уже локализована.

---

# Correlation IDs

Для сложных extension рекомендуется использовать единый:

```text
requestId
```

Например:

```text
req-2026-08-19-001
```

И записывать его во всех contexts:

```text
[popup][req-001] send ANALYZE
[worker][req-001] receive ANALYZE
[worker][req-001] target tab=42
[content][req-001] start
[content][req-001] complete
[worker][req-001] result
[popup][req-001] render
```

Это уже почти полноценный distributed tracing.

---

# Structured logging

Вместо:

```javascript
console.log("something happened");
```

лучше:

```javascript
console.log({
    context: "worker",
    event: "ANALYZE_COMPLETE",
    requestId,
    tabId,
    duration
});
```

Например:

```text
{
    context: "worker",
    event: "ANALYZE_COMPLETE",
    requestId: "req-42",
    tabId: 17,
    duration: 124
}
```

Такой формат значительно удобнее для сложного debugging.

---

# Performance debugging

Debugging — это не только поиск exceptions.

Необходимо анализировать:

```text
CPU
memory
network
DOM operations
message volume
storage operations
```

Например, если content script постоянно выполняет:

```javascript
new MutationObserver(...)
```

и обрабатывает тысячи mutations, проблема может быть не функциональной, а performance-related.

---

# Debugging message storms

В multi-context architecture легко создать:

```text
A → B
B → A
A → B
B → A
...
```

То есть feedback loop.

Логирование:

```text
[popup] SEND
[worker] RECEIVE
[worker] SEND
[popup] RECEIVE
[popup] SEND
...
```

быстро показывает проблему.

---

# Debugging infinite state loops

Похожая проблема:

```text
State changed
   ↓
UI update
   ↓
UI writes state
   ↓
State changed
   ↓
UI update
```

Получается:

```text
state → UI → state → UI → ...
```

Правильная архитектура должна различать:

```text
user intent
```

и:

```text
state projection
```

---

# Breakpoints

Breakpoints особенно полезны для:

```text
message handlers
state transitions
permission requests
network processing
DOM manipulation
```

Например:

```javascript
chrome.runtime.onMessage.addListener(
    async (message) => {

        debugger;

        // ...
    }
);
```

Это позволяет остановить выполнение непосредственно в момент обработки message.

---

# Conditional debugging

Для шумных handlers полезны conditional breakpoints.

Например, интересует только:

```text
requestId === "req-42"
```

Это намного эффективнее, чем останавливать worker на каждом сообщении.

---

# Debugging errors at boundaries

Особое внимание нужно уделять boundary transitions:

```text
Popup → Worker
Worker → Content
Content → Page
Context → Storage
Context → Network
```

Каждый boundary должен иметь:

```text
validation
logging
error handling
timeout/recovery
```

---

# Production-like debugging architecture

Даже небольшое extension стоит проектировать с debugging infrastructure.

Например:

```text
src/
├── runtime/
│   ├── messaging.js
│   ├── logging.js
│   └── errors.js
│
├── background/
│   └── service-worker.js
│
├── content/
│   └── content.js
│
└── ui/
    ├── popup/
    └── side-panel/
```

И общий logger:

```text
runtime/logging
```

может добавлять:

```text
context
requestId
timestamp
event
```

---

# Development mode

Полезно иметь development logging:

```javascript
if (DEBUG) {
    console.log(...);
}
```

В production можно уменьшить объём logging.

Однако критические ошибки должны оставаться диагностируемыми.

---

# Error boundaries

Каждый context желательно иметь на верхнем уровне error handling.

Например:

```javascript
try {
    await handleMessage(message);
} catch (error) {
    console.error("[worker]", error);
}
```

Но важно не превращать это в:

```javascript
catch {
    // ignore
}
```

Иначе debugging становится практически невозможным.

# Итоговая модель debugging

Для профессиональной разработки полезно представить debugging не как:

```text
"открыть Console и найти ошибку"
```

а как систему наблюдения:

```text
                         Extension
                             │
       ┌─────────────────────┼─────────────────────┐
       │                     │                     │
       ▼                     ▼                     ▼
     Popup                Worker               Content
       │                     │                     │
       ▼                     ▼                     ▼
    Console              Console               Console
    Sources              Sources               Sources
    Network              Network               Network
       │                     │                     │
       └─────────────────────┼─────────────────────┘
                             │
                             ▼
                      Message Protocol
                             │
                             ▼
                       Storage / State
                             │
                             ▼
                          Web Page
```

Главная идея:

> **Debugging Manifest V3 extension — это debugging не одного JavaScript runtime, а взаимодействия нескольких runtime contexts.**

Поэтому профессиональный debugging строится вокруг пяти вопросов:

```text
1. Где выполняется код?
2. Каков lifecycle этого context?
3. Через какую границу передаются данные?
4. Где находится authoritative state?
5. На каком boundary произошёл failure?
```

Если эти пять вопросов стали частью обычного рабочего процесса, debugging даже сложного Manifest V3 extension становится значительно более системным.

Именно поэтому следующая стадия production development — это уже не просто умение пользоваться DevTools, а создание **наблюдаемого Extension Runtime**: с structured logging, request IDs, state tracing, error boundaries и диагностикой communication между contexts.
