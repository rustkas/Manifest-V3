# Глава 6. Безопасность Manifest V3

Безопасность browser extension принципиально отличается от безопасности обычного веб-приложения.

Extension находится между несколькими мирами:

```text
┌───────────────────────────────┐
│          Web Page             │
│     untrusted environment     │
└───────────────┬───────────────┘
                │
          Content Script
                │
                ▼
┌───────────────────────────────┐
│      Extension Runtime        │
│   trusted extension context   │
└───────────────┬───────────────┘
                │
         Service Worker
                │
                ▼
┌───────────────────────────────┐
│       Browser APIs            │
└───────────────────────────────┘
```

Главная ошибка начинающего разработчика — воспринимать всё это как один JavaScript runtime.

Это не так.

Каждый контекст имеет свои возможности, ограничения и уровень доверия.

Поэтому безопасность Manifest V3 начинается не с `escape()` и не с проверки отдельных строк.

Она начинается с правильного ответа на вопрос:

> **Кому мы доверяем, а кому — нет?**

---

# 6.1. Trust boundaries

**Trust boundary** — граница между компонентами с различным уровнем доверия.

В extension таких границ несколько.

Упрощённая архитектура:

```text
                         Browser
                            │
          ┌─────────────────┴─────────────────┐
          │                                   │
       Web Page                         Extension
     untrusted                              trusted
          │                                   │
          │                            ┌──────┴──────┐
          │                            │             │
          ▼                          Popup      Service Worker
    Content Script
          │
          └──────────── messaging ────────────────┘
```

Здесь особенно важны три понятия:

```text
Page
Content Script
Extension Context
```

Они связаны между собой, но **не являются одним и тем же security context**.

---

## Web page

Обычная веб-страница контролируется сайтом.

Например:

```text
https://example.com
```

Страница может содержать произвольный HTML:

```html
<h1>Hello</h1>
```

JavaScript:

```javascript
<script>
    // page code
</script>
```

и пользовательские данные.

Extension не должен автоматически считать всё это доверенным.

---

## Content Script

Content Script работает на веб-странице, но имеет отдельную extension execution environment.

Это очень важная особенность браузерных extensions.

Упрощённо:

```text
Web Page
   │
   ├── Page JavaScript
   │
   ├── DOM
   │
   └── Content Script
```

Content Script видит DOM страницы, но его JavaScript execution environment отличается от обычного JavaScript страницы.

Поэтому нельзя рассуждать:

> "Content Script находится на странице, значит он полностью является кодом страницы."

Это неверно.

---

## Extension Service Worker

Service Worker относится уже к extension runtime:

```text
Extension
    │
    └── Service Worker
```

Он не является JavaScript-кодом веб-сайта.

Он работает в extension origin и взаимодействует с browser extension APIs.

---

## Trust model

Полезно принять следующую модель:

```text
                 TRUST
                   │
                   ▼

Service Worker
     ▲
     │
Extension UI
     ▲
     │
Content Script
     ▲
     │
Web Page
     ▲
     │
External Web Data
```

Чем дальше данные находятся от extension-controlled environment, тем осторожнее мы должны с ними обращаться.

---

# 6.2. Extension origin

У extension существует собственный origin.

В Chrome-подобных браузерах он выглядит примерно так:

```text
chrome-extension://<extension-id>/
```

Например:

```text
chrome-extension://abcdefghijklmnop/
```

Это принципиально отличается от:

```text
https://example.com/
```

---

## Extension pages

К extension origin относятся страницы и ресурсы самого extension:

```text
popup.html
options.html
sidepanel.html
```

Условно:

```text
chrome-extension://ID/popup.html
chrome-extension://ID/options.html
chrome-extension://ID/sidepanel.html
```

Они принадлежат extension.

---

## Почему отдельный origin важен?

Потому что браузер может разделять:

```text
Web origin
        ≠
Extension origin
```

Например:

```text
https://example.com
```

не становится доверенным extension только потому, что Content Script работает на этой странице.

Это фундаментальная security boundary.

---

## Extension resources

Extension может иметь:

```text
HTML
CSS
JavaScript
images
fonts
WASM
```

и другие ресурсы.

Они находятся под контролем extension package.

Но это не означает, что extension может без ограничений загружать и выполнять произвольный внешний код.

Здесь появляется Content Security Policy.

---

# 6.3. Content Security Policy

**Content Security Policy (CSP)** — механизм ограничения того, какие ресурсы и виды выполнения кода разрешены.

Для Manifest V3 CSP особенно важна.

Упрощённая идея:

```text
Extension
    │
    ▼
CSP
    │
    ├── allowed scripts
    ├── allowed resources
    ├── restricted execution
    └── restricted remote code
```

---

## Почему CSP необходима extension?

Представим уязвимый код:

```javascript
const html = getUserInput();

document.body.innerHTML = html;
```

Если `html` контролируется злоумышленником, это может привести к XSS.

CSP является дополнительным защитным слоем.

Она не заменяет безопасное программирование, но уменьшает последствия некоторых ошибок.

---

## CSP в Manifest

Manifest V3 позволяет задавать extension CSP через:

```json
{
  "content_security_policy": {
    "extension_pages": "..."
  }
}
```

При этом существуют ограничения платформы на допустимую политику.

В частности, extension pages должны использовать достаточно строгую policy для выполнения JavaScript.

---

## Почему нельзя просто разрешить всё?

Например, разработчик мог бы захотеть:

```text
unsafe-eval
```

или разрешить произвольные remote scripts.

Но именно такие возможности делают эксплуатацию XSS значительно опаснее.

Manifest V3 поэтому специально ограничивает модель выполнения кода.

---

# 6.4. Почему `eval()` запрещён

Одна из самых известных особенностей extension security:

```javascript
eval(code);
```

нельзя использовать в обычном extension page execution context.

Также проблемными являются конструкции, которые фактически превращают строку в JavaScript-код.

Например:

```javascript
new Function(code);
```

Идея проста:

```text
String
  ↓
JavaScript source
  ↓
Execution
```

создаёт серьёзную security проблему.

---

## Почему `eval()` опасен?

Представим:

```javascript
const code = localStorage.getItem("code");

eval(code);
```

Если злоумышленник контролирует `code`, он получает возможность заставить extension выполнить произвольный JavaScript в контексте extension.

А extension может обладать гораздо большими привилегиями, чем обычная веб-страница.

Получается:

```text
Untrusted input
      ↓
eval()
      ↓
Extension JavaScript
      ↓
Extension privileges
```

Это очень опасная комбинация.

---

## Даже если данные "локальные"

Ошибка:

```javascript
const expression = await loadData();

eval(expression);
```

может выглядеть безобидно.

Но данные могут прийти из:

* страницы;
* network response;
* storage;
* message;
* imported file;
* URL;
* другого extension context.

Поэтому безопасное правило:

> **Не превращайте данные в исполняемый JavaScript.**

---

## Что использовать вместо `eval()`?

Если нужно обработать данные:

```javascript
JSON.parse()
```

Если нужно выбрать действие:

```javascript
const handlers = {
  save: saveData,
  delete: deleteData,
  export: exportData
};

handlers[action]();
```

вместо:

```javascript
eval(action);
```

То есть:

```text
Data
 ↓
Parse
 ↓
Validate
 ↓
Interpret
```

а не:

```text
Data
 ↓
Execute
```

---

# 6.5. Remote code restrictions

Manifest V3 придерживается очень важного принципа:

> **Код extension должен поставляться как часть extension package, а не загружаться с удалённого сервера для последующего выполнения.**

Плохая архитектура:

```text
Extension
    │
    ▼
https://example.com/code.js
    │
    ▼
execute
```

Например, идея:

```javascript
const code = await fetch("https://example.com/app.js");
eval(code);
```

не соответствует нормальной security model Manifest V3.

---

## Почему remote code опасен?

Представим:

```text
Extension v1
     │
     ▼
Remote server
     │
     ▼
JavaScript
```

Если сервер или его инфраструктура скомпрометированы, поведение уже установленного extension может измениться без нормального обновления extension package.

Получается:

```text
Installed extension
        │
        ▼
Remote mutable code
        │
        ▼
New behavior
```

Это разрушает важную гарантию:

> Код установленного extension соответствует проверенному extension package.

---

## Данные — можно, код — нет

Это фундаментальное различие.

Нормальная архитектура:

```text
Extension
    │
    ├── bundled JavaScript
    │
    └── fetch()
          │
          ▼
       JSON data
```

Например:

```javascript
const response = await fetch(
  "https://api.example.com/data"
);

const data = await response.json();
```

Здесь сервер предоставляет **данные**.

Extension предоставляет **код**.

---

## Ненормальная архитектура

```text
Extension
    │
    ▼
fetch JavaScript
    │
    ▼
execute remote JavaScript
```

То есть:

```text
Remote data
      ↓
Code
      ↓
Execution
```

— принципиально другая модель.

---

# 6.6. XSS внутри extension

Многие разработчики считают:

> XSS бывает только на обычных сайтах.

Это ошибка.

Extension UI также может содержать XSS.

Например:

```text
popup.html
options.html
sidepanel.html
```

— это полноценные HTML-документы.

Если в них небезопасно вставить пользовательские данные, можно получить XSS.

---

## Опасный пример

Предположим:

```javascript
const name = await chrome.storage.local.get("name");

document.body.innerHTML = `
  <h1>Hello ${name}</h1>
`;
```

Если `name` содержит:

```html
<img src=x onerror=...>
```

то приложение потенциально создаёт XSS-проблему.

---

## Более безопасный подход

Если нужно вставить текст:

```javascript
const title = document.createElement("h1");

title.textContent = name;

document.body.appendChild(title);
```

Здесь значение интерпретируется как текст, а не HTML.

---

## `textContent` против `innerHTML`

Если данные недоверенные:

```javascript
element.textContent = value;
```

обычно значительно безопаснее, чем:

```javascript
element.innerHTML = value;
```

Потому что:

```text
textContent
    ↓
Text

innerHTML
    ↓
HTML parser
```

---

## Если HTML действительно нужен

Иногда extension действительно должен создавать HTML.

Тогда необходимо:

1. минимизировать HTML;
2. контролировать структуру;
3. санитизировать недоверенные данные;
4. не разрешать выполнение скриптов;
5. избегать опасных DOM sinks.

Главное правило:

> **Не помещайте недоверенные данные в HTML без необходимости.**

---

# 6.7. Безопасная работа с DOM

Content Script особенно чувствителен к DOM security.

Он работает непосредственно с DOM веб-страницы.

Например:

```javascript
const title = document.querySelector("h1");
```

Это нормально.

Но дальше:

```javascript
const value = title.textContent;
```

мы получили данные из страницы.

И эти данные следует считать:

```text
UNTRUSTED INPUT
```

---

## Page DOM — недоверенная среда

Например, страница может содержать:

```html
<h1>
    Hello
</h1>
```

Но заголовок может содержать:

```html
<img src=x onerror=...>
```

или просто произвольный текст:

```text
<script>alert(...)</script>
```

Если Content Script извлекает его:

```javascript
const title = document.querySelector("h1")?.textContent;
```

полученное значение нельзя автоматически считать безопасным.

---

## Никогда не делайте так

```javascript
const title = document.querySelector("h1").textContent;

someExtensionElement.innerHTML = title;
```

Вы перенесли данные:

```text
Web Page
   ↓
Content Script
   ↓
Extension UI
```

и при этом использовали HTML sink.

Это потенциальная trust-boundary ошибка.

---

## Лучше

```javascript
someExtensionElement.textContent = title;
```

Теперь:

```text
Page data
    ↓
text
    ↓
Extension UI
```

---

## DOM как источник данных

Полезно ввести понятие:

> **DOM страницы — это external input.**

Например:

```text
document.title
location.href
element.textContent
element.getAttribute(...)
```

могут считаться входными данными.

Их нужно:

```text
Read
 ↓
Validate
 ↓
Normalize
 ↓
Use
```

---

# 6.8. Message validation

Одна из наиболее важных частей безопасности extension — messaging.

Типичная архитектура Manifest V3:

```text
Popup
   │
   │ message
   ▼
Service Worker
   │
   │ message
   ▼
Content Script
```

Можно использовать:

```javascript
chrome.runtime.sendMessage(...)
```

или:

```javascript
chrome.tabs.sendMessage(...)
```

---

## Главная ошибка

Разработчик предполагает:

> "Сообщение пришло от моего extension, значит данные безопасны."

Это две разные вещи.

Даже если сообщение приходит из extension context, его payload всё равно может содержать недоверенные данные.

Например:

```javascript
{
  action: "save",
  content: userControlledData
}
```

`content` необходимо проверять.

---

## Никогда не доверяйте структуре сообщения

Плохой обработчик:

```javascript
chrome.runtime.onMessage.addListener(
  (message) => {
    executeAction(message.action, message.data);
  }
);
```

Здесь слишком много доверия к входу.

Лучше:

```javascript
chrome.runtime.onMessage.addListener(
  (message, sender, sendResponse) => {

    if (!message || typeof message !== "object") {
      return;
    }

    if (message.action === "save") {
      // validate message.data
    }

    if (message.action === "delete") {
      // validate input
    }
  }
);
```

---

## Используйте allowlist

Очень хороший шаблон:

```javascript
const allowedActions = new Set([
  "save",
  "load",
  "delete"
]);

if (!allowedActions.has(message.action)) {
  return;
}
```

То есть:

```text
Input
  ↓
Is action allowed?
  │
 ┌┴──────────┐
 No          Yes
 │            │
Reject     Validate data
               │
               ▼
             Execute
```

---

## Проверяйте sender

При обработке сообщений также может иметь значение:

```javascript
sender
```

Например:

```javascript
sender.tab
sender.id
sender.origin
```

Конкретная проверка зависит от архитектуры.

Но принцип:

> **Не считайте любой входящий message автоматически trusted.**

---

# 6.9. Работа с недоверенными страницами

Теперь объединим предыдущие концепции.

Представим:

```text
https://malicious.example
```

На странице есть:

```text
malicious HTML
malicious JavaScript
malicious links
malicious user data
```

Наш Content Script запускается на ней.

Получаем:

```text
             Untrusted Page
                    │
                    ▼
              Content Script
                    │
                    ▼
             Extension Runtime
```

Самая опасная ошибка — забыть про эту границу.

---

## Content Script должен быть "пограничным контроллером"

Очень полезная архитектурная модель:

```text
                 Web Page
               UNTRUSTED
                    │
                    ▼
          ┌───────────────────┐
          │  Content Script   │
          │   Trust Boundary  │
          └─────────┬─────────┘
                    │
              Validate data
                    │
                    ▼
            Extension Runtime
               TRUSTED
```

То есть Content Script можно рассматривать как **adapter между внешним Web и extension**.

---

## Не передавайте всё подряд

Плохой дизайн:

```text
Page
 ↓
Content Script
 ↓
send entire DOM
 ↓
Service Worker
 ↓
Storage
```

В результате extension может сохранять огромное количество ненужных данных.

Лучше:

```text
Page
 ↓
Extract required fields
 ↓
Validate
 ↓
Normalize
 ↓
Send structured data
```

Например:

```javascript
{
  title: "...",
  author: "...",
  url: "..."
}
```

вместо:

```javascript
{
  entireHTML: document.documentElement.outerHTML
}
```

---

## Validate before privileged operation

Особенно важно, когда данные страницы используются для privileged operations.

Например:

```text
Page
  ↓
URL
  ↓
Service Worker
  ↓
Network request
```

Нельзя автоматически считать URL безопасным.

Например, extension может иметь host permission:

```text
https://api.example.com/*
```

но если код позволяет странице управлять произвольным URL:

```javascript
fetch(message.url);
```

возникает архитектурная проблема.

Лучше использовать allowlist:

```javascript
const allowedHosts = [
  "api.example.com"
];
```

и проверять URL перед операцией.

---

# 6.10. Типичные архитектурные ошибки

Теперь рассмотрим наиболее распространённые ошибки.

---

## Ошибка №1. Использование `eval()`

Плохо:

```javascript
eval(userInput);
```

или:

```javascript
new Function(userInput)();
```

Почему плохо:

```text
Untrusted data
      ↓
Code execution
      ↓
Extension privileges
```

Используйте данные как данные.

---

# Ошибка №2. Remote JavaScript

Плохо:

```javascript
const code = await fetch(url).then(r => r.text());

eval(code);
```

Правильно:

```text
Extension code
    ↓
bundled with extension

Remote server
    ↓
data
```

---

# Ошибка №3. `innerHTML` с недоверенными данными

Плохо:

```javascript
element.innerHTML = userInput;
```

Лучше:

```javascript
element.textContent = userInput;
```

---

# Ошибка №4. Доверие к Content Script input

Плохо:

```text
Content Script
     ↓
"this data came from our extension"
     ↓
Service Worker trusts it
```

На самом деле:

```text
Content Script
     ↓
data extracted from page
     ↓
UNTRUSTED
```

---

# Ошибка №5. Отсутствие validation сообщений

Плохо:

```javascript
if (message.action === "execute") {
    run(message.code);
}
```

Особенно если `message.code` контролируется внешним input.

Лучше:

```text
message
  ↓
schema validation
  ↓
allowlist
  ↓
typed data
  ↓
operation
```

---

# Ошибка №6. Слишком широкие host permissions

Например:

```json
{
  "host_permissions": [
    "<all_urls>"
  ]
}
```

для extension, который работает только с:

```text
https://example.com/*
```

Это увеличивает security scope без необходимости.

---

# Ошибка №7. Передача всего DOM

Плохо:

```javascript
sendMessage({
  html: document.documentElement.outerHTML
});
```

если extension нужен только заголовок.

Лучше:

```javascript
sendMessage({
  title: document.title
});
```

Минимизация данных — тоже security principle.

---

# Ошибка №8. Смешивание Page JavaScript и Extension JavaScript

Архитектура:

```text
Page
  ↕
Content Script
  ↕
Service Worker
```

не должна превращаться в:

```text
Page
  ───────────────► privileged extension logic
```

без чёткой проверки границы.

---

# Ошибка №9. Хранение секретов в extension

Extension code нельзя считать секретным.

Например:

```javascript
const API_SECRET = "super-secret-key";
```

не следует рассматривать как надёжное хранение секрета.

Установленный extension содержит код, который потенциально можно исследовать.

Поэтому:

```text
Extension
    ≠
Secure secret vault
```

Если нужен настоящий server-side secret, его обычно следует держать на сервере.

---

# Ошибка №10. Считать CSP единственной защитой

Нельзя рассуждать:

> "У нас есть CSP, значит XSS невозможен."

CSP — это **defense in depth**, а не замена безопасному коду.

Правильная модель:

```text
Secure coding
      +
Input validation
      +
Safe DOM APIs
      +
CSP
      +
Least privilege
      +
Minimal host access
      ↓
Defense in depth
```

---

# Security Architecture Manifest V3

Теперь можно объединить весь материал главы в одну модель:

```text

                            │
```

# Defense in Depth

Безопасность extension не должна зависеть от одного механизма.

Представим, что в Content Script есть ошибка.

Хорошая архитектура должна иметь дополнительные защитные уровни:

```text
Layer 1
Least Privilege
       ↓
Layer 2
Limited Host Permissions
       ↓
Layer 3
Content Script isolation
       ↓
Layer 4
Input validation
       ↓
Layer 5
Message validation
       ↓
Layer 6
Safe DOM APIs
       ↓
Layer 7
Strict CSP
       ↓
Layer 8
No dynamic code execution
```

Это называется **defense in depth**.

# Практический security checklist

Перед публикацией Manifest V3 extension полезно проверить:

### Permissions

```text
[ ] Все permissions действительно необходимы?
[ ] Можно ли заменить широкое permission более узким?
[ ] Используется ли activeTab вместо постоянного доступа там, где это возможно?
[ ] Optional capabilities действительно optional?
```

### Hosts

```text
[ ] Все host permissions необходимы?
[ ] Можно ли отказаться от <all_urls>?
[ ] Можно ли ограничить конкретным доменом?
[ ] Нужны ли wildcard subdomains?
```

### Code execution

```text
[ ] Нет eval()
[ ] Нет new Function()
[ ] Нет динамического выполнения строк как JavaScript
[ ] Нет remote JavaScript
```

### DOM

```text
[ ] Недоверенные данные не попадают напрямую в innerHTML?
[ ] Используется textContent там, где нужен текст?
[ ] HTML sanitization применяется при необходимости?
```

### Messaging

```text
[ ] Messages валидируются?
[ ] Actions используют allowlist?
[ ] Payload имеет ожидаемый тип?
[ ] Sender учитывается там, где это необходимо?
```

### External data

```text
[ ] Данные веб-страницы считаются untrusted?
[ ] Network responses валидируются?
[ ] URL проверяются?
[ ] Extension не доверяет произвольному input?
```

# Главные выводы главы

### 1. Extension — не единый JavaScript runtime

Есть разные contexts:

```text
Page
Content Script
Extension UI
Service Worker
```

и между ними существуют trust boundaries.

---

### 2. Web page следует считать недоверенной

Даже если Content Script работает на странице:

```text
Page data
    ↓
UNTRUSTED INPUT
```

---

### 3. Extension имеет собственный origin

```text
chrome-extension://<extension-id>/
```

Он отличается от web origins:

```text
https://example.com/
```

---

### 4. CSP является дополнительным защитным слоем

Она ограничивает возможности выполнения кода и уменьшает последствия некоторых ошибок.

Но:

```text
CSP ≠ secure application
```

---

### 5. `eval()` и подобные механизмы динамического выполнения кода не являются нормальной частью Manifest V3 extension architecture

Используйте:

```text
data → parse → validate → process
```

а не:

```text
data → execute
```

---

### 6. Remote code и remote data — разные вещи

Допустимая архитектура:

```text
Bundled code
      +
Remote data
```

а не:

```text
Bundled loader
      +
Remote executable JavaScript
```

---

### 7. DOM страницы — источник недоверенных данных

Особенно важно:

```javascript
element.textContent = value;
```

предпочтительнее прямой вставки недоверенного значения через:

```javascript
element.innerHTML = value;
```

---

### 8. Messages необходимо валидировать

Правильная цепочка:

```text
Message
   ↓
Validate
   ↓
Authorize
   ↓
Process
```

---

### 9. Least Privilege — фундаментальный принцип

Он применяется одновременно к:

```text
permissions
host_permissions
contexts
data
messaging
network
```

---

### 10. Хорошая security architecture начинается с trust boundaries

Главная модель этой главы:

```text
                  UNTRUSTED
                      │
                  Web Page
                      │
                      ▼
                Content Script
                      │
               Validate data
                      │
                      ▼
              Extension Runtime
                      │
                      ▼
                Browser APIs
                      │
                   TRUSTED
```

Именно эту модель нужно держать в голове при разработке любого Manifest V3 extension.

Следующая глава естественно переходит от **безопасности** к **архитектуре выполнения**: мы разберём **Extension Contexts** — Popup, Options Page, Side Panel, Content Script и Service Worker, почему они существуют отдельно и какую роль каждый из них играет.
