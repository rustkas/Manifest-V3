# Глава 38. Testing

Тестирование browser extension существенно отличается от тестирования обычного веб-приложения.

В обычном приложении можно представить архитектуру примерно так:

```text
Application
    │
    ├── Components
    ├── Services
    ├── State
    └── API
```

У Manifest V3 extension архитектура распределённая:

```text
                         Extension
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
       Popup             Service Worker    Content Script
          │                  │                  │
          ▼                  ▼                  ▼
       UI/DOM             Storage/API       Page DOM
          │                                     │
          ▼                                     ▼
      User input                           Web page
```

Кроме того, существуют:

```text
Side Panel
Options Page
DevTools Page
Injected scripts
MAIN world
Browser APIs
Network
Permissions
```

Поэтому testing Manifest V3 — это не один тип тестов.

Нужна **многоуровневая стратегия тестирования**:

```text
Unit
  ↓
Runtime
  ↓
Context
  ↓
Integration
  ↓
Browser automation
  ↓
End-to-end
```

Главный принцип:

> **Чем ближе тест к реальному браузеру и взаимодействию contexts, тем дороже он становится, поэтому дорогие тесты должны проверять только те свойства, которые невозможно надёжно проверить на более низком уровне.**

---

# 38.1. Unit tests

Unit test проверяет небольшую, изолированную часть программы.

Например:

```javascript
function normalizeUrl(url) {
    return new URL(url).origin;
}
```

Для такой функции browser extension вообще не нужен.

Можно проверить:

```text
input
  ↓
function
  ↓
output
```

---

# Почему unit tests особенно важны для extension

Manifest V3 предоставляет большое количество browser APIs:

```text
chrome.tabs
chrome.storage
chrome.scripting
chrome.runtime
chrome.permissions
chrome.alarms
```

Но бизнес-логика extension не должна целиком находиться внутри этих API calls.

Плохая архитектура:

```javascript
chrome.runtime.onMessage.addListener(async message => {
    const tabs = await chrome.tabs.query(...);

    const data = await fetch(...);

    await chrome.storage.local.set(...);

    // вся бизнес-логика здесь
});
```

Такой код трудно тестировать.

Лучше:

```text
Chrome API
     ↓
Adapter
     ↓
Application Service
     ↓
Pure Logic
```

Например:

```javascript
function calculateResult(data, settings) {
    // pure business logic
}
```

Теперь:

```text
Unit Test
    ↓
calculateResult()
```

не требует запуска браузера.

---

# Pure functions

Чем больше логики можно представить как:

```text
input → function → output
```

тем проще тестирование.

Например:

```javascript
function shouldProcessPage(url, settings) {
    return settings.enabled &&
           url.startsWith("https://");
}
```

Тест:

```javascript
expect(
    shouldProcessPage(
        "https://example.com",
        { enabled: true }
    )
).toBe(true);
```

Здесь нет:

```text
Chrome
Tab
Service Worker
DOM
Network
```

и это хорошо.

---

# Unit testing архитектуры

Хорошая extension architecture старается разделить:

```text
Infrastructure
        │
        ▼
Application
        │
        ▼
Domain
```

Например:

```text
chrome.storage
       │
       ▼
StorageAdapter
       │
       ▼
SettingsService
       │
       ▼
Application Logic
```

Тогда:

```text
StorageAdapter
    → integration test

SettingsService
    → unit test

Application Logic
    → unit test
```

---

# Что тестировать unit-тестами

Хорошие кандидаты:

* parsing;
* validation;
* URL matching;
* state transformations;
* reducers;
* message validation;
* serialization;
* rule generation;
* business logic;
* configuration processing;
* permission decisions.

Например:

```javascript
function createRule(config) {
    // ...
}
```

Можно протестировать десятки комбинаций без запуска браузера.

---

# Что не следует тестировать unit-тестом

Не стоит пытаться unit-тестировать:

```text
chrome.tabs.query()
chrome.storage.local.get()
chrome.scripting.executeScript()
```

как настоящие browser APIs.

Их лучше проверять на более высоком уровне.

---

# Mocking Chrome APIs

Иногда unit test всё же должен работать с API abstraction.

Например:

```javascript
const chromeApi = {
    storage: {
        get: async () => ({
            enabled: true
        })
    }
};
```

Тестирует не Chrome, а ваш код:

```text
Application
    ↓
Chrome API abstraction
    ↓
Mock
```

Это существенно лучше, чем пытаться воспроизводить весь браузер.

---

# 38.2. Runtime tests

Runtime tests проверяют поведение extension runtime.

Это уже уровень выше unit tests.

Например:

```text
Service Worker
    ↓
message
    ↓
handler
    ↓
state
```

Можно проверить:

```text
message arrives
handler executes
response is generated
state changes
```

---

# Runtime как отдельный объект тестирования

В предыдущих главах мы рассматривали Extension Runtime как систему:

```text
Events
   ↓
Routing
   ↓
Handlers
   ↓
State
   ↓
Effects
```

Теперь эту систему можно тестировать независимо от UI.

Например:

```text
MESSAGE: GET_SETTINGS
        ↓
Runtime
        ↓
Storage
        ↓
RESPONSE
```

---

# Runtime test

Условный тест:

```javascript
const response = await runtime.handleMessage({
    type: "GET_SETTINGS"
});

expect(response).toEqual({
    theme: "dark"
});
```

Здесь мы проверяем application runtime, а не реальный браузер.

---

# Event simulation

Можно симулировать события:

```text
ACTION_CLICK
TAB_UPDATED
MESSAGE_RECEIVED
ALARM
INSTALL
```

Например:

```javascript
await runtime.dispatch({
    type: "TAB_UPDATED",
    tabId: 42
});
```

И проверить:

```javascript
expect(state.activeTab).toBe(42);
```

---

# Почему runtime tests полезны

Они проверяют архитектуру:

```text
Event
 ↓
Router
 ↓
Handler
 ↓
State
 ↓
Effect
```

без стоимости полноценного браузера.

Это особенно важно для Service Worker.

---

# 38.3. Content Script tests

Content Script является одним из самых сложных объектов тестирования.

Причина:

```text
Content Script
      │
      ├── DOM
      ├── Page lifecycle
      ├── SPA navigation
      ├── Frames
      ├── Shadow DOM
      └── Extension messaging
```

Поэтому полезно разделять тестирование content script на несколько уровней.

---

# Level 1 — DOM logic

Например:

```javascript
function extractProducts(document) {
    return [...document.querySelectorAll(".product")]
        .map(node => node.textContent.trim());
}
```

Эту функцию можно тестировать с искусственным DOM.

```text
HTML fixture
    ↓
DOM
    ↓
extractProducts()
    ↓
result
```

Browser extension при этом не нужен.

---

# Level 2 — Content Script runtime

Затем тестируется:

```text
Content Script
    ↓
DOM
    ↓
message
```

Например:

```text
PAGE
 ↓
Content Script
 ↓
extract
 ↓
sendMessage
```

Можно проверить, что:

1. DOM найден;
2. данные извлечены;
3. сообщение отправлено;
4. payload соответствует schema.

---

# Level 3 — Real browser

Наконец:

```text
Real Web Page
       ↓
Content Script
       ↓
Real Extension Runtime
```

Это уже browser automation.

---

# DOM fixtures

Очень полезная техника — хранить реальные HTML-примеры:

```text
tests/
├── fixtures/
│   ├── page-a.html
│   ├── page-b.html
│   └── page-spa.html
```

Тест:

```text
fixture
   ↓
DOM
   ↓
extractor
   ↓
expected result
```

Это позволяет воспроизводить реальные структуры сайтов.

---

# Dynamic DOM

Особое внимание нужно уделять сайтам, которые меняют DOM после загрузки.

Например:

```text
Initial HTML
     ↓
JavaScript
     ↓
DOM update
     ↓
MutationObserver
     ↓
Content Script
```

Тест должен проверять не только initial page.

---

# SPA navigation

Для SPA:

```text
/page/a
   ↓
history.pushState()
   ↓
/page/b
```

полной загрузки страницы может не произойти.

Поэтому test должен проверять:

```text
initial navigation
client-side navigation
DOM replacement
back/forward
```

---

# 38.4. Service Worker tests

Service Worker необходимо тестировать с учётом его ephemeral nature.

Главная ошибка:

```javascript
let state = {};
```

и тест:

```text
start worker
set state
call function
expect state
```

Такой тест может создавать ложное ощущение надёжности.

---

# Что нужно проверять

Service Worker должен корректно работать после:

```text
cold start
restart
suspension
new event
```

Например:

```text
Worker #1
    ↓
save state
    ↓
terminated
    ↓
Worker #2
    ↓
load state
    ↓
continue
```

---

# Cold-start test

Полезный сценарий:

```text
No worker state
       ↓
Event arrives
       ↓
Worker starts
       ↓
Load persistent state
       ↓
Process event
       ↓
Save result
```

Если приложение работает только после предварительного запуска worker, architecture содержит ошибку.

---

# Storage-backed state

Например:

```javascript
const state =
    await chrome.storage.local.get("state");
```

Тест должен проверять:

```text
Worker start
     ↓
state load
     ↓
event
     ↓
state update
     ↓
state save
```

---

# Alarm testing

Если extension использует:

```javascript
chrome.alarms
```

необходимо проверять:

```text
alarm created
alarm fires
worker starts
handler executes
state updated
```

Особенно важно не тестировать только сам handler.

Нужно проверить путь:

```text
Alarm
  ↓
Worker startup
  ↓
Handler
```

---

# Message tests

Service Worker часто является центральным router:

```text
Popup
   ↓
Worker
   ↓
Content Script
```

Тесты должны проверять:

```text
known message
unknown message
malformed message
missing fields
invalid permissions
target tab unavailable
```

---

# Unknown messages

Например:

```javascript
{
    type: "UNKNOWN"
}
```

не должен приводить к:

```text
worker crash
```

Лучше:

```text
validation
   ↓
reject
   ↓
structured error
```

---

# 38.5. Integration tests

Integration test проверяет взаимодействие нескольких компонентов.

Например:

```text
SettingsService
      +
StorageAdapter
      +
MessageRouter
```

или:

```text
Service Worker
      +
Content Script
```

---

# Unit vs Integration

Упрощённо:

```text
Unit Test
A
```

проверяет:

```text
A
```

Integration test:

```text
A → B → C
```

Например:

```text
MessageRouter
      ↓
SettingsService
      ↓
Storage
```

---

# Extension integration

Хороший integration test может проверять:

```text
Popup
   ↓
Service Worker
   ↓
Storage
```

без реального web page.

Другой:

```text
Service Worker
   ↓
Content Script
```

без сложного пользовательского UI.

---

# Integration boundaries

Особенно важно тестировать границы:

```text
Context ↔ Context
Context ↔ Storage
Context ↔ Network
Content Script ↔ Page
Extension ↔ Browser API
```

Именно на границах чаще всего появляются реальные ошибки.

---

# Example

Пользователь меняет setting:

```text
Options
   ↓
storage.local.set()
   ↓
storage.onChanged
   ↓
Service Worker
   ↓
Side Panel
```

Integration test должен проверить всю цепочку.

---

# Failure testing

Integration test должен проверять не только success:

```text
Storage available
```

но и:

```text
Storage failure
Permission denied
Invalid data
Worker restart
Message timeout
```

---

# 38.6. Browser automation

Browser automation запускает настоящий браузер и взаимодействует с ним программно.

Типичная архитектура:

```text
Test Runner
     │
     ▼
Browser
     │
     ▼
Extension
     │
     ├── Popup
     ├── Worker
     ├── Content Script
     └── Page
```

Это уже значительно ближе к реальному поведению пользователя.

---

# Почему browser automation необходим

Некоторые свойства невозможно надёжно проверить mock'ами:

```text
manifest loading
content script injection
permissions
real DOM
extension lifecycle
popup behavior
tab interaction
service worker integration
```

Поэтому хотя бы небольшой набор browser-level tests необходим для production extension.

---

# Automation tools

Для автоматизации браузера можно использовать современные browser automation frameworks, например:

* Playwright;
* Puppeteer;
* WebDriver-based tools.

Важно не столько название инструмента, сколько архитектура тестов.

---

# Loading unpacked extension

Во время browser test extension обычно запускается как локальное extension.

Упрощённая схема:

```text
Test
 ↓
Launch browser
 ↓
Load extension
 ↓
Open test page
 ↓
Interact
 ↓
Assert
```

---

# Test page

Очень полезно иметь собственный test website:

```text
tests/
├── pages/
│   ├── basic.html
│   ├── dynamic.html
│   ├── spa.html
│   └── iframe.html
```

Например:

```text
basic.html
```

содержит:

```html
<div id="target">
    Hello
</div>
```

Content Script должен найти:

```javascript
document.querySelector("#target");
```

и изменить его.

---

# Browser automation test

Сценарий:

```text
Launch browser
       ↓
Load extension
       ↓
Open test page
       ↓
Wait for content script
       ↓
Inspect DOM
       ↓
Assert result
```

---

# Popup automation

Можно проверить:

```text
click extension action
       ↓
popup opens
       ↓
click button
       ↓
worker receives message
       ↓
state changes
       ↓
popup displays result
```

Это уже полноценный interaction test.

---

# Side Panel automation

Для Side Panel:

```text
Open browser
     ↓
activate extension
     ↓
open Side Panel
     ↓
select tab
     ↓
execute operation
     ↓
assert UI
```

Side Panel особенно удобен для end-to-end workflows, потому что живёт дольше popup.

---

# 38.7. End-to-end tests

End-to-end test проверяет сценарий глазами пользователя.

Не:

```text
function()
```

и не:

```text
service()
```

а:

```text
User
  ↓
Browser
  ↓
Extension
  ↓
Web Page
  ↓
Result
```

---

# Example E2E scenario

Предположим, extension анализирует текущую страницу.

Пользователь:

```text
1. Открывает страницу
2. Нажимает extension icon
3. Открывает Side Panel
4. Нажимает Analyze
5. Extension анализирует DOM
6. Показывает результат
```

E2E test должен повторить именно этот сценарий.

---

# E2E architecture

```text
User action
     ↓
UI
     ↓
Message
     ↓
Service Worker
     ↓
Content Script
     ↓
DOM
     ↓
Result
     ↓
Storage
     ↓
UI update
```

Это позволяет проверить всю архитектуру одновременно.

---

# E2E test example

Условно:

```javascript
await page.goto(testUrl);

await openExtensionPanel();

await panel.getByRole("button", {
    name: "Analyze"
}).click();

await expect(
    panel.getByText("42 items")
).toBeVisible();
```

Здесь нас интересует не внутренняя реализация.

Нам важно:

```text
user action
      ↓
expected observable result
```

---

# Что E2E должен проверять

Хорошие E2E tests:

* основной пользовательский workflow;
* критический permission flow;
* content-script integration;
* authentication flow;
* важные network workflows;
* persistence;
* основные UI paths.

---

# Что E2E не должен проверять

Не нужно превращать каждый unit test в E2E test.

Например, функция:

```javascript
calculatePrice()
```

не должна проверяться через:

```text
Launch browser
→ open extension
→ click popup
→ click button
→ inspect result
```

Это слишком дорого.

Лучше:

```text
calculatePrice()
    ↓
unit test
```

---

# Test pyramid

Для extension особенно полезна следующая модель:

```text
                 E2E
                /   \
           Browser tests
             /       \
        Integration
          /       \
       Runtime   Context
         /         \
      Unit tests
```

Или количественно:

```text
        █
       E2E

      ███
   Browser

     █████
 Integration

  █████████
    Unit
```

Большая часть тестов должна быть дешёвой.

---

# 38.8. Testing multiple contexts

Это центральная тема testing Manifest V3.

Обычный frontend:

```text
Application
    ↓
single runtime
```

Extension:

```text
                   Extension
                       │
       ┌───────────────┼───────────────┐
       │               │               │
       ▼               ▼               ▼
    Popup           Worker          Content
       │               │               │
       ▼               ▼               ▼
      DOM            APIs            Page
```

Каждый context необходимо тестировать отдельно, а затем — их взаимодействие.

---

# Context matrix

Полезно создать тестовую матрицу:

| Context        | Unit | Runtime | Browser | E2E |
| -------------- | ---: | ------: | ------: | --: |
| Service Worker |    ✓ |       ✓ |       ✓ |   ✓ |
| Content Script |    ✓ |       ✓ |       ✓ |   ✓ |
| Popup          |    ✓ |       — |       ✓ |   ✓ |
| Side Panel     |    ✓ |       — |       ✓ |   ✓ |
| Options        |    ✓ |       — |       ✓ |   ✓ |
| Page Bridge    |    ✓ |       ✓ |       ✓ |   ✓ |

Это не означает, что каждый context должен иметь одинаковое количество тестов.

---

# Popup testing

Для Popup:

```text
Unit
 ↓
UI logic
 ↓
Browser test
 ↓
E2E
```

Проверяем:

```text
rendering
events
message sending
state display
closing behavior
```

---

Для Worker:


```text

```

---

# Content Script testing

Для Content Script:

```text
DOM unit tests
       ↓
content runtime
       ↓

E2E
```

Проверяем:

```text
DOM extraction
mutation handling
navigation
messaging
page integration

```

---

# Side Panel testing

Для Side Panel:

```text
UI tests
   ↓
message tests
   ↓

   ↓
E2E
```

Особенно важны:

```text
active tab

```

---

# Options testing

Options Page обычно проще:

```text
UI
 ↓
Storage
 ↓
State
```

Основной workflow:

```text
Open Options
   ↓
Change setting
   ↓
Save
   ↓
Reload
   ↓
Setting persists
```

Это отличный integration/E2E сценарий.

---

# Testing context communication

Предположим:

```text
Popup
   ↓
sendMessage
   ↓
Worker
   ↓
sendMessage
   ↓
Content Script
```

Нужно проверить:

```text
1. Popup sends correct schema
2. Worker validates message
3. Worker routes message
4. Content receives message
5. Content produces response
6. Worker forwards result
7. Popup updates UI
```

---

# Typed messages

Если используется typed protocol:

```typescript
type Message =
    | {
        type: "GET_STATE";
        requestId: string;
    }
    | {
        type: "ANALYZE_PAGE";
        requestId: string;
    };
```

тесты должны проверять:

```text
valid message
invalid type
missing requestId
invalid payload
unknown fields
```

---

# Testing failures

Distributed extension должен тестироваться не только в happy path.

Например:

```text
Popup
  ↓
Worker
  ✗
```

Что должно произойти?

UI должен получить:

```text
error
```

а не зависнуть навсегда.

---

# Timeout testing

Для межконтекстных операций полезно иметь timeout:

```javascript
await requestWithTimeout(
    message,
    5000
);
```

Тест:

```text
send message
   ↓
no response
   ↓
timeout
   ↓
error state
```

---

# Worker restart testing

Один из наиболее важных integration scenarios:

```text
Worker
   ↓
process request
   ↓
state persisted
   ↓
worker terminated
   ↓
new event
   ↓
worker restarts
   ↓
state restored
```

Если этот сценарий не работает, extension может быть нестабильным в реальном использовании.

# Race conditions

Например:

```text
Tab A
  ↓
request 1

Tab A
  ↓
request 2
```

Ответы могут прийти:

```text
response 2
response 1
```

Если код предполагает:

```text
response 1 always arrives first
```

он содержит race condition.

Тесты должны воспроизводить подобные ситуации.

# Итог

Testing Manifest V3 требует отказаться от представления:

```text
Extension = JavaScript application
```

и перейти к модели:

```text
Extension
    │
    ├── multiple contexts
    ├── browser APIs
    ├── events
    ├── messages
    ├── persistent state
    ├── ephemeral runtime
    ├── web pages
    └── user interface
```

Поэтому тестирование должно быть многоуровневым:

```text
                    User
                     │
                     ▼
                    E2E
                     │
                     ▼
              Browser automation
                     │
                     ▼
                Integration
                     │
                     ▼
                  Runtime
                     │
                     ▼
                    Unit
```

Каждый уровень отвечает на свой вопрос:

| Уровень     | Главный вопрос                                       |
| ----------- | ---------------------------------------------------- |
| Unit        | Правильно ли работает отдельная логика?              |
| Runtime     | Правильно ли работает extension runtime?             |
| Context     | Правильно ли работает конкретный context?            |
| Integration | Правильно ли взаимодействуют компоненты?             |
| Browser     | Правильно ли extension работает в реальном браузере? |
| E2E         | Работает ли реальный пользовательский сценарий?      |

Самая важная идея этой главы:

> **Не пытайтесь тестировать всё через браузер. Но и не пытайтесь протестировать браузер с помощью mocks.**

Правильная стратегия находится между этими крайностями:

```text
Pure Logic
    ↓
Unit Tests
    ↓
Extension Runtime
    ↓
Integration
    ↓
Real Browser
    ↓
Real User Workflow
```

Именно такая модель позволяет одновременно получить **быстрые тесты для разработки**, **глубокое покрытие архитектуры** и **достаточную уверенность, что Manifest V3 extension действительно работает в реальном браузере**.
