# Глава 20. Side Panel

Side Panel — один из наиболее интересных UI-механизмов современных браузерных расширений.

Popup рассчитан на короткое взаимодействие:

```text
Click Action
     ↓
Popup
     ↓
Action
     ↓
Popup closes
```

Side Panel предназначена для другого сценария:

```text
Open Side Panel
      ↓
Panel remains visible
      ↓
User browses pages
      ↓
Extension reacts
      ↓
User continues interacting
```

Именно поэтому Side Panel особенно хорошо подходит для расширений, которые нельзя удобно представить в виде небольшой всплывающей панели.

Например:

* AI assistant;
* page analyzer;
* translator;
* research assistant;
* bookmark manager;
* developer tools;
* productivity application;
* document assistant;
* shopping assistant;
* data extraction tool.

---

# 20.1. Что такое Side Panel

Side Panel — это интерфейс расширения, отображаемый в боковой панели браузера.

Концептуально:

```text
┌───────────────────────────────────────────────┐
│ Browser                                      │
├───────────────────────────────────────┬───────┤
│                                       │       │
│                                       │ Side  │
│             Web Page                  │Panel  │
│                                       │       │
│                                       │       │
│                                       │       │
│                                       │       │
└───────────────────────────────────────┴───────┘
```

В отличие от Popup:

```text
┌───────────────┐
│    Popup      │
│               │
│   temporary   │
└───────────────┘
```

Side Panel является частью длительного UI-сеанса.

---

# Popup vs Side Panel

Разница становится особенно очевидной на примере.

Допустим, extension анализирует веб-страницу.

В Popup:

```text
User clicks extension
        ↓
Popup opens
        ↓
[ Analyze ]
        ↓
Result displayed
        ↓
User clicks page
        ↓
Popup closes
```

Пользователю приходится снова открывать extension.

В Side Panel:

```text
User opens Side Panel
        ↓
Analyze current page
        ↓
Read result
        ↓
Open another page
        ↓
Analyze
        ↓
Continue working
```

Panel остаётся доступной.

---

# Side Panel как persistent UI

Важно правильно понимать термин «persistent».

Side Panel не означает:

> JavaScript-код гарантированно работает постоянно.

Это UI surface.

Браузер управляет lifecycle страницы и связанных contexts.

Поэтому нужно различать:

```text
UI persistence
```

и:

```text
runtime persistence
```

Side Panel может оставаться открытой для пользователя, но нельзя строить архитектуру так, будто весь extension runtime никогда не останавливается.

---

# Side Panel — Extension Page

С точки зрения архитектуры Side Panel представляет собой extension page.

Она имеет собственный JavaScript context:

```text
Side Panel
    │
    ├── HTML
    ├── CSS
    ├── JavaScript
    ├── DOM
    └── Extension APIs
```

Но это не означает наличие общего JavaScript state с Service Worker или Content Script.

Например:

```text
Side Panel
    │
    │ message
    ▼
Service Worker
```

а не:

```text
Side Panel
    │
    │ shared variable
    ▼
Service Worker
```

---

# Где Side Panel находится в архитектуре

Теперь наша архитектура расширения становится более полной:

```text
                       Extension
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
        Popup            Options         Side Panel
          │                │                │
          └────────────────┼────────────────┘
                           │
                           ▼
                    Service Worker
                           │
                           ▼
                    Content Scripts
                           │
                           ▼
                         Page
```

Здесь:

```text
side_panel
    │
    └── default_path
            │
```



Браузер загружает:

```text
chrome-extension://<extension-id>/sidepanel.html
```

# 20.3. Side Panel lifecycle

Lifecycle Side Panel отличается от Popup.

Popup:

```text
open
  ↓
initialize
  ↓
user interacts
  ↓
close
  ↓
destroy
```

Side Panel:

```text
open
  ↓
initialize
  ↓
user interacts
  ↓
panel remains open
  ↓
user changes tab
  ↓
panel may remain available
  ↓
user closes panel
```

Но важно:

> Side Panel нельзя считать вечным JavaScript runtime.

---

# Initialization

При загрузке:

```javascript
async function init() {

    const settings =
        await chrome.storage.sync.get({
            theme: "system"
        });

    render(settings);
}

init();
```

---

# Почему нельзя хранить критическое состояние только в memory

Например:

```javascript
let selectedDocument = null;
```

Это нормально как UI state.

Но если данные должны пережить уничтожение страницы:

```javascript
let importantApplicationState = {};
```

— этого недостаточно.

Нужно использовать:

```text
chrome.storage
```

или другое подходящее persistent storage.

---

# UI state vs application state

Очень полезно разделять:

### UI state

```text
selected tab
open section
input value
scroll position
expanded panel
```

Можно хранить в памяти.

### Application state

```text
user settings
saved documents
preferences
persistent tasks
configuration
```

Должен иметь устойчивое хранилище.

# Side Panel и вкладки

Одна из главных особенностей Side Panel — возможность строить UI вокруг текущей вкладки.

Например:

```text
┌──────────────────────────────┬──────────────┐
│                              │              │
│       Wikipedia page         │   Summary    │
│                              │              │
│                              │   Keywords   │
│                              │              │
│                              │   Actions    │
└──────────────────────────────┴──────────────┘
```

Пользователь читает страницу слева и одновременно работает с extension справа.

Это совершенно другой UX, чем Popup.

# 20.4. Side Panel API

Основной API:

```text
chrome.sidePanel
```

Он позволяет управлять Side Panel программно.

Например:

```javascript
await chrome.sidePanel.open({
    windowId: windowId
});
```

В зависимости от сценария можно открывать Side Panel для конкретного окна или вкладки.

---

# Управление поведением Side Panel

Service Worker может настроить Side Panel.

Например:

```javascript
chrome.sidePanel.setOptions({
    path: "sidepanel/sidepanel.html"
});
```

Это позволяет динамически задавать параметры панели.

---

# Side Panel API как configuration layer

Условно:

```text
Service Worker
       │
       ▼
chrome.sidePanel
       │
       ▼
Browser Side Panel
```

Service Worker выступает orchestrator.

# Открытие Side Panel из Action

Можно построить архитектуру:

```text
User
 │
 ▼
Extension Action
 │
 ▼
Service Worker
 │
 ▼
chrome.sidePanel.open()
 │
 ▼
Side Panel
```

Например:

```javascript
chrome.action.onClicked.addListener(
    async (tab) => {

        await chrome.sidePanel.open({
            windowId: tab.windowId
        });

    }
);
```

Такой подход превращает Action не в источник Popup, а в кнопку запуска основного UI.

# Action как launcher

Это интересная архитектура:

```text

       │
       ▼

       │
       ▼

       ▼
Main application
```

Вместо:

```text

   ↓

```

# 20.5. Связь Side Panel с active tab

Это один из главных сценариев использования.

Пользователь находится на:

```text
Tab A
```

Side Panel должна показывать информацию о:

```text
Tab A
```

Пользователь переключается:

```text
Tab A → Tab B
```

и Side Panel должна обновиться:

```text
Page A
   ↓
Panel A

Page B
   ↓
Panel B
```

---

# Получение active tab

Side Panel может использовать:

```javascript
const [tab] =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });
```

Например:

```javascript
const [tab] =
    await chrome.tabs.query({
        active: true,
        currentWindow: true
    });

console.log(tab.id);
console.log(tab.url);
```

Для доступа к определённым tab properties могут потребоваться соответствующие permissions.

---

# Реакция на смену вкладки

Можно отслеживать:

```javascript
chrome.tabs.onActivated.addListener(
    async (activeInfo) => {

        console.log(
            "Active tab:",
            activeInfo.tabId
        );

    }
);
```

Обычно такой listener находится в Service Worker.

Архитектура:

```text
Browser
   │
   │ tab activated
   ▼
Service Worker
   │
   ▼
Message
   │
   ▼
Side Panel
   │
   ▼
Update UI
```

---

# Почему Service Worker должен участвовать

Можно было бы пытаться реализовать всю tab coordination непосредственно в Side Panel.

Но Service Worker естественным образом подходит для browser-level events:

```text
tabs
windows
commands
alarms
action
runtime
```

Поэтому:

```text
Browser events
      ↓
Service Worker
      ↓
Side Panel
```

обычно является хорошей архитектурой.

---

# Пример

Service Worker:

```javascript
chrome.tabs.onActivated.addListener(
    async ({ tabId }) => {

        const tab =
            await chrome.tabs.get(tabId);

        chrome.runtime.sendMessage({
            type: "ACTIVE_TAB_CHANGED",
            tabId: tab.id,
            url: tab.url
        });
    }
);
```

Side Panel:

```javascript
chrome.runtime.onMessage.addListener(
    (message) => {

        if (
            message.type ===
            "ACTIVE_TAB_CHANGED"
        ) {
            updateTab(message);
        }
    }
);
```

---

# Но есть важная проблема

Side Panel может быть закрыта.

Поэтому Service Worker не должен предполагать:

```text
message → guaranteed receiver
```

Communication architecture должна учитывать lifecycle contexts.

Для текущего состояния Side Panel при открытии лучше сделать:

```text
Side Panel opens
     ↓
query current state
     ↓
render
```

а не рассчитывать на событие, которое произошло до её запуска.

---

# Snapshot + events

Очень полезный паттерн:

```text
                Application State
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
     initial snapshot             events
          │                         │
          ▼                         ▼
      Side Panel  <──────────── Service Worker
```

При запуске:

```text
GET_CURRENT_STATE
```

После этого:

```text
STATE_CHANGED
STATE_CHANGED
STATE_CHANGED
```

Это значительно устойчивее.

# 20.6. Side Panel + Content Script

Теперь добавим Content Script.

Получаем:

```text
┌───────────────┐
│  Web Page     │
└───────┬───────┘
        │
        ▼
Content Script
        │
        ▼
Service Worker
        │
        ▼
Side Panel
```

Например, extension анализирует DOM текущей страницы.

---

# Content Script собирает данные

```javascript
const title =
    document.title;

const headings =
    [...document.querySelectorAll("h1, h2, h3")]
        .map(element => element.textContent);
```

Затем:

```javascript
chrome.runtime.sendMessage({
    type: "PAGE_DATA",
    data: {
        title,
        headings
    }
});
```

---

# Service Worker маршрутизирует

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender) => {

        if (message.type !== "PAGE_DATA") {
            return;
        }

        // update application state
    }
);
```

Затем Side Panel получает данные.

---

# Side Panel показывает результат

```javascript
chrome.runtime.onMessage.addListener(
    (message) => {

        if (message.type === "PAGE_DATA") {

            renderPageData(
                message.data
            );
        }
    }
);
```

Получаем pipeline:

```text
DOM
 ↓
Content Script
 ↓
Message
 ↓
Service Worker
 ↓
Message
 ↓
Side Panel
 ↓
UI
```

---

# Почему не обращаться Content Script → Side Panel напрямую?

Технически коммуникационные возможности contexts различаются, но архитектурно лучше не превращать Side Panel в обязательную точку связи.

Например:

```text
Content Script
       │
       ├──────→ Side Panel
       │
       └──────→ Popup
```

создаёт сильную связанность.

Лучше:

```text
Content Script
       │
       ▼
Service Worker
       │
       ▼
Application state
       │
       ▼
UI
```

Тогда Side Panel является одним из consumers состояния.

---

# Side Panel как subscriber

Это очень мощная модель:

```text
                 Application State
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
        Side Panel     Popup      Other UI
```

UI не является владельцем данных.

---

# 20.7. Side Panel + Service Worker

Service Worker является естественным backend для Side Panel.

```text
┌─────────────────┐
│   Side Panel    │
│                 │
│      UI         │
└────────┬────────┘
         │
         │ messages
         ▼
┌─────────────────┐
│ Service Worker  │
│                 │
│ orchestration   │
└─────────────────┘
```

---

# Request/response

Side Panel может запросить данные:

```javascript
const response =
    await chrome.runtime.sendMessage({
        type: "GET_CURRENT_PAGE"
    });
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    async (message, sender) => {

        if (
            message.type ===
            "GET_CURRENT_PAGE"
        ) {

            const [tab] =
                await chrome.tabs.query({
                    active: true,
                    currentWindow: true
                });

            return {
                tabId: tab?.id,
                url: tab?.url
            };
        }
    }
);
```

В production-коде важно придерживаться актуального async message contract и корректно обрабатывать ошибки/отсутствие receiver.

# Side Panel как frontend

Очень полезно концептуально рассматривать Side Panel как frontend:

```text
                 Extension Application
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
          Frontend              Runtime
              │                     │
              ▼                     ▼
        Side Panel            Service Worker
                                    │
                          ┌─────────┼─────────┐
                          ▼         ▼         ▼
                        Tabs     Storage    Network
```

Это уже очень похоже на классическую application architecture.

---

# Side Panel + Storage

Side Panel может напрямую работать с:

```javascript
chrome.storage
```

Например:

```javascript
const settings =
    await chrome.storage.sync.get({
        theme: "system"
    });
```

Но для сложного приложения лучше использовать единый Settings/Application State layer.

---

# Side Panel + Network

Side Panel может выполнять network requests в рамках доступных extension/network policies.

Но не следует превращать её в единственный network layer.

Лучше:

```text
Side Panel
    │
    ▼
Service Worker
    │
    ▼
Network Layer
```

если запросы являются частью application business logic.

---

# Почему Service Worker лучше как orchestrator

Side Panel может исчезнуть.

Service Worker также может быть suspended.

Поэтому долгоживущие задачи не должны зависеть от UI.

Например:

```text
Side Panel
   │
   │ start analysis
   ▼
Service Worker
   │
   ▼
Task
   │
   ▼
Storage
```

Если пользователь закрыл Panel:

```text
Side Panel
   ↓
closed
```

результат всё равно может быть сохранён.

Когда Panel откроется снова:

```text
Side Panel
   ↓
load state
   ↓
show result
```

---

# UI не должен владеть бизнес-процессом

Плохая архитектура:

```text
Side Panel
    │
    ├── network
    ├── scanner
    ├── storage
    ├── state
    ├── scheduling
    └── business logic
```

Лучше:

```text
Side Panel
    │
    ▼
Application API
    │
    ▼
Service Worker
    │
    ├── network
    ├── storage
    ├── scheduling
    └── business logic
```

# Side Panel и navigation

Обычное веб-приложение часто требует:


# Production architecture

Для серьёзного extension можно построить следующую модель:

```text
                           Browser
                              │
                 ┌────────────┴────────────┐
                 │                         │
              Web Page                 Side Panel

                 ▼                         │
           Content Script                  │
                 │                         │
                 └──────────┬──────────────┘

                            │
```

# Typed protocol

Для большого extension сообщения стоит стандартизировать:

```javascript
{
    type: "GET_ACTIVE_TAB"
}
```

Ответ:

```javascript
{
    ok: true,
    data: {
        tabId: 123,
```

Ошибка:

Side Panel тогда становится обычным client приложения.

# Заключение

Side Panel существенно расширяет модель браузерного extension.

Popup заставляет пользователя постоянно переключаться:

```text
Page
 ↓
Popup
 ↓
Page
 ↓
Popup
 ↓
Page
```

Side Panel позволяет построить:

```text
┌───────────────────────────────┬──────────────┐
│                               │              │
│         Web Platform          │  Extension   │
│                               │    App       │
│                               │              │
│                               │              │
└───────────────────────────────┴──────────────┘
```

И это уже не просто маленькое дополнение к браузеру.

Side Panel позволяет превратить extension в **полноценное browser-native application**, которое работает рядом с основной страницей.

Архитектурно наиболее сильная модель выглядит так:

```text
                         Browser
                            │
            ┌───────────────┴───────────────┐
            │                               │
            ▼                               ▼
        Web Page                        Side Panel
            │                               │
            ▼                               │
      Content Script                        │
            │                               │
            └──────────────┬────────────────┘
                           ▼
                    Service Worker
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Storage       Network          Tabs
```

При этом:

**Side Panel — presentation layer.**

**Content Script — page integration layer.**

**Service Worker — orchestration layer.**

**Storage — persistent state layer.**

Такое разделение особенно важно для больших Manifest V3 extensions, потому что оно не позволяет UI, browser events, page integration и application state превратиться в один связанный кусок кода.

Следующая логичная тема — **Commands**: клавиатурные shortcuts и другие способы запуска extension без непосредственного клика по Action.
