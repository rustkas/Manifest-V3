# Часть XIII. Extension Architecture

# Глава 34. Архитектурные паттерны

Manifest V3 заставляет разработчика мыслить о браузерном расширении не как об одной веб-странице, а как о **распределённой системе из нескольких execution contexts**.

Внутри одного extension могут одновременно существовать:

```text
┌──────────────────────────────────────────┐
│                Extension                 │
│                                          │
│  Popup        Options       Side Panel   │
│     │            │               │       │
│     └────────────┼───────────────┘       │
│                  │                       │
│             Service Worker               │
│                  │                       │
│          ┌───────┴────────┐              │
│          │                │              │
│    Content Script    Content Script      │
│          │                │              │
│       Web Page        Web Page            │
└──────────────────────────────────────────┘
```

Каждый context имеет:

* собственный lifecycle;
* собственный JavaScript environment;
* собственные ограничения;
* собственный набор доступных APIs;
* собственную роль в архитектуре.

Поэтому вопрос:

> «Где должен находиться код?»

становится одним из главных архитектурных вопросов Manifest V3.

Неправильный ответ приводит к расширению, которое сложно поддерживать, отлаживать и масштабировать.

Правильный ответ обычно начинается с определения **центра приложения**.

Им может быть:

```text
Popup
Service Worker
Content Script
Side Panel
```

или вообще не один context, а комбинация нескольких.

---

# 34.1. Popup-centric architecture

В Popup-centric architecture главным пользовательским интерфейсом является Popup.

Схема:

```text
                  User
                   │
                   ▼
                Popup
                   │
                   ▼
            Service Worker
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       Storage    Tabs    Network
```

Popup становится точкой входа пользователя в приложение.

---

## Типичный сценарий

Пользователь нажимает:

```text
Extension icon
      ↓
Popup
```

Popup показывает:

```text
┌──────────────────────┐
│ My Extension         │
├──────────────────────┤
│ Current page         │
│                      │
│ Status: Ready        │
│                      │
│ [ Analyze ]          │
│ [ Settings ]         │
└──────────────────────┘
```

После нажатия кнопки:

```text
Popup
  │
  │ sendMessage()
  ▼
Service Worker
  │
  ├── storage
  ├── tabs
  └── network
```

---

# Преимущества

Popup-centric architecture очень проста для небольших расширений.

Преимущества:

* легко понять;
* мало компонентов;
* быстрый старт разработки;
* естественная модель для toolbar extensions;
* удобно для небольших действий;
* легко реализовать MVP.

Например:

```text
Password helper
Color picker
Page translator
Clipboard utility
Simple page analyzer
Tab utility
```

могут прекрасно работать с Popup.

---

# Главный недостаток Popup

Popup имеет очень короткий lifecycle.

Пользователь:

```text
click icon
   ↓
Popup opens
   ↓
user interacts
   ↓
Popup closes
```

После закрытия Popup его JavaScript runtime прекращает существовать.

Следовательно:

> **Popup не должен быть источником истины для состояния extension.**

Плохая архитектура:

```text
Popup
 │
 ├── state
 ├── business logic
 ├── network
 ├── timers
 └── application state
```

Лучше:

```text
Popup
   │
   │ commands
   ▼
Service Worker
   │
   ▼
Persistent state
```

---

# Popup-centric подходит, если

```text
Application complexity
        │
        ▼
      low
        │
        ▼
User interaction
        │
        ▼
    short-lived
```

Если же приложение должно:

* постоянно работать;
* отслеживать вкладки;
* реагировать на события;
* показывать постоянно доступный UI;
* взаимодействовать с несколькими страницами;

Popup-centric модель быстро начинает создавать проблемы.

---

# 34.2. Background-centric architecture

В Background-centric architecture центром extension является Service Worker.

```text
                    Events
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
      Tabs          Commands       Alarms
       │              │              │
       └──────────────┼──────────────┘
                      ▼
               Service Worker
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Storage      Network      UI
          │                         │
          └──────────┬──────────────┘
                     ▼
                   Popup
```

Здесь Service Worker является **orchestrator**.

---

# Основная идея

Service Worker принимает события:

```javascript
chrome.tabs.onUpdated
chrome.commands.onCommand
chrome.runtime.onMessage
chrome.alarms.onAlarm
```

и принимает решения.

Например:

```text
Tab updated
     ↓
Service Worker
     ↓
Check URL
     ↓
Update state
     ↓
Notify UI
```

---

# Почему эта архитектура хорошо соответствует MV3

Manifest V3 использует event-driven Service Worker.

Следовательно:

```text
Event
  ↓
Worker starts
  ↓
Handle event
  ↓
Worker may become inactive
```

Архитектура естественным образом становится:

> **event → decision → action**

а не:

> **permanent process → infinite loop**

---

# Преимущества

Background-centric architecture хорошо подходит для:

* tab managers;
* automation tools;
* productivity extensions;
* background synchronization;
* notification extensions;
* command-driven extensions;
* browser automation;
* cross-tab coordination.

---

# Недостаток

Service Worker не должен рассматриваться как постоянно работающий backend process.

Нельзя полагаться на:

```javascript
let state = {};
```

как на долговременное хранилище.

Вместо этого:

```text
Service Worker
      │
      ▼
chrome.storage
```

---

# Service Worker как application core

В более зрелой архитектуре:

```text
UI
 │
 ▼
Service Worker
 │
 ├── application logic
 ├── state management
 ├── storage
 ├── network
 └── orchestration
```

Но даже здесь желательно отделять **business logic** от самого Chrome event API.

Например:

```text
Chrome Events
      │
      ▼
Event Adapter
      │
      ▼
Application Core
      │
      ├── State
      ├── Commands
      └── Services
```

Это делает код тестируемым.

---

# 34.3. Content-centric architecture

Content-centric architecture используется тогда, когда главным объектом приложения является **сама веб-страница**.

```text
                 Web Page
                    │
                    ▼
              Content Script
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
         DOM      Events    Page Bridge
                    │
                    ▼
              Service Worker
```

В этом случае extension существует прежде всего для того, чтобы:

> анализировать, изменять или дополнять содержимое страниц.

---

# Примеры

Такая архитектура естественна для:

* page analyzers;
* accessibility tools;
* translation extensions;
* SEO tools;
* content extractors;
* form assistants;
* shopping assistants;
* page annotation;
* DOM automation.

---

# Основной runtime

В Content-centric extension основная работа происходит в:

```text
Content Script
```

Например:

```javascript
const observer =
    new MutationObserver(
        mutations => {
            analyzePage();
        }
    );

observer.observe(
    document.body,
    {
        childList: true,
        subtree: true
    }
);
```

Content Script постоянно взаимодействует с DOM.

---

# Service Worker становится coordinator

Например:

```text
Content Script
      │
      │ page data
      ▼
Service Worker
      │
      ├── storage
      ├── API
      └── processing
```

Таким образом:

```text
Content Script = page runtime
Service Worker = privileged runtime
```

---

# Главная проблема Content-centric architecture

Content Script живёт вместе со страницей.

Если пользователь:

```text
navigate
reload
close tab
change frame
```

Content Script может исчезнуть и появиться заново.

Поэтому:

```text
Content Script global state
```

нельзя считать постоянным.

---

# Правильная модель

```text
DOM state
     ↓
Content Script
     ↓
Extension state
     ↓
Service Worker / Storage
```

Если состояние важно после navigation:

```text
chrome.storage
```

должен быть источником истины.

---

# 34.4. Side Panel architecture

Side Panel существенно меняет модель UI.

Вместо:

```text
click icon
   ↓
Popup
   ↓
close
```

появляется:

```text
Browser
 │
 ├── Web Page
 │
 └── Side Panel
        │
        ▼
    Application UI
```

Side Panel может оставаться доступным во время работы пользователя.

---

# Side Panel как application shell

Для сложного extension Side Panel может стать практически полноценным application shell:

```text
┌──────────────────────────────────────────┐
│ Browser                                  │
├──────────────────────────────┬───────────┤
│                              │           │
│         Web Page             │   Side    │
│                              │   Panel   │
│                              │           │
│                              │ Dashboard │
│                              │ Controls  │
│                              │ State     │
│                              │           │
└──────────────────────────────┴───────────┘
```

---

# Side Panel + Content Script

Это особенно мощная комбинация.

```text
Active Tab
    │
    ▼
Content Script
    │
    │ page data
    ▼
Service Worker
    │
    │ state
    ▼
Side Panel
```

Side Panel показывает данные текущей страницы.

Например:

```text
Page
 ↓
Extract article
 ↓
Content Script
 ↓
Service Worker
 ↓
Side Panel
 ↓
Summary
```

---

# Почему Side Panel лучше Popup для сложного UI

Popup:

```text
short-lived
small
temporary
```

Side Panel:

```text
persistent UI
larger workspace
continuous interaction
```

Поэтому Side Panel особенно хорошо подходит для:

* AI assistants;
* research tools;
* writing assistants;
* productivity dashboards;
* page analyzers;
* shopping assistants;
* developer tools;
* knowledge tools.

---

# Side Panel как frontend

В такой архитектуре:

```text
Side Panel
     │
     │ commands
     ▼
Service Worker
     │
     ▼
Application Core
```

Side Panel фактически становится:

```text
Extension frontend
```

а Service Worker:

```text
Extension application backend
```

При этом оба находятся внутри одного extension.

---

# 34.5. Event-driven architecture

Event-driven architecture является одной из фундаментальных моделей Manifest V3.

Вместо:

```text
while (true) {
    checkSomething();
}
```

используется:

```text
Event
  ↓
Handler
  ↓
Action
```

---

# Пример

```javascript
chrome.tabs.onUpdated.addListener(
    (tabId, changeInfo, tab) => {
        if (
            changeInfo.status ===
            "complete"
        ) {
            handleTabReady(tab);
        }
    }
);
```

Архитектурно:

```text
Browser Event
      │
      ▼
Service Worker
      │
      ▼
Handler
      │
      ▼
Application Logic
```

---

# События как входы системы

Можно представить extension как state machine:

```text
                 ┌──────────────┐
                 │    State     │
                 └──────┬───────┘
                        ▲
                        │
                 Application
                        │
        ┌───────────────┼───────────────┐
        │               │               │
        ▼               ▼               ▼
      Tab event      Command         Message
```

Каждое событие вызывает переход состояния.

---

# Event-driven вместо polling

Плохая модель:

```javascript
setInterval(
    checkTabs,
    1000
);
```

Лучше:

```javascript
chrome.tabs.onUpdated
```

если именно navigation является причиной изменения.

Это:

* экономит ресурсы;
* соответствует модели браузера;
* уменьшает background activity;
* упрощает lifecycle;
* делает поведение предсказуемее.

---

# Event-driven architecture и alarms

Для периодических задач используется:

```javascript
chrome.alarms
```

Например:

```text
Alarm
 ↓
Service Worker
 ↓
Synchronize data
 ↓
Storage
```

а не бесконечный timer.

---

# Event-driven state

Событие может быть представлено как:

```text
EVENT
 ↓
REDUCE
 ↓
STATE
 ↓
UI UPDATE
```

Например:

```text
TAB_ACTIVATED
     ↓
currentTab = 123
     ↓
state updated
     ↓
Side Panel updated
```

Это уже приближается к классической reactive architecture.

---

# 34.6. Multi-context architecture

Наиболее естественная модель сложного Manifest V3 extension:

```text
                    Extension
                        │
       ┌────────────────┼────────────────┐
       │                │                │
       ▼                ▼                ▼
     Popup         Side Panel        Options
       │                │                │
       └────────────────┼────────────────┘
                        │
                        ▼
                 Service Worker
                        │
             ┌──────────┼──────────┐
             ▼          ▼          ▼
        Content 1   Content 2   Content 3
             │          │          │
             ▼          ▼          ▼
          Page 1     Page 2     Page 3
```

Здесь extension является не одной программой, а **distributed runtime**.

---

# Почему Multi-context архитектура сложнее

Каждый context имеет собственный lifecycle.

Например:

```text
Popup
  ↓
open
  ↓
close
```

Content Script:

```text
page load
  ↓
active
  ↓
navigation
  ↓
destroy
```

Service Worker:

```text
start
  ↓
event
  ↓
idle
  ↓
suspend
  ↓
restart
```

Side Panel:

```text
open
  ↓
active
  ↓
close
```

Поэтому архитектура должна учитывать:

> любой context может исчезнуть.

---

# Нельзя полагаться на direct references

Например, нельзя проектировать систему так:

```text
Popup
 │
 └── reference → Content Script object
```

Таких постоянных JavaScript references между contexts нет.

Используется communication:

```text
sendMessage()
Port
storage
events
```

---

# Message-oriented architecture

Хорошая Multi-context система строится вокруг сообщений:

```text
Context A
   │
   │ Message
   ▼
Service Worker
   │
   │ Message
   ▼
Context B
```

Service Worker становится маршрутизатором.

---

# State ownership

Ключевой вопрос:

> Где находится source of truth?

Например:

```text
Service Worker
       │
       ▼
Storage
       │
       ├── Popup
       ├── Side Panel
       ├── Options
       └── Content Scripts
```

Такой подход значительно надёжнее, чем:

```text
Popup state
Side Panel state
Content state
Options state
```

которые могут расходиться.

---

# Event propagation

Можно использовать:

```text
Storage
  ↓
chrome.storage.onChanged
  ↓
contexts
```

Например:

```text
State changed
     ↓
storage.local
     ↓
storage.onChanged
     ↓
Side Panel
     ↓
UI update
```

Это создаёт естественную synchronization architecture.

---

# 34.7. Hybrid architecture

На практике наиболее мощные расширения используют **Hybrid architecture**.

Здесь нет одного «главного» context.

Вместо этого каждый context выполняет оптимальную для него роль.

Например:

```text
                         User
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Popup        Side Panel      Commands
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                    Service Worker
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Storage        Network         Tabs
                           │
                           ▼
                    Content Scripts
                           │
                           ▼
                        Web Page
```

---

# Типичная Hybrid architecture

Очень практичная модель:

```text
┌─────────────────────────────────────┐
│ UI                                  │
│                                     │
│ Popup ──────┐                       │
│             │                       │
│ Side Panel ─┼──→ Service Worker     │
│             │          │            │
│ Options ────┘          │            │
└────────────────────────┼────────────┘
                         │
                         ▼
                  Application Core
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Storage          Tabs         Network
                         │
                         ▼
                  Content Scripts
                         │
                         ▼
                       DOM
```

---

# Разделение ответственности

Один из наиболее полезных принципов:

| Context        | Основная ответственность |
| -------------- | ------------------------ |
| Popup          | кратковременный UI       |
| Side Panel     | постоянный UI            |
| Options        | конфигурация             |
| Content Script | работа со страницей      |
| MAIN world     | page-level integration   |
| Service Worker | orchestration            |
| Storage        | persistent state         |

Такой подход значительно уменьшает связанность.

---

# Application Core

Для сложного extension полезно вынести бизнес-логику в отдельный слой:

```text
                Chrome APIs
                    │
                    ▼
              Context Adapters
                    │
                    ▼
              Application Core
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        State     Services   Rules
```

Например:

```text
src/
├── core/
│   ├── state/
│   ├── services/
│   ├── commands/
│   └── protocols/
│
├── background/
│   └── service-worker.js
│
├── content/
│   └── content-script.js
│
├── popup/
│   └── popup.js
│
├── sidepanel/
│   └── sidepanel.js
│
└── options/
    └── options.js
```

Это уже значительно ближе к production architecture.

---

# Context adapters

Вместо того чтобы помещать Chrome API непосредственно в business logic:

```javascript
chrome.tabs.query(...)
```

во всех файлах application code, можно создать adapter:

```javascript
class TabService {

    async getActiveTab() {
        return chrome.tabs.query({
            active: true,
            currentWindow: true
        });
    }

}
```

Тогда:

```text
Chrome API
    ↓
Adapter
    ↓
Application Core
```

Это делает архитектуру более тестируемой.

---

# Command architecture

Ещё один сильный паттерн — использовать commands.

Например:

```text
ANALYZE_PAGE
SAVE_RESULT
OPEN_PANEL
CLEAR_STATE
SYNC_DATA
```

Каждый context генерирует commands:

```text
Popup
  │
  └── ANALYZE_PAGE
           │
           ▼
     Service Worker
           │
           ▼
     Content Script
```

---

# Events vs Commands

Важно различать:

### Command

```text
"Сделай X"
```

Например:

```text
ANALYZE_PAGE
```

### Event

```text
"X произошло"
```

Например:

```text
PAGE_ANALYZED
```

Архитектура может выглядеть:

```text
Command
   ↓
Handler
   ↓
State change
   ↓
Event
   ↓
UI
```

---

# Declarative + Event-driven Hybrid

Manifest V3 позволяет использовать ещё более интересную архитектуру:

```text
Declarative Browser Engine
          │
          │ events
          ▼
    Service Worker
          │
          ▼
 Application Core
```

Например:

```text
Declarative Net Request
          │
          ▼
 Browser Engine
          │
          ▼
     Extension
```

Часть логики выполняется непосредственно браузером, а не JavaScript extension runtime.

Это соответствует принципу:

> **Compile more, execute less.**

---

# Выбор архитектуры

Можно использовать следующую эвристику.

### Небольшой utility

```text
Popup-centric
```

Например:

```text
JSON formatter
Color picker
Clipboard tool
Simple converter
```

---

### Фоновая автоматизация

```text
Background-centric
```

Например:

```text
Tab monitor
Scheduler
Notification system
Synchronization
```

---

### Работа с содержимым страниц

```text
Content-centric
```

Например:

```text
Extractor
SEO analyzer
Accessibility helper
DOM automation
```

---

### Постоянный рабочий интерфейс

```text
Side Panel
```

Например:

```text
AI assistant
Research assistant
Writing assistant
Productivity workspace
```

---

### Сложное коммерческое extension

```text
Hybrid / Multi-context
```

Например:

```text
Side Panel
    +
Content Script
    +
Service Worker
    +
Storage
    +
Network
```

# Сравнение архитектур

| Architecture       | Центр              | Сильная сторона       | Основная проблема         |
| ------------------ | ------------------ | --------------------- | ------------------------- |
| Popup-centric      | Popup              | Простота              | Lifecycle                 |
| Background-centric | Service Worker     | Orchestration         | Ephemeral runtime         |
| Content-centric    | Content Script     | Работа со страницей   | Navigation/lifecycle      |
| Side Panel         | Side Panel         | Persistent UI         | Более сложная координация |
| Event-driven       | Events             | MV3-native модель     | Нужно мыслить событиями   |
| Multi-context      | Несколько contexts | Масштабируемость      | Сложность                 |
| Hybrid             | Комбинация         | Максимальная гибкость | Архитектурная стоимость   |

# Как архитектура эволюционирует

Большинство extensions проходят примерно такую эволюцию:

```text
Stage 1
Popup
```

↓

```text
Stage 2
Popup
  ↓
Service Worker
```

↓

```text
Stage 3
Popup
  ↓
Service Worker
  ↓
Content Script
```

↓

```text
Stage 4
Side Panel
  ↓
Service Worker
  ↓
Content Scripts
```

↓

```text
Stage 5
Multi-context
  ↓
Application Core
  ↓
Declarative + Event-driven runtime
```

Это естественная эволюция от простого utility к полноценному extension application.

# Архитектурное правило №1

Не начинайте с вопроса:

> «Какой context мне использовать?»

Начинайте с вопроса:

> **«Где находится бизнес-логика и где находится источник истины?»**

После этого contexts становятся адаптерами.

Например:

```text
                    Application Core
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
      Popup           Content Script       Side Panel
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                           ▼
                    Service Worker
```

---

# Архитектурное правило №2

Не делайте Service Worker «богом приложения».

Плохая модель:

```text
Service Worker
    │
    ├── UI
    ├── DOM
    ├── state
    ├── business logic
    ├── network
    ├── storage
    └── everything
```

Лучше:

```text
Service Worker
     │
     └── orchestration
             │
             ▼
       Application Core
```

---

# Архитектурное правило №3

Не делайте Content Script полноценным backend.

Плохая модель:

```text
Content Script
 ├── DOM
 ├── database
 ├── network
 ├── application state
 ├── business logic
 └── synchronization
```

Лучше:

```text
Content Script
    │
    ├── DOM
    ├── page events
    └── extraction
            │
            ▼
       Extension Core
```

---

# Архитектурное правило №4

UI не должен владеть глобальным состоянием.

Плохая модель:

```text
Popup
 └── source of truth
```

Лучше:

```text
             Storage
                │
                ▼
         Application State
          /      |       \
       Popup   Panel    Options
```

---

# Архитектурное правило №5

Каждый context должен иметь одну основную ответственность.

```text
Popup       → interaction
Side Panel  → workspace
Content     → page
SW          → orchestration
Storage     → persistence
```

Это значительно уменьшает coupling.

# Итоговая production architecture

Для сложного Manifest V3 extension можно использовать следующую модель:

```text
                         ┌─────────────┐
                         │    User     │
                         └──────┬──────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
           Popup           Side Panel         Commands
              │                 │                 │
              └─────────────────┼─────────────────┘
                                │
                         Message Protocol
                                │
                                ▼
                    ┌─────────────────────┐
                    │   Service Worker    │
                    │                     │
                    │ Event Router        │
                    │ Orchestrator        │
                    └──────────┬──────────┘
                               │
                       Application Core
                               │
              ┌────────────────┼────────────────┐
              │                │                │
              ▼                ▼                ▼
           Storage          Network            Tabs
                                                 │
                                                 ▼
                                         Content Scripts
```

# Заключение

Главный архитектурный переход при разработке Manifest V3 заключается в изменении мышления.

В традиционном веб-приложении мы часто думаем:

```text
Application
    ↓
JavaScript runtime
    ↓
DOM
```

В Manifest V3:

```text
                 Extension
                     │
       ┌─────────────┼─────────────┐
       │             │             │
      UI          Background      Page
       │             │             │
       ▼             ▼             ▼
    Popup        Service Worker  Content
       │             │             │
       └─────────────┼─────────────┘
                     │
                Message Protocol
                     │
                     ▼
                 State Layer
```

Поэтому наиболее важными становятся не сами APIs, а **границы между contexts**.

Хорошая архитектура Manifest V3 обычно обладает следующими свойствами:

1. **UI не владеет persistent state.**
2. **Content Script не является application backend.**
3. **Service Worker не хранит критическое состояние в globals.**
4. **Communication осуществляется через явный protocol.**
5. **Storage является источником persistent state.**
6. **Page JavaScript рассматривается как untrusted environment.**
7. **Declarative APIs используются там, где браузер может выполнить работу вместо JavaScript.**
8. **Каждый context имеет одну основную ответственность.**
9. **Business logic отделена от browser-specific adapters.**
10. **Архитектура строится вокруг событий, сообщений и состояния, а не вокруг постоянно работающего процесса.**

Именно это позволяет перейти от простого:

```text
"browser extension"
```

к:

```text
"полноценному application runtime внутри браузера".
```

И это особенно важно для больших Manifest V3 проектов: **не существует одного «правильного» context. Правильная архитектура распределяет работу между contexts в соответствии с их lifecycle, security model и capabilities.**
