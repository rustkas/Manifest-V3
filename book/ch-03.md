# Глава 3. Первое расширение

В предыдущей главе мы рассмотрели `manifest.json` и увидели, что Manifest V3 описывает архитектуру браузерного расширения.

Теперь создадим первое расширение практически.

Наша задача — пройти весь базовый цикл разработки:

```text
Создать проект
     ↓
Создать manifest.json
     ↓
Добавить UI
     ↓
Загрузить extension в браузер
     ↓
Запустить
     ↓
Inspect
     ↓
Изменить код
     ↓
Reload
     ↓
Проверить результат
```

После этой главы у нас будет не просто набор файлов, а рабочее Manifest V3 extension, которое можно использовать как основу для дальнейшего обучения.

---

# 3.1. Создание структуры проекта

Начнём с максимально простой структуры.

Создадим каталог:

```text
first-extension/
```

Внутри него пока будет только один файл:

```text
first-extension/
└── manifest.json
```

Это важный момент.

**Browser extension не требует специального проекта, package manager или framework.**

На самом базовом уровне расширение — это каталог с `manifest.json` и ресурсами, которые этот manifest описывает.

Мы можем создать его вручную.

Например, в Windows:

```text
C:\projects\first-extension\
```

Или в Linux/macOS:

```text
~/projects/first-extension/
```

В VS Code можно открыть этот каталог:

```text
File → Open Folder
```

и создать внутри него:

```text
manifest.json
```

---

## Почему мы начинаем без npm?

Современная frontend-разработка часто начинается примерно так:

```text
npm create ...
npm install ...
package.json
node_modules/
src/
build/
```

Но Manifest V3 этого не требует.

Браузер способен загрузить extension непосредственно из исходного каталога.

Это очень полезно для обучения, потому что между нашим кодом и браузером практически нет промежуточного слоя:

```text
manifest.json
     ↓
Browser
```

Позже мы можем добавить:

```text
TypeScript
Webpack
Vite
Rollup
esbuild
Rust
WebAssembly
```

и другие инструменты.

Но сначала полезно понять **саму платформу без framework/toolchain abstraction**.

---

# 3.2. Минимальный `manifest.json`

Создадим:

```text
first-extension/
└── manifest.json
```

и запишем:

```json
{
  "manifest_version": 3,
  "name": "First Extension",
  "version": "1.0.0"
}
```

Это минимальное Manifest V3 extension.

Разберём каждое поле.

### `manifest_version`

```json
"manifest_version": 3
```

Мы говорим браузеру:

> Используй модель Manifest V3.

### `name`

```json
"name": "First Extension"
```

Имя extension.

### `version`

```json
"version": "1.0.0"
```

Версия нашего extension.

---

## Проверяем extension

Теперь откроем браузер и перейдём на страницу управления расширениями.

В Chromium-браузерах это обычно:

```text
chrome://extensions/
```

Для Microsoft Edge:

```text
edge://extensions/
```

В Firefox используется собственный интерфейс управления дополнениями и режим временной загрузки, который мы отдельно рассмотрим при изучении кросс-браузерной разработки.

Для первого эксперимента удобно использовать Chromium-based browser.

---

# 3.3. Extension Action

Наше расширение пока ничего не делает.

Добавим пользовательскую точку входа.

Изменим manifest:

```json
{
  "manifest_version": 3,
  "name": "First Extension",
  "version": "1.0.0",

  "action": {}
}
```

`action` сообщает браузеру, что extension имеет action.

В результате браузер может предоставить пользователю кнопку расширения в toolbar.

Однако пока action не имеет popup.

Мы можем добавить:

```json
"action": {
  "default_title": "First Extension"
}
```

Теперь полный manifest:

```json
{
  "manifest_version": 3,
  "name": "First Extension",
  "version": "1.0.0",

  "action": {
    "default_title": "First Extension"
  }
}
```

---

## Action — это не Popup

Это важное различие.

Можно представить:

```text
Action
  │
  ├── Toolbar button
  ├── Title
  ├── Badge
  └── Popup
```

`action` — это механизм взаимодействия extension с toolbar.

Popup — только один из возможных UI-компонентов action.

Поэтому:

```json
"action": {}
```

не означает автоматически:

> создать popup.

Это означает:

> у extension есть action.

---

# 3.4. Popup

Теперь создадим настоящий пользовательский интерфейс.

Структура проекта:

```text
first-extension/
│
├── manifest.json
└── popup.html
```

`popup.html`:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">

  <title>First Extension</title>
</head>

<body>
  <h1>Hello!</h1>
  <p>This is my first browser extension.</p>
</body>
</html>
```

Теперь изменим manifest:

```json
{
  "manifest_version": 3,
  "name": "First Extension",
  "version": "1.0.0",

  "action": {
    "default_title": "First Extension",
    "default_popup": "popup.html"
  }
}
```

Главное новое поле:

```json
"default_popup": "popup.html"
```

Оно говорит браузеру:

> Когда пользователь взаимодействует с action, используй `popup.html` как popup UI.

Теперь архитектура выглядит так:

```text
Browser
   │
   ▼
Toolbar
   │
   ▼
Action
   │
   ▼
popup.html
```

---

## Popup — это Extension Page

Это важная архитектурная деталь.

`popup.html` не является HTML веб-сайта.

Он принадлежит extension.

У него есть extension origin и доступ к extension APIs, разрешённым для соответствующего context.

Таким образом:

```text
Web Page
    │
    └── https://example.com

Extension
    │
    └── extension://...
```

Popup находится во второй категории.

---

## Добавляем JavaScript

Создадим:

```text
first-extension/
│
├── manifest.json
├── popup.html
└── popup.js
```

Изменим HTML:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">

  <title>First Extension</title>
</head>

<body>
  <h1>Hello!</h1>

  <button id="hello">
    Click me
  </button>

  <script src="popup.js"></script>
</body>
</html>
```

`popup.js`:

```javascript
const button = document.querySelector("#hello");

button.addEventListener("click", () => {
  alert("Hello from the extension!");
});
```

Теперь наше extension состоит из:

```text
first-extension/
│
├── manifest.json
├── popup.html
└── popup.js
```

Это уже полноценное маленькое приложение.

---

# 3.5. Загрузка extension в браузер

Теперь загрузим его в браузер.

В Chromium откройте:

```text
chrome://extensions/
```

Найдите переключатель:

```text
Developer mode
```

и включите его.

После этого появится кнопка:

```text
Load unpacked
```

Нажмите её.

Затем выберите каталог:

```text
first-extension/
```

Важно выбирать **каталог extension**, а не отдельный `manifest.json`.

Браузер прочитает:

```text
first-extension/manifest.json
```

и проверит структуру extension.

Если всё корректно, расширение появится в списке установленных extensions.

---

## Что значит "unpacked"?

`Load unpacked` означает:

> загрузить extension непосредственно из каталога исходных файлов.

То есть браузер не требует ZIP-пакета.

Мы можем работать непосредственно с:

```text
manifest.json
popup.html
popup.js
```

---

# 3.6. Developer Mode

Developer Mode — режим браузера, предназначенный для разработки и тестирования расширений.

Он позволяет:

* загружать unpacked extensions;
* перезагружать extension;
* открывать инструменты разработчика;
* получать диагностическую информацию;
* работать с локальными версиями extension.

Для обычного пользователя Developer Mode не нужен.

Для разработчика он является основной частью workflow.

---

## Основной цикл разработки

При разработке extension мы постоянно выполняем:

```text
Edit
  ↓
Save
  ↓
Reload
  ↓
Test
  ↓
Inspect
  ↓
Edit
```

Например:

```text
popup.js
    ↓
изменили код
    ↓
Save
    ↓
Reload extension
    ↓
открыли popup
    ↓
проверили результат
```

Это будет повторяться сотни раз.

Поэтому умение быстро работать со страницей extensions становится одним из базовых навыков extension developer.

# 3.7. Extension ID

После загрузки extension браузер присваивает ему идентификатор.

Например:

```text
abcdefghijklmnopabcdefghijklmnop
```

В интерфейсе управления расширениями он отображается как:

```text
ID: abcdefghijklmnopabcdefghijklmnop
```

Этот ID идентифицирует конкретную установку extension в браузере.

---

## Зачем нужен Extension ID?

Он может использоваться в различных сценариях:

* debugging;
* messaging;
* extension URLs;
* взаимодействие между extensions;
* permissions;
* distribution;
* development tooling.

Например, extension может иметь URL:

```text
chrome-extension://abcdefghijklmnopabcdefghijklmnop/...
```

То есть extension получает собственный origin.

---

## Важное различие

Не следует путать:

```text
Extension ID
```

и:

```text
version
```

Например:

```text
Name:
First Extension

Version:
1.0.0

ID:
abcdefghijklmnopabcdefghijklmnop
```

Версия может изменяться:

```text
1.0.0
→
1.1.0
→
2.0.0
```

а идентичность extension должна оставаться связанной с тем же extension identity.

---

# 3.8. Reload extension

Это одна из самых важных операций разработки.

Предположим, мы изменили:

```text
popup.js
```

или:

```text
manifest.json
```

Браузер не обязан автоматически применить изменение к уже загруженному extension.

На странице:

```text
chrome://extensions/
```

найдите наше расширение и нажмите:

```text
Reload
```

После этого браузер заново загрузит extension.

---

## Почему Reload особенно важен для Manifest?

Если мы изменили:

```json
"permissions": [
  "storage"
]
```

или:

```json
"background": {
  "service_worker": "background.js"
}
```

или:

```json
"content_scripts": [...]
```

необходимо перезагрузить extension.

Изменение manifest не является обычным runtime state update.

Manifest читается браузером как часть конфигурации extension.

---

## Типичный workflow

Например, мы меняем:

```json
"default_popup": "popup.html"
```

на:

```json
"default_popup": "settings.html"
```

После сохранения:

```text
Save manifest.json
       ↓
chrome://extensions/
       ↓
Reload
       ↓
Click extension
       ↓
settings.html
```

---

# 3.9. Inspect extension

Когда extension перестаёт работать, первая задача разработчика — не гадать, а открыть DevTools.

У extension есть несколько независимых execution contexts.

Это означает, что и debugging также разделён.

---

## Inspect Popup

Откройте popup.

Затем через меню разработчика выберите Inspect.

Откроется DevTools для popup.

Там можно увидеть:

```text
Console
Elements
Sources
Network
Application
```

и другие панели.

Например:

```javascript
console.log("Popup started");
```

позволяет проверить запуск popup.

---

## Inspect Service Worker

Позже мы добавим:

```json
"background": {
  "service_worker": "background.js"
}
```

В интерфейсе extensions браузер позволит перейти к DevTools Service Worker.

Это будет отдельный execution context.

Очень важно понимать:

```text
Popup DevTools
        ≠
Service Worker DevTools
        ≠
Content Script DevTools
```

Это не три окна одного и того же JavaScript runtime.

Это разные contexts.

---

## Inspect Content Script

Когда extension начинает внедрять:

```javascript
content.js
```

в веб-страницу, debugging становится ещё интереснее.

Мы можем иметь:

```text
Web Page
     │
     ├── Page JavaScript
     │
     └── Content Script
```

и при этом content script работает в отдельном JavaScript environment.

Поэтому при ошибке необходимо сначала определить:

> В каком именно context возникла ошибка?

# 3.10. Первое production-like расширение

До этого момента мы создавали учебный пример.

Теперь сделаем небольшой проект, который уже имеет структуру, похожую на настоящее extension.

Назовём его:

```text
Page Info
```

Его задача:

> При открытии popup показывать информацию о текущей странице.

Например:

```text
┌───────────────────────────┐
│ Page Info                 │
│                           │
│ Title: Example            │
│ URL: https://example.com  │
│                           │
│ [Get Page Info]           │
└───────────────────────────┘
```

Для этого нам понадобятся:

```text
manifest.json
popup.html
popup.js
```

---

## Структура

```text
page-info/
│
├── manifest.json
│
├── popup.html
│
└── popup.js
```

---

## Manifest

```json
{
  "manifest_version": 3,

  "name": "Page Info",
  "version": "1.0.0",

  "description": "Displays information about the current page.",

  "action": {
    "default_title": "Page Info",
    "default_popup": "popup.html"
  },

  "permissions": [
    "activeTab"
  ]
}
```

Здесь появилось новое permission:

```text
activeTab
```

Оно позволяет extension получить временный доступ к активной вкладке в соответствующем пользовательском сценарии.

Это хороший пример принципа минимальных разрешений.

Мы не запрашиваем:

```text
<all_urls>
```

только для того, чтобы получить информацию о текущей странице.

---

## Popup HTML

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">

  <meta
    name="viewport"
    content="width=device-width, initial-scale=1"
  >

  <title>Page Info</title>

  <style>
    body {
      width: 320px;
      padding: 16px;
      font-family: system-ui, sans-serif;
    }

    h1 {
      font-size: 18px;
      margin-top: 0;
    }

    .label {
      font-weight: 600;
    }

    .value {
      word-break: break-word;
    }
  </style>
</head>

<body>

  <h1>Page Info</h1>

  <p>
    <span class="label">Title:</span>
    <span id="title" class="value">Loading...</span>
  </p>

  <p>
    <span class="label">URL:</span>
    <span id="url" class="value">Loading...</span>
  </p>

  <script src="popup.js"></script>

</body>
</html>
```

---

## Popup JavaScript

```javascript
const titleElement = document.querySelector("#title");
const urlElement = document.querySelector("#url");

chrome.tabs.query(
  {
    active: true,
    currentWindow: true
  },
  (tabs) => {
    const tab = tabs[0];

    if (!tab) {
      titleElement.textContent = "Unknown";
      urlElement.textContent = "Unknown";
      return;
    }

    titleElement.textContent = tab.title ?? "Unknown";
    urlElement.textContent = tab.url ?? "Unknown";
  }
);
```

Теперь extension использует API браузера:

```text
chrome.tabs
```

Это первый важный переход от обычного Web Application к Extension Application.

Обычная веб-страница не может просто выполнить:

```javascript
chrome.tabs.query(...)
```

и получить произвольную информацию о вкладках браузера.

Extension получает такие возможности через extension platform и соответствующие permissions.

# Что мы только что построили?

На первый взгляд это очень маленькое приложение:

```text
Popup
  ↓
chrome.tabs
  ↓
Current Tab
```

Но архитектурно произошло нечто важное.

Мы создали приложение, которое находится **внутри браузера и взаимодействует с самим браузером**.

Это фундаментальное отличие:

```text
Web Application

HTML
 ↓
JavaScript
 ↓
Web Platform
```

против:

```text
Browser Extension

HTML
 ↓
JavaScript
 ↓
Web Platform
 ↓
Extension APIs
 ↓
Browser
```

И именно последний слой открывает совершенно другой класс возможностей.

# Архитектурный вывод

После создания первого extension важно не останавливаться на уровне:

> "Я научился делать popup."

Гораздо важнее понять архитектурную модель.

Наше первое extension пока выглядит так:

```text
                 Browser
                    │
                    ▼
                  Action
                    │
                    ▼
                  Popup
                    │
                    ▼
                chrome.tabs
                    │
                    ▼
               Current Tab
```

Но Manifest V3 позволяет построить гораздо более сложную систему:

```text
                         Browser
                            │
                     ┌──────┴──────┐
                     │             │
                   Action       Commands
                     │             │
                     ▼             ▼
                   Popup       Service Worker
                     │             │
                     └──────┬──────┘
                            │
                       Messaging
                            │
                            ▼
                     Content Script
                            │
                            ▼
                         Web Page
                            │
                     ┌──────┴──────┐
                     │             │
                 Side Panel      Options
                     │             │
                     └──────┬──────┘
                            │
                         Storage
```

# Контрольные вопросы

После этой главы вы должны уметь ответить на следующие вопросы:

1. Что такое unpacked extension?
2. Для чего нужен `manifest.json`?
3. Какие три поля являются базовыми для минимального Manifest V3?
4. Что такое `action`?
5. Чем `action` отличается от popup?
6. Что такое Extension Page?
7. Что делает `default_popup`?
8. Зачем нужен Developer Mode?
9. Что делает `Load unpacked`?
10. Что такое Extension ID?
11. Почему после изменения manifest необходимо выполнить Reload?
12. Чем Popup DevTools отличается от Service Worker DevTools?
13. Что такое execution context?
14. Чем browser extension отличается от обычного web application?
15. Почему extension следует рассматривать как multi-context application?

Если на эти вопросы уже можно уверенно ответить, следующий шаг — перестать рассматривать extension как "popup с JavaScript" и перейти к его настоящей архитектуре: **permissions, execution contexts и Service Worker**.
