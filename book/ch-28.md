# Глава 28. State Architecture

В предыдущей главе мы рассмотрели `chrome.storage` как механизм persistence.

Но storage — это только часть задачи.

Настоящая проблема значительно шире:

> **Где находится состояние приложения, кто им владеет, кто имеет право его изменять и каким образом разные execution contexts узнают об изменениях?**

Для обычного веб-приложения состояние часто можно представить относительно просто:

```text
Browser Page
    ↓
Application
    ↓
State
```

Для Manifest V3 extension ситуация значительно сложнее:

```text
                         Extension
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
    Popup              Service Worker        Content Script
        │                    │                    │
        ▼                    ▼                    ▼
   local state          runtime state        page state
        │                    │                    │
        └────────────────────┼────────────────────┘
                             │
                             ▼
                       Shared State
                             │
                             ▼
                     chrome.storage
```

У каждого context может быть собственное состояние.

При этом часть состояния должна быть общей.

Часть должна переживать перезапуск.

Часть должна существовать только несколько секунд.

Поэтому в хорошо спроектированном extension состояние необходимо **классифицировать и управлять им явно**.

---

# 28.1. Local state

**Local state** — состояние, принадлежащее конкретному execution context.

Например, Popup может иметь:

```javascript
let selectedTab = null;
let isLoading = false;
let error = null;
```

Это состояние относится именно к Popup.

Другому context оно не нужно.

---

# Почему local state полезен

Не всё состояние должно быть глобальным.

Если сделать всё shared:

```text
Everything
    ↓
Global State
```

архитектура быстро станет сложной.

Например:

```text
Popup
    ↓
changes global state
    ↓
Side Panel reacts
    ↓
Service Worker reacts
    ↓
Content Script reacts
```

Хотя на самом деле изменение могло быть чисто локальным.

---

# Пример

Допустим, Popup содержит форму:

```text
┌─────────────────────┐
│ Search: [________]  │
│                     │
│ [ Search ]          │
└─────────────────────┘
```

Текущий текст:

```text
searchQuery = "javascript"
```

не обязательно должен храниться в `chrome.storage`.

Это UI state.

Можно хранить его непосредственно в Popup:

```javascript
let searchQuery = "";
```

---

# Local state обычно ephemeral

Типичные примеры:

```text
isLoading
isOpen
selectedItem
hoveredElement
currentInput
temporaryError
animationState
```

Такие данные:

* не нужны другим contexts;
* не должны переживать закрытие UI;
* часто меняются очень быстро.

---

# Local state и lifecycle

Важно понимать:

```text
Popup state
```

живет примерно столько же, сколько Popup.

Когда Popup закрывается:

```text
Popup
   ↓
destroyed
   ↓
local state lost
```

Это нормально.

Если состояние должно переживать закрытие Popup, оно уже не является исключительно local state.

---

# Критерий

Полезный вопрос:

> **Если этот context будет уничтожен прямо сейчас, должна ли информация сохраниться?**

Если ответ:

**нет** → вероятно, это local/ephemeral state.

Если:

**да** → необходимо рассмотреть shared или persistent state.

---

# Local state не означает `localStorage`

Это принципиально.

Термин:

```text
local state
```

означает:

> состояние, принадлежащее конкретному context.

А:

```text
storage.local
```

означает:

> конкретный storage backend.

Это разные понятия.

---

# Например

Можно иметь:

```text
Popup local state
        │
        └── memory
```

и:

```text
Extension persistent state
        │
        └── storage.local
```

Слово `local` здесь имеет совершенно разный смысл.

---

# 28.2. Shared state

**Shared state** — состояние, которым должны пользоваться несколько contexts.

Например:

```text
enabled = true
```

может быть необходимо:

```text
Popup
Side Panel
Options
Service Worker
Content Script
```

Тогда хранить отдельную копию:

```text
Popup.enabled
SidePanel.enabled
Options.enabled
Worker.enabled
```

опасно.

Они могут рассинхронизироваться.

---

# Single Source of Truth

Лучше иметь:

```text
                 Application State
                       │
                       ▼
                 Single Source
                   of Truth
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Popup        Side Panel       Worker
```

Например:

```text
enabled = true
```

является одним логическим значением.

Contexts получают его из общего state layer.

---

# Где хранить shared state

В Manifest V3 наиболее естественными кандидатами являются:

```text
chrome.storage.local
chrome.storage.sync
chrome.storage.session
```

Выбор зависит от semantics состояния.

---

# Shared ≠ Persistent

Это очень важное различие.

State может быть:

```text
shared
```

но не быть:

```text
persistent
```

Например:

```text
current workflow step
```

может быть общим для Popup и Side Panel, но существовать только в рамках текущей session.

Поэтому категории состояния пересекаются.

---

# State dimensions

Лучше классифицировать state сразу по нескольким измерениям.

Например:

| Свойство        | Вопрос                             |
| --------------- | ---------------------------------- |
| Ownership       | Кто владеет state?                 |
| Scope           | Кто его видит?                     |
| Lifetime        | Как долго он существует?           |
| Persistence     | Переживает ли restart?             |
| Synchronization | Как contexts узнают об изменениях? |

---

# State matrix

Например:

| State             | Scope     | Lifetime       | Storage   |
| ----------------- | --------- | -------------- | --------- |
| Input field       | Popup     | Popup lifetime | Memory    |
| User settings     | Extension | Persistent     | `sync`    |
| Cache             | Extension | Persistent     | `local`   |
| Current workflow  | Extension | Session        | `session` |
| Loading indicator | Context   | Ephemeral      | Memory    |

---

# Shared state должен иметь владельца

Даже если state доступен нескольким contexts, желательно определить:

> **Кто является authority, принимающей решения об изменении?**

Например:

```text
                    Settings
                       │
                       ▼
                Service Worker
                       │
                 owns updates
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        Popup      Side Panel     Options
```

Contexts могут читать state, но изменение проходит через определённый механизм.

---

# Почему ownership важен

Рассмотрим:

```text
Popup → state.set()
Side Panel → state.set()
Options → state.set()
Content Script → state.set()
Worker → state.set()
```

Теперь невозможно легко ответить:

> Кто изменил состояние?

И:

> Как разрешить конфликт?

Поэтому даже shared state должен иметь ясную архитектуру mutation.

---

# Command vs state

Хорошая модель разделяет:

```text
Command
```

и:

```text
State
```

Например:

```text
Popup
  ↓
"ENABLE_FEATURE"
  ↓
Service Worker
  ↓
state.enabled = true
  ↓
Storage
```

То есть Popup не обязательно напрямую изменяет storage.

---

# Почему это удобно

Получается:

```text
UI
 ↓
Intent
 ↓
Command
 ↓
State owner
 ↓
State mutation
 ↓
Persistence
 ↓
State update
```

Это значительно лучше масштабируется.

---

# 28.3. Persistent state

Persistent state — состояние, которое должно переживать уничтожение execution context.

Например:

```text
user settings
subscription status
preferences
application configuration
saved rules
```

Для него используется:

```text
chrome.storage
```

---

# Persistent state и Service Worker

Особенно важно для MV3.

Нельзя делать:

```javascript
let subscription = {
    active: true
};
```

и считать это надёжным источником истины.

После:

```text
Service Worker termination
```

эта переменная исчезнет.

---

# Правильная модель

```text
              Persistent State
                     │
                     ▼
              chrome.storage
                     │
                     ▼
              Service Worker
                     │
                     ▼
              Runtime cache
```

---

# Hydration

Когда Service Worker запускается:

```text
Service Worker starts
        ↓
read persistent state
        ↓
hydrate runtime
        ↓
process event
```

---

# Но не обязательно загружать всё

Если extension имеет большое состояние:

```text
10 000 objects
```

не нужно обязательно загружать всё при каждом startup.

Можно использовать lazy loading:

```text
Worker starts
    ↓
load only required state
    ↓
event
    ↓
load additional state
```

---

# Persistent state должен быть минимальным

Хорошая persistence architecture отвечает на вопрос:

> Что действительно необходимо восстановить?

Например:

```text
enabled
settings
user preferences
rules
```

Но не:

```text
temporary DOM state
last mouse coordinates
every intermediate calculation
```

---

# Persistent state как contract

Можно рассматривать persistent state как API между версиями extension.

Например:

```text
Extension v1
     ↓
storage schema v1
```

После обновления:

```text
Extension v2
     ↓
storage schema v2
```

Поэтому schema должна быть стабильной и versioned.

---

# 28.4. Ephemeral state

**Ephemeral state** существует недолго и не должен сохраняться постоянно.

Примеры:

```text
isLoading
current selection
temporary error
active request
open menu
hover state
animation state
```

---

# Почему ephemeral state важен

Если пытаться сохранять всё:

```text
every UI change
     ↓
chrome.storage
```

получается:

* лишний I/O;
* лишняя синхронизация;
* более сложный lifecycle;
* потенциальное превышение quotas.

---

# Ephemeral state в памяти

Для большинства случаев:

```javascript
let isLoading = false;
```

достаточно.

---

# Ephemeral state в Service Worker

Здесь есть важная особенность.

Service Worker может быть остановлен.

Поэтому:

```javascript
let temporaryData = {};
```

может исчезнуть.

Следовательно, нужно решить:

> Действительно ли состояние является ephemeral?

Если потеря допустима:

```text
memory
```

подходит.

Если потеря недопустима:

```text
storage.session
```

или persistent storage может быть правильнее.

---

# Ephemeral ≠ unimportant

Ephemeral означает:

> короткоживущее.

Это не означает:

> несущественное.

Например:

```text
current transaction state
```

может быть очень важным в течение нескольких секунд.

---

# Ephemeral UI state

Для Popup:

```text
input
selection
loading
expanded section
```

обычно должен оставаться локальным.

```text
Popup
  │
  └── memory
```

---

# Ephemeral shared state

Иногда ephemeral state должен быть доступен нескольким contexts.

Например:

```text
Current workflow:
step = 3
```

может быть нужен:

```text
Side Panel
Service Worker
Content Script
```

Тогда можно использовать:

```text
storage.session
```

или специально организованный message/state layer.

---

# 28.5. State synchronization между contexts

Теперь рассмотрим самую сложную часть.

Предположим:

```text
Options Page
```

изменяет:

```text
enabled = false
```

Но:

```text
Side Panel
```

продолжает считать:

```text
enabled = true
```

Получается:

```text
                 State
                   │
          ┌────────┴────────┐
          ▼                 ▼
      Options           Side Panel
       false               true
```

Это состояние рассинхронизации.

---

# Модель synchronization

Правильнее:

```text
Options
   │
   ▼
State mutation
   │
   ▼
Single source of truth
   │
   ▼
State changed
   │
   ├─────────────┬─────────────┐
   ▼             ▼             ▼
Popup       Side Panel     Content Script
```

---

# Storage-based synchronization

Простейший вариант:

```text
Options
   ↓
chrome.storage.set()
   ↓
chrome.storage.onChanged
   ↓
Other contexts
```

---

# Пример

Options:

```javascript
await chrome.storage.sync.set({
    enabled: false
});
```

Другой context:

```javascript
chrome.storage.onChanged.addListener(
    (changes, area) => {

        if (area !== "sync") {
            return;
        }

        if (changes.enabled) {
            updateUI(changes.enabled.newValue);
        }
    }
);
```

---

# Message-based synchronization

Другой вариант:

```text
Context A
   ↓
runtime.sendMessage()
   ↓
Service Worker
   ↓
broadcast/update
   ↓
Contexts
```

Это полезно, когда изменение должно быть не просто новым state, а событием или командой.

---

# Storage vs Message

Можно использовать простое правило.

Если вопрос:

> **Какое сейчас состояние?**

используйте state/storage.

Если вопрос:

> **Что только что произошло?**

используйте message/event.

Например:

```text
State:
enabled = true
```

против:

```text
Event:
FEATURE_ENABLED
```

---

# State synchronization как reconciliation

Не всегда contexts должны получать каждое изменение.

Можно использовать модель:

```text
Context starts
    ↓
read current state
    ↓
subscribe to changes
```

То есть:

```text
hydrate
+
subscribe
```

---

# Это очень важный pattern

Context должен сначала получить актуальное состояние:

```text
getState()
```

а затем подписаться:

```text
subscribe()
```

Иначе можно пропустить изменение между двумя операциями.

---

# Например

```text
Context startup
      │
      ▼
Load state
      │
      ▼
Initialize UI
      │
      ▼
Subscribe to changes
```

---

# Но существует race condition

Представим:

```text
T1: get state
T2: another context changes state
T3: subscribe
```

Context может не получить изменение T2.

Поэтому production state architecture должна учитывать synchronization races.

---

# Более надёжный pattern

Можно использовать:

```text
Subscribe
   ↓
Read current state
   ↓
Apply snapshot
   ↓
Process future updates
```

или иметь центральный state owner, который отвечает за последовательность изменений.

---

# Versioned state

Для сложных систем полезно добавлять version:

```javascript
{
    version: 42,
    settings: {
        enabled: true
    }
}
```

Теперь contexts могут понимать:

```text
version 41
    ↓
version 42
```

---

# Почему version полезен

При нескольких contexts:

```text
Popup
Side Panel
Worker
Options
```

может возникать:

```text
state 10
state 11
state 12
```

Version позволяет определить:

```text
Is my state current?
```

---

# Optimistic updates

UI иногда может обновить локальное состояние сразу:

```text
User clicks
   ↓
UI updates
   ↓
Command
   ↓
Worker
   ↓
persistent state
```

Но тогда нужно учитывать rollback:

```text
UI optimistic update
       ↓
operation fails
       ↓
restore previous state
```

---

# Для простых extensions лучше не усложнять

Не нужно сразу строить:

```text
distributed consensus system
```

Большинство extensions могут использовать:

```text
storage
+
onChanged
+
messages
```

и этого будет достаточно.

---

# 28.6. Event-driven state updates

Manifest V3 естественным образом подталкивает нас к event-driven architecture.

Вместо:

```text
while(true) {
    checkState();
}
```

лучше:

```text
state changed
    ↓
event
    ↓
update
```

---

# Polling

Плохой подход:

```text
every 1 second:
    check storage
```

Это означает:

```text
timer
 ↓
read
 ↓
compare
 ↓
repeat
```

---

# Event-driven

Лучше:

```text
state changes
      ↓
event
      ↓
consumer reacts
```

---

# Storage events

Например:

```javascript
chrome.storage.onChanged.addListener(
    (changes, areaName) => {
        // react
    }
);
```

Это превращает storage в источник уведомлений об изменениях состояния.

---

# Message events

Также:

```javascript
chrome.runtime.onMessage.addListener(
    message => {
        // react
    }
);
```

---

# Tab events

State может изменяться в ответ на:

```text
tabs.onActivated
tabs.onUpdated
tabs.onRemoved
```

---

# User events

Например:

```text
Action click
Command
Popup interaction
Side Panel interaction
```

---

# Получается event-driven state machine

```text
                  Events
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
      User         Tab         Storage
       │            │            │
       └────────────┼────────────┘
                    ▼
               State Logic
                    │
                    ▼
              State Mutation
                    │
                    ▼
               Persistence
                    │
                    ▼
             State Changed
```

---

# State update pipeline

Хороший универсальный pipeline:

```text
Event
  ↓
Interpretation
  ↓
Command
  ↓
State transition
  ↓
Persistence
  ↓
Notification
  ↓
Consumers update
```

---

# Example

Пользователь нажимает кнопку:

```text
Popup
  ↓
ENABLE_FEATURE
  ↓
Service Worker
  ↓
state.enabled = true
  ↓
storage.sync.set()
  ↓
storage.onChanged
  ↓
Side Panel updates
```

---

# Почему это лучше прямого mutation

Плохой вариант:

```text
Popup
 ├── storage.set()
 ├── sendMessage()
 ├── update side panel
 └── update content script
```

Popup начинает знать архитектуру всей системы.

---

# Лучше

```text
Popup
   ↓
Command
   ↓
State owner
   ↓
State mutation
   ↓
Event propagation
```

Теперь Popup знает только:

> "Я хочу изменить состояние."

---

# Event-driven не означает event-only

Некоторые операции всё равно требуют request/response.

Например:

```text
Popup
   ↓
get current tab
   ↓
Service Worker
   ↓
response
```

Поэтому архитектура обычно сочетает:

```text
Commands
Events
Queries
State
```

---

# CQRS-подобная модель

Для сложного extension можно использовать упрощённую идею CQRS:

```text
Commands
    ↓
State mutation
```

и:

```text
Queries
    ↓
State read
```

Например:

```text
ENABLE_FEATURE
DISABLE_FEATURE
```

— commands.

А:

```text
GET_SETTINGS
GET_STATUS
```

— queries.

---

# Это особенно полезно для Service Worker

Service Worker становится:

```text
                    Service Worker
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
         Commands                   Queries
             │                         │
             ▼                         ▼
       State mutation              State read
             │                         │
             └────────────┬────────────┘
                          ▼
                        State
```

---

# 28.7. Reactive state architecture

Следующий шаг — реактивная архитектура.

В реактивной модели UI не спрашивает постоянно:

```text
"State changed?"
```

Вместо этого:

```text
State changes
    ↓
Subscribers notified
    ↓
UI updates
```

---

# Imperative UI

Без reactive model:

```javascript
if (state.enabled) {
    button.textContent = "Disable";
} else {
    button.textContent = "Enable";
}
```

Но разработчик должен сам следить за каждым местом изменения state.

---

# Reactive UI

Можно мыслить так:

```text
state.enabled
      │
      ▼
    render
      │
      ▼
    button
```

При изменении:

```text
state.enabled
      ↓
change
      ↓
render
      ↓
UI
```

---

# Reactive state graph

Для extension можно построить:

```text
                   State
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        Popup    Side Panel   Content
          │          │          │
          ▼          ▼          ▼
        Render     Render     DOM update
```

---

# Reactive state ≠ framework

Необходимо различать.

Reactive architecture — это architectural pattern.

Она может быть реализована:

```text
без framework
```

или с помощью:

```text
React
Vue
Svelte
Emerge
```

---

# Минимальная реактивная модель

Даже простой объект может иметь subscribers:

```javascript
const state = {
    enabled: false
};

const listeners = new Set();

function subscribe(listener) {
    listeners.add(listener);

    return () => listeners.delete(listener);
}

function setEnabled(value) {
    state.enabled = value;

    for (const listener of listeners) {
        listener(state);
    }
}
```

# Но extension требует cross-context reactivity

Внутри одного context это легко.

Но:

```text
Popup
```

и:

```text
Side Panel
```

не имеют общей JavaScript memory.

Поэтому:

```text
Local reactive state
```

должен быть соединён с:

```text
Cross-context synchronization
```

```text
                 Persistent State
                       │
                       ▼
                 Storage Layer
                       │
                       ▼
               State Synchronizer
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   Popup Store    Panel Store    Worker Store
        │              │              │
        ▼              ▼              ▼
       UI             UI          Runtime
```

# Local stores + shared persistence

Это один из наиболее практичных вариантов.

Каждый context имеет собственный reactive store:

```text
Popup Store
Side Panel Store
Options Store
```

Но все они синхронизируются с общей state representation.

# Например

```text
                 chrome.storage
                       │
              storage.onChanged
                       │
       ┌───────────────┼───────────────┐

 Popup Store      Panel Store      Options Store
       │               │               │
       ▼               ▼               ▼
     Popup          Side Panel       Options
```

# Service Worker как state coordinator

В более сложной архитектуре:

```text
                       Service Worker
                             │
                       State Coordinator
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
            Popup       Side Panel       Content
```

Service Worker может быть владельцем mutation logic.

# Но Service Worker не должен быть единственным местом хранения

Это важный момент.

Service Worker может быть **logical owner**, но persistent state должен находиться в storage.

```text
Logical ownership
       ↓
Service Worker

Persistence
       ↓
chrome.storage
```

---

# Что если Service Worker остановился?

Нормальная архитектура:

```text
Worker
  ↓
terminated
```

не должна приводить к:

```text
State lost
```

После нового startup:

```text
Worker starts
    ↓
read storage
    ↓
reconstruct state
```

# Reactive architecture + MV3 lifecycle

Это даёт очень сильную модель:

```text
            Persistent State
                   │
                   ▼
              chrome.storage
                   │
          ┌────────┴────────┐
          ▼                 ▼
      Context A          Context B
          │                 │
      local store       local store
          │                 │
          ▼                 ▼
          UI                UI
```

Contexts могут исчезать.

Но state остаётся.

# State as data flow

Вместо мышления:

```text
Component A modifies Component B
```

лучше:

```text

 ↓

 ↓
New state
 ↓
Consumers
```

Это делает систему значительно более предсказуемой.

# Однонаправленный поток данных

Очень полезная модель:

```text
             EVENT
               │
               ▼
          STATE LOGIC
               │
               ▼

               ▼

        ▼             ▼
      STORAGE       UI
        │
        ▼
    OTHER CONTEXTS
```

# Не делайте двунаправленную паутину

Плохая архитектура:

```text

  ↕       ↕

  ↕       ↕
```

Со временем невозможно понять:

```text
                      ▲
                      │
          ┌───────────┼───────────┐
          │           │           │
        Popup       Panel      Options
```

и:


# State transitions

Для сложного extension можно описывать изменения как transitions:

```text
State A
   │
   │ ENABLE_FEATURE
   ▼
State B
```

Например:

```text
{
    enabled: false
}
```

после:

```text
ENABLE_FEATURE
```

становится:

```text
{
    enabled: true
}
```

# Reducer-подобная модель

Можно даже использовать функцию:

```javascript
function reducer(state, action) {
    switch (action.type) {
        case "ENABLE_FEATURE":
            return {
                ...state,
                enabled: true
            };

        case "DISABLE_FEATURE":
            return {
                ...state,
                enabled: false
            };

        default:
            return state;
    }
}
```

Это необязательно, но для сложных extensions может значительно упростить reasoning.


Framework может добавить:

но базовая архитектура существует независимо от framework.

# State synchronization protocol

Для production extension полезно формализовать protocol.

Например:

```typescript
type StateUpdate = {
    version: number;
    changed: string[];
};
```

При изменении:

```text
State mutation
     ↓
version++
     ↓
persist
     ↓
notify
```

Consumer получает:

```text
version = 43
```

и может понять:

```text
my version = 42
incoming = 43
```

---

# Conflict handling

Если два contexts изменяют state одновременно:

```text
Popup
   ↓
state version 10

Options
   ↓
state version 10
```

оба изменяют его:

```text
Popup → version 11
Options → version 11
```

возникает conflict.

---

# Поэтому mutation ownership важен

Если mutation проходит через один coordinator:

```text
Popup
   ↓
Command
   ↓
Service Worker
   ↓
State transition
   ↓
version 11
```

а затем:

```text
Options
   ↓
Command
   ↓
Service Worker
   ↓
State transition
   ↓
version 12
```

конфликтов значительно меньше.

---

# Однако Service Worker ephemeral

Это не проблема.

Coordinator может быть:

```text
logical authority
```

но состояние хранится:

```text
persistent state
```

При restart coordinator восстанавливается.

# State selectors

UI не обязательно должен знать структуру всего state.

Можно использовать selectors:

```javascript
function selectTheme(state) {
    return state.settings.theme;
}
```

или:

```javascript
function selectIsEnabled(state) {
```

Они создают abstraction boundary:

```text

 ↓

 ↓
```

а не:

```text

 ↓

```

# Что должно быть local, а что shared?

Полезно использовать простой алгоритм.

### Вопрос 1

Нужно ли состояние другому context?

**Нет.**

→ Local state.

---

### Вопрос 2

Должно ли оно пережить context lifecycle?

**Нет.**

→ Ephemeral state.

---

### Вопрос 3

Должно ли оно пережить Service Worker restart?

**Да.**

→ Persistent или session storage.

---

### Вопрос 4

Должно ли оно синхронизироваться между contexts?

**Да.**

→ Shared state + synchronization mechanism.

---

### Вопрос 5

Должно ли оно синхронизироваться между устройствами?

**Да.**

→ `storage.sync`.

---

# Итоговая классификация

Можно получить такую таблицу:

| Тип        | Scope                   | Lifetime        | Типичное место           |
| ---------- | ----------------------- | --------------- | ------------------------ |
| Local      | Один context            | Context         | Memory                   |
| Ephemeral  | Один/несколько contexts | Короткий        | Memory / session         |
| Shared     | Extension               | Variable        | Storage / coordinator    |
| Persistent | Extension               | Long-term       | `storage.local` / `sync` |
| Managed    | Organization            | Policy lifetime | `storage.managed`        |

# Главные архитектурные принципы

## 1. Не существует одного универсального state

В extension есть несколько классов состояния.

```text
Local
Shared
Persistent
Ephemeral
```

---

## 2. State и storage — разные понятия

State:

```text
что приложение знает сейчас
```

Storage:

```text
где часть этого состояния сохраняется
```

---

## 3. Runtime state должен быть disposable

Особенно в Service Worker:

```text
Runtime
   ↓
can disappear
```

---

## 4. Persistent state должен быть независим от lifecycle

```text
Worker dies
    ↓
State survives
```

---

## 5. Shared state должен иметь Single Source of Truth

Не:

```text
Popup state
Panel state
Options state
```

как независимые источники истины.

А:

```text
             Source of Truth
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Popup       Panel       Options
```

---

## 6. Commands изменяют state, а не UI

```text
Command
   ↓
State transition
   ↓
UI reacts
```

---

## 7. Events сообщают об изменениях

```text
State changed
    ↓
Event
    ↓
Consumers
```

---

## 8. Storage не должен быть message bus

```text
State → storage
Events → messaging
```

---

## 9. Реактивность должна строиться вокруг state

Не:

```text
Component A
   ↓
manually update
Component B
```

а:

```text
State
 ↓
Consumers
```

# Главная идея главы

Для Manifest V3 состояние нельзя рассматривать как просто набор переменных.

Правильнее мыслить им как **отдельной архитектурной подсистемой**:

```text
State Model
     ↓
Ownership
     ↓
Lifetime
     ↓
Persistence
     ↓
Synchronization
     ↓
Reactivity
```

И особенно важно помнить о фундаментальном свойстве MV3:

```text
Contexts are temporary.
State is not necessarily temporary.
```

Поэтому зрелая архитектура extension строится не вокруг вопроса:

> «Где сейчас находится моя переменная?»

а вокруг вопросов:

> **Кому принадлежит это состояние?**

> **Кто имеет право его изменять?**

> **Как долго оно должно существовать?**

> **Должно ли оно переживать lifecycle context?**

> **Кто должен узнать об изменении?**

> **Как восстановить состояние после restart?**

Если эти вопросы определены заранее, Manifest V3 extension перестаёт быть набором разрозненных Popup, Content Script и Service Worker и превращается в **единую event-driven state system**, распределённую между несколькими execution contexts.
