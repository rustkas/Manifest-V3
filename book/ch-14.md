# Часть V. Communication

# Глава 14. Message Passing

В Manifest V3 разные execution contexts не являются частями одного JavaScript runtime.

Popup, Service Worker, Content Script, Options Page и Side Panel могут принадлежать одному extension, но каждый из них имеет собственный execution context.

Поэтому следующий код не создаёт общего состояния:

```javascript
// popup.js

const state = {
    counter: 10
};
```

И:

```javascript
// service-worker.js

console.log(state);
```

`state` здесь не существует.

Между contexts нет общей JavaScript-памяти.

Для взаимодействия используется **message passing**.

```text
┌──────────────┐
│    Popup     │
└──────┬───────┘
       │
       │ message
       ▼
┌──────────────┐
│Service Worker│
└──────┬───────┘
       │
       │ message
       ▼
┌──────────────┐
│Content Script│
└──────────────┘
```

Message passing — один из фундаментальных механизмов архитектуры Manifest V3.

---

# 14.1. Почему contexts не имеют общего JavaScript state

Начнём с самого важного архитектурного факта.

Extension может содержать:

```text
Popup
Service Worker
Content Script
Options Page
Side Panel
DevTools Page
```

Но нельзя представить их как:

```text
Application
    │
    └── one JavaScript heap
```

Правильнее:

```text
              Extension
                  │
      ┌───────────┼───────────┐
      │           │           │
      ▼           ▼           ▼
   Popup      Service       Content
              Worker        Script
      │           │           │
   Heap A       Heap B      Heap C
```

Каждый context имеет собственное выполнение JavaScript.

---

## Пример

Popup:

```javascript
const counter = 42;
```

Service Worker:

```javascript
console.log(counter);
```

Это вызовет ошибку:

```text
ReferenceError: counter is not defined
```

Потому что `counter` принадлежит JavaScript environment Popup.

---

# Даже одинаковое имя — разные переменные

Можно написать:

```javascript
// popup.js

let status = "popup";
```

и:

```javascript
// service-worker.js

let status = "background";
```

Обе переменные существуют независимо:

```text
Popup:
status = "popup"

Service Worker:
status = "background"
```

Изменение одной не изменяет другую.

---

# Нельзя передать ссылку на объект

Например:

```javascript
const user = {
    name: "John"
};
```

Нельзя сделать:

```text
Popup
   │
   └── reference to user ──► Service Worker
```

Потому что это разные JavaScript environments.

Передаваться должны **данные**, а не ссылки на объекты памяти.

Концептуально:

```text
Object
   │
   ▼
serialization / message
   │
   ▼
data
   │
   ▼
another context
```

---

# Message как граница между contexts

Это очень важный архитектурный принцип:

> **Message является boundary между execution contexts.**

Например:

```text
Popup
  │
  │  { type: "GET_STATUS" }
  ▼
Service Worker
```

Service Worker не получает доступ к внутреннему JavaScript state Popup.

Он получает сообщение.

---

# Context isolation — это преимущество

На первый взгляд отсутствие общего state кажется неудобством.

На самом деле это создаёт полезную архитектурную границу.

Например:

```text
Popup
```

может исчезнуть:

```text
User closes popup
```

Service Worker при этом продолжает существовать независимо от UI lifecycle.

Это позволяет разделить:

```text
UI state
```

и:

```text
Application state
```

---

# Где хранить общее состояние?

Если состояние должно переживать исчезновение context:

```text
Popup closes
Service Worker restarts
Browser restarts
```

его следует хранить в подходящем persistent storage, например:

```text
chrome.storage
IndexedDB
```

а contexts взаимодействуют через сообщения:

```text
Popup
  │
  │ message
  ▼
Service Worker
  │
  ▼
Storage
```

---

# Message passing как IPC

Полезная аналогия — **IPC (Inter-Process Communication)**.

Хотя execution contexts extension не обязательно являются отдельными OS-процессами в буквальном смысле, архитектурно механизм похож:

```text
Context A
   │
   │ message
   ▼
Context B
```

Вместо:

```text
shared memory
```

используется:

```text
message passing
```

Это особенно важно для построения больших extensions.

---

# 14.2. `chrome.runtime.sendMessage()`

Для отправки сообщения используется:

```javascript
chrome.runtime.sendMessage(message);
```

Например:

```javascript
chrome.runtime.sendMessage({
    type: "GET_STATUS"
});
```

Получатель может находиться в другом extension context.

---

# Простая схема

```text
Popup
  │
  │ chrome.runtime.sendMessage()
  ▼
Service Worker
  │
  │ onMessage
  ▼
Handler
```

---

# Отправка сообщения

Например, Popup:

```javascript
const response =
    await chrome.runtime.sendMessage({
        type: "GET_STATUS"
    });
```

Здесь Popup отправляет запрос и ожидает response.

---

# Получение сообщения

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        console.log(message);

    }
);
```

Если Popup отправил:

```javascript
{
    type: "GET_STATUS"
}
```

Service Worker получит этот объект.

---

# `message`

Первый аргумент:

```javascript
message
```

содержит данные сообщения.

Например:

```javascript
{
    type: "SAVE_SETTINGS",
    payload: {
        enabled: true
    }
}
```

---

# `sender`

Второй аргумент:

```javascript
sender
```

содержит информацию об отправителе.

Это полезно, например, когда нужно понимать:

```text
Кто отправил сообщение?
```

или:

```text
Из какой вкладки оно пришло?
```

Для security-sensitive операций информация об отправителе особенно важна.

---

# `sendResponse`

Третий аргумент:

```javascript
sendResponse
```

позволяет вернуть ответ отправителю.

Например:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        if (message.type === "GET_STATUS") {

            sendResponse({
                status: "ready"
            });

        }
    }
);
```

Отправитель может получить:

```javascript
const response =
    await chrome.runtime.sendMessage({
        type: "GET_STATUS"
    });

console.log(response.status);
```

---

# Message — не только notification

Очень важно различать:

```text
Notification
```

и:

```text
Request
```

Например:

```javascript
{
    type: "REFRESH"
}
```

может означать команду:

> Выполни действие.

А:

```javascript
{
    type: "GET_SETTINGS"
}
```

означает:

> Выполни действие и верни результат.

Поэтому messaging architecture часто строится вокруг request/response модели.

---

# 14.3. `chrome.runtime.onMessage`

Listener регистрируется следующим образом:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        // handle message

    }
);
```

---

# Один центральный listener

Для небольшого extension можно начать с:

```javascript
chrome.runtime.onMessage.addListener(
    async (message, sender) => {

        switch (message.type) {

            case "GET_STATUS":
                return {
                    status: "ready"
                };

            case "GET_SETTINGS":
                return getSettings();

            default:
                throw new Error(
                    "Unknown message"
                );
        }
    }
);
```

Но при росте extension такой listener становится слишком большим.

---

# Message Router

Лучше разделить:

```text
onMessage
    ↓
router
    ↓
handler
```

Например:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        return routeMessage(
            message,
            sender,
            sendResponse
        );

    }
);
```

А router:

```javascript
async function routeMessage(
    message,
    sender
) {

    switch (message.type) {

        case "GET_STATUS":
            return getStatus();

        case "GET_SETTINGS":
            return getSettings();

        case "START_SCAN":
            return startScan(
                message.payload,
                sender
            );

        default:
            throw new Error(
                `Unknown message: ${message.type}`
            );
    }
}
```

---

# Почему router важен?

Потому что `onMessage` должен быть транспортным уровнем.

Его задача:

```text
receive message
      ↓
route message
```

а не:

```text
receive message
      ↓
500 lines of business logic
```

---

# 14.4. Request/response model

Самая полезная модель messaging:

```text
Request
   ↓
Handler
   ↓
Response
```

Например:

```text
Popup
  │
  │ GET_SETTINGS
  ▼
Service Worker
  │
  │ settings
  ▼
Popup
```

---

# Request

Request можно представить как:

```javascript
{
    type: "GET_SETTINGS"
}
```

---

# Response

Response:

```javascript
{
    ok: true,
    data: {
        enabled: true
    }
}
```

---

# Почему полезно использовать `ok`?

Вместо:

```javascript
return settings;
```

можно использовать единый response envelope:

```javascript
{
    ok: true,
    data: settings
}
```

При ошибке:

```javascript
{
    ok: false,
    error: {
        code: "STORAGE_ERROR",
        message: "Unable to load settings"
    }
}
```

Это создаёт единый protocol.

---

# Request/response protocol

Получается:

```text
┌─────────────┐
│   Request   │
├─────────────┤
│ type        │
│ payload     │
│ requestId   │
└──────┬──────┘
       │
       ▼
   Handler
       │
       ▼
┌─────────────┐
│  Response   │
├─────────────┤
│ ok          │
│ data        │
│ error       │
│ requestId   │
└─────────────┘
```

`requestId` не всегда необходим для простого `sendMessage()`, но становится полезным в более сложных протоколах, особенно если строится собственный message bus.

---

# Команда и payload

Хорошая структура:

```javascript
{
    type: "START_SCAN",
    payload: {
        tabId: 123
    }
}
```

Здесь:

```text
type
```

определяет операцию.

```text
payload
```

содержит её параметры.

---

# Не смешивайте команды и данные

Плохой вариант:

```javascript
{
    action: "scan",
    foo: true,
    random: 123,
    anotherValue: "..."
}
```

Лучше:

```javascript
{
    type: "START_SCAN",
    payload: {
        tabId: 123
    }
}
```

---

# 14.5. Async responses

Большинство реальных extension операций асинхронны.

Например:

```text
message
   ↓
storage
   ↓
network
   ↓
tabs
   ↓
result
```

Поэтому handler часто должен работать с `Promise`.

Например:

```javascript
chrome.runtime.onMessage.addListener(
    async (message) => {

        if (message.type === "GET_SETTINGS") {

            return await loadSettings();

        }
    }
);
```

Современный Chrome поддерживает Promise-based message handling для `onMessage`, но при разработке расширений важно учитывать целевой браузер и актуальную документацию конкретного API. Для максимально переносимого кода следует понимать и традиционный `sendResponse`-механизм.

---

# Классический `sendResponse` pattern

Традиционная форма:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        loadSettings()
            .then(settings => {

                sendResponse({
                    ok: true,
                    data: settings
                });

            })
            .catch(error => {

                sendResponse({
                    ok: false,
                    error: error.message
                });

            });

        return true;
    }
);
```

Здесь:

```javascript
return true;
```

сообщает системе, что response будет отправлен асинхронно через `sendResponse`.

---

# Почему это важно?

Без правильного async handling можно получить ситуацию:

```text
Message
  ↓
Handler starts async operation
  ↓
Listener finishes
  ↓
Response channel closes
  ↓
Response lost
```

Поэтому механизм ответа должен быть выбран и реализован корректно.

---

# Современная Promise-модель

В современных браузерах можно писать более естественно:

```javascript
chrome.runtime.onMessage.addListener(
    async message => {

        if (message.type === "GET_SETTINGS") {

            const settings =
                await loadSettings();

            return {
                ok: true,
                data: settings
            };
        }
    }
);
```

Это значительно ближе к обычному async/await коду.

Но extension developer должен помнить:

> **Message channel — это асинхронная граница между contexts, а не обычный вызов функции.**

---

# Request timeout

Для production-like messaging иногда нужен timeout.

Например:

```text
Popup
  │
  │ request
  ▼
Service Worker
  │
  X
  │
timeout
```

UI не должен зависать бесконечно.

Концептуально:

```javascript
const response =
    await requestWithTimeout(
        {
            type: "START_SCAN"
        },
        5000
    );
```

---

# Почему timeout полезен?

Потому что любой boundary может завершиться ошибкой:

```text
context unavailable
message rejected
handler failed
unexpected exception
browser lifecycle
```

Надёжная архитектура предполагает failure.

---

# 14.6. Message schemas

Когда extension имеет несколько contexts, количество сообщений быстро растёт.

Например:

```text
GET_STATUS
GET_SETTINGS
SAVE_SETTINGS
START_SCAN
STOP_SCAN
GET_RESULT
DELETE_RESULT
SYNC
LOGIN
LOGOUT
...
```

Если структура сообщений нигде не определена, появляется хаос.

Поэтому нужен **message schema**.

---

# Простой schema

Можно договориться, что каждое сообщение имеет:

```javascript
{
    type: string,
    payload?: object
}
```

Например:

```javascript
{
    type: "START_SCAN",
    payload: {
        tabId: 123
    }
}
```

---

# Строгий protocol

Ещё лучше:

```text
Message
├── type
├── payload
└── version
```

Например:

```javascript
{
    type: "START_SCAN",
    version: 1,
    payload: {
        tabId: 123
    }
}
```

---

# Почему version?

Если extension развивается:

```text
v1
```

может стать:

```text
v2
```

И message protocol может эволюционировать.

Для небольшого extension version не обязателен, но для сложного внутреннего protocol это может быть полезно.

---

# Message constants

Не стоит повторять строки:

```javascript
"START_SCAN"
```

в десятках файлов.

Можно определить:

```javascript
export const MESSAGE_TYPES = {
    GET_STATUS: "GET_STATUS",
    GET_SETTINGS: "GET_SETTINGS",
    SAVE_SETTINGS: "SAVE_SETTINGS",
    START_SCAN: "START_SCAN",
    STOP_SCAN: "STOP_SCAN"
};
```

Теперь:

```javascript
{
    type: MESSAGE_TYPES.START_SCAN
}
```

---

# Message factories

Ещё один подход:

```javascript
export function startScan(tabId) {

    return {
        type: "START_SCAN",
        payload: {
            tabId
        }
    };
}
```

Использование:

```javascript
await chrome.runtime.sendMessage(
    startScan(tab.id)
);
```

Это уменьшает количество ошибок при ручном формировании сообщений.

---

# Schema validation

Message нельзя автоматически считать корректным только потому, что он пришёл из собственного extension context.

Нужно проверять:

```text
type
payload
required fields
field types
allowed values
```

Например:

```javascript
function isStartScanMessage(message) {

    return (
        message &&
        message.type === "START_SCAN" &&
        Number.isInteger(
            message.payload?.tabId
        )
    );
}
```

---

# Почему validation особенно важна?

Потому что message boundary — это boundary доверия.

Особенно это важно, когда сообщение связано с:

```text
network requests
storage changes
tabs
permissions
privileged extension operations
```

---

# Message schema как контракт

Можно рассматривать schema как договор:

```text
Sender
   │
   │ contract
   ▼
Receiver
```

Sender обещает:

```text
type = START_SCAN
payload.tabId = integer
```

Receiver не должен гадать, что ему пришло.

---

# Type-safe messaging

JavaScript позволяет передавать что угодно:

```javascript
{
    type: "START_SCAN",
    payload: "hello"
}
```

Но это создаёт ошибки во время выполнения.

TypeScript позволяет описать protocol на уровне типов.

---

# Union type

Например:

```typescript
type ExtensionMessage =
    | {
        type: "GET_STATUS";
      }
    | {
        type: "GET_SETTINGS";
      }
    | {
        type: "START_SCAN";
        payload: {
            tabId: number;
        };
      }
    | {
        type: "STOP_SCAN";
        payload: {
            tabId: number;
        };
      };
```

Теперь TypeScript знает допустимые messages.

---

# Type-safe handler

Можно написать:

```typescript
function handleMessage(
    message: ExtensionMessage
) {

    switch (message.type) {

        case "GET_STATUS":
            return getStatus();

        case "GET_SETTINGS":
            return getSettings();

        case "START_SCAN":
            return startScan(
                message.payload.tabId
            );

        case "STOP_SCAN":
            return stopScan(
                message.payload.tabId
            );
    }
}
```

TypeScript понимает:

```text
START_SCAN
   ↓
payload exists
   ↓
payload.tabId is number
```

---

# Discriminated union

Конструкция:

```typescript
type: "START_SCAN"
```

является **discriminant**.

TypeScript использует его для narrowing.

Например:

```typescript
switch (message.type) {

    case "START_SCAN":
        message.payload.tabId;
        break;

}
```

В этой ветке `message.payload` известен TypeScript.

Это один из лучших способов описывать extension message protocols.

---

# Type-safe responses

Можно типизировать не только requests, но и responses.

Например:

```typescript
type StatusResponse = {
    ok: true;
    data: {
        status: "ready" | "running";
    };
};
```

И ошибка:

```typescript
type ErrorResponse = {
    ok: false;
    error: {
        code: string;
        message: string;
    };
};
```

Общий тип:

```typescript
type Response =
    | StatusResponse
    | ErrorResponse;
```

---

# Request → Response mapping

Для большого extension можно пойти ещё дальше.

Определим protocol:

```typescript
interface MessageMap {

    GET_STATUS: {
        request: undefined;
        response: {
            status: string;
        };
    };

    GET_SETTINGS: {
        request: undefined;
        response: Settings;
    };

    START_SCAN: {
        request: {
            tabId: number;
        };
        response: ScanResult;
    };
}
```

Теперь protocol становится центральным контрактом.

---

# Typed `sendMessage`

Можно создать собственную abstraction:

```typescript
async function sendMessage<
    T extends keyof MessageMap
>(
    type: T,
    payload: MessageMap[T]["request"]
): Promise<MessageMap[T]["response"]> {

    const response =
        await chrome.runtime.sendMessage({
            type,
            payload
        });

    return response;
}
```

Использование:

```typescript
const result =
    await sendMessage(
        "START_SCAN",
        {
            tabId: 123
        }
    );
```

TypeScript теперь контролирует:

```text
message type
       ↓
required payload
       ↓
response type
```

---

# Ошибка становится compile-time error

Например:

```typescript
await sendMessage(
    "START_SCAN",
    {
        tabId: "123"
    }
);
```

TypeScript сообщит:

```text
Type 'string' is not assignable to type 'number'
```

Это именно то, чего мы хотим.

---

# Type-safe messaging architecture

Можно получить:

```text
┌──────────────────────┐
│   Message Protocol   │
│      TypeScript      │
└──────────┬───────────┘
           │
     ┌─────┴─────┐
     ▼           ▼
   Sender      Receiver
     │           │
     ▼           ▼
 compile-time  validation
     │           │
     └─────┬─────┘
           ▼
       Runtime
```

Но важно понимать:

> **TypeScript не заменяет runtime validation.**

---

# Compile-time ≠ runtime

TypeScript проверяет:

```text
ваш исходный код
```

Но message является runtime data.

Поэтому в production extension нужны оба уровня:

```text
TypeScript
    ↓
compile-time safety

Runtime validation
    ↓
actual message safety
```

---

# Например

TypeScript может гарантировать:

```typescript
type StartScan = {
    type: "START_SCAN";
    payload: {
        tabId: number;
    };
};
```

Но runtime всё равно может получить некорректные данные.

Поэтому receiver должен проверять message.

# Message passing между Content Script и Service Worker

Отдельно стоит отметить распространённый сценарий:

```text
Web Page
   │
   ▼
Content Script
   │
   │ runtime.sendMessage()
   ▼
Service Worker
```

Content Script может извлечь информацию:

```javascript
const title =
    document.title;
```

и передать её Service Worker:

```javascript
chrome.runtime.sendMessage({
    type: "PAGE_DATA",
    payload: {
        title
    }
});
```

Service Worker получает:

```javascript
chrome.runtime.onMessage.addListener(
    message => {

        if (message.type === "PAGE_DATA") {
            console.log(
                message.payload.title
            );
        }
    }
);
```

---

# Service Worker → Content Script

Обратное направление:

```text
Service Worker
      │
      │ chrome.tabs.sendMessage()
      ▼
Content Script
```

Например:

```javascript
await chrome.tabs.sendMessage(
    tabId,
    {
        type: "HIGHLIGHT_RESULTS"
    }
);
```

Content Script:

```javascript
chrome.runtime.onMessage.addListener(
    message => {

        if (
            message.type ===
            "HIGHLIGHT_RESULTS"
        ) {
            highlightResults();
        }
    }
);
```

---

# `runtime.sendMessage()` и `tabs.sendMessage()`

Нужно различать два распространённых механизма.

### `chrome.runtime.sendMessage()`

Используется для сообщений между extension contexts.

Например:

```text
Popup → Service Worker
Options → Service Worker
Content Script → Service Worker
```

### `chrome.tabs.sendMessage()`

Используется, когда Service Worker или другой extension context хочет отправить сообщение **в конкретную вкладку**, обычно Content Script.

```text
Service Worker
      │
      ▼
specific tab
      │
      ▼
Content Script
```

# Message lifecycle

Полный lifecycle сообщения можно представить так:

```text
1. Create
   ↓
2. Serialize
   ↓
3. Transport
   ↓
4. Receive
   ↓
5. Validate
   ↓
6. Route
   ↓
7. Execute
   ↓
8. Response
   ↓
9. Handle response
```

Каждый шаг может стать источником ошибки.

---

# Error handling

Никогда не следует считать:

```javascript
await chrome.runtime.sendMessage(...)
```

гарантированно успешным.

Например:

```javascript
try {

    const response =
        await chrome.runtime.sendMessage({
            type: "GET_STATUS"
        });

    console.log(response);

} catch (error) {

    console.error(
        "Message failed",
        error
    );
}
```

---

# Ошибки application-level

Кроме transport error может существовать application error.

Например:

```javascript
{
    ok: false,
    error: {
        code: "NOT_AUTHENTICATED",
        message: "User is not authenticated"
    }
}
```

Поэтому полезно различать:

```text
Transport error
        ↓
message did not complete

Application error
        ↓
message completed,
operation failed
```

---

# Почему это важно?

Например:

```text
sendMessage()
     │
     X
```

означает одно.

А:

```text
sendMessage()
     │
     ▼
{
    ok: false,
    error: ...
}
```

означает другое.

Во втором случае messaging работает, но операция завершилась ошибкой.

---

# Не отправляйте `Error` как основной protocol

Вместо:

```javascript
return error;
```

лучше использовать сериализуемую структуру:

```javascript
{
    ok: false,
    error: {
        code: "NETWORK_ERROR",
        message: "Request failed"
    }
}
```

Такой protocol проще обрабатывать и типизировать.

---

# Централизованный error format

Например:

```typescript
type ErrorResponse = {
    ok: false;
    error: {
        code:
            | "INVALID_MESSAGE"
            | "NOT_FOUND"
            | "PERMISSION_DENIED"
            | "NETWORK_ERROR"
            | "INTERNAL_ERROR";
        message: string;
    };
};
```

Теперь contexts используют единый формат.

# Плохой protocol

Например:


# Message passing и lifecycle Service Worker

Есть ещё одна важная особенность.

Service Worker может быть остановлен браузером.

Поэтому нельзя проектировать messaging так, будто Service Worker:

```text
always running
always has memory
always has cached objects
```

Правильная модель:

```text
Message
   ↓
Service Worker starts
   ↓
Initialize
   ↓
Handle message
   ↓
Persist required state
   ↓
Worker may terminate
```

---

# Поэтому message handler должен быть stateless насколько возможно

Плохой вариант:

```javascript
let currentUser;

chrome.runtime.onMessage.addListener(
    async message => {

        // assume currentUser exists

    }
);
```

Если worker перезапустился:

```text
currentUser === undefined
```

Лучше:

```text
Message
   ↓
Load state
   ↓
Execute
   ↓
Save state
```

# Рекомендуемый минимальный protocol

Для production-like extension можно принять следующую базовую форму:

```typescript
type Message =
    | {
        type: "GET_STATUS";
      }
    | {
        type: "GET_SETTINGS";
      }
    | {
        type: "START_SCAN";
        payload: {
            tabId: number;
        };
      };
```

Response:

```typescript
type Response<T> =
    | {
        ok: true;
        data: T;
      }
    | {
        ok: false;
        error: {
            code: string;
            message: string;
        };
      };
```

Это уже достаточно мощная основа для серьёзного extension.

# Итог главы

Message Passing — это не просто способ вызвать:

```javascript
chrome.runtime.sendMessage()
```

Это **архитектурный механизм связи между независимыми execution contexts**.

Главные идеи главы:

1. **Contexts не имеют общей JavaScript-памяти.**
2. **Нельзя передавать между ними JavaScript references как shared state.**
3. **Данные передаются через messages.**
4. **`chrome.runtime.sendMessage()` используется для отправки сообщений между extension contexts.**
5. **`chrome.runtime.onMessage` используется для их обработки.**
6. **`request/response` — базовая модель для взаимодействия.**
7. **Асинхронные операции требуют корректного async response handling.**
8. **Messages должны иметь формальный schema.**
9. **Message protocol должен иметь предсказуемые success и error responses.**
10. **Runtime validation необходима даже при использовании TypeScript.**
11. **TypeScript discriminated unions позволяют сделать message protocol type-safe.**
12. **Message protocol следует рассматривать как внутренний API extension.**
13. **Service Worker должен маршрутизировать messages к application handlers, а не содержать всю логику внутри `onMessage`.**
14. **Messaging должен учитывать ephemeral lifecycle Service Worker.**

Главная формула этой главы:

```text
Context A
   │
   │ Message
   ▼
Transport
   │
   ▼
Validation
   │
   ▼
Router
   │
   ▼
Handler
   │
   ▼
Application Logic
   │
   ▼
Response
   │
   ▼
Context A
```

А на архитектурном уровне:

```text
             ┌───────────┐
             │   Popup   │
             └─────┬─────┘
                   │
                   │ message
                   ▼
             ┌───────────┐
             │  Message  │
             │   Bus     │
             └─────┬─────┘
                   │
                   ▼
          ┌─────────────────┐
          │ Service Worker  │
          │                 │
          │ Router          │
          │ Validation      │
          │ Handlers        │
          └───────┬─────────┘
                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
       Storage Network    Tabs
                           │
                           ▼
                     Content Script
```

Именно этот подход превращает messaging из набора вызовов Chrome API в **чётко определённый внутренний коммуникационный слой расширения**.
