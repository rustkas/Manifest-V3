# Глава 18. Popup

Popup — один из самых узнаваемых элементов browser extension.

Пользователь нажимает на иконку расширения:

```text
┌───────────────────────────────┐
│ Browser Toolbar               │
│                       [ 🧩 ]   │
└───────────────────────────────┘
                          │
                        click
                          ▼
                 ┌─────────────────┐
                 │      Popup      │
                 │                 │
                 │   Extension UI  │
                 │                 │
                 └─────────────────┘
```

На первый взгляд Popup выглядит как небольшое веб-приложение.

Технически это действительно HTML-страница extension, однако архитектурно относиться к ней как к обычному приложению было бы ошибкой.

Popup имеет очень специфический lifecycle:

```text
open
  ↓
initialize
  ↓
user interaction
  ↓
close
  ↓
destroy
```

Он существует только пока пользователь взаимодействует с ним.

Поэтому правильная архитектура Popup должна учитывать его **ephemeral nature**.

---

# 18.1. Архитектура popup

Popup является extension page.

Минимальная структура может выглядеть так:

```text
extension/
│
├── manifest.json
├── service-worker.js
│
├── popup.html
├── popup.css
└── popup.js
```

В `manifest.json`:

```json
{
    "manifest_version": 3,
    "name": "Example Extension",
    "version": "1.0.0",

    "action": {
        "default_popup": "popup.html"
    },

    "background": {
        "service_worker": "service-worker.js"
    }
}
```

После клика по Action браузер открывает:

```text
popup.html
```

---

# Popup — Extension Page

Popup имеет собственный extension origin.

Условно:

```text
chrome-extension://<extension-id>/popup.html
```

Поэтому Popup имеет собственные:

* DOM;
* JavaScript environment;
* CSS;
* module system;
* extension APIs;
* lifecycle.

Например:

```html
<!doctype html>

<html>
<head>
    <meta charset="utf-8">
    <link rel="stylesheet" href="popup.css">
</head>

<body>

    <button id="start">
        Start
    </button>

    <script type="module" src="popup.js"></script>

</body>
</html>
```

---

# Popup не является Content Script

Это принципиально важно.

Popup:

```text
Extension Page
```

Content Script:

```text
Page-associated Extension Context
```

Они работают в разных execution contexts.

```text
┌──────────────────┐
│      Popup       │
│                  │
│ extension page   │
└──────────────────┘

          ≠

┌──────────────────┐
│  Content Script  │
│                  │
│ isolated world   │
└──────────────────┘
```

Поэтому Popup не получает автоматически доступ к DOM текущей веб-страницы.

Например:

```javascript
document.body
```

в Popup означает:

> DOM Popup.

А не:

> DOM активной вкладки.

Это одна из самых распространённых ошибок начинающих разработчиков.

---

# Popup и текущая вкладка

Если Popup должен узнать информацию о текущей вкладке, он должен явно обратиться к соответствующему API.

Например:

```javascript
const tabs = await chrome.tabs.query({
    active: true,
    currentWindow: true
});

const tab = tabs[0];

console.log(tab.id);
console.log(tab.url);
```

Но это всё ещё не означает, что Popup получил DOM страницы.

Для работы с DOM страницы обычно требуется Content Script:

```text
Popup
   │
   ▼
Service Worker
   │
   ▼
Content Script
   │
   ▼
Page DOM
```

---

# Архитектурная роль Popup

Лучше всего рассматривать Popup как:

> **ephemeral presentation layer для пользовательского взаимодействия с extension.**

Он отвечает за:

```text
UI
├── отображение состояния
├── пользовательский ввод
├── небольшие действия
└── отправку команд
```

Он не должен автоматически становиться:

```text
database
+
business logic
+
background runtime
+
network manager
+
scheduler
```

---

# Хорошая архитектура

```text
                   Popup
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Render                 Commands
          │                     │
          │                     ▼
          │              Service Worker
          │                     │
          │          ┌──────────┼──────────┐
          │          ▼          ▼          ▼
          │       Storage      Tabs      Network
          │
          ▼
        UI
```

Popup показывает состояние и инициирует действия.

Service Worker координирует background operations.

---

# 18.2. Popup lifecycle

Самая важная особенность Popup — его lifecycle.

Упрощённо:

```text
User clicks Action
        │
        ▼
    Popup opens
        │
        ▼
   popup.js starts
        │
        ▼
  UI initialization
        │
        ▼
 User interaction
        │
        ▼
 Popup closes
        │
        ▼
 Popup destroyed
```

После закрытия Popup его JavaScript environment больше не должен рассматриваться как существующий.

---

# Popup открывается по требованию

Popup не работает постоянно.

Нет такой модели:

```text
Browser starts
    ↓
Popup starts
    ↓
Popup waits
```

Вместо этого:

```text
Browser
   │
   │ user click
   ▼
Popup created
```

---

# Popup закрывается автоматически

Popup может закрыться, когда пользователь:

* кликает вне Popup;
* переключается на другой UI;
* открывает другой интерфейс;
* закрывает взаимодействие с extension;
* выполняет действие, после которого браузер закрывает popup.

Следовательно, разработчик не должен рассчитывать на то, что Popup будет открыт долго.

---

# Пример проблемы

Допустим, разработчик пишет:

```javascript
let progress = 0;

setInterval(() => {
    progress++;
    render(progress);
}, 1000);
```

Пока Popup открыт:

```text
0
1
2
3
4
...
```

Но пользователь закрывает Popup:

```text
Popup
  ↓
destroy
```

Таймер и весь JavaScript runtime Popup больше не являются надёжным местом для продолжения операции.

---

# Операция должна жить не в Popup

Если задача должна продолжаться после закрытия UI:

```text
Popup
   │
   │ START
   ▼
Service Worker
   │
   ▼
Background operation
```

Popup инициирует операцию.

Но не владеет её lifecycle.

---

# Popup lifecycle vs Service Worker lifecycle

Это два разных ephemeral runtime.

```text
Popup
─────
open
  ↓
run
  ↓
destroy
```

и:

```text
Service Worker
──────────────
start
  ↓
event handling
  ↓
suspend/terminate
  ↓
restart
```

Но между ними есть принципиальное различие.

Popup существует только как UI interaction.

Service Worker является background event-driven runtime и может быть снова запущен браузером при необходимости.

Поэтому долгоживущую application state необходимо проектировать независимо от обоих runtime.

---

# 18.3. Почему popup нельзя считать обычным приложением

На уровне HTML Popup действительно похож на обычное веб-приложение:

```text
popup.html
    ↓
popup.js
    ↓
DOM
```

Но его lifecycle совершенно другой.

Обычный web application часто предполагает:

```text
open page
     ↓
user works
     ↓
page remains open
```

Popup:

```text
click extension
     ↓
popup opens
     ↓
short interaction
     ↓
popup closes
```

---

# Popup — transient UI

Правильное определение:

> Popup — transient UI, а не persistent application surface.

То есть:

```text
Popup = кратковременный интерфейс
```

а не:

```text
Popup = главное приложение extension
```

---

# Что нельзя предполагать

Нельзя предполагать, что Popup:

* всегда открыт;
* всегда содержит актуальное состояние;
* может выполнять длительные операции;
* является источником истины;
* может напрямую управлять всеми contexts;
* может хранить состояние только в global variables.

---

# Global variables

Например:

```javascript
let currentUser = null;
let scanResults = [];
let isRunning = false;
```

Такие переменные могут быть полезны внутри одного Popup instance.

Но они не являются persistent application state.

После закрытия:

```text
Popup destroyed
```

значения исчезают.

---

# Правильное разделение

Например:

```text
Popup
 └── temporary UI state

Service Worker
 └── runtime coordination

chrome.storage
 └── persistent state
```

Получаем:

```text
             Persistent state
                    │
                    ▼
               chrome.storage
                    │
                    ▼
              Service Worker
                    │
                    ▼
                  Popup
```

---

# Popup как View

Можно использовать классическую модель:

```text
Model
  │
  ▼
Controller
  │
  ▼
View
```

В extension это может выглядеть так:

```text
Persistent State
      │
      ▼
Service Worker
      │
      ▼
Popup
```

Popup становится в основном **View + user interaction layer**.

---

# 18.4. Communication with Service Worker

Popup часто должен взаимодействовать с Service Worker.

Основной механизм:

```javascript
chrome.runtime.sendMessage()
```

Например:

```javascript
const response = await chrome.runtime.sendMessage({
    type: "GET_STATUS"
});

console.log(response);
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {

        if (message.type === "GET_STATUS") {

            sendResponse({
                status: "ready"
            });

        }

    }
);
```

---

# Request/response

Типичный communication pattern:

```text
Popup
  │
  │ GET_STATUS
  ▼
Service Worker
  │
  │ STATUS
  ▼
Popup
```

Popup не должен знать, откуда Service Worker получил информацию.

Например:

```text
Service Worker
   │
   ├── Storage
   ├── Tabs
   ├── Network
   └── Application State
```

Popup получает только результат.

---

# Command pattern

Например, пользователь нажимает:

```text
[ Start Scan ]
```

Popup:

```javascript
await chrome.runtime.sendMessage({
    type: "START_SCAN"
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    async (message) => {

        if (message.type === "START_SCAN") {
            await startScan();
        }

    }
);
```

Архитектура:

```text
User
 │
 ▼
Popup
 │
 │ command
 ▼
Service Worker
 │
 ▼
Application logic
```

---

# Typed communication

Для большого extension сообщения лучше типизировать.

Например:

```typescript
type PopupMessage =
    | {
        type: "GET_STATUS";
    }
    | {
        type: "START_SCAN";
    }
    | {
        type: "STOP_SCAN";
    };
```

Теперь Popup и Service Worker используют общий protocol.

---

# Popup и Content Script

Иногда Popup хочет воздействовать непосредственно на текущую страницу.

Например:

```text
Popup
   │
   ▼
Content Script
   │
   ▼
DOM
```

Можно использовать Service Worker как coordinator:

```text
Popup
   │
   ▼
Service Worker
   │
   ▼
Content Script
```

Например:

```javascript
await chrome.runtime.sendMessage({
    type: "START_PAGE_OPERATION"
});
```

Service Worker:

```javascript
chrome.tabs.sendMessage(
    tabId,
    {
        type: "START_PAGE_OPERATION"
    }
);
```

---

# Почему это часто лучше?

Потому что Service Worker становится центральным coordinator:

```text
Popup
   │
   ▼
Service Worker
   │
   ├── Storage
   ├── Tabs
   └── Content Scripts
```

Popup остаётся простым UI.

---

# Но прямое взаимодействие тоже возможно

Архитектура не обязана всегда использовать Service Worker.

Если Popup может напрямую выполнить нужную операцию и это соответствует permission model, прямой вызов допустим.

Например:

```text
Popup
  │
  ▼
chrome.storage.local
```

Главное — не создавать искусственную сложность.

---

# Long-lived connection

Если Popup должен получать поток данных, можно использовать Port:

```javascript
const port = chrome.runtime.connect({
    name: "popup"
});
```

Service Worker:

```javascript
chrome.runtime.onConnect.addListener(port => {

    if (port.name === "popup") {

        port.postMessage({
            type: "STATE",
            payload: getState()
        });

    }

});
```

Но здесь нужно помнить:

> Закрытие Popup означает закрытие его UI context, поэтому Port, связанный с ним, также нельзя считать постоянным каналом.

---

# 18.5. Работа с состоянием

State management — одна из самых важных тем при проектировании Popup.

Нужно разделять несколько видов состояния.

---

# 1. UI state

Например:

```text
isLoading
selectedTab
isExpanded
inputValue
```

Такое состояние может спокойно жить в Popup:

```javascript
let isLoading = false;
```

---

# 2. Application state

Например:

```text
scannerStatus
currentTask
results
```

Если состояние должно существовать независимо от Popup, оно должно находиться за пределами Popup.

Например:

```text
Service Worker
     │
     ▼
Storage
```

---

# 3. Persistent state

Например:

```text
user settings
preferences
configuration
cached data
```

может храниться:

```javascript
chrome.storage.local
```

---

# Пример

Плохая архитектура:

```text
Popup
 ├── settings
 ├── scan state
 ├── results
 ├── network
 └── UI
```

Лучше:

```text
Popup
 └── UI

Service Worker
 ├── coordination
 └── application logic

Storage
 └── persistent state
```

---

# Получение initial state

Когда Popup открывается, он должен получить актуальное состояние.

Например:

```javascript
const state = await chrome.runtime.sendMessage({
    type: "GET_STATE"
});

render(state);
```

Получается:

```text
Popup opens
    │
    ▼
GET_STATE
    │
    ▼
Service Worker
    │
    ▼
State
    │
    ▼
Popup
    │
    ▼
Render
```

---

# Snapshot model

Очень полезный подход:

> Popup при открытии получает snapshot состояния.

Например:

```javascript
{
    status: "running",
    progress: 72
}
```

После этого Popup отображает:

```text
Scanner
──────────────

Running

Progress: 72%
```

---

# А если состояние изменилось?

Если операция продолжается после открытия Popup:

```text
Service Worker
     │
     ├── progress 73
     ├── progress 74
     ├── progress 75
     └── ...
```

Popup может получать события через messaging или Port.

Но если Popup закрывается:

```text
Popup
  ↓
destroy
```

это не должно останавливать саму операцию.

---

# Reopen model

Пользователь может:

```text
open Popup
   ↓
see 30%
   ↓
close Popup
   ↓
wait
   ↓
open Popup again
```

Popup должен получить:

```text
current state = 80%
```

а не:

```text
state = undefined
```

Именно поэтому состояние не следует хранить исключительно в Popup.

---

# Popup как stateless-ish UI

Полностью stateless Popup невозможен — UI всё равно имеет локальное состояние.

Но архитектурно полезно стремиться к модели:

```text
Persistent State
       │
       ▼
   State Snapshot
       │
       ▼
     Popup
       │
       ▼
     Render
```

Popup можно уничтожить и создать снова без потери application state.

---

# 18.6. Закрытие popup

Закрытие Popup — нормальное событие, а не исключительная ситуация.

Например:

```text
Popup opened
     ↓
User clicks "Start"
     ↓
Service Worker starts operation
     ↓
Popup closes
```

Правильная система продолжает работать:

```text
Popup        Service Worker
  │                 │
  │ START           │
  ├────────────────►│
  │                 │
  X                 │
closed              │
                    │
                    ▼
              operation continues
```

---

# Неправильная архитектура

Например:

```javascript
button.onclick = async () => {

    await longRunningOperation();

    showResult();

};
```

Если операция действительно должна быть длительной, она не должна зависеть от того, остаётся ли Popup открытым.

Лучше:

```javascript
button.onclick = async () => {

    await chrome.runtime.sendMessage({
        type: "START_OPERATION"
    });

};
```

А operation выполняется в подходящем background context.

---

# Закрытие как естественный lifecycle event

Не нужно пытаться удерживать Popup открытым.

Popup предназначен для короткого взаимодействия.

Пользователь:

```text
opens
interacts
leaves
```

Это нормальный сценарий.

---

# Нужно ли слушать `unload`?

Обычно архитектуру не следует строить вокруг:

```javascript
window.addEventListener("unload", ...)
```

или подобных механизмов.

Почему?

Потому что правильнее не зависеть от момента закрытия.

Если важное состояние нужно сохранить:

```text
save it before
```

а не:

```text
hope to save it during destruction
```

---

# 18.7. UX limitations

Popup имеет несколько фундаментальных ограничений.

---

## 1. Малый размер

Popup предназначен для компактного интерфейса.

Он плохо подходит для:

```text
large tables
complex forms
long documents
rich editors
multi-step workflows
```

---

# 2. Короткая сессия

Пользователь обычно открывает Popup на несколько секунд.

Поэтому UX должен быть:

```text
open
 ↓
understand
 ↓
act
 ↓
close
```

а не:

```text
open
 ↓
study application
 ↓
configure complex system
 ↓
work for 20 minutes
```

---

# 3. Popup легко потерять

Пользователь может кликнуть вне него.

Popup закроется.

Поэтому не стоит заставлять пользователя выполнять длинную последовательность действий:

```text
Step 1
 ↓
Step 2
 ↓
Step 3
 ↓
Step 4
 ↓
Step 5
```

если любое внешнее взаимодействие уничтожает текущий UI session.

---

# 4. Popup не подходит для background monitoring

Плохой UX:

```text
Open Popup
   ↓
wait 10 minutes
   ↓
monitor progress
```

Для этого лучше:

```text
Side Panel
```

или другой persistent UI surface.

---

# 5. Popup плохо подходит для complex state

Если нужно одновременно показывать:

```text
status
logs
results
filters
charts
controls
history
```

Popup быстро становится перегруженным.

---

# 6. Popup не является полноценным application window

Это важно учитывать при проектировании.

Если extension начинает выглядеть как:

```text
┌─────────────────────────────┐
│ Application                 │
├─────────────────────────────┤
│ Sidebar                     │
│                             │
│ Main content                │
│                             │
│ Logs                        │
│                             │
└─────────────────────────────┘
```

то Popup, скорее всего, уже не является подходящей UI surface.

---

# 18.8. Когда popup — плохой UI choice

Теперь можно сформулировать практические критерии.

Popup — плохой выбор, если интерфейс должен быть:

### Долгоживущим

Например:

```text
continuous monitoring
long-running workflow
live dashboard
```

Лучше использовать:

```text
Side Panel
```

или отдельную extension page.

---

# Если нужно много места

Например:

```text
data table
editor
visualization
logs
```

Popup будет слишком маленьким.

Лучше:

```text
Extension Page
Side Panel
```

---

# Если пользователь должен работать долго

Например:

```text
10–30 минут
```

Popup неудобен.

Лучше использовать persistent UI.

---

# Если есть сложная навигация

Например:

```text
Dashboard
   ├── Projects
   ├── Settings
   ├── History
   ├── Reports
   └── Account
```

Это уже скорее application interface.

# Snapshot + Command

Очень хороший универсальный паттерн для Popup:

```text

2. Get snapshot
3. Render
4. User sends command
5. Service Worker changes state
6. Popup receives updated state
7. Render
8. Close
```

Например:

```text
Popup
 │
 │ GET_STATE
 ▼
Service Worker
 │
 │ STATE
 ▼
Popup
 │
 │ START
 ▼
Service Worker
 │
 │ STATE_CHANGED
 ▼
Popup
```

# Главные правила главы

## Правило 1

**Popup — extension page, но с особым ephemeral lifecycle.**

```text
Popup ≠ persistent application
```

---

## Правило 2

**Не храните критическое состояние только в Popup.**

```text
Popup state
    ≠
Persistent state
```

---

## Правило 3

**Долгие операции не должны зависеть от Popup.**

```text
Popup
  ↓
command
  ↓
Service Worker
```

---

## Правило 4

**Popup должен быстро открываться и быстро объяснять состояние.**

Пользователь должен почти сразу понять:

```text
What is happening?
What can I do?
What happened?
```

---

## Правило 5

**Popup не получает автоматически DOM текущей страницы.**

```text
Popup DOM
    ≠
Page DOM
```

Для страницы используется Content Script.

---

## Правило 6

**Popup можно уничтожить в любой момент.**

Поэтому приложение должно быть готово к:

```text
open
close
open again
```

без потери application state.

---

## Правило 7

**Используйте Popup для quick interactions.**

```text
quick
small
focused
contextual
```

---

## Правило 8

**Не пытайтесь превратить Popup в полноценный desktop application.**

Если интерфейс становится большим:

```text
Popup
  ↓
Side Panel / Extension Page
```

# Итоговая архитектурная модель

Popup занимает очень конкретное место в Manifest V3:

```text
                    Browser
                       │
                       ▼
                  Extension Action
                       │
                       ▼
                    Popup
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
          UI State          Commands
                                │
                                ▼
                         Service Worker
                                │
                    ┌───────────┼───────────┐
                    ▼           ▼           ▼
                 Storage       Tabs       Network
                    │
                    ▼
              Application State
                    │
                    ▼
                  Popup
                    │
                    ▼
                  Render
```

Главная идея этой архитектуры проста:

> **Popup должен быть короткоживущим UI, а не местом, где живёт само приложение.**

Он отображает актуальное состояние, принимает пользовательские действия и передаёт команды в application runtime. Если Popup закрывается — extension не должен «ломаться». Если пользователь открыл его снова — Popup должен заново получить актуальное состояние и продолжить работу с ним.

Именно это отличает правильно спроектированный Manifest V3 Popup от маленькой веб-страницы, случайно помещённой в browser toolbar.
