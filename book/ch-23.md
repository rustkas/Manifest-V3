# Часть IX. Declarative APIs

# Глава 23. Философия Declarative APIs

До этого момента мы в основном рассматривали **imperative programming** — подход, при котором extension получает событие, выполняет JavaScript-код и самостоятельно принимает решение о следующем действии.

Например:

```text
User action
    ↓
Service Worker
    ↓
JavaScript
    ↓
chrome.tabs
    ↓
Content Script
    ↓
DOM
```

Для многих задач это естественная модель.

Но Manifest V3 постепенно усиливает другой подход:

> **Вместо того чтобы постоянно говорить браузеру, что делать, extension описывает правила, а браузер самостоятельно применяет их.**

Это и есть философия **Declarative APIs**.

Declarative APIs особенно важны для Manifest V3, потому что они позволяют перенести часть логики из JavaScript runtime extension непосредственно в браузерный runtime.

---

# 23.1. Imperative vs Declarative

Начнём с фундаментального различия.

## Imperative programming

Imperative подход описывает:

> **как выполнить операцию.**

Например:

```javascript
chrome.tabs.onUpdated.addListener(
    async (tabId, changeInfo, tab) => {

        if (changeInfo.url) {

            if (tab.url.includes("example.com")) {

                // выполнить действие
            }
        }
    }
);
```

Extension говорит браузеру:

```text
Когда произошло событие
        ↓
запусти мой JavaScript
        ↓
проверь условие
        ↓
прими решение
        ↓
выполни действие
```

То есть:

```text
Event
 ↓
JavaScript
 ↓
Condition
 ↓
Decision
 ↓
Action
```

---

# Declarative programming

Declarative подход описывает:

> **что должно быть достигнуто или какое правило должно действовать.**

Упрощённо:

```text
IF
    request matches X

THEN
    apply rule Y
```

Extension не обязательно должен самостоятельно обрабатывать каждый event.

Вместо этого он регистрирует правило:

```text
Rule
 ↓
Browser
```

А браузер самостоятельно решает:

```text
Event
 ↓
Rule matching
 ↓
Action
```

---

# Главное различие

Можно сформулировать так:

### Imperative

```text
"Browser, сообщи мне о каждом событии.
Я сам решу, что делать."
```

### Declarative

```text
"Browser, вот мои правила.
Сам применяй их, когда они подходят."
```

Это фундаментальная разница архитектурных моделей.

---

# Пример

Предположим, extension должен блокировать определённые network requests.

Imperative модель концептуально выглядит так:

```text
Network request
       ↓
Extension
       ↓
JavaScript
       ↓
Inspect request
       ↓
Decision
       ↓
Block
```

Declarative модель:

```text
Rules
  ↓
Browser
  ↓
Network request
  ↓
Rule matching
  ↓
Block
```

Второй вариант потенциально не требует запуска JavaScript extension для каждого запроса.

И это принципиально важно.

---

# Imperative architecture

Типичная архитектура:

```text
                 Browser
                    │
                  Event
                    │
                    ▼
             Service Worker
                    │
               JavaScript
                    │
             Application logic
                    │
                    ▼
                Chrome API
```

---

# Declarative architecture

В declarative architecture:

```text
                 Extension
                    │
                  Rules
                    │
                    ▼
              Browser runtime
                    │
             Rule evaluation
                    │
                    ▼
                 Action
```

JavaScript runtime может вообще не участвовать в конкретной операции.

---

# Почему это важно именно для MV3

Manifest V3 значительно сильнее ориентирован на модель:

```text
Event-driven
+
Ephemeral
+
Declarative
```

Вместо:

```text
Persistent background process
+
arbitrary JavaScript
```

Это связано сразу с несколькими проблемами:

* performance;
* memory;
* security;
* lifecycle;
* predictability;
* browser resource management.

---

# 23.2. Почему MV3 движется к declarative model

Чтобы понять эту тенденцию, необходимо вспомнить архитектуру MV2.

В Manifest V2 extension мог иметь:

```text
Persistent Background Page
```

которая фактически представляла собой постоянно работающий JavaScript runtime.

Архитектура:

```text
Browser
   ↓
Background Page
   ↓
JavaScript
   ↓
Events
   ↓
Logic
```

Если extension установлено, background page могла существовать долгое время.

---

# Проблема persistent background

Представим сотни extensions:

```text
Extension A
    ↓
Persistent JS

Extension B
    ↓
Persistent JS

Extension C
    ↓
Persistent JS

Extension D
    ↓
Persistent JS
```

Каждое расширение потенциально:

* занимает память;
* создаёт timers;
* держит event listeners;
* выполняет background work;
* выполняет network operations;
* поддерживает собственное состояние.

Для браузера это дорого.

---

# MV3 Service Worker

Manifest V3 меняет модель:

```text
Persistent background page
        ↓
Service Worker
```

Теперь:

```text
Event
 ↓
Start worker
 ↓
Handle event
 ↓
Worker may terminate
```

То есть extension runtime становится ephemeral.

---

# Declarative APIs дополняют эту модель

Если задача может быть описана правилом, нет смысла запускать Service Worker для каждого события.

Вместо:

```text
Event
 ↓
Wake Service Worker
 ↓
Run JavaScript
 ↓
Evaluate rule
 ↓
Perform action
```

можно сделать:

```text
Event
 ↓
Browser
 ↓
Declarative rule
 ↓
Action
```

Это значительно ближе к философии MV3.

---

# DeclarativeNetRequest как пример

Один из наиболее известных примеров — `declarativeNetRequest`.

Extension может определить правила:

```text
IF request matches pattern X
THEN block/modify request
```

Браузер затем сам применяет эти правила.

Концептуально:

```text
Extension
   │
   │ rules
   ▼
Browser
   │
   ├── request A → no match
   ├── request B → match
   └── request C → match
                    │
                    ▼
                  action
```

JavaScript Service Worker не обязан просыпаться для каждого network request.

---

# Declarative Content

Ещё один важный пример — declarative content.

Идея:

```text
IF page satisfies condition
THEN make extension action available
```

Вместо постоянного анализа страницы JavaScript-кодом extension может зарегистрировать условия.

---

# Declarative API как перенос ответственности

Imperative:

```text
Extension
    ↓
Browser event
    ↓
Extension logic
    ↓
Decision
```

Declarative:

```text
Extension
    ↓
Rule
    ↓
Browser
    ↓
Decision
```

Ответственность за execution частично перемещается:

```text
Extension → Browser
```

---

# 23.3. Browser-controlled execution

Это одна из самых важных идей всей главы.

В обычном JavaScript-приложении разработчик контролирует runtime:

```text
Application
     ↓
JavaScript
     ↓
Event loop
     ↓
Application logic
```

В browser extension ситуация другая.

Браузер контролирует:

* lifecycle;
* permissions;
* contexts;
* tabs;
* navigation;
* network;
* extension runtime;
* suspension;
* execution boundaries.

Declarative APIs позволяют использовать это управление.

---

# Browser как execution engine

Вместо:

```text
Extension
    ↓
"Run this code"
```

получаем:

```text
Extension
    ↓
"Here is the policy"
    ↓
Browser
    ↓
"Я сам применю её"
```

Это очень важное архитектурное изменение.

---

# Policy вместо procedure

Imperative code описывает procedure:

```text
1. Get request
2. Inspect URL
3. Check condition
4. Decide
5. Block
```

Declarative rule описывает policy:

```text
Requests matching X
→ block
```

Таким образом:

```text
Imperative
    = procedure

Declarative
    = policy
```

---

# Почему браузеру выгодно контролировать execution

Браузер знает гораздо больше о своей внутренней работе, чем extension.

Он знает:

```text
Network stack
Rendering
Tabs
Frames
Processes
Memory
CPU
Security boundaries
Lifecycle
```

Поэтому браузер может оптимизировать выполнение declarative rules лучше, чем произвольный JavaScript extension.

---

# Например

Extension говорит:

```text
Block requests matching:
example.com/ads/*
```

Браузер может:

```text
Network request
       ↓
Rule engine
       ↓
Match
       ↓
Block
```

без необходимости:

```text
Network
 ↓
IPC
 ↓
Service Worker
 ↓
JavaScript
 ↓
IPC
 ↓
Network
```

Это потенциально более эффективная архитектура.

---

# Declarative APIs как policy engine

Можно представить:

```text
                 Extension
                    │
                    ▼
                  Rules
                    │
                    ▼
             Browser Policy Engine
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Tabs        Network      Pages
        │           │           │
        ▼           ▼           ▼
      Action       Action       Action
```

Это уже не просто API.

Это механизм передачи **policy** браузеру.

---

# 23.4. Performance

Performance — одна из главных причин существования declarative APIs.

Рассмотрим две архитектуры.

---

## Imperative pipeline

```text
Event
 ↓
Browser
 ↓
Extension boundary
 ↓
Service Worker startup
 ↓
JavaScript
 ↓
Application logic
 ↓
Chrome API
 ↓
Browser
```

Каждый дополнительный переход потенциально имеет стоимость.

---

## Declarative pipeline

```text
Event
 ↓
Browser
 ↓
Rule engine
 ↓
Action
```

Меньше runtime overhead.

---

# Особенно важно для частых событий

Некоторые browser events могут происходить очень часто.

Например:

```text
Network requests
DOM-related conditions
Navigation
Tab activity
```

Если extension должен выполнять JavaScript для каждого события:

```text
1000 events
   ↓
1000 JS callbacks
```

это может быть дорого.

Declarative rule engine может обработать их внутри browser runtime.

---

# Compile once, execute many

Хорошая модель:

```text
Extension
   ↓
Register rules
   ↓
Browser stores rules
   ↓
Many events
   ↓
Fast matching
```

Вместо:

```text
Many events
   ↓
Wake extension
   ↓
Run JavaScript
```

Это особенно хорошо соответствует принципу:

> **Compile/register more, execute less.**

---

# CPU

Declarative execution может снизить количество работы JavaScript runtime.

Например:

```text
Imperative:
10 000 events
×
JavaScript callback
```

против:

```text
Declarative:
10 000 events
×
browser rule evaluation
```

Конкретная производительность зависит от API и реализации браузера, но архитектурная цель очевидна:

> не будить extension runtime там, где задача может быть выполнена самим браузером.

---

# Memory

Ephemeral Service Worker уже уменьшает постоянное потребление памяти.

Declarative APIs усиливают этот эффект.

Вместо:

```text
Service Worker
     ↓
loaded
     ↓
waiting
```

может быть:

```text
Rules
 ↓
browser-managed runtime
```

---

# Startup cost

Service Worker может потребовать:

```text
Load JavaScript
 ↓
Initialize modules
 ↓
Initialize state
 ↓
Register handlers
```

Declarative rule может быть зарегистрировано заранее.

Тогда execution не требует полного запуска application runtime.

---

# Но declarative ≠ всегда быстрее

Важно избежать неправильного вывода:

> «Declarative API всегда быстрее JavaScript».

Это неверно.

Преимущество возникает тогда, когда задача естественно соответствует конкретному declarative API.

Если требуется сложная бизнес-логика:

```text
parse data
 ↓
call multiple services
 ↓
AI processing
 ↓
complex algorithm
 ↓
database
```

declarative API может быть просто неподходящим.

---

# Правильное правило

Используйте:

```text
Declarative
```

если задача является:

```text
policy
matching
filtering
simple browser action
```

Используйте:

```text
Imperative
```

если задача требует:

```text
complex computation
stateful business logic
orchestration
external services
dynamic algorithms
```

---

# 23.5. Security

Security — ещё одна фундаментальная причина declarative architecture.

Чем больше произвольного JavaScript выполняется в browser context, тем больше потенциальная поверхность атаки.

---

# Arbitrary JavaScript

Imperative extension может выполнять:

```text
JavaScript
 ↓
DOM
 ↓
Network
 ↓
Storage
 ↓
Tabs
 ↓
Other extension APIs
```

Разработчик получает большую свободу.

Но:

> большая свобода означает большую поверхность для ошибок.

---

# Declarative ограничивает возможности

Declarative API обычно позволяет только определённый набор операций.

Например:

```text
Rule
 ↓
Match
 ↓
Allowed action
```

Нельзя произвольно выполнить:

```javascript
eval(...)
```

или:

```javascript
run arbitrary code
```

в рамках declarative rule engine.

---

# Capability model

Это можно представить как:

```text
Imperative API

Extension
   ↓
Large capability surface
```

против:

```text
Declarative API

Extension
   ↓
Specific rule language
   ↓
Specific capabilities
```

То есть declarative API представляет собой более ограниченный **capability surface**.

---

# Security by construction

В идеале declarative система позволяет сказать:

```text
Extension can do:
    A
    B
    C

Extension cannot do:
    D
    E
    F
```

Это проще анализировать, чем произвольный runtime:

```text
"Extension может выполнить любой JavaScript,
который разработчик написал."
```

---

# Permissions + Declarative APIs

Declarative model хорошо сочетается с permission model.

Архитектура:

```text
Manifest
   │
   ├── Permissions
   │
   └── Declarative rules
           │
           ▼
        Browser
```

Браузер может контролировать:

```text
What
+
Where
+
When
+
Which action
```

---

# Минимизация доверия

Это соответствует принципу:

> **Don't give the extension more power than it needs.**

Если задача решается:

```text
Declarative rule
```

не обязательно давать extension возможность:

```text
arbitrary JavaScript
+
broad host access
+
persistent runtime
```

Это важная архитектурная идея.

---

# 23.6. Lifecycle independence

Теперь рассмотрим связь с Service Worker lifecycle.

Это одна из самых сильных сторон declarative model.

---

# Проблема Service Worker

Service Worker:

```text
Start
 ↓
Handle event
 ↓
Idle
 ↓
Terminate
```

Поэтому нельзя рассчитывать:

```javascript
let state = {};
```

как на постоянное хранилище.

---

# Declarative rules не зависят от runtime state так же, как JS logic

Концептуально:

```text
Service Worker
    ↓
register rules
```

После регистрации:

```text
Service Worker
    ↓
may terminate
```

А rules продолжают существовать в browser-managed subsystem согласно модели конкретного API.

---

# Очень важная идея

Можно разделить:

```text
Application runtime
```

и:

```text
Browser policy
```

Например:

```text
Application runtime
    ↓
Service Worker
    ↓
Business logic
```

и:

```text
Browser policy
    ↓
Declarative rules
```

Они имеют разные lifecycle characteristics.

---

# Это уменьшает зависимость от worker startup

Представим:

```text
Network request
```

В imperative architecture:

```text
Request
 ↓
wake worker
 ↓
execute logic
```

В declarative architecture:

```text
Request
 ↓
browser rule engine
```

Service Worker может вообще не понадобиться для конкретного события.

---

# Lifecycle independence

Таким образом:

```text
Imperative
Event
 ↓
Extension runtime
 ↓
Action
```

а:

```text
Declarative
Event
 ↓
Browser runtime
 ↓
Action
```

Это означает:

> Declarative logic может жить на уровне браузерной инфраструктуры, а не extension JavaScript runtime.

---

# Это особенно важно для MV3

MV3 не пытается сделать Service Worker постоянным.

Напротив:

```text
Service Worker
   ↓
ephemeral
```

Поэтому архитектура должна учитывать:

```text
What must run in worker?
What can run declaratively?
What must be persisted?
What can browser execute?
```

---

# 23.7. Declarative architecture

Теперь соберём всё вместе.

Declarative architecture — это не просто использование одного API.

Это способ проектировать extension.

---

# Уровень 1. User intent

Пользователь хочет:

```text
Block trackers
```

или:

```text
Show action on matching pages
```

или:

```text
Redirect matching requests
```

---

# Уровень 2. Policy

Мы формулируем:

```text
IF condition
THEN action
```

Например:

```text
IF
    URL matches X

THEN
    apply Y
```

---

# Уровень 3. Browser rule

Extension преобразует policy в browser-recognized rule:

```text
Policy
 ↓
Declarative rule
```

---

# Уровень 4. Browser execution

Браузер:

```text
Event
 ↓
Rule engine
 ↓
Match
 ↓
Action
```

---

# Полная модель

```text
                 USER
                  │
                  ▼
              Intent
                  │
                  ▼
               Policy
                  │
                  ▼
        Declarative Rule
                  │
                  ▼
          Browser Runtime
                  │
          ┌───────┴────────┐
          ▼                ▼
      Event stream      Browser state
          │                │
          └───────┬────────┘
                  ▼
             Rule Match
                  │
                  ▼
                Action
```

---

# Declarative и Imperative вместе

Самая важная мысль:

> MV3 не означает, что imperative JavaScript исчезает.

Правильная архитектура обычно **гибридная**.

Например:

```text
                 Extension
                     │
          ┌──────────┴──────────┐
          │                     │
    Declarative                Imperative
       │                         │
       ▼                         ▼
 Browser rules              Service Worker
       │                         │
       │                    Business logic
       │                         │
       └──────────┬──────────────┘
                  ▼
              Application
```

---

# Когда использовать Declarative

Подходит:

```text
Filtering
Matching
Blocking
Redirect rules
Context conditions
Browser policies
Simple automatic actions
```

---

# Когда использовать Imperative

Подходит:

```text
Complex business logic
State machines
Data processing
API calls
AI
Database operations
Multi-step workflows
UI orchestration
```

---

# Когда использовать оба

Очень часто.

Например, extension для анализа страниц:

```text
Declarative
    ↓
Determine whether page is relevant
    ↓
Imperative
    ↓
Analyze page
    ↓
Storage
    ↓
Side Panel
```

---

# Declarative as first filter

Очень мощный паттерн:

```text
                    Event
                      │
                      ▼
              Declarative Filter
                 /          \
              no             yes
              │                │
              ▼                ▼
            Ignore        Service Worker
                              │
                              ▼
                       Complex processing
```

Это позволяет не запускать сложную логику там, где она не нужна.

---

# Это похоже на compiler pipeline

Можно провести интересную аналогию.

Imperative code:

```text
Source code
 ↓
Runtime
 ↓
Execution
```

Declarative architecture:

```text
Policy
 ↓
Rule representation
 ↓
Browser rule engine
 ↓
Execution
```

В этом смысле browser становится частично **execution engine для domain-specific policies**.

---

# Declarative API как DSL

Многие declarative APIs фактически представляют собой специализированный язык правил.

Например:

```text
IF
    URL matches pattern

THEN
    action
```

Это уже мини-язык:

```text
Condition
+
Action
+
Constraints
```

То есть extension разработчик не пишет произвольный алгоритм.

Он программирует браузер через ограниченный DSL.

---

# Почему это архитектурно интересно

Можно представить:

```text
JavaScript
     ↓
General-purpose programming
```

и:

```text
Declarative API
     ↓
Domain-specific programming
```

Второй вариант позволяет браузеру лучше понимать намерение разработчика.

---

# Browser can optimize intent

Если браузер знает:

```text
"Это правило блокировки request"
```

он может оптимизировать выполнение.

Если браузер получает:

```javascript
function(event) {

    // arbitrary JavaScript
}
```

он гораздо хуже понимает, что именно пытается сделать приложение.

# Declarative architecture и Emerge

Для современного web framework это особенно интересная идея.

Можно представить архитектуру:

```text
HTML
 ↓
Web Platform
 ↓
Declarative Application Model
 ↓
Browser
```

Вместо того чтобы превращать каждое действие пользователя в JavaScript callback:

```text
Event
 ↓
JS
 ↓
DOM mutation
```

часть поведения можно описывать декларативно:

```text
State
+
Rules
+
Effects
```

Manifest V3 показывает, что браузерная платформа сама движется в этом направлении.

---

# Declarative не означает "без программирования"

Это важное уточнение.

Declarative system всё равно является программированием.

Разница:

```text
Imperative:

HOW?
```

против:

```text
Declarative:

WHAT?
```

---

# Сравнение

| Характеристика   | Imperative         | Declarative               |
| ---------------- | ------------------ | ------------------------- |
| Описание         | Как делать         | Что должно происходить    |
| Runtime          | Extension JS       | Browser                   |
| Контроль         | Высокий            | Ограниченный              |
| Гибкость         | Высокая            | Ограниченная              |
| Performance      | Зависит от runtime | Может быть эффективнее    |
| Security surface | Шире               | Уже                       |
| Lifecycle        | Зависит от worker  | Частично browser-managed  |
| Подходит для     | Business logic     | Policies/rules            |
| Сложность        | Выше               | Ниже для подходящих задач |

---

# Архитектурное правило №1

Не начинайте проектирование extension с вопроса:

> Какой JavaScript мне написать?

Начинайте с вопроса:

> **Может ли эта задача быть выражена как browser policy?**

Если да:

```text
Declarative API
```

может быть лучшим решением.

---

# Архитектурное правило №2

Не пытайтесь сделать всё declarative.

Если задача требует:

```text
complex algorithm
+
state
+
external API
+
business logic
```

используйте imperative runtime.

---

# Архитектурное правило №3

Используйте declarative слой как **frontline filter**.

Например:

```text
All browser events
        ↓
Declarative filtering
        ↓
Relevant events
        ↓
Service Worker
        ↓
Application logic
```

Это может значительно сократить объём работы JavaScript runtime.

---

# Архитектурное правило №4

Разделяйте:

```text
Policy
```

и:

```text
Execution
```

Policy:

```text
Что должно происходить?
```

Execution:

```text
Как выполнить сложную работу?
```

Это приводит к гораздо более чистой архитектуре.

---

# Архитектурное правило №5

Учитывайте lifecycle браузера.

В MV3 нужно постоянно задавать вопрос:

```text
Может ли эта задача выполняться
без Service Worker?
```

Если ответ:

```text
Да
```

и существует подходящий declarative API — это часто стоит рассмотреть первым.

# Главный вывод главы

Manifest V3 следует рассматривать не просто как новую версию `manifest.json`.

Это изменение архитектурной модели:

```text
MV2
────────────────────────────
Persistent JS
      ↓
Background page
      ↓
Imperative control
```

превращается в:

```text
MV3
────────────────────────────
Ephemeral JS
      +
Declarative rules
      ↓
Browser-controlled execution
```

Поэтому зрелое MV3 extension должно использовать **два разных типа программирования**:

```text
                    Extension
                       │
          ┌────────────┴────────────┐
          │                         │
     Imperative                 Declarative
          │                         │
          ▼                         ▼
 Service Worker               Browser Rules
          │                         │
          ▼                         ▼
 Business Logic              Browser Policy
          │                         │
          └────────────┬────────────┘
                       ▼
                    Result
```

**Imperative code отвечает за сложность.
Declarative code отвечает за правила.
Browser отвечает за выполнение там, где это возможно.**

Именно такое разделение позволяет строить Manifest V3 extensions, которые меньше зависят от постоянно работающего JavaScript runtime, лучше соответствуют lifecycle браузера и эффективнее используют возможности самой браузерной платформы.

Следующий логический шаг — перейти от философии к конкретным механизмам и разобрать **`declarativeNetRequest`, `declarativeContent` и другие Declarative APIs**, то есть понять, **какие именно части поведения extension можно передать браузеру и как проектировать правила для них**.
