# Глава 11. Background Service Worker

В Manifest V3 произошёл один из наиболее важных архитектурных переходов по сравнению с Manifest V2.

В старой модели background page или background script мог фактически существовать постоянно:

```text
Browser
   │
   ▼
Extension
   │
   ▼
Background Page
   │
   └── постоянно работает
```

В Manifest V3 background-часть extension строится вокруг **Service Worker**:

```text
Browser
   │
   ▼
Extension
   │
   ▼
Service Worker
   │
   ├── event
   ├── execute
   └── suspend
```

Это фундаментально меняет способ проектирования расширения.

Главное правило этой главы:

> **Service Worker Manifest V3 нельзя рассматривать как постоянно работающий background process.**

Он является **event-driven runtime**, который браузер запускает тогда, когда extension необходимо обработать событие.

---

# 11.1. Новая модель background scripts в MV3

В Manifest V2 широко использовалась модель:

```text
Background Page
       │
       │
       │
       ▼
   постоянно
   работает
```

Background page могла существовать всё время жизни браузера.

Например:

```javascript
setInterval(() => {
    checkSomething();
}, 60 * 1000);
```

Такой подход естественно воспринимался как:

```text
Start extension
      ↓
Start background process
      ↓
Process stays alive
```

---

# Manifest V3 меняет эту модель

В MV3:

```text
Extension installed
       │
       ▼
Service Worker registered
       │
       ▼
wait for events
       │
       ▼
event occurs
       │
       ▼
Service Worker starts
       │
       ▼
handle event
       │
       ▼
worker may stop
```

То есть worker не должен рассматриваться как daemon.

---

# Background Service Worker

В manifest указывается:

```json
{
  "manifest_version": 3,
  "background": {
    "service_worker": "service-worker.js"
  }
}
```

Теперь файл:

```text
service-worker.js
```

становится background runtime extension.

---

# Простая архитектура

```text
                    Browser
                       │
                       ▼
                  Extension
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
        Content Scripts      Service Worker
              │                 │
              │                 ├── events
              │                 ├── storage
              │                 ├── messaging
              │                 └── extension APIs
              │
              ▼
             DOM
```

Service Worker становится центральной частью extension backend.

---

# Что делает Service Worker?

Типичные задачи:

* обработка событий;
* messaging;
* работа с `chrome.storage`;
* обработка команд;
* реакция на изменение tabs;
* обработка alarms;
* запуск extension logic;
* координация Content Scripts;
* работа с некоторыми network/API операциями;
* управление состоянием extension.

---

# Что Service Worker обычно не делает?

Service Worker не является хорошим местом для:

```text
UI
DOM manipulation
long-running loops
permanent in-memory state
```

Например:

```javascript
document.querySelector(...)
```

в обычном extension Service Worker не является способом работы с DOM страницы.

DOM находится в другом context — например Content Script.

---

# Разделение ответственности

Хорошая архитектура:

```text
                  Extension
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
     Popup       Content       Service
                   Script       Worker
        │            │            │
        ▼            ▼            ▼
       UI           DOM       Logic/API
```

Service Worker — это не "весь extension".

Он является background/event-driven runtime.

---

# 11.2. Почему Manifest V3 использует Service Worker

Основная идея MV3 — уменьшить постоянное потребление ресурсов extension.

Если extension имеет background page, которая работает постоянно:

```text
Browser
  │
  ├── Tab
  ├── Tab
  ├── Extension
  │      └── Background Page ← always running
  │
  └── ...
```

то extension может постоянно занимать:

* память;
* CPU;
* event-loop resources;
* другие системные ресурсы.

Особенно это плохо для расширений, которые большую часть времени ничего не делают.

---

# Event-driven подход

Вместо:

```text
start
  ↓
run forever
  ↓
wait
  ↓
wait
  ↓
wait
```

используется:

```text
wait
 ↓
event
 ↓
start
 ↓
handle
 ↓
stop
```

Например:

```text
User clicks extension
        │
        ▼
chrome.action.onClicked
        │
        ▼
Service Worker starts
        │
        ▼
handler executes
        │
        ▼
worker becomes inactive
```

---

# Это похоже на serverless architecture

Очень полезная аналогия:

```text
Traditional server:

Process
  ↓
runs continuously
  ↓
handles requests
```

Service Worker:

```text
Event
  ↓
runtime starts
  ↓
handler executes
  ↓
runtime can stop
```

Поэтому MV3 Service Worker концептуально ближе к:

```text
serverless function
```

чем к:

```text
traditional daemon
```

---

# Но это не обычный cloud serverless

Важно не переносить аналогию слишком далеко.

Service Worker работает внутри браузера:

```text
Browser
   └── Extension
          └── Service Worker
```

Он не находится на сервере.

Он использует браузерные extension APIs и browser event system.

---

# Главная цель

Архитектурная идея MV3:

> **Extension должен выполнять background code тогда, когда это необходимо, а не постоянно.**

---

# 11.3. Регистрация background worker

Service Worker регистрируется через:

```json
{
  "background": {
    "service_worker": "service-worker.js"
  }
}
```

Например, структура:

```text
my-extension/
│
├── manifest.json
├── service-worker.js
├── popup.html
├── popup.js
└── content.js
```

---

# Минимальный manifest

```json
{
  "manifest_version": 3,
  "name": "My Extension",
  "version": "1.0.0",
  "background": {
    "service_worker": "service-worker.js"
  }
}
```

---

# Минимальный Service Worker

```javascript
console.log("Service Worker loaded");
```

Но для реального extension полезнее регистрировать обработчики событий.

Например:

```javascript
chrome.runtime.onInstalled.addListener(() => {
    console.log("Extension installed");
});
```

---

# Что означает регистрация?

Важно различать:

```text
registered
```

и:

```text
running
```

Регистрация Service Worker означает, что браузер знает:

> "Для этого extension background runtime представлен этим worker-файлом."

Это **не означает**, что JavaScript постоянно выполняется.

---

# Архитектурная модель

Можно представить:

```text
manifest.json
     │
     │ declares
     ▼
service-worker.js
     │
     │ browser can start
     ▼
Service Worker runtime
```

---

# 11.4. `background.service_worker`

В Manifest V3 используется:

```json
{
  "background": {
    "service_worker": "service-worker.js"
  }
}
```

Поле:

```text
background
```

описывает background configuration.

Поле:

```text
service_worker
```

указывает JavaScript-файл worker.

---

# Пример

```json
{
  "manifest_version": 3,

  "name": "Example Extension",

  "version": "1.0.0",

  "background": {
    "service_worker": "service-worker.js"
  }
}
```

---

# Один Service Worker

В обычной архитектуре MV3 background configuration указывает один Service Worker entry point.

Например:

```text
background.service_worker
            │
            ▼
    service-worker.js
```

Далее этот worker может импортировать другие модули.

---

# ES Modules

Для более крупного extension удобно использовать module architecture:

```json
{
  "background": {
    "service_worker": "service-worker.js",
    "type": "module"
  }
}
```

Тогда:

```javascript
// service-worker.js

import {
    handleMessage
} from "./background/messages.js";
```

Архитектура:

```text
service-worker.js
       │
       ├── messages.js
       ├── tabs.js
       ├── commands.js
       └── storage.js
```

Это особенно важно для production-like extension.

---

# Service Worker — entry point

Можно рассматривать:

```text
service-worker.js
```

как:

```text
main()
```

для background architecture.

Но это не обычная:

```javascript
main();
```

которая запускается один раз и потом работает бесконечно.

Это скорее:

```text
Event registration
       +
Event handlers
```

---

# Пример

```javascript
chrome.runtime.onInstalled.addListener(() => {
    console.log("installed");
});

chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {
        console.log(message);
    }
);

chrome.commands.onCommand.addListener(
    command => {
        console.log(command);
    }
);
```

Service Worker в основном объявляет:

> какие события extension умеет обрабатывать.

---

# 11.5. Event-driven architecture

Теперь мы подошли к главной архитектурной идее MV3.

Service Worker строится вокруг событий.

```text
Event
  │
  ▼
Handler
  │
  ▼
Work
  │
  ▼
Finish
```

---

# Типичные события

Например:

```text
chrome.runtime
chrome.tabs
chrome.commands
chrome.alarms
chrome.action
chrome.contextMenus
chrome.webNavigation
chrome.storage
```

Конкретные API зависят от задачи и разрешений.

---

# `runtime.onInstalled`

Например:

```javascript
chrome.runtime.onInstalled.addListener(() => {
    console.log("Extension installed");
});
```

Браузер сообщает extension:

```text
Extension event
      ↓
onInstalled
      ↓
handler
```

---

# `runtime.onMessage`

Content Script:

```javascript
chrome.runtime.sendMessage({
    type: "GET_DATA"
});
```

Service Worker:

```javascript
chrome.runtime.onMessage.addListener(
    (message, sender, sendResponse) => {
        if (message.type === "GET_DATA") {
            sendResponse({
                value: "hello"
            });
        }
    }
);
```

Архитектура:

```text
Content Script
       │
       │ message
       ▼
Service Worker
       │
       ▼
handler
```

---

# `action.onClicked`

Например:

```javascript
chrome.action.onClicked.addListener(
    tab => {
        console.log("Clicked:", tab.id);
    }
);
```

Событие:

```text
User
 │
 ▼
Extension Action
 │
 ▼
Service Worker
 │
 ▼
onClicked
```

---

# `commands.onCommand`

Если manifest содержит command:

```json
{
  "commands": {
    "open-panel": {
      "suggested_key": {
        "default": "Ctrl+Shift+O"
      },
      "description": "Open panel"
    }
  }
}
```

Service Worker:

```javascript
chrome.commands.onCommand.addListener(
    command => {
        if (command === "open-panel") {
            // ...
        }
    }
);
```

---

# Event-driven = no permanent loop

Плохая архитектурная идея:

```javascript
setInterval(() => {
    doWork();
}, 1000);
```

Почему?

Потому что концепция Service Worker:

```text
event → work → finish
```

а не:

```text
start → infinite loop
```

Для планируемой работы следует рассматривать соответствующие event-based APIs, например `chrome.alarms`.

---

# `chrome.alarms`

Например:

```javascript
chrome.alarms.create("sync", {
    periodInMinutes: 30
});
```

и:

```javascript
chrome.alarms.onAlarm.addListener(
    alarm => {
        if (alarm.name === "sync") {
            syncData();
        }
    }
);
```

Получаем:

```text
Alarm
  ↓
Worker starts
  ↓
onAlarm
  ↓
syncData()
  ↓
finish
```

Это значительно ближе к модели MV3.

---

# Event-driven architecture как конечный автомат

Полезно представить worker как state machine:

```text
             ┌─────────────┐
             │   INACTIVE  │
             └──────┬──────┘
                    │
                  event
                    │
                    ▼
             ┌─────────────┐
             │   STARTING  │
             └──────┬──────┘
                    │
                    ▼
             ┌─────────────┐
             │   RUNNING   │
             └──────┬──────┘
                    │
                 finish
                    │
                    ▼
             ┌─────────────┐
             │   INACTIVE  │
             └─────────────┘
```

Это гораздо лучше отражает реальную архитектурную модель, чем:

```text
RUNNING forever
```

---

# 11.6. Startup

Service Worker запускается браузером, когда необходимо обработать соответствующее событие.

Например:

```text
User action
      │
      ▼
Browser
      │
      ▼
Extension event
      │
      ▼
Start Service Worker
      │
      ▼
Execute handler
```

---

# Startup ≠ installation

Очень важно различать:

```text
Extension installation
```

и:

```text
Service Worker startup
```

Extension может быть установлен:

```text
Monday
```

а Service Worker может быть запущен:

```text
Tuesday
```

из-за события.

---

# Startup может происходить много раз

Например:

```text
09:00 → worker starts
09:00 → handles event
09:01 → worker stops

10:00 → worker starts
10:00 → handles event
10:01 → worker stops

11:00 → worker starts
...
```

Поэтому архитектура должна выдерживать повторные startup cycles.

---

# Что происходит при startup?

JavaScript-файл Service Worker загружается.

Например:

```javascript
console.log("worker startup");
```

и затем регистрируются event handlers:

```javascript
chrome.runtime.onMessage.addListener(...);
chrome.commands.onCommand.addListener(...);
```

---

# Поэтому handlers должны регистрироваться при загрузке

Правильный подход:

```javascript
chrome.runtime.onMessage.addListener(
    handleMessage
);
```

а не:

```javascript
// register later after some
// long-running initialization
```

Service Worker должен быстро подготовить event handlers.

---

# Startup должен быть быстрым

Архитектурно полезно придерживаться:

```text
Startup
  ↓
register handlers
  ↓
minimal initialization
  ↓
wait for event
```

Не следует превращать startup в огромный bootstrap process.

---

# 11.7. Suspension

После обработки событий Service Worker может стать неактивным.

Упрощённо:

```text
RUNNING
   │
   │ no more work
   ▼
INACTIVE
```

Это принципиально отличается от background page.

---

# Что такое suspension?

Suspension означает, что браузер прекращает выполнение worker, когда он больше не нужен.

Это позволяет экономить ресурсы.

---

# Почему это важно разработчику?

Потому что нельзя думать:

```javascript
let counter = 0;
```

как о надёжном persistent storage.

Например:

```javascript
let counter = 0;

counter++;

console.log(counter);
```

Сегодня вы можете увидеть:

```text
1
```

Затем worker будет остановлен.

При следующем запуске:

```text
counter = 0
```

снова.

---

# In-memory state

Следовательно:

```text
Service Worker memory
```

является:

> **временным runtime state.**

Это не persistent storage.

---

# Где хранить persistent state?

Если данные должны переживать worker lifecycle, необходимо использовать подходящее постоянное хранилище.

Например:

```text
chrome.storage
IndexedDB
```

в зависимости от характера данных.

Типичный вариант:

```javascript
await chrome.storage.local.set({
    counter: 42
});
```

Затем при следующем запуске:

```javascript
const {
    counter
} = await chrome.storage.local.get(
    "counter"
);
```

---

# Memory vs Storage

Очень важно различать:

```text
RAM / Worker memory
        │
        │ temporary
        ▼
   lost on restart
```

и:

```text
chrome.storage
        │
        │ persistent
        ▼
available after restart
```

---

# 11.8. Termination

После периода бездействия browser runtime может завершить Service Worker.

Упрощённо:

```text
Service Worker
      │
      ▼
No active work
      │
      ▼
Termination
```

После termination:

```text
JavaScript heap
      ↓
gone
```

Поэтому:

```javascript
let state = {
    user: ...
};
```

не является постоянным состоянием extension.

---

# Очень важная ошибка

Плохой код:

```javascript
let currentUser = null;

chrome.runtime.onMessage.addListener(
    async message => {
        if (message.type === "LOGIN") {
            currentUser = message.user;
        }
    }
);
```

Предположение:

```text
currentUser
```

будет существовать всегда — ошибочно.

Worker может завершиться.

---

# Правильнее

Сохранять критически важное состояние:

```javascript
await chrome.storage.local.set({
    currentUser: user
});
```

а затем при необходимости читать:

```javascript
const {
    currentUser
} = await chrome.storage.local.get(
    "currentUser"
);
```

---

# 11.9. Restart

После termination Service Worker может снова быть запущен.

То есть lifecycle:

```text
START
  │
  ▼
RUN
  │
  ▼
SUSPEND / TERMINATE
  │
  ▼
STOPPED
  │
  │ new event
  ▼
START
```

Это нормальный lifecycle, а не ошибка.

---

# Extension должен быть restart-safe

Очень полезный architectural principle:

> **Любой Service Worker должен быть готов к тому, что его runtime будет запущен заново в любой момент между событиями.**

---

# Что означает restart-safe?

Например, worker не должен рассчитывать:

```javascript
let initialized = true;
```

на то, что эта переменная обязательно будет существовать.

Вместо этого:

```text
persistent state
       ↓
storage
       ↓
load on demand
```

---

# Idempotency

Для background logic особенно полезно понятие **idempotency**.

Допустим:

```javascript
syncData();
```

может быть вызвана после restart.

Желательно, чтобы повторное выполнение не приводило к повреждению состояния.

Например:

```text
sync
sync
sync
```

не должно создавать:

```text
duplicate data
duplicate records
duplicate side effects
```

если операция по смыслу должна быть повторяемой.

---

# Пример плохой архитектуры

```javascript
let processed = [];

chrome.runtime.onMessage.addListener(
    message => {
        if (!processed.includes(message.id)) {
            process(message);
            processed.push(message.id);
        }
    }
);
```

Проблема:

```text
processed
```

находится в памяти worker.

После restart:

```text
processed = []
```

и сообщение может быть обработано повторно.

---

# Более надёжная архитектура

Persistent state:

```text
chrome.storage
       │
       ▼
processed IDs
```

или другая подходящая persistence mechanism.

Тогда:

```text
Worker restart
      ↓
load state
      ↓
continue
```

---

# Restart не должен быть исключением

В традиционном backend можно иногда считать:

```text
process restart
```

редким событием.

В MV3 это часть нормальной архитектуры.

Поэтому нужно проектировать:

```text
start
stop
start
stop
start
```

как нормальный lifecycle.

---

# 11.10. Почему нельзя рассчитывать на постоянное состояние

Это, пожалуй, самый важный практический вывод главы.

Рассмотрим:

```javascript
let cache = {};
let currentTab = null;
let user = null;
```

Все эти значения находятся в:

```text
Service Worker memory
```

и могут исчезнуть после завершения worker.

---

# Что можно хранить в памяти?

В памяти отлично подходят:

```text
temporary cache
computed values
current operation
short-lived state
```

Например:

```javascript
const cache = new Map();
```

может быть полезным для оптимизации.

Но нельзя полагаться на него как на единственный источник истины.

---

# Source of Truth

Хорошая архитектура:

```text
             Service Worker
                   │
          ┌────────┴────────┐
          │                 │
      RAM cache        Persistent state
          │                 │
          ▼                 ▼
      temporary        chrome.storage
```

То есть:

```text
RAM
=
cache
```

а:

```text
storage
=
state
```

---

# Неправильная модель

```text
Service Worker
      │
      ▼
   variables
      │
      ▼
  application state
```

Проблема:

```text
Worker terminated
      ↓
state lost
```

---

# Правильная модель

```text
Persistent Storage
        │
        │ source of truth
        ▼
Service Worker
        │
        │ temporary cache
        ▼
      RAM
```

# Service Worker как stateless runtime

В идеале background architecture можно сделать почти stateless:

```text
             Event
               │
               ▼
        Service Worker
               │
        ┌──────┴──────┐
        │             │
       read          write
        │             │
        ▼             ▼
     Storage        Storage
```

Тогда worker становится вычислительным runtime:

```text
Input
  ↓
Read state
  ↓
Compute
  ↓
Write state
  ↓
Finish
```

---

# Это очень похоже на functional architecture

Например:

```text
State + Event
      │
      ▼
  Handler
      │
      ▼
New State
```

Вместо:

```text
Long-running object
with mutable state
```

# Service Worker и Content Script

Одна из наиболее важных архитектур MV3:

```text
                 Web Page
                    │
                    ▼
             Content Script
                    │
                    │ message
                    ▼
             Service Worker
                    │
              ┌─────┼─────┐
              ▼     ▼     ▼
           Storage APIs Network
```

Content Script занимается:

```text
DOM
page interaction
events
data extraction
```

Service Worker:

```text
background logic
state
coordination
extension APIs
```

# Service Worker и Popup

Popup также может общаться с worker:

```text
Popup
  │
  │ chrome.runtime
  ▼
Service Worker
```

Но есть важное отличие:

> Popup имеет UI lifecycle и закрывается, когда пользователь перестаёт с ним взаимодействовать.

Поэтому Popup тоже не должен использоваться как persistent background state.

# Главные ошибки разработчиков

### Ошибка 1. Считать worker постоянно работающим

```javascript
let state = {};
```

Нельзя считать этот state permanent.

---

### Ошибка 2. Использовать infinite loops

```javascript
while (true) {
    ...
}
```

Service Worker не предназначен для такой архитектуры.

---

### Ошибка 3. Использовать `setInterval()` как главный scheduler

Для периодической работы следует рассматривать event-driven механизмы, прежде всего `chrome.alarms`.

---

### Ошибка 4. Хранить важные данные только в RAM

```javascript
let userSettings = {};
```

Если данные должны переживать restart, сохраняйте их в persistent storage.

---

### Ошибка 5. Делать огромный startup

```text
worker startup
   ↓
load everything
   ↓
initialize everything
   ↓
build entire application
```

Лучше:

```text
worker startup
   ↓
register handlers
   ↓
wait
```

и загружать необходимые данные по мере необходимости.

---

### Ошибка 6. Считать restart exception

Restart — нормальная часть lifecycle.

# Архитектурный принцип

Из всего этого следует важный принцип Manifest V3:

> **Service Worker должен быть designed for disappearance.**

То есть хороший Service Worker должен нормально работать, даже если браузер делает:

```text
start
stop
start
stop
start
```

# Практическая формула

При проектировании каждого background operation задавайте четыре вопроса:

```text
1. Какое событие запускает операцию?

2. Какие данные нужны для её выполнения?

3. Где эти данные должны храниться постоянно?

4. Что произойдёт, если worker исчезнет
   сразу после завершения операции?
```

Если на эти вопросы есть хорошие ответы, архитектура обычно хорошо соответствует модели MV3.

```text

```

а как:

```text
"event-driven background runtime"
```

Его модель:

```text
             EVENT
               │

        ┌──────────────┐
        │   START      │
        └──────┬───────┘
               │
               ▼

        │              │

               ▼
        ┌──────────────┐

        └──────┬───────┘
```

## Главные выводы главы

1. **Manifest V3 заменяет постоянную background page модель Service Worker-моделью.**

2. **Service Worker является event-driven runtime**, а не постоянно работающим процессом.

3. `background.service_worker` указывает entry point background runtime:

```json
{
  "background": {
    "service_worker": "service-worker.js"
  }
}
```

4. Service Worker может **запускаться, приостанавливаться и завершаться** в течение жизненного цикла extension.

5. **Нельзя рассчитывать на постоянство JavaScript memory.**

```javascript
let state = {};
```

— это только временное runtime state.

6. Persistent state необходимо хранить в подходящем persistent storage.

7. Service Worker должен быть **restart-safe**.

8. Основной паттерн MV3:

```text
Event
 ↓
Start
 ↓
Handle
 ↓
Persist
 ↓
Finish
 ↓
Worker may terminate
```

9. Не следует строить Service Worker вокруг бесконечных циклов или предположения, что background runtime всегда существует.

10. Самая полезная ментальная модель:

> **Service Worker — это не сервер, который постоянно работает внутри расширения. Это event-driven вычислительный слой расширения, который браузер запускает тогда, когда extension необходимо выполнить background work.**

Именно понимание этой модели будет критически важно в следующих главах — особенно при изучении **messaging, `chrome.runtime`, `chrome.storage`, alarms, tabs, commands и архитектуры взаимодействия Content Script ↔ Service Worker**.
