# Глава 30. Web Platform внутри Extension

Manifest V3 extension — это не отдельный язык и не отдельный runtime, построенный с нуля.

В основе расширения находится **Web Platform**.

HTML, CSS, JavaScript, DOM, Fetch, Web Crypto, IndexedDB, Web Components, ES Modules и многие другие технологии доступны extension-разработчику непосредственно из браузера.

Extension APIs добавляют к этой платформе специальные возможности:

```text
┌───────────────────────────────────────────┐
│              Extension APIs               │
│  tabs • storage • runtime • scripting     │
│  alarms • sidePanel • commands • DNR      │
├───────────────────────────────────────────┤
│              Web Platform                 │
│  HTML • CSS • JS • DOM • Fetch            │
│  IndexedDB • Web Crypto • Workers         │
│  Web Components • ESM • Web APIs          │
├───────────────────────────────────────────┤
│                 Browser                   │
│        Chromium / Firefox / Edge          │
└───────────────────────────────────────────┘
```

Это принципиально важная идея.

> **Browser extension — это Web application + extension capabilities.**

Поэтому современный разработчик Manifest V3 должен хорошо знать не только `chrome.*` APIs, но и саму Web Platform.

# 30.1. DOM

DOM — Document Object Model — представляет HTML-документ как дерево объектов.

Например:

```html
<button id="save">
    Save
</button>
```

можно получить:

```javascript
const button =
    document.getElementById("save");
```

и изменить:

```javascript
button.textContent = "Saved";
```

DOM является стандартным Web Platform API.

Для его использования не требуется специальный extension API.

---

## DOM в Extension Page

Например, Popup:

```text
popup.html
    ↓
DOM
    ↓
popup.js
```

может использовать:

```javascript
document.querySelector(...)
document.createElement(...)
element.append(...)
element.remove()
```

точно так же, как обычная HTML-страница.

---

## DOM в Content Script

Content Script также может работать с DOM страницы:

```javascript
const title =
    document.querySelector("h1");
```

Это одна из основных причин существования Content Scripts.

Архитектура:

```text
Web Page
   │
   ├── HTML
   ├── CSS
   └── DOM
        ▲
        │
   Content Script
```

Однако Content Script работает в отдельном JavaScript environment — isolated world.

Поэтому:

```text
DOM
  ↓
shared

JavaScript globals
  ↓
isolated
```

Это различие было подробно рассмотрено в предыдущих главах.

---

## DOM API

В extension доступны стандартные API:

```javascript
document.querySelector()
document.querySelectorAll()
document.createElement()
document.createTextNode()
element.append()
element.remove()
element.replaceWith()
element.addEventListener()
```

и многие другие.

---

## MutationObserver

Extension может наблюдать за изменениями DOM:

```javascript
const observer =
    new MutationObserver(
        mutations => {
            console.log(mutations);
        }
    );

observer.observe(
    document.body,
    {
        childList: true,
        subtree: true
    }
);
```

Это особенно полезно для Content Scripts, работающих с динамическими SPA.

Например:

```text
Page
 ↓
React / Vue / Angular
 ↓
DOM changes
 ↓
MutationObserver
 ↓
Extension
```

---

## IntersectionObserver

Можно использовать:

```javascript
const observer =
    new IntersectionObserver(entries => {
        // ...
    });
```

Например, чтобы обнаружить появление элемента в viewport.

---

## ResizeObserver

Также доступен:

```javascript
const observer =
    new ResizeObserver(entries => {
        // ...
    });
```

Таким образом, extension может использовать современную модель наблюдения за DOM без собственного framework runtime.

---

# 30.2. Fetch

`fetch()` относится к Web Platform, а не к Extension API.

Это означает, что extension может использовать стандартный API:

```javascript
const response =
    await fetch(url);

const data =
    await response.json();
```

---

## Fetch в разных contexts

Fetch может использоваться в различных extension contexts, но сетевые ограничения зависят от context.

Например:

```text
Popup
   ↓
fetch()

Options
   ↓
fetch()

Side Panel
   ↓
fetch()

Service Worker
   ↓
fetch()

Content Script
   ↓
fetch()
```

При этом нельзя считать все эти случаи полностью эквивалентными.

Нужно учитывать:

```text
origin
CORS
host permissions
credentials
cookies
security policy
```

---

## Extension network layer

В архитектуре большого расширения разумно отделять Web Platform API от application logic:

```text
Application
     ↓
API Client
     ↓
fetch()
     ↓
Network
```

Тогда при необходимости можно централизовать:

```text
authentication
retry
timeouts
serialization
logging
error handling
```

---

# 30.3. Web Storage

Web Platform предоставляет Web Storage API:

```javascript
localStorage
sessionStorage
```

Например:

```javascript
localStorage.setItem(
    "theme",
    "dark"
);
```

и:

```javascript
const theme =
    localStorage.getItem("theme");
```

---

## Но Web Storage и `chrome.storage` — разные системы

Это очень важно.

```text
Web Platform
    │
    ├── localStorage
    └── sessionStorage

Extension Platform
    │
    └── chrome.storage
```

`localStorage` не является заменой:

```javascript
chrome.storage.local
```

---

## Когда использовать Web Storage

Web Storage может быть удобен для локального состояния конкретной extension page.

Например:

```text
popup.html
    ↓
localStorage
```

Но для extension-wide state обычно лучше рассматривать:

```text
chrome.storage
```

потому что Popup, Service Worker, Options и другие contexts должны иметь согласованную модель состояния.

---

## `sessionStorage`

`sessionStorage` предназначен для состояния текущего browsing context.

Это делает его ещё менее подходящим для глобального состояния extension.

---

## Архитектурное правило

Если состояние принадлежит:

```text
конкретному document
```

можно рассматривать:

```text
localStorage
sessionStorage
```

Если состояние принадлежит:

```text
extension
```

обычно следует рассматривать:

```text
chrome.storage
```

---

# 30.4. IndexedDB

IndexedDB — полноценная клиентская database API Web Platform.

В отличие от `localStorage`, IndexedDB предназначена для структурированного хранения больших объёмов данных.

Концептуально:

```text
localStorage
    ↓
key → string

IndexedDB
    ↓
database
 ├── object stores
 ├── indexes
 ├── transactions
 └── structured data
```

---

## Пример

```javascript
const request =
    indexedDB.open(
        "my-extension",
        1
    );
```

Затем создаётся object store:

```javascript
request.onupgradeneeded = event => {

    const db =
        event.target.result;

    db.createObjectStore(
        "items",
        {
            keyPath: "id"
        }
    );
};
```

---

## Structured data

IndexedDB может хранить объекты:

```javascript
{
    id: 1,
    title: "Example",
    createdAt: Date.now()
}
```

без необходимости вручную превращать всё в JSON strings.

---

## IndexedDB и Service Worker

IndexedDB особенно интересна для MV3, потому что Service Worker является ephemeral runtime.

Нельзя рассчитывать:

```text
Service Worker global memory
```

как на постоянное хранилище.

Вместо этого:

```text
Service Worker
      │
      ▼
IndexedDB
      │
      ▼
Persistent application data
```

---

## IndexedDB vs `chrome.storage`

У этих механизмов разные задачи.

|                           | `chrome.storage` | IndexedDB |
| ------------------------- | ---------------- | --------- |
| Простота                  | высокая          | средняя   |
| Settings                  | отлично          | избыточно |
| Structured data           | ограниченно      | отлично   |
| Большие данные            | ограниченно      | лучше     |
| Индексы                   | нет              | да        |
| Transactions              | ограниченно      | да        |
| Extension synchronization | `sync`           | нет       |
| Database model            | нет              | да        |

Поэтому можно использовать:

```text
chrome.storage
    ↓
configuration / settings / state

IndexedDB
    ↓
large structured application data
```

---

# 30.5. Web Workers

Web Platform предоставляет Web Workers.

Worker позволяет выполнять JavaScript отдельно от основного UI thread.

Например:

```javascript
const worker =
    new Worker(
        "./worker.js",
        {
            type: "module"
        }
    );
```

После этого:

```javascript
worker.postMessage({
    type: "PROCESS",
    data
});
```

Worker может отправить результат:

```javascript
self.postMessage({
    type: "RESULT",
    value
});
```

---

## Зачем Worker extension?

Например, extension получает большой объём данных:

```text
Content Script
      ↓
large document
      ↓
parsing
      ↓
analysis
```

Если выполнить тяжёлую работу непосредственно в UI context:

```text
UI
 ↓
CPU-heavy JavaScript
 ↓
freeze
```

это ухудшит UX.

Worker позволяет:

```text
UI
 │
 ├──────────────→ Worker
 │                   │
 │              heavy computation
 │                   │
 └──── result ←──────┘
```

---

## Worker ≠ Service Worker

Названия похожи, но это разные концепции.

### Web Worker

Предназначен прежде всего для:

```text
background computation
```

### Service Worker

В Manifest V3 используется как:

```text
event-driven extension runtime
```

То есть:

```text
Web Worker
    ↓
computation

Extension Service Worker
    ↓
extension orchestration
```

---

## WebAssembly

Web Worker также может использоваться вместе с WebAssembly:

```text
Extension
    ↓
Web Worker
    ↓
WASM
    ↓
CPU-intensive processing
```

Например:

```text
parsing
compression
image processing
cryptography
data transformation
```

Это особенно интересная архитектура для вычислительно тяжёлых extension.

---

# 30.6. Web Crypto

Web Crypto API предоставляет криптографические примитивы.

Например:

```javascript
crypto.getRandomValues(
    new Uint8Array(32)
);
```

---

## Генерация случайных данных

Можно получить криптографически стойкие случайные значения:

```javascript
const bytes =
    crypto.getRandomValues(
        new Uint8Array(16)
    );
```

Это гораздо правильнее для security-sensitive randomness, чем:

```javascript
Math.random()
```

---

## SubtleCrypto

Более сложные операции доступны через:

```javascript
crypto.subtle
```

Например:

```javascript
const digest =
    await crypto.subtle.digest(
        "SHA-256",
        data
    );
```

---

## Hashing

Можно вычислить SHA-256:

```javascript
const hash =
    await crypto.subtle.digest(
        "SHA-256",
        new TextEncoder().encode(
            "hello"
        )
    );
```

---

## Encryption

Web Crypto поддерживает различные криптографические операции, включая encryption/decryption.

Концептуально:

```text
Plaintext
    ↓
Crypto API
    ↓
Ciphertext
```

и:

```text
Ciphertext
    ↓
Crypto API
    ↓
Plaintext
```

---

## Web Crypto не превращает extension в secure enclave

Очень важно не переоценивать эту технологию.

Если ключ находится внутри extension:

```text
Extension
 ├── code
 └── key
```

пользователь потенциально может исследовать extension runtime.

Web Crypto защищает операции криптографии, но не делает client-side secret недоступным владельцу устройства.

---

## Где Web Crypto полезен

Например:

```text
hashing
key generation
signatures
encryption
secure random values
```

и для реализации security protocols на client side.

---

# 30.7. Web Components

Web Components позволяют создавать собственные HTML elements.

Например:

```javascript
class UserCard
    extends HTMLElement {

    connectedCallback() {
        this.innerHTML = `
            <strong>
                User
            </strong>
        `;
    }
}

customElements.define(
    "user-card",
    UserCard
);
```

Теперь:

```html
<user-card></user-card>
```

является полноценным custom element.

---

## Почему Web Components интересны для extensions

Extension UI часто состоит из небольших независимых компонентов:

```text
<extension-toolbar>
<extension-settings>
<extension-user-card>
<extension-status>
```

Web Components позволяют создавать их без React, Vue или другого UI framework.

---

## Shadow DOM

Можно использовать:

```javascript
this.attachShadow({
    mode: "open"
});
```

После этого компонент получает собственное DOM subtree.

```text
Document
│
├── normal DOM
│
└── <my-component>
       │
       └── Shadow DOM
```

---

## CSS isolation

Shadow DOM позволяет изолировать стили компонента:

```text
Page CSS
    │
    X
    │
Shadow DOM
    │
Component CSS
```

Это особенно полезно для UI, который вставляется Content Script в существующую страницу.

---

## Content Script + Web Component

Например:

```text
Content Script
      ↓
create custom element
      ↓
Shadow DOM
      ↓
Extension UI
```

Получается удобная архитектура:

```text
Host Page
    │
    ├── its DOM
    ├── its CSS
    └── its JavaScript
         │
         X
         │
    Shadow DOM
         │
    Extension UI
```

---

# 30.8. CSS

CSS в extension работает как стандартная Web Platform technology.

Можно использовать:

```css
.container {
    display: grid;
    gap: 1rem;
}
```

современные layout systems:

```text
Flexbox
Grid
Container Queries
```

а также:

```text
transitions
animations
custom properties
media queries
```

---

## CSS Modules?

Сам браузер не предоставляет CSS Modules в том смысле, в котором это делают bundlers.

Но extension может использовать обычные:

```html
<link
    rel="stylesheet"
    href="styles.css">
```

и:

```javascript
const sheet =
    new CSSStyleSheet();
```

---

## Constructable Stylesheets

Современная Web Platform позволяет:

```javascript
const sheet =
    new CSSStyleSheet();

sheet.replaceSync(`
    :host {
        display: block;
    }
`);
```

и использовать stylesheet внутри Shadow DOM.

Это особенно удобно для Web Components.

---

## CSS custom properties

Можно использовать:

```css
:root {
    --extension-primary: #2563eb;
}
```

и:

```css
.button {
    color: var(--extension-primary);
}
```

Это удобно для темизации extension.

---

## Content Script CSS

Content Script может добавлять CSS в страницу.

Но нужно учитывать:

```text
host page styles
extension styles
specificity
Shadow DOM
```

Иначе CSS extension может конфликтовать с CSS сайта.

# 30.9. ESM

ES Modules — одна из наиболее важных возможностей современной Web Platform.

Вместо одного огромного:

```text
background.js
```

можно построить модульную систему:

```text
background/
├── service-worker.js
├── api.js
├── auth.js
├── storage.js
└── messaging.js
```

---

## Import

```javascript
import {
    getUser
} from "./api.js";
```

---

## Export

```javascript
export async function getUser() {
    // ...
}
```

---

## ESM в extension

Для extension contexts, поддерживающих module scripts, можно использовать:

```html
<script
    type="module"
    src="./app.js">
</script>
```

---

## Service Worker

Manifest V3 Service Worker может быть объявлен как module:

```json
{
    "background": {
        "service_worker": "background.js",
        "type": "module"
    }
}
```

Теперь:

```javascript
import {
    initialize
} from "./core.js";
```

становится частью архитектуры background runtime.

---

## Почему ESM важен

ESM позволяет разделить:

```text
application
    │
    ├── core
    ├── network
    ├── storage
    ├── auth
    ├── messaging
    └── UI
```

вместо:

```text
one giant script
```

---

# Dynamic import

Web Platform также предоставляет:

```javascript
const module =
    await import(
        "./heavy-module.js"
    );
```

Это позволяет загружать код только тогда, когда он действительно нужен.

---

## Lazy loading

Например:

```text
Extension startup
      ↓
small core
      ↓
user activates feature
      ↓
dynamic import
      ↓
feature module
```

Это соответствует философии MV3:

> Загружать и выполнять только необходимый код.

---

# ESM + Web Workers

Можно создавать module workers:

```javascript
const worker =
    new Worker(
        "./worker.js",
        {
            type: "module"
        }
    );
```

Это позволяет строить полностью модульную вычислительную подсистему.


## Extension Platform

```text

```

---

# Два уровня API

Очень полезно мыслить следующим образом:

```text
                  Extension
                      │
          ┌───────────┴───────────┐
          │                       │
          ▼                       ▼
    Web Platform           Extension APIs
          │                       │
          │                       │
     DOM / CSS               tabs
     Fetch                   storage
     IndexedDB               runtime
     Workers                 scripting
     Crypto                  alarms
     Web Components          sidePanel
     ESM                     action
     WASM                    commands
          │                       │
          └───────────┬───────────┘
                      ▼
                   Browser
```

---

# Web Platform не требует `chrome.*`

Например:

```javascript
document.querySelector(...)
```

не является:

```javascript
chrome.document.querySelector(...)
```

Потому что DOM — стандартный Web API.

То же самое:

```javascript
fetch(...)
```

а не:

```javascript
chrome.fetch(...)
```

И:

```javascript
indexedDB.open(...)
```

а не:

```javascript
chrome.indexedDB.open(...)
```

---

# Extension APIs добавляют capabilities

Например, Web Platform позволяет:

```javascript
fetch(...)
```

а Extension API позволяет получить информацию о вкладках:

```javascript
chrome.tabs.query(...)
```

Web Platform предоставляет:

```javascript
document
```

а Extension API позволяет выполнять определённые операции с extension-controlled contexts и tabs через соответствующие APIs.

---

# Capability model

Можно представить extension как комбинацию:

```text
JavaScript
   +
Web Platform
   +
Extension capabilities
```

То есть:

```text
Extension
   =
Web application
   +
Browser privileges
```

---

# Почему это архитектурно важно

Если задача решается стандартным Web API:

```text
DOM
CSS
Fetch
IndexedDB
Web Crypto
Web Components
Web Workers
```

не следует автоматически искать:

```text
chrome.*
```

---

# Platform First

Например, вам нужен компонент UI.

Не обязательно сразу:

```text
React
```

Можно использовать:

```text
Web Components
Shadow DOM
CSS
ESM
```

Вам нужен persistent database?

Можно рассмотреть:

```text
IndexedDB
```

а не автоматически добавлять стороннюю database abstraction.

Нужно выполнить тяжёлое вычисление?

Можно рассмотреть:

```text
Web Worker
WASM
```

Нужно получить криптографически стойкий random value?

```javascript
crypto.getRandomValues(...)
```

Нужно загрузить данные?

```javascript
fetch(...)
```

---

# Это приводит к важному принципу

> **Сначала Web Platform, затем Extension API, и только после этого — сторонний framework или library.**

Например:

```text
Задача
  ↓
Есть Web API?
  │
  ├── Да → использовать Web Platform
  │
  └── Нет
       ↓
Есть Extension API?
       │
       ├── Да → использовать Extension API
       │
       └── Нет
            ↓
       library / framework / backend
```

# Web Platform как фундамент Emerge

Для архитектуры, которую мы рассматриваем в рамках Emerge, это особенно важно.

# Extension без framework

Полностью рабочее расширение может быть создано без React, Vue, Angular или другого UI framework:

```text
HTML
CSS
ESM
DOM
Web Components
Fetch
IndexedDB
Service Worker
chrome.* APIs
```

Например:

```text
src/
├── manifest.json
├── background/
│   └── service-worker.js
├── popup/
│   ├── popup.html
│   ├── popup.js
│   └── popup.css
├── components/
│   └── user-card.js
├── network/
│   └── api.js
├── storage/
│   └── database.js
└── content/
    └── content.js
```

Это уже полноценное application architecture.

# Web Platform + MV3

Наиболее интересная архитектура выглядит так:

```text
                 Application
                     │
                   Emerge
                     │
        ┌────────────┴────────────┐
        │                         │
 Web Platform              Extension APIs
        │                         │
 ┌──────┼───────────┐       ┌─────┼─────────┐
 │      │           │       │     │         │
DOM   Fetch       ESM     tabs storage   runtime
 │      │           │       │     │         │
CSS  IndexedDB    Workers  action alarms scripting
 │      │           │
Web Components   Web Crypto
 │
WASM
```

Это значительно более мощная модель, чем представление:

```text
Chrome Extension
=
chrome.* APIs
```

# Главный архитектурный вывод

Manifest V3 не следует изучать как набор:

```text
chrome.*
```

API.

Правильнее представлять его как **двухуровневую платформу**:

```text
┌─────────────────────────────────────┐
│         Extension capabilities      │
│                                     │
│ runtime • tabs • storage • action   │
│ scripting • sidePanel • alarms      │
│ permissions • DNR • commands        │
├─────────────────────────────────────┤
│             Web Platform            │
│                                     │
│ HTML • CSS • JS • DOM • Fetch       │
│ IndexedDB • Workers • Crypto        │
│ Web Components • ESM • WASM         │
├─────────────────────────────────────┤
│              Browser                │
└─────────────────────────────────────┘
```

Именно **Web Platform является фундаментом**, а Manifest V3 предоставляет дополнительные browser capabilities поверх него.

Поэтому хороший разработчик расширений должен уметь ответить на два вопроса для каждой новой задачи:

1. **Можно ли решить её стандартными Web APIs?**
2. **Если нельзя — какой Extension API предоставляет необходимую capability?**

И только после этого имеет смысл выбирать framework, библиотеку или собственный runtime.

> **Manifest V3 не заменяет Web Platform. Он расширяет её возможностями, специфичными для браузерных расширений.**

Это понимание становится особенно важным для следующей части учебника: когда мы начнём рассматривать реальные архитектуры расширений, станет видно, что большая часть application code может оставаться обычным современным Web Platform code, а `chrome.*` APIs образуют относительно тонкий слой интеграции с браузером.
